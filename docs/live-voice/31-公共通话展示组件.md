## 1. 一句话定位

**把 nook 与对话框各自手写的「通话字幕」渲染抽成一个 props 驱动的展示组件 `LiveCallTranscript`（`NEW`），共享字幕渲染次序、空态规则、说话人标签与文案键；两处改为使用它，行为不变；角色栏作为第三处直接复用，从第一天起就不产生第三份实现。**

三条不变量：

1. **组件不读 store**（`30` §3.2 冻结 4）：`lines` 与 `call` 由载体传入。
2. **组件不碰生命周期**（`30` §3.2 冻结 4）：不调 `start`/`stop`、不发请求、不假定 `owner`、不渲染挂断按钮。
3. **组件只碰字幕**：状态条与挂断按钮（对话框的 `.call-bar`）**留在载体**——它们按 `phase` 分支并触发 `stop`，属生命周期，不是展示。

**为什么这件事本身很小**：两处既有实现的**结构性差异为零**——次序、空态条件、四条来源的判据逐字符相同（§2 的逐行对照）。真正不同的只有**样式载体**（Tailwind vs `index.css` 手工类）与**文案轨道**（`UI_COPY` vs `messages.json`）。所以这不是「设计一个组件」，是「把一份已经存在的结构提出来，并选定它的样式与文案归属」。

### 2.3 三处实测差异的性质

**D1 — 挂载门不同，且不是组件的职责。** nook 用 `callInProgress`（无 error 态），对话框用 `callVisible`（含 error 态，`12 §3.6` 的硬修正：错误态必须留在通话版面上，否则 `.dialogue-call-alert` 随版面消失）。`30` §3.2 冻结 4 把「共享什么」限定为**字幕渲染次序 / 空态 / 说话人标签结构 / 文案键**，**不含挂载门**。⇒ **门留在载体**；角色栏的门由 `32` 定。

**D2 — 空态文案不同，必须收敛为对话框的规则。** nook 恒定显示 `Connecting…`：在 `phase==='live'` 但尚无任何台词的窗口里（真人语音往返有数百毫秒），nook 会显示「正在连接…」——**与同屏状态条自相矛盾**（nook 的 `call` lane 在 `live` 时显示 `On a call`，`:722-730`）。对话框的 `connecting ? Connecting… : Listening…`（`:1009`）是对的。⇒ **公共组件采用对话框规则**；这是 nook 的**一处可见行为修正**（§4.4-C1 落实，§6.1-A4 钉住）。

**D3 — 说话人样式三种写法**（nook 已提交/流式 = `font-serif font-bold text-rust`；nook 语音/玩家 = `font-mono`；对话框 = 统一 `.call-speaker`）。三者语义相同、字形不同。`30` §3.2 **不要求共享样式**（共享清单为「字幕渲染次序、空态、说话人标签结构、文案键」——**无「样式」**）。⇒ 结构共享，样式由 §3.3 的方案决定。

### 3.2 props 签名（`NEW`）

```ts
import type { LiveCallLines, LiveCallState } from '../../lib/live-call-store.js';

export interface LiveCallTranscriptProps {
  /**
   * 角色真实台词（已提交 + 流式），由载体从 store 快照取出后传入。
   * 契约 30 §3.2 冻结 4：组件 MUST NOT 自己读 store。
   */
  lines: LiveCallLines;
  /**
   * 只读三个字段。MUST NOT 传归属字段（角色 id / 通话持有者）—— 归属不属展示，
   * 组件 MUST NOT 假定通话归属（30 §3.2 冻结 4）。
   * `phase` 只用于空态文案二选一（§3.5 第 3 步）。
   */
  call: Pick<LiveCallState, 'outputText' | 'inputText' | 'phase'>;
  /** 宿主版式钩子：追加到根元素的 class（不改组件自身 CSS）。 */
  className?: string;
}

export const LiveCallTranscript: React.FC<LiveCallTranscriptProps>;
```

> **JSDoc 措辞为何是「归属字段（角色 id / 通话持有者）」**：§6.2-S3 的两条正则（`/\bowner\b/`、`/characterId/`）扫的是**整份 `.tsx`（含注释）**，而本 JSDoc 与组件同文件 ⇒ 注释里写那两个裸词就会当场踩红 S3 自己给出的断言。故这里**逐字避开**它们；理由与「为何不选修法 (b)」写在 §6.2-S3 段。**实现方 MUST 照抄本措辞**（或等效地不含两个裸词），MUST NOT 在注释里补回它们。

**类型 import 用 `import type`**（`live-call-store.ts:31` 的 `LiveCallState` / `:44` 的 `LiveCallLines`）。`import type` 编译期擦除 ⇒ 组件对 store **零运行时依赖**；这正是 §6 用读源码断言守住的那条。

**刻意不存在的 props**（每条对应一条冻结）：

| 不存在的 prop | 依据 |
|---|---|
| `characterId` / `owner` | `30` §3.2 冻结 4「MUST NOT 假定 owner」 |
| `onHangUp` / `onStart` | 同上「MUST NOT 调 `start`/`stop`」 |
| `showStatusBar` / `error` | 状态条与告警属宿主生命周期层（§3.4） |

| `variant` / `theme` | 版式差异由宿主 CSS 承担（§3.3），不做组件内分支 |

### 3.3 样式归属：**组件自带 CSS + 宿主 class 钩子**（兼容 Tailwind 与手工类）

**问题**：nook 在 3D 画布上（玻璃面板，Tailwind utility），对话框在 `dialogue` Depth 的 overlay 里（斜 0.4° 的实心纸，`index.css`）。两套视觉体系不通用（`12 §3.5` 已实测记录：照抄 nook 的 class 会得到「一张半透明玻璃贴在纸上」）。

**方案：分层。组件自带 CSS 只做「结构性」的事，宿主的版式类通过 `className` 落到同一个根元素上。**

```css
/* live-call-transcript.css —— 结构性：无尺寸、无滚动、无外层容器版式 */
.live-call-transcript { display: block; }
.live-call-transcript__line { margin: 0; display: block; }
.live-call-transcript__speaker { margin-inline-end: .4rem; font-family: var(--ux-font-ui); font-size: .78rem; color: var(--rust); }
.live-call-transcript__line--streaming { color: color-mix(in srgb, var(--ink) 70%, transparent); }
.live-call-transcript__line--voice { color: var(--muted); }
.live-call-transcript__line--player { font-style: italic; color: var(--muted); }
.live-call-transcript__line--player .live-call-transcript__speaker { font-style: normal; }
.live-call-transcript__placeholder { margin: 0; font-style: italic; color: var(--muted); }
```

- 全部落在 `--ink`/`--muted`/`--rust` 三个**全局 token**（`index.css:51-59` 定义）上，nook 的 Tailwind 主题与对话框的纸**取同一批 token**（`tailwind.config.js` 的 `colors.ink/muted/rust` 就是 `var(--ux-color-*)`）⇒ **同一份 CSS 在两个宿主里都成立**。
- 尺寸 / 字体族 / `max-height` / 滚动保留在宿主：
  - 对话框：`className="call-stage__transcript"` → 继续吃 `index.css:841-850`（`min-height:3.2em; max-height:9.6em; overflow-y:auto; font-family:'LXGW WenKai'…; font-size:1.12rem`）与 `index.css:914` 的窄屏覆写。**既有纸的观感逐字节不变**。
  - nook：外盒（`data-nook-zone="transcript"` 的玻璃卡）**不动**；内层滚动职责由组件根承担，`className="max-h-32 overflow-y-auto space-y-1.5"`（Tailwind，仍在 nook 侧）。
  - 角色栏（`32`）：自定 `className`，或直接吃结构性默认值。
- **两个宿主的视觉差异被压到只剩 class 名**，「第三处」不再有理由分叉。

**为什么不做成 headless（只出结构、零 CSS）**：三个宿主都要各自写 `--streaming/--voice/--player` 三条颜色规则，正是「三份零共享」债的原形；且 `30` §3.2 逐字要求共享「说话人标签结构」，结构若没有最小样式，说话人只是一个裸 `<span>`，三处必然各写各的。**分层（结构样式自带、版式宿主）是契约允许范围内的最大共享。**

### 3.4 组件严格边界：**不含状态条与挂断按钮**

对话框的 `.call-bar`（`.call-status` + `.call-hangup`，`:1013-1020`）与 `.dialogue-call-alert`（`:1021`）**不搬进组件**：

- 挂断按钮的 `onClick` 必然触发 `stop`（`CharacterModal.tsx:159-161` 的 `hangUp`）⇒ 搬进来就违反 `30` §3.2 冻结 4「MUST NOT 调 `start`/`stop`」。
- 状态文案按 `phase` 三分支（`connecting` / `live` / `error`，`:1015`）**只在对话框出现**（nook 的状态徽标在 `call` lane，`:722-730`，形态完全不同）⇒ 不是共享面。
- `30` §3.2 的共享清单里没有「状态条」。

⇒ **组件 = 字幕列表 + 空态；其余全部宿主所有。** 这条边界就是本任务验收 (e) 的实质。

### 3.5 渲染契约逐步（每步写「漏了会怎样」）

渲染等价于 `CharacterModal.tsx:982-1011` 的结构（今日），即两处判据的**并集**。

```tsx
export const LiveCallTranscript: React.FC<LiveCallTranscriptProps> = ({ lines, call, className }) => {
  const { t } = useLocale();
  const empty =
    lines.lines.length === 0 &&
    lines.streaming === '' &&
    call.outputText === '' &&
    call.inputText === '';
  return (
    <div data-live-call-transcript="" className={className ? `live-call-transcript ${className}` : 'live-call-transcript'}>
      {empty && (
        <p className="live-call-transcript__placeholder">
          {call.phase === 'connecting' ? t('Connecting…') : t('Listening…')}
        </p>
      )}
      {lines.lines.map((line, i) => (
        <p key={i} className="live-call-transcript__line">
          <span className="live-call-transcript__speaker">{t('They say')}</span>
          {line}
        </p>
      ))}
      {lines.streaming !== '' && (
        <p className="live-call-transcript__line live-call-transcript__line--streaming">
          <span className="live-call-transcript__speaker">{t('They say')}</span>
          {lines.streaming}
        </p>
      )}
      {lines.streaming === '' && call.outputText !== '' && (
        <p className="live-call-transcript__line live-call-transcript__line--voice">
          <span className="live-call-transcript__speaker">{t('They say')}</span>
          {call.outputText}
        </p>
      )}
      {call.inputText !== '' && (
        <p className="live-call-transcript__line live-call-transcript__line--player">
          <span className="live-call-transcript__speaker">{t('You')}</span>
          {call.inputText}
        </p>
      )}
    </div>
  );
};
```

逐步：

1. **算 `empty`**（四源全空）。落在渲染期，不是 state（纯函数，无 `useState`）。
   **漏了会怎样**：把 `empty` 缓存成 state 或 `useMemo` 依赖写错 → 第一条台词到达时不重算，占位符与真台词**同时**留在屏幕上。
2. **空态节点在列表之前渲染**（判据 `empty`），与两处既有位置一致。
   **漏了会怎样**：位置只影响 DOM 顺序（`empty` 与列表互斥），但若某宿主用 `:first-child` 定基线，换位会让它失锚。
3. **空态文案按 `phase` 二选一**：`connecting → Connecting…`，其余（`live`/`error`/`idle`）→ `Listening…`。**D2 的收敛点。**
   **漏了会怎样**（nook 侧）：沿用恒定 `Connecting…` → `live` 且无台词的窗口里，屏幕同时显示「正在连接…」与 `On a call`，玩家以为卡住了（**归因错误**：不是连接问题）。
4. **已提交台词逐条渲染，说话人恒为 `They say`**（`t('They say')`）。
   **漏了会怎样**：漏说话人 → 玩家分不清谁在说；改用 `characterId`/显示名代替 → 引入归属（`30` §3.2 禁止），且三处各自取名必然不一致。
5. **流式台词条件渲染 `streaming !== ''`**，说话人同为 `They say`，修饰 `--streaming`。
   **漏了会怎样**：无条件渲染 → 空串也生成一个只剩说话人的空行。
6. **语音前端自转写：`streaming === '' && outputText !== ''`**。**这条是「同一句话不得打印两次」的机械落点**（`10` §2.3「展示规则」、`00` §2.7）。
   **漏了会怎样**：丢掉 `streaming === ''` 前置 → 角色真实台词的流式副本与语音前端转写**同时**打印，每句话出现两次。
7. **玩家台词：`inputText !== ''`**，说话人 `You`，修饰 `--player`。
   **漏了会怎样**：漏 → 玩家在通话中说话看不到自己的转写，无法确认麦克风在工作（`00` §2.9「降级必须可见」在麦克风侧的唯一落点）。
8. **次序恒为 `lines → streaming → outputText → inputText`**，不得按 phase 重排、不得合并。
   **漏了会怎样**：有人在 nook 侧把 `inputText` 提前 → 两处次序分叉，同一通话在两个投影里读起来不一样，`10` §4.1「状态自动一致」的承诺在**展示层**破功。
9. **`className` 追加到根元素、不覆盖组件类**。
   **漏了会怎样**：宿主传 `className` 就直接替换 → 丢失 `.live-call-transcript__*` 的结构样式（三条颜色规则全失效），且宿主必须复刻整套结构选择器。

### 6.2 源码断言（守住 `30` §3.2 冻结 4 的三条 MUST NOT）

**为什么必须读源码**：静态渲染只能证明「给了 props 会画什么」，**证明不了「组件没有别的输入与副作用」**。三条 MUST NOT 全是「不该存在」的性质，只能靠源码文本断言（与 `character-rail.test.mjs:255-300` 同一体例）。

```js
const src = await readFile(new URL('../src/components/live/LiveCallTranscript.tsx', import.meta.url), 'utf8');

test('S1: the component never subscribes to the call store', () => {
  assert.doesNotMatch(src, /useLiveCall(State|Lines|Actions|Available)\s*\(/);
  // A runtime import of the store binding would make the component reactive to it;
  // `import type` is erased and allowed.
  assert.doesNotMatch(src, /^import (?!type\b)[^\n]*from '[^']*live-call(-store)?\.js';?$/m);
});

test('S2: the component never starts or stops a call', () => {
  assert.doesNotMatch(src, /useLiveCallActions/);
  assert.doesNotMatch(src, /\b(start|stop)\s*\(/);      // no call to start()/stop()
  assert.doesNotMatch(src, /fetch\s*\(/);               // no request of its own
});

test('S3: the component never assumes an owner', () => {
  assert.doesNotMatch(src, /\bowner\b/);
  assert.doesNotMatch(src, /characterId/);
});

```

**S3 扫的是整份 .tsx（含注释）⇒ §3.2 的 JSDoc 会踩红它自己；本批已按修法 (a) 处理。** 两条正则（`/\bowner\b/`、`/characterId/`）作用于 `readFile` 的**全文**，不是剥离注释后的源码。§3.2 的 JSDoc 与组件同文件，故其措辞已改为「归属字段（角色 id / 通话持有者）」「通话归属」，**避开两个裸词** ⇒ 文档给的注释不再违反它自己给的断言。

**为什么不选修法 (b)（S3 先 strip 注释，同 `check-ux-contract.mjs:41` 的 `stripComments`）**：剥离注释会把「注释里提到归属字段」也划进允许面，**反而放宽判据**——一句 `// characterId` 的注释正是「有人图方便把角色 id 传进来做归属判断」的前兆，让它保持变红更有信号。本组三条断言守的是「组件**没有**别的输入」这类负面性质，**MUST NOT** 用剥离源码的方式软化；**MUST NOT** 为让将来某条注释变绿而放宽成只查 props 类型块。

**S1 的正则必须允许 `import type`**：组件**需要** `LiveCallLines` / `LiveCallState` 两个类型（§3.2）。用 `import type` 而非删除类型标注——类型是「描述入参」不是「读 store」，且 `import type` 不产生运行时边。若有人把它改成值导入，S1 变红，**这正是要守的**。

**S2 的 `\b(start|stop)\s*\(` 有一处已知假阳性风险**：变量名若叫 `startIndex` 之类不会命中（`\b` + `(`），但 `onStop(` 会命中——**这是有意的**（组件不应有任何 stop 语义的回调）。若将来确需排除，**MUST NOT** 放宽到只查 `useLiveCallActions`（那就漏掉了「自己 `fetch('/api/live/close')`」这条最危险的路径）。

## 10. 发现的冲突与待裁决

### 10.1 C1 — nook 空态文案的收敛是「修正」而非「无关改动」

`30` 要求「不改变现有行为」，而 D2 的收敛**改变了 nook 的一处可见行为**（`live` 且无台词时从「正在连接…」变成「聆听中…」）。两者不冲突——**空态文案属 `30` §3.2 明文要求共享的「空态」**，且对话框的规则是更正确的一方（nook 的恒定文案与同屏状态条自相矛盾）。**处置**：按对话框规则实现，在 §4.4 登记为修正 C-1，由 §6.1-A4 钉住。**若裁决要求 nook 文案级不变**，替代方案是给组件加 `emptyLabel?: string` —— **不推荐**（引入 `labels` 口子，违反 `30` §3.3 冻结 5 的精神）。

### 10.2 C2 — 说话人样式的收敛需要一个明示决策

`30` §3.2 的共享清单里**没有「样式」**，但也没有禁止统一。本文的选择是：**结构样式统一**（§3.3 分层），**版式差异化归宿主**，nook 的三处说话人字形变体收敛为一（C-3）。理由：若不统一，说话人这个「共享结构」在三个宿主里必然长出三套字形，正是决策 4 要避免的债。
**待集成者确认**：nook 的 `font-serif font-bold` / `font-mono` 是否**必须**保留？若是，§4.4-C3 给出了**只改宿主 CSS、不改组件**的复原路径（4 行），本文默认不走。

### 10.3 C3 — `Listening…` 在 nook 侧是「首次成为调用点」

`Listening…`（`messages.json:1214`）在 nook 迁移后**首次**成为 nook 的调用点。它已存在且三语齐备（对话框 `:1009` 在用），**不新增键**；但 `35` 的门禁回写应记录「nook 的调用点集合新增 `Listening…`」——used 键数不变，**warn 数也不变**（该键已 used）。

### 10.4 C4 — 组件不加 `role="log"` 是刻意的

两处既有实现均无 `role`（nook 内层 `div`、`.call-stage__transcript`）。加 role 会改变可访问性树，属**新增语义**而非迁移。**新增载体（角色栏）可在自己的外盒加 `role="log"`**——那是宿主决定，不是组件强加。

### 10.5 C5 — 「公共组件」的边界与 `30` §10-5 的措辞差异

`30` §10 第 5 条验收写「三处字幕渲染走同一组件」。本文的实际边界是「**字幕列表**走同一组件，**状态条与挂断按钮**仍各自实现」。这不违反冻结 4（它共享的是「字幕渲染次序、空态、说话人标签结构、文案键」），但**验收措辞比实现宽**。**建议 `35` 把 §10-5 的判据写细**：机械判据 = §6.2 的 S1–S3（组件侧）+ §6.3 的 A8–A10（迁移侧）。**MUST NOT** 把它读成「`.call-bar` 也要进组件」——那会与冻结 4 的 MUST NOT 直接冲突。
