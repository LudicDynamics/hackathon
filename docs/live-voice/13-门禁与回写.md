### 2.2 `check-request-bodies.mjs`：**键集不变，但 `file` 必须改**

端点形状与请求体键集**一条都不变**（`docs/live-voice/00 §2.2` 冻结，L2 不改，见契约 10 §6「不改：端点形状不变」）。已登记的两行（`check-request-bodies.mjs:100-111`）：

```js
{ route: '/api/live/session', file: 'apps/web/src/lib/live-call.ts', keys: ['character', 'sdp', 'language'], doc: 'docs/live-voice/00-共同上下文.md §2.2' },
{ route: '/api/live/close',   file: 'apps/web/src/lib/live-call.ts', keys: ['character'],                      doc: 'docs/live-voice/00-共同上下文.md §2.2' },
```

**问题在 `file` 而不在 `keys`**：`main()`（`:251`）是 `found.set(b.route, bodyKeysFor(read(b.file), b.route))`——**门禁只扫 `file` 指定的那一个文件**。`bodyKeysFor` 找不到 `fetch(route, …, JSON.stringify({…}))` 就回 `null` → `compare` 报 `missing-call`（`:222-232`，文案是「the call site moved or was renamed」，修复建议恰恰是「update BODIES」）。

而契约 10 §2.2 冻结 2 要求「**只有 store 发 `POST /api/live/close`**，组件 MUST NOT 直接发 close」，§8 反模式 2 要求「MUST NOT 让 `CharacterModal` 直接 `fetch('/api/live/*')`」；`§5.1` 要求资源与状态机搬进 store。**结论（见下「落定」）**：两处 `fetch`（今天在 `live-call.ts:395` 与 `:449`、卸载兜底 `:478`）随 `start`/`stop` 一起搬进 `live-call-store.ts` → **`BODIES` 的两行 `file` 必须改成 `apps/web/src/lib/live-call-store.ts`**。

**改为（完整两行）**：

```js
{
  route: '/api/live/session',
  file: 'apps/web/src/lib/live-call-store.ts',
  keys: ['character', 'sdp', 'language'],
  doc: 'docs/live-voice/00-共同上下文.md §2.2',
},
{
  route: '/api/live/close',
  file: 'apps/web/src/lib/live-call-store.ts',
  keys: ['character'],
  doc: 'docs/live-voice/00-共同上下文.md §2.2',
},
```

**落定（2026-09-15，与 11 号确认）**：11 号的方案是 `live-call-store.ts` 拥有状态机与全部资源（含 `airp:character-frame` 监听），`live-call.ts` **只 re-export 4 个 hook + 类型**。那么两个 `fetch` 随 `start`/`stop` 落进 store，`bodyKeysFor('live-call.ts')` **再也扫不到** → `file` **必须改**（上面完整两行）。「薄绑定」与「fetch 留原文件」不可兼得：既然 `live-call.ts` 只 re-export，它就不可能再持有 `start`/`stop` 的实现。

**11 号曾提「两个 gate 的登记表都不动」——对 `check-ws-contract` 成立，对 `check-request-bodies` 不成立**（见 §11-C1）。口径澄清：「契约 10 §6 明说 check-request-bodies 不改」指的是**端点形状 / 请求体键集**不改，不是 `file` 指针不改——指针错了登记就失效，这属于 L2 的登记面改动，不违反契约。

**唯一不改 `file` 的情形（不推荐）**：把两个 `fetch` 留在 `live-call.ts`。那样契约 10 §2.2 冻结 2「**只有 store 发 `POST /api/live/close`**」会被解释成「store 的文件集合含薄绑定层」，措辞开始含糊；且 `live-call.ts` 就从「无 React 依赖之外的纯 re-export」退回成有副作用的文件。本批**取改 `file`**。

**`ROUTES` 清单核对（已实测）**：`BODIES.length === 11`（输出 `11 route(s) pinned`），**已含** `/api/live/session`（`:101`）与 `/api/live/close`（`:107`）。`GET /api/live/config` **刻意不登记**——它是无 body 的就绪探针，脚本头注释即此口径（`:32-35`）与 `:97-99`。L2 不新增端点，故 11 条**不变**。

**漏了会怎样**：`file` 没跟着搬 → 门禁报 2 条 `missing-call`（红），或（更坏）有人顺手把条目删掉 → `/api/live` 的 body 键从此无门禁，重演 `/api/dice` 的 `{filePath}` vs `body.path` 静默 400（脚本头 `:3-15` 记录的原始事故）。

### STT 与通话模式的关系（W11 结论）

证据链：话筒按钮是**文字输入行**的兄弟节点——`CharacterModal.tsx:923-943` 的 `speech-input-row` 内，`:938` 的 `<VoiceInputButton …>`。`VoiceInputButton`（`chrome/VoiceInputButton.tsx:24`）内部持有 `useVoiceInput`，而该 hook 的卸载清理会**释放麦克风轨并关掉 `/ws/stt` socket**（`lib/voice-input.ts:168-174` 的 `end()`；`releaseAudio` 逐个 `track.stop()`，`:149`）。
