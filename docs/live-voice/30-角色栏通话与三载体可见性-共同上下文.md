## 2. 三载体模型（L3 核心抽象）

### 2.1 载体的定义

**载体（carrier）= 通话 UI 的宿主**。每个载体有自己的 `owner`，且**只挂断自己发起的那条**。

| 载体 | owner | 入口 | 渲染条件 |
|---|---|---|---|
| nook 投影 | `nook:<id>` | `NookView.tsx:686` 的 `call` lane | `App.tsx:1164` `nookChar` |
| 角色对话框 | `dialogue:<id>` | `CharacterModal.tsx:947-957` 模式切换 | `App.tsx:1499` `activeCharacter` |
| **右侧角色栏（NEW）** | **`rail:<id>`** | **本批新增** | `App.tsx:1381` `!nookChar` |

### 2.2 冻结 1：`owner` 是三载体唯一的归属标识

- `owner` 是**任意字符串**（`live-call-store.ts:53`），**store 不改形状**。新增 `rail:<id>` 是接口内的事。
- **`stop(owner)` 只挂断 owner 匹配的那条**（`live-call-store.ts:642`）——这是**承重语义**，任何载体 MUST NOT 绕过它。
- **MUST NOT 用全局快照冒充「本载体的归属」**。判据：一个载体若要问「这条通话是不是我的」，MUST 比较 `call.characterId === <本载体的角色>`，MUST NOT 只看 `call.phase`。

> **本条源自两个实测缺陷**（§4），它们的共同根因正是把全局快照当归属用。

### 2.3 冻结 2：不开「跨投影续存」

**通话生命周期绑定发起它的载体**：载体卸载 ⇒ 该载体的通话挂断。

- 载体卸载时的挂断 MUST 是 `stop(<自己的 owner>)`，**带 owner**。
- **已知后果（有意为之）**：从角色栏发起的通话，玩家进入 nook 时**会被挂断**（角色栏在 `!nookChar` 下不渲染）。这是决策 2 的直接推论，**不是缺陷**。
- **MUST NOT** 为「保住跨载体通话」新增不灭的全局通话条。若将来要开这个口子，必须另立契约并解决「挂断入口在不灭宿主上」的问题（`20` §2 的两扇门）。

### 2.4 冻结 3：同一角色至多一条通话，互斥粒度是**角色**不是全局

沿用 `10:243`：互斥粒度 = 角色，与后端 `live-session.ts:382-386` 同粒度。

- 角色 A 通话中，角色 B 的**任何**载体 MUST 显示「可发起」（若可用）或「空闲」，MUST NOT 显示为「通话中」。
- 角色 A 通话中，在 B 的载体发起通话 ⇒ store 的先挂后开（`10:119` 冻结 1）自动处理。

## 4. 缺陷 1/2（决策 1：本批必修）

### 4.1 缺陷 1：nook 通话按钮不按角色过滤 → 会挂断别人的通话

**证据**（`file:line`）。⚠️ **本代码块是缺陷的「当时快照」，不是活引用**（按 §7.1 引用纪律的例外）：其中的行号记录的是**发现缺陷那一刻**的实测值（`:695`），此后同一文件的行号可能漂移（今日实测为 `:696`）。**下游文档引用时必须以符号名定位，不要照抄这里的行号。**
```js
NookView.tsx:183  const callInProgress = call.phase === 'connecting' || call.phase === 'live';  // 不检查 characterId
NookView.tsx:695  } else void stopCall();   // 无条件，无 owner
NookView.tsx:699/700/702/709/717  // aria-label / title / className / 图标 / 文案 全用 callInProgress
```

**可达路径**（主 agent 逐入口核验）：
```
A 通话中 → 不关任何东西，从右侧角色栏点 B 的「去 ta 的小天地」（App.tsx:1392 直传 openPrivateSpace）
→ 此时对话框未开，openPrivateSpace 的 closeCharacterRef.current() 是 no-op
→ 进入 B 的 nook，A 的通话仍在
→ B 的按钮显示「挂断」→ 一点 ⇒ 挂断的是 A 的通话
```

**其他入口不可达**：对话框内「去 ta 的小天地」（`:940`）会先 `closeCharacter`（`App.tsx:354`）⇒ 对话框卸载 ⇒ `:826` cleanup 挂断。

**冻结 6**：nook 的 `call` lane MUST 按角色判定（`call.characterId === characterId`），`stop` MUST 带 owner。

### 4.2 缺陷 2：`10:187` 与 `12:77` 互相矛盾 → 他角色通话时按钮被误禁用

**证据**：
- `10-对话框通话-共同上下文.md:187`：「nook 通话中打开**另一个**角色的对话框 → 对话框显示「空闲」，点通话会**先挂断 nook 那条**再开新的」
- `12-对话框通话界面.md:77`：明文要求 `disabled={callActive}`，理由在 `12:93`（错误态必须可重试）
- 实现 `CharacterModal.tsx:955`：`disabled={callActive}`，而 `callActive`（`:139`）**是全局的** ⇒ 按钮灰掉，「先挂断再开新的」永不发生

**根因**：两个意图本不矛盾，是**取值把两件事捆在了一起**。

**冻结 7**（主 agent 亲自收口，明月授权）：
- `disabled` MUST 用一个**同时满足两个意图**的谓词：**错误态可重试** ∧ **他角色通话时不误禁**。
- 等价形式：`disabled={callActive && call.characterId === characterId}`（错误态下 `callActive` 为 false ⇒ 可点；他角色通话时 `characterId` 不匹配 ⇒ 不禁）。

- **冻结 7b（2026-09-15 追加，源自 `34` §4.5 实测）**：**只改 `:955` 的字面量不够**——`callActive` 的**定义本身**（`:139` 的 `call.phase === 'connecting' || call.phase === 'live'`）也必须收窄为「**本角色的**通话在传输」：
  ```js
  const callTransporting = call.phase === 'connecting' || call.phase === 'live';  // 全局相位
  const callActive = callTransporting && call.characterId === characterId;         // 本角色
  ```
  **不收窄会怎样（两处他角色串扰）**：
  1. `:958` 的文案 `{callActive ? t('On a call') : …}` 仍是全局 ⇒ 他角色通话时本纸按钮**写着「On a call」却可点**（文案与可点性矛盾；玩家以为切过去，实际会开自己的新通话并挂断别人——误挂只是换了个入口）。
  2. `:879` 的渲染期镜像 `callActiveRef.current = callActive` 喂 **8 个门**（`:433/445/451/595/608/661/672/846`，主 agent 已逐个核验）⇒ 他角色通话时本纸的 TTS 预取静默、mock 问候语**不播种**（不可逆的 `airp:greeted` 会丢）、帧消费停摆、`handleSend` 拒发。
  - **收窄后冻结 7 的字面量仍逐字在位**（`a ∧ a ≡ a`），门禁 `required-source` 匹配照常命中。
  - **命名纪律**：`NookView.tsx` 保留 `callInProgress` 这个名字（`:190` 的 L2 守卫 + `:197` 依赖数组 + `live-call-store.test.mjs:533` 的逐字断言三处不必改），但**渲染判据 MUST 只用本角色派生**（`34` §8.1 W1）。
- **`10:187` 与 `12:77` 两份文档 MUST 同步修订**，以本冻结为准。
- **`aria-pressed` 继续用 `callVisible`**（`12:93` 的设计不变）。

## 5. 三载体可见性门（决策 3）

### 5.1 两扇门的性质不同（关键区分）

| 门 | 条件 | 性质 | 影响谁 |
|---|---|---|---|
| **G-A `!nookChar`** | `App.tsx:1381`（角色栏） | **不渲染**（DOM 消失） | 角色栏、Canvas+PresenceLayer（`:1207`） |
| **G-B `is-immersive`** | `prototype.css:176-179` 的 `.prototype-chrome` | **隐藏**（`opacity:0 + visibility:hidden`，DOM 还在） | 角色栏根元素（`CharacterRail.tsx:80`）、App 级 `ActivityRail`（`App.tsx:1325`） |

**实测澄清**：nook 内所有 lane **都不带 `prototype-chrome`**（`grep` 零命中）⇒ **G-B 管不到 nook 内任何 surface**，`call`（`:686`）与 `transcript`（`:746`）在沉浸下仍可见。**前提是 nook 未被卸载**（卸载即由 `NookView.tsx:201` 的 cleanup 挂断）。

### 5.2 冻结 8：可见性统一契约

**MUST**：本批产出一份**唯一的**「三载体可见性清单」，由 L3 与并行会话 `01a0a16c` **共同收口**，MUST NOT 各写一份。

**清单 MUST 回答**：对每个通话 UI surface，在 `!nookChar` 与 `is-immersive` 两扇楼下**是否可见**，以及**挂断入口是否可达**。

**硬约束（源自 `00` §2.9 与 `10` §2.2 冻结 5）**：**任何时刻，若通话存在，则 MUST 至少有一处可见的挂断入口。** 判据不是「有没有 UI」，而是「**玩家能不能点到挂断**」。

**本批的解法**：⚠️ **本节初稿（2026-09-15 早些时候）有一处错误断言，已被证伪并修正**——

> ❌ 原稿写「空集性由决策 2 推出：载体卸载即挂断 ⇒ 窗口为空集」。
> **错误根因**：决策 2 只保证「载体**卸载**即挂断」，而 **G-B 是隐藏不是卸载**（§5.1 的两扇门性质表已写明）——把「卸载」与「不可见」混为一谈。
> **证伪（实测，`DesignVisibility` 发现 + 主 agent 复核）**：
> ```
> 角色栏发起通话 → 无对话框 → 玩家按 Tab（App.tsx:720-723）
>   前置守卫 App.tsx:708 是 `if (isTextEditingTarget(event.target) || activeCharacter) return;`
>   ⇒ activeCharacter 为 null 时不挡 ⇒ Tab 生效 ⇒ shell.immersive = true
>   → `.is-immersive .prototype-chrome`（prototype.css:176-179）隐藏角色栏根（CharacterRail.tsx:80）
>   ⇒ 通话存在，但玩家点不到任何挂断入口（G-A 未触发：仍在 DOM；G-B 卡在「挂载 ≠ 可见」）
> ```


**修正后的解法（冻结 8b）**：
1. 决策 2（生命周期绑载体）**仍然有效**，但它只覆盖「载体卸载」这一支，**不足以**推出空集性。
2. **需要沉浸例外**，但 **MUST NOT 用「穿透 `.prototype-chrome`」实现**——`opacity: 0 !important` 在祖先上，后代救不回（浏览器实测：`checkVisibility({opacityProperty:true})` → false；且它**只挡视觉不挡命中**，`elementFromPoint` 仍返回后代 ⇒ 会造出「可点但不可见」的按钮，比「点不到」更坏）。
   ⚠️ **更正（2026-09-15 评审门）**：本行初稿还写「且 `.is-immersive .prototype-chrome.<类>` 会触发 `check-ux-contract` 的反模式检测（实测）」——**这是假的**。`tools/check-ux-contract.mjs:189` 的 `auto` 检测**只在该规则自己的 `property === 'pointer-events'` 时触发**；P3 的 property 是 `opacity`、P4 是 `display` ⇒ **永不触发**。全仓唯一的 `pointer-events` 规则 target 是 `index.css` 的 `.object--ghost`。⇒ **穿透没有任何门禁兜底**，否掉它**只能靠 CSS 语义**（本条前半句），守卫靠 §5.4 冻结 10 的断言 + S4b 的可见性验收。
3. **正确形状**：照抄既有 `.prototype-edge-wake` 范式（`prototype.css:686` + `:700-702`）——**另挂一个不带 `prototype-chrome` 的独立元素**。精确设计见 `33` §7.3 的 S4b。
4. **设计文档 MUST 给出空集性的逐步证明**，覆盖三类情形：nook 载体、对话框载体、角色栏载体，各自在 G-A / G-B 下的挂断可达性。

**承重的既有语义（MUST NOT 顺手「修正」）**：`CharacterModal.tsx:158` 的 `hangUp` 是**无条件** `stop()`（注释原文「whoever started it」）。**MUST NOT 改成 `stop('dialogue:'+characterId)`**——在「nook X 通话中打开 Y 的对话框」时 owner 不匹配 ⇒ `stop` 静默 return（`live-call-store.ts:642`），而 nook 已被 `inert` ⇒ **挂断入口真空集**。

### 5.3 冻结 9：nook 的 `phase:'error'` 必须有挂断入口（V-1，本批必修）

**实测证据**（`DesignVisibility` 发现 + `DesignDefects` 复核 + 主 agent 核验）：
- `fail()`（`live-call-store.ts:416-418`）**只 `commitState({phase:'error'})`，不 `releaseLocal()`** ⇒ error 态下**麦克风与 peer 仍活着**，可能仍在计费（`00` §2.9）。
- 而 nook 的 `callInProgress`（`NookView.tsx` 的 `call` lane，今日 `:183`）**不含 `error`** ⇒ 按钮回到「Speak aloud」，而 else 分支（`void stopCall()`，今日 `:696`）又只在非 start 相位走 ⇒ **没有挂断入口**。

**冻结 9**：
- nook 的通话态判据 MUST 为 **`callMine && (callInProgress || call.phase === 'error')`**——与对话框 `CharacterModal.tsx:146` 的既有正确范式逐字同款。
- error 时按钮 MUST 显示为**挂断**（而非「开始」），且 `role="alert"` 的告警 MUST **保留在通话 lane 内**（不随版面消失）。
- **顺带修**：`NookView.tsx` 的 error 告警分支（`:731` 的 `{call.phase === 'error' && call.error && …}`）是**全局**的 ⇒ **他角色的通话错误会显示在本 nook 上**（同一 hunk 修掉，从属于冻结 6 的按角色判定）。

**注**：本条的修法与 §5.2 的空集性要求同源——error 态下若无挂断入口，就是一个新的挂断真空集窗口。

### 5.4 冻结 10：S4b 唤醒元素的 owner 契约（评审门阻断项裁决）

**冲突**（`ReviewL3Consistency` 发现，主 agent 核实）：同一控件 `33` §7.3 与 `32` §4.2 给出**不一致**的 `onClick`：
- `32` §4.2（正确）：`railCallOwner` 定义为「`liveCall.owner` 若以 `rail:` 开头则**取原值**，否则 null」⇒ 已含前缀 ⇒ `liveCallStop(railCallOwner)` ✅
- `33` §7.3（错误）：`liveCallStop(\`rail:${railCallOwner}\`)` ⇒ 实际传 **`rail:rail:<id>`** ⇒ owner 不匹配 ⇒ `stop` 静默 return（`live-call-store.ts:642`）⇒ **唤醒按钮永远不做事**，§5.2 的空集性补丁当场失效。

**冻结 10**：
- **`railCallOwner` MUST 是「已含 `rail:` 前缀的完整 owner」或 `null`**；调用方 MUST **原样传递**，MUST NOT 再拼前缀。
- **判据**：S4b 的 onClick MUST 逐字为 `() => void liveCallStop(railCallOwner)`。
- **验收**：MUST 有一条断言证明「唤醒按钮在 `owner === 'rail:X'` 时真的调用 `stop('rail:X')` 并生效」（**不是**只断言按钮存在）。**理由**：这是本批唯一一处「按钮渲染出来但点了没用」的静默失败形态，与本批反复出现的「静默失效」同族。
