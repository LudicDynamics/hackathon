## 0. 一句话

**技术可行，store 无需改动，后端零改动**；但撞到两道**可见性命门**，且这两道门在现有实现里**已经被处理过**，有现成范式可照抄。

---

## 1. 为什么技术上顺（三条硬证据）

### 1.1 store 的形状本就是为此准备的

`apps/web/src/lib/live-call-store.ts:731` 导出全局单例；`:56-79` 的接口里 `owner` 是**任意字符串**（`:53` 注释原文「Origin entry; `stop(owner)` only hangs up when it matches」）。现有两个 owner：`nook:<id>`（`NookView.tsx:694`）与 `dialogue:<id>`（`CharacterModal.tsx:155`）。

⇒ 新增 `rail:<id>` 是**接口内的事，store 一行不用改**。L2 批次抽单例时的一条理由正是「通话不该绑死载体」（`10-对话框通话-共同上下文.md:55` 的实测论据）。

### 1.2 通话不需要任何可见面板即可运行

`live-call-store.ts` 把全部资源放在 module 级：

| 资源 | 位置 |
|---|---|
| `committed` / `pending*` 快照与字幕缓冲 | `:304-316` |
| `RTCPeerConnection` / data channel | `:304-316`（`:516-631` 的 start 内建立） |
| `MediaStream` 与轨道释放 | `:388-408` 的 `releaseLocal` |
| 音频宿主 | **一个从不挂载 DOM 的游离 `new Audio()`**（`deps.openAudio`，`:296-298`） |
| 250ms 惰性时钟 | store 内部 |
| 帧监听 | `:714-715`，构造期一次性挂 `window` |

`live-call.ts` 的四个 hook 是**零副作用**的 `useSyncExternalStore` 绑定。⇒ **组件卸载不影响通话**，这正是「无遮罩」成立的前提。

### 1.3 契约那条「静默计费」约束，是被遮罩逼出来的

`10` §5.4（`:266`）原文：

> 玩家挂断的唯一可见入口就在当前投影里。一旦离开投影（关对话框、关 nook、切世界），画布与世界没有任何通话 UI，通话如果续存就是**静默计费**——这正是 `00` §2.9 与「降级必须可见」禁止的。

约束的成立前提是「**投影之外无可见 UI**」。角色栏**常驻**可见 ⇒ 该前提不成立 ⇒ **新方案不是绕过约束，是解开约束**。

## 2. 两道可见性命门（必须处理，否则违反契约）

### 门 1：沉浸模式会隐藏角色栏

- 角色栏根元素：`CharacterRail.tsx:80` —— `className="prototype-residents prototype-chrome character-rail"`。**带 `prototype-chrome`**。
- 规则：`prototype.css:176-179`
  ```css
  .is-immersive .prototype-chrome {
    opacity: 0 !important; visibility: hidden !important; pointer-events: none !important;
  }
  ```
- 触发：Tab 键或「隐藏界面」按钮（`App.tsx:1309`、`:720-723`），状态位 `shell.immersive`（`:1137` 挂 `is-immersive`）。
- **后果**：通话中玩家按 Tab ⇒ 麦克风与挂断**同时消失** ⇒ 违反 `10` §2.2 冻结 5 / `00` §2.9。
- **现成范式**：`prototype.css:700-702`
  ```css
  .is-immersive .prototype-edge-wake { display: block; }
  ```
  `App.tsx:1311-1318` 就是这个模式的实例：沉浸模式下**专门保留一个可见恢复入口**。新方案照抄即可，不必发明。
- ⚠️ 同一模式还影响 App 级全局 `ActivityRail`（`App.tsx:1325`，同样带 `prototype-chrome`）——可见性是**跨功能**的共同问题。

### 门 2：角色栏在 nook 打开时不渲染

- `App.tsx:1381`：`{!nookChar && (<CharacterRail ... />)}`。
- 与 `prototype-nook` 的渲染互斥（`App.tsx:1164-1206` vs `:1207-1265`）。
- **后果**：从角色栏发起的通话，玩家随后进入 nook ⇒ 角色栏消失。所幸 nook 自己有通话 UI（`NookView.tsx:680-733`）且 `sameCharacterOnCall` 守卫（`:189`）已让同角色显示为「通话中」⇒ **逻辑上已闭环**，但**设计文档必须显式验证这条路径**。
- 补充：nook 的通话 UI 挂在 `prototype-nook` 内（`NookView.tsx:637` 的 `data-nook-zone="left-lane"`，**不带 `prototype-chrome`**）⇒ **nook 现有通话在沉浸模式下是安全的**。风险只存在于新入口。

## 6. 通话期间的画布反馈（无遮罩方案的关键缺口）

无遮罩意味着**没有面板承载字幕**。玩家能看到的可能来源：

| 来源 | 现状 | 可用性 |
|---|---|---|
| 角色头像（`PresenceLayer`） | 有 `following` 徽标先例（`PresenceLayer.tsx:92-93`） | ✅ 同构，可直接加「通话中」 |
| `ActivityRail`（App 级 `:1325`） | 带 `prototype-chrome`，沉浸下隐藏 | ⚠️ 受门 1 影响 |
| 字幕 | 现在两处各写一遍（`NookView.tsx:739-777`、`CharacterModal.tsx:982-1011`） | ❌ 无公共组件，需新设计 |

**已实测的重复度**：nook 通话 UI 与对话框 `.call-stage` 是**两套独立实现**，共享的只有：同一 store 的四个 hook、同一套语义次序（lines → streaming → outputText → inputText）、同一批句子键。**样式零共享**（nook 用 Tailwind utility，对话框用 `index.css:832-870` 手工类），**i18n 双轨**（nook 走 `legacy-ui-copy.ts:49-57` 的 `UI_COPY.liveCall*`，对话框走 `messages.json:1210-1218`）。

⇒ 若新方案要做字幕 UI，这是**第三个**独立实现。**强烈建议借此次抽出公共通话展示组件**，否则三份重复会立即失控。

## 7. 顺带记录：调查中发现的事故（已修复）

调查期间发现 `NookView.tsx` 的**在途改动**误删了 HEAD 已有的：

```js
// HEAD:201（L2 提交 182a077）
useEffect(() => () => void stopCall(`nook:${characterId}`), [characterId, stopCall]);
```

- **后果**：nook 发起的通话在关 nook 后不挂断；`App.tsx:1164/1207` 互斥分支使 NookView 真卸载，画布无挂断入口 ⇒ **静默计费**。

- **状态**：责任方（会话 `01a0a16c`）已修复并补测试；主 agent 独立验证（`grep -c` = 1、diff 纯 `+5/-0`），并做了三条反证确认新测试真能抓住该回归（删 cleanup / 去 owner / 依赖数组改 `[]` 均变红）。

- **后果**：从角色栏发起的通话，玩家随后进入 nook ⇒ 角色栏消失。所幸 nook 自己有通话 UI（`NookView.tsx:686` 的 `data-nook-zone="call"`、`:746` 的 `data-nook-zone="transcript"`）且 `sameCharacterOnCall` 守卫（`:190`）已让同角色显示为「通话中」⇒ **逻辑上已闭环**，但**设计文档必须显式验证这条路径**。
