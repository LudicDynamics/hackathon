## 5. 空集性证明（`30` §5.2 的硬约束）

> **要证命题 P**：在任何时刻，若通话存在（`committed.phase ∈ {connecting, live, error}`，即快照 ≠ `IDLE`），则至少有一处**可见且可点**的挂断入口。

### 5.0 引理：哪些隐藏属性可被后代救回（决定 §7 的 CSS 形状）

`.is-immersive .prototype-chrome` 用三个 `!important` 属性隐藏。它们在祖先→后代的传播性**不同**：

| 属性 | 祖先设值后，后代能否救回 | 依据 |
|---|---|---|
| `opacity: 0` | **不能** | 祖先的 `opacity` 是**合成结果**：整棵子树被合成进一个透明层，后代的自有 `opacity: 1` 只是让它在自己那层不透明，仍乘进祖先的 0 |
| `visibility: hidden` | **能** | `visibility` 是**可继承属性**，后代显式 `visibility: visible` 即恢复 |
| `pointer-events: none` | **能** | 后代显式 `pointer-events: auto` 即恢复 |
| `opacity: 0`（**对命中**） | **不适用** | `opacity` **不影响命中测试**：`elementFromPoint` 仍返回被透明的后代 ⇒ `opacity:0` 只挡**视觉**、不挡**命中**（下节验收纪律的依据） |

**主 agent 2026-09-15 用浏览器实测核了本引理**（不是只信推理），两个方向都成立：

| 实验 | 祖先 | 后代自有值 | `checkVisibility({opacityProperty,visibilityProperty})` |
|---|---|---|---|
| opacity 合成 | `opacity: 0 !important` | `opacity: 1 !important` | **`false`**（救不回）✅ |
| visibility 继承 | `visibility: hidden !important` | `visibility: visible !important` | **`true`**（能救回）✅ |

> **推论（重要）**：想让某个 surface 穿透 G-B，**必须把覆盖规则打在带 `prototype-chrome` 的那个元素本身**，或打在它的祖先链上；**把规则打在后代元素上一定无效**（`opacity` 挡死）。这条推论直接否掉了「只让角色栏的通话那一行穿透」的设计——见 §7.3。

> ⚠️ **补精度（主 agent 实测，`33` 初稿未写）——「穿透失败」的准确含义**：`document.elementFromPoint(...)` 在 `opacity: 0` 的祖先下**仍然返回那个后代**（`pointer-events` 也没被改）⇒ **`opacity:0` 挡住的是「视觉」，不是「命中」**。所以准确表述是：**玩家看不见按钮**，而不是「点不到」——后者更危险，因为它意味着**可点但不可见**（玩家会盲点出一个看不见的挂断）。
> **对验收的硬要求（判据与 `35 §3` / `A12` 逐字一致，`DesignGates` 2026-09-15 要求两处不得各写一版）**：
> 1. **MUST 用视觉可见性**：`checkVisibility({ opacityProperty: true, visibilityProperty: true })` 或截图。
> 2. **MUST NOT 只查 `elementFromPoint` / DOM 存在性**——对「可点但不可见」会**假绿**。
> 3. **MUST NOT** 用 `assert.doesNotMatch(html, ...)` 去匹配 CSS 声明文本（如 `display` 后跟 `none`）之类**冒充**可见性证明——那断言的是**写法**，不是渲染结果。
> 4. **静态 markup 断言只能证明「控件被渲染」，证明不了「沉浸下可见」** ⇒ 「沉浸 + 通话中 ⇒ 唤醒控件可见且可点」**MUST** 落进**浏览器冒烟**（`35` 的 **A12**），**MUST NOT** 只靠 `character-rail.test.mjs`。
> 5. **MUST 记录 `skipped` 数**：本批任何新增/修改的渲染断言，**MUST 先确认其渲染组不是 skip 状态**（`fail 0` 单独不构成通过——`character-rail.test.mjs` 今日整组 11 skip，见 §9.2 先决条件）。
>
> 这正是本批反复撞到的「**断言守写法不守行为**」的同一种病。

### 5.1 前置引理：通话存在 ⇒ 它的发起载体仍挂载（决策 2 的形式化）

**引理 L1**：`owner` 的载体卸载 ⇒ 该通话被 `stop(<owner>)` 挂断。
- nook：`NookView.tsx` 的卸载 cleanup `useEffect(() => () => void stopCall(\`nook:${characterId}\`), [characterId, stopCall])`（今日 `:201`），**已有测试守卫**（`10` §2.2 冻结 5 的「守卫」段）。
- 对话框：`CharacterModal.tsx` 的卸载 cleanup `useEffect(() => () => { void stopOwnedCall(); }, [characterId, stopOwnedCall])`（今日 `:826`）+ `handleClose` 内的先挂断（今日 `:544`）。
- 角色栏：**尚无**，`DesignRailEntry` 必须按行补 `stop(\`rail:${view.id}\`)` 的卸载 cleanup（`30` §6 落点表已列「角色栏…必须接线」）。

**引理 L2**：`stop(owner)` 只在 owner 匹配时生效，不匹配**静默 no-op**。
- 证据：`live-call-store.ts` 的 `stop()` 首行守卫 `if (owner !== undefined && committed.owner !== owner) return;`（今日 `:642`）。
- **owner 的字面形状（契约 `30` §5.4 冻结 10）**：所有 owner（`nook:<id>` / `dialogue:<id>` / `rail:<id>`）都是**已含前缀的完整字符串**；调用方 MUST **原样传递**，MUST NOT 再拼一次前缀。反例（本文 §7.3 初稿的错误）：``liveCallStop(`rail:${railCallOwner}`)`` ⇒ 实参 `rail:rail:<id>` ⇒ 不匹配 ⇒ 本引理的静默 return ⇒ **按钮渲染出来但点了没用**。
- ⇒ 载体卸载时若传自己的 owner，**不会误关别人的通话**（`30` §2.2 冻结 1）。

**由 L1**：若通话存在，则发起它的那个载体**必然仍挂载**。于是证明只需按「发起载体」穷举三种互斥主情形（A/B/C）；A 另有一个**可点性**子分支（A′）。

### 5.2 逐步证明（按发起载体穷举：三种主情形 + 一个子分支）

#### 情形 A：`owner === "nook:X"`

1. 由 **L1**，`NookView(X)` 仍挂载。nook 的渲染条件是 `App.tsx` 的 `{nookChar && (…)}`（今日 `:1164`）⇒ **`nookChar === X`**。
2. ⇒ **G-A 在此情形为假**（`!nookChar` 不成立），角色栏（S4）**不在场**。G-A 与 S1 的关系是**互斥**的，不是「可能同时消失」。
3. G-B：S1 不带 `prototype-chrome`（§3.1 实测零命中）⇒ **S1 在沉浸下仍可见可点**。
4. ⇒ 挂断入口 = **S1 的按钮**（`NookView.tsx:687-721`，`onClick` 在非 idle 分支走 `stopCall()`）。

**为什么 A 不可能是空的**：能杀死 S1 的只有两种机制——G-A（要求 `!nookChar`，与步骤 1 矛盾）和 G-B（要求带 chrome，实测不带）。两者都够不着 S1。**除非 `NookView` 被卸载，而卸载就由 L1 挂断** ⇒ 不构成「通话存在」的时刻。

> ⚠️ **A 的正确性依赖缺陷 1 已修**：现状 S1 的按钮判据是**全局** `callInProgress`（`NookView.tsx:183`）且 `stopCall()` **无 owner**（`:696`）。这**不影响空集性**（入口存在且可点），但会让「入口挂断的**不是本条通话**」——`30` §4.1 冻结 6 的回归由 `DesignDefects` 负责，本文只登记**边界**：**入口的存在性 ∈ 本文；入口挂断的对象 ∈ `33` 不负责、`31`/`32` 负责**。两处必须同批（主 agent IRC：只改 `stopCall('nook:<id>')` 而不改按钮判据，会从「误挂别人的」变成「点了没反应」）。

##### 情形 A′：`owner === "nook:X"` 且**另一个**角色的对话框已打开（本文新发现的分支）

**为什么它是独立分支**：`activeCharacter !== null` 会同时做两件事——`App.tsx:1169` 给 `prototype-nook` 加 `inert`、`App.tsx:1182` 令 `NookView` 的 `inactive` 为真，进而 `NookView.tsx:482` 的根 `inert={inactive}` 与 `:698` 的按钮 `disabled={inactive}`。⇒ **S1 从「可点」变成「不可点」**，而通话与 nook 都还在（L1 不触发）。

**可达路径**：nook 里 X 通话中 → 点画布上**角色 Y 的 sprite 卡**（`CanvasObject.tsx:344-347` 的 `onOpenCharacterModal(charId)` → `NookView.tsx:626` 的 `handleOpenCharacterModal`）→ 守卫判据 `sameCharacterOnCall = callInProgress && call.characterId === id`（`:190`）对 Y **为假** ⇒ **放行**（这正是 `30` §4.1 冻结 7 / `10` §4.3 要的「他角色不误挡」）→ Y 的对话框打开。

**⚠️ 可达性是「内容条件」，本文如实标注**：nook 的 `<Canvas>` **不传 `presence`**（`NookView.tsx:607-629` 的 prop 列表无该项，`Canvas.tsx:56` 的注释逐字「Absent value = no avatars (nook path)」）⇒ nook 里**没有** `PresenceLayer` 头像可点；nook 自带的 `NookPortrait` activate（`NookView.tsx:546`）传的是**本角色** `characterId`，会被守卫挡下（`sameCharacterOnCall` 为真）。⇒ 从 nook 内打开**他角色**对话框的**唯一**入口是**画布上的他角色 sprite 卡**（`CanvasObject.tsx:344-347`）。**该卡存在与否取决于世界内容**（作者是否在该层放了 `kind === 'sprite'` 的卡）⇒ A′ 是「**内容可达**」，**不是**「任何世界都可达」。本文因此**不**把它列为空集性破口，只列为 V-5。

**玩家永远有退路（这是 A′ 不构成静默计费的原因）**：关掉 Y 的对话框（Esc / 关闭按钮）⇒ `activeCharacter` 回 null ⇒ nook 的 `inert`（`App.tsx:1169`）与 `inactive`（`:1182`）复位 ⇒ S1 恢复可点。**A′ 是绕路，不是陷阱。**

**此分支下入口在哪**：
1. `.call-hangup`（S3，`CharacterModal.tsx:1017`）**不出现**——`callVisible`（`:146`）含 `call.characterId === characterId`，召唤的是 Y 而通话属于 X ⇒ false。
2. 但 `modeSwitchVisible = liveCallAvailable === true`（`:147`）为真（通话能开起来 ⇒ store 的 `available` 曾为 true，且它只被 `ensureConfig` 写过一次，`live-call-store.ts:410-412`/`495-505`）⇒ `.dialogue-modes` 渲染。
3. 其「Text」按钮 `onClick={hangUp}`（`:948`），而 `hangUp` 是 `void liveCallActions.stop()`（`:159-161`，**无参 ⇒ 无条件**）⇒ **这就是可达的挂断入口**。
4. S1 不可点、S4 因 G-A 未挂载、S5 非控件。

**⇒ P 在 A′ 下仍成立**，但入口是**另一类控件**（模式切换，不是挂断按钮）。

**为什么这仍须单列（不是「A 的细节」）**：它把「挂断入口」从「标着 Hang up 的按钮」变成了「标着 Text 的按钮」。`30` §5.2 的判据（「玩家能不能点到挂断」）**字面成立**，但**玩家意图映射错位**——玩家看到的是一个「切回文字」的按钮，不知道它会挂断自己（X 的）通话。本契约不把它算作空集性**破**，但登记为 **V-5（可发现性缺口）**。

**漏了会怎样**：若实现者按「A 只有一种子情形」去做验证，A′ 的回归用例会写不出来；且若将来有人把 `hangUp` 改成 `stop('dialogue:' + characterId)`（带 owner，出于「只挂自己」的良好动机），**A′ 的空集性会立刻破** —— 因为那时 Y 的 owner 不匹配 X 的通话，`stop` 静默 return（`live-call-store.ts:642`），而 S1 正被 `inert`，**挂断入口 = ∅**。这条链是 L2 的 `hangUp` 注释（「Unconditional: the dialogue hangs up the same character's call, whoever started it」，`:158`）在承重，**MUST NOT 把它改成带 owner**。



#### 情形 B：`owner === "dialogue:X"`

1. 由 **L1**，`CharacterModal(X)` 仍挂载 ⇒ `App.tsx` 的 `{activeCharacter && (<CharacterModal …/>)}`（今日 `:1499`）为真，且 `activeCharacter.id === X`。
2. `callVisible = (callActive || call.phase === 'error') && call.characterId === characterId`（`CharacterModal.tsx:146`）⇒ 本条通话（`characterId === X`）**必然**令 `callVisible` 为真（active 或 error 都被包含）。
3. ⇒ 通话版面 `.call-stage`（`:980`）渲染，其内 `.call-hangup`（`:1017`）。
4. 可见性：S3 **不受 G-A 管辖**（门是 `activeCharacter`，不是 `nookChar`）；S3 **不带 chrome**（`.character-modal-layer` 实测零命中）⇒ **不受 G-B 管辖**。
5. ⇒ 挂断入口 = **`.call-hangup`**，两扇门都杀不掉它。

**为什么 B 不可能是空的**：唯一能让 S3 消失的机制是 `activeCharacter` 变 null 或组件卸载；前者触发 `App.closeCharacter`（`:1116-1132`），它**先**导致组件卸载，卸载 cleanup（`:826`）即 `stop('dialogue:X')` ⇒ 回到 idle。**没有「`activeCharacter` 已 null 而通话仍在」的窗口。**

#### 情形 C：`owner === "rail:X"`（本批新增）

1. 由 **L1**，角色栏仍挂载 ⇒ G-A 为真（`!nookChar`）：**nook 不在场**，S1/S2 不存在。
2. 通话中若玩家打开 X 的对话框：`callVisible`（`:146`）对 X 为真 ⇒ **S3 出现，且是合法挂断入口**（`:1017`）。但这是**玩家的额外动作**，不能作为 P 的证明前提。
3. 只看角色栏自身：S4 在 **G-A 下可见**（步骤 1 保证），但在 **G-B 下不可见**（`CharacterRail.tsx` 根元素带 `prototype-chrome`，今日 `:80`）。
4. **G-B 可达性核验**：沉浸只能由玩家动作进入，共两条路——
   - **鼠标路（无条件）**：点 `.prototype-immersion-toggle`（`App.tsx:1308-1310`；它**不带 `prototype-chrome`**，沉浸下只是 `opacity: 0`（`scene-shell.css:53`），**仍可命中**——这正是既有设计：`App.tsx:1311-1319` 的 `.prototype-edge-wake` 是它的可见替身）。
   - **键盘路**：`Tab`（`App.tsx:720-723`）。前置早退 `if (isTextEditingTarget(event.target) || activeCharacter) return;`（今日 `:708`）；`isTextEditingTarget`（`:151-156`）对 `input/textarea/select` 与**任何 `button`/`a`/`[role=switch]` 内**的元素返回 true。⇒ **两个前提**：(i) `activeCharacter === null`（情形 C 成立）；(ii) **焦点不在按钮上**。点完角色栏的通话按钮后焦点正留在那个 `button` 上 ⇒ **紧接的第一次 Tab 会被吞掉**（走浏览器默认 Tab 挪焦点），**再按一次**或改用鼠标路即可。**这不削弱可达性**（鼠标路无条件），但 `R8` 的浏览器用例 MUST 按这个真实节奏写（先点一下画布空白/按两次 Tab），否则会误判成「不可达」。
   ⇒ G-B **可以被真正触发**。
5. ⇒ 触发后：S1/S2 不存在（G-A），S4 被隐藏，S5 不是控件，S3 未挂载。**挂断入口集合 = ∅。**

**结论：情形 C 让 P 不成立。** 这是三情形穷举里**唯一**让 P 为假的分支，也是 §7 唯一需要裁决的对象。（情形 A′ 是 A 的子分支，它**不破** P——见 §5.2 情形 A′ 与 V-5。）

> **要点（回答任务书第 5 问）**：**决策 2 不足以独立推出 P。** 决策 2 给的是 L1（载体一关即挂断），它保证的是「**通话存在 ⇒ 载体仍挂载**」；而 P 要的是「**通话存在 ⇒ 挂断入口可见可点**」。在 G-B 下 **挂载 ≠ 可见**——角色栏正是「挂载但被隐藏」的那个载体。**L1 ∧ G-B-隐藏 ≠ P**。

## 6. 静默计费审计（`00` §2.9 / `10` §2.2 冻结 5）

**被审约束**（`10` §2.2 冻结 5，今日 `:123` 逐字）：

> 入口关闭 = 挂断，且只挂断本入口发起的那条（owner 语义）。player 离开全屏投影后，画布与世界里没有任何可见的通话 UI 或挂断入口——**续存就是静默计费**，违反 `00` §2.9 的成本约束与「降级必须可见」。

（同段论证另见 `10` §5.1 的「为什么卸载要 close」段，今日 `:272`：「玩家挂断的唯一可见入口就在当前投影里。一旦离开投影…」）

**审计口径**：把约束拆成两个可核验命题——

- **B1（换载体）**：载体消失 ⇒ 该载体的通话被挂断。**判据不是「组件卸载」，是「玩家失去挂断能力」**（冻结 5 的下一句就是理由）。
- **B2（同一载体）**：通话存在期间，该载体**任一可见状态**下都至少有一处可点挂断。

### 6.1 逐组合判决

| 组合 | 该门的实际取值 | B1 | B2 | 静默计费成立？ |
|---|---|---|---|---|
| nook 通话，玩家在 nook 内 | G-A 假 | ✅ `NookView.tsx` 卸载 cleanup（`:201`） | ✅ S1 可见（G-B 管不到） | **否** |
| nook 通话，玩家开沉浸 | G-A 假，G-B 真 | ✅ 同上 | ✅ S1 可见 | **否** |

| 角色栏通话，玩家在画布 | G-A 真 | ✅ **需要** S4 卸载 cleanup（`DesignRailEntry` 必补） | ✅ S4 可见 | **否** |
| **角色栏通话，玩家开沉浸** | G-A 真，G-B 真 | ✅ 载体未卸载，**不挂断** | ❌ **S4 被隐藏，无入口** | **是（唯一缺口）** |
| nook 通话，`phase === 'error'` | — | — | ❌ **S1 显示「开始」而非「挂断」（§5.3 / V-1）** | **是（第二个缺口）—— 本批必修（`30` §5.3 冻结 9 / `34` §6.2）** |
| nook 通话 + **他角色对话框打开**（A′） | G-A 假 | ✅ 载体未卸载 | ⚠️ S1 被 `inert`/`disabled`，入口变成对话框的「Text」按钮 | **否**（P 成立，但入口与文案错位 → **V-5**） |
| 对话框通话，`phase === 'error'` | — | — | ✅ `.call-hangup` 标签变 `Close`（`:1018`） | **否** |

**结论**（逐行点数）：上表 **9 行**中，**7 行「否」**（约束成立；含 A′——入口虽错位但确实可点），**2 行「是」**（约束不成立：角色栏 + 沉浸；nook + error）。两个缺口都不在「通话资源」层，而在**可见性/入口**层——这正是本契约要收口的对象。

### 6.2 为什么缺口 1 不能靠「角色栏常驻」绕过

## 7. 沉浸模式例外：裁决与精确形状

### 7.1 裁决：**需要例外**（不可省略）

**理由（三条，缺一不可）**：

1. **§5.2 情形 C 是真空集反例**，不是「理论上可能」。可达路径完全由既有代码构成：角色栏发起通话 → 无对话框（`activeCharacter === null`，故 `App.tsx:708` 的早退不触发）→ 按 **Tab**（`App.tsx:720-723`）。工具条 `.prototype-immersion-toggle`（`:1308-1310`）同样可达。
2. **决策 2 不足以单独推出 P**（§5.2 的要点）。决策 2 给的是 L1（挂载性），P 要的是**可见可点性**；G-B 恰好卡在两者之间。
3. **不可用「禁用沉浸」代替**：沉浸是 Tab/按钮驱动的**核心玩家动作**（`docs/ux/03-Chrome与公开状态.md` 的主题），禁用它 = 为了一个边缘组合砍掉主功能。`20` §2 门 1 也**不**建议禁用，而是建议「照抄现成范式」。

### 7.2 形状裁决：**MUST NOT 用「穿透 `.is-immersive .prototype-chrome`」实现**

**两个独立理由**：

- **CSS 语义理由（§5.0 引理）**：`opacity: 0 !important` 打在祖先上，后代 `opacity: 1` **救不回来**（合成层相乘）。⇒ 想救回角色栏内的挂断按钮，唯一办法是让**整个角色栏根元素**在沉浸下可见——那就等于**取消沉浸对角色栏的隐藏**，破坏沉浸模式本身。
- **「没有门禁兜底」（本节初稿把这条写反了——2026-09-15 评审门由 `ReviewL3Honesty` 查出，主 agent 已复核）**：本批**不存在**任何会拦住「穿透 `.prototype-chrome`」的门禁。

  `tools/check-ux-contract.mjs` 的 `auto` 反模式检测**只在该规则自己的 `property === 'pointer-events'` 时才触发**：它构造的正则以 `e.property` 为首、匹配「该 property: auto」（`check-ux-contract.mjs:189`）。本批计划加的 P3 的 `property` 是 `opacity`、P4 是 `display` ⇒ **无论候选 CSS 写成什么，P3/P4 都不触发该检测**。全仓唯一 `property === 'pointer-events'` 的规则是 `visual.ghost.pointer-events`（`target: apps/web/src/index.css` 的 `.object--ghost`）⇒ **它管不到 `prototype.css`**。

  实测（把 P3/P4 的真实规则分别喂给同一段含 `.is-immersive .prototype-chrome.character-rail--on-call { … pointer-events: auto !important; }` 的候选 CSS）：

  | 喂进去的规则 | 该规则的 `property` | 结果 |
  |---|---|---|
  | P3 | `opacity` | **零 finding** |
  | P4 | `display` | **零 finding** |
  | `visual.ghost.pointer-events` | `pointer-events` | `target` 不匹配 ⇒ **规则根本不跑**（`check-ux-contract.mjs:158`） |

  ⇒ **走「穿透」路线不会被任何门禁抓到。** 这比「被门禁抓」**更**危险——错路**没有机械信号**。因此本契约否掉它**只靠 CSS 语义**（§5.0：`opacity` 打在祖先上、后代救不回），**MUST NOT** 把门禁当作否掉它的理由；实现期的守卫靠契约 `30` §5.4 **冻结 10** 的断言（唤起控件在 `owner === 'rail:X'` 时真的调用 `stop('rail:X')` 并生效）+ `35` 的 `A12` 浏览器冒烟。若将来真要机械拦住「穿透」，**须新增**一条 `property: 'pointer-events'` 且 `selector` 覆盖 `.is-immersive .prototype-chrome` 的 `css-declaration` 规则——那是**新增规则、要改规则数口径**（`35` §2.5），本批**不新增**。

### 7.3 精确形状：`prototype-edge-wake` 范式的镜像（S4b，NEW）

**关键观察**：`20` §2 门 1 建议照抄的现成范式 `.is-immersive .prototype-edge-wake { display: block; }`（`prototype.css` 今日 `:700-702`）**根本不穿透 `prototype-chrome`**——`.prototype-edge-wake`（`App.tsx:1311-1319`）**从不带 `prototype-chrome`**，它本来就「默认隐藏、沉浸下显示」（`prototype.css:686` 的 `display: none` + `:700` 的覆盖）。⇒ **既有范式给的不是「穿透」，是「另挂一个无 chrome 的元素」。**

**设计（S4b）**：

```tsx
// App.tsx，NEW —— 放在 {!nookChar && ( … )} 块内，与 .prototype-edge-wake 相邻
// （今日 :1311-1319 的 edge-wake 之后）。不携带 prototype-chrome。
{!nookChar && railCallOwner && (
  <button
    type="button"
    className="prototype-call-wake"
    onClick={() => void liveCallStop(railCallOwner)}   // 原样传递：railCallOwner 已含 `rail:` 前缀（契约 `30` §5.4 冻结 10）
    aria-label={t('Hang up')}
    title={t('Hang up')}
  />
)}
```

```css
/* prototype.css —— 追加在 .prototype-edge-wake 两条规则旁（今日 :686 / :700-702） */
.prototype-call-wake { display: none; }
.is-immersive .prototype-call-wake {
  display: block;
  position: absolute;
  z-index: var(--depth-chrome-badge);   /* 同 rail 的层；MUST 用 token，不用数字 */
  top: 155px;                            /* 与 .prototype-residents 的 top 对齐（scene-shell.css:135） */
  right: 26px;
}
```

## 13. 发现的冲突

### V-1 — `nook + phase:error` 无挂断入口（本文新发现，非本批引入）

**事实（逐条实测）**：
- `NookView.tsx:183` `callInProgress = call.phase === 'connecting' || call.phase === 'live'` —— **不含 `error`**。
- `:744` `{callInProgress && (…transcript…)}` ⇒ error 时字幕段消失。
- `:690` 按钮 `if (call.phase === 'idle' || call.phase === 'error') { …startCall… } else void stopCall()` ⇒ **error 时按钮变「开始通话」**。
- `live-call-store.ts:477-482`：`error` 帧只 `commitState({phase:'error'})`，**不 `releaseLocal()`** ⇒ 资源与远端会话可能仍在。

**性质**：与对话框的刻意设计**相反**。`CharacterModal.tsx:146` 逐字把 error 纳入 `callVisible`，且 `:143-144` 注释给出理由（「otherwise its `role="alert"` would vanish together with the layout (contract §9.1(a))」）。⇒ **nook 侧漏了同一处理**。

**裁决（已裁，`30` §5.3 冻结 9 + `34` §5/§6.2）：本批必修。** 修法与缺陷 1 **同处同一段代码、同一次 hunk 组**：nook 的通话态判据 MUST 为 `callMine && (callInProgress || call.phase === 'error')`——与对话框 `CharacterModal.tsx:146` 的既有正确范式**逐字同款**（本文上段引作「正确范式」的那条）。error 时按钮 MUST 显示为**挂断**（而非「开始」），`role="alert"` 的告警 MUST **保留在通话 lane 内**；顺带同 hunk 修掉 `:731` 告警分支的**全局**判定（他角色错误不显示在本 nook 上）。⇒ **本文原「不裁」的表述已过期**；「无入口」这一事实与 §6.1 的「第二个缺口」行在本批一并闭环。（此前本文把它归给 `31`/`32` 的生命周期范围，现已由 `30` §5.3 冻结 9 收回本批。）

### V-5 — 他角色对话框打开时，nook 通话的挂断入口**变成了「Text」按钮**（本文新发现）

**事实链（全部实测，见 §5.2 情形 A′）**：`activeCharacter !== null` ⇒ `NookView.tsx:482` 的根 `inert` + `:698` 的按钮 `disabled` ⇒ S1 不可点；`.call-hangup` 因 owner ≠ 召唤角色而不渲染（`CharacterModal.tsx:146`）；**唯一可点入口是 `.dialogue-modes` 的「Text」按钮**（`:948`），它 `onClick={hangUp}`（`:159-161`，无参无条件）。
