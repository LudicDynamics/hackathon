## 1. 一句话定位

**给右侧角色栏的每一行加一个「开始通话」入口（`available === true` 时才渲染），并在角色栏根部加一个常显的通话卡（状态 + 字幕 + 挂断）承载 `rail:<id>` 这条通话——入口在 hover 面板里，挂断入口在常显卡里，两者分离，从而不需要任何 hover 就能点到挂断。**

三条不变量：

1. **角色栏不持有通话 state**（`30` §7 第 2 行）——通话态**完全由 store 快照派生**。⇒ `character-rail.test.mjs` 的 `useState<` 恰好 1 次（`:257`）逐字不变。
2. **入口与挂断入口分离**：麦克风是「发起」（放在 hover/focus 才显示的 `.character-rail__actions` 面板）、通话卡是「挂断」（在角色栏根部**常显**）。⇒ `33` §6.2 的 B2（同一载体任一可见状态下都必须有可点挂断）在**非沉浸**下成立，不依赖 hover。
3. **两扇门下都不新增宿主**：非沉浸靠 S4（角色栏根部常显卡），沉浸靠 S4b（`33` §7.3 的 `prototype-call-wake`，App 级、无 `prototype-chrome`）。⇒ `30` §2.3 冻结 2 与 `33` §5.2 情形 C 的空集性补丁闭合。

### 2.3 三方案

**方案 A —— 麦克风加入 `.character-rail__actions` 面板（复用 `.character-rail__action`）**

```tsx

  <button
    type="button"
    className="character-rail__action"
    onClick={() => void start({ characterId: view.id, locale: locale === 'ja' ? 'ja' : 'en', owner: `rail:${view.id}` })}
    // PER-ROW, never the global snapshot (30 §4.2 freeze 7; see §7.2 for why).
    disabled={rowCallActive}
    aria-label={`${rowCallActive ? t('On a call') : t('Start a call')} · ${displayName}`}
  >
    {rowCallActive ? t('On a call') : t('Start a call')}
  </button>
)}
```

- **UF-3a**：`available` 门控 ⇒ node 下不渲染 ⇒ 计数**不变**（§2.2 实测）。⚠️ 但见 §2.2 的 skip 警告。
- **UF-1b**：不新增 `useState` ⇒ 不变。
- **UF-3c**：面板样式（`:114-164`）不动 ⇒ 不变。
- **语义**：与「三个键」同族（都是这一行的动作），命中 `character-rail.css:113` 的既有注释「The three keys are ALWAYS in the DOM (UF-3a); CSS decides visibility」——**新增第四个键后该注释需改措辞**（见 §9 D-6）。
- **缺点**：**面板是 hover/focus 才显示的** ⇒ 若挂断入口也放这里，`33` §6.2 的 B2 破（键鼠玩家不悬停就点不到挂断）。**这正是本设计把挂断入口分离出去的理由（§3）**。

**方案 B —— 独立按钮（新 class，不进门控面板）**

- **UF-3a**：**不触发**（新 class 不计入 `class="character-rail__action"`）⇒ 计数**不变**。
- **UF-3c**：新按钮的 CSS 若用 `z-index` 或 `transition: left/top` ⇒ **变红**（`:287-289`）。可用 transform/opacity 规避。
- **UF-1b**：不新增 `useState` ⇒ 不变。
- **缺点**：**绕开了 `UF-3a` 的语义**（「三个键恒在 DOM」这条断言原本守的是「不把动作做成分级挂载」）。用一个新 class 躲开它，等于让断言**守不住新增动作**——门禁的意义被削。且新按钮会与 orb/expander 争夺同一侧空间（orb 右下是 follow-dot、右侧是 expander，`:81-101`）。

**方案 C —— orb 徽标（复用 `.character-rail__follow-dot` 的形状）**

```tsx
// 形状演示（若采纳）：加在 orb 按钮内（今日 :114 之后）
{railCallActive && <span className="character-rail__call-dot" aria-hidden="true" />}
```

- **UF-3a**：不新增 `.character-rail__action` ⇒ 计数**不变**。**UF-3c**：同方案 B 的 CSS 约束。
- **严重问题（否决理由）**：orb 的**手势已有一意**——点击 =「交谈」（`:103-108` 的注释逐字「The gesture means ONE thing everywhere: talk」）。在 orb 上叠加「通话中」徽标，会把「**这行的通话状态**」与「**点它会开对话框**」挤在同一个控件上；且 orb 右下**已被 `.character-rail__follow-dot` 占用**（`:114`，CSS `:46-57`），第二枚徽标必然重叠。
- **它只是指示器，不是入口**：徽标不能**发起**通话（orb 的 onClick 已绑交谈），在其上再挂一个 click 就是「一个控件两个意思」。⇒ 徽标**至多**能表达「通话中」，**不能**承担 `30` §11 未决 1 的「入口」。

### 2.4 裁定：**方案 A（入口）+ 常显通话卡（挂断）**

| 维度 | 方案 A | 方案 B | 方案 C |
|---|---|---|---|
| UF-3a 计数 | **不变**（门控，实测） | 不变（新 class） | 不变 |
| UF-1b `useState<` | 不变 | 不变 | 不变 |
| UF-3c CSS | 不变（复用面板样式） | 需规避 z-index/left/top | 需规避 |

| **能承担挂断入口** | ❌（hover 门控） | 可（若常显） | ❌（非控件） |

⇒ **裁定：入口走方案 A**（`available && entry.canTalk` 门控，复用 `.character-rail__action`，**零测试改动**）；
**挂断入口不进面板**，改为在角色栏根部渲染**常显**的通话卡（`character-rail__call`，§3）——这解决了方案 A 唯一的致命缺点，且与 `33` §4 表第 4 行的 DOM 落点（「`CharacterRail.tsx` 根内，预计新增 class `character-rail__call`」）逐字一致。

**为什么「入口能躲过 UF-3a 就值得选」不是作弊**：`available` 是**契约已有的就绪门**（`00` §2.9「false means no entry may be rendered」；`live-call.ts:47` 的 `useLiveCallAvailable` 注释逐字引它）。**在没有通话能力的服务上不渲染通话入口**是契约要求的行为，不是为躲断言。躲断言只是它的顺带结果。

## 3. 通话态的精确渲染条件与元素

### 3.1 派生量（**全部是派生量，无 state**）

放在 `CharacterRail` 组件体（今日 `:60` 的 `const { t } = useLocale();` 与 `:61` 的 `useState` 之后，**不得引入新 `useState`**）：

| 符号 | 形态 | 定义 | 说明 |
|---|---|---|---|
| `available` | `useLiveCallAvailable()` | —— | 就绪门。**只门「入口」，不门「通话态」**（§3.6） |
| `call` | `useLiveCallState()` | —— | 全局快照 |
| `lines` | `useLiveCallLines()` | —— | 角色台词 |
| `{ start, stop }` | `useLiveCallActions()` | —— | module 级稳定引用（`live-call.ts:58-65`） |
| `railOwnsCall` | 派生 boolean | `typeof call.owner === 'string' && call.owner.startsWith('rail:')` | **本载体是否是这条通话的发起者**（`30` §2.2 冻结 1 的判据：比 `owner`，不比 `phase`） |
| `railCallActive` | 派生 boolean | `call.phase === 'connecting' \|\| call.phase === 'live'` | 语义：真的在传输（镜像 `NookView.tsx:183` 的 `callInProgress`、`CharacterModal.tsx` 的 `callActive`） |
| `railCallVisible` | 派生 boolean | **`railOwnsCall && (railCallActive \|\| call.phase === 'error')`** | 语义：**本载体的通话卡该出现**。**含 `error`**（`33` §5.3：复刻对话框的 `callVisible` 口径，**不得**复刻 nook 的 `callInProgress` 缺口） |
| `railCallName` | 派生 string | `views.find(v => v.id === call.characterId)?.name ?? call.characterId ?? ''` | 仅用于 aria-label 的「· 名字」后缀 |

**漏了会怎样（1）**：把 `railCallVisible` 写成只看 `railCallActive`（不含 `error`）⇒ 通话失败后**通话卡连同 `role="alert"` 一起消失**，玩家看不到原因，也**点不到挂断/关闭**——正是 `33` §V-1 的 nook 缺口在角色栏的原样复刻，也违反 `00` §2.9「降级必须可见」。
**漏了会怎样（2）**：把判据写成只看 `call.phase`（不看 `owner`）⇒ **角色 A 通话时，角色 B 的角色栏也会显示「通话中」**，正是 `30` §4.2 缺陷 2 的同型错误（把全局快照当本载体的归属，`30` §2.2 冻结 1 明文禁止）。
**漏了会怎样（3）**：把 `railCallVisible` 再加一个 `&& views.some(v => v.id === call.characterId)` ⇒ **角色从 `views` 消失时通话卡也消失**，通话仍在却无挂断入口（新的空集性窗口）。**故 `railCallVisible` MUST NOT 依赖 `views`**（`railCallName` 只是显示层，缺它是空串，不影响是否渲染）。

### 3.2 通话卡（`NEW`，角色栏根部的**一个**子节点）

```tsx
// CharacterRail.tsx，根元素内、{views.map(...)} 之前（今日 :80 之后、:83 之前）
{railCallVisible && (
  <div
    className={`character-rail__call character-rail__call--${call.phase}`}
    data-rail-call=""
    role="log"
  >
    <span className="character-rail__call-status" role="status">
      {call.phase === 'connecting'
        ? t('Connecting…')
        : call.phase === 'live'
          ? t('On a call')
          : t('Could not connect')}
    </span>

    {call.phase === 'error' && call.error ? (
      <p className="character-rail__call-alert" role="alert">{call.error}</p>
    ) : (
      <LiveCallTranscript
        lines={lines}
        call={{ outputText: call.outputText, inputText: call.inputText, phase: call.phase }}
        className="character-rail__call-transcript"
      />
    )}

    <button
      type="button"
      className="character-rail__call-hangup"
      onClick={() => void stop(`rail:${call.characterId}`)}
      aria-label={`${call.phase === 'error' ? t('Close') : t('Hang up')} · ${railCallName}`}
    >
      {call.phase === 'error' ? t('Close') : t('Hang up')}
    </button>
  </div>
)}
```

**逐步契约（每步写「漏了会怎样」）**：

1. **渲染门**：`railCallVisible`（§3.1）。**漏了**：非本载体的通话也渲染卡 ⇒ 两处「挂断」按钮歧义（`30` §2.2 冻结 1）。
2. **位置：角色栏根部的直接子节点**（不是某个 `.character-rail__item` 内）。理由：进程内**至多一条通话**（`30` §2.4 冻结 3），故卡**至多一张**；放进 row 会（a）与固定行高（`--character-rail-row-height: 114px`，`character-rail.css` 的 `.character-rail` 规则，今日 `:8`）冲突、（b）与 hover 面板争同一侧锚点（`right: calc(100% + 10px)`，`character-rail.css` 的 `.character-rail__actions`，今日 `:117`）。**漏了**：卡与行内面板重叠，或撑破行高把 label/status 挤出可视区。
3. **`role="log"` 放在外盒上**（`31` §3.6 逐字：「新增载体（角色栏）可以在自己的**外盒**上加 `role="log"`，那是宿主的事」）。**漏了**：字幕流对读屏不可达。
4. **状态文案按 `phase` 三支**（镜像 `CharacterModal.tsx:1015`：`connecting` → `Connecting…` / `live` → `On a call` / 其余 → `Could not connect`）。**漏了**：`error` 相位的状态条显示 `On a call`，与同屏的 alert 自相矛盾。
5. **error 相位：alert 顶替字幕**（`call.error` 非空 ⇒ 渲染 `role="alert"`，不渲染字幕）。镜像 `CharacterModal.tsx:1021` 的 `.dialogue-call-alert`。**漏了**：错误文案与「空的」字幕区并存，玩家以为通话还在。
6. **挂断 onClick：`stop(\`rail:${call.characterId}\`)`——带 owner**（`30` §2.3 冻结 2 逐字：「载体卸载时的挂断 MUST 是 `stop(<自己的 owner>)`，带 owner」；`33` §5.1 L2 的机制依据）。**漏了**：无 owner 的 `stop()` 会挂断**任何**通话，误挂别人的。
7. **挂断标签：`phase === 'error'` 时 `Close`，否则 `Hang up`**（镜像 `CharacterModal.tsx:1018`）。**漏了**：错误态显示 `Hang up` 无 UI 缺陷，但语义不诚实。
8. **`data-rail-call=""` 测试锚点**（`31` §3.6 同款纪律）。**漏了**：测试用 `class="character-rail__call"` 计数时会把 `character-rail__call-status` 等**子串命中**误计。

### 3.3 字幕宿主（回答 `30` §11 未决 2）：与 `31` 的接口

**宿主 = 通话卡内**（`<LiveCallTranscript className="character-rail__call-transcript" />`），**不是画布角落、不是独立悬浮层**。

**与 `31` 的接口（逐字对齐 `31` §3.2，不自创）**：

```ts
// 我只消费这一个签名（31 §3.2 冻结）
interface LiveCallTranscriptProps {
  lines: LiveCallLines;                                             // 从 useLiveCallLines() 取
  call: Pick<LiveCallState, 'outputText' | 'inputText' | 'phase'>;  // 只传三字段
  className?: string;                                               // 宿主版式钩子
}
```

- **MUST NOT 传** `characterId` / `owner`（`30` §3.2 冻结 4）⇒ 字幕与「哪条通话」解耦。
- **MUST NOT 传** `onHangUp` / `onStart`（同上）⇒ 挂断按钮归**通话卡**（本载体），不归组件。
- **组件不发 `data-nook-zone`、不带 role**（`31` §3.6）⇒ `role="log"` 由本载体外盒承担（§3.2 第 3 步）。
- **尺寸/滚动归宿主**（`31` §3.3）：`character-rail.css` 给 `.character-rail__call-transcript` 定 `max-height` 与滚动，**不改组件 CSS**。

**为什么字幕必须在通话卡里**：与挂断按钮同盒 ⇒「看见台词」与「挂断」在同一视觉单元内，`33` §6.2 的 B2 一次满足；且通话卡在角色栏列内、**不遮画布**——这正是「无遮罩」的实现（对比对话框的 `.call-stage` 是全屏层）。
**漏了会怎样**：把字幕放到画布角落 ⇒ 需新宿主（违反 `30` §2.3 冻结 2「MUST NOT 新增不灭的全局通话条」），且与 `33` §4 的 surface 清单失锚。

### 3.4 orb 是否加「通话中」视觉（回答 `30` §11 未决 5）：**裁定：不加**

**理由（三条）**：
1. **手势一意性**：orb 的点击已是「交谈」（`CharacterRail.tsx:103-108` 注释逐字「The gesture means ONE thing everywhere: talk」）。叠加徽标会把「**这一行在通话**」与「**点它开对话框**」挤在同一控件上（§2.3 方案 C 的否决理由）。
2. **位置已被占**：orb 右下是 `.character-rail__follow-dot`（`CharacterRail.tsx:114`；CSS `:46-57`）。第二枚徽标须另找位，而窄屏 44px orb（`scene-shell.css:198-199`）没有余量。
3. **信息已由通话卡承担**：`railCallVisible` 时通话卡常显，状态条已是 `On a call`。徽标是**冗余的第二处真相**（`10` §4.1 的精神在视觉上同样适用）。

**若评审仍要徽标**（本文给出**唯一可接受形状**）：
- 放在 orb **左上**（避 follow-dot）：`right: auto; left: -2px; top: -2px;`
- class `character-rail__call-dot`，**不新增** `character-rail__action`（UF-3a 安全）；

### 3.5 在场性裁决（回答 `30` §11 未决 6）：**「不在场」的角色 MUST NOT 能从角色栏发起通话**

**事实（实测）**：
- 角色栏派生：`character-rail.mjs` 的 `railEntry()`（`:19-36`）的 `canTalk`（`:23`）= `view.state === 'in-scene'`；非 in-scene 给出 `talkHintKey`（`:27-29`）。
- orb 已按 `canTalk` 分支（`CharacterRail.tsx:105-108`）。
- 后端：`apps/server/src/routes/live.ts` 的通话创建**只校验 nook 目录**（`nookIdOf(character)` 的 `statKind` 是不是 `dir`，`:93-99`），**不校验在场**。
- 契约 `30` §2.4 冻结 3 只规定「互斥粒度 = 角色」，**不涉及在场**。

**裁决：角色栏的麦克风与 orb 用同一个 `entry.canTalk`**（渲染条件 = `available && entry.canTalk`，§2.3 方案 A 的代码）。

**理由（四条，缺一不可）**：
1. **同一行不得自相矛盾**。玩家点 not-in-scene 角色的 orb，得到 `They are not here right now.` / `They are in another scene. Go to them instead.`（`CharacterRail.tsx:107` + `character-rail.mjs:27-29`）。**若紧邻的麦克风却能真的拨通**，同一行在同一瞬间给出两份相反的真相——违反 `10` §4.1「MUST NOT 在两处各维护一份 state」的**精神**（真理单源）。
2. **角色栏的唯一投影是 presence**。`CharacterRail` 的契约逐字「never derives membership itself — the ONE projection (`usePresence().views`) is handed in」（`:17-19`）。**在场性是本组件唯一拥有的世界知识**；绕开它需另引世界状态（违反「the rail never reads useWorld」的源码断言，`character-rail.test.mjs:292-299`）。
3. **与 nook 的不对称可辩护，不是不一致**。nook 是**某个角色的投影**（玩家已在那个角色的空间里；`presence` 是「它在不在那一格」）；角色栏是**全体角色名单**（`absent` = 不在世界里）。后者的 `absent` 是「这个世界里没有它」，此时「打电话给它」在虚构层没有落点。
4. **与既有断言自洽**：`canTalk` 已由 `railEntry` 给出（`character-rail.mjs:23`），**本文不改该模块** ⇒ `character-rail.test.mjs:47-49`（`inScene.canTalk === true`、`elsewhere/absent.canTalk === false`）与 `:81-85`（hint 键）**逐字不变**。

**被否决的替代（登记理由以免评审重开）**：「允许不在场也拨通」需给 `railEntry` 新增字段（如 `canCall` 恒真），会让 `UF-0`（`:47-49`）的语义分叉成两个「能不能」的判据，且需**新文案**（无场景可回放时的提示），违反 §5 的「0 新键」目标；**收益为无**（不在场的角色没有可见的对话场景）。⇒ **否决**。

### 3.6 `available` 只门「入口」、不门「通话态」——堵住一个新的空集性窗口

**这是 `DesignVisibility` 提醒、本文明确裁定的一条**（同型于 `33` §5.2 情形 C）。

**风险**：入口用 `available` 门控（§2.4）后，若把**通话卡**也门在 `available` 之后，则当
- 通话**已建立**（`railCallVisible === true`），而
- `available` 转为 `false`（`ensureConfig` 的网络探测晚到、瞬时失败、或 `setAvailable(false)` 在 `:503` 的 catch 分支触发）

⇒ **通话仍在传输（继续计费），但入口与通话卡全都不渲染 ⇒ 挂断入口真空集**。

**裁定（MUST）**：
- **入口**（§2.3 方案 A 的麦克风）渲染条件 = `available && entry.canTalk`；
- **通话态**（§3.2 的通话卡）渲染条件 = `railCallVisible`，**与 `available` 无关**。

**依据**：与对话框的分法逐字同型——`CharacterModal.tsx:147` 的 `modeSwitchVisible = liveCallAvailable === true` 门的是**整块模式切换**（入口），而 `:146` 的 `callVisible` **与 `available` 无关**。

**漏了会怎样**：把通话卡门在 `available` 后 ⇒ `available` 任一瞬时为 `false` 都制造「通话存在但挂断不可达」的窗口——与 `33` §5.2 情形 C 同类，但**触发条件更弱**（不需要玩家按 Tab，只需要一次探测失败）。

### 3.7 载体卸载即挂断（`30` §2.3 冻结 2）的精确 cleanup

**机制**：角色栏在 `App.tsx` 的 `{!nookChar && (…)}`（`:1381-1396`）下渲染 ⇒ **玩家进 nook 时整个 `CharacterRail` 卸载** ⇒ 必须挂断 `rail:*` 通话。**已知后果（有意为之，`30` §2.3 逐字）**：从角色栏发起的通话，玩家进入 nook 时**会被挂断**——这是决策 2 的直接推论，**不是缺陷**。

```tsx
// CharacterRail.tsx —— 新增（需把 :1 的 import 改成
//   import React, { useCallback, useEffect, useRef, useState } from 'react';
//   —— 此改动不影响 UF-1b：它数的是 `useState<`（:257），不是 import 行）
//
// 1) 与 NookView 同款的 ref 镜像（NookView.tsx:203-209 的既有体例）：
//    渲染期赋值，让 cleanup 读到的是「卸载那一刻」的 owner 前缀，而不是闭包快照。
const railOwnsCallRef = useRef(false);
railOwnsCallRef.current = railOwnsCall;   // 与 §3.1 的 railOwnsCall 同一渲染期

// 2) 卸载 cleanup：只挂断本载体发起的那条（30 §2.3 冻结 2）。
useEffect(() => {
  return () => {
    if (railOwnsCallRef.current) void stop(`rail:${callRef.current.characterId}`);
  };
}, [stop]);
```

其中 `callRef` 是同款镜像：`const callRef = useRef(call); callRef.current = call;`（`NookView.tsx:203-209` 的 `stateRef` / `nookIdRef` 就是这个体例）。

**为什么 cleanup 用 `railOwnsCallRef`（镜像）+ `stop`（hook）而不是直接读 module 单例**：
- **`live-call-store.js` 只被 `live-call.ts` import**（实测：`grep "from '.*live-call-store.js'" apps/web/src/` → 仅 `live-call.ts:25` 一处；**没有任何组件**直接 import 它）。`live-call.ts` 的头注释逐字：「It exists so the store can stay React-free while **the two entries keep one import path**」（`:8-9`）⇒ **组件直接 import store 会破这条唯一的导入路径纪律**。**故 MUST 经 hook**（本设计初稿曾写成 `liveCallStore.getSnapshot()`，已改）。
- **`stop` 是 module 级稳定引用**（`live-call.ts:58-61` 的 `ACTIONS`），进依赖数组不会重跑 effect（`live-call.ts:56-57` 的注释逐字：「an effect that depends on it never re-fires on a re-render」）⇒ `[stop]` 等价于 `[]` 且满足 lint。
- **为什么必需 ref 镜像**：cleanup 闭包捕获的是**首次渲染**的 `railOwnsCall` / `call`（`[]`/`[stop]` 依赖下），若通话是**之后**才发起的，闭包里的值恒 `false`/`idle` ⇒ **卸载时不会挂断**。ref 镜像（`NookView.tsx:203-209` 的既有体例）解决这一点。

**为什么判据是 `railOwnsCallRef`（前缀 `rail:`）而不是一个 `railCallCharacterId` 变量**：`owner` 前缀 `rail:` 正是「本载体发起」的定义（`30` §2.2 冻结 1）；且 `stop(owner)` 的 owner 守卫（`live-call-store.ts` 的 `stop()` 首行，今日 `:642` 逐字 `if (owner !== undefined && committed.owner !== owner) return;`）保证**不误关别人的**——即便 ref 的时序有偏差，守卫也是第二道防线。

**为什么不另立一个 `startsWith('rail:')` 判定式**：判据必须锚在**渲染期派生**的 `railOwnsCall`（§3.1）上，它与通话卡的门（`railCallVisible`）**同源**——若 cleanup 另写一套判定，两处就可能分叉（`10` §4.1 的「两处真相」病）。⇒ **cleanup 的 `railOwnsCallRef` 与 §3.1 的 `railOwnsCall` MUST 是同一个派生量**。

**漏了会怎样（1）**：不写 cleanup ⇒ 角色栏通话中进 nook，通话**继续计费**（会话 / Sideband / 音频资源全在 store 的 module 级，**从不挂载 DOM** ⇒ 组件卸载不影响通话），而角色栏已不在 DOM ⇒ **没有任何挂断入口** ⇒ 违反 `00` §2.9 与 `10` §2.2 冻结 5 的静默计费约束。
**漏了会怎样（2）**：cleanup 写成 `void stop()`（无 owner）⇒ 卸载角色栏会**误挂断对话框的通话**：若玩家在角色栏通话期间又在对话框开了**同角色**的通话，store 的 adopt 分支（`live-call-store.ts:521-526`）会把 owner 改成 `dialogue:`；此时角色栏卸载的**无参** `stop()` 就会挂断它 ⇒ 违反 `30` §2.2 冻结 1。
**漏了会怎样（3）**：把 cleanup 放进 `views.map` 的回调（每行一个 effect）⇒ **`views` 重排会重跑 effect**，把仍然有效的通话挂断。**故 cleanup MUST 挂在组件根部**（不在 `map` 里）。
**漏了会怎样（4）**：把 cleanup 的依赖写成 `[call]` / `[railOwnsCall]`（快照或派生量本身）⇒ 每次快照变化都重跑 cleanup ⇒ **通话中每次都挂断自己**。**故依赖 MUST 是 `[stop]`**（module 级稳定引用，等价于 `[]`），**且判据 MUST 经 ref 镜像读取**（§3.7 开头）。

**与 `33` §5.2 空集性证明的关系**：本条是引理 L1 的第三支（nook：`NookView.tsx:201`；对话框：`CharacterModal.tsx:826`；**角色栏：本文**）。⇒「通话存在 ⇒ 发起它的载体仍挂载」对第三载体成立。

### 7.2 为什么 error 之后**入口也可重试**（与 `30` §4.2 冻结 7 一致）

`30` §4.2 冻结 7 要求 `disabled` 用一个**同时满足两个意图**的谓词：**错误态可重试** ∧ **他角色通话时不误禁**。

⇒ 麦克风的 `disabled={railCallActive}`（§2.3 的行内代码）**只在真的在传输时禁用**：
- `phase === 'error'` ⇒ `railCallActive === false` ⇒ **可点**（重试）；
- 他角色（A）通话时，B 的入口：`railCallActive` 是**全局**的 ⇒ **会被误禁**。⚠️ **这是本文必须修正的一点**：

**修正（MUST）**：麦克风的 `disabled` 判据**不得**用全局 `railCallActive`，而要用**本角色**的判据：

```tsx
// 本行的角色是否正占着那条通话（30 §2.2 冻结 1：比 characterId，不比 phase）
const rowCallActive =
  (call.phase === 'connecting' || call.phase === 'live') && call.characterId === view.id;
// ...
<button
  disabled={rowCallActive}
  aria-label={`${rowCallActive ? t('On a call') : t('Start a call')} · ${displayName}`}

  {rowCallActive ? t('On a call') : t('Start a call')}
```

**漏了会怎样**：用全局 `railCallActive` ⇒ **角色 A 通话时，角色 B 的角色栏麦克风被禁用**——正是 `30` §4.2 缺陷 2（「他角色通话时按钮被误禁用」）在角色栏的**原样复刻**，而冻结 7 明文禁止。判据 MUST 是 `call.characterId === view.id`（与 `CharacterModal.tsx:146` 的 `call.characterId === characterId` 同款）。

### 7.3 错误态下点击入口的行为（`start()` 的先挂后开）

在 `phase === 'error'` 且**本角色**是 `call.characterId` 时点麦克风 ⇒ `start({characterId, locale, owner: 'rail:'+id})`：
- store 的 adopt 分支（`live-call-store.ts:521-526`）只在 `connecting|live` 时命中，**error 不命中**；
- 落到 `:531-534`：`if (phase !== 'idle') await stop(); if (phase !== 'idle') return;` ⇒ **先挂断旧的 error 通话，再开新的**（`10:119` 冻结 1 的「先挂后开」）。
**漏了会怎样**：若在错误态**不**先 `stop` 就直接 `start`，store 会持两条远端会话（旧的是 `error` 但 `releaseLocal()` 未被 error 帧调用——`33` §V-1 实测：`fail()`（`:416-418`）只 `commitState({phase:'error'})`）。⇒ **本文的入口不自作聪明**：只调 `start()`，让 store 的既有先挂后开处理（`10` §2.2 冻结 1）。

## 11. 发现的冲突

### W-1 — 契约 `30` §5.2 的推论不成立（**已由 `Main` 裁定修订，本文只登记依赖**）

`30` §5.2 末尾逐字：「不靠新宿主，靠**生命周期绑载体**——载体卸载即挂断，故『通话存在但挂断入口不可达』的窗口 MUST 为空集」。**证伪**（`33` §5.2 情形 C）：G-B 是**隐藏**不是卸载，`opacity:0 !important` 在祖先上后代救不回 ⇒ 角色栏通话 + 按 Tab ⇒ 挂断入口真空集。
**本文的处置**：S4b 是本推论缺口的兑现（§4.2）；**MUST NOT** 用「穿透 `.prototype-chrome`」实现（`33` §7.2 两条独立理由）。

### W-2 — `30` §7 第 1 行「新按钮若复用该 class，必须改计数」**在门控方案下不成立**（本文实测）

`30` §7 第 1 行逐字：「新按钮若复用该 class，**必须改计数**」。**实测**：`available` 门控而复用 class 时，node 下**不渲染** ⇒ 计数**仍 3**（§2.2）。
**性质**：不是矛盾，是**条件不完备**——§7 那句话缺了「非门控」这个前提。**建议**在 `30` §7 补一句：「若入口用 `useLiveCallAvailable()` 门控，则 node 静态渲染下计数不变；恒渲染才有计数改动」。
**本文的处置**：§2.4 选门控 ⇒ **UF-3a 零改动**。**但**这条必须在 C14（skip 修复）之后复跑确认，否则是「改计数而断言没跑」的假绿。

### W-3 — `character-rail.test.mjs` 渲染组全 skip（**已由 `Main` 确认为真缺陷**）

见 §10.1。**性质**：不是「既有、无害」，而是**一条真缺陷**——渲染断言全灭，且**会在本批制造假绿**（本文 §2.2 的实验若在 skip 状态下做，结论无效）。`Main` 已公开更正 L2 的宽措辞。**处置**：C14，与任何渲染断言改动**同批**。

### W-4 — `33` §9.2 的建议断言**不可直接执行**（本设计已回执，`DesignVisibility` 已改）

`33` §9.2 初稿写 `render([view(...)], { call: {...} })`，但 rail 的 `render()`（`:129-141`）**没有注入面**。⇒ 必须补 §10.2 的 stub seam。`DesignVisibility` 已据此改写 `33 §9.2`。

### W-5 — `33` §9.2 的 `Hang up · Alpha` **只在 `live` 相位成立**

rail 的 aria-label 体例 `${t(label)} · ${displayName}`（`CharacterRail.tsx:141/152/162`）**对**；但通话态的标签随相位变（§3.2 第 7 步：error ⇒ `Close`）。⇒ 断言 MUST 分两相位（本文 §10.3 的 A3/A4 已分）。

### W-6 — `available` 门控引入一个新的空集性风险（`DesignVisibility` 提醒，本文 §3.6 裁定堵住）

若把**通话卡**也门在 `available` 后 ⇒ `available` 瞬时 `false` 即制造「通话存在但挂断不可达」。**裁定**：`available` 只门入口，MUST NOT 门通话态（§3.6）。
