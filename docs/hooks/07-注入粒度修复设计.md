# 07 — 注入粒度修复设计（一个 trace 恰好注入一次）

> 本篇是 B2/B3 注入批次的**修订篇**：它只冻结一件事——**注入块的粒度**。跨篇共享形状（`Section`、线格式、条目上限、游标语义、失败纪律）仍以 `docs/hooks/00-共同上下文.md` 为准，本篇只按节号引用，并在**契约冲突处**给出可粘贴的替换文本。
> 本篇**不改代码**；落地由 01/06 的持有者在评审后执行。
> 事实一律带 `file:line`（2026-09-14 现场重核）；推断标 `[推断]`。

## 1. 一句话定位

**同一个 trace（一次 `agent_start` → `agent_end`/settled，= 一次 player 输入）内，状态块必须注入恰好一次——在该 trace 的第一个 provider 请求上；其后每次 `context` handler 仍被引擎调用，但必须返回 `undefined`（不改 `messages`）。**

判据是引擎自带的 `turnIndex`：`agent_start` 把它置 0（首请求），工具循环的续接请求 ≥1（`vendor/pi-rp/packages/coding-agent/src/core/agent-session.ts:1032-1033`、`:1055-1061`、`:1064-1074`）。

### 1.1 被修的 bug（已定案，不重查）

`extensions/context.ts:167-194` 的 `context` handler 对**每个** provider 请求重贴同一段块；而块里含 `next_step` 祈使句（`packages/shared/src/render/next-step.ts:48-57`），该句在 `agent_start` 时按**冻结 facts** 算出（`extensions/context.ts:139-140`，事件读已排除 writer 自己的事件）。于是一个含工具调用的玩家回合里，整轮恒为同一句「The player has just made a choice… **Answer that choice this turn before moving on.**」→ 模型反复重写 → 同一玩家回合重复 chalk。实测口径见 `docs/layout/07-自动生成与坐标写入治理设计.md:92-99`（`extensions/context.ts:140` 含 `next_step`；`vendor/pi-rp/packages/agent/src/agent-loop.ts:175-193,281-` 在 tool result 后再次 `turn_start`）。

### 1.2 与「上一版设计」的关系（一句话）

上一版（外部 ticket 曾冻结的）「首请求 = 六节 + 祈使句；续接请求 = 六节照旧、仅去掉祈使句」**已被推翻**，本篇不保留该载荷形态：续接请求**完全不注入**。原因见 §2.1 的论证（祈使句在模型动手后即成假话；块在 `agent_start` 冻结，续接本就是陈旧值）。
`docs/layout/07` 的 `renderWriterContinuationBlock(block, firstProviderRequest)`（`:378`）随之作废，见 §4.5 与 §7。

**触发 ≠ 注入**：handler 被调用 N 次，不等于块出现 N 次。

### 3.5 风险三：steer / followUp 中途插入的消息**不重复注入**

### 2.7 提示词侧：**不加**「若已回应则忽略此句」（明确否决）

不改 `extensions/instructions.ts`。理由：`NEXT_STEP_RULES`（`extensions/instructions.ts:37-42`）的立论是「It is computed from the event log at the moment of your request, so **trust it over your own recollection of the turn**」——**要求模型相信它、胜过自己的记忆**。再补一句「若已回应则忽略」等于让模型在同一条指令里同时接收「相信它」与「判断它已失效」两个相反 stance：模型只能在两者间猜，是治标且自相矛盾。**根因在注入粒度，不在措辞**；修好粒度后，首请求里那句话对**该请求**永远是真话。

## 3. 行为契约逐步（每步写「漏了会怎样」）

时序事实：`agent_start` 的 extension 事件在 `agent-loop.ts:109` 发出且被 await，`turn_start{turnIndex:0}` 紧随 `:110`，首请求在 `:116` 的 `runLoop` 内才发生（`agent-loop.ts:193` → `transformContext` → `runner.ts:1133`）。续接请求前，内层循环在 `:176` 再发一次 `turn_start`（`turnIndex` 已被 `:1074` 自增）。

| # | 事件 | 应发生 | 漏了会怎样 |
|---|---|---|---|
| 1 | 玩家提交输入 → `agent_start` | `extensions/context.ts:128-163` **首行** `currentTurnIndex = -1;`（fail-closed 复位），随后算块一次（扫盘 + 两 db + 渲染），`writeTurnBlock(sessionId, block)`，writer 游标结算一次 | 若把重活搬到 `context`：每请求扫盘 + 读库（违反 `00 §2 约束 1/2`）；若省掉首行复位：镜像停在上一 trace 的末值，`turn_start` 前若有 `context` 且该值恰为 0 即误注入（§4.1 加固） |

| 4 | 模型产出 tool call → 执行 → `turn_end` | `_turnIndex++`（`:1074`）；块**不被**重算、缓存**不被**改写；`turn_end` handler 把镜像置 `-1`（§4.1 加固 2）——**无害**，因为下一个 `turn_start{1}` 会立刻把它写回 | 若在 `turn_end` 重算块：把 I/O 拉回循环内，且本 trace 的事实根本没变；若 `turn_end` 不复位：**单请求 trace** 结束后镜像停在 `0`，两 trace 之间的 `/prompt` 会误注入（§4.1 加固 2） |
| 5 | 内层循环再发 `turn_start{turnIndex:1}` | 记录器写入 `1` | 同 #2 |
| 6 | **续接 provider 请求** → `context` | 记录器 ≥1 → handler **直接 `return undefined`**（不改 `messages`，不读缓存，不拼串） | 门若写成「读缓存后判断」仍会读到旧串并贴出 → bug 不变 |
| 7 | 循环重复 4–6 直到无 tool call 或终止 | 整个 trace 只有 #3 那一次注入 | tool loop 越长，重复祈使句越多（旧行为 N 次） |

**latch/变体何时选定**：本设计**没有** latch（无消费位），也**没有**变体（首/续不产出两份不同文本）。唯一「选定」发生在 `context` 调用时对**引擎给的 `turnIndex`** 做一次相等判断；记录器由 `turn_start` 更新，并在**轮边界显式复位**（§4.1 加固：`agent_start` 首行 `currentTurnIndex = -1;`）——引擎自己的 `_turnIndex` 则在其 `agent_start` 分支复位（`agent-session.ts:1032-1033`）。

**加固 1（fail-closed，零成本）**：镜像**只由 `turn_start` 更新**，所以 `agent_start` 对它的复位本来**不可见**。正常路径下这不是问题（`agent-loop.ts:109-110` 与 `:138-139` 两个 loop 入口都在 `agent_start` 之后立刻发 `turn_start{0}`，且 `await` 链完整 → 首个 provider 请求前镜像必然已是 0）。但若将来某条路径在 `turn_start` **之前**触发 `context`，镜像会停在上一 trace 的值——**恰为 0 时就是误注入**。在 `agent_start` handler 首行写 `currentTurnIndex = -1;` 即得 fail-closed：`-1 ≠ 0` → 不注入，下一个 `turn_start{0}` 立刻恢复（`-1` 正是 `extensions/toolkit/turn.ts:14` 的同一初值语义）。

**加固 2（`turn_end` 复位；修一个**真 bug**，评审 ③）**：仅靠加固 1 **不够**。`/prompt` 预览（`previewPrompt()`）在**两 trace 之间**触发时，镜像停在**上一 trace 最后一个** `turnIndex`；若那条 trace 只有**一个** provider 请求（无工具调用——**最常见的情形**），末值**就是 `0`** → 预览会命中 `turnIndex === 0` → **注入一份陈旧块**。也就是说 §4.4 表里「trace 之间读到末值（≥1）」**只对多请求 trace 成立**，是**假保证**（严重度：非数据破坏——不进模型、无消费位——但设计明写的保证在此场景为假）。
**解法**：在 `turn_end` handler 里同样把镜像置 `-1`（`turn_end` 在每轮响应**之后**发射，`agent-loop.ts:205`；扩展 handler 在 `_turnIndex++`（`agent-session.ts:1074`）**之前**被 await，`agent-session.ts:1062-1069`——所以置 `-1` 不会影响该轮任何请求）。于是：**trace 一结束，镜像即 `-1`**；两 trace 之间的任何 `previewPrompt` 命中 `-1` → **不产出**；下一个 `agent_start` + `turn_start{0}` 照常交付。这条与加固 1 合起来使门**对顺序免疫、对 trace 边界免疫**。**（此为唯一需要第 5 个注册的理由。）**

**与 `extensions/toolkit/turn.ts` 的关系**：`turn.ts:16-20` 已经注册了 `turn_start` 消费者（为 A 入口的 turn 锚）。**不冲突**：loader 对每个扩展文件各建一个 `createJiti({moduleCache:false})`（`docs/hooks/00 §9` 约 `:231-236`、`docs/hooks/06 §3.1:112-141` 实测），`turn.ts` 的 `currentTurnIndex` 与 `context.ts` 的记录器是**两个独立模块实例**；且 pi-rp 的 `emit` 会把同一事件依次交给**所有** handler（`runner.ts` 的 emit 循环），两个消费者各自记录、互不覆盖。`context.ts` **不得** import `toolkit/turn.ts`（跨文件读不到其状态）。

**`steer` / `followUp`**：它们在 loop 内部被取出（`agent-loop.ts:182-190`、`:263-268`），**不再触发 `agent_start`**（`docs/hooks/01 §3.5:202-211` 已核实），因此记录器保持 ≥1 → **拿不到块**。
**判定：这是期望行为。** 理由：steering 是**同一玩家回合内**的插话，不是新的 trace；该 trace 的块已在首个请求交付过，其祈使句若在插话后重贴，会重复「重做」指令（正是本 bug 的机制）；且块在 `agent_start` 冻结，插话时的世界变化会经 `dynamics` 出现在**下一次 trace**。

### 4.4 判据评估：`turnIndex`（采用） vs consumption latch（否决）

| 维度 | `turnIndex`（g3，**采用**） | `consumeTurnBlock(sessionId)`（否决） |
|---|---|---|
| 首请求判据 | 引擎确定性量：`agent_start` 置 0（`agent-session.ts:1032-1033`），续接 ≥1 | 首次读即置占位 |
| 复位 | 引擎每 trace 自动置 0；**本站另在 `turn_end` 置 `-1`**（§4.1 加固 2） | 必须自己保证每次 `agent_start` 复位，漏一次就漏注入（§3 步骤 9） |
| 状态量 | 无消费位（只有一个只读镜像 `turnIndex`） | 一个可变消费位；跨 resume/`/tree` 还需另行复位 |
| `/prompt`（`previewPrompt()`）安全性 | **安全**：它直接 `emitContext`、**不经过** `agent_start`/`turn_start`（`agent-session.ts:1850-1857`；调用点 `commands/builtins.ts:436`）。trace 进行中它读到 `turnIndex ≥ 1` → 返回 `undefined`；trace **之间**读到 `-1`（§4.1 加固 2 的 `turn_end` 复位）→ 同样不产出。**永不消耗块，也永不误注入**（仅靠加固 1 时，单请求 trace 的末值 `0` 会导致误注入——见 §4.1 加固 2） | **致命**：用户在 trace 中途敲 `/prompt`，`emitContext` 命中的正是同一个 handler；消费位被这次**诊断调用**吃掉 → 真正的 provider 请求再也拿不到块。这是数据破坏级缺陷 |
| 单测性 | 谓词纯函数可单测（§4.2） | 需要状态机测试 |

**结论：判据选 `turnIndex`（g3），不引入 consumption latch。** 若评审坚持加一层 latch 作**冗余**，它也只能以 `turnIndex === 0` 为前置（即先过门再谈消费位），且**不得**在 gate 之前消费——否则退回 `/prompt` 破坏。本设计按「只用 g3」冻结。

**另一个被否决的候选（显式登记，评审核实，避免后人再提）**：「在 handler 内扫 `event.messages` 里是否已含本 `customType` 块 → 有则 `return undefined`」。**不成立**：块只 append 到 `agent-loop.ts:289-291` 的**局部** messages，**不写回** `agentContext.messages`、不落盘（`context` 路径的本质，`00 §1` 裁决 1）——所以续接请求的 `event.messages` **永远看不到块**，判据恒为「没有」→ 每个请求各贴一份，**bug 不变**。它**唯一**优于 `turnIndex` 处：`previewPrompt()` 仍能拿到块（其输入是 `agent.state.messages`，`agent-session.ts:1850-1852`）——但这条优势只对应 §8.2 待拍板项 1，**不足以换取每请求注入**。`turnIndex` 是必需的。

**旁证**：引擎在 `agent_start` 同时记 `_currentTraceStartIndex`（`agent-session.ts:1034-1036`），说明「trace 起点」在引擎侧是一等概念（`_turnIndex` 声明见 `:509`）。

### 4.5 `renderWriterContinuationBlock` 的最终裁定

**不引入。** `docs/layout/07:378` 提议的 `renderWriterContinuationBlock(block: string, firstProviderRequest: boolean): string` 建立在「续接仍注入一份去掉祈使句的块」这一**已被推翻**的载荷形态上；新裁定下续接请求**不产出任何文本**，该 helper 无用武之地，且会把「续接要不要贴块」这个已裁决的问题重新变成可配置项。
若评审坚持保留一个单一函数做门，最终签名应为：

```ts
/** 01 §3.3 — the payload for a provider request. `null` = do NOT inject. */
export function renderWriterContinuationBlock(block: string, turnIndex: number): string | null {
  return isFirstProviderRequest(turnIndex) ? block : null;
}
```

`extensions/context.ts` 把 `null` 映射为 `return undefined`。**推荐删除该 helper**、直接使用 §4.2 的谓词——少一层间接。

## 6. 验收测试

### 6.1 杀手断言（引擎级探针，`tools/probe-inject.mjs` 重写）

探针现断言**的正是 bug**（「每请求恰好一份」），必须反向重写：

- **A2′（新语义）**：对每个**用户轮**（= 每个 trace），`requestsPerTurn[turn]` 里**恰好 1 个**请求的 `markerCount === 1`，其余 `=== 0`。
- **A4′**：含工具循环的第 2 轮，`requestsPerTurn[1].length > 1` 且 `[1, 0, 0, …]`（首请求 1、续接全 0，而非全体 1）。
- **A3′（新语义；必红项）**：现 A3 断言 `perTurn.every(counts.every(c === 1))`——修复后续接请求 `markerCount === 0`，**该条必红**。反向重写为：对每个用户轮，`counts.filter((c) => c === 1).length === 1 && counts.every((c) => c === 0 || c === 1)`；且**跨轮不累积**（第 k 轮不是 k）。
- **A11（新增，核心判别力断言，评审要求）**：对每个 trace，**「payload 里携带世界状态的 provider 请求个数 === 1」**。判据必须**不依赖 `STATE_HEADER`**（`[World state`）——否则会与 A2′ 同源、被同一假绿骗过。用 provider 落盘的结构量：该请求的 `messageCountOut === messageCountIn`（续接请求**一条消息都不加**）。**这一条是「续接完全不注入」与「续接注入一份去头去尾的事实块」的唯一区分器**（见 §2.8 的判别力说明）。
- **A5**（不变）：session jsonl 里 `airp_world_state` 计数 `=== 0`。
- **A8′（新语义；**必红项**）**：现 A8 断言 `flat.every((r) => markerCount(r) === 1)`——同样**必红**。反向重写为：降级世界（无 `viewpoint` 行）下，每 trace 的**首请求** `markerCount === 1`、续接 `=== 0`，三轮**全部正常完成**（`00 §11` 的「注入永远不能让一轮失败」仍成立）；`Viewpoint:` 节缺席不变。
- **A10（新增；**判别力依赖 seed 时机**，见下方反证）**：祈使句**逐字串**在该 run 的全部 wire texts 里出现次数 **=== 1**。
  逐字串取 `packages/shared/src/render/next-step.ts:48-49` 的 `'The player has just made a choice'`；探针在 seed 阶段 `appendEvent({ type: 'choice_selected', actor: { type: 'player' }, … })`（`next-step.ts:114` 要求**窗口尾部**是该 type **且** `actor.type !== 'writer'`）。
  **⚠️ 期望值必须是 `1`，不是 trace 数（评审 ①，此前两处自相矛盾）**：writer 游标在**每个 trace 的 `agent_start`** 推进到 `getMaxSeq()`（`extensions/context.ts:149-151` → `settleTurnCursor(advance:true)`）；**一次 seed 后第 1 轮游标即越过该事件**，第 2/3 轮事件窗口为空 → 祈使句**只在第 1 个 trace 出现**。所以 `=== 1` 是**唯一确定**的期望值；写「trace 数」会在**正确实现**上误红。

| 口径 | 修复前实测 | 修复后期望 |
|---|---|---|
| `count('[World state')` 于**一次 run** | = provider 请求数 N（`agent_start` 后每个续接请求各 +1） | = 玩家轮数（每 trace 1 个请求带块）；续接请求 = 0 |
| `count('The player has just made a choice')` 于**一次 run** | **= 1**（反证：默认不判别，见下） | **= 1** |
| **带世界状态的请求个数 / trace**（A11，不看 `STATE_HEADER`） | = provider 请求数 N | **= 1**（续接 `messageCountOut === messageCountIn`） |

**哪条能证「没有这个修复就会失败」**：**A2′ / A3′ / A4′ / A8′ / A11 五条**。修复前：A2 断言 `!==1` 即红；A3/A8 的 `every(c === 1)` 直接红；A11 计数 = N 而非 1；A4′ 的 `[1,0,…]` 也红（旧行为全 1）。**A10 不在其中——除非 seed 时机正确**（见下）。

**⚠️ 反证（主代理实测，2026-09-14）：A10 默认不具判别力。** 把 `extensions/context.ts` 的注入门注释掉重跑 `probe-inject.mjs`，**A10 仍然通过**（A2′/A3′/A4′/A8′/A11 全红）。
机制：祈使句源自 seed 的 `choice_selected`，而 writer 游标在**每个 trace 的 `agent_start`** 推进 → 该句**只落在第 1 个 trace**；探针脚本第 1 个 trace **只有 1 个 provider 请求** → 「每请求重贴」也只渲染 **1** 次 → 修复前后都 `=== 1`。
**判别条件**：祈使句必须落在**含工具循环的 trace**（探针 trace 2 = 2 个请求）。故 A10 的 seed **不能**在启动前一次性 `appendEvent`，而要在 **turn 1 完成后、turn 2 开始前**追加 `choice_selected`；此时「每请求重贴」渲染 **2** 次（红）、修复后 **1** 次（绿），期望值仍 `=== 1`。
**实现必须自证**：注释掉门 → A10 红（期望 2）；恢复 → 绿。

**⚠️ A10 单独拦不住其自称能拦的假绿**（评审指出，必改）：A10 只数祈使句逐字串；而「续接贴一份**去掉 `STATE_HEADER` 与 `next_step`** 的事实块」这一变体（`docs/layout/07:377-378`，本篇 §4.5 否决）在续接请求里**既无 marker 也无祈使句** → **A2′ 绿、A10 也绿**。**必须**靠 **A11**（携带世界状态的请求个数，判据与 `STATE_HEADER` 解耦）才能把它与本方案区分开。三条（A2′/A10/A11）缺一不可。

1. **`turnIndex` 在所有入口下都从 0 开始，门不漏**（原未知项已关闭）。`_turnIndex` 的**唯一复位点**是 `agent_start` 分支（`agent-session.ts:1032-1033`）；两个 loop 入口都发 `agent_start` + `turn_start{0}`：`runAgentLoop`（`agent-loop.ts:109→110`）与 `runAgentLoopContinue`（`:138→139`）。`firstTurn` 分支（`agent-loop.ts:175-179`）保证首个 provider 请求前**恰好一次** `turn_start{0}`，`await` 链完整（`:110`）→ 扩展侧镜像在首个 provider 请求（`agent-loop.ts:193` → `:290-291` → `sdk.ts:443`）前**必然已写入 0**，无竞态。error/aborted 也先发 `turn_end`（`agent-loop.ts:197-199`）→ 我们的 `turn_end` handler 同样被调用（§4.1 加固 2），镜像回到 `-1`。
   > **⚠️ 已更正的旧说法**：早前写「trace 结束后镜像恒 ≥1 → 两 trace 之间的 `/prompt` 预览读 ≥1 → 不产出」——**该保证对单请求 trace 为假**（末值就是 `0`，会误注入）。修法 = §4.1 **加固 2**（`turn_end` 置 `-1`），评审 ③。
   > **加固 1**（`agent_start` 首行 `currentTurnIndex = -1;`）使门对 `agent_start`/`turn_start` 的**发射顺序**免疫；**加固 2** 使门对 **trace 边界**免疫。
   > **`continueSession` 补证（评审要求）**：`CreateAgentSessionOptions`（`sdk.ts:68-131`）里**没有** `continueSession` 选项——它只是 `sdk.ts:199` 的一行**文档示例注释**（`sdk.ts:68-131` 逐字段核对，无此字段；`hasExistingSession` 只用于恢复 model/preset，`sdk.ts:237-258`）。同名方法 `AgentSession.continueSession()`（`agent-session.ts:2645-2691`）是 `/continue` 命令（`commands/builtins.ts:602`）的运行时路径，它调用 `_runAgentContinue()`（`:2690`）→ `agent.continue()`（`agent-session.ts:2492-2499`）→ `runAgentLoopContinue`（`agent.ts:427`）→ 发 `agent_start` + `turn_start{0}`（`agent-loop.ts:138-139`）。**结论：无论以何种入口续跑，都经由这两个 loop 入口，`turnIndex` 必从 0 起。**（repo 内 grep `continueSession`：仅 vendor 的上述位置，无 FixSpaceAirp 结论需对齐。）

2. **只有 2 个生产 `emitContext` 调用点**（原 §8.4 未知项已关闭）：① `vendor/pi-rp/packages/coding-agent/src/core/sdk.ts:443`（经 `transformContext`，`agent-loop.ts:290-291` 每请求消费）= 唯一模型路径；② `core/agent-session.ts:1854`（`previewPrompt()`，唯一调用点 `commands/builtins.ts:436`）——不经 `agent_start`/`turn_start`。其余仅测试/脚手架（`vendor/pi-rp/packages/coding-agent/test/extensions-runner.test.ts:765`、`test/suite/harness.ts:181`）；`runner.ts:1133` 只定义不自调用。**判据安全性不受影响。**
