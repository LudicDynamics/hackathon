# 06 — 接线与生命周期（扩展注册 · 身份分节 · 缓存失效 · 只读 · 探针）

> 本文件是 B2/B3 设计批次的第 06 篇，只写**接线与生命周期**：扩展如何被发现、注册什么钩子、`AIRP_AGENT_ROLE` 怎么选分节表、缓存什么时候失效、存储只读与否、子代理为什么没有注入、以及**整批的验收探针**。
> 跨篇共享形状（`Section`、线格式、条目上限、视点表、游标语义、失败纪律）一律以 **`00-共同上下文.md`** 为准，本文只按节号引用，不重述。分节表**内容**（键名、英文格式、来源函数、上限、方位词）归 **02**；`WorldEvent` → 人话渲染器归 **03**；`collectSections` / `renderState` / 三层兜底归 **01**；`viewpoint` 表 DDL / `POST /api/viewpoint` / 共享量化函数归 **05**；`extensions/instructions.ts` 的提示词正文归 **04**。本文只**引用名字**并规定接线。
>
> 结论先行（五条拍板）：
> 1. **一个扩展文件** `extensions/context.ts`，`export default` 一个工厂函数；注册**五样**：上述三样 + `pi.on('turn_start', …)`（门判据）+ `pi.on('turn_end', …)`（trace 结束复位；01 §3.3 / §4.1）。
> 2. **分节表按 `AIRP_AGENT_ROLE` 选**，且**必须由 `context.ts` 自己解析**——不能复用 `extensions/toolkit/actor.ts` 的缓存（loader 配 `moduleCache:false`，两个顶层扩展文件**不共享模块状态**；机制见 §3.1）。
> 3. **缓存不需要 `session_compact` 清空，也不需要挂 `session_start` / `leaf_changed`**。每轮在 `agent_start` 全量重算，缓存每个轮边界被**无条件覆写**；`/new`,`/resume`,`/fork`,`/tree` 换分支后**下一次 `agent_start` 必然重算**。`previewPrompt()`（`/prompt` 预览）现在**什么都不注入**（不触发 `agent_start`/`turn_start` → 门不放行），不喂模型。这是**有意的最小化**（契约 §9.2 允许）。
> 4. **接受读写打开**（否决 `{readonly:true}`）：扩展必须写 `read_cursors`（`local-store.ts:448`），纯只读做不到；`LocalWorldStore` 构造时无条件读写打开两库并跑 DDL（`local-store.ts:63-73`）。并发由 WAL + `busy_timeout=5000`（`db/schema.ts:5-6`、`:91-92`）承担。写进注释，不假装只读。
> 5. **探针是 `tools/probe-inject.mjs`**（NEW），真 spawn 作家 → 3 个用户轮 → 断言注入块**每 trace 恰好一份、不累积、内容正确、不落盘**。它是整批的验收测试（§6）。

## 2. 契约（形状与签名）

### 2.1 文件与默认导出

新建 `extensions/context.ts`，与 `extensions/tools.ts` 同级（**不能**放 `extensions/toolkit/`——子目录不会被当扩展加载，见 §3.2）：

```ts
// extensions/context.ts —— 本批唯一的新顶层扩展文件。
//
// 关键接线事实（机制见 §3.1）：pi-rp 的扩展加载器**逐个文件**调用
// `createJiti(..., { moduleCache: false })`（`vendor/pi-rp/packages/coding-agent/src/core/extensions/loader.ts:503-509`，调用点 :556）。
// `moduleCache:false` 下**每个顶层扩展文件各自一份模块图** —— `context.ts` 与 `tools.ts`
// 各自 import 同一个 `toolkit/*.ts` 会拿到**不同实例**，进程级状态不可跨文件共享。
//（契约 §9 与本文 §3.1 一致：不共享。本文按 **不依赖共享** 写，见 §3.1 / §10-7；
//  即便将来 loader 改成共享，下面的代码也不会错。）
// 因此：本文件自带它需要的缓存（身份解析、分节表），store 走 getter + 自开回落（§5.4）。
import type { ExtensionAPI } from '@earendil-works/pi-coding-agent';
import { resolveAgentActor, readerOfActor, AGENT_ROLE_ENV } from '../packages/shared/dist/index.js';
// 门判据镜像：per-extension-file 模块状态（§3.1），只由 turn_start/turn_end 更新。
// -1 = 「不在任何 trace 内 / 未见过 turn_start」→ 不注入（fail-closed）。
let currentTurnIndex = -1;

export default function registerAirpContext(pi: ExtensionAPI): void {
  // 1) customType 策略（先声明者胜，loader.ts:210-214 —— 只能注册一次）
  pi.registerCustomType(WORLD_STATE_CUSTOM_TYPE, {
    context: 'include',      // 实时上下文可见
    llmRole: 'user',         // 与契约 §4.1 的线格式一致（喂给模型的是一段 user 文本）
    compaction: 'exclude',   // 只从总结输入里剔除；**不是**有界机制（AUDIT §2.3 坑 2）
  });

  // 2) 轮内镜像：注入门判据 + trace 结束复位（§2.2 第 4/5 项；门体见 §4.1）
  pi.on('turn_start', (event) => { currentTurnIndex = event.turnIndex; });   // 门判据
  pi.on('turn_end', () => { currentTurnIndex = -1; });                       // trace 结束复位

  // 3) 轮边界：算一次、缓存、结算游标
  pi.on('agent_start', (event, ctx) => { /* §4.1 */ });

  // 4) 注入接缝：纯、廉价、无 I/O；只在首个 provider 请求产出块（§4.2）
  pi.on('context', (event) => { /* §4.2 */ });
}

/** 注入块的 customType。冻结：测试、日志、诊断都按它断言。 */
export const WORLD_STATE_CUSTOM_TYPE = 'airp_world_state';
```

### 2.2 注册清单（**精确、封闭**）

| # | 注册项 | 参数 | 为什么是这个 | 为什么不是别的 |
|---|---|---|---|---|
| 1 | `pi.registerCustomType(WORLD_STATE_CUSTOM_TYPE, {context:'include', llmRole:'user', compaction:'exclude'})` | 见上 | 声明「这是动态注入层」（`types.ts:1459`；语义 `core/messages.ts:69-91`） | 不填 `renderContent`（§2.4） |
| 2 | `pi.on('agent_start', handler)` | `handler: (event, ctx) => void \| Promise<void>` | **轮边界信号**：每次 agent run 恰好一次（`agent/src/agent-loop.ts:109` / `:138`，经 `agent-session.ts:1032-1037` 转发），**且事件没有 result 类型**（`types.ts:800-802`，`ExtensionHandler<AgentStartEvent>` 即 `void`）——不可能误注入 | 不用 `before_agent_start`：它的 `message` 会被持久化成 `custom_message` 会话条目并**逐轮累积**（`agent-session.ts:2107-2127`，AUDIT S1）。也不用它当轮边界（它带 `systemPrompt` 回写口，容易顺手碰缓存） |
| 3 | `pi.on('context', handler)` | `handler: (event, ctx) => {messages?}`（第二参是标准 `ExtensionContext`，`types.ts:1319`；01 §2.1 同款） | 引擎**唯一的临时注入接缝**：`structuredClone` 后接受替换数组，**不落盘**（`runner.ts:1133-1163`） | 不挂 `before_provider_request`：它拿的是 provider payload（已过 `convertToLlm`），改它等于手改 wire 格式 |
| 4 | `pi.on('turn_start', handler)` | `handler: (event) => void`，记 `event.turnIndex`（`TurnStartEvent`，`types.ts:829-832`） | **门判据**：注入门 + trace 边界复位；与 `toolkit/turn.ts` 各有独立模块实例（`loader.ts:503-509` `moduleCache:false`），`runner.ts` 依次 await 所有 handler → **不冲突** | 不拿它当轮边界（轮边界仍是 `agent_start`） |
| 5 | `pi.on('turn_end', handler)` | `handler: (event) => void`（`TurnEndEvent`），置镜像 `-1` | **trace 结束复位**：`turn_end` 在每轮响应**之后**发射（`agent-loop.ts:205`），扩展 handler 在 `_turnIndex++`（`agent-session.ts:1074`）**之前**被 await（`:1062-1069`）→ 置 `-1` 不影响该轮任何请求，却使两 trace 之间的 `previewPrompt()` 命中 `-1`（不误注入），见 §4.2 加固 2 | 不省略：单请求 trace 的末值恰为 `0`，缺它会让两 trace 之间的 `/prompt` 误注入陈旧块 |

**不注册**（各带理由，写进 `context.ts` 头注释，避免后人「补全」）：

| 不注册 | 理由 |
|---|---|
| `before_agent_start` | 累积（S1）；`agent_start` 已覆盖轮边界信号 |
| `session_compact` | 每轮全量、无指纹，**没有需要重置的东西**（契约 §9.2 / AUDIT §3.3） |
| `session_start` / `leaf_changed` | 最小版不需要（§4.3）；`previewPrompt()` 走注入门后**无块可显示**，且不喂模型 |
| `tool_result`（只兜 `write`/`edit` 那条） | 属于事件表写入侧（doc-21 §2 入口 B），不是本批 |
| 任何 `state_*` / 状态文件 / 状态命名空间 | 契约 §12 第 5 条，AGENTS.md §3.2 |

> **与 `extensions/toolkit/turn.ts:16-20` 的关系（不冲突）**：它也注册了 `turn_start`（为 A 入口的 turn 锚），但 loader 对每个扩展文件各建一个 `createJiti({moduleCache:false})`（`loader.ts:503-509`，调用点 `:556`）——两个文件各有**独立模块实例**；且 pi-rp 的 emit 依次 await 所有 handler（`runner.ts`），两个消费者各自记录、互不覆盖。

### 2.3 `context` handler 的形状（纯函数边界）

> **handler 体不自造第二份**：唯一版本是 **`01 §2.1`**，本文只引用、不复制。它三步（**顺序不可换**）：
> 0. **先过注入门**——`if (!isFirstProviderRequest(currentTurnIndex)) return;`（`currentTurnIndex` 由 §2.1 的 `turn_start`/`turn_end` 记录器维护；判据 `00 §2` 约束 4 / 01 §3.3）。门放**最前** = 续接请求零成本（不读缓存、不拼串）。
> 1. **再过滤旧块**——`event.messages.filter(m => !(m.role === 'custom' && m.customType === WORLD_STATE_CUSTOM_TYPE))`。引擎今天确实不累积（S2 实测），但把「**每 trace 恰好一份**（首个 provider 请求）」当**本地不变量**，而不是对引擎行为的假设。
> 2. **再取本轮缓存**——`readTurnBlock(ctx.sessionManager.getSessionId())`（01 §3.2 的单槽缓存）；`null` 即 `return`（不注入，契约 §11）。
> 之后**尾追加**一条 `role:'custom'` 消息（字段见 01 §2.2）。**它绝不调用 `renderState`**（那会在每个请求重渲染，违反契约 §2 约束 1），也不碰 `systemPrompt`。

- **尾追加**，不插中间、不碰 `systemPrompt`（契约 §2 约束 3、§12 第 4 条）。
- `display: false`：`CustomMessage.display`（`core/messages.ts:110`）。
- **每次 LLM 调用都会触发**（`runner.ts:1133`；调用点 `core/sdk.ts:427-449` 的 `transformContext`，被 `agent/src/agent-loop.ts:290-291` 逐请求消费）——所以 handler 只做字符串取值与拼接，**不做任何 I/O**（契约 §2 约束 1）。
- 同一个 run 内的工具循环轮会各触发一次，但**只有第一个 provider 请求产出块**：其后 handler 返回 `undefined`（不改 `messages`）。判据是引擎 `turnIndex`（首请求 === 0），见 `docs/hooks/07-注入粒度修复设计.md §4.1`。旧正文「每次各注入一份……这是期望行为」作废——那是同一玩家回合重复生成祈使句的根因。

### 2.4 不注册 `renderContent`（有意简化，写进注释）

`convertToLlm` 把 custom 转成普通 user 消息时**丢掉 `customType`**（`core/messages.ts:268-294`；AUDIT §2.3 坑 3），所以跨 seam 的身份只能靠 `renderContent` 包一层标记。

**本批不用它**，理由：`context` 路径下注入块**从不落盘**（`agent-loop.ts:290-291` 的返回值只用于本次 provider 调用），也就**没有一次存储往返需要活下来**。身份由**文本首行的固定标记**承担（契约 §4.1 的 `[World state]` 前缀，§6 探针就按它计数）。若将来有人把注入块改成持久路径，**必须**同时补 `renderContent`——把这句写进注释。

> **片段记号约定（全篇）**：代码块里出现的 `worldStoreFor()`、`ownStore()`、`warnOnce()` 都是**本文件的局部 helper**（`context.ts` 内），**不是**要 import 的符号——实现时用内联代码即可，不要去找同名导出。**真正存在的**符号一律带 `file:line` 或标注 NEW：`makeSectionDeps` / `collectSections` / `buildNextStepFacts`（**01**，NEW，家 `packages/shared/src/inject/collect.ts`）、`writeTurnBlock` / `readTurnBlock`（**01**，NEW，家 `packages/shared/src/inject/turn-cache.ts`）、`renderState`（**01**，NEW）、`sectionsFor` / `WRITER_SECTIONS` / `CHARACTER_SECTIONS`（**02**，NEW）、`settleTurnCursor`（**03**，NEW，家 `packages/shared/src/store/cursor.ts`）、`readViewpoint`（**05**，NEW）、`peekWorldStore`（**06**，NEW）、`resolveAgentActor` / `readerOfActor` / `AGENT_ROLE_ENV`（`packages/shared/src/actions/actor.ts:14/23/53`，已存在）、`WORLD_STATE_CUSTOM_TYPE`（`extensions/context.ts`，NEW）。

## 3. `AIRP_AGENT_ROLE` 分节

### 3.1 前提实测：模块状态**不跨扩展文件共享**（一致结论，含机制与鲁棒性）

**实测环境**：pi-rp 的加载器用 **`jiti/static`**（`loader.ts:17`）并且**显式设 `moduleCache: false`**：

```ts
// loader.ts:495-520 loadExtensionModule()
const jiti = createJiti(import.meta.url, { moduleCache: false, ... });  // :503-509
// 每个 extensionPath 调一次（loadExtension 的 :556 调用点）
```

**实测矩阵**（fixture：`shared.ts` 一个模块级计数器；`f1.ts` 先 bump，`f2.ts` 读同一计数器——`f2=0` 即不共享）：

```
per-file createJiti, moduleCache:false  （= loader 配置）→ f1()=1  f2()=0   # 不共享
per-file createJiti, 默认 opts(=true)                   → f1()=1  f2()=1   # 共享
one shared jiti,     moduleCache:false                  → f1()=1  f2()=0   # 不共享
one shared jiti,     默认 opts(=true)                   → f1()=2  f2()=2   # 共享
```

**机制结论：决定变量是 `moduleCache`（不是「几个 jiti 实例」）。** loader 显式关掉它（`:504`），所以**运行时真实行为是「不共享」**——`extensions/context.ts` 拿不到 `extensions/toolkit/actor.ts` 的 `agentActor()` 缓存实例。契约 §9 的口径与本条一致。

> **读数陷阱（两方一度以为矛盾）**：若 fixture 是「两个文件**各自** bump」（而非 bump/read），不共享时**每个文件各从 0 起**，会读到 `A=1`、`B=1`——与「共享」下的 `f1=1, f2=1` **数字相同、含义相反**。比较分享结论时**必须用 bump/read 配对**，否则数字会骗人。

**关键：本设计的结论不依赖 loader 是否共享模块**（loader 将来改配置也不会坏）：
1. **分节选择不依赖共享。** `sectionsFor(actor)` 在 `context.ts` 的工厂里按 `AIRP_AGENT_ROLE` 解析（§3.3）——只要 `resolveAgentActor` 是纯函数（`actions/actor.ts:23-46`），无论模块是否共享，结果都一样。**不要**写「复用 toolkit 的 actor 缓存」。
2. **store 连接用 getter 且回落到自开**（§5.4）——共享时复用 B1 的连接，不共享时自开一个。

唯一会被共享与否**改变**的是「进程内 SQLite 连接数」（1 个 vs 2 个），而 WAL 下两者都无害。

**推论（归 02，见 §10-7）**：「不共享」一旦成立，`extensions/` 下的模块级常量**只有本文件可见**——分节表常量与共享量化函数必须放 `packages/shared/`，不能放 `extensions/`。

### 3.2 发现机制（为什么必须是顶层 `extensions/*.ts`）

`apps/server/src/engine/presets.ts:124-149`：

```ts
const searchDirs = [path.join(repoRoot, 'extensions')];                    // :126
if (worldRoot) searchDirs.push(path.join(worldRoot, 'extensions'));        // :127-129
for (const file of fs.readdirSync(dir)) {                                  // :133  只 readdir，不递归
  if ((file.endsWith('.ts') || file.endsWith('.js')) && …) args.push('--extension', …); // :134-141
}
```

- 只扫**顶层**：`extensions/toolkit/*` 永远不会被当扩展加载（`extensions/tools.ts:4-7` 同一结论）。所以 `context.ts` 必须与 `tools.ts` 同级。
- 也扫**世界级** `<worldRoot>/extensions/`：世界可以带自己的扩展。
- 筛选跳过 `.d.ts` / `.test.ts` / `.spec.ts`（`:136-138`）。
- 文件顺序由 `readdirSync` 决定 → **`registerCustomType` 先声明者胜**（`loader.ts:210-214`）意味着：若某个世界级扩展也叫 `airp_world_state` 且先加载，本扩展的注册是**静默空操作**。登记为已知坑（§8 待确认 6）；生产仓库里没有第二个声明者。

工厂函数形状：**`export default function (pi: ExtensionAPI): void`**。loader 对非函数默认导出返回错误串（`loader.ts:558-560`："Extension does not export a valid factory function"），而 `extensionArgs` 侧静默——「注册了但没生效」外部看不出来，**只能靠 §6 探针的可观测断言兜住**（与 `extensions/tools.ts:37-47` 同一理由）。

### 3.3 解析与分节（复用 toolkit 的**模式**，不复用它的**实例**）

`extensions/toolkit/actor.ts:17-31` 是本仓库的既有先例：**resolve 一次、warn 一次**；注释点明「逐次日志会在一次 scene-init 里刷十几次 stderr」。本文件照抄该模式，但是**副本**：

```ts
// 会话语义 = 一个 agent 一个进程（契约 §9）。工厂每次进程启动只跑一次，所以直接在
// 工厂里解析即可，不需要懒加载，也不需要 actor.ts 那个 warned 标志位。
// 注意「进程级」的覆盖范围：loader 配 moduleCache:false（§3.1），本文件的模块级状态
// **只对本文件可见**——不要想拿它去当另一个扩展文件的缓存。
const resolved = resolveAgentActor(process.env[AGENT_ROLE_ENV]);
const actor = resolved.actor;
if (resolved.warning) process.stderr.write(`[airp/context] ${resolved.warning}\n`);
const sections = sectionsFor(actor);          // 02 导出；writer→6 节，character:<id>→4 节
const reader = readerOfActor(actor);          // 'writer' | 'character:<id>' | null（actions/actor.ts:53）
```

- `resolveAgentActor` 是**纯函数、永不抛**（`packages/shared/src/actions/actor.ts:23-46`），整个退化表可单测；`AGENT_ROLE_ENV` = `'AIRP_AGENT_ROLE'`（同文件 `:14`）。
- 退化行为：未设 / 空 / `character:` 空 id / 未知值 → **一律退回 writer** 并给 warning（`:28-45`）。`scene-init` / `nook-init` 也退回 writer 且**不报警**（`:31-33`，它们合法继承父进程 env）。

## 4. 缓存与失效

### 4.1 轮边界（`agent_start`）算一次

```ts
// 说明：本骨架只做「接线」。所有重活与失败语义都在 01 的函数里（01 §4/§5），
// 这里不复制它们的实现，只按 01 冻结的签名调用。
pi.on('agent_start', async (event, ctx) => {
  currentTurnIndex = -1;                                 // 加固 1：fail-closed 复位（§4.2）
  const sessionId = ctx.sessionManager.getSessionId();   // 缓存键（01 §3.2）
  try {
    // 01 §4.7：makeSectionDeps 解析一次 deps.layer / viewport / 事件备忘录。
    // `sections` 是 §3.3 工厂里 sectionsFor(actor) 得到的分节表（02）。
    const deps = await makeSectionDeps({ store: worldStoreFor(ctx), actor, reader, specs: sections });
    const collected = await collectSections({ ...deps, specs: sections });   // 01 §4.1，逐节 fail-soft
    // 01 §4.5：facts 是**异步**构建（要读事件窗口备忘录），没有同步的 nextStepFactsFrom。
    const facts = await buildNextStepFacts(deps, collected);
    const block = renderState(collected, facts);           // 01 §4.2：纯、同步、永不抛、永不返空串
    writeTurnBlock(sessionId, block);                      // 01 §3.2 单槽缓存；null 才表示不注入
    // 契约 §6.2 第 2 条：**只有作家**在轮边界推进游标。
    // 角色进程也加载这个扩展（apps/server/src/engine/launch.ts:129-130 展开 extensionArgs），
    // readerOfActor 对角色返回 'character:<id>'——所以 `if (block && reader)` 是 bug：
    // 角色每轮会把角色游标推到 getMaxSeq()，正是契约明令禁止的「开遮罩时就推进」。
    // 角色游标由 03 拥有、在 server 进程于关遮罩时结算（§4.4）。
    if (actor.type === 'writer') {
      await settleTurnCursor(worldStoreFor(ctx), reader, { advance: true });
    }
  } catch (err) {
    writeTurnBlock(sessionId, null);                       // L3：整块 null → 不注入（契约 §11 第三层）
    warnOnce('[airp/context] state block assembly failed', err);
  }
});
```

> **为什么守卫是 `actor.type` 而不是 `reader`**：见下 §4.4。`block` 永远是非空串（01 §4.2 的 `renderState` 永不返空串），所以 `if (block)` 恒真、不构成守卫。

- `agent_start` **必然先于**该 run 的第一个 provider 请求：`agent/src/agent-loop.ts:109`（`emit agent_start`）在 `:116` `runLoop()` 之前，且 `emit` 是 await 的（`agent-session.ts:1037` → `_handleAgentEvent` 的 `await this._emitExtensionEvent(event)`）。
- **重活只在这里**（扫盘 / 读两个 db / 渲染），符合契约 §2 约束 2。
- 缓存键 = `sessionId`（**01 拥有缓存实现**）。本文件把 `ctx.sessionManager.getSessionId()` 交给 01 的缓存（`toolkit/turn.ts:31` 已用同一 API）。
### 4.2 注入只读缓存 + 注入门

`context` handler 先过**注入门**（`if (!isFirstProviderRequest(currentTurnIndex)) return;`，`currentTurnIndex` 由 §2.1 的 `turn_start`/`turn_end` 记录器维护），再取 `readTurnBlock(sessionId)` 的字符串并拼消息（§2.3）。**没有 I/O，没有指纹，没有差分**（契约 §1 裁决 2、§12 第 9 条）。

门与缓存都**只读**：判据是引擎自带的 `turnIndex`（首请求 === 0；`agent_start` 在 `agent-session.ts:1032-1033` 把它置 0，续接请求 ≥1 见 `:1055-1061`、`:1064-1074`）。`previewPrompt()` 既不触发 `agent_start` 也不触发 `turn_start`（`:1850-1857`），所以它**永不消耗块、也永不误注入**——这是否决 consumption latch 的理由（`docs/hooks/07-注入粒度修复设计.md §4.4`）。

**加固 1（fail-closed）**：镜像只由 `turn_start` 更新，`agent_start` 对它的复位本来不可见 → 在 `agent_start` handler **首行**写 `currentTurnIndex = -1;`（§4.1 骨架），使门对 `agent_start`/`turn_start` 的**发射顺序**免疫（`-1 ≠ 0` → 不注入；下一个 `turn_start{0}` 立刻恢复）。

**加固 2（`turn_end` 复位）**：单请求 trace（无工具调用，最常见）的末值恰为 `0`，只靠加固 1 会让**两 trace 之间**的 `/prompt` 预览命中 `turnIndex === 0` 而误注入陈旧块。所以在 `turn_end` 也置 `-1`（§2.2 第 5 项）。`turn_end` 在每轮响应之后发射、扩展 handler 在 `_turnIndex++` 之前被 await → 置 `-1` 不影响该轮任何请求。加固 1 + 2 合起来使门**对 trace 边界免疫**。

`renderState` 的产物是**每 trace 自足的全量**（契约 §0 / §3.1 `text` 必须自足）。缓存只让 handler 变纯，**不是**「上一轮记忆」——这是与 doc-22 §4 指纹 Map 的根本区别。

### 4.3 失效：**不做**，并说明为什么这是对的

| 事件 | 会触发吗 | 本设计的行为 | 依据 |
|---|---|---|---|
| `session_compact` | 压缩后触发，事件体**不带 sessionId** | **不需要清缓存** | 每轮全量重算、无指纹（契约 §9.2；AUDIT §3.3 已作废 doc-22 §4 规则 5） |
| `/new`、`/resume`、`/fork` | **不触发 `session_compact`**；触发 `session_start`（reason `new`/`resume`/`fork`） | 由**键含 sessionId** + 下一轮无条件重算兜住 | `types.ts:622-628`；AUDIT §2.4 |
| `/tree` 换分支 | 不触发 `session_compact`；触发 `leaf_changed` | 同上（下一次 `agent_start` 必然重算） | `types.ts:720-724`；AUDIT §2.4 |

**最小正确行为 = 什么都不挂。** 论证两步：

1. **缓存不是备忘录。** 它每个 `agent_start` 都被**无条件覆写**（§4.1），没有任何「沿用上一轮」的路径。所以「失效」这件事在本设计里**不存在**——不存在的东西不需要清。
2. **`/prompt` 预览不再有陈旧窗口**：分支切换后、下一次 `agent_start` 之前，`previewPrompt()`（`agent-session.ts:1850-1857`，它也调 `emitContext`）**不经过 `agent_start`/`turn_start`** → 过不了注入门（trace 间镜像为 `-1`）→ 预览**什么都不注入**。所以既没有「上一分支的块」可显示，也**永不消耗块**。为它挂两个钩子仍然不值。

**有意简化的前提是「一个进程一个会话」**（契约 §9：模块级状态 = 进程级 = 会话级；`launch.ts` 用 `--session` / `--continue` 钉住一个会话文件）。若将来出现长驻进程多会话复用，**必须**补：

```ts
// 清空 = 往当前会话的槽写 null（01 §3.2 的 writeTurnBlock）。
// 这两个钩子的事件体带 sessionId，直接透传即可（实现时按 pi-rp 的事件类型填）。
pi.on('session_start', (event) => { writeTurnBlock(event.sessionId, null); });
pi.on('leaf_changed',  (event) => { writeTurnBlock(event.sessionId, null); });
```

把这段写进 `context.ts` 注释（契约 §9.2 要求「在注释里写清这是有意的简化」）。

### 4.4 游标结算的接缝（与 03 的分工）

- **本批只为作家结算，且轮边界带 `actor.type === 'writer'` 守卫**：`settleTurnCursor(store, reader, { advance: true })` 在 §4.1 的轮边界调用**一次**。函数归 **03**，**家在 `packages/shared/src/store/cursor.ts`（NEW）**，经 barrel `packages/shared/src/index.ts` 导出——**不能放 `extensions/`**：角色那侧的调用点在 **server 进程**（见下），而 `extensions/` 在 pnpm workspace 之外、只被 agent 的 jiti 加载，server import 不到（`extensions/toolkit/deps.ts:13-18`）。扩展侧按相对路径 `../packages/shared/dist/index.js` 引它。**守卫由 `actor.type` 承担，不是 `reader !== null`**：角色进程也加载本扩展（`launch.ts:129-130` 展开 `extensionArgs`），`readerOfActor` 对角色返回 `'character:<id>'`（`actions/actor.ts:53`），只查 `reader` 会让角色每轮推进（契约 §6.2 第 2 条）。
- **03 冻结的签名**（06 引用，不重定义）：

  ```ts
  export async function settleTurnCursor(
    store: WorldStore,
    reader: string | null,
    opts?: { advance?: boolean; seq?: number; onWarn?: (m: string) => void },
  ): Promise<void>;   // reader===null 或 advance===false 时空操作；默认 seq = await store.getMaxSeq()；永不抛
  ```

  即契约 §6.2 的「注入成功后推到 `getMaxSeq()`」——`writeCursor(reader, await getMaxSeq())` 包了一层 fail-soft。
- **绝不在 `context` handler 里推进**：那会在工具循环的每个请求各推一次，等于没消费（契约 §6.2「一个坑」）。
- **角色侧不归本扩展**：同一个函数在 **server 进程**被调用**第二次**，`reader = 'character:<id>'`，触发点是**关遮罩**——今天的帧是 `character_stop`（`apps/server/src/index.ts:141-163`，紧随 `lifecycle.stopCharacter`，`apps/server/src/engine/lifecycle.ts:117-124`）；**开遮罩**要触发角色进程 spawn 并把"开时高水位"记下来（`seq` 在关遮罩时传给 `settleTurnCursor`）。扩展在**另一个进程**，看不到这些帧。**拥有者是 03（事件段篇）**，契约 §6.2 已写死；06 只负责把 03 定的调用挂上。

## 5. 存储：只读还是读写（**拍板：读写**）

### 5.1 doc-22 §6 的断言不成立

doc-22 写「server 写、扩展**只读打开**，开 WAL」。**当前代码里没有只读路径**：

- `LocalWorldStore` 构造时**读写打开两个 db 并跑 DDL**：`packages/shared/src/store/local-store.ts:63-73`（`new DatabaseSync(path)` 无 options → 默认读写；紧跟 `initCanvasDatabase` / `initHistoryDatabase`）。
- 扩展用的就是它：`extensions/toolkit/deps.ts:18`、`:37`（`new LocalWorldStore(root)`）。
- AUDIT §4.3 已登记同一条。

### 5.2 裁决与理由

**接受读写打开，不新增 `{readonly:true}` 路径。** 三条理由：

1. **纯只读做不到。** 扩展必须写 `read_cursors`（`local-store.ts:448-462`）。契约 §10 已定：要么新开只读路径、要么接受读写；**选后者**。只给 canvas 只读、history 读写是**最糟**的——两个 db 权限语义不同，会制造一类只在深夜复现的 bug。
2. **代价不对称。** `LocalWorldStore` 是动作层的共用存储门面（`packages/shared/src/actions/*` 全部经 `createActionService`）。加一个构造参数要改构造函数、DDL 调用、`close()`、以及两端 `deps.ts`，收益是「一个本来就要写的库少开一个写事务」。
3. **并发已经有答案。** 两端各自 `new` 一个 store 是**既定架构**（AGENTS.md §3、docs/tools/00 §1），两库都是 `journal_mode = WAL` + `busy_timeout = 5000`（`db/schema.ts:5-6`、`:91-92`）。

### 5.3 要在注释里写明的三件事

```ts
// 存储：**读写打开**，不是只读（契约 §10，否决 doc-22 §6 的「扩展侧只读打开」）。
//  - LocalWorldStore 构造时无条件读写打开 canvas.db / history.db 并跑 DDL
//    （packages/shared/src/store/local-store.ts:63-73）。
//  - 本扩展**必须**写 read_cursors（同文件 :448），纯只读做不到。
//  - 并发由 WAL + busy_timeout 承担（packages/shared/src/db/schema.ts:5-6, :91-92）。
// 副作用要知道：**agent 进程的 store 构造也会跑 DDL** —— 也就是说 `viewpoint` 表
// 不只由 server 建，作家进程一起来就会建一次（CREATE TABLE IF NOT EXISTS 幂等，无副作用，
// 但实现者必须知道它不是「server 专属」）。
//
// ⚠️ **扩展侧绝不得让 LocalWorldStore 触发 DDL 重建**（评审 A-10；这是并发风险，
//    不是「无害的第二连接」）。initCanvasDatabase 里带着**形状探测式重建**：
//    presence / links 在缺 UNIQUE / 缺新列时走 `DROP TABLE` 再 `CREATE`
//    （packages/shared/src/db/schema.ts:29-58 presence / :117-136 events）。这段 DDL 在**每次 store 构造**
//    时都跑（local-store.ts:71-72）。若扩展「再开第二个连接」时形状探测判断漂移
//    （例如两端对 `links` 列的预期不一致），扩展会在服务端正在服务的库上
//    `DROP TABLE presence/links` —— **并发写入下的数据丢失**。
//    WAL + busy_timeout **不挡 DDL**（DDL 拿排他锁，busy_timeout 只是等待）。
//    纪律：扩展侧只**复用** B1 已建好的 store（§5.4 的 getter）；连接数最多 2 是上限，
//    **任何**让 `LocalWorldStore` 在扩展侧触发 rebuild 的改动都必须先登记。
```

### 5.4 与 `extensions/toolkit/deps.ts` 的连接方式（**必须走 getter**）

因为 §3.1 的机制（`moduleCache:false` 下不共享；该分歧在两种读法下都不影响本方案的正确性），`context.ts` **不能假设** `deps.ts` 里的 store 缓存是自己的。契约：

- **本轮新增导出**（06 负责，落点在 `deps.ts`）：`export function peekWorldStore(): LocalWorldStore | null` —— 只读窥视 B1 的 store 缓存，**不构造**。
- `context.ts` 的取值顺序：`peekWorldStore() ?? ownStore(ctx)`，其中 `ownStore` 是 `context.ts` 自己的懒加载 store（`new LocalWorldStore(ctx.cwd)`；`ctx.cwd` 是**世界根**，`launch.ts` 把进程 cwd 钉在世界根）。
  - **共享时**（jiti 缓存命中）：`peekWorldStore()` 命中 B1 的 store → 进程内只有 1 个连接。
  - **不共享时**（loader 的 `moduleCache:false`）：`peekWorldStore()` 走的是 `deps.ts` 那份副本的缓存——如果 `tools.ts` 已跑过工具就命中，否则 null，`context.ts` 自开一个。**最坏 = 进程内 2 个连接**（各含 canvas + history），WAL 下无害。
  - 两种读法都正确，因为 `peekWorldStore()` **不是**正确性依赖，只是一个省连接的优化；**回落到自开永远安全**。
  - 两个连接写同一个 `read_cursors` 行：**只有 `context.ts` 的这条路径会写游标**（工具侧今天没有任何 `writeCursor` 调用点，AUDIT §4.1），所以没有写者竞争。
  - **不要**为了让 `tools.ts` 与 `context.ts` 共用一个 store 而把 store 缓存搬进一个新的共享 helper 模块并宣称「这样就有进程级单例了」——那取决于 §3.1 的未决分歧，**不构成可靠保证**；按「回落到自开」写就不会错。

### 6.2 探针怎么「看见」LLM 载荷

`RpcClient` 把 agent 起成**子进程**（`tools/probe-tools-engine.mjs:40-47`），探针进程**读不到**子进程内存里的 provider 状态。所以 provider 把**每个请求的完整消息数组**追加写到探针指定的一行 JSON 文件：

```ts
fs.appendFileSync(process.env.AIRP_INJECT_PROBE_OUT!, line + '\n');
```

- 环境变量由**探针显式传入**（同 `probe-tools-engine.mjs:44` 的 `PI_OFFLINE` 手法）：`env: { ...spec.env, AIRP_INJECT_PROBE_OUT: outFile }`。
- `textOf` 把 `content`（string 或 block 数组）拍平成文本；注入块在 wire 上是 `role:'user'` 的纯文本（§2.4），能被拍平。
- provider 脚本化：第 1、3 轮返回纯文本；**第 2 轮返回一次 `chalk` 工具调用**（仿 `tool-probe-provider.ts:88-104`），让该 run 内部产生**工具循环的多请求**，以覆盖「一轮内多请求」的情形。

1. **误判成 writer 的次生风险**（§8 表）：未知 role 一律退回 writer 是 B1 已定的退化策略（`actions/actor.ts:28-45`），本批不改。但若真发生，两个进程会写同一行 `read_cursors['writer']`。**建议**：不改退化策略，只在 `context.ts` 的 warn 里把 reader id 一并打出来，便于事后定位。**待明月确认是否需要更严的处置。**
