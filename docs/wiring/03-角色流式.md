# docs/wiring/03 — 角色流式（A3：`CharacterModal` 接真实流）

> 2026-09-12。本文只写设计，**不改任何代码**。权威地基是 `docs/wiring/00-共同上下文.md`（下称 00），本文件 MUST NOT 改动 00 冻结的形状。
> 帧名清单唯一真相源：`docs/tools/12-工具注册与路由统一.md §6.2`。两条通道模型：`docs/tools/00 §5.3`。
> 每条断言带 `file:line`；不确定标 `[推断]`。

---

## 1. 一句话定位

把 `CharacterModal` 从"本地随机假台词"改造成**真实角色 agent 的流式显示端**：`useWorld` 把 `character_delta`/`character_message`/`character_idle` 帧转成一个 window 事件，`App` 按 `activeModalCharId` 路由，`CharacterModal` 用一个"可增长缓冲 + 节拍泵"把帧渲染成逐字台词、把 `[emo: tag]` 变成立绘表情与瞬时 stinger；假台词库降级为**沉默兜底**，开场硬编码台词删除。

## 2. 签名参数

### 2.1 新增前端契约：`airp:character-frame`（useWorld → App，window CustomEvent）

| 项 | 值 |
|---|---|
| 事件名 | `airp:character-frame`（沿用 `airp:world-event` / `airp:item-drag-start` 惯例：`App.tsx:150`、`RightSidebar.tsx:87`） |
| `detail` | 原始帧 `msg` **逐字**（`{ type, source, characterId?, delta?/text?, timestamp }`） |
| 派发者 | `apps/web/src/state/useWorld.ts` 的 `onmessage`（`:265-322`），新增 4 个字面量 `case`（三条角色演出帧 + 带 guard 的 `error`） |
| 订阅者 | `apps/web/src/App.tsx`（唯一订户），路由后以 prop 下传 |
| 过滤器归属 | **App**（`activeModalCharId` 是"当前打开遮罩"的唯一真相源，`App.tsx:47`）。`CharacterModal` 不做任何 `characterId` 比较 |

三条角色帧的派发**无条件**（不写"有 id 才发"分支）：00 §3 末段冻结「`characterId` 缺失时按当前打开的角色遮罩兜底」——A1 落地前所有帧都没有 `characterId`，条件派发会让单角色世界直接哑掉。唯一例外是 `error` 帧：它只在 `source === 'character'`（且带 `characterId`）时派发，见 §2.2、§11 冲突 1。

### 2.2 `useWorld` 侧

`UseWorldApi`（`useWorld.ts:50-72`）**不加成员**（与 02 已对齐）。改动仅在 `onmessage` 的 `switch`（`:276-318`）内新增四条分支（三条角色演出帧 + 一条带 guard 的 `error`）：

```ts
// 演出帧通道（docs/tools/12 §6.2）。帧不碰 state、不 refetch、不走 §4 的
// seenEventIds 去重——它们不是 world_event 通道。
case 'character_delta':
case 'character_message':
case 'character_idle':
  window.dispatchEvent(new CustomEvent('airp:character-frame', { detail: msg }));
  break;
// error 只在"角色车道"的报错上复用同一 seam（裁决 A-err，§11 冲突 1）：
// writer 车道（index.ts:99/:112，无 characterId）留 default，绝不灌进角色遮罩。
case 'error':
  if (msg.source === 'character' && typeof msg.characterId === 'string') {
    window.dispatchEvent(new CustomEvent('airp:character-frame', { detail: msg }));
  }
  break;
```

必须是**字面量 `case` 标签**：`tools/check-ws-contract.mjs:129` 只认 `case 'x'` / `msg.type === 'x'` 两种写法，`const F = 'character_delta'; case F:` 对门禁不可见。

### 2.3 `CharacterModal` 新增 props

```ts
interface CharacterModalProps {
  characterId: string;
  avatar?: string;
  bio?: string;
  onClose: () => void;
  onSendMessage?: (msg: string) => void;
  locale?: 'en' | 'ja';
  /** 最近一条属于本角色的真实帧；App 已按 activeModalCharId 过滤。null = 无。 */
  incoming?: CharacterFrame | null;
}
```

`incoming`（数据下推）**取代**任务书里备选的 `onDelta`（命令下推）：

- `onDelta` 要求 App 在 render-adjacent 的 effect 里调用一个命令式 handler，等于把"谁来喂"和"何时喂"拆到两个文件；`incoming` 是声明式的——"渲染这一帧"。
- React 19（`apps/web/package.json:14`）下 prop 变化驱动 effect 是既有惯例，且 identity 变化天然保证"两条内容相同的帧被处理两次"。
- 跨组件（useWorld→App）走 window 事件、同树父子（App→Modal）走 prop：前者是仓库既有 seam（`App.tsx:150`、`RightSidebar.tsx:87`、`CardRenderer.tsx:104`），后者是 React 惯例。不引入 React context（00 §8.1 的纪律是"字面量就是契约"，context 会把它藏起来）。

### 2.4 帧类型

export type CharacterFrame =
  | { type: 'character_delta'; characterId?: string; delta: string; timestamp?: string }
  | { type: 'character_message'; characterId?: string; text: string; timestamp?: string }
  | { type: 'character_idle'; characterId?: string; timestamp?: string }
  | { type: 'error'; source?: string; characterId?: string; message: string; timestamp?: string };

**家**：`apps/web/src/components/overlay/CharacterModal.tsx`（`export type`），App 已 import 该模块（`App.tsx:5`），零新增 import 面。`useWorld` 派发时不引用该类型（`detail: msg` 保持无类型），因此 state 层不依赖 UI 层。备选：放 `useWorld.ts` 并 export（语义上"WS 消费点拥有帧词汇"），见 §12。

## 3. 行为契约逐步（每步写"漏了会怎样"）

### 步骤 0：`useWorld` 收到角色帧 → 无条件派发

帧源：`event-bridge.ts:59`（`character_delta`，载荷 `{type, source, delta, timestamp}`）、`:70`（`character_message`，`{type, source, text, timestamp}`）、`:183`（`character_idle`，`{type, source, timestamp}`）；`timestamp` 由 `push` 统一附加（`event-bridge.ts:52`）；A1 落地后每条再附加 `characterId`（00 §3.4）。

**漏了会怎样**：`check:ws` 继续报两条 DARK（`character_delta`、`character_idle`）；遮罩永远收不到任何真实帧，本改造整体不成立。

### 步骤 1：`App` 订阅并按 `activeModalCharId` 路由

在既有的 world-event 订阅 effect（`App.tsx:148-152`）之后新增一个同形状的 effect，deps = `[activeModalCharId]`：

```ts
const [activeModalFrame, setActiveModalFrame] = useState<CharacterFrame | null>(null);

useEffect(() => {
  const onCharacterFrame = (e: Event) => {
    const msg = (e as CustomEvent).detail as CharacterFrame | undefined;
    if (!msg || typeof msg.type !== 'string') return;
    if (msg.characterId !== undefined) {
      if (msg.characterId !== activeModalCharId) return;        // 多角色：不是这个遮罩的帧
    } else if (activeModalCharId === null) {
      return;                                                    // 无 id 且没有遮罩 → 无可归属
    }
    setActiveModalFrame({ ...msg, characterId: msg.characterId ?? activeModalCharId ?? undefined });
  };
  window.addEventListener('airp:character-frame', onCharacterFrame);
  return () => window.removeEventListener('airp:character-frame', onCharacterFrame);
}, [activeModalCharId]);
```

- `{ ...msg }` 保证**每条帧都是新对象 identity**，`CharacterModal` 的 `useEffect([incoming])` 才必然触发。
- 缺 id 时补上 `activeModalCharId`，让 Modal 侧看到的 `incoming.characterId` 永远有值（Modal 只用来做 `key`/调试，不做过滤）。

**漏了会怎样**：
- 不做 `characterId !== activeModalCharId` 这层过滤 → nanami 与 sumi 的 delta 混进同一个缓冲，台词变成两人合唱（`templates/firstsnow/characters/` 有 nanami + sumi 两个角色，这是真实场景，00 §2.3）。
- 复用同一个对象（如 `setActiveModalFrame(msg)` 而 `msg` 被复用）→ 第二条同内容帧 identity 不变，effect 不重跑，逐字流断在半路。
- 订阅放 `[ ]` 空 deps → 回调闭包永远读到 `activeModalCharId === null`（首次挂载值），所有帧被丢弃。
- 用 `activeModalCharIdRef` 替代 deps → 也行，但多一个 ref 要同步；deps 方案每次开关遮罩重订阅一次，成本可忽略。

### 步骤 2：开遮罩时清空上一轮的残留

`openCharacterModal`（`App.tsx:120-124`）在 `setActiveModalCharId(charId)` 之前加 `setActiveModalFrame(null)`。

**漏了会怎样**：上一个角色（或同一角色上一轮）的最后一条帧仍挂在 state 上，新遮罩挂载时 `incoming` 非 null → 会先把旧台词演一遍（"换人后先说上一人的话"）。

### 步骤 3：`CharacterModal` 拆掉"整句驱动"，改成"可增长缓冲 + 节拍泵"

现状 `streamLine(fullText, mood)`（`:106-144`）**不能复用**，必须重写驱动器：

- 它在入口就把 `line` 设成整句、`shown` 清空（`:107-110`），并递归排一个跑到底的定时器（`:125-140`）。
- 它的取消哨兵是 `streamTimer.current === null`（`:126`）。
- 若对每条 delta 调用它：`clearTimers()`（`:108`）+ `setShown('')`（`:110`）会让已显示的文字**每个 token 都归零闪烁**，韵律表完全失效。

所以：**保留它的韵律与沉思窗，替换它的输入契约**。`streamLine` 整体删除（不是保留旁路）——同一片状态有两个写者是本仓库明令禁止的第二套约定。

保留/抽取的部分：

| 保留 | 现状位置 |
|---|---|
| 沉思窗 `100 + Math.random() * 300` ms | `:114` |
| 逐字节拍 45ms / 逗号 300ms / 句末 150ms | `:134-138` |
| `setPhase('thinking')` → `setEmo('thinking')` → `streaming` 的相位语义 | `:111,116,117` |
| `playStinger(mood)` 一次一响、绝不碰 BGM 主轨 | `:118-123` |

新增状态与 ref：

```ts
const lineRef = useRef('');        // 已收到的全文（缓冲）
const shownRef = useRef(0);        // 已显示的字符数（唯一游标）
const streamingRef = useRef(false);
const messageEndedRef = useRef(false);
const channelIdleRef = useRef(false);
const phaseRef = useRef<Phase>('idle');
const phaseBeforeTurnRef = useRef<Phase>('idle');
const lastEmoRef = useRef<Emotion>('normal');
const stingerFiredRef = useRef(false);   // 见步骤 4 的"一响"语义
const turnWatchdog = useRef<number | null>(null);
```

**逐步：`character_delta`（流式正文增长）**

1. 若 `!streamingRef.current`：`beginStream()` —— `streamingRef.current = true`；`messageEndedRef = false`；`channelIdleRef = false`；`stingerFiredRef = false`；`lineRef = ''`；`shownRef = 0`；`setLine('')`、`setShown('')`、`setPhase('thinking')`、`setEmo('thinking')`；起沉思窗（`:114` 的公式），揭幕时 `setPhase('streaming')` 并调 `pump()`。
2. `lineRef.current += incoming.delta`。
3. `pump()`：若 `streamTimer.current !== null` 直接返回（已有一步在排）；否则取 `parseEmoLines(lineRef.current)`，把可显示文本设为 frontier（见步骤 4 的 `tailOpen` 规则），按 `charDelay(prev)` 排下一步，每步 `shownRef.current++` 并 `setShown(text.slice(0, shownRef.current))`。
4. `streamTimer.current === null` 且 `shownRef.current >= text.length` 时**停止排程但不改 phase**——流还开着，可能在等下一个 token。
5. `settleIfDrained()`：当 `shownRef.current >= text.length` 且（`messageEndedRef` 或 `channelIdleRef`）→ `setPhase('done')`、`streamingRef.current = false`、清 watchdog。

**漏了会怎样**：
- 不做 `beginStream()` 的幂等判断 → 每个 delta 重启沉思窗，立绘永远在 `thinking` 抖动，`shown` 不断归零。
- 把缓冲写进 `useState` 而非 ref → 每 token 一次全量 render，且 effect 依赖链抖动（`line`/`shown` 本就每步 render，够用）。
- 每步不重算 `text.length` 而是闭包捕获一个常量 → token 到了但长度阈值不变，泵停在旧长度上等一个永不到来的终点。
- 在 `shown >= length` 时立刻 `setPhase('done')` → 第一条 delta 之后（缓冲只有 5 个字）就"演完"，`busy` 提前解除，玩家能发第二条 prompt（见步骤 6 的竞态 R6）。

**逐步：`character_message`（落定，权威文本）**

- `messageEndedRef.current = true`。
- 若 `lineRef.current === ''`（delta 全丢：断线重连 / 非流式客户端 / 服务端只在 `message_end` 给文本，`event-bridge.ts:66-72`）：`beginStream()` 后 `lineRef.current = incoming.text`，并**立即**把 `shownRef` 推到末尾（权威文本，不需再逐字等）——一次性 `setShown(text)` + `settleIfDrained()`。
- 若 `lineRef.current` 非空但与 `incoming.text` 不等：以 `incoming.text` 为准重置 `lineRef`（delta 与最终文本本应逐字相同，不等说明丢帧），并让泵自然追上。
- 若泵已停（`streamTimer.current === null`）且已追平 → 直接 `settleIfDrained()`。

**漏了会怎样**：不处理"delta 全丢"→ 断线重连后遮罩空白且 `thinking` 卡死（`character_message` 是唯一的救援帧，`docs/tools/12 §6.2` 注明它是"非流式客户端的保留路径"，所以它 MUST 被消费）；不等 `character_message`/`idle` 就用 delta 收尾 → `phase` 停在 `streaming`，`busy` 永不解禁（`handleSend` 的 `:176` 守卫会把输入锁死）。

**逐步：`character_idle`（收工）**

- `channelIdleRef.current = true`；`settleIfDrained()`。
- 若本 turn **一个字符都没产生**（`lineRef.current === ''`，例：纯工具轮，`message_end` 被 `messageText` 过滤成空，`event-bridge.ts:68-71`）：不动 `line`/`shown`，只把 `phase` 归还给 `phaseBeforeTurnRef`（有上一句就是 `done`，否则 `idle`），并清 watchdog。

**漏了会怎样**：把 `idle` 一律当成"演完"→ 纯工具轮结束时空纸一张（`shown === ''`）；更糟的是若把 `phase` 置回 `idle` 而渲染条件仍是 `phase === 'streaming' || 'done'`（`:230`），上一句台词会**从纸上消失**。这正是步骤 7 要改渲染条件的原因。

### 步骤 4：`[emo: tag]` 如何作用于流式正文

角色 preset 明确要求**逐行打标**：`extensions/instructions.ts:179`（`[One sentence per line]`）要求一句一行，`:181-184`（`[How your face is shown]`）给出六个合法标签 `[emo: normal]`/`[emo: smile]`/`[emo: shock]`/`[emo: sad]`/`[emo: angry]`/`[emo: thinking]`，`:186` 要求"首行必打、之后凡表情与前一行不同也打"。而现状 `parseEmoTag`（`CharacterModal.tsx:60-65`）只剥**行首**一个标签（`/^\[emo:\s*([a-z]+)\]\s*/`）。一次 assistant turn 可以有多行台词 → 第 2 行起标签会**原样显示在纸上**，且表情不再切换。这是"真实流一接就穿帮"的点，必须处理。

设计：保留 `parseEmoTag`（单行单元），新增一个多行折叠：

```ts
/** Fold per-line [emo:] tags: returns tag-free display text, the mood of the LAST
 *  tagged line, and whether the frontier line is an unterminated tag prefix. */
function parseEmoLines(raw: string, opts?: { final?: boolean }):
  { text: string; emo: Emotion; tailOpen: boolean }
```

规则（逐条）：

1. 按 `\n` 切行，对每行跑 `parseEmoTag`；若该行**确实带标签**（`/^\[emo:\s*[a-z]+\]/.test(line)`）则把 `emo` 更新为该行解析值（**最后一条带标签的行胜出**）。`parseEmoTag` 对"无标签"与"非法标签"都返回 `normal`（`:62,64`），所以必须额外判定"是否带了标签"，否则 `[emo: bogus]` 与无标签不可分辨。
2. 拼回的 `text` 是**去标签**的显示文本；`shown` 游标始终在这份去标签文本上推进——标签占位不进入逐字节拍（标签是元数据，不是台词）。
3. **前沿未闭合标签冻结**：仅当最后一行匹配 `/^\[emo[\s:]*[a-z]*$/`（`[emo`、`[emo:`、`[emo: sm`、`[emo: smi` … 命中）时才 `tailOpen = true`——冻结前缀**必须以 `[emo` 开头**，绝不能把以 `[` 开头的普通正文（如 `[System] …`）误冻。把**该行**暂时输出为空串，泵不推进前沿，`[emo: smi` 永不上屏。
   - **保险阀**：该行已见 `[emo` 却迟迟没有 `]`（前缀长度超过 **24** 字符）视为普通文本，照常显示（一个野生 `[emo` 绝不能把遮罩挂死）。
   - `opts.final`（`character_message` 路径）为真时**不冻结**——消息已收尾，不会再有字符到来。
4. **stinger 一响**：`emo` 一旦从上一值变化（且 `emo !== 'thinking'`），立即 `setEmo(emo)` 并 `playStinger(emo)`（`apps/web/src/lib/audio.ts:851`）；`thinking` 不发音（它已是揭幕期的暂态）。只在**揭幕之后**才判定（`streamingRef.current === true`），避免沉思窗里误响。

**漏了会怎样**：

- 只做行首标签 → 多行台词把 `[emo: smile]` 当正文显示；评委一眼看出"提示词泄漏"。
- 只更新 `emo` 不更新已验证的 `prev` → 每条 delta 都重放一次 stinger（`playStinger` 是一次性短音，`docs/audio/00-共同上下文.md:327`），变成连发噪音。
- 无保险阀 → LLM 输出一个迟迟不闭合的 `[emo` 前缀就永久冻结前沿，遮罩像死机。
- 在 `thinking` 期间就按 `normal` 发 stinger → 每次开聊都先响一声"正常"音。

> 现状 `streamLine` 的注释（`:118-123`）已把这条纪律钉死：`[emo:]` 只触发瞬时 stinger、**绝不碰 BGM 主轨**（`docs/audio/02 §3.8`、`docs/audio/04 §3.2`）。本改造保留该调用点与语义。

### 步骤 5：`FALLBACK_REPLIES` 降级为沉默兜底

删除 `FALLBACK_REPLIES`（`:40-47`）与 `FALLBACK_REPLIES_JA`（`:49-54`）两个 6/4 条随机库，改为每条 locale **一条**：

```ts
/** 真实流缺席时的沉默兜底——一句诚实的"舞台指示"，绝不是伪造的角色台词。 */
const SILENCE_LINE: Record<'en' | 'ja', { text: string; emo: Emotion }> = {
  en: { text: '[emo: sad] (She does not answer right now.)', emo: 'sad' },
  ja: { text: '[emo: sad] （今は、答えが返ってこない。）', emo: 'sad' },
};
```

**何时用**：仅在步骤 6 的 watchdog 超时（发了 prompt 却整轮没有 delta/message）时调一次。**何时不用**：任何收到过真实帧的 turn（包括只在末尾收到 `character_message` 的）。

命名从 `FALLBACK_REPLIES` 改成 `SILENCE_LINE` 是刻意的：让"这是兜底不是回复"在类型名上就不可混淆（旧名字的注释自称 `T3.1 STOPGAP`，与"随机角色台词"的行为不符，`docs/前端接线体检.md:139`）。

**漏了会怎样**：留着随机库 → 本改造的核心诉求（"不再说假话"）直接失败：任何未接上的路径都会静默回落到假台词，且**看起来完全正常**——这比崩溃更难发现。

### 步骤 6：开场硬编码台词删除、`handleSend` 不再本地取假回复

**开场（`:147-157`）** → 删除定时器与那句硬编码台词，替换成一个幂等的重置 effect（挂载时 `line=''`/`shown=''`/`emo='normal'`/`phase='idle'`/`playerEcho=''`）。

删除理由（两条，任一条独立成立）：

1. 它是**冒充角色说话的另一个人格**：`locale === 'ja' ? '（あなたを見つめて）話したいこと、ある？' : '(Watching you) Is there something you would like to know?'`（`:151`）是前端作者写的台词，与真实 preset 人格（`templates/firstsnow/characters/nanami/preset.json` 的 persona 块）无关。

## 6. WS 前端（入方向数据流全图与竞态）

```
event-bridge.mapEngineEvent          useWorld.onmessage           App                    CharacterModal
  (event-bridge.ts:59/:70/:183)        (useWorld.ts:276-318)      (App.tsx:148-152→新)     (帧消费 effect)
  character_delta  ──WS──►  case 'character_delta' ──airp:character-frame──► 过滤 activeModalCharId
  character_message ─WS──►  case 'character_message' ──►  (detail = msg, 逐字)      ──incoming prop──►
  character_idle   ──WS──►  case 'character_idle'  ──►                    ──►  buffer/pump/stinger
  error(character) ─WS──►  case 'error' + guard ──► 同一 seam ───────────►  显示 message + 复位
```

**三条帧的语义分工**（`docs/tools/12 §6.2`）：`_delta` = 实时增长；`_message` = 落定全文（非流式客户端的保留路径，也是丢帧救援）；`_idle` = 收工。

### 6.1 竞态：**先收 delta，再打开遮罩**

时间线：`useWorld` 的 WS 订阅在 `App` 挂载时就建立（`useWorld.ts:256-259`），角色 agent 进程在 `openCharacterModal`（`App.tsx:120-124`）**之后**才 spawn（`index.ts:119-141` → `lifecycle.startCharacter`）。所以"先 delta 后遮罩"的窗口只有一种：

- 前端**已经**收到过 delta 的时刻，`activeModalCharId` 仍是 `null`。

处置（步骤 1 的 `else if (activeModalCharId === null) return;`）：

- 有 `characterId` 但遮罩没开 → **丢弃**（00 §3 末段只要求"按当前打开的遮罩兜底"，不要求离线缓冲）。漏了也不穿帮——丢的是一句还没人看的台词。
- 无 `characterId` 且遮罩没开 → **丢弃**。
- 更重要的反例是 `openCharacterModal` 里的顺序：**先发 `character_start` 再 `setActiveModalCharId`**（`:122-123`）。若角色启动极快，首条 delta 会在 `setState` 之前到达 → 因 `activeModalCharId === null` 被丢；真正开演从第二条 delta 起。代价：丢失首 token（下一条立即补齐，因为缓冲从第二条开始累积）。**判定：可接受，不做跨 effect 的帧队列**——为几十毫秒的窗口引入一个缓冲队列，是给一个不存在的场景造机制。

### 6.2 竞态：**帧到达时遮罩已关**

时间线：`closeCharacterModal`（`App.tsx:125-131`）先 `sendMessage({type:'character_stop'})` 再 `setActiveModalCharId(null)`；而 agent 进程的收尾帧（`character_message`/`character_idle`）可能在 `stopCharacter`（`index.ts:204`）之后、甚至断开过程中才发出。

处置：

- `activeModalFrame` state 在关闭时**不清空**（只在 `openCharacterModal` 清空）：让 state 保持在"最后一条帧"上，`CharacterModal` 已 unmount，无人消费。下次打开时由 `openCharacterModal` 清空（步骤 2）——若也在此处清空，只是多一次相同值的 `setState`，无收益。
- **Close 动画窗口**（`closing` 220ms，`:93-97`）：这段窗口内 Modal **仍挂载**且仍收 `incoming`。所以"帧在 220ms 内到达"会继续被消费——视觉上是纸面在消退中继续吐字。处置：帧消费 effect 里 `if (closing) return;`（`closing` 已是 state，`:82`）。**漏了会怎样**：关遮罩的最后一瞬新台词闪一下，且 `playStinger` 会在关闭动画里再响一声音（听感像 bug）。

### 6.3 竞态：**两条 turn 交错 / 早到的 idle**

- `character_idle` 可能在 `character_message` **之前**到达（`agent_settled` 与 `message_end` 的先后由引擎决定）。处置：`settleIfDrained()` 必须同时看"已追平"与"已终结"，两者都满足才 `done`；只收到 `idle` 时若前沿还没追平，继续把缓冲演完，再把 `phase` 落 `done`。**漏了会怎样**：最后几个字被 `done` 截断（`shown` 停在半句）。
- 手打第二条 prompt 时第一条还没 settle：由步骤 6 的乐观 `thinking` 挡住（R6）。

## 11. 发现的冲突

### 冲突 1（P1，**已裁决：本批必做**）：`error` 帧无人消费 → "已消灭假话"会以另一种方式复发

- **事实**：`index.ts:99、112、140、145、158` 五处 `ws.send({type:'error', …})`；其中 `:140`/`:145`/`:158` 带 `source:'character'` + `characterId`，`:99`/`:112` 是 writer 车道（无 `characterId`）。`error` 被登记为 `INTENTIONALLY_UNCONSUMED`（`tools/check-ws-contract.mjs:57`：*"diagnostics go to the server console; a UI surface is unbuilt"*）。
- **冲突点**：本改造的判据是"角色说真话"，但 agent 不存在（`index.ts:145`）时前端**没有任何信号**——只能等 95s watchdog 兜底，期间玩家看着一个 `thinking` 的遮罩。这是"静默失败"，正是 00 §8.3 要禁止的形状。
- **裁决（主 agent，A-err）**：**接进同一 seam，但必须带 source guard**——`case 'error'` 内仅当 `msg.source === 'character' && typeof msg.characterId === 'string'` 才 dispatch；writer 车道的错误（`:99`/`:112`，无 `characterId`）留在 `default`，绝不灌进角色遮罩。实现见 §2.2、§8.1 的 `case 'error'`（R3 指出无条件转发会把 `Writer agent is not running` 灌进角色遮罩，故必须 guard）。
- **Modal 侧**：对 `incoming.type === 'error'` 直接显示 `incoming.message`（服务端已给英文文案，`index.ts:145`），并把 `phase` 复位、清 watchdog。于是 watchdog 从"唯一兜底"降为"最后兜底"。
- **门禁影响**：加 `case 'error'` **不产生新 finding**（`error` 已在 `INTENTIONALLY_UNCONSUMED`，`tools/check-ws-contract.mjs:57`；"未消费不算缺陷"，消费它同样不算），但让 `consumed` 计数 +1（见冲突 5）。

### 冲突 2（P2）：`character_message` 被登记为 `INTENTIONALLY_UNCONSUMED`，与本设计"必须消费"矛盾

- **事实**：`tools/check-ws-contract.mjs:62` 的理由是*"retained for a non-streaming client; _delta is the live path"*。
- **冲突点**：本设计把 `character_message` 当作**丢帧救援路径**（delta 全丢 / 断线重连 / `message_end` 过滤后仅存文本）必需的一条；一旦它在某次真实故障中是唯一到达的帧，不消费就是白屏。
- **建议**：实现时**保留**该 `case`（不必从 `INTENTIONALLY_UNCONSUMED` 删除——门禁口径不变），但把上面那句理由更新为*"retained as the authoritative settle frame; the modal consumes it for lost-delta recovery"*。这是门禁注释级修正，不改比较逻辑，收益是下一位维护者不会按旧理由把 `case` 删掉。**归 00 §9 维护者（主 agent）**。

### 冲突 3（P2）：A3 的消费面在 `check:ws` 里只有 `useWorld.ts` 一个文件被扫描 —— App/Modal 的消费不可见

- **事实**：`CONSUMERS = ['apps/web/src/state/useWorld.ts']`（`tools/check-ws-contract.mjs:48`）。本设计的 `App.tsx` 订阅 effect 与 `CharacterModal.tsx` 的帧消费 effect **都不在扫描面内**。
- **冲突点**：门禁只认"有人 `case`"这一个证据。若实现时把 `case` 写全、却在 App 侧漏了订阅（或订阅了但事件名拼错），`check:ws` 依旧全绿——**门禁证明不了端到端可通**。本批的机械核验只覆盖"帧名有了消费者"，行为正确性必须走 §10.2 的手工走查。
- **处置**：**接受**（不扩扫描面：`CONSUMERS` 的显式清单纪律是刻意的，`check-ws-contract.mjs:47`）。记录在此，避免下一位维护者把"`check:ws` clean"误读成"角色遮罩已端到端验证"。**归主 agent 决定是否把 `App.tsx` 加入 `CONSUMERS`**（若加，本改造会更早暴露拼错的事件名；代价是 `App.tsx` 里 `airp:character-frame` 的字面量会被当成帧名误判，**故不建议**）。

### 冲突 4（P2）：任务书设想的 `onDelta` 命令式 handler 与 React 19 惯用法冲突

- **事实**：任务书 Change 段写"新增 prop/handler（如 `incoming`/`onDelta`）"。
- **冲突点**：`onDelta` 需要 App 主动调用，等于把帧回调从 effect 里"推"进子组件；React 19 + 现有仓库（`App.tsx:150`、`RightSidebar.tsx:87`）全部用"事件/数据下推 + 声明式消费"。
- **处置**：选 `incoming`（§2.3 已论证）。**不视为违反任务书**——任务书给的是二选一示例；此处取"或"的后者并写明理由。

### 冲突 5（P2）：`00 §9` 的 `consumed === 9` 与门禁实测不符（实测 10；含 A-err 为 11）

- **事实**：`docs/wiring/00-共同上下文.md:151` 把总判据写死为 `summary.findings === 9` 且 `summary.consumed === 9`。用门禁自身的 `consumedFrom()`（`tools/check-ws-contract.mjs:124-134`，取自真实 `useWorld.ts` 文本）实测"本批落地态"：
  - 基线 `consumed = 8`：`file_changed, item_moved, god_action, world_frozen, world_thawed, card_position, tool_start, tool_end`。
  - A2（删 `item_moved`/`god_action`、加 `world_event`）→ **7**。
  - A3（再加 `character_delta`/`character_message`/`character_idle`）→ **10**；`findings = 9`（全 DARK，名单见 §10.1）。
  - 本批 A-err（加 `case 'error'`）→ **11**。
- **冲突点**：基线 8 − 2 + 1 + 3 = 10，**不可能**回到 9；`REVIEW-R2` §1:48 的独立合成复算也给出 `A2+A3 → consumed = 10`（与 `00 §9:151` 的 `consumed === 9` 差 1，含 A-err 差 2）。`findings = 9` 三方一致，无需改；**要改的是 `consumed`**。
- **处置**：`00 §9` 的 `consumed` 计数须由主 agent 更正为 **10**（不含 A-err）或 **11**（含本批 A-err），或删掉该字面量改由门禁输出比对。**归 `00` 维护者（主 agent）**；本篇只登记，不改 00。
