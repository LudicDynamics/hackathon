> 2026-09-12，主控亲笔。核实范围：**服务端广播面 ↔ 前端消费面 ↔ 冻结契约**（`docs/tools/12-工具注册与路由统一.md §6.2`）。

## 1. 一句话结论

**前端不是"没接线"，而是"接的是已经被删掉的线"。**

服务端在 B1/B4 把交互事件统一成 `world_event` 一条流、删掉了 `item_moved`/`god_action`/`use_item_on` 三条裸帧、改名 `roll_resolved`→`dice_result`；前端 `apps/web/src/state/useWorld.ts` 的 WS switch **原封未动**——它仍在监听那三条已被删除的帧，而对 `world_event` 与全部 11 条演出帧**零消费**。

两端**各自编译通过、各自有测试绿**，所以没人发现。

## 3. 机械核验：`tools/check-ws-contract.mjs`

体检若只停在"读代码下结论"，下一批改动会再漂一次。所以本次落了**可重复执行的门禁**（skill 教训 1：冻结契约若不能被机械核验就等于没冻结）。

### 3.1 它做什么

对三个集合求差：

1. **CONTRACT** — `docs/tools/12 §6.2` 第一张表的帧名（"要删的帧"子表不算承诺）。
2. **EMITTED** — 服务端真正的 `broadcast(...)` / `push(...)` / `frameSink?.(...)` 调用里的帧名。
3. **CONSUMED** — `apps/web/src/state/useWorld.ts` 里 `case '...'` / `msg.type === '...'` 的帧名。

四类漂移：`GHOST`（消费了但无人发射＝死监听）、`DARK`（发射了但无人消费＝暗帧）、`UNDECLARED`（发射了但契约没写＝契约失真）、`MISSING`（契约写了但无人发射＝承诺落空）。

```
node tools/check-ws-contract.mjs          # 退出码 0=clean / 1=findings
node tools/check-ws-contract.mjs --json   # 机器可读
```

### 3.2 当前输出（14 findings，全部为真）

```
GHOST  apps/web/src/state/useWorld.ts:270  listens for `item_moved` but no server file emits it
GHOST  apps/web/src/state/useWorld.ts:271  listens for `god_action` but no server file emits it
DARK   event-bridge.ts:58   writer_delta              / character_delta
DARK   event-bridge.ts:79   chalk_writing

DARK   event-bridge.ts:143  dice_result

DARK   event-bridge.ts:280  world_event
DARK   event-bridge.ts:0    show_frame                （逐字广播 details.frame，无字面量）
```

> `show_frame` 的重构发现：门禁第一版用"missing 特例"豁免它，等于**它从未被查过 dark**。抽出纯函数 `compare()` 后该特例消失，它作为一条真暗帧正确浮出——门禁本身也经历了一次"静默漏检"的修复。

### 3.3 非空性证明（防"假绿"）

门禁自身必须能证明"没有这个缺陷就会变绿"。实测：把 `useWorld.ts` 按目标形态补上 `world_event` + 12 条演出帧、删掉两条死监听后，

```
check-ws-contract: clean (24 emitted, 18 consumed, 24 in contract)   exit=0
```

恢复原状后回到 `14 finding(s) exit=1`。**门禁随修复真的会翻绿，不是恒红**。该证明已固化为永久单测 `tools/check-ws-contract.test.mjs`（直接驱动纯函数 `compare()`，含 4 类检测的非空性用例）。

## 4. 缺陷分级

### P0 — 真实功能损坏（不是演出问题）

**掷骰 HTTP 路径必失败。**

- 前端发 `{ filePath, rollType, expect }`（`apps/web/src/components/narrative/DiceRoller.tsx:151-155`）；
- 服务端 `/api/dice` 只读 `body.path`，缺 `path` 直接 400（`apps/server/src/routes/world.ts:679-690`，契约见 `docs/tools/12:710`）；
- 于是 `parseDiceVerdict(raw)`（`DiceRoller.tsx:46-51`）拿到 400 体 → 返回 `null` → `throw` → `closeOverlay()`（`:160-165`）。

后果：玩家**主动掷骰**永远失败；只有"服务端已经预结算过"的骰子卡（`DiceRoller.tsx:59-63` 的 `rollDice.result/passed` 分支）还能显示。这是真 bug，与演出无关。

### P1 — 演出层整体死亡

12 条暗帧意味着：作家/角色的流式正文、笔尖落下、幻影落地、骰子仪式、画布增量合并、生图进度、idle⇄writing 状态机、`show_frame` 演出——**一条都没接**。

最扎眼的是角色对话：`CharacterModal.tsx:35-47` 有一段本地假回复库 `FALLBACK_REPLIES`，注释自称 `T3.1 STOPGAP until the backend character agent streams real responses`。而**服务端其实早在发 `character_delta`/`character_message`**（`event-bridge.ts:58,70`），`character_prompt` 分支也已是完整实现（`index.ts:142-159`）。**是前端没接，不是后端没做。**

### P1 — `airp:world-event` 转发集合错

契约要求转发 `file_changed` + `card_position` + `world_event{entity_*}`（`docs/tools/12:677-694`）。现状 `useWorld.ts:268-275` 转发的是 `file_changed` + `item_moved` + `god_action` —— 后两条永不触发。`App.tsx:148-152` 的背包/角色视图刷新靠这条链，目前能跑是因为 `file_changed` 恰好覆盖了绝大多数变更。

## 5. 为什么一直没被发现

1. **两端各自绿**。`node --test` 的 `apps/server/test/map-engine-event.test.mjs` 只断言**服务端映射出什么帧**，没有任何测试断言**前端消费了什么帧**。跨端契约只测了一端＝最常见的假绿形状。
2. **`file_changed` 意外兜底**。`fs.watch` 只看 `.airpworld/assets/` 与 `.airpworld/sessions/`（`event-bridge.ts:363-368`），`canvas.db` 的写入**不被过滤**——于是绝大多数世界变化仍会触发整层重取。**数据新鲜度靠巧合活着**，掩盖了事件通道其实已断。代价是丢掉了"谁改的、改了什么"的语义，演出帧全灭。
3. **没有跨端门禁**。文档侧有 `tools/check-hooks-docs.mjs` 守 hooks 文档，但**没有任何机制比对两端的帧名**。
4. **契约文档自己也过期**，读文档会得到错误结论（§6）。
