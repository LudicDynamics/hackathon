## 1. 一句话定位

修 `DiceRoller` 的 **P0 请求体 bug**：它今天把 `{ filePath, rollType, expect }` POST 给 `/api/dice`，而服务端只读 `body.path`（`apps/server/src/routes/world.ts:684`），于是**每一次玩家主动掷骰都必然 400**，失败又静默（`DiceRoller.tsx:161-165`），玩家看到的是"仪式跑完、什么都没发生、骰子卡回到可点状态"。本文冻结四件事：**请求体收缩为 `{ path }`**、**成功响应边界守卫的兼容性证明**、**失败必须对玩家可见**、**结算读引擎的 `crit`/`fumble` 并接活 `onRollComplete`（本批纳入的两个真 bug，见 §11-D2/D3）**；另为 A4 唯一的 P0 真 bug 新增机械门禁 `pnpm check:bodies`（§10.2）。

**谁是调用者**：玩家 UI（点击骰子卡）。作家/角色走工具路径（`roll_dice`），与本篇无关。
**边界**：改 `apps/web/src/components/narrative/DiceRoller.tsx` 与其直接 props 链，并新增 A4 的机械门禁（`tools/check-request-bodies.mjs` + 同名 `.test.mjs` + `package.json` 的 `check:bodies`）；**不改服务端**（服务端形状已由 `docs/tools/12 §2.4` 冻结并落地）。

## 2. 签名与参数

### 2.1 前端发出的请求（要改成）

```ts
// POST /api/dice
interface DiceRequestBody {
  path: string;          // 世界根相对 POSIX 路径，无前导 './'（docs/tools/07 §2.4；校验见 apps/server/src/routes/world.ts:685-687）
  forcedResult?: number; // 本批前端不发送（见 §12-U2）
}
```

- **`path`**：`DiceRollerProps.filePath`（`DiceRoller.tsx:26`）。来源链：`LayerItem.path`（`apps/web/src/state/useWorld.ts:11`）→ `ChalkCard.tsx:35`（`filePath: path`）→ `fm.tsx:124`（`filePath={filePath ?? ''}`）。
  示例值：`world/baker-street/evening.md`（`templates/holmes-world/world/baker-street/evening.md:3-6`）。
- **`forcedResult`**：**本批不发**。服务端只在收了它时把 actor 记成 `god`（`routes/world.ts:691-692`）；前端没有上帝掷骰入口（`apps/web/src/components/god/` 下 grep `dice`/`forcedResult` 零命中）。
- **删掉的字段**：`filePath`（改名 `path`）、`rollType`、`expect`。理由：`doc-20 §7` 明禁调用者提交 `type/expect`——引擎以文件里的 `roll_dice` 为唯一真相（`docs/tools/12:194`）。`rollType` 更是**第二份真相**的活标本（`docs/tools/07:920`）。

### 2.2 服务端读的字段（现状，不改）

```ts
const { path: dicePath, forcedResult } = req.body as { path?: unknown; forcedResult?: unknown };
// apps/server/src/routes/world.ts:684
if (typeof dicePath !== 'string' || dicePath === '') → 400 invalid_argument   // :685-687
if (forcedResult !== undefined && 非有限数) → 400 invalid_argument              // :688-690
```

### 2.3 成功响应（不改，前端消费面要证明兼容）

```ts
// HTTP_STATUS/动作层的唯一成功形状：{ ok: true, ...details }（routes/world.ts:61）
{ ok: true,
  path, name, dice, desc, expect,       // roll-dice.ts:27-35
  result: number, passed: boolean,      // :37, :39
  rolls: number[], crit: boolean, fumble: boolean, forged: boolean,  // :41-47
  layer: string | null,                 // :49
  event: WorldEvent }                   // :246（{...details, event}）
```

### 2.3.1 兼容性证明：`RollDiceDetails` vs `parseDiceVerdict`（判定式**不用改**）

**命题**：把请求体改成 `{ path }` 后，`parseDiceVerdict`（`DiceRoller.tsx:46-51`）的**判定式不需要任何修改**即可继续工作（返回值按 §2.3.2 另扩 `crit`/`fumble`，属新增返回字段，不改判定式）。

**证明（逐行代入）**。守卫的判定是两条合取（`:47-49`）：

```ts
if (!raw || typeof raw !== 'object' || !('result' in raw) || !('passed' in raw)) return null; // :47
if (typeof result !== 'number' || typeof passed !== 'boolean') return null;                  // :49
```

服务端成功体（§2.3）里：

1. `raw` 是真对象（`{ ok:true, ...details }`，`routes/world.ts:61`）→ 第 1 条前两个分句 false。
2. `'result' in raw`：`details.result` 是**必填**字段，由 `rollDice` 在 `roll-dice.ts:186` 无条件写入，且类型 `number`（`:37`）→ true。
3. `'passed' in raw`：`details.passed` 同为必填，`:187` 写入，类型 `boolean`（`:39`）→ true。

四条全部成立 → 守卫**必返回** `{ result, passed }`（`:50`），永不 `null`。多出的 12 个字段（`ok/path/name/dice/desc/expect/rolls/crit/fumble/forged/layer/event`）**不进守卫的判定式**，被结构性忽略。

**反证（"需要改"的两个候选都不成立）**：

- 候选 A"需要把 `ok` 也纳入守卫"：`ok` 是**成功标志**，不是 `DiceVerdict` 的字段。守卫的语义是"这一坨 JSON 里有没有一个可用的 `{result,passed}`"——`ok:false` 的失败体（§2.4）正是**没有**这两个键，于是守卫返回 `null`，与"畸形响应"汇合到同一条失败路径。**但**这会把 409/422 的语义压成一句"畸形"——所以本文在第 3 步**先**判 `res.ok`/`ok:false`（§3 第 4 步），守卫只在成功分支兜底。**守卫本身仍不改**。
- 候选 B"需要放宽到读 `rolls/crit/fumble`"：`docs/tools/07 §6.3:769` 建议这么做，而 `crit`/`fumble` 是引擎已算的**必填**字段（`roll-dice.ts:43-45`）。本批**采纳**：`parseDiceVerdict` 扩为返回 `{ result, passed, crit, fumble }`（§2.3.2），`settleIfReady` 改读它们、删掉硬编码阈值（§3 步骤 7、§11-D2）。

**结论**：`docs/tools/12:710` 的断言"新响应含 `result`/`passed`，故不用改"在**判定式**层面成立，且本文给出了逐条代入的证明：守卫原有的两条判定式不变，唯一必要改动是**调用时机**（放到 `res.ok` 之后）。在此之上，本批另按 §11-D2 把返回值**扩展**出 `crit`/`fumble`（新增返回字段，不改判定式）。

### 2.3.2 内部类型 `DiceVerdict` 扩为四字段（本批 A-D2）

```ts
interface DiceVerdict {   // DiceRoller.tsx:40-43
  result: number;
  passed: boolean;
  crit: boolean;    // roll-dice.ts:43（必填）
  fumble: boolean;  // roll-dice.ts:44（必填）
}
```

`parseDiceVerdict`（`:46-51`）的**判定式不变**（仍只要求 `result`/`passed` 存在且类型正确），只是**返回**里多带 `crit`/`fumble`（`typeof raw.crit === 'boolean' ? raw.crit : false`，`fumble` 同理）。消费点见 §3 步骤 7、§11-D2。

### 2.4 失败响应（前端要新增消费）

两种形状，**都只带 `error` 字符串**（`packages/shared/src/actions/errors.ts:75-80`）：

```ts
{ ok: false, code: ActionErrorCode, error: string }   // 动作层失败（:76-79）
{ error: 'No active world' }                          // 路由级兜底，注意**无 ok 字段**（routes/world.ts:683）
```

### 2.5 前端消费的组件签名（要改成）

```ts
interface DiceRollerProps {
  filePath: string;
  rollDice: {
    // type?: string;   ← 删：请求体已不发它，仅 :153 用它，成死字段
```

## 3. 行为契约（逐步）——每步写"漏了会怎样"

前置：`rollDie()`（`DiceRoller.tsx:134-174`）在蓄力条满 / 点击后触发；翻滚 tween 与 HTTP 响应**并行**，两者都完成才结算（`settleIfReady`，`:113-132`）。

1. **组装请求体**：`body = { path: filePath }`，**不**包含 `rollType`/`expect`/`filePath`。
   *漏了会怎样*：今天就是这样——服务端收到 `{filePath, rollType, expect}`，`body.path` 为 `undefined` → `400 {ok:false, code:'invalid_argument', error:'path must be a non-empty world-relative path'}`（`routes/world.ts:686`）。**一次都掷不出来**（`前端接线体检.md:133`）。

2. **空路径前置守卫**：`filePath === ''` 时**不发请求**，直接走失败路径（第 6 步）。
   *漏了会怎样*：`fm.tsx:124` 的 `filePath ?? ''` 兜底会把空串一路送到服务端；用户看到一次无谓的 400 往返，错误文案是服务端的 `path must be a non-empty world-relative path`，指向的是前端自己的兜底 bug。

3. **读响应只读一次流**：`const res = await fetch(...)` 之后 `const raw = await res.json()`（异常时 `null`），**不再调用两次 `res.json()`**。
   *漏了会怎样*：Body 只能读一次；先 `parseDiceVerdict(await res.json())` 再想取 `error` 会拿到 `TypeError: body used already`，错误被吞进 catch（`:161-165`）。

4. **先判失败、再判成功**：`if (!res.ok || raw?.ok === false)` → 取 `typeof raw?.error === 'string' ? raw.error : \`/api/dice → ${res.status}\`` 走第 6 步。
   *漏了会怎样*：今天的顺序是**先 `parseDiceVerdict`**（`:157`）。400 体里没有 `result`/`passed`，守卫返回 `null`（`:47`），抛 `'Malformed /api/dice response'`（`:158`）——把 `409 dice_already_rolled`（`errors.ts:33`）、`422 not_interactive`（`:29`）、`422 invalid_field_value`（`:32`）全部**退化成同一句"响应畸形"**，玩家无从区分"已经掷过了"和"文件坏了"、和"服务端挂了"。

5. **成功路径仍过边界守卫**：`const verdict = parseDiceVerdict(raw)`（`:46-51`）；判定式**不改**，返回值按 §2.3.2 扩为四字段；`null` → 视为失败（不静默）。
6. **失败可见 + 可重试**：失败路径**先** `closeOverlay()`（它把 `error` 重置为 `null`，`DiceRoller.tsx:98-109`），**再** `setError(msg)`；骰子卡内联渲染错误行（英文文案，逐字，见 §7.2），并因为 `rolled` 仍为 `null`（`:59-63`）自动回到"Roll the Dice"按钮（`:279-284`）。
   *漏了会怎样*：今天 catch 里只有 `console.error` + `closeOverlay()`（`:161-165`）。全屏遮罩消失、卡片回到可点状态、UI 与"掷过一次且失败"完全同形——**玩家会持续重试，且永远不知道自己在撞什么**。

7. **结算（本批改）**：`pendingRef.current.verdict = verdict` → `settleIfReady()`（`:159-160`）；翻滚 tween 到点后同样调它（`:168-173`）。`settleIfReady`（`:113-132`）三处改动：① `setRolled(verdict)` 不变；② 效果判定改读 `verdict.crit`/`verdict.fumble`（引擎已算，`roll-dice.ts:43-45`），**删掉 `:121-126` 的 `verdict.result >= 95`/`verdict.result <= 5` 硬编码**（本批 A-D2，活 bug 见 §11-D2）；③ 落定处调一次 `onRollComplete?.(verdict.result, verdict.passed)`，接活 `App.tsx:523` 的 toast（本批 A-D3，§11-D3）。
   *漏了会怎样*：crit/fumble 硬编码对 `type:1d6` 检定永久失真（掷 6 通过不出 crit、掷 2/3 失败误判 fumble，证据见 §11-D2）；`onRollComplete` 永不调用则 `App.tsx:523` 的 toast 是一条看起来在工作、实际永不执行的死线。

8. **清场**：`closeOverlay()` 里把 `error` 也重置为 `null`（`:98-109` 新增一行）。
   *漏了会怎样*：上一次的失败文案会挂到下一次成功的仪式上（跨次状态污染）。**注意**这使第 6 步的 `setError(msg)` 必须排在 `closeOverlay()` **之后**，否则被这里的重置覆盖、错误行永不渲染、失败重新静默（R3-1）。

## 5. 落账

A4 是纯前端修复，**自身不写事件表**。它触发的那一条账由服务端动作函数落：

- 事件 type：`roll_resolved`（`packages/shared/src/actions/roll-dice.ts:223`）。
- `actor`：`{ type: 'player' }`（玩家点击；仅带 `forcedResult` 时才是 `god`——`routes/world.ts:691-692`）。
- `subject`：`path`（`roll-dice.ts:234`）。
- `layer`：`resolveLayer(path)`，为 `null` 时整个键省略（`:236`）。
- `turn`：`req:<uuid>`（`routes/world.ts:45`）。
- `detail`：`{ path, name, dice, desc, expect, result, passed }`（`:225-233`）。
- 失败时**不落账**（`docs/tools/07 §5.3` 表，`:684-687`）。

**前端侧的落账纪律**：响应体里那份 `event`（`roll-dice.ts:246`）与尾部读表广播的 `world_event` 是**同一行的两副本**，前端 MUST 按 `event.id` 去重（`docs/tools/07:761`；去重器归 A2 的 `seenEventIds`，见 `docs/wiring/00 §4.2`）。
*漏了会怎样*：一次掷骰演出两遍（HTTP 响应一遍、`world_event` 重取后一遍）。

## 6. WS 前端

**本项不发帧、不新增消费**。

- **`roll_resolved`（事件）**：走 `world_event` 通道（`apps/server/src/engine/event-bridge.ts:280`），被 A2 的 `case 'world_event'` 通用消费（去重 + 整层重取，`docs/wiring/00 §4.1/§4.4`）。A4 不重复处理。
- **`dice_result`（演出帧）**：`event-bridge.ts:143-156` 广播，载荷与 HTTP 响应逐字相同（`docs/tools/12:580`）。**A4 不消费它**——按 `docs/wiring/00 §1` 的"不做"清单，B 档行明列「`dice_result` 仪式」（`docs/wiring/前端接线体检.md:184`）。故 `check:ws` 的这条 DARK finding **不为 A4 所消**（见 §10.2）。
- **玩家的即时反馈通道是 HTTP 响应，不是 WS**（`docs/tools/12:313` 原话："玩家侧的骰子演出由前端消费 HTTP 响应驱动"）。
- **跨玩家可见性**：B 档接上 `dice_result` 之前，"别人掷出的结果"靠 `world_event{roll_resolved}` → 整层重取 → 卡片 frontmatter 里已有 `result/passed` → `DiceRoller` 的初始 `rolled`（`:59-63`）显示结果卡。**这条链依赖 A2**，A4 不改。
  *漏了会怎样*（若 A2 未落地）：只有本机点击的那一次因为读了 HTTP 响应而显示，别的端永远看不到结果（`docs/tools/07 §11 冲突 3`）。

## 11. 发现的冲突

### D1 — `dice_result` 的归属（**已裁决：B 档，定稿**）
`docs/wiring/00 §1` 的"不做"清单（`:32`）**已**补入 `dice_result`（B 档）与 `writer_delta`（B 档），使 §9 的算术闭合（14 → 9，全 DARK）。`dice_result` 是演出帧（`docs/tools/12 §6.2:580`），按裁决归**B 档**，本批**不消费**（§6）；`character_idle` 由 A3 收。

### D2 — crit/fumble 前端硬编码是**活的** bug（既有模板已触发）

`DiceRoller.tsx:121-126` 用 `result >= 95 → crit` / `!passed && result <= 5 → fumble` 判特效，而引擎的定义是"每颗骰子都是最大面 / 都是 1"（`roll-dice.ts:168-169`；`docs/tools/07 §2.2.7:342-344` 已判此实现为错）。**现状不只是理论问题**：仓库里已有两个 `type: 1d6` 的检定（`templates/firstsnow/world/intro/relationships/studio/README.md:7`、`templates/whitechapel/world/intro/london/third-scene/README.md:7`）——`1d6` 永远掷不出 `>=95`，所以**crit 金光永不出现**；且掷出 2 或 3（`expect: ">3"` → failed）会被误判成 fumble 猩红。
**本批修法（裁决 A-D2，已纳入）**：`crit`/`fumble` 是响应体**必填**字段（`roll-dice.ts:43-45`）——`parseDiceVerdict`（`:46-51`）扩为返回 `{ result, passed, crit, fumble }`；`settleIfReady`（`:113-132`）的 `:121-126` 改读 `verdict.crit ? 'crit' : verdict.fumble ? 'fumble' : null`，**删掉 `>=95`/`<=5` 硬编码**（字段缺失时才回落旧阈值作防御）。落点见 §3 步骤 7、§8。

### D3 — `onRollComplete` 是死 prop（`App.tsx:523` 的 toast 永不触发）

`DiceRoller.tsx:34` 声明 `onRollComplete?`、`:56` 解构，**但全组件从未调用它**（对 `apps/web` grep `onRollComplete` 只有这两处 + `fm.tsx:130` 的传参）。于是 `App.tsx:523` 的 `onDiceRolled={(res, pass) => showToast(...)}` 是一条**看起来在工作、实际永不执行的线**。这是"死代码读起来像功能"的同型缺陷（与 `useWorld.ts:270-271` 的死监听同类）。
**本批修法（裁决 A-D3，已纳入）**：`settleIfReady`（`:113-132`）落定处调一次 `onRollComplete?.(verdict.result, verdict.passed)`，接活 `App.tsx:523` 的 toast。落点见 §3 步骤 7、§8。

### D4 — `routes/world.ts:683` 的错误体形状与 `01 §7.1` 不一致（登记，不改）

"没开世界"走的是 `res.status(400).json({ error: 'No active world' })`——**无 `ok`/`code` 字段**，与 `ActionError.toHttp()` 的 `{ ok:false, code, error }`（`errors.ts:76-79`）不同型。`docs/tools/12 §7.2:726` 说"保持现状形状，前端认它"。因此 §3 第 4 步的失败判定**必须同时容忍两种形状**（`!res.ok || raw?.ok === false`），且取文案时只信 `error` 字符串。归服务端（12）的既有登记，本批不碰。
