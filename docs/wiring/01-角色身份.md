## 1. 一句话定位

**让 `source === 'character'` 的演出帧带上 `characterId`**：服务端从 `clientKey` 派生、`EventSink → emitEngine → mapEngineEvent → push` 一路透传、在 `mapEngineEvent` 的 `push` 闭包里一次性给本次产生的每一帧附加 `characterId`（有值才附）；前端 `useWorld` 把 `character_*` 帧转成 `airp:character-frame`，由 `App` 只接受存在且匹配 active character 的 `characterId`，再送入 `CharacterFrameQueue`。缺失/不匹配必须丢弃并显示诊断，不得用当前遮罩 id 补身份。

**为什么必须有**：`firstsnow` 有 nanami / sumi 两个角色（00 §2.3），而今天所有角色帧只有 `source: 'character'`（`event-bridge.ts:59,70,183`），前端无法分辨谁说 —— 遮罩一开，两个角色的台词会同时灌进同一个 `CharacterModal`。

## 3. 行为契约逐步

1. **监听点带身份**：`startCharacter` 已把 `clientKey` 写成 `` `character:${characterId}` ``（`lifecycle.ts:94-106`，派生点在 `:105`）。writer 侧写死 `'writer'`（`lifecycle.ts:77`）。
   - *漏了会怎样*：`clientKey` 是唯一携带身份的信息；若监听时不传 `clientKey`（或传常量），下游**没有任何其他来源**能知道这是谁，A1 无法实现。

2. **`handleEngineEvent` 由 `clientKey` 派生 id**：`clientKey.startsWith(CHARACTER_ROLE_PREFIX)` 时取 `slice(prefix.length)`，否则 `undefined`；**空 id（`'character:'`）也返回 `undefined`**（见 §7）。
   - *漏了会怎样*：`eventSink` 只能传 `undefined`，后面每一环都白改；而 TypeScript **不会报错**（第三参可选），故障是静默的 —— 帧里没有 `characterId`，前端回退到"当前遮罩"，多角色世界再次串台。

3. **`eventSink` 把它交给桥**：`lifecycle.ts:158` 的 `this.eventSink?.(source, event)` → `this.eventSink?.(source, event, characterIdFromClientKey(clientKey))`。
   - *漏了会怎样*：同上，静默丢失。

4. **`index.ts` 的 sink 桥接透传**：`index.ts:41` 必须显式接住第三参并转交给 `emitEngine`。
   - *漏了会怎样*：**这一行是最易漏的一处** —— `(source, event) => emitEngine(source, event)` 在新签名下**照样通过类型检查**（多余实参不可见，可选形参可省），所以编译器是哑的；结果整条链在这里断掉。

5. **`emitEngine` 透传给映射器**：`event-bridge.ts:245-249` 把 `characterId` 传给 `mapEngineEvent`。
   - *漏了会怎样*：同上，哑失败。

6. **`mapEngineEvent` 在 `push` 闭包里盖章**：`event-bridge.ts:52` 的 `push` 改为附带 `characterId`（有值才附）；角色 lane 的 production frame 若无法派生 ID，必须在 server migration adapter 显式失败/不发给前端。**这是本设计的核心切口**：一次改动覆盖 `character_delta`、`character_message`、`character_idle` 以及角色触发的 `tool_start/tool_end/chalk_*/dice_result/show_frame` 等全部帧。
   - *漏了会怎样*：逐帧手写必然有漏网之鱼；漏掉的角色帧前端会 strict drop 并显示 notice，不得回退到当前遮罩。
   - *为什么这样切*：帧名清单是冻结的，身份只能做载荷字段；`push` 是唯一收口点，所以切口在 `push` 而不在逐帧调用点。

7. **广播**：`broadcast`（`event-bridge.ts:231-242`）逐 client fan-out，帧里已含 `characterId`。
   - *漏了会怎样*：与 6 同因；此步无独立失败模式。

8. **前端 `useWorld` 路由**：`useWorld.ts` 的 `onmessage` switch（`:276-318`）新增 `character_delta` / `character_message` / `character_idle` 三个 `case`，**无条件** `dispatchEvent(new CustomEvent('airp:character-frame', { detail: msg }))`，体内不改任何 React state。
   - *漏了会怎样*：三条 `character_*` 帧落进 `default:`（`:316-317`）被丢弃，且 `pnpm check:ws` 会持续报 `character_delta` / `character_idle` 为 DARK（`tools/check-ws-contract.mjs:70-83`）。
   - *为什么无条件接收此前没有 ID 的历史帧不再成立*：UX batch 的 production public path 严格要求 ID；若旧帧仍需兼容，服务端 migration adapter 必须在 `airp:character-frame` 之前补 ID，前端不得 fallback。

9. **`App` 按 `characterId` 归属**：订阅 `airp:character-frame`，只有 `detail.characterId` 存在且等于 active character id 才下推；缺 id 或不匹配 → 丢弃 + visible notice。`activeModalCharId` 只决定当前 target，不是缺失 ID 的补值源。
   - *漏了会怎样*：事件被 dispatch 到 window 却无人归属，模态框永远不更新（`CharacterModal` 的入方向仍是死路）。
   - *归属为什么在 App 不在 Modal*：Modal 只吃 props（`CharacterModal.tsx:18-26`），多一个订阅点就有两处过滤会打架；`App` 同时持有 `activeModalCharId` 与发送端 `sendMessage`（`App.tsx:120-131`），是天然的归属层。

10. **`CharacterModal` 消费**（实现归 03，见 §8 边界说明）：03 把真实帧喂进**重写后的流式驱动器**（`beginStream`/`pump`，`docs/wiring/03-角色流式.md §3 步骤 3`；既有 `streamLine` 被整体删除、不复用），删除假回复库调用点（`CharacterModal.tsx:180-183`）。
    - *漏了会怎样*：帧到了 App 也到了 Modal，但台词仍由 `FALLBACK_REPLIES`（`:40-54`）随机吐 —— 即"角色说假话"，那是 03 的验收面。

## 5. 落账

**本件不产生任何世界事件，也不消费任何世界事件。**

理由链：`character_delta`/`character_message`/`character_idle` 是 `agent_settled` / `message_update` / `message_end` 的映射产物（`event-bridge.ts:55-74,182-185`），属于通道①"演出帧（瞬时、不入库）"（`docs/tools/12 §6.1:551-556`）。

- **不调 `appendEvent`**：落账的唯一入口是动作层/`index.ts` 的命令分支，本件不碰。
- **角色相关的落账已存在且与本件无关**：`character_talked` 由 `index.ts:169-185` 的 `character_stop` 分支落（`actor = player`，`docs/tools/12 §5.4`）；`character_start`/`character_prompt` 本身不落账（`index.ts:119-159`）。
- **世界事件侧的身份另有来源**：`world_event` 载荷里的身份是 `event.actor`（可带 `id`，`actor.ts:7`；`docs/tools/12 §6.3:616`），**不是**本件要加的顶层 `characterId`。两者不共用字段。

*漏了会怎样（把演出帧也落账的话）*：`character_delta` 是逐 token 的，落账会把 `history.db` 撑爆，且 `character_*` 不是世界事实 —— 直接违反 `doc-21 §1.1` 的"世界怎么变成现在这样的 vs 世界变化的动画"判据。

## 6. WS 前端

### 6.1 帧形状（本件后的角色帧）

```jsonc
{
  "type": "character_delta",          // 或 character_message / character_idle
  "source": "character",              // 现状即有（event-bridge.ts:59,70,183）
  "delta": "……",                     // 各帧自有载荷不变
  "characterId": "nanami",            // 本件新增，可选
  "timestamp": "2026-09-12T06:20:11.455Z"
}
```

契约：**旧帧可能没有 `characterId`，前端 MUST 容忍**（00 §3 末段）。帧名、其余字段、`timestamp` 语义（`event-bridge.ts:52` 广播时刻）全部不变。

### 6.2 `useWorld` 的分支（落点归 03，形状在此冻结）

在 `useWorld.ts:276` 的 switch 内、`default:`（`:316`）之前插入：

```ts
// Character frames carry `characterId` (A1). Unconditional dispatch: before A1
// lands (and for any legacy frame) there is no id, and the App must still be
// able to fall back to the currently-open overlay. No UI state lives here.
case 'character_delta':
case 'character_message':
case 'character_idle':
  window.dispatchEvent(new CustomEvent('airp:character-frame', { detail: msg }));
  break;
```

- **不进** `airp:world-event` 转发集合（00 §5 只列 `file_changed` / `card_position` / `world_event{entity_*}`）；`useWorld.ts:268-275` 的转发条件**不动**。
- **不进** `world_event` 的去重/整层重取路径（那是 02 的面，00 §4）。
- `character_message` 目前在 `tools/check-ws-contract.mjs:62` 属 INTENTIONALLY_UNCONSUMED（"保留给非流式客户端"），加不加 case 都不产 finding；**建议加**，因为 03 的"台词落定"用的是它。
- `UseWorldApi`（`useWorld.ts:50-72`）**不加任何字段**；`return`（`:332-342`）不动。

### 6.3 `App` 的归属（03 落点）

归属判据（唯一可观测语义）：`detail.characterId` 必须存在且等于当前打开遮罩 id；无 id 或不匹配 → 丢弃并显示诊断。旧的 `detail.characterId ?? activeModalCharId` 仅是迁移前历史 fallback，UX batch 禁止。

*为什么用 window 事件而不是把帧塞进 `useWorld` 的 state*：`useWorld` 的 state 是"整层画布载荷"（`LayerState`，`useWorld.ts:39-48`），角色台词与它无关；塞进去会造成 `state?.items` 依赖的 footprint 重测（`:222-253`）被台词帧频繁触发。

## 7. 错误边界

| 边界 | 处置 | 漏了会怎样 |
|---|---|---|
| `clientKey` 为 `'character:'`（空 id） | `characterIdFromClientKey` 返回 `undefined`，不附 `characterId` | strict App router 丢弃并 visible notice；不得使用 activeModal fallback |
| `clientKey` 为 `'writer'` | 返回 `undefined`，writer 帧不附字段 | 无害；但若实现成 `clientKey.slice(...)` 不加前缀判断，writer 帧会带 `characterId: 'writer'`（假身份）。 |
| `clientKey` 含多余前缀（`'character:character:x'`） | `slice` 得 `'character:x'`，**不是非法**（id 允许含冒号 `[推断]`，id 只来自目录名） | 无。目录名含冒号在 POSIX 合法，`launch.ts:148` 用路径拼，不解析。 |
| 同一 id 重复 `character_start` | `startCharacter` 先 `await stopCharacter`（`lifecycle.ts:95`），不会有两个实例同时推流 | 若不先停，同一 id 的两路 delta 会交错，前端看到重字。**现状已兜住**。 |
| 角色进程崩溃 / 重启 | 新 client 走 `startCharacter` 重新绑定 `clientKey`（`lifecycle.ts:104-106`），id 不变 | 无额外风险。 |
| 旧帧（无 `characterId`） | 前端兜底到"当前打开的遮罩"；无遮罩 → 丢弃 | 若前端写 `if (!msg.characterId) return`，A1 之前的世界全哑。 |
| `world_event` 帧 | 顶层**没有** `characterId`（身份在 `event.actor.id`）；不由本件处理 | 若前端拿 `world_event.characterId` 兜底，永远 `undefined`。 |
| `show_frame`（角色触发 `show` 工具） | `event-bridge.ts:163` 的 `push(details.frame)` 也会被盖章 → ShowFrame 多一个 `characterId` 键 | 见 §11 冲突 3：与 `:160-161` "broadcast the ShowFrame verbatim" 的注释有措辞张力，本批按 00 §3 第 4 条统一盖章，登记不改形状。 |
| 已构建产物 | `apps/server/dist/engine/*.js` 是编译产物（grep 命中 `dist/engine/event-bridge.js`）；`pnpm dev` 走 `tsx watch src/index.ts`（`apps/server/package.json` scripts） | 用 `pnpm start`（`node dist/index.js`）跑旧产物时行为不变 —— 必须重建（`pnpm --filter @airp/server build`）才生效；本批不跑全量 build（00 §10），此条只是运行提示。 |

### 8.2 哪些老帧可能没有 `characterId`（穷举）

1. **全部 writer 帧**（`source: 'writer'`）—— 按设计永不携带。
2. **`frameSink` 路径的两帧**：`turn_aborted`（`lifecycle.ts:168-173`）、`replay_entry`（`lifecycle.ts:257`）—— 它们绕过 `mapEngineEvent`、直接 `broadcast`，**本批不动**（00 §3 第 6 条，角色版登记为后续，见 §12）。注意 `turn_aborted` 带 `source`（`:170`），所以角色超时帧**有 source 无 id**。
3. **`world_event`**（`event-bridge.ts:280`）—— 顶层无 `characterId`；角色身份在 `event.actor.id`。
4. **非角色广播帧**：`connected`、`file_changed`（`:380-385`）、`card_position`、`world_frozen`/`world_thawed`（`docs/tools/12 §6.2:571-591` 列出的归路由发的帧）—— 无 id。
5. **`error` 帧**：角色相关的 error **已有** `characterId`（`index.ts:140,145,158`），但它是 `ws.send` 直发、不由 `mapEngineEvent` 产生，形状独立（`docs/tools/12 §6.2:591`）。
6. **`clientKey` 为 `'character:'`** 时：本设计显式不附（§7 第 1 行）。
7. **时间维度上的"老帧"**：帧是瞬时的、不重放，所以没有"历史帧"问题；唯一的"老"是**未重建的 dist 产物**（§7 末行）。

### 8.3 后端兼容性

- **可选参数 = 源码级兼容**：`mapEngineEvent` 三个既有调用面（`EventBridge.emitEngine` `:246`、测试 `apps/server/test/map-engine-event.test.mjs:17` 的 `frames()`、探针的纯函数调用，`docs/tools/12:1031` 点名）**全部无需改**，三参调用行为逐字不变。
- **`EventSink` 加可选参**：`lifecycle.ts` 内部唯一实参点是 `:158`；外部唯一实现点是 `index.ts:41`。类型放宽不会报错，也不会强迫任何既有实现改 —— 代价是**漏改不报错**（§3 步骤 4）。
- **帧是加字段、非改字段**：`Record<string, unknown>` 载荷 + 前端 `switch(msg.type)`（`useWorld.ts:276`）→ 多余键被忽略。任何"严格形状"消费者：`apps/server/test/map-engine-event.test.mjs:17` 的 `frames()` 只剥 `timestamp`，**但它的所有用例都以 3 参调用**（writer 或未传 id），故 `characterId` 不出现，断言不变。

- **`CHARACTER_ROLE_PREFIX` 跨包可用**：`@airp/shared` 已在 `apps/server/package.json` 的 dependencies 里（`@airp/shared: workspace:*`），且 `packages/shared/src/index.ts:16` re-export `./actions/actor.js`（该文件 `:15` 定义常量）。

## 11. 发现的冲突

1. **`docs/tools/12 §8.6:1031` 说"保留既有的 `mapEngineEvent` 签名"**（为不破坏探针的纯函数调用），而本件要给 `mapEngineEvent` 加第四参。
   - **裁决**：加**可选**参不改可调用性 —— 三参调用（探针、`emitEngine` 以外的测试）行为逐字不变。冲突只在措辞层面，**不改 `docs/tools/12`**（00 §0：冲突写进本篇，不回改上游）。
2. **`docs/tools/12:138`**（"role 的拼法用 `CHARACTER_ROLE_PREFIX`，不许再写字面量"）与现状 `lifecycle.ts:105` 的字面量 `` `character:${characterId}` `` 冲突。
   - **裁决**：本件顺手按规则改（§8.1 第 3 点），不额外开条目。
3. **`event-bridge.ts:160-161`** 注释"broadcast the ShowFrame verbatim" 与本件"凡 `push` 的帧都盖章"（含 `:163` 的 `push(details.frame)`）有张力。
   - **裁决**：`verbatim` 的语义是"不伪造/不合成帧"（该注释的上下文是 `details.frame` 缺失时不许编），**不禁止附加一个路由字段**；且 00 §3 第 4 条明说"一次添加覆盖全部角色帧，不逐帧手写"。**按盖章执行**，把 ShowFrame 多一个 `characterId` 键登记在此。若后续 `show` 的消费方对形状做严格校验，再回来单开例外。
4. **00 §3 第 6 条**把 `frameSink` 路径（`turn_aborted`/`replay_entry`）排除在本批之外，但角色超时帧确实带 `source: 'character'`（`lifecycle.ts:168-173`）。
   - **裁决**：遵守 00，不动；**登记为后续**（§12 第 1 条）。这意味着 §8.2 第 2 条的存在是**已知缺口**，不是遗漏。
5. **`tools/check-ws-contract.mjs:59`** 把 `turn_aborted`/`replay_entry` 列为 intentionally-unconsumed —— 与本件"前端不消费它们"一致，**无实质冲突**，记录以证明 §8.2 的排除有机械依据。

7. **`launch.ts` 行号：R2 F4 与裁决书 R2-b 给出的坐标都与源码不符。** 原 `01`（作者时）写 `:143`（characterId 形参）/`:145`（path.join），R2 与裁决书都判定照此改；但 commit `09131cb`（"feat(prompts)…"）在 `characterLaunch` 上方插了 3 行注释，整体下移 3 行。**实读 `apps/server/src/engine/launch.ts`（HEAD `09131cb`，工作树与 HEAD 同哈希 `3333b2ea`）**：`:142` `export function characterLaunch(`、`:143` `repoRoot`、`:144` `worldRoot`、`:145` `vendorCliPath`、`:146` `characterId: string`、`:148` `const characterPreset = path.join(worldRoot, 'characters', characterId, 'preset.json')`。即 R2 的 `:145` 实为 `vendorCliPath` 形参，裁决书的 `:146` 也偏一行；`path.join` 同样比裁决书的 `:146` 再下两行。**本篇按源码实读落**：§2 → `:146`（characterId 第 4 参）、§7 → `:148`（path.join）。同类转录偏差：裁决书称 §8 落点 #11 写 `CharacterModal.tsx:180-186`，本篇实为 `:178-186`（`:184` 是 `handleSend` 的 `};`、`:186` 是 `const busy = ...`）；按裁决意图收窄为 `:178-183`，不含 `busy`。**下游若引用本件，以 `:146`/`:148` 为准。**
