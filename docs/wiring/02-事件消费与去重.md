## 2. 签名参数

改造后 `useWorld.ts` 里新增的内部件（**不进 `UseWorldApi`**，理由见 §3.9 / §9）：

```ts
/** 去重窗口。契约 docs/tools/12:634 = "上限 200、FIFO 淘汰"。 */
const SEEN_EVENT_LIMIT = 200;

/** world_event 帧的载荷（docs/tools/12 §6.3 / :606-628 逐字）。 */
interface WorldEventFrame {
  type: 'world_event';
  event: {
    seq: number;            // 唯一排序游标（01 §2.7）
    id: string;             // 去重键，形如 `evt-<seq>`（packages/shared/src/store/local-store.ts:417）
    projectId: string;
    type: string;           // 15 类之一（packages/shared/src/schemas/events.ts:9-25）
    actor: { type: string; id?: string };
    layer: string | null;
    subject: string | null;
    turn: string | null;
    detail: unknown;
    createdAt: string;      // 落账时刻
  };
  timestamp: string;        // 广播时刻，由 bridge 补（event-bridge.ts:280）
}
```

函数级签名（`useWorld()` 体内的 ref / 闭包，非导出）：

| 名字 | 签名 | 作用 |
|---|---|---|
| `seenEventIdsRef` | `useRef<Set<string>>` | 去重集合，键 = `event.id` |
| `seenEventOrderRef` | `useRef<string[]>` | FIFO 淘汰队列，与集合同进同出 |
| `noteWorldEvent` | `(id: string) => boolean` | 首次见到返回 `true` 并登记；重复返回 `false` |
| `forwardWorldEvent` | `(msg: WorldEventFrame) => void` | 按 §3.5 的转发集合决定是否 `dispatchEvent` |

> 命名说明：`WorldEventFrame` 是**载荷类型**，不是帧名常量表。`00 §8.1` 禁止的是在前端再造一套**帧名字符串常量**；本文所有帧名仍以 `case 'world_event'` 这类字面量出现，符合契约口径。

## 3. 行为契约逐步（每步写「漏了会怎样」）

### 3.1 删除两条死监听

- 删 `useWorld.ts:270`（`msg.type === 'item_moved'`）与 `:271`（`msg.type === 'god_action'`）。
- 删 `useWorld.ts:278`（`case 'item_moved':`）与 `:279`（`case 'god_action':`）。

事实依据：服务端**从不广播**这两帧（`docs/wiring/前端接线体检.md:56`；`item_moved` 在 `routes/world.ts:565-567` 注释明确删除）。机械核验把二者报为 GHOST（`node tools/check-ws-contract.mjs` 输出 `apps/web/src/state/useWorld.ts:270` / `:271`）。

**漏了（不删）会怎样**：`pnpm check:ws` 永久红（2 条 ghost finding）；更糟的是这两条 `case` 与 `file_changed` 共享同一个 `void fetchLayer(...)` 整层重取分支（`:277-281`），后人在此加逻辑时会以为"移动/神动作会进来"，而实际永不触发——**死代码伪装成活的**，正是本次体检的起因（体检 §1）。

### 3.2 新增 `case 'world_event'`（形状/分派）

形状即 §2 的 `WorldEventFrame`，与 `event-bridge.ts:280` 的 `broadcast({ type:'world_event', event, timestamp })` 逐字一致；`docs/tools/12 §6.3`（`:606-628`）是唯一真相源。

分派规则：

1. **`event.seq` 只用于排序语义，本批前端不缓存 seq**（`00 §4.1`：`seq` 是唯一排序游标，但本批最小实现不做增量对齐）。
2. **`event.id` 是去重键**（`docs/tools/12:632`）。
3. **不按 `event.type` 做事件语义**——前端只按 `event.type` 决定「要不要转发 DOM 事件」（§3.5），事件语义在 `doc-21`（`00 §8.4`）。

**漏了（不加 case）会怎样**：`world_event` 继续落 `default: break`（`:316-317`），机械核验保留 1 条 dark finding（`event-bridge.ts:280`）；玩家/作家/角色的每一次动作事件在 UI 上**完全不可见**——背包刷新只能靠 `file_changed` 的巧合兜底（体检 §5.2）。且后续批次（`entity_*` 增量合并、`use_item_on` 演出）无处挂载。

### 3.3 去重：`seenEventIds`（上限 200、FIFO）

- 契约：`docs/tools/12:630-634`——**`details.event`（HTTP 响应/工具返回里的兜底）与 `world_event` 帧是同一行的两份副本**（同源 `01 §11.2`），前端 MUST 按 `event.id` 去重，否则每条动作事件演两遍。
- 实现：`noteWorldEvent(id)` 用 `Set` 判重 + `string[]` 队列做 FIFO；当队列长度 > `SEEN_EVENT_LIMIT`（200）时 `shift()` 掉最老的 id 并从集合 `delete`。

**为什么上限 200**：`Set` 无界增长在长会话（世界事件逐条累加）里是内存泄漏；200 远超"两份副本到达的时间差"所需的窗口（HTTP 响应与尾部读表 ≤1s，见 `docs/tools/12:692`），淘汰掉的老 id 不可能再有副本到达。

**为什么 FIFO 而非 LRU**：副本到达的顺序天然单调（同一行先后的差异只在几百 ms 内），FIFO 足够且契约就是这么写的（`docs/tools/12:634`）。

**漏了（不去重）会怎样**：`details.event` 与 `world_event` 是同一行的两份副本，两份都进消费面时同一条事件演两遍；本批虽只消费 `world_event`，但去重结构必须**先建好**（`00 §4.2`），否则后续批次接响应副本时会引入"演两遍"的回归，且那时去重键已被两处消费点分散，改动面翻倍。

**漏了（用 `Set` 但不淘汰）会怎样**：无界增长，长会话内存单调上升，且不会被任何测试暴露。

#### 3.3.1 去重如何**不误吞**（本设计的核心风险点）

"同一行两副本"这件事有**两个方向**，必须同时说清：

**(a) 不能误吞 → 键必须是 `event.id`，不是 `type`/`seq`。**
`id = evt-<seq>`（`local-store.ts:417`）在**一个世界历史库内**全局唯一，因此只有真正的同一行才会撞键。若图省事按 `event.type` 判重，两条独立的 `entity_moved`（不同 id）会被第二条吞掉——事件流凭空少一条，且**UI 上表现为"某些动作没反应"**，极难定位。按 `seq` 判重同样危险：跨世界（不同 `history.db`）`seq` 会重叠。

**(b) 不能抢先填 → 本批 `Set` **只由 `world_event` 填充**，HTTP 响应副本的消费面是后续批次。**
`00 §4.2` 明文冻结这一点。若本批就在某处（例如 `moveCard` 的响应处理）把响应里的 `event.id` 塞进同一个 `Set`，而响应副本的**消费**还没实现，那么先到的副本（响应）会把后到的真副本（`world_event` 帧）判为重复而丢弃——**事件被永久吞掉**。纪律：**谁消费、谁登记**；登记点与消费点必须是同一处。结构建好（一个 `Set` + 一个 `noteWorldEvent`），但本批只有一个调用者。

**(c) 畸形帧不能污染集合。**
`event` 缺失 / `event.id` 非字符串时，**不登记、不消费**，直接 `break`。否则 `Set` 里会塞入 `undefined`，之后所有畸形帧互相判重（`undefined === undefined`），且一旦实现者把键放宽成 `String(ev.id)`，`"undefined"` 会吞掉**全部**后续畸形帧——故障被伪装成"事件通道正常但没数据"。

**(d) 去重必须发生在转发与重取之前。**
顺序：`判重 → 转发 airp:world-event（若命中集合）→ 整层重取`。反过来（先转发再判重）会让同一行的两份副本各触发一次 `fetchBackpack()`（`App.tsx:149`）——幂等但白跑 render，且违背契约"演两遍"的初衷。

**(e) 世界切换的 id 复用（已知边界，本批不处理）。**
`evt-<seq>` 是**每个 `history.db` 内**的唯一键；跨世界切档时新库可能复用 `evt-1`。`useWorld` 不感知世界切换，`Set` 会残留旧世界 id，理论上吞掉新世界头 200 条中的同 id 事件。契约明文按 `event.id` 去重（`docs/tools/12:632`），本批**不偏离契约**；硬化方案（键用 `${projectId}:${id}` 或切档时清空）登记于 §11/§12。

### 3.4 是否触发整层重取：**是**（本批最小实现）

`case 'world_event'` 在判重通过后执行 `void fetchLayer(layerRef.current)`，与现有 `file_changed` 分支同构（`:277-281`）。

理由（`00 §4.4` 冻结）：`entity_*` 类事件**必然伴随文件变化**（`fs.watch` 的 `file_changed`，`event-bridge.ts:380-386`），重取语义上安全；正确性优先于性能。增量合并（`event.type` 局部化）登记为后续。

**漏了（不重取）会怎样**：若某类事件**不**伴随文件变化（例如纯 `world_snapshot`/`following_changed`），前端状态永不刷新；且因为 `file_changed` 恰好覆盖大多数变更（体检 §5.2），这个洞会被"大部分时候看起来正常"长期掩盖。

**排版顺带说明**：这次重取与 `file_changed` 的重取可能对同一次变更各发一次 `fetchLayer`（两者时序差 ≤1s，`docs/tools/12:692`）。`fetchLayer` 自带 `reqSeqRef` 陈旧响应守卫（`useWorld.ts:93,102`），晚到的旧响应会被丢弃，**不会造成状态回退**；代价只是一次多余请求。登记为可接受。

### 3.5 修正 `airp:world-event` 转发集合

契约（`00 §5` / `docs/tools/12 §6.6:677-694`）要求转发的集合 = `file_changed` + `card_position` + `world_event{entity_created|entity_edited|entity_deleted|entity_moved}`：

```ts
// 目标形态（与 00 §5 逐字）
if (msg.type === 'file_changed' ||
    msg.type === 'card_position' ||
    (msg.type === 'world_event' && [
      'entity_created','entity_edited','entity_deleted','entity_moved',
    ].includes(msg.event?.type))) {
  window.dispatchEvent(new CustomEvent('airp:world-event', { detail: msg }));
}
```

- 现状 `useWorld.ts:268-275` 转发的是 `file_changed` + `item_moved` + `god_action`——后两条永不触发（体检 §4 P1）。
- `canvas_patched` **不转发**（`docs/tools/12:694`）。
- 消费方 `App.tsx:148-152` 只做 `fetchBackpack()`，**一字不改**。

**实现排版（推荐，非契约改动）**：把 `world_event` 的转发放进 `case 'world_event'` 内、**判重通过之后**调用 `forwardWorldEvent(msg)`；`file_changed`/`card_position` 的转发留在 switch 之前的原位置。可观测集合与上面逐字一致，但有两个好处：(1) 世界事件转发被去重门控（§3.3.1-(d)）；(2) 避免门禁把 `msg.type === 'world_event'` 误记为"已消费"却在 switch 里没有真实 `case` —— 机械核验的 `consumedFrom` 同时匹配 `case 'x'` 与 `msg.type === 'x'`（`tools/check-ws-contract.mjs:129`），把二者解耦能杜绝"假绿"。

**漏了（不修集合）会怎样**：`airp:world-event` 只在永不触发的死帧上派发，`App.tsx:149` 的 `fetchBackpack()` 只能靠 `file_changed` 的巧合（体检 §4 P1）；契约要求的 `card_position` 转发缺失 → 拖卡落库后背包/角色视图不刷新。

**漏了（转发了 `canvas_patched`）会怎样**：`docs/tools/12:694` 明确不转发——画布状态变化不影响背包清单（背包是目录扫描），多转发只是噪音 + 多余 `fetchBackpack()`。本批不会转发它，登记为"必须不转发"。

### 3.6 `world_frozen` / `world_thawed` / `card_position` / `tool_start` / `tool_end`

**行为一字不改**（`:282-315`）。`world_event` 的 `case` 插在 `file_changed` 之后、`world_frozen` 之前，保持 switch 可读。

**漏了（顺手重构它们）会怎样**：超出 A 档边界，且 `tool_start/tool_end` 喂的是 `writerToolsInFlight` 忙计数（`:89,306-315`），动它有 footprint 测量的连带风险（`lib/footprint.ts` 契约）。本批 MUST NOT。

### 3.7 `default` 分支

保持 `:316-317` 原样。`agent_event`/`roll_resolved` 等仍落在此处（注释同步更新为当前真实集合，去掉已删帧的暗示——纯注释，不影响门禁）。

### 3.8 与乐观移动（`moveCard`）的交互

`moveCard` 先本地乐观合并再 `POST /api/card/position`（`:141-165`）。若该动作也会落一条 `entity_moved` 世界事件并触发本批的整层重取，理论上可能与乐观值竞争。安全性依据：服务端广播发生在动作**提交之后**（`docs/tools/12:653` "broadcast 必须在动作成功之后"），故重取读到的是已提交位置；且 `file_changed` 今天就已触发同样的整层重取，**本改造不引入新竞态**。此判断对 `arrangeCards(place)` 是否落事件依赖 `[推断]`（未在本文核实服务端 `place` 是否 `appendEvent`）。

**漏了（忽略此交互）会怎样**：若某天广播改成动作提交**前**发出，乐观值会被未提交的旧位置覆盖，表现为"拖完弹回"。登记为需在实现后 smoke 验证的观察点。

### 3.9 `UseWorldApi`（`:50-72`）**不新增** state / prop

**决定**：本批 `UseWorldApi` 原样（9 个成员）。去重 `Set`、`noteWorldEvent` 均为实现细节，App 不需要；`airp:world-event` 通过 window DOM 事件暴露给 `App.tsx:148-152`，已经够用。

**漏了（不去动它）会怎样**：无副作用——不暴露反而正确。

**反过来（若强行暴露 `seenEventIds` / `lastEventSeq`）会怎样**：产生一条**无消费者的公开 API**，本批无测试覆盖，后续批次若真实需求形状不同（例如需要 `lastEventSeq` 的门控而不是裸 Set）还得改一次——面越大越难改。**等到真有消费者再加**（`00 §8` 反模式精神：不加没有拉力的抽象）。

## 5. 落账

**本改造不产生任何事件落账。**

- `world_event` 是**读取**已落账行后的广播（`event-bridge.ts:260-291` 的尾部读表；事件由 `packages/shared/src/store/local-store.ts:400-425` 的 `appendEvent` 写入）。
- 前端消费不改任何 `history.db` / 事件表；前端**不是** `AppendEventArgs` 的调用者。
- `event.id`/`event.seq` 的生成方是 store（`local-store.ts:416-421`：`seq = lastInsertRowid`，随后 `UPDATE events SET id = 'evt-<seq>'` 并 `COMMIT`）。契约因此保证：**读到即已提交**（`event-bridge.ts:256-258` 注释），前端不去重也不会读到半行——去重防的是**同一行到达两次**，不是**未提交行**。

**漏了（把前端去重当成落账保证）会怎样**：会误以为前端 `Set` 有并发保护作用，进而忽略 T0.6（`expectedRevision`）那类真正的并发保护——本批明确不做 T0.6（`00 §1` 不做清单）。

## 6. WS 前端

### 6.1 入方向（服务端 → 前端）

本批新增消费的帧只有一条：

```
world_event  { type:'world_event', event:{ seq,id,projectId,type,actor,layer,subject,turn,detail,createdAt }, timestamp }
```

来源：`apps/server/src/engine/event-bridge.ts:280`（尾部读表唯一通道）。
形状真相源：`docs/tools/12 §6.3`（`:606-628`）。15 类 `event.type` 见 `packages/shared/src/schemas/events.ts:9-25`。

处理顺序（`case 'world_event'` 内）：

1. 取 `msg.event`；非对象或 `id` 非字符串 → `break`（§3.3.1-(c)）。
2. `if (!noteWorldEvent(ev.id)) break;`（去重；重复副本在此终止）。
3. `forwardWorldEvent(msg)`：若 `ev.type ∈ {entity_created, entity_edited, entity_deleted, entity_moved}` → `window.dispatchEvent(new CustomEvent('airp:world-event', { detail: msg }))`。
4. `void fetchLayer(layerRef.current)`（整层重取）。

### 6.1bis 与 A3（角色流式）的接缝：`airp:character-frame`（边界冻结）

`character_delta`/`character_message`/`character_idle` 属 **A3**（03 篇），**不进 02 的 `world_event` 去重/refetch 路径**。与 `Design01CharId`/`Design03Stream` 在 IRC 上冻结的接缝（02 只登记边界，不实现其细节）：

- useWorld 新增**唯一**出口：`window.dispatchEvent(new CustomEvent('airp:character-frame', { detail: msg }))`，`detail` = 原始帧逐字。
- 三个 `case` 为**字面量标签**（`character_delta`/`character_message`/`character_idle`），case 体内**无条件** dispatch，不碰 state、不 refetch、**不去重**（它们不是 `world_event` 通道），也不进 §3.5 的转发集合。
- 过滤/归属在 **App**（`activeModalCharId`），不在 useWorld，也不在 02。
- `UseWorldApi` 仍**不加**成员（§3.9）；去重 Set 不外露。新增出口是 window DOM 事件，不是 API 字段。

**为什么必须在 02 划清**：若把 `character_*` 也塞进 §3.3 的去重 Set，会立刻违反 §3.3.1-(b)（登记点必须与消费点同处）——角色帧没有 HTTP 副本，登记它们只会白占窗口并误吞后续真副本。

## 11. 发现的冲突

1. **`docs/tools/12 §6.6` 的行号漂移**：该节说「`useWorld.ts:170-177` 把 `file_changed` / `item_moved` / `god_action` 转发」，实际转发块在 `useWorld.ts:268-275`（漂移约 100 行）。与体检 §6 第 6 条同源。**不回改 `docs/tools/12`**（非本批 C 档归属），登记给 05 文档回写。
2. **`airp:world-event` 的 DOM 事件名与 WS 帧名 `world_event` 同语义不同物**（体检 §2.3 注）：`useWorld.ts:274` 派发的是 `CustomEvent`，服务端帧是 `world_event`。两者**不共用命名空间**，实现时 MUST NOT 当作同一集合处理。机械核验只扫 `case`/`msg.type ===`，不会把 DOM 事件名计入 CONSUMED——正确，无需处理。
3. **门禁计数口径的边界**：`tools/check-ws-contract.mjs:129` 的 `consumedFrom` 同时匹配 `case 'x'` 与 `msg.type === 'x'`。因此若只在转发 `if` 里写 `msg.type === 'world_event'` 而 switch 无对应 `case`，门禁仍会判 `world_event` "已消费" → **假绿**。本设计（§3.5）通过「转发放进 case 内」规避；但若他人选择「转发留在 switch 前的 `if`」，则 §10.1 的 DARK 消失证明**不足以**证明 switch 真的有 `case`，需人工复核。登记为门禁口径的已知弱点。
4. **跨世界 `evt-<seq>` id 复用**（§3.3.1-(e)）：`docs/tools/12:632` 冻结「按 `event.id` 去重」，但 `id` 只在单个 `history.db` 内唯一（`local-store.ts:417`）。契约与本设计的键选择一致，冲突在于**契约未讨论切档场景**。本批不偏离契约；硬化项登记于 §12。
5. **`00 §4.2` 与「`details.event` 也过同一 `Set`」的时序**：契约（`docs/tools/12:634`）说「`world_event` 与响应里的 `event` 都先过它」，而 `00 §4.2` 又说本批只消费 `world_event`。二者不矛盾（结构先建、单填充者），**已在 §3.3.1-(b) 明确纪律**：登记点必须与消费点同处，避免后续批次误用。若他人理解为"本批就应双向登记"，会引入 §3.3.1-(b) 的吞事件 bug。
6. **`error` 帧的归属（已裁决）**：`Design03Stream` 主张 useWorld 增 `case 'error'`（转进 `airp:character-frame` seam），理由是 `apps/server/src/index.ts:140,145` 的 `{type:'error',source:'character',characterId,message}` 不消费会让 Modal 静默超时→又播假台词。**裁决：A3 接，带 source guard**——`case 'error'` 内仅当 `msg.source === 'character' && typeof msg.characterId === 'string'` 才 `dispatchEvent`；writer 错误（`apps/server/src/index.ts:99,112`，无 `characterId`）留在 `default`。**02 不接**（`error` 不属 A2 的 world_event 通道）；`error` 在 `INTENTIONALLY_UNCONSUMED`（`tools/check-ws-contract.mjs:57`），加 `case` 不产 finding、不改变本文 §10 的计数。见 §6.1bis。
7. **`dice_result` 演出帧的范围归属（已裁决：B 档）**：`00 §1` 的不做清单明列「`dice_result` 的骰子仪式演出（归 B 档）」，`docs/tools/12 §6.2:580` 明确它是演出帧。**裁决：归 B 档，本批不消费**；02 与 04 的验收均如实写「`dice_result` 的 DARK 不为本批所消」，它与其余 8 条一并留在 `00 §9` 的残余 9 条里。
