# AIRP 游玩页重构设计简报

> 状态：**设计门，尚未进入生产重构**。
>
> 本文先把当前游玩页说清楚，再约束原型变体的共同验收口径。原型阶段不得修改 `apps/web/src` 的生产 UI；只有明月验收选定方向后，才进入契约回写与实现拆解。

## 1. 一句话产品任务

玩家应该在一张持续存在的世界画布上，先知道自己在哪里、看见值得注意的对象，再用一个自然动作推进故事，并能理解世界是否真的回应了自己。

这不是“把控制面板做得更漂亮”，而是重新设计一张**叙事空间工作台**：空间是主角，界面家具只在需要时出现，所有视觉表达都为“看见 → 理解 → 行动 → 看到回应”服务。
### 1.1 关键前提：无限画布不能被视觉变体省略

上一版原型把“无限画布”误压缩成了有限的中央舞台或静态地图，这不符合 AIRP 的产品身份。后续原型必须把**世界空间本身**作为第一等体验，而不是只展示它的视觉皮肤：

- 视口是世界的窗口，不是世界的边界；画布内容需要延伸到当前视野之外，至少存在可通过平移发现的第二空间区域。
- 每个变体至少要有一条真实可演示的平移路径和一条缩放路径。桌面可以用拖拽/滚轮，移动端可以用拖动/双指替代按钮，但不能只有一张漂亮的静态地图。
- 卡片、Chalk、角色、关系线和背景要落在同一套世界坐标中；Chrome、阅读层、对话和行动台只能覆盖在窗口之上，不能把世界包进一个固定大小的 panel/frame。
- 打开或关闭阅读、对话、活动和行动层时，要保持世界相机和实体相对位置；关闭后玩家应回到同一个空间，而不是重新进入一张页面。
- 手机必须仍然能拖动画布、缩放或使用等价的显式控件；不能依赖 hover，也不能把所有实体改成纵向列表来逃避空间设计。

原型截图只证明一个当前视野，不证明画布有限。`DESIGN.md` 必须写明世界窗口、平移/缩放操作、覆盖层与相机连续性。

## 2. 当前游玩页的内容与元素

以下是从 `apps/web/src/App.tsx` 及其子组件整理出的当前界面事实。它描述“现在有什么”，不是要求未来继续保留原位置。

### 2.1 世界舞台 / Canvas

- 世界或层的背景、材质、颗粒、网格、暗角和可选动效。
- 可拖拽、缩放、平移的空间画布；卡片坐标、相机记忆和层级切换属于世界空间，不应被 UI 覆盖层改写。
- 场景实体：普通道具、图片/信件、门牌或 gate、Chalk/板书、choice/status/dice 等互动字段。
- 实体之间的关系线、hover/focus 反馈、拖拽中的临时投影与落定演出。
- 角色在场投影：角色头像、位置、跟随状态和离场/异地提示。

### 2.2 顶部世界 Chrome

当前 `prototype-worldtop` 包含：

- Worldlines 品牌。
- 世界 / 层级 breadcrumb，可返回父层。
- 世界醒着/暂停状态。
- 物品数量与人物数量摘要。
- 世界启动器、世界/存档列表。
- 语言选择。
- 世界设置、TTS 设置、静音、视觉效果开关。
- 顶栏关闭与沉浸模式唤回入口。

这些元素都是真实产品能力，但当前聚在同一条横向工具带上，身份、导航、状态和设置的优先级容易互相竞争。

### 2.3 叙事阅读层

`prototype-narrative` 是一张可打开的故事纸页，当前承载：

- “The story so far” 眉题。
- 世界/章节名、开场或故事继续的时间标签。
- 世界描述和当前层 README 正文。
- 最近的 Chalk 引语。
- “当前玩家身处哪个世界 / 当前地点”的页脚身份说明。

它是回看和定位用的阅读层，不应该变成第二个会持续抢注意力的主舞台。

### 2.4 舞台边缘工具与身份

- 左侧 Explore / Return 工具。
- 右侧角色 rail：同场角色、异地角色、跟随切换、前往角色、进入角色私域。
- 玩家头像 orb 与玩家身份/简介卡。
- 随身物品/Belongings 数量、物品列表、物品详情、使用或放置入口。
- 沉浸模式按钮与边缘唤回按钮。

这些元素目前主要通过多个绝对定位控件表达，视觉上容易像“工具散落在画布四周”，而不是一个有清楚呼吸节奏的产品系统。

### 2.5 角色对话层

点击角色后打开 `CharacterModal`：

- 背景中的世界被压暗/弱化。
- 角色媒体或立绘。
- 角色名字、身份与状态信息。
- 当前台词、逐字流式回应和推进提示。
- 玩家输入与发送动作。
- 访问角色私域（nook）、关闭、Escape 回退。

对话需要成为“聚焦某个人”的完整舞台，但不能让身份、输入、台词、活动状态互相争夺同一张纸面。

### 2.6 行动台 / Writer Channel

当前底部 `prototype-dock` 是游玩页的主要行动台：

- “Speak to the writer” 入口标题。
- 世界暂停/行动会推动世界的说明。
- 作家实时状态（ready、writing、error、stop requested 等）。
- 单行自然语言输入、历史上下键、发送键。
- 作家工作中的 Stop。
- 可重试的错误路径。
- `What do you do?` 快捷入口，以及 authoring 状态下的 God Hand / freeze / Chalk 工具。

它是玩家推进故事的主要入口，不能被做成普通聊天框，也不能被状态、调试工具和装饰挤成一条难以聚焦的底栏。

### 2.7 活动与事实反馈

- `ActivityRail`：作家与功能 Agent 的实时活动提示。
- `AgentActivityLog`：可展开的原始活动流。
- `WorldToast`：已落盘世界事实的短暂回执。
- `WriterInkLayer`、phantom、粒子和骰子仪式：空间内的进行中/落定演出。

这里必须区分“正在处理”“事实已经落盘”和“演出仍在播放”，否则视觉动效会替代真实状态。

### 2.8 Nook / 角色私域

进入角色私域后，当前仍复用画布投影，但加入：

- 角色身份与返回入口。
- 角色自己的世界背景、卡片、板书与互动。
- 私域笔记输入。
- live-call、活动提示、toast 等下方信息。
- 从私域继续打开角色对话或执行实体互动。

Nook 应该让人感到“进入了这个角色的空间”，而不是打开一个盖在主画布里的暗色小面板。

### 2.9 世界选择与其他覆盖层

- 首次进入或切换世界的 WorldLauncher / WorldShelf：世界砖块、素材预览、存档、加载状态、删除确认。
- BagItemDialog：携带物品详情与行动。
- DiceCeremony：掷骰过程中与落定后的仪式层。
- RadialMenu / GodModeToolbar：作者或调试能力。
- 服务失败、加载、空状态和输入错误提示。

它们的共同问题不是“缺少按钮”，而是需要在同一产品美学下明确：这是世界外的目录、世界内的阅读、动作中的处理，还是已经落地的事实。

## 3. 当前信息层级

### 3.1 玩家真正需要的顺序

1. **我在哪里？** 世界、层、当前空间和在场角色。
2. **这里有什么值得看？** 场景实体、板书、关系、角色状态。
3. **我现在能做什么？** 阅读、选择、使用、进入、对话、向作家表达行动。
4. **刚才发生了什么？** 处理阶段、世界事实、作家或角色回应。
5. **我还能管理什么？** 物品、设置、语言、活动记录、作者工具。

### 3.2 设计诊断

当前实现把 1–5 中不少内容同时放在视口边缘：顶栏、左工具、右角色、玩家 orb、背包、活动、toast、行动台。即使每个控件单独合理，整体也容易产生三种负担：

- **主舞台被家具切碎**：玩家先看见框和按钮，后看见世界。
- **状态与动作混在一起**：实时作家状态、事实 toast、作者工具都靠近行动台或顶栏。
- **多种表面语言并存**：世界背景、暖纸、旧控件、对话、Nook、启动器之间缺少一个更强的整体构图。

因此本轮不再以“逐个组件换皮”为目标，而以一张完整游玩页的**构图、节奏、材质和注意力路径**为目标。

## 4. 本轮重构的设计自由度

原型阶段只冻结产品事实和玩家目标，不冻结具体家具摆放：

- 可以重新决定顶栏、侧栏、行动台、活动流、背包和身份信息的组合方式。
- 可以把常驻控件改为边缘唤回、折叠抽屉、浮动纸页、舞台内嵌标记或上下文面板。
- 可以重新选择排版比例、留白密度、纸面/透明面/玻璃面/墨面层次、色彩主次与标题字体。
- 可以做明显不同的 desktop / narrow / phone 构图，不要求把桌面布局缩小成手机布局。
- 可以重新设计进入对话、打开 Nook、阅读故事、唤起行动台和进入 authoring 的视觉过渡。
- 可以选择克制的静态编辑感、戏剧化的舞台感、档案馆/书房感或其他独立方向；但必须有完整且一致的美学语法，不能只是随机装饰。

## 5. 仍然不可牺牲的产品底线

这些是事实、理解和可恢复性的底线，不是视觉限制：

- 画布仍是世界空间；视觉覆盖层不能偷偷改写坐标、事实或相机语义。
- 同一个玩家意图必须能找到一个明确主动作，并有键盘/触屏等等价目标路径。
- `accepted / processing / landed / revealed / completed` 不能被一张漂亮的“成功”动画替代；失败、取消和服务不可用也必须说清下一步。
- 已落地的世界事实必须可回访；文件存在、动画结束或 toast 出现不能单独证明事实。
- 叙事、实体、角色、作家、活动和设置的责任边界不能因换皮合并成第二套状态真相。
- Effects off、reduced motion、低性能、窄屏、媒体失败时，文字、状态、焦点、关闭和核心行动仍可用。
- 原型可以使用静态 fixture，但不得伪装成真实后台已经完成了某个动作。

## 6. 原型变体验收口径

明月先验收原型，不验收生产实现。每个变体需要回答：

1. 第一眼能否说出“我在哪里、主舞台是什么、下一步是什么”？
2. 画布与 UI 是否属于同一套美学，而不是把一堆漂亮面板贴上去？
3. 页面是否有一个令人记住的构图或视觉观念？
4. 行动台、状态、角色、物品、阅读和作者工具的优先级是否自然？
5. 发生对话、作家处理中、事实落定、错误和沉浸模式时，注意力是否仍然连续？
6. 390×844 与桌面是否是有意设计的两种构图，而不是压缩后互相遮挡？
7. 即使去掉动效和图片，信息层级、行动和结果是否仍清楚？
8. 是否能从初始视野平移/缩放到另一片仍属于同一世界的空间，并在关闭覆盖层后回到相同相机位置？

评审时优先看：整体气质、构图记忆点、内容与家具的关系、行动路径和状态诚实度；不要先用当前 CSS class 或当前组件位置反驳新方向。

## 7. 原型交付格式

每个独立变体只写原型，不改生产 UI：

```text
prototypes/play-page/<variant-id>/
  index.html          # 可直接打开或由 Vite 静态服务预览
  styles.css          # 该变体的完整视觉语法
  interaction.js      # 可选，仅用于切换静态状态/展示路径
  DESIGN.md           # 设计命题、内容分区、状态与取舍
```

原型允许使用项目已有公开素材或内联 fixture，但不能 import `apps/web/src/App.tsx`、不能写入真实世界、不能建立第二套生产状态。每个变体至少提供：

- 默认游玩态；
- 一次主要行动态（例如行动台聚焦、对话或阅读）；
- 一次处理中/落定或失败态；
- 角色、物品、活动/事实反馈的可见表达；
- 桌面与手机两种有意构图。

原型被选定后，才把选定方向回写到共享契约，删除不必要的旧硬约束，重新拆实现任务。
