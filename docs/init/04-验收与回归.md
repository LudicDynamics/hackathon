## 1. 一句话定位

**给 I1 一份「评审照抄命令行就能判对错」的判决书**：一个**离线确定性**端到端探针（真 writer spawn + 假 provider，走真 `/airp-init` 命令），一张纯函数单测清单（与 `01-纯函数与校验.md` 的用例表互为镜像），一张本批必须回写的上游文档清单（`doc-11 §6.1` 的 `path`→`layer` 等）。

**04 不实现任何功能**；它只回答一个问题：**「没有这条接线就会失败」如何被机械证明。**

**判据（契约 §10 末段，逐字）**：对一个 stub 层发 `/airp-init`（经真 spawned writer + 确定性 provider），断言 (a) 目标目录长出 `README.md` + ≥1 内容文件；(b) `events` 表新增一条 `layer_initialized`（`by` 与传入一致）；(c) 第二次发同一命令**不再动作**（判空短路）。

**必须遵守的硬约束（契约 §2.1/§8 + `AGENTS.md §6.5`）**：探针**离线**（`PI_OFFLINE=1`，无 API key，`provider:'airp-init-probe'`），**不联网**；断言必须**「修复前会失败」**。

### 3.2 探针 §1：场景正例（P1–P7）

流程：`makeTmpWorld()` → `seedStubLayer` → `cpSync` 后删 `.airpworld/sessions`（`probe-inject.mjs:71`）→ `writerLaunch(REPO, tmp, VENDOR_CLI)` → `new RpcClient({...spec, args:[...args,'--extension',INIT_PROVIDER], env:{...env, PI_OFFLINE:'1', AIRP_INIT_PROBE_TARGET:'world/probe-stub', AIRP_INIT_PROBE_MODE:'product'}, provider:'airp-init-probe', model:'deterministic'})` → `await client.start()` → `await client.prompt('/airp-init ' + JSON.stringify({kind:'scene', target:'world/probe-stub', request:'她最后待的地方', by:'player'}))`。

**关键时序事实（本探针可靠性的地基，逐条已核）**：
- `RpcClient.prompt` 返回**在 handler 完成后**——`agent-session.js:1521-1535`：`_tryExecuteExtensionCommand` 被 `await`，handler 跑完才 `preflightResult?.(true)` → RPC 的 `response`（`rpc-mode.js:429-436`）→ `prompt()` 的 Promise resolve。**故 `await client.prompt(...)` 之后，`spawnAgent` 已结束、事件已 commit。**
- 扩展命令**不触发父会话 LLM**（`docs/rpc.md:41`；`agent-session.js:1506` 注释逐字「execute immediately ... manage their own LLM interaction via `pi.sendMessage()`」）→ provider 的请求**全部来自子代理**，脚本序号干净。
- `appendEvent` 只在 COMMIT 后返回（`local-store.ts:378-380`「return it ALREADY COMMITTED」、`:418` `exec('COMMIT')`；`event-bridge.ts:261-268` 注释逐字）→ 探针随后用第二个 `LocalWorldStore` 读，必见该行。

断言实现（伪码，写全）：

```js
// tools/probe-init.mjs
async function assertScenePositive(tmp, client) {
  const stubDir = path.join(tmp, 'world', 'probe-stub');
  const readme  = path.join(stubDir, 'README.md');
  const prop    = path.join(stubDir, 'probe-prop.md');

  // P1/P2/P3
  assert.ok(fs.existsSync(readme), 'P1: README.md must land in the stub layer');
  assert.ok(fs.existsSync(prop),   'P2: an object file must land alongside it');
  const fm = parseFrontmatter(fs.readFileSync(readme, 'utf-8'));
  assert.equal(fm.frontmatter?.type, 'readme', 'P3: README carries type: readme');
  const children = fs.readdirSync(stubDir).filter((n) => !n.endsWith('.json'));
  assert.ok(children.length >= 1, `P2: >=1 non-json direct child, got ${children.length}`);

  // P4–P7 —— 直接读 history.db（不走 WS）
  const store = new LocalWorldStore(tmp);
  const ev = (await store.getEventsSince(0)).find(
    (e) => e.type === 'layer_initialized' && e.detail?.layer === 'world/probe-stub');
  store.close();
  assert.ok(ev, 'P4: a layer_initialized event must be appended');
  assert.equal(ev.detail.by, 'player', 'P5: by is carried verbatim');
  assert.equal(ev.actor.type, 'engine', 'P6: actor is ALWAYS engine (actions/layer.ts:120)');
  assert.ok(ev.detail.files.includes('world/probe-stub/README.md'), 'P7: files lists the README');
  assert.ok(ev.detail.files.includes('world/probe-stub/probe-prop.md'), 'P7: files lists the object');
}
```

**漏了会怎样**：只断言 P1/P2 不断言 P4/P5，实现者可以「写盘但不落账」交卷——作家下一轮感知不到「这里长出来了」（doc-11 §6.1 的消费方），`hasUnseenCreation`（`inject/collect.ts:143-144`）永远不触发，前端幻影永远不落地。只断言 P4 不断言 P6，实现者可能把 actor 写成 `player`，违反 `actions/layer.ts:116-120` 的既有裁决（契约 §2.2）。

### 3.3 探针 §2：幂等短路（P8/P9）

**同 client、同世界**再发一次同命令。断言 `events` 条数不变、`world/probe-stub` 目录文件集不变。

**机理**：命令第 2 步判空（契约 §2.3）→ `isLayerEmpty(files, 'world/probe-stub')` 现为 `false` → 直接返回，**不进 `spawnAgent`**。


**漏了会怎样**：不测幂等，实现者可能漏掉判空短路 → 每次进入 stub 层都重写目录，**覆盖玩家已看过的作品**（doc-11 §3.1「目录里已有 README.md（哪怕写过一次）不初始化」）。这是 doc-11 的**硬判据**，必须机械守住。

### 3.5 探针 §4：小天地正例（P14/P15）

换 fixture（`seedEmptyNook`）+ 换新 `RpcClient`（新进程 → `requestIndex` 重置），`AIRP_INIT_PROBE_TARGET='characters/probe-nook'`，命令 `{kind:'nook', target:'probe-nook', by:'player'}`。

## 12. 仍未知待拍板 / 探针不稳定源

### 12.1 探针可能的不稳定源（点名）

1. **超时断言不在探针内**（P16 只覆盖「completed 但空产物」，**不覆盖 `timed-out`**）。机理：要触发 `timed-out` 需让 provider 挂住 / 睡过 `timeoutMs`（场景 60s、小天地 45s，契约 §2.3、`run.ts:145-166` 的 `Promise.race`），会让探针跑 45–60s+，与「离线快速门禁」定位冲突。**处置**：`timed-out` 分支列为**手测**（用一个睡死的 provider），或由 `packages/shared/test` 层用**注入假 `spawnAgent`** 单测命令的分流逻辑（若 02 篇抽出可测内核）。**这是刻意的不覆盖，不是遗漏。**
2. **`RpcClient.send` 的 30s 请求超时**（`rpc-client.js:668-672`，逐字 `Timeout waiting for response to ${command.type}`）。`prompt()` 的 RPC `response` 在 handler 完成后才发（`rpc-mode.js:429-436`），而 handler 内的 `spawnAgent` 最坏 60s → **真 provider 下 `client.prompt('/airp-init …')` 可能超 30s 抛「Timeout waiting for response」。** 探针用确定性 provider（毫秒级）绕开；但**服务端 R2 调用者必须知道这条**（真初始化 > 30s → RPC 超时）→ 属 03/02 的触发链路设计，**登记给 02 篇**（契约 §2.1 的 R2 路径需自行处理超时/静默）。
3. **文件系统时序**：`appendEvent` commit 后才可见（`local-store.ts:378-380`）→ 探针在 `prompt()` resolve 后读账是安全的；但**不要**改成读 `fs.watch`/WS（debounce 尾巴，`event-bridge.ts:12` 的 `WATCH_DEBOUNCE_MS = 150`）。
4. **会话残留**：世界副本里若带 `.airpworld/sessions/*.jsonl`，`writerLaunch` 会加 `--continue`（`launch.ts:119`）→ 复用旧会话、命令幂等判据被污染。**探针 MUST `rmSync(.airpworld/sessions)`**（照 `probe-inject.mjs:71`）。

7. **`getCommands()` 的时序**：`rpc-mode.js:793` 的 `get_commands` 依赖扩展已 bind；`client.start()` 后再调（照 `probe-inject.mjs:134-139` 的 `start()` → `prompt()` 顺序）。**不要**在 `start()` 前调。
