## ① 一句话定位

给玩家一条**能走进去、也能原路退回来**的路：小天地画布上的门牌（子目录 README）双击/回车 ⇒ 进入该子场景；顶部一条面包屑 + 一个「返回上一场景」 ⇒ 逐级退回；一个守在顶栏右侧的「离开小天地」 ⇒ 一次性退出整个小天地并**复位场景**。

**为什么这是 N2d 的全部**：后端（`02`）已经能把「`characters/elias/office` 这个场景的卡 + 它的直接子目录门牌」端出来，前端却（a）不传 `onEnterGate`，门牌是**死点击**；（b）没有 `nookScene` 状态，无法让第二次请求带上 `?scene=`；（c）`NookView` 的 props 里没有 `scene`/`onEnterScene`，App 无从驱动它。三条缺一，玩家就停在「看得见 5 个门牌、一个也进不去」。

### 步骤 3 —— 门牌进门：`onEnterGate` 接线（**今天的核心缺口**）

**现状（【实测】，`06-验收与回归.md:414` 独立复核过）**：`NookView.tsx` 的两处 `<Canvas>`（空态 `:561`、state 态 `:603`）**都没有传 `onEnterGate`**；而 layer 的 `App.tsx:1251` 传了（`onEnterGate={(target) => { void enterGate(target, 'double-click'); }}`）。

⇒ 今天的行为链：`CanvasObject` 的 `isGate` 为真（`:205`，门牌三条件全中）→ 双击 `:288-293` / 回车 `:294-305` 调 `requestEnter(gateTarget)` → `requestEnter` 调 `onEnterGate?.(target)`（`:246`）→ `onEnterGate` 是 `undefined` ⇒ **静默 no-op**。

设计（两处 `<Canvas>` 各加一行，其余 props 不动）：

```ts
// NookView.tsx 内部，NEW
const handleEnterGate = useCallback((target: string) => {
  // 门牌回调给的是【完整世界根路径】（CanvasObject.tsx:235-237：
  //   gateTarget = frontmatter.target ?? path.replace(/\/README\.md$/, '')
  //   对 nook 门牌 ⇒ 'characters/elias/office'）。
  // 契约 §5.1 冻结的形状 + 契约 §4.6 冻结的转换：MUST 走唯一实现，MUST NOT 在前端拆 '/'。
  const nookId = nookIdOf(characterId);                        // rules/characters.ts:35 → 'characters/elias'
  if (nookId === null) return;                                 // characterId 非法（防御性）
  const scene = nookScenePathOf(target, nookId);               // NEW（01 实现，00 §5.1）→ 段 / ''（根）/ null（越界）
  if (scene === null) return;                                  // ← 不在【本】角色子树内 ⇒ 越界门牌，不进
  onEnterScene(scene === '' ? null : scene);                   // '' = 角色根 ⇒ 状态的根哨兵是 null（§4.6）
}, [characterId, onEnterScene]);
```

两处 `<Canvas>` 各加 `onEnterGate={handleEnterGate}`。

- **⚠️ 两个「空」不是同一个「空」（必须逐字照抄上面两行判断）**：契约 §5.1 的冻结签名是 **`nookScenePathOf(sceneId, nookId): string | null`**，其语义（`00-共同上下文.md:359-369`）是：
  - `nookScenePathOf('characters/elias', 'characters/elias')` → **`''`**（**角色根本身**，合法）；
  - `nookScenePathOf('characters/ryo/x', 'characters/elias')` → **`null`**（**不在该角色子树内**，非法）。

  而契约 §4.6 冻结的状态是 `nookScene: string | null`，**`null` = 角色根**。⇒ **`''`（合法根）与 `null`（非法越界）在返回值里只差一个真值判断，语义却相反**；若写成 `if (!scene) return;`，则「点门牌回到角色根」会被**静默吞掉**（玩家点了没反应）。**MUST 用 `=== null` 判越界、用 `=== ''` 判根。** ⇒ 冲突 **C6 已裁决（2026-09-15）**：`''` 是**合法值**（本角色根），`null` 是**越界值**，两者 **MUST NOT 合并** —— 本文保留归一、§5.1 保留两参签名，均按此实现。
- **`nookIdOf` 而非手写 `'characters/' + characterId`**：`rules/characters.ts:35` 是唯一构造 nook 路径形状的地方（其 doc 注释逐字「callers must not concatenate it themselves (docs/nook/00 anti-pattern 2)」）。
- **`characterIdOfPath` 不需要了**：新签名把「归属哪个角色」交给 `nookScenePathOf` 的第二参数（`nookId`）自己判 ⇒ **越界由 `null` 表达，不再需要前端单独调 `characterIdOfPath`**。这比本文初稿更少代码、更少口径。（初稿写的是 `characterIdOfPath(target) !== characterId`；随 §5.1 的签名更正**一并删除**。）⇒ **NookView 的 import 面只需 `nookScenePathOf` 与 `nookIdOf` 两个符号**（`isNookSceneId` 也不再需要：`nookScenePathOf` 内部已经做形状与归属校验，非法输入返 `null`）。
- **越界门牌会被挡**：门牌路径理论上都是本角色子树，但**防的是「服务器将来把别角色的路径塞进 items」**——那会让玩家在 elias 的小天地里点进 ryo 的场景，而 `nookScene` 的语义是「相对**本**角色根」。挡不住时请求 `characters/elias/x` ⇒ 404 ⇒ **错场景的报错，指向不存在的目录**（比不响应更难诊断）。
- **漏了会怎样**：门牌渲染成「可进入」的样子（`CardRenderer.tsx:142` 按 `filename === 'README.md'` 渲染门牌卡，带 `DoorOpen` 图标与「SCENE · ENTRANCE」文案），但点了没反应——**这就是今天的状态**，也是 `06` 的 N2-A26 修复前断言要锁的那条。
- **跨端点名**：生产端 = `02` 的门牌项（`items[].path = '<子场景>/README.md'`，`00` §4.3）；消费端 = `CardRenderer` 渲染（既有）+ `CanvasObject.requestEnter`（既有）+ **`NookView.handleEnterGate`（NEW）** + `App.onEnterScene`（NEW）。**缺本文这一环，两端以「死点击」形态落地。**

### 步骤 5 —— 返回上一场景：**取父路径，不是回根**

```ts
// NookView.tsx 内部，NEW
const handleBackScene = useCallback(() => {
  if (scene === null) return;                             // 已在根，无上一级
  const slash = scene.lastIndexOf('/');
  onEnterScene(slash === -1 ? null : scene.slice(0, slash));  // 'a/b' → 'a'；'office' → null
}, [scene, onEnterScene]);
```

- **`scene` 是相对段，父段就是它自己的字符串前缀**——`'a/b'` → `'a'`，`'office'` → `null`。这是**纯字符串前缀**，不是路径解析（无前导/尾随斜杠、无 normalize）。契约 §4.1 保证状态形状合法：`nookScene` **只由两个写入点写入**——`handleEnterGate`（步骤 3，把 `nookScenePathOf` 的 `''` 归一成 `null`）与 `onEnterScene(null)`（退出复位）。⇒ **状态值域 = `'<seg>[/<seg>]*' | null`，永不出现 `''`**（`''` 是 §5.1 的返回哨兵，不是状态哨兵；这一层归一**只发生在步骤 3 一处**，所以步骤 5 可以放心地用 `null` 判根）。
- **⚠️ 与 `nookSceneParent` 的边界（评审 A / `02:436` 的 major，本文明确划线）**：
  - **「完整 id → 父 id」MUST 用 `nookSceneParent`（`00` §5.1 的唯一实现）**。**本文没有任何一处做这件事** —— 本文全部 `lastIndexOf('/')`/`slice` 只出现在**本步骤**，且只作用于**相对段**（`nookScene`，值域 `'<seg>[/<seg>]*'`，**永不带动 `characters/<id>` 前缀**）。`nookSceneParent` 在本文**不被调用**（§8.4 逐字标「本文**不用**」）。
  - **本步骤取父是相对段的前缀**（`'a/b'` → `'a'`）——**不是**「完整 id → 父 id」。这与**步骤 12（面包屑）**的方向相反：那里是**完整 id → 相对段**，**MUST** 用 `nookScenePathOf(state.layer, nookId)`（**两参**）。两者**不可互换**，也**不可互相代劳**。
  - **`02:436` 指认的落点复核**：若指认的是「面包屑/显示身份」，落点是**步骤 12**（已用两参 `nookScenePathOf`）；若指认的是「返回按钮」，落点是**本步骤**（相对段前缀，**已裁决不收口**，C2）。**两处都不是单参 `nookScenePathOf`，也不是自写完整 id 拆段。**
- **契约 C2 已裁决（主 agent 2026-09-15）：相对段取父由前端自取前缀，不收口**（它不是语义判断）。理由：§5.1 禁的是**校验/归属判断**在多地各写一份；这里没有判断，只有一次前缀操作，且 `nookScene` 的形状**已由 `nookScenePathOf` 的返回类型与步骤 3 的归一保证**。（`01` 若有反例可用证据推翻。）见冲突 **C2**（§⑪ 已标「✅ 已裁决」）。
- **深度不限**（契约 §4.6 / §3 决定 1）：`'a/b/c'` → `'a/b'`。**不是回根**。

#### 7.1 为什么 MUST 有 `isRootScene` 这道门（独立小节，且**不只是隐藏按钮**）

```ts
// NookView.tsx，NEW

const showInitPrompt = onRequestInit !== undefined && isRootScene;    // NEW
```

**这道门的存在理由，与「空态猜错」无关**——空态判据已经同源（上面已证）。它防的是**一次真的内容损坏**：

```text
resolveInit(text)            NookView.tsx:346-355
  → onRequestInit('nook', characterId, req)     ← 实参里【只有 characterId】，没有 scene
  → App.tsx:1203 逐字 sendMessage({ type: 'airp_init', kind, target, request, by: 'player' })
  → target = characterId 被【原样转发】
```

⇒ **`airp_init` 的 `target` 恒为「角色根」，且这条通路没有地方能表达子场景。** `NookView` 里没有任何 prop、任何 state 能把这个请求改道到 `characters/elias/office`。所以子场景里弹出一个**可提交**的初始化控件，等于给玩家一个**会写错地方的按钮**：他以为在给空子场景布置，实际在**父/根房间**铺了一层家具。契约 §5.4 的 hazard B（`00` §5.4 表 B 行）是同一类损坏——「在已布置好的房间里再铺一层」，`extensions/instructions.ts:333` 逐字「第二套家具读起来是杂物，不是生活」。

**为什么不能「只是隐藏按钮」（把 `StubPrompt` 换成一个 disabled 的 `WriterBar`）**：

1. **`onRequestInit` 的缺失 ≠ 语义上的「不该初始化」**。今天的 `:590-601` 用 `onRequestInit ? <StubPrompt/> : <WriterBar disabled/>` 分流——那个三元表达的是「**宿主没接初始化能力**」（App 没传 callback），而不是「**这个场景不该被初始化**」。子场景的情形是后者：宿主**有能力**（callback 在），但**目标不对**。用同一个三元承担两种语义，会让下一个读代码的人以为「子场景=不支持初始化」，而真相是「初始化只对根有意义」。**一个判据表达一个含义。**
2. **只隐藏按钮，居中文案照出**是**可以**的（本文正是这么做的，见下）；但**只隐藏 `StubPrompt` 而不动居中文案**是对的，**「把整个文案也藏掉」是错的**——空房间必须仍然读到「这里是空的」（`docs/nook/02` §3.8 步 18：`doc-11 §4.1` 的「走进一个空房间」语义）。⇒ 门必须**精确地**开在「可提交控件」上，而不是开在「空态」上。如果图省事写成 `if (isEmpty && isRootScene) { 整个空态块 }`，子场景的空态会变成**一片空白画布**（更糟）。
3. **`isRootScene` 是「场景身份」的判据，不是「空态」的判据**：它同时是**范围护栏**——契约 §6 明令本批不做子场景 nook-init。把范围护栏和 UI 条件分开写，将来「子场景也能初始化」落地时，改的是那一个 `&& isRootScene`，而不是去翻空态逻辑。

**渲染条件变化**：`:584-604` 的 `!initializing && (…)` 块里的 `StubPrompt`/`WriterBar` 改由 `showInitPrompt` 门住；**居中文案**（`copy.nookEmptyTitle`/`nookEmptyBody`，`:583-586`）**保留**。

- **`漏了会怎样`**：见上（在父亲房间里铺一层家具）。**且它不会报错**——`airp_init` 对已有内容的根会「已有内容就停」（`extensions/instructions.ts:333`），所以玩家看到的是**什么都没发生**（点了、输了字、房间没变），比报错更难诊断。
- **子场景的空态：只能看，不能初始化**。契约 §6 明令本批不做。**登记 §⑫ U3**（玩家会在这里撞到「看不到出路」——这是**已知的、被接受的**范围边界，不是 bug）。

**实现（一个 effect 覆盖 #1–#3，一个显式调用覆盖 #4）：**

```ts

// openPrivateSpace（:361-384）的换角色分支，紧邻 :379 的 setNookChar(characterId)：

```

- **为什么 effect 只判 `=== null` 而不判「换值」**：effect 看不到**上一个** `nookChar`（`useEffect(…, [nookChar])` 的闭包只有新值），要判「换值」得再引入一个 `prevRef`——**那是把「哪个位点会换值」的知识藏进一个 ref 比较里**，比在唯一一个换值位点（`:379`）显式写一行更难审查。⇒ **契约要求「判据是取值变化」，落实为「effect 管所有 `null` 落点 + `:379` 管唯一的非 `null` 换值」**：合起来等价，且每一处都看得见。

- **裁定**：**不给返回绑 `Esc`**。`Esc` 保持「退出小天地」（`App.tsx:659`）。
- **理由**：`Esc` 今天已有明确承诺（`entry.owner === 'nook'` → `closeNook`）。若随深度改绑返回，`Esc` 的含义**依赖当前所处深度**（根场景 = 退出、子场景 = 退一级），玩家无法建立稳定预期；且深场景退出要连按多次才能离开。**语义稳定 > 少点一次。**
- **反例条件（若将来这些成立，可复议）**：① 面包屑/返回的**可视性**不足（玩家找不到它）；② 深度实测常见 ≥ 3 层且玩家频繁逐级退；③ 产品明确要求 `Esc` 是「浏览器式逐级返回」。**当前三者都不成立**（深度不限但实测最深 2 段、返回按钮在顶栏恒显）。

- 契约 §4.6 末条冻结「不引入路由库，URL 不含 nook 状态」。**后果**：玩家在子场景里刷新 / 分享链接 / 浏览器前进后退，都会回到**角色根**（并因 `nookChar` 也在内存而回到**世界启动层**）。

**U6 —— C3 修法的容器选择器（✅ 已裁决）**

**U8（✅ 已裁 2026-09-15，主 agent）：本批不修 `CardRenderer` 的内联三元 i18n 机制，登记为已知缺口。**

- **不是待拍板 —— 已裁定「本批不修」，理由是范围纪律**：修它要把 `t()`/`UI_COPY` 引入 Canvas 内**所有**卡片文案 ⇒ 那是另一范围的工作，会把这批从「子场景通路」稀释成「Canvas 卡片 i18n 重构」。**范围纪律优先。**
- **缺口是什么（具体后果，不是抽象风险）**：`CardRenderer.tsx:160-161` 逐字 `ja ? 'まだ白紙 …' : 'UNWRITTEN …'`（`ja` 来自 `:76` `locale === 'ja'`）——**不走 `t()`、也不走 `UI_COPY`**。⇒ 本批改后的 `stub=true` **新文案，中文用户会看到英文**（`zh-CN` 落到 `ja === false` 分支）。`check:i18n` **看不到它**（它只扫字面量 `t(`）。
- **触发条件（下一个读者据此判断「这是不是忘了本地化」）**：**仅**当文案走**内联 `locale === 'ja' ? … : …` 三元、不经 `UI_COPY`/`t()`** 时发生。⇒ 这不是「忘了本地化」，是**机制缺陷 + 已知取舍**：`tools/check-i18n.mjs:18-21` 头部逐字登记的既有缺陷**完全同型**（*"inline `locale === 'ja' ? … : …` ternaries bypass `t()` entirely (zh-CN silently gets English). That is a niko-side pattern predating this gate"*）。**本批改动（步骤 14 只换字符串、沿用三元）不引入新缺陷、也不构成回归。**
- **将来的修法（登记，非本批）**：给 `CardRenderer` 接 `useLocale().t`，或把 `meta` 两条提进 `UI_COPY` + `messages.json`（`stub` / `SCENE · ENTRANCE` 各一条 en + ja + zh-CN）。**超出 N2d「只做加法」边界。**

## 附二：C3 的**精确症状**（N2Verify 复核，本文确认）

上表 C3 与步骤 11 的措辞是「**进门 + 焦点跳到 writer**」——**精确地说是**：

- **症状 = 焦点被甩到 writer**（capture 阶段的 `App.tsx:725-730` 抢走）。
- **不是**「进两次门」：`CanvasObject.tsx:239` 逐字 `if (enterPendingKey.current === target) return;` —— 去重是**按 `target` 键控**的 500ms 窗口，即使 capture/冒泡各触发一次 `requestEnter`，`onEnterGate` **只会被调一次**。⇒ **`nookScene` 不会跳两次、不会多一次 `GET /api/nook`。**
- **`Esc` 不受影响**：`App.tsx:659` 的 nook 分支与 `Enter` 分支互不干扰。
- **返回按钮不受影响**：`isTextEditingTarget`（`App.tsx:157`）的选择器逐字含 `button,a,[role="switch"]` ⇒ 返回按钮上的 `Enter` 已被 `:708` 排除。**门牌卡的根 `div`（`tabIndex={0}`，不是 button）是唯一落入缝里的目标。**
- **⇒ `06` 的 C3 断言应写成「焦点仍在画布/门牌」**（本文 §⑩ 表 #9 已如此），**不要**写成「只进一次门」（那条在修复前也绿，是假绿）。
