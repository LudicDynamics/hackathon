# doc-22 Hook 注入协议：状态块与事件段

> 状态：**定案，待实现（2026-09-12）**。起因：doc-21 把"事件只描述变化"钉死之后，"柜台上有铜钥匙 / 玩家在哪 / 角色各自在哪"这些**当前值**就没有归宿了——它们不是事件，但 agent 每轮都必须知道。本文定这一块。

## 0. 一句话

**每轮注入 = 状态块（当前值，指纹去重）+ 事件段（变化，游标去重）。两者机制不同，不能互相替代。**

---

## 1. 为什么两样都要

一个很自然的想法是"只留一样就够了"——两个方向都塌。

| 只留…… | 塌在哪 |
|---|---|
| **只留事件** | 事件重放不出"现在什么样"。角色刚 spawn，要知道"柜台上有铜钥匙"就得把创世至今的事件全读一遍再在脑子里做加减——这是把日志当数据库用，且随轮次线性变长 |
| **只留状态** | 指纹 diff 只能说出"和上次不一样了"，说不出**谁干的、什么顺序、中间经过了什么**。而 AIRP 要的恰恰是因果：作家需要知道"玩家把钥匙**拿走了**"，不是"钥匙现在在背包里" |

Nodesign 只需要前半段（它是工具型产品，没人在乎谁动的），AIRP 两段都要。**这就是 AIRP 比 Nodesign 多一层的地方，不是抄漏了。**

| | 状态块 | 事件段 |
|---|---|---|
| 回答 | 世界现在什么样 | 世界怎么变成这样的 |
| 来源 | `canvas.db` + 目录扫描 | `history.db` 事件表 |
| 去重 | **每节指纹**比对上一轮 | **`seq` 游标** |
| 丢了会怎样 | agent 瞎猜"这个/这里" | agent 不知道刚发生了什么，装傻或胡编 |
| 落地 | 本文 | doc-21 |

## 2. 从 Nodesign 抄什么

九条，逐条抄。解剖过程见 doc-18 §124/§125，这里只列定案。

| # | 机制 | 抄成什么 |
|---|---|---|
| 1 | **按节组织**：每节 `{ key, title, text, items? }` | 状态块是若干节的拼接，不是一段散文。节是去重、诊断和增删的最小单位 |
| 2 | **首轮全量，之后只报变化** | 每节算 djb2 指纹存进程内存；变了的节重发，没变的不发 |
| 3 | **清单节报增删** | 素材/文件清单这类节带 `items`，变化时只说"新增 2：a、b；移除 1：c（现共 9 件）"，不重列全表 |
| 4 | **没变的节末尾点名** | `未变：本层现有、在场角色`——**这一行不能省**。不点名，模型会以为这些东西消失了 |
| 5 | **一节都没变 → 一句话** | `[世界状态：与上一轮相同（……）]` |
| 6 | **压缩后重置记忆，下一轮重新全量** | 摘要把旧状态块吞了，"同上轮"没有所指。pi-rp 的 `session_compact` 事件是钩子 |
| 7 | **量化再算指纹** | 相机挪一像素不算"变了"（Nodesign 按 1/8 视口量化）。AIRP 的对应做法见 §5 |
| 8 | **fail-soft 到节** | 某节采不到就**让它不出现**（"扫不动就不说，别拿错信息误导"），单节异常 warn + 跳过，绝不炸一轮 |
| 9 | **一份措辞，两处复用** | `describeViewpoint` 同时供注入和 `read_user_view` 工具。AIRP 对应：状态块的 formatter 与 `look_at` 的 formatter 是同一套（doc-20 §3.1） |

### 2.1 它的接线我们不抄

Nodesign 把状态块**拼进 prompt 文本**（`client.prompt` 前加 `<system>…</system>`）——因为它从 Claude SDK 的 `UserPromptSubmit` hook 迁过来时，当时判断 pi 侧没有等价物。

AIRP 走 **`before_agent_start` 返回 `{ message: … }`**，三点更好：

- **身份清楚**：是一条独立的 `custom_message`，不是混在玩家那句话里。作家不会把系统噪音当成玩家说的（doc-03 人话协议最容易破功的地方）；
- **不炸缓存**：`BeforeAgentStartEventResult` 还允许替换 `systemPrompt`——**不要用它**。system prompt 是每轮不变的冻结区，改一个字整段缓存作废（doc-18 §157）。可变内容只能挂在尾部，`message` 正好在尾部；
- **可声明策略**：`pi.registerCustomType(type, { compaction: "exclude", context: "include" })`。pi-rp 源码里这个字段的注释点名了这个用法：注入式的 state 快照"模型下次请求要看到，但总结只关心正文"。再配 `display: false`，状态块不进画布（doc-05 §5：chat 中间语言绝不进画布）。

## 3. 分节表

### 3.1 作家（6 节）

| key | 标题 | 来源 | 节型 | 纪律 |
|---|---|---|---|---|
| `viewpoint` | 玩家视点 | `canvas.db` 视点表（前端上报） | 单行 | **不给坐标数字，给人话方位**。附一句指代消解优先级 |
| `layer_files` | 本层现有 | 目录扫描 | 清单 | 只列路径 + 一行这是什么，**不灌全文** |
| `cast` | 在场角色 | `canvas.db` `presence` | 清单 | 谁在这层、大致在哪、谁在跟随 |
| `bag` | 玩家背包 | `player/` 扫描 | 清单 | 同上，只列不灌 |
| `recent_chalk` | 最近板书 | 跨层按 mtime 取 8 | 清单 | 路径 + 首行，正文自己 `look_at` |
| `dynamics` | 世界动态 | `history.db` 事件表 | **游标** | doc-21 §5.1：游标增量、排除自己、合并、上限 12 |

### 3.2 角色（4 节）

| key | 标题 | 差异 |
|---|---|---|
| `standing` | 你在哪 | 换成角色自己的位置 +「玩家此刻在你面前」，不报玩家的相机 |
| `layer_files` | 本层现有 | 同作家。层内的 chalk 按时间排，兼掉 `recent_chalk` 的职责 |
| `cast` | 还有谁在 | 排除自己 |
| `dynamics` | 最近发生了什么 | doc-21 §5.2：本层过滤、首次取最近 12 条、关遮罩推游标 |

**角色不注入 `bag`**：玩家的口袋不在角色的视野里。但这是**省 token 和合乎叙事，不是门禁**——角色真要 `look_at player/` 也拦不住，AIRP 不做权限防备（doc-05 §4.1）。

### 3.3 注状态，不注指令

"怎么用这些东西"住 preset（缓存的 system prompt），**每轮再说一遍就是上下文里的 N 倍重复**。状态块里只有两类句子例外，因为它们依附于当下的值：

- 指代消解那一句（"他说「这个」多半指选中的 > 开着的窗 > 视口里的"）；
- 指路那一句（"要细节直接 `look_at` 上面的路径"）。

除此之外状态块里不出现祈使句。

## 4. 装配规则

```
[世界状态]                      ← 首轮：全量
  玩家视点：……
  本层现有：……
  ...
请基于这些处理玩家这一轮的行动。

────────────────────────────────

[世界状态]           ← 之后，只报变化
  玩家视点（有变化）：他走到柜台前，选中了铜钥匙。
  本层现有（有变化）：新增 1：02-柜台.md（现共 5 件）

[世界动态]                      ← 事件段，独立成段
  · 玩家把「铜钥匙」从柜台拿到了背包里。
  · 玩家掷骰：检定「推理检定」掷出 62（>50 通过）。
```

五条固定规则：

1. **首轮全量**，结尾一句"请基于这些处理玩家这一轮的行动"；
2. **之后逐节比指纹**：变了的节重发（标「有变化」），带 `items` 的节改报增删；
3. **没变的节在末尾一行点名**（规则 4 的理由见 §2）；
4. **一节都没变**就一句 `[世界状态：与上一轮相同（……）]`；
5. **`session_compact` 后清空指纹记忆**，下一轮重新全量。

**事件段永远独立成段**，不参与指纹比对——它本来就是增量，游标已经保证不重复（doc-21 §5.4）。

指纹记忆存**模块级 Map**：扩展跑在 agent 进程内，进程 = 会话，模块级天然就是会话级。不落盘。

## 5. 防抖：状态最怕"看起来一直在变"

相机每帧都在动。不做处理的话每一轮 `viewpoint` 节都"有变化"，指纹 diff 等于没做。三道闸：

| 闸 | 位置 | 做法 |
|---|---|---|
| **上报节流** | 前端 | 只在变化时发，最快 1.2s 一次；变化判据用量化后的 key（抄 Nodesign `useViewpointReport`） |
| **量化** | 前端与服务端**用同一个量化函数** | 相机位移不超过 1/8 视口就算没动 |
| **人话化** | 渲染 | AIRP 注入的本来就不是坐标而是方位词（"在柜台附近"）——**方位词的粒度就是天然的量化**。坐标只供引擎排座，不灌给 agent（doc-20 §3.2） |

第三道是 AIRP 相对 Nodesign 的简化：它要给 agent 报视口矩形（因为 agent 要往视口里摆东西），我们不用。

另加一条 **TTL**：视点超过 10 分钟没上报就当玩家不在，该节**整节缺席**而不是报一份陈旧值。

## 6. 状态存哪

| 状态 | 存哪 | 理由 |
|---|---|---|
| 当前层、卡片坐标、关系线、角色 presence、跟随 | `canvas.db`（已有表） | **属于世界**：进存档、跟着快照回滚 |
| 玩家视点（当前层/相机/选中/开着的窗） | `canvas.db` 新增 `viewpoint` 单行表 | 见下 |
| 每轮指纹记忆 | agent 进程内存 | 会话级，随会话消亡 |

**视点为什么也进 `canvas.db`，而 Nodesign 放进程内存**：Nodesign 的注入装配跑在 server 进程里，内存直接可取；AIRP 的装配跑在**扩展里，也就是 agent 进程**，与 server 不是同一个进程。共享文件是唯一不需要 sidecar 的通道——这正是 B2 已经选定的路子（server 写、扩展只读打开，开 WAL）。

**但它不属于世界**：单行、带 `at` 做 TTL、**快照不打包、回滚不还原**。它是"此刻玩家在看哪"，重启即作废。单玩家世界（doc-05 §6）所以单行就够，将来要拆多人再加 `player_id`。

前端上报的值**一律 sanitize**：数值 clamp、字符串限长、数组截断。前端上报不可信，这是注入链路上唯一的外部输入。

## 7. 两层：注入摘要，细节走工具

状态块给的是**一行摘要 + 一份清单**；要细节，agent 自己调工具。Nodesign 是 `read_user_view`，AIRP 是 `look_at`。

这和 B3 的"只给清单不灌全文"、pi-rp Agent Skills 的 progressive disclosure、doc-05 §1 的懒加载是**同一条原则的四次出现**。判据：注入负责让 agent **知道有这么个东西**，工具负责让它**看清楚**。

---

## 8. 明确不做

- **不注入全文**：任何节都只给路径 + 一行。注入正文 = 在上下文里造第二份世界副本（doc-05 §8.5）。
- **不做"哪些节该注入"的运行时配置**：分节表硬编码，改要改代码。可配置的注入次序是上下文事故的温床。
- **不在状态块里放规则和指令**（§3.3）。
- **不把状态写进事件表**：没有 `state_changed` 事件（doc-21 §8）。
- **不做 summary 压缩层**（2026-09-12 撤销）：注入块天生有界——状态块靠指纹 diff + 条目上限，事件段靠游标 + 12 条折叠，**大小不随轮次增长，没有压缩的对象**。真要压的两样东西各有归宿：画布上的叙事正文归 doc-08（`fold_chalk`，且是无损重组不是摘要），会话 transcript 归 pi-rp 自己的 compaction。理由详见后端实现计划 §6.6。

## 10. 留白

- **注入块末尾的「下一步」段（优先级最高的待设计）**：§3 的分节表解决"世界什么样"，但 agent 卡壳的典型形态是**知道了却不动**。注入块最后要再收一段祈使的、由事实推出来的"现在轮到你做什么"（未回应的玩家动作 / 刚生成尚未被看见的内容 / 明确的"什么都没发生，别为填空而写"）。**格式与措辞在 doc-12 #6 定**，本文只负责它在装配里的位置：永远在最后一节，跟着事件段走。
- **`bag` 与 `layer_files` 的条目上限**：暂定各 12，试玩时按实际上下文占用调。
- **多玩家**：`viewpoint` 表单行的假设只在单玩家世界成立（doc-05 §6 已定），云端版（doc-17）再议。
