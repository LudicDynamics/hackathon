## 1. 一句话定位

**给 `/ws` 加三道门：① upgrade 时校验 `?v=1`，不匹配**先完成握手再**带 4400 关闭；② 每 30 秒给每个连接发协议层 ping，上一轮没回 pong 的直接 terminate；③ 前端按 `closeKind` 决定「重连」还是「不重连」——这三件今天全缺，且第一件是被 `AGENTS.md:53` 的「唯一 WebSocket」边界锁死的高危改动。**

今天的实情：`wss.on('connection')`（`apps/server/src/index.ts:188`）直接接受一切 upgrade；全仓 **零** `ping`/`pong`/`isAlive`/`heartbeat`；`useWorld` 的 `ws.onclose`（`apps/web/src/state/useWorld.ts:986-995`）只检查 `stopped`，然后**无条件** 1200ms 重连——一个被服务端因协议不匹配踢掉的客户端会**每 1.2 秒**重连一次，永远。

## 2. 签名与参数

### 2.1 `apps/server/src/gateway/heartbeat.ts`（NEW）

```ts
export interface HeartbeatOptions {
  /** Ping cadence. Default `AIRP_WS_HEARTBEAT_MS` ?? 30_000 (plan §9:542). */
  intervalMs?: number;
  /** Injected clock — tests drive liveness without real timers. */
  now?: () => number;
}

export interface HeartbeatHandle {
  /** One sweep. Exported shape so a test can drive it directly. */
  tick(): void;
  stop(): void;
}

/**
 * Pure decision for one client: a socket that did not answer the previous ping
 * is dead and MUST be terminated. Exported so the unit test can assert the
 * truth table without a real WebSocket.
 */
export function shouldTerminate(state: { isAlive: boolean }): boolean;

/**
 * Server-side liveness. Browser JS cannot send a protocol-level ping, so the
 * server drives it: mark every client not-alive, ping, and terminate any client
 * that was still not-alive at the START of the sweep (i.e. missed the previous
 * pong). One missed pong = terminate — mobile NAT drops must not linger as
 * zombie members of the fan-out set.
 *
 * NOTE: this function only ever sees clients that ALREADY exist when a sweep
 * runs. It therefore CANNOT install the per-connection `isAlive = true` /
 * `on('pong')` wiring for connections created later — that lives in
 * `wss.on('connection')` (`index.ts:188`, §3.2 第 7 步 / §8).
 *
 * Mirrors `~/projects/worldlines-rivet/services/gateway/ws.mjs:134-155`.
 */
export function startHeartbeat(
  wss: { clients: Iterable<HeartbeatClient> },
  options?: HeartbeatOptions,
): HeartbeatHandle;

export interface HeartbeatClient {
  isAlive?: boolean;
  ping(): void;
  terminate(): void;
  on(event: 'pong', handler: () => void): void;
}
```

### 2.2 `index.ts` 的 upgrade 门禁（NEW）

```ts
// Replace the bare `new WebSocketServer({ server })` (index.ts:53) with a
// noServer server + an explicit upgrade handler, because a rejected upgrade
// must still complete the handshake to carry a close CODE.
const wss = new WebSocketServer({ noServer: true });

server.on('upgrade', (req, socket, head) => {
  const url = new URL(req.url ?? '/', 'http://localhost');
  // `/ws/stt` keeps the SAME wss + connection-time path split as today
  // (index.ts:188-191). It MUST also `handleUpgrade` here, or the connection
  // event never fires and voice input dies.
  if (url.pathname === '/ws' || url.pathname.startsWith(STT_STREAM_PATH)) {
    if (url.pathname === '/ws' && url.searchParams.get('v') !== PROTOCOL_VERSION) {
      wss.handleUpgrade(req, socket, head, (ws) => {
        ws.close(WS_CLOSE.PROTOCOL_MISMATCH, 'protocol version mismatch');
      });
      return;
    }
    wss.handleUpgrade(req, socket, head, (ws) => wss.emit('connection', ws, req));
    return;
  }
  // unknown path: no upgrade
});

const heartbeat = startHeartbeat(wss);
```

> **STT 的 upgrade 归属（B1 修订）**：`/ws/stt` 今天由 `wss.on('connection')` 内的路径判断分流（`index.ts:188-191`：`if (req.url?.startsWith(STT_STREAM_PATH)) { handleSttStream(ws); return; }`）。**全仓只有一个 `new WebSocketServer`（`index.ts:53`），STT 没有自己的 upgrade 处理器**——`handleSttStream` 只是被 `connection` 事件调用的一个函数（`apps/server/src/engine/stt-stream.ts:33`）。改成 `noServer` 后，`connection` 只能由我们自己的 `handleUpgrade` 回调里的 `emit('connection', …)` 产生，所以 STT 分支**也必须** `handleUpgrade` + `emit`（**不能**只 `return`）——否则 `/ws/stt` 永不 upgrade，语音输入整条死。这与 §8 的做法一致；本文件 §2.2 / §3.1 第 4 步 / §8 三处必须保持同一写法。

## 3. 行为契约逐步

### 3.1 版本协商

1. **upgrade 时解析 `req.url` 的 `pathname` 与 `v`。**
   漏了会怎样：无从判断，只能全部接受（现状）。
2. **`pathname === '/ws'` 且 `v !== PROTOCOL_VERSION` → `handleUpgrade` 后 `ws.close(4400, reason)`。**
   漏了会怎样：若直接 `socket.destroy()`，客户端只看到 HTTP 400 或 `1006`，**拿不到 4400**，`closeKind` 无从分类。这是 rivet 血泪注释的原话（`ws.mjs:51-57`：「只有 upgrade 成功后的 close frame 才能把 4400/4404 + reason 送达客户端」）。
3. **`pathname` 不是 `/ws`（也不是 `/ws/stt`）→ 不 upgrade（走 `server` 的普通 HTTP 处理）。**
   漏了会怎样：SPA fallback（`index.ts:180-185` 的 `app.get('*')`）与静态资源（`:177` 的 `express.static`）会与 WS 抢 upgrade。
   **`[推断]` base-path 前缀风险（m6）**：这里的等值判断假定到达服务端的 `pathname` 就是 `/ws`。但前端 `apps/web/src/lib/base-path.ts:8` 的 `ROOTED = /^\/(?:api|ws)(?:[/?#]|$)/` 会把 `/ws?v=1` 重写成 `<BASE>/ws?v=1`（子路径部署，`Dockerfile.vercel:15` 的 `AIRP_WEB_BASE`）。**若反向代理不剥掉 `<BASE>` 前缀，`pathname` 会是 `<BASE>/ws`，本门禁判「不 upgrade」**。这是**部署侧行为，主 agent 未证实**，本设计不断言它一定是 bug。处置见 §12.6（待部署方确认；若确认会撞上，需把判断放宽为「去掉已知 base 前缀后等值」或让代理剥前缀）。
4. **`/ws/stt` 的 upgrade 走与 `/ws` **同一个** `wss`：`handleUpgrade` 后 `emit('connection', ws, req)`，由 `wss.on('connection')`（`index.ts:188`）里的路径判断分流给 `handleSttStream`。**
   漏了会怎样：STT 语音输入**整条死掉**——`handleSttStream`（`apps/server/src/engine/stt-stream.ts:33`）只能由 `connection` 事件拿到已经 upgrade 的 socket（今天 `index.ts:190-191`），而 `noServer` 下 `connection` 只由我们 `handleUpgrade` 回调里的 `emit` 产生（`{ server }` 模式的隐式 upgrade 处理器已随 `noServer` 消失）。若这里只 `return`（不 `handleUpgrade`），`/ws/stt` 永不 upgrade、`connection` 永不触发、麦克风 UI 永远卡在「连接中」。
   **与今天的语义完全一致**：今天 `req.url?.startsWith(STT_STREAM_PATH)`（`:190`）就是判前缀，本批只是把「谁来 upgrade」从 `{ server }` 的隐式处理器换成我们自己的 `handleUpgrade`，**分流仍然在 `connection` 里按路径做**（`00 §2` 不做项 7：STT 仍共享同一 wss；STT 连接同样被加上 `isAlive`/pong，无害）。
5. **`PROTOCOL_VERSION` 只作用于 `/ws`，不影响 HTTP。**
   漏了会怎样：若把 `?v=` 也当成 `/api/*` 的门禁，所有既有 HTTP 调用（`airp-gateway.ts` 的 `request(...)`）全 400。

### 3.2 心跳

6. **每 `intervalMs`（默认 30000）扫一遍 `wss.clients`：先判 `isAlive === false` → `terminate()` + `continue`；否则置 `false` 并发 `ping()`。**
   漏了会怎样：死 socket 永久留在 `wss.clients` 里，成为每帧 fan-out 的**静默**成员。**实测（主 agent NAT 黑洞 spike）**：黑洞 socket 上 `send` **不抛错**（OS 缓冲接受写入），`broadcast` 的 per-client try/catch（`apps/server/src/engine/event-bridge.ts:440-450`，`try` 在 `:446`、`catch` 在 `:447`、`console.warn` 在 `:448`）**一次都不会触发**，**连 `console.warn` 都不打**。所以代价不是「CPU + 日志噪音随重连线性增长」，而是**完全静默的成员泄漏**：send 成功、无异常、无日志；**只有主动 ping + 超时 terminate 能发现**。这与 `docs/tools/00` 硬约束 4 的精神一致——「不静默降级」的前提是**先能看见**；看不见的泄漏必须靠主动探活回收，而不是等它自己报错。
7. **连接建立时置 `ws.isAlive = true`，并监听 `pong` 置回 `true`。落点是 `wss.on('connection')`（`index.ts:188`），与既有 `connected` 帧（`:196`）同址——不是 `startHeartbeat`。**
   漏了会怎样：`undefined !== false` 会让新连接躲过第一轮清扫（无害），但**pong 不置回**就会在第二轮被误杀——**每 30 秒杀掉全部活连接**，前端陷入重连循环。
   **为什么不能放进 `startHeartbeat`**：它的签名只收 `{ clients: Iterable<HeartbeatClient> }`（§2.1），而 `emit('connection')` 建立的连接只是被塞进 `wss.clients`，**不经过 `startHeartbeat` 的任何钩子**；`startHeartbeat` 只在 `intervalMs` 到点时遍历 `wss.clients`，**天然错过「上一轮 sweep 之后才建」的连接**。若把初始化放在那里，新连接 `isAlive` 初值恒 `undefined`：它躲过第一轮判（`undefined === false` 为假），却从不装 `pong` 处理器，于是第二轮 sweep 见它仍非 `true` → `terminate()`。**约每 60s（两轮）把当时在册的全部客户端杀光**，前端陷入重连循环。所以连接级初始化**必须在连接时**做，落点见 §4 表与 §8 表新增行。
8. **`terminate()` 用 `try/catch` 包住；`ping()` 同理。**
   漏了会怎样：一个已 `CLOSING` 的 socket 抛错会中断整个 sweep，**后面的客户端全部漏检**（与 `broadcast` 的 per-client 纪律同因）。
9. **定时器 `unref()`，`SIGTERM`/`SIGINT` 时 `heartbeat.stop()`。**
   漏了会怎样：`unref` 漏 → 测试进程不退出；`stop` 漏 → 关服时定时器继续 `ping` 已关的连接（日志噪音），且与既有 `lifecycle.stopAll()`（`index.ts:360-366`）的退出路径打架。

### 3.3 关闭码分类（前端）

10. **`closeKind('protocol')` → 不重连，发可见 notice。**
    漏了会怎样：协议不匹配（例如部署了新前端连旧后端）会导致**每 1.2 秒一次**的重连风暴，且服务端每轮都要 `handleUpgrade` + `close`。
11. **`closeKind(null)`（1006 网络抖动等）→ 保持既有 1200ms 重连。**
    漏了会怎样：正常掉线不重连，玩家输入永久禁用（`perform/01 §6.4` 记录的事故族）。
12. **`closeKind('session')`（4404/1001）→ 本批与 `null` 同处理（重连）。**
    漏了会怎样：**AIRP 不发 4404**（单世界单会话，无「会话不存在」概念，`00 §3.1`），所以这条分支今天不可能到达；若将来多世界引入 4404，重连会失败但**不静默**（用户看到输入禁用 + notice）。登记 §12.4。

## 6. WS / 前端反应

| 事件 | 服务端 | 前端 |
|---|---|---|
| 连上 | 版本匹配 → upgrade → `connected` frame（`index.ts:196`）→ `eventBridge.replayTo(ws)`（`02`） | `onopen`：`resetWriter('socket_open')`、`fetchLayer` |
| 版本不匹配 | `handleUpgrade` → `ws.close(4400, 'protocol version mismatch')` | `onclose` → `closeKind === 'protocol'` → **不重连** + notice |
| 30s 无 pong | `terminate()` | `onclose` → `closeKind(1006) === null` → 1200ms 重连 |
| 正常关服 | `SIGTERM`/`SIGINT` → `heartbeat.stop()` + `lifecycle.stopAll()`（`:360-366`）→ 进程退出（socket 由 OS 关，前端看到 1006） | 同上（重连会失败直到服务端回来） |

**`connected` 帧与心跳无交互**：`connected` 是应用层标记（`check-ws-contract.mjs:82` 的 `INTENTIONALLY_UNCONSUMED` 理由「socket 已开就是信号」），心跳是协议层 ping/pong，两者不共享通道。

## 7. 错误边界（不静默降级）

| 情形 | 行为 | 判据 |
|---|---|---|
| `req.url` 为 `undefined`/畸形 | `new URL(req.url ?? '/', 'http://localhost')` 兜底；`pathname === '/'` → 不 upgrade | 不抛错、不断言 |
| 版本不匹配 | **响亮**：close code 4400 + reason 字符串（人话，供日志；前端**不得**嗅探它） | `00 §6.6` 反模式 6 |
| `ping()` 抛错 | 吞掉并 `continue`（该 socket 下轮必被 terminate） | rivet `ws.mjs:134-155` 原设计 |
| `terminate()` 抛错 | 吞掉 | 同上 |
| 心跳定时器本身抛错 | **不允许**：sweep 体内的每个客户端都单独 try/catch，循环本身无抛出点 | — |
| 前端连的是旧后端（无版本门禁） | 旧后端的 `wss.on('connection')` 见 `req.url === '/ws?v=1'`，`startsWith(STT_STREAM_PATH)` 为 false → 正常接受 | **前向兼容**：`?v=` 对旧后端是**无害的额外 query** |
| 前端连的是新后端但漏改 `?v=` | 全站 4400 → `closeKind` notice → **不重连** | 这是有意的响度；见 §9 执行序 |
| 死 socket（NAT 黑洞） | 主动 ping 超时后 `terminate` 回收 | **静默泄漏**：`send` 不抛错、无 warn（§3.2 第 6 步）——只能靠探活发现 |

**`noServer` 改造的连带面**（必须一次做完，否则启动即坏）：
- `/ws/stt`：upgrade 钩子必须对 STT 路径**也**做 `handleUpgrade` + `emit('connection')`（§2.2 / §3.1 第 4 步），**保留今天的分流语义**——STT 与主通道共享**同一个** `wss`，靠 `connection` 事件里的路径判断分流（`index.ts:188-191`）。**绝不能**在该分支只 `return` 不 `handleUpgrade`。

## 9. 与现状差异

| 今天 | 变成 |
|---|---|
| `new WebSocketServer({ server })`（`:53`），一切 upgrade 接受 | `noServer` + 显式 upgrade 钩子，`/ws` 校验 `?v=`，`/ws/stt` **同样** `handleUpgrade` + `emit`（分流仍在 `connection` 里） |
| 无版本概念 | `PROTOCOL_VERSION = '1'`，不匹配关 4400 |
| 无心跳；死 socket 永久留在 `wss.clients`（**静默**） | 30s 服务端 ping；一次未回 → terminate |
| `useWorld.onclose` 无条件重连（`:986-995`） | `closeKind` 分类：`protocol` 不重连 + 可见 notice |
| `closeKind` 不存在 | `01` 提供唯一分类实现 |

### 9.1 执行序（**本批最危险的一处，必须按顺序**）

`airp-gateway.ts:156` 与 `index.ts:53` 的改动**必须在同一个提交里**，否则：

| 提交顺序 | 后果 |
|---|---|
| 先加服务端门禁，后改前端 | **每一个客户端**连上即 4400 → `closeKind` notice → **不重连**（若 §2.3 的 `protocol` 分支先落地）或无限 1.2s 重连风暴（若只改服务端） |
| 先改前端加 `?v=1`，后加服务端门禁 | **无害**：旧后端忽略额外 query，正常连接 |

**结论：先改前端（可独立验证），同提交/紧邻提交加服务端。** 手工验证见 `04 §11.3`。

## 10. 验收测试（可机械核验）

**新建**的 `apps/server/test/gateway-replay.test.mjs`（含心跳）：

1. **`shouldTerminate` 真值表**：`{isAlive:true} → false`、`{isAlive:false} → true`。
2. **一次 sweep 的语义**（假 timer + 假 clients）：新连接（`isAlive:true`）→ 置 `false` + `ping` 一次；下一轮仍 `false` → `terminate` 一次；期间收到 `pong` 的连接在下一轮**不**被 terminate。
3. **坏 client 不中断 sweep**：第 1 个 client 的 `ping` 抛错 → 第 2 个 client 仍被 `ping`。
4. **`stop()` 后 `tick()` 不再动作**（或定时器已清）。
5. **`intervalMs` 默认 30000**（可用 `AIRP_WS_HEARTBEAT_MS` 覆盖——见 §12.1）。
6. **前端拼出的 URL 含 `?v=1`**（源码扫描：`airp-gateway.ts` 的 `new WebSocket(` 调用里出现 `PROTOCOL_VERSION`，`04 §10.2`）。

- 测试 2：把 sweep 里「先判 `isAlive === false`」删掉（改成先置 `false` 再判）→ 真值表必须红（活连接会被误杀）。
