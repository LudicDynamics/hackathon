# docs/presence/05 — 初始位置初始化设计

> 状态：**只读审计后的设计（2026-09-14）**。本文只描述落点与验收，不改
> `docs/presence/00-共同上下文.md`、`docs/nook/00-共同上下文.md` 或源码。

## 1. 一句话定位

**世界第一次加载时，初始化代理只为 `canvas.db` 中尚无行的 manifest 角色按 `characters[].home` 解析并排座，再复用既有 `moveCharacter` 以 `engine` actor 落一条真实 `character_moved`；已有行、文件与第二状态源一律不碰。**

范围同时覆盖两条“加载世界”入口：服务启动加载默认世界（`apps/server/src/index.ts:103-130`）与玩家调用 `/api/worlds/load`（`apps/server/src/routes/world.ts:567-626`）。[推断] 这两条入口必须共用同一个 shared helper，否则默认世界和手动换世界会有两套初始位置语义。

本设计不把角色卡重新放回画布：`presence` 表的行才是“在场”真相（冻结契约 `docs/presence/00-共同上下文.md:75-89`），角色头像/视频属于 Nook 投影（`docs/nook/00-共同上下文.md:147-165`），不在本文新增文件。

## 2. 签名 / 契约

### 2.1 既有动作（必须复用，不改签名）

源码中的动作签名是：

```ts
// packages/shared/src/actions/move-to.ts:21-28,45-48
export interface MoveCharacterInput {
  character?: string;
  destination: string;
  near?: string;
}

export async function moveCharacter(
  ctx: ActionContext,
  input: MoveCharacterInput,
): Promise<ActionResult<MoveCharacterDetails>>;
```

它的坐标不是调用方提供的：动作在 `packages/shared/src/actions/move-to.ts:84-95` 调
`store.seatPresence()`，再以 `upsertPresence()` 写行；`MoveCharacterDetails` 的坐标和
`seat` 只从动作结果返回（`move-to.ts:30-43,131-148`）。因此初始化代理不能自己制造
`x/y`、不能向动作传 `x/y`，也不能把 `seatPresence` 的结果当成第二份位置状态。

### 2.2 NEW：初始化代理的最小签名（已裁决）

```ts
// packages/shared/src/actions/initial-presence.ts — NEW
export interface InitialPresenceResult {
  /** 本次真正创建的行；每项保留既有 MoveCharacterDetails。 */
  initialized: MoveCharacterDetails[];
  /** 加载前已有行或本批重复 id；只用于诊断，不是状态源。 */
  skipped: string[];
}

export function initializeMissingCharacterPresence(
  store: WorldStore,
  opts: { turn: string },
): Promise<InitialPresenceResult>;
```

helper 内部固定 `ctx.actor = { type: 'engine' }`，调用
`moveCharacter(ctx, { character: id, destination: resolvedHome.layer })`；它不接受外部
actor，不自行调用 `seatPresence`，也不直接写 `upsertPresence`。单角色动作失败即抛出，
加载入口必须关闭这个尚未激活的新 store；不返回一份“部分成功但客户端看不到失败”的假
成功结果。

初始化结果是服务端内部诊断，`/api/worlds/load` 继续返回 `{ ok, manifest, path }`；坐标的
公开来源仍只有 `/api/layer` 与 `/api/characters`，避免第三份响应快照成为状态源。


### 2.3 输入与输出的冻结语义

- 输入角色集合 = `store.getManifest().characters`；manifest 的 `characters` 形状由
  `CharacterConfigSchema` 定义（`packages/shared/src/schemas/world.ts:17-25`）。
- 初始化资格 = **加载开始时** `store.getPresence()` 没有该角色的行；冻结要求是已有行的
  `layer/x/y/following` 不得覆盖（`docs/presence/00-共同上下文.md:171-189`）。
- 目标层 = `resolveHome(store, characterId)` 的 `.layer`；不得直接信任 raw `home`。
  `resolveHome` 对合法真实层返回 `{ layer: home, fromHome: true }`，坏/缺失 home 回退
  `map` 且 `fromHome: false`（`packages/shared/src/actions/presence.ts:192-216`）。
- 坐标 = `moveCharacter` 内部调用 `store.seatPresence()` 的结果；`seatPresence` 返回的
  `x/y` 是头像中心点（`packages/shared/src/store/local-store.ts:1590-1618`）。
- 行与事件 = `upsertPresence` 写一行，`moveCharacter` 随后追加一个
  `character_moved`（`move-to.ts:84-129`）。首行没有 `from`，不能伪造 `map` 作为旧层。
- 单角色动作失败即令加载失败；新 store 在激活前关闭，客户端不会收到“部分成功”的假快照。

## 3. 逐步行为（每一步写漏了会怎样）

### 步骤 0：在新 store 激活前取得并校验 manifest

加载代码已先解析 `world.json`（`/worlds/load`：`world.ts:573-576`），随后构造
`LocalWorldStore`（`world.ts:605`；默认启动同类构造在 `index.ts:120`）。初始化应在
新 store 对外可见、EventBridge 开始 tail 之前运行，并再次使用 `getManifest()` 取得带
目录派生 layers 的完整 manifest（`local-store.ts:348-358`）。

**漏了会怎样：** 若把初始化放到 `setActiveStore(store)` 之后，其他请求或 Agent 可能读到
“部分角色已有行、部分还没有”的半成品；若跳过 manifest 校验，坏 `world.json` 可能被
`resolveHome` 的 catch 隐式降到 `map`，把结构性坏世界伪装成可用世界。

### 步骤 1：一次性快照已有 presence 行

在任何写入前执行 `const existing = new Set(store.getPresence().map(p => p.characterId))`。
`getPresence()` 已按 `character_id` 稳定排序并可读全表（`local-store.ts:1679-1687`），不是
另建表或缓存坐标。

**[推断]** 每个角色各查一次会让“加载开始时没有行”的边界不明确；更严重的是，并发/重复 manifest 条目可能把刚由本批创建的行当成旧行，导致重复移动、覆盖位置或产生重复事件。快照只决定资格，不复制 `layer/x/y/following`。

### 步骤 2：按 manifest 顺序筛出候选并去重

候选是 manifest 中 id 不在 `existing` 的角色；同一批内相同 id 只处理一次，建议保留第一
次出现。manifest schema 目前只约束 `id: string`，没有唯一性约束（`schemas/world.ts:17-25`），
因此 helper 不能把重复 id 当成正常两个角色。

**漏了会怎样：** 重复 id 且 home 不同会让第二次调用看到第一行后又把它搬去另一个 home，
违反“已有行不得覆盖”；空 id 或路径形 id 会在动作层失败，若不收集会被误报为全部初始化成功。

### 步骤 3：每个候选调用 `resolveHome`

对每个 id 调用 `resolveHome(store, id)`，只把返回的 `layer` 交给下一步；不把
`characters[].home` 直接塞给 `moveCharacter`。合法 home 必须命中 `manifest.layers`；stub
目录也算真实层，因为 `scanLayers` 会把无 README 目录保留为派生 layer
（`local-store.ts:361-372`，`store/layers.ts:56-63`）。

**漏了会怎样：** 直接使用坏 home 会令 `moveCharacter` 抛 `not_found`，或把层路径与 map
映射写错；把 `home` 当当前在场位置也会让后续 `/api/characters` 产生错误事实。坏 home
按既有语义回退 `map`，`fromHome:false` 是诊断事实，不是额外 presence 字段。

### 步骤 4：以 engine actor 调用既有 `moveCharacter`

顺序为：

```text
resolveHome(id).layer
  → moveCharacter({ actor: {type:'engine'}, turn, store },
                  { character: id, destination: layer })
  → moveCharacter 内部 seatPresence(layer)
  → upsertPresence({ characterId, layer, x, y })
  → appendEvent(character_moved, actor=engine)
```

`moveCharacter` 会先确认角色目录存在（`resolveTargetCharacter`：`presence.ts:53-81`），
再解析目标层（`presence.ts:133-165`），然后排座、写行、落事件（`move-to.ts:51-123`）。
不传 `near`，保证初始化不虚构“站在某物旁”；不传 `following`，新行按
`upsertPresence` 的默认值 `false` 建立，已有行则保持原 flag（`local-store.ts:1644-1676`）。

**漏了会怎样：** 直接调用 `store.upsertPresence` 会绕过动作层的角色/层校验、`seatPresence`
与 `character_moved` 落账，形成第二条写通路；手工调用 `seatPresence` 后再调用
`moveCharacter` 会排两次座，第二次坐标才是真相而第一次结果变成无名副作用；把 actor
设为 player 会把自动初始化伪装成玩家动作。

### 步骤 5：按单角色收集成功与失败

成功项只接受 `details.moved === true` 且存在 `details.event` 的动作结果；失败记录
`{ character, reason }` 后继续处理其余候选，或按第 12 节待拍板的 fail-fast 策略中止。
即使 `seatPresence` 返回 `exhausted:true` 仍是已落行的成功：它的明确语义是“在最后候选
落座”，不是抛错（`local-store.ts:1621-1641`）。

**漏了会怎样：** 一个坏角色会吞掉整个循环，其他角色没有初始化且 load 响应仍可能 200；
反过来若 `console.warn` 后假装成功，`/api/characters` 的 null 会被 UI 解释成角色不在世界，
违反冻结的失败可见要求（`docs/presence/00-共同上下文.md:135-138,432-440`）。

### 步骤 6：把新 store 安全交给活跃世界与读取通道

初始化完成后才 `setActiveStore(store)`，再 `clientManifest(store)`、
`eventBridge.startTailReader(store)`、`eventBridge.watchWorld(resolvedPath)`；现有 load
顺序在 `world.ts:605-613`，默认启动的对应顺序在 `index.ts:120-124`。若采用全 load
失败策略，必须在 catch 中关闭这个尚未激活或已解绑的 store，避免把关闭的数据库留在
`activeStore`。

**漏了会怎样：** 先启动 tail reader 再初始化会让初始事件在客户端收到时序不稳定；先
激活再失败会留下“activeStore 指向已关闭数据库”的坏状态。尤其当前 `/worlds/load` 在
`setActiveStore(store)` 之后才执行 `clientManifest`（`world.ts:605-608`），初始化错误若
直接插在这里，必须同步设计清理。

### 步骤 7：返回现有 load 形状，前端随后重取

继续返回 `{ ok:true, manifest, path }`（`world.ts:620`），让前端既有流程先
`airpGateway.loadWorld`，再 `enterLayer(entryLayer)`，再 `loadChromeData()`（`App.tsx:716-730`）。
`/api/characters` 读取全表 map（`world.ts:1014-1067`），`/api/layer` 读取当前层含
`x/y/following` 的 rows（`world.ts:979-989`）。

**漏了会怎样：** 若 load 响应自己再返回一份 presence，而 `/api/characters` 又返回另一份，
UI 会有两个快照来源；若初始化后不重取，角色虽已在数据库中，首屏仍显示 null/缺席。

## 4. 文件副作用

| 对象 | 预期副作用 | 明确不做 |
|---|---|---|
| `.airpworld/canvas.db` | 对每个缺行角色插入一行 `presence`，坐标由 `seatPresence` 产生；`following` 新行是 `false` | 不改已有 row 的 `layer/x/y/following`；不新建另一张状态表 |
| `.airpworld/history.db` | 每个成功的新行追加一条 `character_moved` | 不新增事件 type，不写 `layer_initializing` 或 `presence_initialized` |
| `world.json` | 只读 `characters[].home` 与 manifest；`getManifest` 派生 layers | 不回写 home，不把当前层写回 manifest |
| `characters/<id>/` | `moveCharacter` 只读 README/目录存在性；初始化不搬目录、不删卡、不生成角色卡 | 不恢复 `world/**` 下 `type: character` 文件；模板迁移由并行模板设计负责 |
| `world/**` / 其他正文 | 只读 layer 目录、卡片占用域 | 不因初始 presence 生成 README、Nook 文件或卡片 |

`LocalWorldStore` 构造函数当前只创建 `.airpworld`、初始化 canvas/history schema，并异步
处理 character-creation journal（`local-store.ts:117-128`）；这证明初始化不应隐含在构造函数
里。[推断] 构造函数若承担世界级业务写入，会让所有临时 store/测试 store 都自动落事件，
边界比 load 入口更差。

`seatPresence` 的占用域是当前层 cards 与其他 presence 的并集（`local-store.ts:1598-1619`），
因此初始化角色会避开已有卡与先前已落的角色；初始化循环必须顺序等待每个动作，才能让
下一角色读到前一角色的占用。

## 5. 事件落账

1. **一角色一条事件。** `moveCharacter` 只有真实写入后才调用 `appendEvent`，事件 type 为
   `character_moved`，detail 为 `{ character, name, to }`，首见角色没有 `from`；实现依据
   `move-to.ts:103-123`，事件 detail schema 依据 `schemas/events.ts:59-65`。
2. **actor 固定 engine。** 这是世界加载事实，不是玩家/作家/角色的叙事动作；`actor` 由 helper 内部固定，不能复用请求传入 actor（动作 actor 直接写入事件的实现见 `local-store.ts:683-713`）。
3. **turn 同一批共享。** **[推断]** 一个 load 生成一个 `turn`，每条初始化事件携带同一 turn；这是事件归组，不是第二状态源。具体 turn 前缀仍待拍板（第 12 节）。
4. **提交顺序是 presence 后 event。** 现有动作先 `upsertPresence`，再 `appendEvent`
   （`move-to.ts:84-129`）。`appendEvent` 只在 history DB 提交后返回（`local-store.ts:661-714`），
   EventBridge 可读到完整 seq。
5. **不做手工补事件。** 若 helper 另行 `appendEvent`，会绕过 action 层并可能与动作重复；
   初始事件必须来自 `moveCharacter` 唯一通路。
6. **失败边界必须正视。** 当前动作在 presence 写成功、event 写失败时抛
   `event_failed`，错误信息明确“moved but event could not be recorded”（`move-to.ts:109-128`），
   但不会自动回滚 canvas row。该非原子性是本设计的已知阻断项，见第 11/12 节；不能靠
   “下次 load 会重试”掩盖，因为下次快照会认为该角色已有 presence 行。
事件历史的坐标不是 detail 的一部分；detail 只说明角色从哪（若有）到哪，而事件 detail schema
   没有 `x/y`（`schemas/events.ts:59-65`），坐标仍从 `presence` / `/api/layer` 读取。这遵守
事件自洽字段表，也避免历史事件成为第二坐标源。

## 6. WS / 前端感知

### 6.1 初始加载不依赖新增 WS 帧

EventBridge 的唯一世界事件通道是 `{ type: 'world_event', event }`，tail reader 从
`history.db` 读已提交事件并广播（`apps/server/src/engine/event-bridge.ts:481-510`）。它在
`startTailReader` 时先把 cursor 对齐到 `getMaxSeq()`，不重放旧历史
（`event-bridge.ts:523-563`；对应测试 `apps/server/test/event-bridge.test.mjs:68-103`）。

因此建议初始化发生在 `startTailReader` **之前**：初始 `character_moved` 仍永久落在
history，但不会被误发给尚未完成换世界的旧客户端；初始化完成后 tail 对齐到这些事件的
max seq，再开始 watch。初始角色的可见性靠 load 后的 `/api/characters` 与 `/api/layer` 重取，
不是靠新增帧名。[推断] 这比“先 watch、再初始化、让客户端碰运气收事件”安全，因为 WS 帧中
没有一个明确的 world-load generation，且旧客户端可能仍在上一世界的 layer。

### 6.2 既有前端路径

- `/api/characters` 每个 manifest 角色始终有 `presence` 键；有行是
  `{ layer, following }`，无行是 `null`（`apps/server/src/routes/world.ts:1052-1067`）。
- `/api/layer` 的 presence 返回 `characterId/x/y/following`，并按 character id 稳定排序
  （`world.ts:979-989`；冻结形状见 `docs/presence/00-共同上下文.md:172-210`）。
- App 换世界后已经调用 `loadChromeData()`，该函数并行读取 manifest/backpack/characters/shelf
  （`apps/web/src/App.tsx:402-416`）。`useWorld.enterLayer` 负责首层 `/api/layer` 重取
  （`apps/web/src/state/useWorld.ts:244-286`）。
- 当前 `world_event` 分支会对层数据重取（`useWorld.ts:517-541`）；但初始事件按 6.1
  history-only 处理，所以不应把“是否收到初始 WS”作为角色初始可见性的前置条件。
- 初始坐标仍由服务端权威返回；前端不可自行根据 `home` 计算坐标、不可把坐标灌给 Agent。

### 6.3 后续运行时事件不受影响

完成初始化并启动 tail 后，普通 `moveCharacter` / `setFollowing` / `enterLayer` 的事件仍
走既有 EventBridge；本设计不新增 `presence_initialized` 帧，不开第二条 WebSocket，也不
增加第二个 `airp:world-event` 消费路径（全局约束见 `docs/presence/00-共同上下文.md:432-440`）。

## 7. 错误边界

| 情况 | 现有事实 | 设计处理 |
|---|---|---|
| 无 active world | middleware 对大多数世界 API 返回 409 `no_active_world`（`world.ts:473-490`）；具体读路由缺世界时多为 400（如 `/characters`：`world.ts:1009-1013`） | 初始化只接受新构造的 store；不在无 active world 分支偷偷创建 presence |
| home 缺失 / 空串 | `resolveHome` 返回 `map, fromHome:false`（`presence.ts:198-216`） | 仍按冻结语义初始化到 map；必须在结果/日志中可诊断“非真实 home”，不可直接把坏字符串当 layer |
| home 不在派生 layers | `resolveHome` 警告并回退 map（`presence.ts:203-212`） | 不把它当 load 致命错误；是否将 fallback 原因进 load summary 待拍板。不能新增 presence 字段 |
| home 指向 stub 目录 | `scanLayers` 将真实目录纳入 layers，即使 README 缺失（`local-store.ts:361-372`） | 允许初始化；stub 不是 presence 的边界，也不触发 scene/nook 初始化 |
| manifest JSON / schema 坏 | `/worlds/load` 在建 store 前只做 JSON parse（`world.ts:573-576`），之后 `clientManifest` 的 `getManifest` 会 validate（`local-store.ts:353-358`） | 初始化应在 `getManifest` 成功后运行；schema 失败不得被 `resolveHome` 的 fallback 吞掉，load 必须失败并清理新 store |
| manifest 角色目录不存在/为空 | `resolveTargetCharacter` 通过 `listFiles(characters/<id>)` 判不存在，抛 `not_found`（`presence.ts:68-70`）；`listFiles` 对空目录返回空数组（`local-store.ts:231-253`） | 记录该角色失败；是否阻断整个 load 待拍板。不能伪造一行或用角色卡文件补偿 |
| id 含 `/`、`.` 或非法显示 id | 动作层显式拒绝路径形 character（`presence.ts:59-70`）；manifest schema 本身未做 kebab-case 校验（`schemas/world.ts:17-25`） | 不绕过动作校验；失败必须进入 `failures` 或明确 load 错误 |
| 排座耗尽 | `seatPresence` 返回最后候选并 `exhausted:true`，不抛异常（`local-store.ts:1638-1641`） | 视为成功落账；可保留 `details.seat.exhausted` 供诊断，不能因 warning 丢角色 |
| 事件追加失败 | presence 可能已写入，动作抛 `event_failed`（`move-to.ts:109-128`） | 不能静默继续后返回“全部成功”；需要第 12 节的原子修复/失败策略决策 |
| 重复 load 同一 save | `/worlds/load` 受 `shelfBusy` 串行化（`world.ts:569-571`），新 store 读同一 `.airpworld/canvas.db` | 已有行跳过；不得重新 seat、改变坐标或重复事件 |
| 同一 store 的并发 helper | 当前 `seatPresence` 没有自己的 `withSeatLock`；锁只包 `seatUnplaced` / `reseatLayer`（`local-store.ts:399-414,889-955`） | 正常 load 通过“激活前运行 + `shelfBusy` + 顺序循环”避免；helper 仍建议用 per-store ephemeral promise guard，不能新增持久状态表 |

`console.warn` 只能作为开发诊断，不能替代失败结果或 UI 可见错误；这与冻结共同上下文
对失败反馈的要求一致。

### 9.1 是否可以安全复用 `moveCharacter`

**结论：[推断] 正常成功路径可以安全复用，前提是初始化只做“快照筛选 + `resolveHome`”，不
提前调用 `seatPresence`，并在 store 激活前顺序执行。** 依据是动作已经具备所需全部副作用：
角色/目的地校验、排座、保持 following、写 presence、落 `character_moved`
（`move-to.ts:51-148`）。

**不能安全复用的情形：**

- literal 地先 `store.seatPresence()` 再调用 `moveCharacter`：动作没有 `x/y` 参数，会
  再排一次，产生未使用的坐标与额外查询；
- 用 `createActionService(store, actor)` 让调用方 actor 可配置而不强制 engine；
- 在已有 row 上调用以“修复”坐标；动作会合法地移动它，违反初始化只补缺行；
- event append 失败后把已有行当作“下次仍可重试”——当前动作不具备跨 canvas/history
  的原子提交。

## 10. 验收测试（含修复前非空失败断言）

> 用户要求跳过本阶段测试执行；以下是实现阶段的测试设计，不是本次运行记录。
> 每个关键用例都必须能证明“没有初始化接线就会失败”，不能接受空数组/空结果的假绿。

### 10.1 首次 load 的闭环非空性（必须）

fixture：临时 repo 中的 `world.json` 至少有 `watson.home = world/a`、`edith.home =
world/b`；两个角色目录各有 README；`world/a`、`world/b` 有 README（另加一个 stub home
用例）。

步骤：POST `/api/worlds/load`，等待响应后 GET `/api/characters`，再 GET
`/api/layer?layer=world/a` 与 `world/b`。

断言：

- load 仍 200，响应保留 `{ ok:true, manifest, path }`；
- `characters` 中 watson/edith 的 `presence` 都是对象，不是 null；
- 各 home 层的 `/layer` `presence` 各含对应 `characterId`，且 `typeof x/y === 'number'`、
  `following === false`；
- `store.getPresence()` 行数等于 manifest 中**唯一且目录有效**的候选数；
- history 中每个新角色恰有一条 `character_moved`，`actor.type === 'engine'`，
  `detail.from` 缺失，`detail.to === resolvedHome.layer`。

**修复前非空失败断言（必须逐字保留在测试注释/测试名附近）：**

```js
// 没有 world-load initializer 时，这条先红：角色不是 null，且 /layer 有非空行。
assert.ok(chars.characters.every((c) => c.presence !== null),
  'world load must initialize every manifest character presence');
assert.ok(layer.presence.some((p) => p.characterId === 'watson'),
  'home layer must expose a non-empty initial presence row');
```

修复前现状可由源码对应：load route 只在 `world.ts:605-620` 建 store/回 manifest，
没有任何 `moveCharacter` 调用；现有测试则必须先手工 `seed()`（`presence-follow.test.mjs:89-93`）。
因此这两条不是“只要断言结构就会过”的空断言。

### 10.2 已有行绝不覆盖

先在 store 中写入 watson 的固定 row（例如 layer=`world/old`、x=123、y=456、following=true），
再执行 load initializer；另一个 edith 不写 row。断言 watson 的 `layer/x/y/following` 完全
不变且不新增 watson `character_moved`，edith 有一行并有一条 engine 事件。

这直接守住冻结契约“已有 presence 行不得覆盖”；不能只断言总行数，因为坐标被覆盖时行数仍相同。

### 10.3 重复 load / 同世界重启幂等

对同一保存目录连续两次 `/worlds/load`（每次真实关闭旧 store 后重新构造）并分别读取
`/api/characters`、`getPresence()`、history：

- 第二次不会改任何已有 row 的 `layer/x/y/following`；
- 第二次不会让 `character_moved` 数量增加；
- load 两次都不产生重复角色；
- EventBridge 第二次 align 到该 history 的 max seq，不向客户端 replay 初始历史。

测试必须使用角色目录确实存在的 fixture；不可用“第一次不落行所以第二次也不落行”的假绿。

### 10.4 顺序与碰撞

manifest 放至少两个都 home 到同层的角色。断言两行的 `(x,y)` 不相同，且第二个角色排座
看到第一个 presence 的占用；所有动作按 manifest 顺序完成，事件 seq 递增且 turn 相同。
这守的是 `seatPresence` 的 cards + pres 占用实现（`local-store.ts:1598-1620`），不允许
helper 用固定锚点直接 upsert。

### 10.5 坏 home / stub / 目录错误

- `home: 'world/missing'`：`resolveHome` 回 `{ layer:'map', fromHome:false }`；断言 row
  落 map，事件 `detail.to === 'map'`，不要断言只打 warning 就算成功。
- home 指向存在但无 README 的 stub：断言初始化成功并落 stub layer，不触发 scene init。
- manifest 有角色但 `characters/<id>/` 缺失：断言实现选定的失败策略（见第 12 节），至少
  不能出现伪 presence 或无对应事件。

### 10.6 并发守卫

直接对同一 store `Promise.all([initializeMissingCharacterPresence(...), initializeMissingCharacterPresence(...)])`
或用两个并发 load 请求（后者还应被 `shelfBusy` 拦截）验证：每个 id 至多一行、至多一条
初始事件、坐标不被第二次调用改写。若只依赖 route 的 `shelfBusy`，必须另测 helper 在同
store 被误调用时的行为，避免把调用约束误当动作原子性。

### 10.7 事件桥与 API 感知

将 bridge 绑定 recording sink，在初始化前启动会违反设计顺序，因此验收应验证：

1. 初始化事件已经在 `history.db` 且 load 后 `/api/characters`/`/api/layer` 可见；
2. `startTailReader` 对初始化前已有事件不 replay（沿用 `event-bridge.test.mjs:68-103`）；
3. 初始化完成后追加一条普通事件，bridge 才广播一个 `world_event`，且事件 shape 通过
   `WorldEventSchema`；
4. 不新增 WS frame type，不创建第二 websocket。

### 10.8 失败可见与非原子性回归

注入一个会让 `appendEvent` 失败的 fake store 或受控 history DB：断言 helper 返回/抛出
明确 failure，不能报告 initialized 成功；同时记录当前实现的 row/event 不一致，直到第
12 节决定原子修法后，将断言收紧为“失败时无残留 row”或“残留 row 有可恢复标记”。

## 11. 发现的冲突

### C-1：`moveCharacter` 的写行与事件不是跨 DB 原子操作

`move-to.ts:84-95` 先写 canvas row，`move-to.ts:109-129` 后写 history event；
`local-store.ts:661-722` 的 event transaction 只覆盖 history DB。事件失败会留下 presence，
而初始化资格按“有行”跳过，造成永远缺 `character_moved` 的半事实。

**影响：** “重复 load 幂等”与“失败后可修复”目前不能同时由现有动作保证。

**不擅自修法：** 本文不增加 `presence_initialized` 事件、不加第二张 repair 表、不手工补
`appendEvent`；需要主代理决定是动作层提供跨库恢复/幂等事件键，还是加载失败时删除本批
残留 row（删除也必须有明确 ownership 与测试）。

### C-2：`worlds/load` 当前先激活新 store，再做 manifest 与 tail 初始化

现状是 `setActiveStore(store)` 在 `world.ts:605-606`，`clientManifest` 在 `:608`，tail/watch
在 `:612-613`。若初始化插在 `:607` 之后而失败，catch `:621-625` 目前只返回 500、没有把
activeStore 恢复/关闭的明确动作。

**影响：** 可见到未完成的初始 presence，或 activeStore 指向已经关闭/半初始化的数据库。

**设计要求：** 初始化必须前移到 `setActiveStore` 之前，或补足完整 two-phase activation
与失败清理；不能只加一行 await。

### C-3：坏 home 的“回退 map”是既有语义，但 load API 没有 fallback 诊断字段

`resolveHome` 明确返回 `fromHome:false` 并只 `console.warn`（`presence.ts:203-216`）；
`/api/characters` 只公开 `{layer,following}`（`world.ts:1052-1062`），冻结又禁止新增
presence 字段。若产品要求玩家知道角色因坏 home 被送到 map，当前 API 形状没有承载位置来源。

**不擅自扩张：** 本文按冻结语义先落 map；是否在 `/worlds/load` 的内部初始化 summary、
server log 或管理诊断中暴露 `fromHome:false`，列为待拍板，不把它塞进角色 presence。

### C-4：manifest 允许重复 / 非 kebab id，角色动作校验较晚

`CharacterConfigSchema` 只要求 `id: string`（`schemas/world.ts:17-25`），而动作的目录存在性
与 path 形校验在 `resolveTargetCharacter`（`presence.ts:53-81`）。因此 schema 成功并不意味
初始化候选可执行；重复 id 还会让“首次快照”语义不清。

**不擅自扩张：** helper 先做加载快照与批内去重，非法条目进入失败；是否把 manifest 校验
升级为唯一/kebab-case 约束由上位 manifest 设计拍板。

## 12. 已裁决事项

1. **单角色失败 = 整个加载失败。** 这是唯一不会把失败角色静默显示成“不在场”的形态。
   `/api/worlds/load` 在新 store 激活前执行初始化；任一动作失败就关闭新 store，保留既有
   active store 的一致性（手动切换时旧 store 已按既有流程解除）。
2. **事件失败的跨库非原子性暂不扩张。** 既有 `moveCharacter` 的 presence → history 顺序
   保持不变；本批不新增 repair 表、事件类型或绕过动作层的补事件。有效模板的正常路径不受
   影响，未来若要修复需另立 store/action 契约。
3. **并发调用使用进程内 WeakMap promise guard。** 路由的 `shelfBusy` 继续保护加载请求；
   helper 自身也保证同一 `WorldStore` 同时只有一次初始化，不新增持久锁。
4. **重复 manifest id 采用 first-wins。** 读取 presence 资格和本批已处理 id 的快照；
   首次条目完成后后续重复 id 只列入 `skipped`，绝不把角色搬到第二个 home。
5. **角色目录缺失沿用动作层失败。** manifest 是角色注册集合，但 `moveCharacter` 仍要求
   `characters/<id>/` 可读；结构性错误令加载失败，不用 world 卡或 README 临时补偿。
6. **初始事件只保留在 history。** 初始化在 `eventBridge.startTailReader` 前完成，旧客户端
   不接收这批初始事件；首屏位置只从 `/api/characters` 与 `/api/layer` 读取。
7. **加载响应形状不变。** 不把初始化坐标或 failures 塞入 `{ ok, manifest, path }`，避免
   第三份位置快照；失败以现有 HTTP 错误路径返回，服务端保留具体异常用于诊断。
8. **两个加载入口共享 helper，turn 是 opaque 本批标识。** 默认启动和手动加载都传入
   `init:${randomUUID()}` 形式的 turn，不用层名、角色名或持久计数器伪造排序语义。
9. **角色卡正文迁移判定已完成。** 当前 39 个 canonical `type: character` 文件的正文与
   对应 `characters/<id>/README.md` 正文逐一相同（实测 mismatch = 0），因此删除 world
   卡不会丢失独有内容；archive 历史文件保留，不作为 canonical 模板或新角色存在依据。
10. **模板迁移范围固定。** 当前 `templates/` 下 `type: character` / `type: spirit` 命中
    为 39 个，按 21 个 edition 的 canonical 模板删除；`portrait` kind 继续只作普通陈设，
    不代表 manifest character，也不生成 `portrait.md`。
