## 1. 一句话定位

**右侧角色栏是「谁在哪儿」的唯一常驻答案**：它把 `usePresence()` 的 `CharacterPresenceView[]`
逐项投影成头像 + 状态 + hover 功能键，用两档视觉（`in-scene` 全彩 / 其余灰）如实地表达三种
状态（同场景 / 在别处 / 不在场），并把玩家能对一个人做的四件事（直聊 / 去 ta 那里 / 跟随·解散 /
去 ta 的小天地）收敛到一处；它自己不推导任何状态，也不碰相机。

**形态冻结（契约 §4.2.1）**：右侧是**上下布局** —— 角色栏在上、背包在下。载体是既有的
`.prototype-residents` 容器（`apps/web/src/App.tsx:828-840`，样式
`apps/web/src/scene-shell.css:110-112`，`top:155px; right:26px`），从「右上头像列」扩展为
**世界全部角色**的竖排栏。**不引入左右双 tab 侧边栏**；`docs/doc-05 §4.1.1` /
`docs/doc-06 §5.0` 画的「背包 ▸ 角色」双 tab 布局已作废（契约 §7 P-5，回写义务见本文 §11 C-0）。

## 2. 签名与参数

### 2.1 组件（NEW）

```tsx
// NEW  apps/web/src/components/sidebar/CharacterRail.tsx
import type { CharacterPresenceView } from '../../lib/presence.js';   // owner: 04

export interface CharacterRailProps {
  /** 契约 §4.1 的唯一投影结果；由 `04` 的 usePresence 返回（owner 04），本组件不得自行推导。 */
  views: CharacterPresenceView[];
  /** true = 该角色有一条跟随开关请求在飞行中（UF-1）。不是跟随真值。 */
  pendingFollowing: ReadonlySet<string>;
  /** nook 已打开 → 禁用「去 ta 的小天地」（§6.4）。 */
  nookOpen: boolean;
  /** 点头像：仅在 view.state === 'in-scene' 时由本组件调用（UF-2）。 */
  onOpenCharacter(id: string): void;
  /** hover 键「去 ta 那里」；相机/跨层时序全在 04 的单一入口里（UF-3）。 */
  onTravelTo(id: string): void;
  /** hover 键「跟随 | 解散」，已算好的终态（契约 §2.4）。 */
  onToggleFollowing(id: string, next: boolean): void;
  /** hover 键「去 ta 的小天地」；与在场状态无关（UF-4）。 */
  onOpenNook(id: string): void;
}

export function CharacterRail(props: CharacterRailProps): React.ReactElement;
```

**展开器状态是组件内部 UI state，不是 prop**：`const [expanded, setExpanded] = useState<ReadonlySet<string>>(new Set())`；
每项的展开器 `aria-controls` 指向组件内生成的 `character-actions-${id}`（§3.6）。它只影响三个功能键的
显隐，**不是跟随真值**，也不上抛给 App。

**只传 id 上抛，不传 `CharacterView`**：`CharacterPresenceView` 已含渲染所需的 `id/name/avatar`，
而 `CharacterView` 是 `App.tsx` 的**模块私有类型（未导出）**；rail 需要完整对象时也无从 import。
App 侧在回调里 `characters.find(c => c.id === id)` 取完整对象再交给 `openCharacter`
（`App.tsx:588-605`）——`App.tsx:712-715` 的既有 `onOpenCharacterModal` 就是这个模式。

组件内部用 `useLocale()` 的 `t()` 取文案（§5）；**不接收 locale prop** —— `UI_COPY` 的
`Locale` 类型不含 `zh-CN`（`apps/web/src/lib/legacy-ui-copy.ts:1`、`legacy-ui-copy.ts:108`），
本文新 UI 一律走 `messages.json`（§5.1）。

### 2.2 纯判定模块（NEW，可测）

// NEW  apps/web/src/lib/character-rail.mjs   （+ 同目录 character-rail.d.mts 声明）
/**
 * 契约 §2.2 判定表的唯一派生（不含 i18n、不含 DOM）。
 * 返回「该渲染什么、能不能做什么」；文案 key 由 .tsx 用 t() 取

export function railEntry(view) {
  // view: CharacterPresenceView
  return {
    canTalk: view.state === 'in-scene',
    canTravel: view.state !== 'absent',
    statusKey: view.state === 'in-scene' ? 'In this scene'
             : view.state === 'elsewhere' ? 'Elsewhere' : 'Not here',
    followActionKey: view.following ? 'Dismiss' : 'Follow',
    /** 非 null = 点头像时应显示这条提示而不是直聊 */
    talkHintKey: view.state === 'in-scene' ? null
               : view.state === 'absent' ? 'They are not here right now.'
               : 'They are in another scene. Go to them instead.',
    /** 非 null = 「去 ta 那里」只提示、不导航 */

    tone: view.state === 'in-scene' ? 'full' : 'muted',
    followedByPlayer: view.following,
  };
}
```

## 3. 行为契约（逐步；每步写「漏了会怎样」）

### 3.1 列表与状态（UF-0）

| # | 步骤 | 漏了会怎样 |
|---|---|---|
| 1 | 取 `views: CharacterPresenceView[]`（App 传入） | 组件自行读 `state.presence` 或 `characters` → 与画布出现**第二份投影**，违反契约 §4.1 与 `docs/ux/00 §4.6`（公开状态单一投影） |
| 2 | 按 `views` 的**数组序**逐项渲染，不按状态重排 | 状态一翻转列表就整体位移，玩家正要点的那个人会跑掉；且违反契约 §4.2「用阻尼替代硬切」的精神 |
| 3 | 每项推导 `railEntry(view)`（§2.2） | 判定散落在 JSX 里，画布与角色栏可能各判一次（契约 §2.2 末句明令禁止） |
| 4 | `tone==='full'` → 全彩头像；`muted` → 灰度 + 降对比（`in-scene` 之外的两种状态同档） | 三种状态在视觉上不可分；玩家会以为「在别处」的人就在本层 |
| 5 | `view.following === true` → 头像右下角状态图标，且状态标签追加 `Following you` | 跟随中的角色与普通在场角色无法区分；`docs/doc-06 §5.4:338` 的承诺落空 |

**状态呈现逐字对齐契约 §2.2**（本文不新增状态、不加第四档）：

| 契约 §2.2 条件 | `state` | 头像 | 状态标签 key | 点头像 | `canTravel` |
|---|---|---|---|---|---|
| `P(c) === null` | `absent` | 灰 | `Not here` | 不直聊（`They are not here right now.`） | **false**（只提示，不导航） |
| `P(c).layer !== L` | `elsewhere` | 灰 | `Elsewhere` | 不直聊（`They are in another scene. Go to them instead.`） | **true** |
| `P(c).layer === L` | `in-scene` | 全彩 | `In this scene` | **直聊** | **true** |
| 任意状态下 `following === true` | 附加 | 右下角状态图标 | 追加 `Following you` | 与上同 | 与上同 |

**位置文案**：行内只允许显示 `view.layer`（在场层）。契约 §3.2 与 `docs/tools/05 §6.5` 明文
`home` **不是**「ta 在哪」；现状 `RightSidebar.tsx:134` 的 `{copy.at}: {char.home || copy.unknown}`
是错的（随该文件删除，§3.5）。`in-scene` 时本项**不显示层名**（玩家就在这一层，层名是噪音）。

### 3.2 点头像 = 开启直聊（UF-2；契约 §7 P-1 的新口径）

| # | 步骤 | 漏了会怎样 |
|---|---|---|
| 1 | `canTalk === true` 时，点头像调 `onOpenCharacter(view.id)` | 直聊入口消失；玩家只能去画布上找人，而侧栏存在的理由之一就是「不用在画布上找」 |
| 2 | App 侧实现为 `characters.find(c => c.id === id)` → `openCharacter(character)` —— 传**完整 `CharacterView`**，不是 id | `CharacterModal` 缺 `avatar` / `emotions` / `voice`（`App.tsx:927-940`），立绘、情绪差分、语音全部降级 |
| 3 | `canTalk === false` 时**不**调 `onOpenCharacter`，改为 `notify(t(railEntry(view).talkHintKey))` | 点开一个不在本层的角色，`App.tsx:600-604` 会发 `character_start` → spawn 一个不该活的进程，且违反契约 §2.2「不直聊」 |
| 4 | 键盘同语义：头像按钮的 `click` 即触发，Enter/Space 走浏览器原生行为 | 键盘用户无法直聊（§3.6） |

**这是对 `docs/doc-06 §5.4` / `docs/doc-05 §4.1.1` 的修订（契约 §7 P-1）**：原口径
「点头像/名字 = 导航」（`docs/doc-06-演出与交互设计.md:336`、`docs/doc-05-AIRP产品构想.md:51`）
作废，导航改由 hover 键「去 ta 那里」承担。回写要求见 §11 C-0。

### 3.3 跟随开关（UF-1；契约 §2.4）

rail 组件只调 `onToggleFollowing(view.id, next)`；App 侧实现：

| # | 步骤 | 漏了会怎样 |
|---|---|---|
| 1 | 点 `Follow`/`Dismiss` 时算 `next = !view.following`（`view` 来自投影，**不是**组件本地 state） | 本地存一份跟随真值 → 与作家调用的 `set_following` 分叉（契约 §2.4、`docs/tools/05 §6.4`） |
| 2 | 立刻把 `id` 放进 `pendingFollowing`（只禁用该按钮 + pending 样式），**不改文案** | 文案先行翻转再回滚，玩家读到「假装成功」（`docs/ux/00 §4.4` 事实先于演出） |
| 3 | `await airpGateway.setFollowing(id, next)`（§2.3） | 按钮点了没反应；若绕过网关则 `check:bodies` 扫不到（`tools/check-request-bodies.mjs:44-52`） |
| 4 | 成功 → **不本地写入任何跟随状态**；等 `following_changed` 的 `world_event` 到达 → App `loadChromeData()` 重取 `/api/characters` → 新 `views` 自然翻转 | 本地乐观写入 = 两份真相；且幂等 no-op（`changed:false`，`packages/shared/src/actions/following.ts:130-134`）时本地会与服务端不一致 |
| 5 | 失败 → `notify(t('Could not change whether {name} follows you.', { name: view.name }))`，清 pending | 失败静默；`console.warn` 不算「失败可见」（契约 §6 全局 MUST NOT #6、`docs/tools/00 §6.2`） |
| 6 | pending 期间再次点击直接忽略 | 连点产生两条请求；第二次读到旧 `view.following`，会算出与第一次相同的终态（语义无害），但会让按钮在正确回执到达后被错误地重新 pending |

- **`changed: false` 也是成功**：清 pending、**不提示**（避免噪音）。漏了会永久禁用按钮。**这是用例 UF-1c**（§10）。
- 真值来源始终是 `presence.following`（契约 §2.4 末条）。`pendingFollowing` **MUST NOT** 被任何判定读作跟随状态：`railEntry()` 只吃 `view.following`，`pendingFollowing` 的语义只是「请求在飞」（命名不得歧义）。
- 终态语义见 `SetFollowingInput.following`（`packages/shared/src/actions/following.ts:22-27`：`/** The state to write, not a toggle. */`），与契约 §2.4 一致（`docs/tools/05 §3.6.1`）。

### 3.4 功能键与展开器（UF-3）

每个角色项上有三个功能键，**始终在 DOM 中**，可见性由 CSS + 展开器状态控制（§3.6）。
**展开由独立可见的展开器负责；点头像不是展开器**（契约 §2.2 ★，见 §3.2 与 §3.6）：

| 键 | 文案 key | 行为 | 漏了会怎样 |
|---|---|---|---|
| 去 ta 那里 | `Go to them` | `onTravelTo(id)` → App 调 `04` 的单一入口 `usePresence().navigateTo(id)` | P-1 把导航从「点头像」移到这里，若这里也没有，`docs/doc-06 §5.4:336` 的导航能力彻底消失 |
| 跟随 \| 解散 | `Follow` / `Dismiss`（随 `view.following`） | 同 §3.3 | 跟随无法开关 |
| 去 ta 的小天地 | `Visit their nook` | `onOpenNook(id)` → `openNook(id)` | 小天地入口只剩直聊遮罩里那一个（`App.tsx:943`） |

**「去 ta 那里」的三档语义**（契约 §3.4 表面；rail 只负责把 `canTravel` / `travelHintKey` 接到按钮上，
**相机时序一律不在 UI 组件里再写一遍**）：

| 状态 | 行为（全在 `04` 的 `navigateTo` 内部） | 提示（精确英文，= `messages.json` key） |
|---|---|---|
| `in-scene` | `camera.flyTo(view.position.x, view.position.y)`（保持当前 z） | 无 |
| `elsewhere` | 进入 `view.layer`，等层切换重渲染提交后再 `flyTo` 新层里该角色的坐标 | 无 |
| `absent` | **不导航**，也不调 `enterLayer` | `They are not here right now.`（`docs/doc-06 §5.4:347`：不在场就是不在场，不硬造位置） |

- `absent` 时按钮仍**可见可点**（任务书要求「给可见提示，不导航」），点击只出提示。**这是用例 UF-3b**（§10）。
- **跨层导航的相机竞态（契约 §3.4 ★）归 `04`**：`Canvas.tsx:144-152` 在层变化时 `camera.save(prev)` + `camera.restore(currentLayer)`，而 `App.tsx:187-191` 在 `nookChar === null && !activeCharacter` 时 `cameraStack.setCurrent(...)`；两者都在渲染提交后跑，与 `await enterLayer()` 的先后**无保证**。因此 rail MUST 调单一入口 `navigateTo(id)`（owner `04`，内部 `requestAnimationFrame` 等一次重渲染提交再 `flyTo`）。rail MUST NOT 裸写 `await enterLayer(); flyTo();`。
- 跨层后读新层坐标的接缝是 `readLayerState()`（契约 §3.4，`04` 消费）；`navigateTo` 返回失败（跨层后读不到该角色）时用 `We could not travel there right now.`，到达后仍读不到坐标用 `They moved before you arrived.`（两键均见 §5.2；`04` 的 IRC 逐字确认）。
- **相机不写记忆**（契约 §3.4）：导航是瞬时取景，MUST NOT 写该层相机记忆（`useCamera.ts:39` 的 `CAM_MEMORY` 只在 `save` 时写；`flyTo` 只改 target，见 `useCamera.ts:159-163`）。

**触屏与键盘的等价路径（契约 §2.2 ★ 冻结，U-1 已裁决）**：

契约 §2.2 新增的裁决把三个动作钉成**三设备同义**，本文照此实现：

| 动作 | 触屏 | 鼠标 | 键盘 |
|---|---|---|---|
| **直聊**（点头像本体） | tap 头像 | click 头像 | 聚焦头像后 Enter/Space |
| **露出功能键** | tap **展开器**（独立、可见） | hover 头像（加速路径） | Tab 聚焦头像 → Tab 进入功能键 |
| **去 ta 那里 / 跟随\|解散 / 去 ta 的小天地** | tap 对应键 | click 对应键 | 聚焦后 Enter/Space |

- **点头像 = 直聊，跨设备一致**：触屏 tap 头像**不**展开功能键行（那是 U-1 的旧默认，已作废）；
  展开由**独立展开器**承担，因此同一手势永远是同一个意思（`skill://airp-natural-flow-direct-manipulation`
  的硬停条件）。
- **展开器在触屏必须可见**，MUST NOT 只靠 hover 露出（`@media (hover: none)` 下常驻或首次 tap 后常驻）。
  它带 `aria-expanded` + `aria-controls`（指向功能键行的 id）——**这是必须项**，本文原稿的
  「除非实现了折叠」已作废（折叠现在是必须的）。
- 桌面 hover 头像是**加速路径**：hover 或 `:focus-within` 时露出同一组功能键，不改变上面的三设备同义。
  既有先例：`scene-shell.css:82` 的 `@media (hover: none) { .object:focus-within > .entity-interactions … }`
  是「触屏无 hover 时的等价路径」的同类写法。
- 键盘：头像、展开器、三个功能键都是 `<button>`；`Tab` 序为 头像 → 展开器 → 三键 → 下一个角色。
  展开器是**独立焦点点**（不是头像的一部分），否则键盘无法在不触发直聊的前提下露出功能键。
- 每个功能键给 `aria-label`，含角色名。**实现修正（2026-09-14）**：本文初稿写「复用
  `Go to {name}` / `Follow {name}`」这类键，但 `messages.json` **没有** `Follow {name}` /
  `Dismiss {name}`，而本批次禁止新增键。实现改为**组合既有键**：
  `t('Follow') + ' · ' + name`、`t('Dismiss') + ' · ' + name`、`t('Go to them') + ' · ' + name`、
  `t('Visit their nook') + ' · ' + name`，直聊仍用既有 `Talk to {name}`。
  这样竖列里多个同名键对读屏用户仍可区分（**UF-7b 由此满足**），且不扩大键表。
  `railEntry` 的 `followActionHintKey` 字段据此删除（实现已不产出）。
- 头像 `<img>` 有 `alt`（角色显示名）；纯图形 orb 用 `role="img"` + `aria-label`。
  **MUST NOT** 用 `title` 当唯一无障碍名（`App.tsx:791` 现状的 `title=...` 是 hover 提示，不是 a11y 名）。

  /** 「去 ta 那里」的唯一调用点；三档语义 + 相机竞态（契约 §3.4 ★）全在内部。 */
  navigateTo(characterId: string): Promise<PresenceTravelOutcome>;
}

export function usePresence(input: {
  characters: CharacterPresenceSource[];   // 宽类型；App 的 CharacterView[] 结构兼容
  layer: string;
  presence: PresenceEntry[];               // world.state.presence
  readLayerState(): LayerState | null;
  enterLayer(next: string): Promise<unknown>;   // 契约 §7 P-10：04 不抄 01 的真实类型，只需「能 await」
  camera: Pick<CameraApi, 'flyTo'>;
  notify(message: string): void;
}): UsePresenceApi;
```

本文的用法（App 侧装配，不是 rail 组件内部）：

```ts
const { views, navigateTo } = usePresence({
  characters, layer, presence: state?.presence ?? [],
  readLayerState: world.readLayerState,   // 契约 §3.4 的只读接缝
  enterLayer: world.enterLayer,
  camera,
  notify: (key) => notify(t(key)),        // 让 04 的英文串当 messages key 用（§5.2）
});
// rail 的 onTravelTo：
onTravelTo: (id) => { void navigateTo(id); },
```

**契约 §7 P-10（已裁决）**：`04` 的 `enterLayer` 参数 MUST NOT 抄写 `01` 的真实返回类型
（`Promise<EnterLayerResult | null>`）——那会让 `01`/`04` 编译期互相绑定。`04` 只依赖「可 await」
这一最小契约，因此声明为 `Promise<unknown>`。`03` 的 App 侧装配（下图）传的是 `01` 的真实
`world.enterLayer`，**类型兼容**（`Promise<EnterLayerResult | null>` 可赋给 `Promise<unknown>`）。

- **`settled`（220ms 稳定窗口）由 `usePresence` 自己持有**：App / rail MUST NOT 再实现一份 220ms
  静默期（契约 §4.2 的「唯一真相源」；否则就是第二份阈值）——这也是本文 §2.1 props 里没有
  `settled` 的原因。
- `characters` 是 `04` 定义的宽类型 `CharacterPresenceSource`（只含 `id/name?/avatar?/role?/presence`），
  App 现有 `CharacterView` 结构兼容可直接传（`04` §2.1/§11 D-3）。
- 三档语义（`absent` 不导航 + 可见提示 / `in-scene` 直接 `flyTo` / `elsewhere` 先 `enterLayer` + 等一帧 +
  `readLayerState` + `flyTo`）与相机竞态（契约 §3.4 ★）**全在 `04` 内部**；`03` 只调 `navigateTo`。
- 三句提示串（`They are not here right now.` / `We could not travel there right now.` /
  `They moved before you arrived.`）由 `04` 回吐，`03` 已在 §5.2 登记 zh-CN + ja 条目。
- 相机**不写记忆**（契约 §3.4；`useCamera.ts:39` 的 `CAM_MEMORY` 只在 `save` 时写，`flyTo` 只改 target）。

### 6.4 nook 投影下的显隐（契约 §2.5）

契约 §2.5 把「nook 打开时右侧栏的显隐」判给 `03` 并写明理由。**裁决：nook 打开时角色栏继续可见
（保持现状：`.prototype-residents` 是 `.prototype-chrome`，`App.tsx:828`），但成员判定输入不变。**

理由：

1. 契约 §2.5 冻结「成员判定永远基于 `layer`，与 nook 无关」；角色栏在 nook 打开时显示的状态
   仍然是「玩家所在场景的在场关系」，这没有违反它 —— nook 是角色的私人空间，不改变玩家在哪。
2. 现状 nook 打开时 `.prototype-world` 内的 chrome 并未被隐藏（`App.tsx:661-686` 与
   `:687-726` 是 `nookChar` 的二选一分支，`:728` 起的 chrome 在两个分支之外），因此**保持可见
   不需要新代码**，隐藏反而要加例外。
3. **但 nook 打开时不再允许从角色栏进入另一个 nook**：`openNook` 持有 `callerProjectionRef`
   与相机栈（`App.tsx:205-215`），叠开第二个 nook 会破坏 `docs/nook/00` 的单 active projection。

   `Already inside a nook.` → 归 i18n，见 §11 C-4）。这是 UI 关，不改变世界状态。
4. 「跟随」在 nook 里仍可用（它只写 presence，与 projection 无关）。
