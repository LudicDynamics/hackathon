### 1.1 B1 的实测证据（主代理 2026-09-14 亲跑，不是读代码推断）

```
after move_to a  -> {"characterId":"watson","layer":"world/a","x":1056,"y":540,"following":false,…}
after follow on  -> {"characterId":"watson","layer":"world/a","x":1056,"y":540,"following":true,…}

after enter b   -> {"characterId":"watson","layer":"world/a","x":1056,"y":540,"following":true,…}
```

## 2. 语义（冻结，逐条）

### 2.1 三个概念的唯一定义

| 概念 | 定义 | 真相源 |
|---|---|---|
| **在场**（in the world） | `presence` 表里**有一行**该角色 | `canvas.db` 的 `presence` 行（`packages/shared/src/db/schema.ts:28-37`） |
| **同场景**（in the same scene） | 在场 **且** `presence.layer === 玩家当前 layer` | `presence.layer` 与前端 `world.layer` |
| **跟随中**（following） | 在场 **且** `presence.following === true` | `presence.following` |

**「同场景」不是「见过」**。现有 `encounters`（`App.tsx:134/418/594`）是「点开过对话的角色」的本地记忆，
与在场无关，**不得**用于任何成员判定。它随世界切换清空（`App.tsx:260`）、刷新即失，是浏览器内存里的假状态。

**「跟随」不是文件搬移、不是位置拷贝、不启动进程**（`docs/tools/05 §3.6`）：`characters/<id>/` 一个字节都不动；
跟随的兑现点是 `layer_entered`（`docs/tools/05 §3.6.2`），实现落点即 **B1**。

### 2.2 判定表（前端唯一派生规则）

设 `L` = 玩家当前 layer，`P(c)` = 角色 `c` 的 presence（`null` = 不在场）。

| 条件 | 状态 | 画布头像 | 右侧栏头像 | 点头像 |
|---|---|---|---|---|
| `P(c) === null` | **不在场** | 不渲染 | 灰 | 不直聊（提示「ta 此刻不在这里」） |
| `P(c).layer !== L` | **在别处** | 不渲染（本层没有它） | 灰 | 不直聊（提示，并给「去 ta 那里」） |
| `P(c).layer === L` | **同场景** | 渲染于 `(x, y)` | 全彩 | **直聊** |
| 任意状态下 `P(c).following === true` | 附加 **跟随中** | 头像右下角状态图标 | 头像右下角状态图标 | 与上同 |

**这条表是唯一判据**，画布与侧栏 MUST 读同一份派生结果，不得各自实现一遍（见 §4.1）。

**★ 触屏与键盘的等价路径（裁决，回应 03 的 U-1 / C-5）**：

上表「点头像 = 直聊」是**跨输入设备一致**的语义，**不因触屏而改变**。同一手势 MUST NOT 在
桌面是「直聊」、在触屏是「展开功能键」——那会让同一个动作有两种含义，正是
`skill://airp-natural-flow-direct-manipulation` 的硬停条件（「同一手势含义模糊」）。

冻结的三个动作三设备同义：

1. **直聊** = 点（tap/click）头像本体。触屏、鼠标、键盘（聚焦后 Enter/Space）都是它。
2. **功能键（去 ta 那里 / 跟随|解散 / 去 ta 的小天地）** = 由一个**独立的、可见的展开器**
   露出（触屏 tap 展开器 / 桌面 hover 头像 / 键盘聚焦 orb 后 Tab 进入），不是点头像本身。
   桌面 hover 是**加速路径**，不是唯一路径。
3. **展开器在触屏必须可见**（不能只靠 hover），且带 `aria-expanded`。

触屏无 hover 时的完整路径：`tap 展开器 → 三键出现 → tap 直聊/跟随/导航`；
桌面：`hover 头像 → 三键出现`（或 Tab 聚焦）→ 点键。**等价目标路径成立**（skill 第 3 条）。

### 2.3 跟随的兑现（B1 的正确接线）

`docs/tools/05 §3.6.2` 已冻结三步链，本批次把它落地：

```
玩家点门牌/双击子场景卡 → App enterLayer(next)
  → POST /api/enter-layer { layer }
    → serviceFor(store, {type:'player'}).enterLayer({ layer })
      1. appendEvent('layer_entered', …)          ← 现状已有（layer.ts:72-79）
      2. carryFollowers(ctx, layer)               ← ★ 本批新增调用
    → eventBridge 尾部读表 → world_event × N（1 条 layer_entered + M 条 character_moved）
    → 前端 useWorld 收 world_event → 整层重取 → presence 里有跟随者 → 头像出现
```

**顺序不可反**：先落 `layer_entered`，再搬人（`docs/tools/05 §3.6.2`）。`actor` 用 `engine`，
`detail.from` = 旧层、`to` = 新层（`presence.ts:249-261` 已按此实现，本批只补调用）。
失败必须可见：`carryFollowers` 返回 `{ moved, failures }`，`enterLayer` 的 `details` MUST 带上 `failures`，
前端 MUST 对非空 `failures` 给出玩家可见提示（`console.warn` 不算，`docs/tools/00 §6.2`）。

**★ 进 stub 层的行为已实测（主代理 2026-09-14 亲跑，`01` 可据此写测试）**：目标层是
**尚未写出（目录在、无 README，即 `first: true`）** 的 stub 层时，`carryFollowers` 依然正常：

```
enter stub details: "world/stub" first= true
carryFollowers into stub -> {"moved":[{"characterId":"watson","layer":"world/stub","x":1056,"y":540,"following":true,…}],"failures":[]}
```

即 **stub 层不是跟随的边界**（`docs/tools/05 §3.2` 明写「stub 层目录允许作为 destination」；
门槛逻辑与跟随无关）。座位在空层里照样求得出来（这里是锚点第 1 格 `(1056, 540)`）。
`01` 的测试 SHOULD 覆盖这条，防止实现者误加「stub 层不搬人」的门槛——那会让玩家进新场景时
跟随者掉队，而新场景恰恰是跟随最有存在感的地方。

### 2.4 跟随开关（B3）

- 玩家 UI 是 **toggle 的交互**，但**动作不是 toggle**：前端自己算 `next = !current`，发给后端的永远是终态
  （`docs/tools/05 §3.6.1`；`following.ts:6-7` 注释同口径）。
- 点两次是幂等的：动作层返回 `changed: false` 且不落事件（`following.ts:121-136`）。
- **前端不持有跟随真值**。开关状态一律从 `presence.following` 派生；本地 state 会与作家调用的
  `set_following` 分叉（`docs/tools/05 §6.4`）。

### 2.6 角色初始在场（2026-09-14 修订）

`world.json.characters[].home` 是角色**首次加载**的初始层来源；它不是当前层，也不是角色文件的
路径别名。世界加载入口在新 `LocalWorldStore` 对外激活前，必须调用共享的
`initializeMissingCharacterPresence(store, { turn })` 接缝：

1. 一次性读取 `store.getPresence()`，已有 `characterId` 的行原样保留
   （`layer` / `x` / `y` / `following` 一个字段都不得覆盖）。
2. 对没有行的 manifest 角色调用既有 `resolveHome`，再以固定
   `{ type: 'engine' }` 身份调用既有 `moveCharacter({ character, destination })`。
3. 坐标由 `moveCharacter` 内部唯一调用 `store.seatPresence` 生成；初始化接缝不得先自行
   `seatPresence`，也不得直接 `upsertPresence`。
4. `moveCharacter` 写 presence 后追加既有 `character_moved` 事件；首次出现不写虚构的
   `detail.from`。初始化失败不得被 warning 冒充成功，加载入口必须清理未激活的新 store。

该接线同时覆盖服务器默认世界启动与 `POST /api/worlds/load`。初始化在
`eventBridge.startTailReader` 之前完成；初始事件保留在 history，但不通过旧世界的 WS 重放，
首屏角色位置仍由 `/api/characters` 与 `/api/layer` 读取。初始化不是新的 WS 帧、状态表或
世界文件，角色的 `characters/<id>/README.md` 只保存角色资料和媒体 metadata。
旧存档若仍有 `home/<character-id>.md` 的 legacy card，`/api/layer` 不渲染它，且
`seatPresence` 不将这类角色卡计入新 presence 的占位；文件与旧 `cards` 行不在本批删除，
但不会再造成第二个可见角色组件。

### 3.4 「去 ta 那里」（新增能力，**不新增路由**）

导航用现有两条路由组合，纯前端：

| 情形 | 行为 |
|---|---|
| `P(c)` 为 null | **不导航**；提示「ta 此刻不在这里」（`docs/doc-06 §5.4` 末条：不在场就是不在场，不硬造位置） |
| `P(c).layer === L` | 相机 `flyTo(P(c).x, P(c).y)` —— 同场景移动到角色的坐标 |
| `P(c).layer !== L` | 先 `await enterLayer(P(c).layer)`，再在新层的 presence 里读 `(x, y)` 并 `flyTo` |

**读「新层坐标」的接缝**：`enterLayer` 解析后 React state 未必已 flush，因此 `useWorld` MUST 新增一个
**同步读取器** `readLayerState(): LayerState | null`（返回内部 `stateRef` 的当前值，与既有
`stateRef` 纪律一致，见 `useWorld.ts:141` / `:471`）。导航在 `await enterLayer(...)` 之后调用它取坐标。
`readLayerState` 是**只读**接缝，不触发渲染、不写状态。

**相机不影响记忆**：导航是一次**瞬时取景**，MUST NOT 写入该层的相机记忆（`useCamera` 的
`save/restore` 语义，`apps/web/src/state/useCamera.ts:36`）。理由：记忆是「玩家在场景里的视点」，
被一次导航覆盖会让返回场景时丢掉玩家自己的位置。相机通过 `camera.flyTo(x, y)`（保持当前 z）执行。

**★ 跨层导航的相机竞态（主代理 2026-09-14 亲自核实，MUST 处理）**：

现状有两处会在层变化时写相机，且顺序不由导航方控制：

1. `apps/web/src/components/canvas/Canvas.tsx:144-152` 的 effect —— 层变化时
   `camera.save(prev)` + `camera.restore(currentLayer)`（恢复该层的相机记忆）；
2. `apps/web/src/App.tsx:187-191` 的 effect —— `nookChar === null && !activeCharacter` 时
   `cameraStack.setCurrent(...)`。

而导航的 `flyTo` 发生在 `await enterLayer(...)` **之后**。若 `restore(currentLayer)` 落在
`flyTo` 之后（React effect 在渲染提交后执行，与 await 的时序并不保证谁先），
**相机会被拉回该层记忆的旧位置，导航看起来「没生效」**。这是一个真实的时序竞争，不是理论风险。

**冻结的裁决（`04` 定稿实现，`03` 只调用）**：导航 MUST 以「先落地、后取景」的**单一入口**执行——
即把「进入目标层 → 等该层的相机恢复稳定 → 再 `flyTo(角色坐标)`」封装成**一个**函数（建议
`navigateToCharacter(view)`，NEW），内部使用 `requestAnimationFrame`（或等效的一次帧等待）
在层切换的重渲染提交后再 `flyTo`，而不是裸调 `await enterLayer()` 紧接着 `flyTo`。

**验收必须覆盖这条**：一条测试（或浏览器步骤）要证明「跨层导航后相机最终停在角色坐标」，
而不是停在目标层的记忆位置。只测「`enterLayer` 被调用」是**假绿**——它不会发现这个竞态。

### 3.5 事件消费（B1/B3 的前端感知）

`following_changed` / `character_moved` 走 **`world_event`** 唯一通道（`docs/tools/00 §5.3`），
**不新增帧**。前端需要它们触发的行为：

1. `useWorld` 已经对**任何** `world_event` 整层重取（`useWorld.ts:430-453`）→ 画布 presence 自动更新，**无需改动**；
2. 右侧栏的跨层知识来自 `/api/characters`，因此 App 的 `airp:world-event` 监听
   （`App.tsx:337-345`，回调只做 `loadChromeData()`）必须在 `following_changed` / `character_moved`
   到达时重新取数。

**★ 修正（主代理 2026-09-14 核实，推翻本节初稿）**：初稿说改 `useWorld.forwardWorldEvent`
（`useWorld.ts:333-341`）的转发集合。**这是错的**——`forwardWorldEvent` 是一个**死函数**：
定义在 `:333-341`、被列进 `:723` 的 `useEffect` 依赖数组、但**全仓没有任何调用点**
（`grep -n forwardWorldEvent apps/web/src` 只有定义处、注释引用和依赖数组三处）。
它按 `entity_*` 过滤并 dispatch，却从未被 `onMessage` 调用，所以当前**真正**的转发点是
`onMessage` 顶部那条无条件的 dispatch：

```ts
// apps/web/src/state/useWorld.ts:422-425 —— 真正的转发点（现状）
if (msg.type === 'file_changed' || msg.type === 'card_position') {
  window.dispatchEvent(new CustomEvent('airp:world-event', { detail: msg }));
}
```

`world_event` **不在**这条无条件转发里；它只走 `case 'world_event'` 分支（`:430-453`），
而那个分支只做去重 + `fetchLayer`，**不 dispatch**。因此现状是：
**`following_changed` / `character_moved` 到不了 App 的 `loadChromeData()`**，右侧栏不会自动刷新。

**冻结的修法**（二选一，由 `01` 定稿并写清理由，`04` 不得另写一套）：

- **(a) 首选**：在 `case 'world_event'` 分支内、`fetchLayer` 之前，复用**已存在**的
  `forwardWorldEvent(msg)`，并把它的过滤集合改为「当前层重取也要重取 chrome 的事件」——
  即保留 `entity_*` 并增补 `following_changed` / `character_moved`。顺带让这个死函数复活，
  消灭「定义了却没接线」的第二处孤儿（与 B1 同类）。
- **(b) 备选**：只在条件里增补，不复活死函数；但那样 `forwardWorldEvent` 仍是死代码，
  MUST 在同一批次删除或标注（`docs/ux/03 §8.2` 的删除测试精神）。

**写法约束（两法都要守）**：过滤集合 MUST 保持 `[...].includes(x.event?.type)` 的**数组字面量**形式——
`check:ws` 的 `consumedFrom` 只认 `case 'x'` 与 `<expr>.type === 'x'`，而 `emittedFrom` 只扫
`broadcast|push|send|JSON.stringify({` 之后的 `type:` 字面量（`tools/check-ws-contract.mjs:100-133,135-149`）。
**MUST NOT** 把过滤集合改写成 `msg.event?.type === 'following_changed'` 这类链式比较——它会被
`consumedFrom` 正则读成一个**帧名**，从而报 GHOST（该帧从未被广播）。

## 4. 冻结：前端投影与阻尼

### 4.1 单一投影（唯一 owner）

角色在场的**公开投影**只有一个 owner，画布与侧栏都是它的消费者：

```ts
// NEW internal projection; not sent over WS. Owner: apps/web/src/lib/presence.ts
export type PresenceState = 'in-scene' | 'elsewhere' | 'absent';

export interface CharacterPresenceView {
  id: string;
  name: string;
  avatar?: string;
  role?: string;
  /** §2.2 的唯一派生结果 */
  state: PresenceState;
  /** 在场层；absent 时为 null */
  layer: string | null;
  following: boolean;
  /** 同场景时的世界坐标中心点；否则 null */
  position: { x: number; y: number } | null;
  /** true = 这个角色是从上一个层「带过来」的（用于阻尼入场，§4.2） */
  arrivedByFollow: boolean;
}

export function projectPresence(input: {
  characters: CharacterView[];              // /api/characters（含 presence）
  layer: string;                            // 玩家当前层
  presence: PresenceEntry[];                // /api/layer 的当前层 presence
}): CharacterPresenceView[];
// ★ P-21: 入参没有 `settled`。稳定窗口由 `createPresenceStabilizer`（04 拥有）
//   在投影**之前**回放上一帧快照；projectPresence 保持纯函数（§4.2 表第 5 行）。
```

- `state === 'in-scene'` 时 `position` **必须**来自 `/api/layer` 的 presence（不是 `/api/characters`）——
  后者只有层，没有坐标。
- 侧栏与画布 MUST 消费同一个 `CharacterPresenceView[]`，**不得**各自从 `state.presence` 或
  `characters` 重新推导（`docs/ux/00 §4.6`：公开状态单一投影）。
- 投影是**纯函数**，不得读 DOM、不得发请求、不得持有 timer（可测性，§6.1）。

### 4.2 阻尼与延迟（冻结阈值 —— 唯一真相源）

**为什么需要**：presence 是按层取回的离散快照，直接替换会造成「头像瞬间跳变/整列变灰」的硬切。
本批次用**有阻尼的过渡**替代硬切，让「跟随」在视觉上像「跟上来」而不是「换了张图」。

| 场景 | 冻结行为 | 时长 / 曲线 |
|---|---|---|
| **同层坐标变化**（`move_to`、`carryFollowers` 后重取） | 头像位置以 transform 过渡滑行 | `480ms cubic-bezier(.22,.61,.36,1)` |
| **切层：离场** | 离场头像保留快照并淡出 | `260ms ease-out`，透明度 → 0 |
| **切层：入场** | 淡入 + `8px` 上浮，按索引错峰 | `360ms cubic-bezier(.22,.61,.36,1)`，`stagger 60ms` |
| **切层：跟随带过来的角色** | 视作入场，但**不做跨层滑行**（跨层坐标无几何意义） | 同入场，错峰排在最后 |
| **侧栏成员状态翻转**（同场景 ⇄ 他处/不在场） | **稳定窗口**：新层 payload 落地后延迟再翻转 | `220ms` 静默期，期间沿用上一帧投影 |
| **Reduced motion** | 全部降为透明度即时或 ≤`120ms`，**不做位移** | `docs/ux/00 §4.7` 优先级：`prefers-reduced-motion` > 页面不可见 > 默认（**不含 Effects 开关，见下**） |

**★ 裁决（主代理 2026-09-14，回应 CanvasPresence 的 C-1）：presence 阻尼 MUST NOT 受 `effectsEnabled` 控制。**

事实：`effectsEnabled` 默认值是 **false**（`apps/web/src/App.tsx:138-140`：`localStorage.getItem('airp:effects') === 'on'`，
未设置即 false）。照本表初稿字面实现，「跟上来」的阻尼会**默认全程关闭**——正好废掉明月这次
特意要的「阻尼感与延迟」，属于把好设计默认关在门外。

理由：`effectsEnabled` 在现状里 gate 的是**环境装饰**（粒子 `Canvas.tsx:113`、指针视差 `:318`、
动态背景，开关文案也是 "Particles, parallax and animated backgrounds"）。而 presence 的
入场/滑行/淡出是**承载信息的状态过渡**：它告诉玩家「谁跟过来了」「谁掉队了」。
把它和装饰开关绑在一起，等于「关了特效就再也看不出谁在跟随」——信息随装饰一起消失是错的。

**冻结的降级输入只有两个**：`prefers-reduced-motion`（`apps/web/src/lib/appearance-view.ts:73-77`
已有读取实现，可复用）与页面可见性。`Effects off` **不是** presence 阻尼的降级条件。
空场景/低端机也不必额外降级：本条全部是 `transform` / `opacity`，合成成本与装饰层不是一个量级（§4.3）。

- 稳定窗口（`settled`）的实现 MUST 只影响**投影输入**，不阻塞世界数据或交互。漏掉它的后果：
  切层瞬间整列灰一下再亮回来，玩家读成「他们掉队了」。
- 离场头像的瞬时保留是**纯客户端展示**，MUST NOT 进入 `items` / `presence` 状态，也 MUST NOT 可交互
  （`pointer-events: none`）。

### 4.3 Theatre Depth 与合成成本

- 画布在场头像属于 `entity` 深度（`docs/ux/00 §4.2`），MUST 复用既有 `--depth-entity-*` token

- 头像**不参与** Canvas 的取景 effect（`Canvas.tsx:159-183` 只按 `.object` 算 bounds），

  （`docs/tools/05 §3.9`），前端不重算。

## 9. 落地期回写（§0 的「同步回写」纪律）

### P-22（实测发现并已修复）：`lib/presence.ts` 的提示串必须由装配方翻译

**真 Chromium 冒烟实测**：日文会话里点「不在场」角色的「去 ta 那里」，toast 弹出
**英文** `They are not here right now.` —— 英文漏进了日文 UI。

**根因**：`lib/presence.ts` 是**纯模块**（不 import i18n），按 `04 §7` 的设计只输出**英文 key 串**；
翻译应由装配方完成（`04 §7` / `03 §6.3` 都写了 `notify: (key) => notify(t(key))`）。
集成时把 App 的 `notify` **直接透传**进 `usePresence`，而 `App.tsx` 的 `{toast}` 渲染原样输出，
于是英文 key 落进了日文 UI。

**冻结（已修）**：`App.tsx` 的 `usePresence({...})` MUST 传 `notify: (key: string) => notify(t(key))`，
**不得**传裸 `notify`。`lib/presence.ts` MUST 保持无 i18n 依赖（§4.1「纯函数」的前提）。

**更一般的教训**：这是「**只改一端 = 死口径**」的 i18n 版本——`presence.ts` 说「我发 key」，
`App` 说「我收原文」，两端各自都"对"，中间的口径没人守。
**`check:i18n` 抓不到它**：那三句 key **在 `messages.json` 里存在**（门禁据此算它们「被解析」），
只是**实际调用点没经过 `t()`**。**门禁能证明键存在，不能证明键被使用**——
这条是本批次的机械门禁缺口，`04 §9` 可考虑补一条「presence 提示串必须经 `t()`」的门禁。

**验证**：修后同一条路径的 toast 为 `彼は今ここにはいません。`（日文，与场景语言一致）。
