## 0. 为什么现在要单独立项

仓库已经多次提到“视觉皮肤随题材变化”，但没有把**组件实例自身的多样化**立成独立设计项目：

- `docs/doc-05-AIRP产品构想.md:78-80` 把统一画布、材质皮肤和物件并列为产品基础；`:142` 规定世界/层的 `material` 决定画布材质。
- `docs/doc-04-视觉设计风格.md:146` 将 token 单一源与换肤列为系统能力；`:157-163` 给出字体分工、材质词汇表和 token 换肤原则；`:224-226` 又要求在 v2 圆角、软影、低饱和色基准下重新定义皮肤。
- `docs/doc-10-组件协议与官方组件清单.md:107` 明确三种原型在组件“皮肤（材质/字体/动效）”上分歧很大，且建议组件协议只定结构、皮肤归题材包 / `doc-04`；`:166-170` 的组件 schema、官方清单、交互、落地与 `look_at` 仍是待设计项。
- `packages/shared/src/schemas/forms.ts:157-193` 已经存在只覆盖 Chalk 的 `ChalkStyle`（`font`/`big`/`tone`/`card`/`collapsed`/`aged` 的归一化）；它证明需求曾局部落地，但不是所有组件的通用外观协议。
- `packages/shared/src/schemas/components.ts:65-75` 的组件核心只收语义字段，`:93-226` 的各 kind schema 通过 `.passthrough()` 保留未知字段；`packages/shared/src/schemas/frontmatter.ts:117-142` 的实体 schema 也保留未知字段。这使本批可以在不破坏旧文件的前提下设计命名空间，但**不等于现有代码已经支持该能力**。

本项目要正式回答：同一个 `kind` 是否可以通过 frontmatter 选择不同视觉主题；主题如何由多维属性组合；默认无背景如何表达；世界、层、组件实例三层如何协作；作者如何可靠地产出；前端如何渲染且不把任意 CSS 变成注入面。

## 1. 目标与非目标

### 1.1 目标

1. 同一语义组件（包括 `chalk`、`note`、`letter` 及已注册 component kinds）可声明多套外观，而不复制 kind 或修改互动协议。
2. 外观至少能覆盖用户提出的维度：字体、背景/表面是否存在、材质/装饰风格，并允许安全的排列组合。
3. 默认样式仍然稳定：旧文件无外观字段时，渲染结果不改变；Chalk 默认透明背景。
4. 外观选择是可验证、可降级、可解释的有限集合，不允许 frontmatter 直接注入 CSS、任意 class、脚本或未经授权的资源。
5. 外观不改变实体语义：`type`、`component`、`title/body`、`choice/status/roll_dice`、`accepts`、可收藏性、点击后果、事件和路径均不因换肤而改变。
6. 设计能够覆盖文件真相、服务端/共享 schema、前端渲染、作者提示与测试验收的完整闭环。

### 1.2 非目标

- 本批不新增组件 kind，不重做 `COMPONENT_REGISTRY`，不重写 `CARD_FORMS` 的尺寸/碰撞契约。
- 本批不新增独立状态文件、主题数据库、运行时用户自定义 CSS、脚本化组件或 iframe 市场协议。
- 本批不把世界级 `material`、场景 `bgStyle`、音频 `audio.theme` 改造成组件外观；它们仍是各自领域字段。
- 本批不实现组件编辑器、批量迁移工具或具体素材生产，除非后续评审明确进入实现阶段。
- 演出型 `show` 的一次性 `show_frame` 不是落盘组件实例；如需外观参数，必须另行证明不污染本批的落盘 frontmatter 契约。

## 3. 统一术语

| 术语 | 冻结含义 |
|---|---|
| **组件语义** | `type` / `component` kind 及其字段、互动、路径、落盘和事件行为；换外观不得改变它。 |
| **组件外观** | 仅回答“怎么画”：字体、色调、surface/background、装饰、密度、动效强度等；本批统一放在 frontmatter 的 `appearance` 命名空间中。 |
| **外观 preset** | 由代码或受信任题材包登记的稳定英文 kebab-case ID；frontmatter 只能引用 ID，不能携带 CSS。 |
| **外观维度** | 可独立组合且有默认值的受控轴，例如 `font`、`surface`、`accent`、`ornament`；各维度允许集合由组件/题材注册定义。 |
| **appearance resolver** | 将世界/层上下文、kind 默认、`appearance.preset` 与显式维度归一化为前端可消费的已验证外观对象的唯一逻辑；具体代码落点由 `01`/`02` 设计，不能多处各算一遍。 |
| **默认无背景** | Chalk 的默认 `surface`/背景必须是真透明或等价的 bare ink，不得被全局卡片壳偷偷补成纸面。其他 kind 的默认值由其现有视觉语义冻结并登记。 |

## 4. Frontmatter 共享形状（冻结基线）

所有落盘实体沿用现有 frontmatter；本批新增一个可选命名空间，不把外观字段散落到顶层：

```yaml
appearance:
  preset: parchment-letter       # 可选，稳定英文 kebab-case ID
  font: serif                    # 可选，受控维度 ID
  surface: parchment             # 可选；`none` 表示无表面/无背景
  accent: rust                   # 可选，受控色调 ID
  ornament: seal                 # 可选，受控装饰 ID
  motion: calm                   # 可选，受控动效档位
```

冻结规则：

1. `appearance` 是可选 object；**缺失**等价于旧默认行为，且不启用世界/层 context preset。显式写出空 object `{}` 才表示实体选择加入当前 context preset；这是旧内容零视觉回归的硬门槛。
2. `preset` 与各显式维度的优先级由 resolver 统一定义：基础默认 → kind 默认 →（仅当 `appearance` 存在时）context preset → 实例显式 `appearance.preset` → 实例显式维度。子文档不得各自发明优先级。
3. 所有 ID 都是英文小写 kebab-case 稳定标识；显示名与说明随世界语言，不把日语/中文显示名写进路径或协议 ID。
4. 解析读取必须宽容：未知键/值不得生效，但要进入统一 `warnings`/`details` 并回退到安全默认。所有实体写入入口（`createEntity`/`write`、`editEntity`/`edit`、组件 handler 的 frontmatter rewrite）必须在落盘/事件前调用严格 `validateAppearanceInput(raw, kind)`；非法 namespace、未登记 ID、未知键、raw CSS、外部 URL 等拒绝写入且不产生对应 `entity_edited`。
5. `appearance` 不得包含 raw CSS、任意 CSS class、HTML、脚本、数据 URI 或未经路径校验的外部 URL。v1 外观只引用受信 registry 的 token/装饰 ID，不新增主题资产 URL；未来若纳入资源，必须另行修订本节并复用既有资源边界。
6. 外观字段不进入 `status.data`、`choice`、`roll_dice`，也不改变 `look_at` 对互动字段的既有语义。`look_at` 是否展示已验证外观摘要由 `05` 设计，但不能暴露原始 YAML 作为唯一用户体验。
7. 旧字段兼容必须是有边界的：现有 Chalk `font` / `color` / `tone` / `big` / `size` / `card` / `chrome` 行为需由 `05` 评估迁移或兼容读取；不得让同名字段在新旧语义之间静默变义。

**跨端输出冻结：** 服务端统一调用 `resolveAppearance`，并在 `GET /api/layer` 与 `GET /api/nook` 的每个 `items[]` 上返回可选 `appearance: AppearanceResolution`；旧服务端/旧响应缺失该字段时，前端按 kind 旧默认。前端只消费已验证 resolution，绝不在 React 重算 resolver；本批不新增 WS 帧。

**token 归属冻结：** `01` 的独立 appearance registry 是 ID、kind 能力、preset 与安全 token 元数据的唯一登记处；`02` 只负责 context 装配与 resolver；`04` 只负责把已验证 token 映射到 DOM/CSS，不得维护第二张 token 表。

**未知键两种时机必须分开：** 读取旧文件时保留原始 frontmatter 并诊断，不因单个未知 appearance 键丢弃整篇实体；作者/迁移写回时严格拒绝未知键，迁移器只能在明确策略下删除已证明等价的旧键。

## 5. 组合与默认原则

- **语义先于皮肤**：`letter` 仍是信、`lock` 仍是锁；外观不能把它伪装成另一个 kind 以改变交互。
- **可组合但不任意**：允许正交维度组合，但组件可声明禁用/固定某些不合适的组合（例如透明 Chalk 不应自动获得 letter seal）。组合矩阵、冲突规则与可达性由 `01` 冻结。
- **可读性优先**：任何组合都必须满足卡面摘要、正文、互动控件、聚焦态和无障碍对比度；装饰是加法，不得挤压正文或改变卡片 footprint。
- **尺寸不随外观偷偷漂移**：`CARD_FORMS` 仍是声明尺寸唯一源，外观不得在运行时另算碰撞尺寸；如某外观确实需要不同尺寸，必须作为显式 form/version 设计并经过 footprint 契约，而不能用 CSS 溢出掩盖。
- **确定性**：同一世界、同一实体路径、同一外观输入应得到稳定结果；不得用随机主题让页面刷新后换皮。
- **可降级**：缺失 preset、未知维度、registry token 缺失、浏览器不支持动效时，语义内容仍可读，按固定链回退，并留下可测试的诊断信息；v1 appearance 不发起主题资源请求。

**作者查询边界冻结：** `look_at` 只返回验证后外观的世界语言显示名；`get_component` 的可选 details 返回合法写法/schema、稳定 ID、preset、维度、组合与本地化 label。实例正文/frontmatter 仍由 `read`/`look_at` 读取，不让 `get_component` 变成实例读取器。

子文档统一使用以下章节：一句话定位、签名/数据形状、逐步行为契约（每步写漏了会怎样）、文件与副作用、落账与事件、WS/前端边界、错误边界、代码落点、与现状差异、验收测试、发现的冲突/需修订上位文档、仍未知待拍板。现状断言必须带 `file:line`；推断标 `[推断]`；新符号标 `NEW` 并写签名。
