## 0. 预期效果（按玩家看到的体验定义）

玩家必须能在不读模型聊天记录的前提下回答三件事：

1. **谁正在工作**：作家、角色或功能性 agent 是否仍在处理，是否已经结束；
2. **正在做什么**：工具动作以低干扰、可消散的胶囊弱提示呈现；不要求暴露原始参数、思维链或 chat history；
3. **最后留下什么**：角色的可说台词不因工具循环而丢失；作家正文仍通过 Chalk 演出；功能 agent 的产物变化和失败结果可感知。

这不是把 agent chat history 展示给玩家，也不是展示思维链。它是一个面向玩家的、经过白名单归一化的演出状态层。

**真实模型链路已经接通**：本批不把「接入真实模型」列为前置条件，也不以确定性探针代替真实链路验收；设计和实现必须覆盖真实模型可能产生的多条 assistant message、工具循环、空文本和括号动作内容。

## 2. Agent 身份与可见范围

### 2.1 身份

| `source` | 含义 | 当前来源 |
|---|---|---|
| `writer` | 作家 agent | `apps/server/src/engine/lifecycle.ts` 的 writer RpcClient |
| `character` | 角色 agent | character RpcClient；必须使 `agentId` 为 `character:<characterId>`，不在帧中重复增加 `characterId` 字段 |
| `functional` | 功能性 agent（scene-init / nook-init 等） | 子 agent 或命令执行链；必须带稳定 `agentId`，不能伪装成 writer |

`agentId` 的规则：

- writer：`writer`；
- character：`character:<characterId>`；`characterId` 必须与 `/api/characters` 返回的稳定 id 逐字一致，半角冒号是冻结分隔符；
- functional：稳定功能名，例如 `scene-init` 或 `nook-init`；若同一功能可并发，追加本次 `turnId`，不能使用随机展示名。

### 2.2 可见范围

- `writer` 和 `functional` 的活动胶囊进入全局底部 activity rail；不展示 chat history；
- `character` 的活动胶囊进入当前角色对话纸**上沿之外的独立 activity rail**，不入纸、不遮挡台词，避免与作家全局状态混淆；角色关闭时，其未完成胶囊必须终止或收束，不能泄漏到下一个角色；
- 角色台词仍由 `CharacterModal` 的对话纸呈现；胶囊不是台词，不进入角色 TTS；
- 初始化成功/失败仍以 `world_event` 和现有画布刷新为最终事实，胶囊只是过程感知。

## 3. 统一 agent activity 帧（设计冻结）

本批新增一个跨端帧：`agent_activity`。它是玩家感知专用帧，不替代既有 `tool_start` / `tool_end` / `agent_progress`，也不进入世界事件表。

```ts
interface AgentActivityFrame {
  type: 'agent_activity';
  source: 'writer' | 'character' | 'functional';
  agentId: string;
  turnId: string;
  activityId: string;
  phase: 'started' | 'completed' | 'failed';
  operation:
    | 'read'
    | 'create'
    | 'write'
    | 'edit'
    | 'delete'
    | 'move'
    | 'use'
    | 'look'
    | 'roll'
    | 'choose'
    | 'initialize'
    | 'other';
  subject?: string;
  toolName?: string;
  error?: string;
  timestamp: string;
}
```

冻结要求：

- `activityId` 在 start/end/failed 间保持一致；
- `turnId` 标识一次 pi-rp engine turn（上游定义为一次 LLM response + 其工具调用），不等同于 session id 或整个 agent run；server 在 `turn_start` 事件生成/绑定它，在 `turn_end` 后不再复用。缺少 engine turn 的命令型 functional 根活动才使用带 `functional:` 前缀的合成 turnId；不得把 `agent_start` 的 run id 冒充 engine turn。
- `subject` 只能是经服务端白名单和路径裁剪后的玩家可读对象名，不得带原始 JSON 参数、密钥、绝对路径或模型思维内容；
- `error` 只允许安全、可展示的失败摘要；完整错误进入服务端日志，不进玩家胶囊；
- `tool_start` / `tool_end` 仍然服务既有 writer footprint / 演出逻辑；前端 activity rail 只消费 `agent_activity`；
- `agent_activity` 不落 `history.db`，因为它是临时演出，不是世界变更；真实变更仍由既有 action/event 链落账；
- 所有新增帧必须加入 `docs/tools/12 §6.2`、前端 `useWorld` 消费面和 `tools/check-ws` 的契约集合。

### 3.1 operation 归一化

工具名不能直接成为玩家文案。服务端必须用单一白名单归一化：

| 工具/命令名 | operation | 默认 subject 来源 |
|---|---|---|
| `look_at`, `view_canvas` | `look` | `path` / `name` |
| `read` | `read` | `path` |
| `write`, `chalk`, `create_file` | `write` | `path` / `details.path` / `name` |
| `edit` | `edit` | `path` / `name` |
| `delete` | `delete` | `path` / `name` |
| `move`, `move_to`, `rename` | `move` | `from` / `to` / `path` |
| `choose`, `choose_option` | `choose` | `name` / `path` |
| `roll_dice` | `roll` | `name` / `path` |
| `use_item`, `use_item_on` | `use` | `itemName` / `targetName` |
| `show`, `get_component` | `use` | `component` / `target` |
| `link`, `arrange`, `set_following` | `edit` | `path` / `layer` / `name` |
| `generate_image` | `create` | `name` / `path` |
| `subagent`, `subagent_profiles` | `use` | 合法 `profileId` |
| `airp-init`, `scene-init`, `nook-init` | `initialize` | 合法 `target` |
| 其它 | `other` | 省略 |

这张表是唯一 authority；同一映射同时服务 writer、character、functional 和 child relay，子文档不得自行发明第二套映射。新增工具必须先修改本文，再同步工具契约和测试。

### 3.2 胶囊默认生命周期

- `started`：立即出现「正在读取……」「正在修改……」类弱提示；
- `completed`：更新为过去式结果，例如「写下了 xxx」「修改了 xxx」；
- `failed`：更新为「修改 xxx 失败」并保留更长时间；
- completed 默认 2400ms 后淡出；failed 默认 4500ms 后淡出；started 若没有结束事件，最多 90000ms 后转为超时失败；
- 同时存在多个活动时按开始时间堆叠，最多展示 3 个，超出的进入短队列，不得丢失 completed/failed 的可见反馈；
- 同一 `activityId` 的状态更新必须幂等；重复 WS 帧不得产生重复胶囊；
- 文案由前端按 locale 生成，`subject` 只作为插槽；不能把模型原文直接当 UI 文案。

实现约束：TTL 和可见上限必须落在 `apps/web/src/lib/agent-activity.ts` 的导出常量（`ACTIVITY_COMPLETE_TTL_MS = 2400`、`ACTIVITY_FAILED_TTL_MS = 4500`、`ACTIVITY_STALE_TTL_MS = 90000`、`MAX_VISIBLE_ACTIVITIES = 3`）中；去重、状态归并和过期清理必须是可由 `node:test` 直接调用的纯函数或无 DOM reducer，不能只写在 React effect 或 CSS 里。

## 4. 角色 turn 与多 assistant message 语义

### 4.1 turn 与 message 必须分开

一次角色 turn 可以包含多个 assistant message 和多个工具循环：

```text
turn_start
  assistant message 1 / text_delta*
  tool_start / tool_end
  assistant message 2 / text_delta*
  tool_start / tool_end
  assistant message 3 / text_delta*
turn_end / character_idle
```

`character_message` 只能表示「当前 assistant message 的边界」，不能覆盖整个 turn 已累计的角色台词。

### 4.2 玩家最终看到的角色文本

- 同一 turn 内所有可说文本按 assistant message 出现顺序保留；
- 工具循环产生的空 assistant message 不产生空页；
- assistant message 内的文本块只保留一次，不能同时由 delta 和 message_end 重复追加；
- `character_idle` 才是整轮封口；在此之前不能用后一个 `character_message` 抹掉前一个可说文本；
- 角色前端可以继续按换行分页，但分页的输入必须是「当前 turn 的可说文本序列」，而不是最后一个 `character_message.text`；
- 角色对话纸不变成可滚动 chat history；若演出空间有限，仍由既有分页/翻页语义控制，但文本不能静默丢失。

### 4.3 角色工具感知

角色调用工具时，activity rail 必须显示经过归一化的动作，例如：

```text
正在查看信件……
查看了信件
正在写入信件……
写下了信件
```


不得显示：

- 原始 tool args；
- 绝对路径；
- 模型内部思考；
- 未经清洗的文件全文。
可测性约束：角色 turn 聚合必须下沉到零 React 纯模块 `apps/web/src/components/overlay/dialogue-pages.ts`（若实现者拆出 `character-turn.ts`，必须在同批文档回写并保留同一导出语义），至少提供 `createCharacterTurn()`、`consumeCharacterFrame(buffer, frame)`、`resetCharacterTurn()`。React 组件只负责把帧送入纯函数并投影页面；角色多 assistant message 的旧实现必失败回归不得只依赖浏览器手测。

## 5. TTS 可朗读文本清洗（设计冻结）

现有 `parseEmoTag` 只处理 `[emo: tag]`；TTS 请求目前直接使用页文本。必须新增一个**共享纯函数**，唯一实现落点为 `packages/shared/src/rules/tts-text.ts`，并从 `packages/shared/src/index.ts` 显式导出。它是前端预检和服务端唯一合成点的同一语义来源。前端在发请求前清洗以跳过空文本；服务端收到请求后必须幂等重清洗，确保任何客户端都不会把动作内容送给厂商或写进缓存 key。

### 5.1 清洗顺序

```text
原始角色页
→ 去除前导 [emo: tag] 控制标签
→ 共享纯函数去除动作/舞台指示括号片段
→ trim 空白
→ 为空则前端跳过 TTS；服务端返回既有 invalid_argument
→ 非空文本才 POST /api/tts
→ 服务端再次幂等清洗后再截断、hash、合成
```

前端和服务端 MUST import 同一个 helper，MUST NOT 各自维护正则副本。服务端清洗是安全边界，前端清洗是避免空请求与减少延迟的预检。

### 5.2 必须过滤的括号

默认过滤成对包裹的以下片段（含括号本身）：

- ASCII round brackets：`(...)`
- 全角圆括号：`（...）`
- ASCII square brackets：`[...]`
- 全角方括号：`【...】`

`[emo: tag]` 由情绪标签解析器优先消费，不应被误当成台词。

示例：

```text
（笑了一下）好啊       → 好啊
(laughs) Sure          → Sure
【把信递给你】拿着      → 拿着
（笑了一下）           → 空文本，不发 TTS
[emo: smile] 好啊      → 好啊
```

为避免误删，正文显示仍保留原始文本；只把清洗结果用于 TTS 请求和 TTS cache key。清洗后的文本不得回写角色消息、不得改变页面上玩家看到的台词。

### 5.3 异常括号（冻结：fail-closed）

清洗 helper 遇到以下任一情况，返回空串，不抛异常，也不把部分文本送去 TTS：

- 只有开括号或只有闭括号；
- 括号类型交叉或栈无法正确闭合；
- 跨换行仍未闭合；
- 其它无法证明为成对动作片段的结构。

这是「宁可这一页无声，也不朗读疑似动作或控制文本」的安全口径。页面仍显示原文，前端跳过 TTS 并沿用无语音 stinger 语义；服务端返回既有 `invalid_argument` 防线。`SILENCE_LINE` 这类本来就是舞台指示的兜底文本接受静音，不新增豁免标记。
### 5.4 TTS 与页面演出

- 原始台词页仍是页面和打字机的输入；
- 清洗后为空：页面仍显示、仍可翻页，但不请求 TTS；按既有无语音 stinger 语义处理；
- 清洗后非空：以清洗后的文本参与请求；缓存 key 必须因此稳定变化；
- 同一页不能同时因原文和清洗文发出两次请求；
- TTS 不读取 activity rail 文案，工具胶囊永远不朗读。

## 6. 作家与功能 agent 的正文/活动分离

- 作家 chat history 不在画面中展开，继续保持现有设计；
- 作家 Chalk 仍是叙事正文的唯一画布落点；
- writer/functional 工具活动通过全局 activity rail 感知；
- scene-init/nook-init 的产物成功仍由 `layer_initialized` / 对应 world event 作为事实；activity rail 只表现过程和工具动作；
- functional agent 无独立可见聊天回复，除非未来另立契约；其 `SubagentResult.text` 不能直接冒充玩家台词。

## 7. 前端生命周期与边界

### 7.1 全局 activity rail

挂在画布/场景外壳下方，不遮挡 Chalk、输入框和角色纸；它是全局/surface 维度，不随当前世界层切换而清空，支持 writer 与 functional 并存，按 `agentId`/`turnId` 过滤和收束。

### 7.2 角色 activity rail

挂在 `CharacterModal` 对话纸上沿之外的独立流式带，不入纸、不遮挡台词；角色关闭时：

- 已完成胶囊可立即淡出；
- started 胶囊必须转为取消/收束态，不能继续显示为正在工作；
- 下一角色不能继承上一角色的 `activityId`。

### 7.3 状态与胶囊不是同一东西

- `agent_progress` = agent 生命周期/阶段状态；
- `agent_activity` = 某个具体工具动作的瞬时感知；
- `writer_delta` / `character_delta` = 正文演出；
- `world_event` = 已落盘的世界变化。

前端不得用胶囊替代生命周期，也不得用 `world_event` 猜测工具已开始。

## 9. 评审与验收总门槛

实现前必须由设计评审确认：

- 跨 agent source / agentId / turnId / activityId 一致；
- `agent_activity` 同时接入服务端发射、前端消费、WS 契约和测试；
- 角色多 assistant message 的回归测试在旧实现下会失败，在新实现下保留所有可说文本；
- TTS 过滤测试覆盖括号动作、情绪标签、纯动作行和异常括号；
- TTS 缓存和请求体语义不会因清洗重复请求或污染显示文本；
- writer/functional 胶囊在成功、失败、超时、并发和重复帧下可感知且不泄漏；
- 真实模型路径无需新增开关即可使用这些能力；
- docs/tts、docs/tools、docs/perform、AGENTS.md 的架构口径在实现同批回写；
- `pnpm build`、`pnpm test`、`pnpm probe`、`pnpm probe:inject`、`pnpm probe:prompt`、`pnpm probe:init`、`pnpm check:ws`、`pnpm check:bodies`、`pnpm check:i18n` 及新增专项测试通过。
