## ① 一句话定位

**把本批三条冻结契约（`agent_activity` 帧、角色 turn 多消息、TTS 清洗同一 helper）翻译成一组"旧实现必失败"的可执行断言，并把每个断言明确归到「机械门禁能抓」还是「只能人工评审」，再把实现后必须改的文档逐条钉死。**

本文最重要的两条结论，先说：

1. **本批最大的假绿风险是「用编译通过 / 门禁转绿当行为证明」**：`pnpm check:ws` 只比**帧名字面量集合**（`tools/check-ws-contract.mjs:188-228` 的四个漂移类），`pnpm check:bodies` 只比**请求体键集合**（`tools/check-request-bodies.mjs:270-300`）——**两者都看不见"这条帧是否真的驱动了可见行为"**。契约 §9 与 `docs/perform/00 §10` 都点了这条：**每条新帧 MUST 附"该帧真的驱动了可见行为"的判据。**
2. **本批的"旧实现必失败"断言有一半落不到 node 测试里，除非先把纯函数切出来**：`CharacterModal` 的 turn 聚合与 rail 的胶囊生命周期都是 React 组件内状态。**若不把它们切成无 React 的纯模块，契约 §9 要求的"角色多 assistant message 回归测试在旧实现下会失败"就无法机械化**，只能靠浏览器手测——这是本批设计必须先解决的**前置**，见 §11 冲突 1。

### 4.3 角色多 assistant message 回归（本批最贵）

**契约 §4.1/§4.2**：一次 turn 可有多个 assistant message 与多个工具循环；所有可说文本按出现顺序保留；工具循环产生的空 message 不产空页；同一 message 的文本**只保留一次**（不能 delta 与 `message_end` 双追加）；`character_idle` 才是整轮封口。

**现状缺陷（实测）**：`CharacterModal.tsx:576-596` 的 `character_message` 分支在**两条路径上都整体替换** `lineRef`——`lostAll` 路径 :584、非 `lostAll` 路径 :591（注释写"丢帧 → 以权威文本为准"）。于是 `message 1` 被 `message 2` 覆盖，契约 §8 第 1 条登记的正是这条。

| ID | 断言 | 旧实现为何必失败 |

| **CM1** 多消息保序（**非空性核心**） | 输入「msg1 / tool / msg2 / tool / msg3」→ turn 结束后页序列 = `[msg1, msg2, msg3]` | 旧实现只剩 `[msg3]`；新实现必须通过 `CharacterTurnBuffer` 纯函数断言 |

## ⑦ 前端接线

> 本节只声明**测试与回写视角**的接线契约；具体 UI 归 `FrontendPerceptionDesign`。

### 7.1 消费链（唯一路径）

```text
服务端 broadcast({ type:'agent_activity', … })
  → useWorld.ts onmessage 的 switch 加 case 'agent_activity'
      · 不可省：门禁 consumedFrom（check-ws-contract.mjs:132-143）只认 case / .type=== 字面量
      · default 分支（:541-543）会静默吞掉未列帧 → 这是本批最容易的"发射了但没人消费"（DARK）
  → window.dispatchEvent(new CustomEvent('airp:agent-frame', { detail: msg }))   // :351-353 已无条件转发
  → agentActivityStore.ingest(frame) → normalizeAgentActivityFrame → upsertActivity
  → useAgentActivity(surface) → ActivityRail
```

**为什么 case 与 store 两处都要**：`case` 是为门禁与"确实被路由"的证明；`ingest` 才产生可见行为。**只加 case 不 ingest = 门禁绿而 rail 空**——这正是 `docs/perform/00 §10` 点名的门禁假绿。

### 7.2 归属（surface）

- `writer` / `functional` → `surface:'rail'`（全局底部 rail，任何角色/小天地打开状态仍可见）；
- `character` → `surface:'character-modal'`，由 hook 用 `agentId === \`character:<id>\`` 过滤；
- 角色关闭 → `clearSurface('character-modal')`；**下一角色不得继承上一角色的 `activityId`**（契约 §7.2）；
- rail MUST NOT 遮挡 Chalk / 输入框 / 角色纸（契约 §7.1）。

### 7.3 状态与胶囊不是同一东西（契约 §7.3）

`agent_progress`（生命周期/阶段）与 `agent_activity`（具体动作）是两条正交通道：既有 `App.tsx:145-153` 与 `WriterResult.tsx:14` 读 `agent_progress`；**rail 只读 `agent_activity`**。MUST NOT 用 `world_event` 猜"工具已开始"（`file_changed`/`world_event` 有 debounce/尾读延迟，契约 §7.3 明文）。

### 冲突 1（已裁定）：角色 turn 聚合采用 `CharacterTurnBuffer`

共同契约 §4 的可测性约束与 `01 §3.2` 已冻结唯一纯函数形态：`apps/web/src/components/overlay/dialogue-pages.ts`（或同批回写拆出的 `character-turn.ts`）导出 `createCharacterTurn()`、`consumeCharacterFrame(buffer, frame)`、`resetCharacterTurn()`，以 `messages[] + openDelta + ended` 承载多 assistant message 和末尾 delta。04 不再提出单字符串 `mergeTurnMessages` 方案；CM1–CM5 均直接针对该 projection 断言，React 组件只负责投影页面。

### 冲突 2（已裁定）：异常括号 fail-closed


契约 §5.3 现已冻结为 fail-closed：单侧括号（只有开 / 只有闭）、交叉结构、无法闭合、跨行未闭合 → **统一返回空串**；**不抛异常、不送厂商**；页面保留原文，前端跳过 TTS，走既有无语音 stinger 语义。

因此 §4.4 的 T8/T9/T10b 全部落笔（不再「未定」），`sanitiseTtsText` 签名确定为 `(raw: string) => string`——**空串是合法返回值，不是错误信号**。配对嵌套（T10）、跨行但成对（T9b）、连续（T11）、空括号（T12）仍走移除。

**留给实现的边界（无歧义）**：`''` 在服务端 → 400 `invalid_argument`（契约 §5.1 既有语义）；在前端 → 跳过请求。**两端对 `''` 的处置必须一致**，测试 H3 与 V7 成对锁定。

### 冲突 3（**已裁定**，2026-09-13 主 agent）：`SILENCE_LINE` 接受静音，不做豁免

`CharacterModal.tsx:74-77` 两条（`[emo: sad] (She does not answer right now.)` / `[emo: sad] （今は、答えが返ってこない。）`）清洗后均为 `''`。
