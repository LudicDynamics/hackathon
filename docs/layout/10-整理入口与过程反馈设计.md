## 1. 一句话定位

**让玩家从左侧画布工具栏发起一次可追踪的「整理当前层」请求，并看到由真实接线驱动的 `accepted → processing → arranging → verifying → landed/completed` 及 `failed/conflict/cancelled` 状态；按钮点击只表示请求被接受，不表示坐标已写入或验证完成。**

这是玩家明确授权的整体动作：独立于 Writer、不能伪装 Writer turn；不写世界正文；不在浏览器计算坐标；不把一个 activity 胶囊或 HTTP 200 当作完成。

## 4. 主动作与辅助路径

### 4.1 左侧主动作

在 `App.tsx:1023-1027` 的 `.prototype-tools` 中新增带图标和可见文字的 `CanvasArrangeControl`：

- visible label：`Arrange canvas`；
- `title`：`Arrange the current layer`；
- `aria-label`：`Arrange the current layer`；
- `aria-keyshortcuts="Shift+R"`；
- `data-testid="canvas-arrange-control"`；
- 未终态时禁用重复提交，但取消是独立、可聚焦的 button；
- 状态在 control 下方/关联 region 显示，不将“accepted”替换成 “Done”。

整理与 Explore、God Hand、Return to scene 是四种意图。不得用 `attention === 'authoring'` 作为整理权限或 Chalk 权限。

### 4.2 键盘、触控和辅助技术

1. Tab 可聚焦到按钮；读屏读到 `Arrange the current layer (Shift+R)`；
2. 原生 button 的 Enter/Space 与鼠标同源，不自写按键模拟；
3. 非输入控件、无更高层 modal/nook/shelf 焦点时，`Shift+R` 调同一个 `requestArrange()`；
4. immersive 时 `Shift+R` 必须先显示 interface 后再执行，或播报 `Show the interface with Tab before arranging the canvas.`，二者由评审冻结其一；
5. 输入框/textarea/select/button/contenteditable 中 Shift+R 不提交整理；Writer 的 Enter 仍保留；
6. Escape 只在整理 control 成为当前 focus owner 时请求取消，否则保留 App 已有 modal/shelf/journal/layer 返回语义；
7. 触控只使用单击，不新增长按/双击；
8. 状态文本、focus ring、disabled 状态均可被辅助技术读取；动画、截图缩略图、颜色不是唯一状态来源。

## 5. HTTP、身份和 output 接线

### 5.1 请求（依 B 的运行时设计）

B 已提出唯一入口：`POST /api/canvas/arrange`，请求体如下。D 只按最终评审冻结的字段发送：

```json
{
  "world": "<active world id or root>",
  "layer": "<current layer>",
  "requestId": "<client UUID>",
  "expectedRevision": 17,
  "screenshot": true
}
```

```ts
// NEW — apps/web/src/lib/airp-gateway.ts
export interface CanvasArrangeRequest {
  world: string;
  layer: string;
  requestId?: string;
  expectedRevision?: number;
  screenshot?: boolean;
}

// NEW — apps/web/src/lib/airp-gateway.ts
export interface CanvasArrangeAccepted {
  accepted: true;
  operationId: string;
  agentId: 'canvas-arranger';
  turnId: string; // functional:canvas-arranger:<uuid>
  layer: string;
  stage: 'accepted';
}

// NEW — apps/web/src/lib/airp-gateway.ts
export function arrangeCanvas(
  input: CanvasArrangeRequest,
): Promise<CanvasArrangeAccepted>;
```

gateway 方法必须调用已有私有 `request<T>`。`requestId` 是浏览器一次点击的身份；`operationId` 是服务端 operation；`turnId` 是本次 functional turn，三者不能互换。`agentId` 必须逐字为 `canvas-arranger`。`world` 的具体取值（manifest id/root）仍交评审，不得由 D 猜。

HTTP 200/`accepted:true` 仅代表已登记，不能显示完成；accepted 后本地阶段至少为 `accepted`，再由唯一映射转 `processing`。

### 5.2 取消

```ts
// NEW — apps/web/src/lib/airp-gateway.ts
export interface CanvasArrangeCancelAccepted {
  ok: true;
  operationId: string;
  stage: 'cancel_requested' | 'already_completed' | 'already_cancelled';
}

// NEW — apps/web/src/lib/airp-gateway.ts
export function cancelCanvasArrangement(
  operationId: string,
  world: string,
  layer: string,
): Promise<CanvasArrangeCancelAccepted>;
```

请求：`POST /api/canvas/arrange/:operationId/cancel`，body `{ "world": "...", "layer": "..." }`。cancel response 只表示“请求取消”；收到 functional terminal 和事务回滚/部分提交结果后，才显示 `cancelled`。若已提交，坐标事实保留并 refresh；不能声称回滚全部。

### 5.3 错误与 output

沿用 `{ok:false, code, error}`；首层只显示安全原因与下一步：

- `in_progress`（409）：若带已有 `operationId` 且 world/layer 相同，绑定并展示已有进度，不双开；
- `revision_conflict`：进入本地 `conflict`（不是 failed/cancelled），显示 `The canvas changed while arranging. Refresh, then retry.`；
- `writer_busy`：`The writer is working. Arrange the canvas after it finishes.`；
- `screenshot_unavailable`：`Could not inspect the canvas. Nothing was changed. Try again.`；
- `connection_lost`/`timeout`：`Connection lost while arranging. Refresh to check the saved canvas, then retry.`；
- 未知 role/Actor/权限失败：`Canvas arrangement is unavailable. Nothing was changed. Try again later.`，fail-closed。

不把原始 JSON、堆栈、绝对路径、prompt、内部坐标、模型文本放首层。可展开详情才显示安全 `code`、duration、changed count、verified、screenshot 枚举。

### 5.4 完成 proof

`agent_activity {phase:'completed', operation:'edit'}` 只封口具体工具动作，不是整体完成 proof。只有服务端统一碰撞求解/全层 AABB 校验已经针对最新结构化 rows 证明无重叠、版本未变化，且 D 已从同层 `refresh()` 读回结果后，才允许 `landed/completed`。Nodesign 的“读—截图—写”或模型返回坐标只能作为流程纪律，不能替代这一 proof。

## 6. 本地展示态与唯一映射

### 6.1 NEW 类型

```ts
// NEW — apps/web/src/state/useCanvasArrange.ts
export type CanvasArrangePhase =
  | 'idle'
  | 'accepted'
  | 'processing'
  | 'arranging'
  | 'verifying'
  | 'landed'
  | 'completed'
  | 'failed'
  | 'conflict'
  | 'cancelled';

// NEW — apps/web/src/state/useCanvasArrange.ts
export interface CanvasArrangeSnapshot {
  phase: CanvasArrangePhase;
  world: string | null;
  layer: string | null;
  requestId: string | null;
  operationId: string | null;
  agentId: 'canvas-arranger' | null;
  turnId: string | null;
  reason?: string;
  changedCards?: number;
  verified?: boolean;
  screenshot?: 'confirmed' | 'unavailable' | 'not_requested';
}
```

这些 phase 只属于 D 的本地请求展示态；不扩写 `agent_activity.phase`。`landed` 只在服务端已提交且 `canvas_patched`/refresh 已确认坐标到达、但最终结构化/真实绘制复核尚未完成时使用；`completed` 必须在最终验证闭环后使用。

### 6.2 唯一映射表

| 触发事实 | 本地态 | 首层英文文案 | 漏掉会怎样 |
|---|---|---|---|
| click/Enter/Space/Shift+R 通过前置检查 | `accepted` | `Arrange request accepted. Checking the current layer…` | 玩家重复点击或把点击当完成 |
| POST ack 返回 accepted，建立 operation identity | `processing` | `Reading the current canvas…` | 200 被误报为已整理 |
| matching functional activity `started` + operation `look/read` | `processing` | `Reading the current canvas…` | 看不见真实读取阶段 |
| matching functional activity `started` + operation `edit` | `arranging` | `Arranging cards on this layer…` | 写入阶段不可见 |
| edit terminal 后同层 patch/服务端写入确认，开始 refresh | `verifying` | `Checking the saved positions…` | patch 到达即假装完成 |
| 已提交坐标由同层 refresh 读回，等待最终 proof | `landed` | `Positions saved. Confirming the final layout…` | 玩家不知道已提交但仍在验证 |
| refresh 成功且服务端 proof 表示无重叠、版本一致、截图结果可诚实表达 | `completed` | `Canvas arranged. The current layer has been refreshed.` | 完成没有真实重读依据 |
| functional failed/timeout/screenshot/permission error | `failed` | `Canvas arrangement failed: {reason}. Refresh, then retry.` | 只 console.warn，玩家无法恢复 |
| 并发/版本变化/无法证明最新 rows | `conflict` | `The canvas changed while arranging. Refresh, then retry.` | 压成 failed 会掩盖“状态未知”，玩家可能错误重试或覆盖最新事实 |
| cancel 后确认未提交回滚 | `cancelled` | `Arrangement cancelled before positions were saved. Nothing changed.` | 一按 cancel 就谎称停止 |
| cancel 后确认部分提交 | `cancelled` | `Some cards were already arranged before cancellation. Refresh to see them.` | 已提交事实丢失或被误回滚 |

`processing → arranging → verifying → landed/completed` 不能靠时间、spawn 回调或 rail 胶囊猜测；每次转移都必须由该表唯一映射。并发/版本/无法证明最新状态必须进入独立 `conflict`，不能压成 failed 或 cancelled。activity `completed` 只封口具体工具动作，不等于总体 completed。

### 6.3 状态吸收与重复

- 未终态重复 click/Shift+R 不生成新 requestId；聚焦已有状态；
- terminal 吸收迟到 activity，不能回退；
- terminal 后新请求生成新 requestId；不能复用旧 operation/turn；
- no-op 也必须有 functional terminal 和 refresh/verification，不得永久停在 arranging；
- 不能以“最后一条 functional activity”猜 operation。优先 `operationId`；若既有 activity 不带 operationId，只允许在同层单飞下用 `agentId + turnId + 当前 layer` 关联，并由 E 覆盖断线/乱序。

### 6.4 行为步骤（每步漏项后果）

1. **检查作用域**：确认 `worldReady`、当前 world/layer、无更高层 modal、Writer 未忙；生成一次 `requestId`。  
   *漏掉*：请求可能写入空世界/错误层，或输入框快捷键误发整理。
2. **提交接受请求**：通过 gateway 的 `request<T>` 发唯一 POST，保存 server 返回的 `operationId/turnId`。  
   *漏掉*：App 直接 fetch 会产生第二套错误处理，或无法取消/去重。
3. **显示 accepted**：只显示“请求已接受，正在检查当前层”，控制仍可取消但不能重复提交。  
   *漏掉*：HTTP 200 被读成完成，玩家会在 Agent 尚未读取时继续触发第二次整理。
4. **接收 processing 证据**：只把匹配 `agentId='canvas-arranger'`、`turnId` 的 functional `look/read` started 映射为 processing。  
   *漏掉*：任意 functional/initializer 胶囊都可能冒领本次整理，或 spawn 被误报为完成。
5. **接收 arranging 证据**：同一 operation 的 functional `edit` started 才进入 arranging；不由计时器或模型文本猜测。  
   *漏掉*：按钮会在真正写入前显示错误阶段，且 activity phase 被污染。
6. **接收写入信号**：同层 `canvas_patched` 只由 `useWorld` 合并，随后 controller 进入 verifying；错层帧不改变本地状态。  
   *漏掉*：旧层坐标可能污染当前层，或 patch 到达即被错误宣布完成。
7. **刷新真实状态**：调用现有 `refresh()`，等待 `reqSeqRef` 选择的当前层 response；前端不重算坐标。  
   *漏掉*：UI 只显示 optimistic state，刷新后跳回旧位置，无法证明落盘。
8. **确认 landed/completed**：仅当最新结构化 rows 的服务端全层碰撞/版本 proof 通过时显示 landed，再完成最终 refresh 后显示 completed。  
   *漏掉*：模型返回坐标、文件存在或单个动作成功会被冒充为安全布局。
9. **收束失败/冲突/取消**：将 terminal reason 映射为 failed/conflict/cancelled，显示回滚、状态未知或部分提交事实，并提供 retry/refresh。
   *漏掉*：把“无法证明最新”当普通失败会让玩家误以为可以立即重试，可能覆盖另一写入。
10. **失效旧身份**：切层/切世界/卸载时令旧 operation 失效并请求取消；迟到 activity/patch 只可入 rail，不得改新层控制。  
    *漏掉*：旧异步 continuation 会串到新世界，造成错误状态和错误操作。

## 7. functional activity 和 WS 接线

### 7.1 不新增帧

**不新增帧名、不新增 WebSocket。** D 复用：

- `agent_activity`：既有 `started | completed | failed`，进入全局 `<ActivityRail surface="rail" />`；
- `canvas_patched`：既有同层 cards 增量，仍由 `useWorld` 合并；
- `world_event`：不新增 arranged 事件；真实坐标仍是 `canvas.db` 当前值。

`agent_progress` 是既有生命周期帧；D 不自行把 accepted 等本地态塞入该帧，也不新增 functional frame。如果 B 认为必须加 operation 字段，必须先同批更新发射、`useWorld` 唯一消费点、`docs/tools/12` 与 check:ws；不能留死监听。

### 7.2 rail 与控制区双投影

rail 示例（严格使用 `apps/web/src/lib/agent-activity.ts:409-451` 的白名单）：

```text
Reading the current canvas…
Editing the canvas…
Edited the canvas
```

## 9. 并发、取消、切层/切世界、性能和失败

点击前 `writerLocked` 为真时 disabled，说明 Writer 忙；不发送 `writer_abort`。已接受整理不因 Writer 后来启动而自动打断 Writer；由服务端 functional Actor/Scope、版本/按层锁裁决。并发/版本无法证明最新时进入独立 `conflict`，不压成 failed/cancelled；不吞掉玩家位置。
状态反馈不引入新的 depth 数值、遮罩 token 或 z-index 合约；若确需视觉强调，沿用现有 `--depth-modal` 系列和 shell 层级，由 monitor 的 `tools/ux-contract.json` 约束。


### 9.2 拖拽、footprint、生成

整理 control 锁定重复整理，但不私自禁用 Canvas 原有阅读/拖拽；服务端必须以版本/事务处理竞争。footprint、新卡 `file_changed` 或别的 `canvas_patched` 不得被 active operation 冒领。前端不根据 `reqSeqRef`、HTTP 到达顺序或本地 optimistic state 判断成功。

### 9.3 切层

`enterLayer` 成功后，旧 operation 失去当前 layer 作用域；若有 cancel endpoint 则请求取消。旧 activity/patch 只进入 rail 或被 layer guard 丢弃，不能改变新层 control。切回原层不自动恢复，除非 B 提供可核验只读状态；否则用户重新发起。

### 9.4 切世界

`loadWorld` 起始失效并取消旧 operation，清除本地 control snapshot；旧 world activity 不成为新世界事实。`airp:world-unavailable` 已由 `useWorld` 清理 state (`:164-177`)，D 不阻止。新世界不自动重试。

### 9.5 取消

cancel button/Escape 只发一次 cancel POST，先显示 `Cancellation requested…`。事务未提交时显示 nothing changed；已提交时保留坐标、refresh 并显示部分完成。late completion 不能将 cancelled 改回 arranging；若服务端已 complete，保持 completed 并显示 already complete。

### 9.6 断线/超时/刷新

未取得 operationId 的 POST 断线可 retry；已取得 operationId 不自动重发，显示 refresh/check/retry。activity 丢失不能直接推断 failed 或 completed；若无法证明最新状态，不能显示完成。浏览器刷新后没有 status API 时回到 idle，让用户明确 retry，不声称旧 operation 状态。

### 9.7 截图失败

C 的截图来自用户同一画布路径，失败必须可见。`screenshot:true` 失败且服务端不能提供独立结构化 proof 时进入 failed，显示 `Could not inspect the canvas. Nothing was changed. Try again.`。若评审允许结构化 proof 成功但截图不可用，必须使用独立 `screenshot:'unavailable'` 文案：`Canvas arranged from saved card measurements; visual inspection was unavailable.`，绝不说“画面已确认”。retry 使用新 requestId。

### 9.8 低性能

hidden、reduced motion、effects off、窄屏均保留文本状态和按钮。可展示 `The canvas is taking longer than expected. Keep waiting or cancel.`，但不得用动画计时把 processing 改 completed；activity timer 仍沿用 `ACTIVITY_*` 冻结常量。
