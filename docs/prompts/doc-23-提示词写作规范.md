# doc-23 提示词写作规范：把提示词当文档维护

> 状态：**定案（2026-09-12 立项）**。起因：读 Nodesign 的 `server/engine/agent/prompts/nodesign-prelude.md`（762 行 / 62KB，常驻注入）+ `prompts/tools/` 下 9 份懒加载细则，发现它的质量差距不在"写得漂亮"，而在**它是被当作一份随开发维护的文档在写的**。
> 关联：doc-12（作家提示词**写什么**——本文管**怎么写**）、doc-22（每轮注入什么）、doc-21（事件段的内容）、doc-11（preset 装配）、`AGENTS.md` §7.3（写 preset 前先扫上游文档）/ §7.4（preset 格式铁律）。
> 参考实现：`~/projects/Nodesign/server/engine/agent/prompts/`（本文所有引文出自这里）。

## 0. 一句话

**提示词不是许愿，是文档。**我们觉得 agent 应该这么做，不等于它知道该这么做——流程要写全、坑要写明、后果要写实，并且像文档一样随开发同步维护。

---

## 1. 这条规范要治的病

我们目前的 preset 写法（doc-05 §4.2 那份骨架）典型长这样：

```
## 叙事规则
- 诚实：没验证就明说，不假装 OK
- 细节质感：铺"沉默细节"
- 懒加载调度：进入新区域→委托生成
```

每一条都对，每一条 agent 都执行不了。"细节质感"是形容词不是判据；"进入新区域→委托生成"没说**什么算新区域**、**委托谁**、**委托失败怎么办**、**委托期间玩家在等什么**。写的人心里有一整套流程，纸面上只落了标题。

Nodesign 同一件事的写法（`nodesign-prelude.md:422`，铸角色）：

> 上场两步，**同一回合内做完，不用等**：
> 1. `cast_role` 登卡（写 `角色/<名>/角色卡.md` + 登记展示名 —— 板上署名要靠它）。
> 2. 立刻 `Agent(subagent_type: "rp-actor", name: "rp-<id>", prompt: ...)` —— prompt 第一行写卡路径，然后贴**卡的全文** + 这一场的开场指令（从哪一拍接、跟谁对戏、演完这拍是候场还是收场）。
>
> ⛔ 别用普通子代理演角色 —— 一次性的，演完就没了。
> **绝不重派同一个名字** —— 重派会新起一个失忆的同名角色顶掉旧的，演过的剧情全部失联。

差别不是详略，是**它把"做完之后会发生什么"也写进去了**。

## 2. 九条写法（从 Nodesign prelude 提炼，每条带原文证据）

### 2.1 每条规则都跟一个"为什么"，而且是机制性的

> **你的笔只有旁白这一支**……理由很实在：你的上下文里装着整个平台的工具和协议，角色子代理的上下文里只有"它是谁" —— 深度扮演天生是它的主场，你亲自下场演反而是折损。（`:400`）

理由不是为了礼貌，是为了**让 agent 在规则没覆盖到的新情形里能自己推**。只给结论的规则一遇到边界就会被绕过去；给了机制的规则，agent 会自己算出边界在哪。

⛔ 反面："请扮演好导演角色。"——没有可推理的内容。

### 2.2 坑要写成"后果"，不是"注意"

> ⚠️ npm 在装不进的路径下会**返回 0 但什么都没装**，装完 `ls node_modules/包名` 确认一眼再 require。（`:60`）

> 后台进程会静默继承当时的 cwd，而 playwright 的 goto 对 404 不抛错 —— 有人因此量出一组"60fps 零掉帧"的漂亮数字，测的其实是 404 页面，重测真实页面是 63% 掉帧。**看起来完全成功的无效测量**最贵。（`:333`）

第二段是整份 prelude 最值得学的一段：它讲了一个**具体事故**，连数字都留着。agent 读到"63% 掉帧"会真的去 `pwd`；读到"注意工作目录可能变化"不会。

**判据：每个坑都要能回答"不照做会看到什么现象"。**答不上来的，说明我们自己也没踩过，那就先别写进去占地方。

### 2.3 给判据，不给形容词

> **判据**：有名字的、会再出现的、用户会想单独跟他说话的，铸角色；一句话的过场，旁白带过。（`:417`）

> 动笔前问一句：这段话里有几成字是在描述关系？超过一半，它就该是一张图，不是一段文。（`:201`）

判据的形状是**可当场自问自答的一句话**。"重要的角色要铸卡"不是判据，因为"重要"要再判一次。

### 2.4 流程写成编号步骤，每步带上"漏了会怎样"

DirectEdit 那节（`:303`）是五步 + 每步的失败模式：

> 4. 处理完调 `clear_pending_changes`，不清下轮会重复处理一遍。

> **pending-move / pending-style / pending-delete 是结构化操作意图**……用户已经在画布上看到视觉结果但源码没动，你必须真的落进文件，否则下次 reload 视觉跳回，他会觉得白拖了。

"他会觉得白拖了"——把后果写到**用户的体感**那一层，而不是停在"数据不一致"。

### 2.5 点名"最容易漏的那一条"

> **演完一拍调 `await_user` 候场。** ⚠️ 开场指令里这条最容易漏，漏了整套就散了：角色不挂着，用户的话只能积压送不到它手里。（`:441`）

这句话只有**维护过**这份提示词的人写得出来——它是统计出来的，不是设计出来的。所以它也是本文核心主张的证据：提示词的质量来自迭代，不来自初稿。

### 2.6 给默认动作 + 例外，别罗列可能性

> **还是模板 / 没有真内容 → Write 整文件**……**已经有真内容 → Edit 短 diff**。迭代阶段 Write 整文件会冲掉用户 DirectEdit 的并发改动。（`:325`）

agent 面对"你可以 A 也可以 B"时会随机挑，面对"默认 A，遇到 X 才 B"时会稳定。**能给默认值的地方一律给默认值。**

### 2.7 "不做"也要写成合法输出

> **轮到你但角色此刻真的无话** → `pass_turn` 跳过这一拍，沉默也是表演。（`:441`）
> 连着两次等空会被劝散场 —— **角色自己散场不是事故**。（`:441`）
> **没验证就明说没验证**，不要说"应该没问题"。看不出来也直说"我看着差点意思但说不清，想听你的反馈"。（`:342`）

不写这一条，agent 就会为了交差而编。这对 AIRP 尤其要命——doc-12 #6 里"世界无变化，**不要为了填空而写**"就是这一条的 AIRP 版，它必须和"下一步指引"写在一起，否则指引本身会变成逼它硬写的压力。

### 2.8 说清哪些事**不归这份提示词管**，以及去哪找

> 工具用法不在这里教：胖工具（生图 / DirectEdit 细则 / 技术参考）在你第一次用到时由系统注入。（`:14`）
> 设计怎么做由 skill 讲（deck 看 `deskskill-engine-mini`……你自己判断何时 `Skill` 加载）。（`:5`）

于是形成两层：**常驻层写平台事实与硬约束**（762 行但每行都是每轮都要成立的东西），**细则层懒加载**（`prompts/tools/` 下 9 份，如 `direct-edit-protocol.md` 开篇即写「prelude 常驻部分只教流程骨架（get → 处理 → clear → 收尾总结）；本文是每类 pending change 的完整处理细则，agent 第一次调 get_pending_changes 时注入」）。

这与 doc-22 §7「注入摘要，细节走工具」、pi-rp Agent Skills 的 progressive disclosure 是同一条原则。**常驻层不怕长，怕含糊；胖细则不怕胖，怕常驻。**

### 2.9 重复的规则只写一遍，别处指路

> **触发时机在上一节**：不是每次收尾的默认动作，是"自检两轮用户还不满意"时请的外援。（`:357`）

同一条纪律在两个地方写两遍，改的时候必然只改一处，于是提示词开始自相矛盾——agent 遇到矛盾的表现是**两条都不执行**。

## 3. AIRP 的落点

### 3.1 平台侧提示词正文在 `extensions/instructions.ts`，不在 preset JSON 里

这是**唯一的编辑入口**，写之前先认清楚（`apps/server/src/engine/presets.ts::extensionArgs` 把 `extensions/*.ts` 直接当 `--extension` 交给 pi-rp，**没有构建步骤**，改完重启服务即生效）：

| 谁 | 提示词正文在哪 | 现状 |
|---|---|---|
| 作家 | `extensions/instructions.ts` 的 `WRITER_INSTRUCTION`（slot `writer-char`，别名 `writer-instruction`） | 6 条，标题清单式 |
| 角色 | 同文件 `CHARACTER_INSTRUCTION`（slot `system-char`，别名 `char-instruction`） | 5 条 |
| 场景初始化器 | 同文件 `SCENE_INIT_INSTRUCTION`（slot `scene-init-instruction`） | 交付物 3 条 + 纪律 5 条 + 三行回报 |
| 小天地初始化器 | 同文件 `NOOK_INIT_INSTRUCTION`（slot `nook-init-instruction`） | 纪律 6 条 + 三行回报 |

`presets/*.json` 与世界侧的 `.airpworld/prompt-presets/*.json`、`characters/<名>/preset.json` **只是装配单**：一条 `{"kind":"slot","slot":"system-char"}` 把平台正文引进来，其余是世界/角色自己的 `file` 槽（`identity.md` / `personality.md`……）。**所以平台口径改一处，全世界全角色跟着变，不需要逐个 preset 维护**——这也是 §4 那条"改了能力就同 commit 改提示词"能真正执行的前提：它本来就是一个 TypeScript 源文件，跟代码同仓、同 diff、同 review。

⚠️ **别在模板的 preset JSON 里另抄一份平台口径**。抄了就变成 §2.9 说的"同一条纪律写两遍"，而且是**跨 N 个世界模板的两遍**，必然改一处漏 N-1 处。世界侧 preset 只放属于那个世界/那个角色的东西。

### 3.2 四份正文按本文要改什么

| 常量 | 重点 |
|---|---|
| `WRITER_INSTRUCTION` | 现在的「Single-Turn Pipeline Discipline」是六个标题（Focus / Land / Inject / Dice / Evolve / Communicate）。按 §2.4 展开成**每步 + 漏了会怎样**；第 4 条骰子协议已经有 §2.7 的味道（"Never pre-write result"），把这种写法推广到其余五条；再补 §2.7 的"世界无变化不要为填空而写"出口 |
| `CHARACTER_INSTRUCTION` | 角色不知道自己该干什么是最常见的卡壳（doc-12 #6）。要写清：你被打开时手上已经有什么（doc-22 的 4 节状态块）、想知道更多用哪个工具、什么时候该闭嘴。现在第 3 条"Scene awareness"是纯形容词，要换成判据 |
| `SCENE_INIT_INSTRUCTION` / `NOOK_INIT_INSTRUCTION` | 两份已经是四份里写得最好的（有交付物清单、有三行回报格式、`NOOK` 第 1 条"a chair repaired three times, not he is nostalgic"正是 §2.3 的判据写法）。缺的是 §2.8：**明写"你看不见作家的对话历史"**（Nodesign `:357` 的派遣纪律），以及委托失败时怎么回话 |
| skill 文件 | 作家的剧情与手艺走 skill（doc-05 §4.1），同样适用本文九条 |

**另**：`writer-char`/`writer-instruction`、`system-char`/`char-instruction` 是两对同渲染的别名。别名本身无害，但**新写的 preset 一律用前者**（AGENTS.md §7.4 与 doc-05 §5.1 的示例都用前者），别让两个名字在模板里各占一半。

### 3.3 分工

本文管**怎么写**（文风与结构），doc-12 管**作家写什么**（内容清单），doc-22 管**每轮注入什么**（运行时装配），`AGENTS.md` §7.4 管**preset JSON 的语法铁律**。四者不重叠。

## 4. 维护纪律：提示词是代码的一部分

这是用户立本专题时的原话——**"写提示词本质上相当于维护文档，并且也需要像维护文档一样随着开发而维护"**。落成四条：

1. **提示词进版本库，与被它描述的代码同仓**。AIRP 这一条天然成立：平台口径就是 `extensions/instructions.ts` 里的四个导出常量（§3.1），本身是源码。不许出现"临时改一下 prompt 试试"的场外副本，也不许在世界模板的 preset JSON 里另抄一份平台口径。
2. **改了能力就同 commit 改提示词**——与 `AGENTS.md` §6.3 对文档的要求同级。加了工具而提示词没提，agent 不会用；删了工具而提示词还写着，agent 会去调一个不存在的东西然后卡住。**后者比前者更糟**。
3. **每次事故补一条，带现象**。§2.2 那两个例子都是事故的化石。AIRP 这边已经攒了几条可以直接入册的：`bash` 绕过事件表（doc-21 §2.2）、frontmatter 要在 Phase ② 写回而不是正文阶段（doc-07）、子代理看不见对话历史（doc-11）。
4. **提示词要有测试**。Nodesign 的 `prelude-render.test.js` 有三组断言，其中第三组是**新鲜度**——重跑变换函数与盘上文件对账，注释写明「防改 md 忘跑脚本」。AIRP 这边没有生成步骤（slot 直接 `render: () => WRITER_INSTRUCTION`），所以不需要新鲜度那一组；要的是另外两条：**每个 preset JSON 引用的 slot 名都真的注册过**（写错一个字 slot 静默渲染成空，agent 少一整段人格却不报错），以及 **`file` 槽指向的 md 都存在**（`onMissing:"skip"` 会把缺失吞掉，见 AGENTS.md §7.4 第 4 条）。**没测试的提示词会静默腐烂**，因为它坏了不报错，只是变笨。

## 5. 明确不做

- **不做提示词的 A/B 实验框架**。赛时规模不需要，凭具体失败案例改就够。
- **不追求"提示词写短"**。Nodesign 762 行常驻是有意的；我们要控的是**每轮注入块**（doc-22 有界），不是常驻协议。
- **不把本文的九条写进 preset 本身**给 agent 看——这是给人看的写作规范，agent 只该看到成品。

## 6. 留白

- **AIRP 版的"模式切片"**：Nodesign 用 `<!-- nd:mode:rp:start -->` 标记在同一份 md 里切设计/演出两套。AIRP 也会有作家/角色/初始化器共享的公共段，是走 pi-rp 的 slot 组合还是同款标记切片，等第一份 preset 写到一半再定。
- **语气**：Nodesign 用短句、第二人称、允许口语（"闭嘴。"）。AIRP 的作家 preset 面对的是叙事任务，语气是否照搬，写第一版时试。
