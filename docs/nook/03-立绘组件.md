## ① 一句话定位

**`portrait` 是小天地里一件「会动的陈设」：一张带 alpha 的静音 webm（`video:`），以一张静态立绘（`poster:`）为回退；它是一个新 kind，不是 `sprite` 的马甲。**

判据（契约 §3.5）：`sprite` 语义是「画布上的角色小像/占位」（`CanvasObject.tsx:46-67` 渲的是一张内联 SVG 头像 + 名牌），`portrait` 是「角色房间里的一个人形陈设」。两者的尺寸、形态、回退策略、性能约束都不同，合并会让 sprite 的头像语义被矩形视频污染。

### 1. 声明尺寸 `288×384`（3:4）与 `chrome: 'bare'`

**依据（实测，2026-09-13）**：

| 事实 | 证据 |
|---|---|
| 现有立绘素材全部 **1080×1440 = 3:4** | `ffprobe`：`templates/firstsnow/assets/characters/{nanami,sumi,director}.webp`、`templates/whitechapel/assets/characters/{holmes,watson}.webp` 一致 |
| 车间/世界侧的 `base.png` / `base-transparent.png` 亦 **1080×1440 或 1086×1448** | `assets/worlds/divergence-demo/characters/ryo/base.png` 实测 `1080,1440,rgb24`；`…/base-transparent.png` 实测 `1080,1440,rgba`；`assets/worlds/throne/characters/caogeng/base.png` 1086×1448 |
| 微动片实测尺寸是 360×640（**9:16，非 3:4**） | `assets/_inbox/motion-test/ryo-final.webm` / `ryo-tool.webm` 360×640；`ryo-alpha.webm` 720×1280；`portrait-motion.webm` 540×720（**这个是 3:4**） |

**裁决**：`w: 288, h: 384`，即 **3:4**（契约先行版 320×480 是 2:3，与素材实际比例不符 → 见 §⑪-2，已按主 agent 2026-09-13 定向补充改为 3:4 系）。

- **宽 288 的依据**：与周围卡同一量级——`board` 288（`forms.ts:92`）、`gate` 288（`:67`）、`thread` 300（`:95`）、`instrument` 320（`:91`）。288 恰好等于 `CARD_FORMS.board.w`，无需新造数字。
- **高 384 = 288 × 4/3**，不是拍脑袋：它是上面比例的机械结果。
- **为什么按素材比例而不是按 webm 比例**：`poster` 回退是**常态路径**（§④ 的四个触发条件里三个都会走到它），且素材比例是 3:4；若按 9:16 定框，静态回退会大留白。视频按 `object-fit: contain` 放进 3:4 框（§③-5），损失可接受。
- **`chrome: 'bare'` 的依据**：`chrome` 是**呈现层材质词汇**（`forms.ts:37-47`：`slab`=铁门/`board`=桌面/`panel`=仪表/`scroll`=卷轴…），非「有无边框」。立绘是**没有纸面的影像**（同 `chalk`/`sprite` 两个 `bare` 先例，`forms.ts:66/68`）；视频/图片自带边缘，再包一层 `paper` 会与 alpha 透明区打架（纸边落在透明区会显出一圈实色）。**`chrome` 的唯一消费点是 `chalkStyleOf` 的 `card: f.chrome === 'paper'`（`forms.ts:186`）+ `get_component` 的详情文本（`actions/component.ts:63`）——它进不了立绘分支的 CSS**，所以 `bare` 是零副作用的正确档位。

**漏了会怎样**：若把 `chrome` 写成 `paper`，`get_component` 详单会向模型宣称「立绘是纸卡」（语义谎言），且 `.portrait` 若要读 `data-chrome` 会被误判（本批不读，但记账错误已在工具面可见）。

### 2. `click` / `channels` / `secondLayer` / `movable` 的逐项论证

| 字段 | 取值 | 论证 |
|---|---|---|
| `click` | **`'look'`** | `ClickOutcome` 四级（`types.ts:19-20`）= `read` 开阅读 / `continue` 续写说话 / `visual` 视觉替应 / `look` 纯看。判据句是「点击后世界变不变」（`docs/tools/10:1076`）。立绘**点它什么都不该发生**：它没有第二层正文（`read` 错）、不向角色说话（`continue` 错）、不改 `status` 也不走 handler（`visual` 错）。**`look` 是唯一剩下的、也是唯一正确的**——「纯粹看着它」。<br>⚠️ `look` 在全仓**从未被任何 kind 使用过**（实测：16 个 `click` 值全是 `read`/`visual`），故它今天是「声明性档位」。前端今天不消费 `click`（grep 全仓无 `def.click` 的读取者，只有 `actions/component.ts:62` 的文本回显）→ **取值不影响渲染**，只影响 `get_component` 给模型的语义。这正是要把它填对的理由（模型据此知道「这东西点下去不会变世界」）。 |
| `channels` | **`{ status: true }`** | 契约反模式 6 说「全屏/多视频是合成负担」；`channels` 是「这个 kind 允许承载哪些通用互动字段」。立绘是陈设，**允许作家挂一个 `status` 快照**（「她正望着窗外」）是合理的、也是 `doc-09` 通用字段的本意；`choice`（要玩家选，立绘没有选项）、`rollDice`（掷骰，无检定语义）、`useItemTarget`（被 `use_item_on` 作用，立绘不被道具作用）都不该有。<br>对照：`thread`（同 pack）就是 `{ choice: true, status: true }`（`room.ts:40`）——**`status` 是 room pack 的标配，`choice` 不是**。本文比 `thread` 更窄（去掉 `choice`），因为「对一幅立绘做选择」没有产品语义。 |
| `secondLayer` | **`'none'`** | 七档（`types.ts:23-30`）全部是「第二层阅读的形态」（`read`=全文 / `read+continue`=全文+续写 footer / `fragments` / `pairs` / `pages` / `board`）。`click: 'look'` 的前提就是「不打开第二层」；给一个 `read` 会自相矛盾（`AGENTS §7.5` 第 5 条：第二层形态与单击语义必须自洽）。**`none` 与 `look` 是一对，必须同改**。 |
| `movable` | **`true`** | `ComponentDef.movable` 的注释逐字是「**Presentation-layer draggability only**」（`types.ts:86`）；`get_component` 回显为 `Movable: yes/no`（`actions/component.ts:63`）。**它不进任何引擎门禁**——实测 `not_movable` 错误的三个来源全是**路径级**判定（`actions/delete.ts:70-97` 拒 README/目录/世界外路径；`actions/move.ts:91-97` 同族），与 kind 无关。立绘是「小天地里的一件陈设」，玩家当然能挪它（契约判据：能在小天地里正常看卡/拖卡）→ **`true`**。`craft` pack 的两个 `movable: false`（`craft.ts:18/46`）是「钢琴/棋盘钉在地上」的语义，立绘不受此约束。 |

**漏了会怎样（逐项）**：`click` 写成 `visual` → 模型被告知「点亮栏会改世界」，与实现相反；`channels.choice` 误加 → `relatedOf`（`registry.ts:110-114`）会向模型推荐 `choose` 工具（推荐一个死路）；`secondLayer` 非 `none` → 前端若将来按它分派会尝试打开不存在的第二层；`movable: false` → 玩家拖不动立绘，直接违反本批判据。

### 3. `match` 判据：`fm.component === 'portrait'`（**只认 `component`，不认 `type`**）

**与 room pack 既有两条逐字同形**：`room.ts:10` `match: (fm) => fm.component === 'diary'`、`room.ts:35` `match: (fm) => fm.component === 'thread'`。

**为什么不接受 `type: portrait`**：

- 解析优先级（`registry.ts:72-74`）：`type: chalk` → `type: gate`/`README.md` → `type: sprite`/`type: character` → **然后才**遍历 `ALL` 的 `match`。`type: portrait` 不撞前三条，理论上能被 `match` 接住。
- 但**全仓没有 `type: <kind>` 的先例**（除历史遗留的 `note`/`letter`，它们是「`type: note` 早于 `type: component`」的兼容层——`components.ts:76-81` 逐字写明）。`docs/tools/10:657` 更是把口径钉死：*「**`type` 只有 `component`，kind 在 `component` 字段里**——不是 `type: lock`」*。
- **接受 `type: portrait` 会造第二个真相源**，且给模型两条路走 → 它可能两条都写，或只写错的。

**frontmatter 完整契约（MUST 逐字遵守）**：

```yaml
type: component          # MUST —— 缺了仍是 portrait（见下），但会脱离 Registry 口径
component: portrait      # MUST —— 唯一的 kind 身份来源；缺了 → 退化成 note
title: <string>          # MUST —— ComponentCoreSchema:69
video: <world-rel path>  # 强烈建议（本批唯一推荐形态）
poster: <world-rel path> # 可选；缺省走 §④ 的回退链
caption: <string>        # 可选
preview / body / age     # 可选，ComponentCoreSchema:70-72 提供，本分支不渲染
```

**「漏了 `component:` 会怎样」（主 agent 定向补充要求）**：`resolveComponentKind`（`registry.ts:67-79`）按 `ALL` 顺序试 `match`，`portrait` 的 `match` 只认 `fm.component === 'portrait'` → 不命中 → 继续试 `note`（`core.ts:87-91`：`fm.type === undefined && fm.component === undefined` 才命中）→ **也**不命中（因为 `type: component` 在）→ **兜底 `return 'note'`（`:79`）**。于是：

- 卡片被渲成**便签**（`.note`，`CardRenderer.tsx:267-291`），`video`/`poster` **完全不渲染**（`CardRenderer` 无任何 image/video 分支——实测 `grep "photo|image|img |api/asset"` 在该文件零命中）；
- `cardFormOf` 返回 `CARD_FORMS.note`（200×168，`forms.ts:73`）→ 占位尺寸也错 → 与 footprint 的「唯一真相」冲突（`AGENTS §7.5` 第 7 条）；
- **静默**：没有 throw、没有 console 警告。这是本 kind 最容易踩的坑。

**缓解措施（MUST 写进 `05`）**：`05` 需要一条断言「一张只写 `component: portrait` 的最小卡 → `cardKindOf` 返回 `'portrait'`」，以及一条**负例**「一张漏写 `component` 的卡 → 返回 `'note'`（证明它是静默降级而非报错）」。

**`example` 自检**：§②-2.1(4) 的 example 里 `type: component` + `component: portrait` 都在，`video`/`poster`/`caption` 均为**非空字符串**（避免 `stringifyFrontmatter` 往返时 `undefined` 键被丢弃造成 `deepEqual` 失败——`components.test.mjs:76-77`）。空值、`null`、注释行都不进 example。

### 6. 性能：同时播放 ≤ 1（`AGENTS §7.6` + 契约反模式 6）

// 输出「哪一条 path 可以播视频」。可单测，无 DOM 依赖。
export function portraitPlayStateOf(
  cards: { path: string; kind: string }[]
): { playing: string | null; still: Set<string> } {
  const portraits = cards.filter((c) => c.kind === 'portrait');
  const playing = portraits.length ? portraits[portraits.length - 1].path : null;  // 最大 z
  const still = new Set(portraits.filter((p) => p.path !== playing).map((p) => p.path));
  return { playing, still };
}

### 7. 尺寸契约：为什么 `portrait` 是「实测恒等于声明」的 kind

`footprint/00 §3.5` 要求前端测量 `.object` 的 `offsetHeight` 并 `POST /api/card/footprint` 回写。**`portrait` 不违例**——它只是**实测值恒等于声明值**：

- 外壳宽度 = `item.w`（行值，`CanvasObject.tsx:133`）；
- `.portrait__media` 的 `aspect-ratio: 3 / 4` 使内容高度 = 宽 × 4/3 **恒成立**，与视频是否加载、poster 是 3:4 还是 9:16 无关（两者都是 `position:absolute` + `object-fit`，不参与布局）；

**漏了会怎样**：(i) 下 caption 卡的实测高比声明高大 ~20px → 每加一行 caption 触发一次 `reseatLayer`（footprint `§5.1` 第 4 条：`row.h !== meta.seatH` → 重排）→ 玩家自己拖过的位置被冲掉（`AGENTS §7.5` 已警告过这个风险）。这在「作家顺手补一行说明」这种高频小改动上会反复发生。

**⚠️ 关键分歧（必须写清，否则实现会猜错）**：

- **`base.png` 系在 `assets/worlds/<world>/characters/<id>/`**（世界根的 `characters/` 子树）；
- **`assets/characters/<id>/*.webp` 系在 `templates/<world>/assets/characters/`**（世界根的 `assets/` 子树）。

契约 §5.4 的示例 `assets/characters/ryo/ryo.webm` 走的是**第二条**（`assets/` 子树）。而**现有立绘素材**在**第一条**（`characters/<id>/`）。**两者都对——世界根下有两个不同的目录树**，`/api/asset` 只要求路径相对世界根，不关心在哪棵子树。

**裁决（前端行为）**：**`poster:` 缺省时，前端 MUST NOT 自己拼 `base.png`/`base-transparent.png` 的路径。** 理由：

1. 前端**不知道**该角色目录里有什么文件（`/api/nook` 的 `items` 只回 md，契约 §5.1——`base.png` 不是 md，**不在 `items` 里**；`store.listFiles` 虽能列全，但契约把 `items` 限成 md）。
2. 「猜文件名」会造第二条真相源（契约反模式 2 的同族错误）：今天猜 `base-transparent.png`，明天创作者叫它 `still.png` 就静默失败。
3. 与 `avatar` 的既有口径冲突（`avatar` 是**显式**写在 README frontmatter / `world.json` 里的绝对 `/api/asset` URL，`routes/world.ts:541-553` 读它）——**从不猜**。

**因此 `poster` 缺省的实际行为 = 回退链 #2/#4/#6 的 `.portrait__missing` 铭牌**。而「想让静态立绘生效」的**唯一正确做法**是显式写 `poster:`。

**给创作者的推荐值（写进 `field.desc` 与文档，不是前端逻辑）**：

```yaml
# 本批 firstsnow/nanami 的实际取值（推荐范式）：
poster: assets/characters/nanami/nanami-poster.png
# 若无同源首帧，退而用既有立绘：
poster: characters/<id>/base-transparent.png   # 优先：真透明（实测 rgba），叠在纸面色上不显灰边
poster: characters/<id>/base.png               # 次之：不透明（实测 rgb24），会显出一个矩形底
```

**⭐ 本批新立的推荐：poster 从 webm 自身首帧导出。** 理由（比 `base-transparent.png` 更强）：**前后帧逐像素同源** → 视频加载失败时画面几乎不跳变（同一个人的同一瞬间，只是不动了），这是「回退」能做到的最无缝形态。一条命令：

```bash
ffmpeg -c:v libvpx-vp9 -i <id>.webm -frames:v 1 <id>-poster.png   # MUST 带 -c:v libvpx-vp9，否则 alpha 丢（SKILL.md:32-40）
```

**⚠️ 实测提醒**：`templates/firstsnow/assets/characters/nanami.webp`（既有 `avatar` 图）画的是**成年电台主播**，而本批的 webm 是**柜台前写作业的女孩**——**两者不是同一个人**。若拿它当 poster，视频一坏会从「小女孩」跳成「成年女性」，比空白更糟。**这是「poster 必须与视频形态同族」的实证**（见下段）。

**`base-transparent.png` 优先的依据**：`portrait` 的 `.portrait__media` **没有背景色**（§③-5 的 CSS 里 `.portrait` 与 `.portrait__media` 都不设 `background`），故不透明 PNG 的底色会直接暴露成矩形；而透明 PNG 让立绘像贴纸一样落在小天地的纸上——这正是 `motion-clip.mjs` 产出的 webm 的同一视觉目标（`SKILL.md:103`「带 alpha，像贴纸」）。**静态回退必须与视频的动态形态视觉同族**，否则「视频坏了」这件事会以最刺眼的方式暴露。

**⚠️ 与代码的对应**：上面的 `PortraitFig`（§③-4）**已按「`<video>` 与 `<img>` 二选一三元」写成**——`visible ? <video …/> : posterOk ? <img …/> : null`（不是「常驻 `<img>` + `(!loaded || !visible)`」的初稿）。故 #8 换图不留白，且前台**零冗余请求**。矩阵的行据此读作「#8 的 poster 由新建的 `<img>` 承载」；#8 与 #2/#4 的区别只在 `<video>` **是否会自己回来**（#8 会，#2/#4 不会）。

**若 `05` 要一条机械断言**：断言「不写 `poster:` 时渲染 `.portrait__missing`（**不是** `img`，**不是**静默空白）」。这条能防住「实现者自作聪明去拼 `base.png`」。

### 7.3 「失败可见」的硬要求（契约反模式 4 / `docs/tools/00` 硬约束 4）

**MUST NOT 只 `console.warn`。** 本设计给的可见性有三条腿：

1. **画面本身**：`.portrait__missing` 是一块**有边框、有角色名、有纸面渐变**的实心块——玩家一眼看出「这里本该有个人，但没有」。它**不是**空白框，也**不是** 0 高度的塌陷（`aspect-ratio` 保证框恒在）。
2. **`aria-label`**：`role="img"` + `aria-label={title}` → 读屏用户也能得到「这是谁的立绘，没加载出来」。
3. **`caption` 通路**：需要更明确的原因时，`caption` 是作家可控的一行文字（它渲染在框外，不受媒体失败影响）。

**MUST NOT**：把 `video` 的 404 静默吞掉——`onError={() => setFailedSrc(video!)}` 是**必需**的（没有它，浏览器会保留一个黑/空的 `<video>` 元素，视觉上比铭牌更糟，且**永远不会有任何提示**）。

### 冲突 11 — 验收断言必须显式指定解码器，否则会写出「假绿/假红」（**2026-09-13 实测，主 agent 广播**）

**事实**：`ffmpeg -i nanami.webm -frames:v 1 -pix_fmt rgba out.png`（默认解码）实测透明占比 **0.0%**；加 `-c:v libvpx-vp9` 后为 **25.4%**。对照组 `ryo-alpha.webm` 同样：默认 0.0% / 显式 26.4%。

**根因**：本机 webm 的 alpha 走「独立 alpha 平面 + `alpha_mode=1`」，**隐式解码路径不还原 alpha**。

**处置**：`packages/shared/test/nook-portrait.test.mjs` 的 `transparentRatio()` **MUST** 显式传 `-c:v libvpx-vp9` 解码 webm（测试注释已写死原因）；`poster` 是 PNG（alpha 在常规像素格式里），用默认解码器即可。**MUST NOT** 只读 `ffprobe` 的 `alpha_mode` tag 当透明度证明（SKILL.md 逐字警告）。任何其它切片（`02`/`05`）若在浏览器/探针里判「视频是否真透明」，同此规则。
