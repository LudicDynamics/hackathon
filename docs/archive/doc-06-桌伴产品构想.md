# 桌伴（Deskmate）产品构想

> 2026-08-30 初稿 | 基于明月与秋青子的讨论共识

---

## 1. 一句话定位

> **一个住在你电脑桌面上、会聊天、会记住你、还会把世界里的东西摆到你面前的 AI 伙伴。**

它不是工作助手（Nodesign 的定位），而是"桌面的伙伴"——工作的时候它陪着，休息的时候它陪你聊天，它记得你，它会主动把有用的/好看的东西摆到你的桌面上。

---

## 2. 产品灵魂：与 Nodesign 的分水岭

| 维度 | Nodesign | 桌伴 |
|---|---|---|
| 核心关系 | 工具人：你说需求→它干活 | 伙伴：它陪你，它记得你，它主动 |
| 用户角色 | 操作者/上帝 | 被陪伴的人 |
| Agent 输出 | 工作产物（站点/文档/幻灯） | 聊天+卡片+桌面内容+陪伴 |
| 画布意义 | 工作台 | 世界（桌面延伸） |
| 与用户的关系 | 用完即走 | 常驻后台，随时可聊 |
| 记忆系统 | 操作记录目录 | 关系型记忆：记得你这个人 |
| 桌面 | 只有窗口内的画布 | 桌面壁纸之上也是画布 |

**一句话分水岭**：Nodesign 是"你来找它干活"，桌伴是"它就在你身边"。

---

## 3. 核心体验

### 3.1 双形态：窗口 + 桌宠，随场景切换

- **窗口形态**：聊天窗、画布窗、设置——工作状态用的界面，和正常桌面应用一样
- **桌宠形态**：一个趴在桌面壁纸上的小精灵，无边框透明窗口，只渲染精灵本身，看起来像"活在桌面上"
- **切换逻辑**：工作状态用窗口，休息状态缩成桌宠。用户主动切换，也支持场景自动切换（比如检测到用户长时间没操作，自动缩成桌宠）

### 3.2 桌宠——桌面上的伙伴

- **视觉**：早期用简单图形占位（几何体/球/像素小动物），后面迭代到更丰富的视觉风格
- **行为**：有 idle 动画（趴着/打盹/东张西望），用户鼠标移过去会有反应（看过来/凑近/躲开）
- **交互**：点击桌宠→弹出聊天窗；拖拽可以移动它在桌面上的位置；右键有快捷菜单
- **穿越窗口**：桌宠窗口是置顶透明的，看起来像在壁纸之上、窗口之下（实际是透明窗口穿透鼠标事件到下层窗口，只在自己区域内响应点击）
- **常驻**：开机自启，系统托盘有图标，退出时提示"桌伴还在后台哦"

### 3.3 桌面画布——壁纸之上的第二层

- **透明叠加层**：一个全屏透明窗口，浮动在壁纸之上、图标之下（或桌面图标之上，看实现）
- **卡片系统**：伙伴和用户都可以往桌面上放卡片
  - 伙伴主动：根据对用户的了解，把有用的东西摆到桌面上（天气预报、日程提醒、觉得重要的事）
  - 用户主动：自己拖拽内容到桌面上（截图、笔记、文件快捷方式）
  - 双向同步：桌面上的卡片在画布窗口里也能看到和管理
- **交互**：拖拽排列、关闭、新卡片从边缘飞入
- **未来方向**：全面深度——文件、网页剪藏、截图识别、伙伴帮你整理桌面

### 3.4 聊天——不只是对话

- **日常聊天**：和伙伴聊天，像和朋友说话一样自然
- **上下文感知**：伙伴知道你在做什么（正在编辑什么文件、正在看什么网页），可以自然地聊相关话题
- **记忆支撑**：聊到过去的事，伙伴真的记得——"上次你说周末要去看电影，好看吗？"
- **多角色**：默认角色 + 可定制角色 + 多角色切换（记忆按角色隔离，但 general wiki 共享）

### 3.5 画布——世界的内容底座

- 继承 Nodesign 的无限画布设计思路（卡片=文件投影、路径即 id、真实文件双向同步）
- 但画布的内容不再是"工作产物"，而是"世界的内容"——伙伴的笔记、用户和伙伴的回忆、桌面卡片的源头
- 桌面画布 ←→ 窗口画布 双向同步：卡片的来源是画布，画布上的东西也可以搬到桌面

## 4. 架构设计

### 4.1 总体架构

```
┌──────────────────────────────────────────────────────┐
│  Electron 主进程（Node.js）                           │
│                                                       │
│  ├─ 窗口管理（多窗口调度）                              │
│  │   ├─ 聊天窗（正常 BrowserWindow）                   │
│  │   ├─ 画布窗（正常 BrowserWindow）                   │
│  │   ├─ 桌宠窗（透明 + 无边框 + 置顶 + 穿透）          │
│  │   └─ 桌面画布层（全屏透明 + 无边框 + 穿透）          │
│  │                                                       │
│  ├─ 系统能力                                          │
│  │   ├─ 系统托盘（常驻后台）                            │
│  │   ├─ 开机自启                                      │
│  │   ├─ 全局快捷键                                    │
│  │   └─ 文件系统访问（桌面卡片持久化）                  │
│  │                                                       │
│  └─ IPC 桥接（主进程 ↔ 渲染进程 + pi-rp + MCP）        │
│                                                       │
├──────────────────────────────────────────────────────┤
│  Electron 渲染进程（React/TypeScript）                │
│                                                       │
│  ├─ 桌宠精灵渲染（Canvas / SVG / Lottie）              │
│  ├─ 桌面卡片渲染（可拖拽、可关闭、可排列）              │
│  ├─ 聊天界面                                        │
│  ├─ 画布界面（继承 Nodesign 设计思路）                 │

│  ├─ subagent 委托                                    │
│  └─ 与 Electron 主进程通过 IPC 通信                   │
│                                                       │
├──────────────────────────────────────────────────────┤
│  nocturne_memory（MCP 服务，独立进程）                │
│                                                       │

│  ├─ 工作记忆（general wiki，共享）                    │
│  ├─ 多角色记忆隔离                                   │
│  └─ 跨产品记忆共享（MCP 协议）                        │

```

### 4.2 关于 Electron 为什么适合

| 顾虑 | 回应 |
|---|---|
| Electron 太重 | 桌伴是常驻后台应用，开机自启，内存占用不是用户感知痛点；Chromium 固定开销是逃不掉的 |
| 渲染效果 | 硬件加速 Canvas/WebGL + CSS 动画，桌宠精灵和桌面卡片的渲染上限极高 |
| 开发效率 | 明月熟悉的技术栈（React/TypeScript），快速出原型 |
| 系统集成 | 系统托盘、全局快捷键、透明窗口、穿透事件——这些 Electron 都有成熟的 API |
| pi-rp 集成 | pi-rp 本身就是 Node.js 进程，和 Electron 主进程天然一家人，IPC 通信零摩擦 |
| 记忆系统集成 | nocturne_memory 走 MCP 协议，HTTP 或 stdio 通信，Node.js 调用方便 |

### 4.3 桌宠窗口的技术关键

**透明窗口 + 事件穿透**是桌宠体验的核心：

- 桌宠窗口 = `BrowserWindow` 设置 `transparent: true` + `frame: false` + `alwaysOnTop: true`
- 窗口只渲染精灵本身，其余区域全透明
- 鼠标事件：精灵区域响应点击/拖拽，透明区域穿透到下层窗口
- 桌面画布层同理：全屏透明窗口，卡片区域响应交互，空白区域穿透

**穿越窗口效果**：桌宠窗口高度置顶但鼠标事件穿透，视觉上它就在所有窗口之上，但交互上不挡用户操作。

### 4.4 记忆系统结构

```
nocturne_memory
├── /general          ← 工作记忆，跨角色共享（用户偏好、习惯、常用设置）
├── /角色A/personal   ← 角色 A 对用户的记忆（专属回忆、关系深度）
├── /角色A/cards      ← 角色 A 放在桌面上的卡片
├── /角色B/personal   ← 角色 B 对用户的记忆（独立于角色 A）
└── /角色B/cards
```

- 记忆按角色隔离，但 general wiki 所有角色共享
- 工作记忆 = 关系型记忆的子集，一个 tag 区分
- 通过 MCP 协议，记忆系统可以跨产品使用（Nodesign 里聊过的事，回到桌伴还认得）

## 5. 第一阶段（桌宠形态 + 桌面画布）

### 5.1 目标

一个能跑的原型，核心体验闭环：

1. 一个 Electron 应用，开机自启，常驻系统托盘
2. 桌宠窗口：透明无边框，简单图形（球/几何体/像素小动物），有 idle 动画，鼠标移过去有反应
3. 桌面画布层：全屏透明，伙伴可以往上贴卡片，用户可以拖拽排列
4. 点击桌宠打开聊天窗（先用最简单的对话，记忆系统不在第一阶段核心流程里）
5. 画布窗口：简单的无限画布，卡片是文件投影

### 5.2 技术栈

| 层 | 技术 |
|---|---|
| 桌面壳 | Electron |
| 前端 | React + TypeScript |
| 桌宠渲染 | Canvas 2D / CSS 动画（初期占位图形） |
| 桌面卡片 | React 拖拽组件（react-dnd / dnd-kit） |
| Agent 引擎 | pi-rp（RPC 模式，子进程） |
| 持久化 | 本地 JSON 文件（初期）→ 后期接入 nocturne_memory |
| 窗口通信 | Electron IPC |

### 5.3 后续迭代方向

- **桌宠视觉升级**：从简单图形到更丰富的动画/风格
- **桌面画布深度**：全面交互（文件拖拽、网页剪藏、截图识别）
- **记忆系统接入**：nocturne_memory 上线，关系型记忆开始积累
- **多角色系统**：默认角色 + 可定制角色 + 多角色切换
- **跨产品记忆**：通过 MCP 协议，Nodesign 等产品共享记忆

## 6. 与 Nodesign 的关系

| 方面 | 关系 |
|---|---|
| 技术 | 不照搬 Nodesign 代码（AGPL-3.0），但**设计思路继承**：无限画布、卡片=文件投影、路径即 id、人话哲学、视点上报表 |
| Agent 引擎 | **复用 pi-rp**，这是明月自己维护的，不属于 Nodesign |
| 记忆系统 | **复用 nocturne_memory**，明月自己的 MCP 记忆系统 |
| 产品定位 | 完全不同的赛道：Nodesign 是创作工作台，桌伴是陪伴型桌面伙伴 |
| 生态关系 | 记忆系统跨产品共享，其他完全独立 |

## 7. 尚未决定的问题（开放讨论）

- 桌宠的默认角色设定（名字/性格/外观）——等视觉风格方向定了再细化
- 多角色系统上线后，用户如何切换角色、角色之间如何交互
- 桌面画布的深度迭代时间线
- 商业模式（桌面陪伴产品可能的付费模式：订阅/买断/角色皮肤内购）
- 跨产品记忆的具体实现路径（MCP 协议细节）
