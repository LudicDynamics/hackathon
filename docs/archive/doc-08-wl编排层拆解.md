> 附属文档：doc-05-AIRP产品构想.md（AIRP 设计）、doc-07-AIRP黑客松作战计划.md（执行计划）

> 素材来源：worldlines-rivet 源码走读（`launch.mjs` / `.pi/extensions/handoff.ts` / `pass-mic.ts` / `ip-context.ts` / `state-updater.ts`）+ 设计文档（`docs/ARCHITECTURE.md` / `docs/CO-CREATION.md` / `docs/archive/CROSS-SESSION-COORDINATION.md` / `wl-opening-choice-tree/docs/design/pass-mic-design.md`）
> 定位：wl 是明月自己的项目（无 AGPL 顾虑），它的**多 agent 编排层**实现是业界少见的高完成度参考。**2026-09-10 更新：AIRP 已砍掉世界内角色编排，不再需要 wl 的编排层**——本文的解读立场从"AIRP 多 agent 编排层蓝图"改为：
> 1. **wl 机制本身的分析存档**（它的设计思想对多 agent 产品仍有普遍参考价值）；
> 2. **AIRP 实际采用的子集**：懒加载 spawn、opening 播种、角色独立会话文件——这三个机制用于 AIRP 的**角色遮罩对话**（被点开时才 spawn 的独立进程），见 §10。
> **关键区分**：wl 的编排三件套（handoff / pass_mic / 单更新器）服务的是"多个角色在同一场戏里实时互动"；AIRP 砍掉了这个需求（叙事由作家一人写，角色只在遮罩里与玩家一对一），所以编排层整体不采用——**不是 wl 不好，是 AIRP 不需要这场戏**。

## 0. 一句话

wl 的编排层 = **一个作家主进程 + N 个懒加载的角色子进程**，通过三个原语运转：**handoff（递话筒）** 驱动角色回合、**pass_mic（传话筒）** 让角色主动发起对话、**共享状态文件**让世界状态在所有进程间流动。它的设计哲学是"共创"：**作家是 showrunner（编排 + 终审），角色是小作家（只写自己的反应与领地），信息不对称是作者权的自然产物，不是外部封锁**。

> ⚠️ AIRP 2026-09-10：这套"showrunner + 多角色共创"的架构，AIRP **完整不采用**。AIRP 的作家就是唯一的讲故事的人；角色是"被点开时才活过来的对话对象"。下文机制分析保留（值得读），§10 是 AIRP 的实际采用清单。

## 1. 进程拓扑：mode 三态 + 懒加载

### 1.1 mode 三态（进程架构的前提）

`ip.json.mode` 决定主进程是谁、handoff 是否存在：

| mode | 主进程 | 角色子进程 | handoff 工具 |
|---|---|---|---|
| `solo`（单角色直聊） | 恰一个角色预设 | 无 | 不注册（无旁白层，玩家输入直达角色） |
| `single-writer`（单作家） | 作家预设 | 无 | 不注册（无角色可递） |
| `multi`（多角色，默认） | 作家预设 | 有（懒加载 spawn） | 注册 |

**思路**：同一个引擎，靠配置（而不是代码）切出三种形态——"配置决定拓扑"是 wl 的工程手段，但**AIRP 不需要 mode 三态（2026-08-31 明月拍板）**：AIRP 直接就是 writer 主进程 + 角色子进程，没有 solo / single-writer / multi 的区分。玩家双模（角色/上帝）不是进程拓扑的切换，而是交互模式——上帝模式 = 玩家直接改世界文件，作家现编理由（或委托 subagent）。

### 1.2 角色进程：懒加载 spawn + 常驻复用

- 角色**首次被递话筒时才 spawn**（`getOrSpawnCharacter`），此后常驻（RpcClient 池复用）——"懒加载世界"的进程层实现；
- 每个角色有**独立会话文件**（`saves/<ip>/<save>/characters/<id>.jsonl`）——跨递话筒、跨续档的"记忆"就是它；
- spawn 参数（`launch.mjs` 的 `characterLaunch`，唯一事实源）：`--config-dir <ip> --preset <角色id> --schema world[,<id>] --strict --settings-file <save>/settings.json --session <角色会话文件> -e <角色扩展>`
- env 只加 `WL_PROCESS_ROLE=character:<id>`（其余继承主进程）；
- 角色预设 `tools: { deny: ["*"], allow: ["pass_mic"] }`——**纯发声，唯一工具是递话筒**。没有 handoff（防递归递话筒）、没有 choice、没有 state-updater。

**思路**：
1. **"角色 = 一个独立 pi 会话进程"**，不搞线程/daemon——进程即隔离，会话文件即记忆，重启不丢；
2. **懒加载**：只有剧情真的需要角色开口时才花进程成本——世界活性不靠常驻，靠按需唤醒；
3. **角色工具面最小化**：纯发声（chalk 对应 AIRP 的 chalk），一切编排权在作家。

> ⚠️ AIRP 注：spawn 参数里的 `--schema world[,<id>] --strict` 是 wl 的 state 门禁，**AIRP 没有 state、没有 schema 门禁**——spawn 参数简化为 `--config-dir <世界目录> --preset <角色id> --settings-file ... --session <角色会话> -e <角色扩展>`。角色知道什么 = 自己的 preset 引用哪些文件 + 遮罩 invoke 时注入的最近场景情况 + 自己手动 read_canvas/read。

### 1.3 作家主进程

- 主进程预设由 `autoActivate: true` 表达（pi-rp chooseDefaultPreset，不传 `--preset`）；
- 加载 `world + player + 全部角色` 的 state schema——**作家是全量视角**（2026-08-27 起"全量仪表盘"，此前对角色领地做过渲染过滤，已移除：作家看得到一切，纪律是揭晓节奏）；
- 作家没有任何 state 写工具（`tools.allow: [handoff, subagent, subagent_profiles]`）——**结构性无写路径**，状态演化全部交给 state-updater（见 §6）；
- 常驻：一个存档 = 一个作家 pi 会话，续档 = `--continue`。

> ⚠️ AIRP 注：wl 的"全量视角"靠加载全部 state schema 自动获得；**AIRP 没有 state 注入——作家想知道场景有什么，手动 `read_canvas` / `read`**（read_canvas 以渲染视角读画布内容，这就是作家的"眼睛"）。"状态更新 = writer 手动 write/edit"，没有更新器、没有自动推断。

### 1.4 subagent 与 creator

- **subagent**（如 referee 裁判）：不是固定架构角色，是通用的按需能力——任何 `delegatable: true` 的预设都能被作家 `subagent` 工具拉起，每次咨询现拉 in-memory 子会话，连续性来自继承历史 + state 快照 + 压缩摘要。referee 实例：`inheritHistory: 300`、thinkingLevel high、零工具（纯判断）、加载全命名空间 + 暗线知识，persona 有 need-to-know 三级放料硬规则；
- **creator**（创作助手）：创作台侧的独立 RPC 子进程，只产提案零写入（`propose` 经 custom entry 落前端表单，唯一写入者始终是人）——"助手永远不直接改文件"。

**对 AIRP**：subagent 正是 doc-05 §4.3 的 world subagent 委托机制；creator 模式给 AIRP 的"上帝模式"一个参考——玩家（上帝）是唯一写入者，agent 只提案。

## 2. 编排原语：handoff（递话筒）

### 2.1 工具签名与语义

```
handoff(i, character_id, scene_brief, context?, since?)
```

- `i`：一句话意图，2-6 词，仅展示给玩家、不进角色上下文；
- `scene_brief`：本拍手写场景简述——**角色唯一的"手写"上下文**；
- `context`：增量范围档位 `brief`（默认，无扩展层）/ `since-last` / `all`；
- `since`：引用锚点（从包含该句子的消息开始回放），优先于 `context`；找不到 → **报错标红，不静默回退**。

### 2.2 一次递话筒的完整时序

1. 玩家输入 → 作家进程；
2. 作家写旁白推进，涉及独立角色时调 `handoff`（旁白写正文即可，handoff 自动把最新一条旁白转交角色——保底机制，**不需要也禁止另填字段**）；
3. `handoff.ts`：懒加载/复用角色 RpcClient → 下发最新 world → 组装角色上下文（§4 的分层模型）→ prompt 角色进程；
4. 角色回复以 `character_reply` 消息**流式直显**给玩家（seam 渲染：`<character_reply>` 来源标签在作家 LLM payload 处生产，玩家端零标签）；
5. 领地快照回传主进程；
6. 作家顺着角色停下的地方**续写收尾**（不复述、不润色、不改写），以景物/氛围落点停笔等玩家。

三条铁律：scene_brief 只写角色看得见的 / 旁白写正文自动转交角色 / 人称分清。

**思路**：
1. **角色是"暂时接管话筒"而不是"独立并行"**——一次只有一个角色在说话（单跳、单向），杜绝多进程互等死锁，编排权始终在作家；
2. **作家的旁白与角色的台词是同一段叙事的两半**：旁白转交角色、角色回复后作家续写——叙事流从不中断，玩家的体验是一条连续的故事线；
3. **流式直显**：角色说话时玩家直接看到（不是等作家转述），"在场感"由此而来。

## 3. 角色间通信：pass_mic + relay + 阻塞门禁

### 3.1 pass_mic：角色主动递话筒

角色专属工具（`pass-mic.ts`，与 handoff 同属编排层）：

```
pass_mic(target)   // target = "player" 或 角色 id
```

**精简交接是本设计的核心约束**：工具只传一个 id，**不带 prose 参数**——角色先写正文，writer 从自己的 text_delta 累积器取 prose 自动转发（它本就订阅了角色的 message_update，零新增传输）。

两种 target：
- `target="player"`：裁决通过后落**单次往返 relay**（`remaining:1`），角色回合终止；玩家下一条输入以 `player_direct_input` **直达角色**，角色回一句后自动回作家；
- `target="<角色id>"`：writer 编排——A 回合终止，writer 以含 `<character_reply from="A">` 信封的上下文 spawn B，B 流式回复后 handoff 返回 ok、作家续写。**B 的回复不回流 A**（单向单跳，B 想继续必须自己再调工具）。

### 3.2 阻塞门禁（人类保留最终闸门）

同一角色**连续第 2 次** `pass_mic(非player)`（期间无玩家干预）→ ack `blocked`、回合终止 + 挂起提示；`/approve` 执行挂起的传递、`/deny` 丢弃，两者都清零该角色计数（**计数只由玩家干预重置**）。空 prose 直接调工具 → error，回合继续（防空信封，堵住"调工具跳过我的回合"漏洞）。

### 3.3 对称性读法（D6 决策的精髓）

- `/at <角色>` = 玩家发起的单次往返（`remaining:1`，`/endchat` 可取消）；
- `pass_mic(player)` = 角色发起的单次往返（同构）；
- `pass_mic(B)` = 角色发起的单跳（可被门禁阻塞）。

`/at` 与 `pass_mic(player)` 都是 `remaining:1` 的一次性往返——**要维持多轮直聊，角色必须每轮显式 `pass_mic(player)`**，否则对话落回作家。无限续聊被刻意删除。

**思路**：
1. **对称性**：玩家发起 / 角色发起走同一个 relay 机制，只是入口不同——一个机制两处复用，不造两套；
2. **工具只传 id 不传 prose**：prose 从作家自己的累积器拿，杜绝重复传输与内容漂移；
3. **门禁防乒乓**：角色间无限互递的失控场景，用"计数 + 玩家裁决"兜住——**AI 之间的通信，人类保留最终闸门**；
4. **单次往返**：直聊是有成本的（角色回合占作家编排权），"维持需显式续"让直聊始终是角色与玩家的共同选择。

### 3.4 消息标记：from/to 统一

`character_id` 曾在两种消息里语义相反（回复里是说话人、直聊输入里是接收人）——重设计统一为 `from`/`to`：`character_reply`/`character_ooc` → `{from, to?}`（to 省略 = 作家/黑板）；`player_direct_input` → `{to}`。双写过渡（旧 `character_id` 同值保留）实现零旧档迁移。

**思路**："一个字段背两个语义"是消息协议的隐性炸弹——任何"谁对谁说"的新功能（pass_mic 首当其冲）都会被绊倒。命名统一是编排层的地基。

## 4. 上下文构造：分层模型（编排层的核心）

**角色每次被递话筒时拿到什么**，由 per-character 配置（IP 级 `_context` 默认 + 角色预设 `handoffContext` 覆写）决定——**结构性配置，不是每次 handoff 的策展焦虑**。

### 4.1 七层组装

| 层 | 内容 | 决策者 |
|---|---|---|
| L0 | `scene_brief`（本拍手写） | 作家每次，必填 |
| L1 | 保底旁白（自动抓取最近一条有 text 的旁白） | 自动——作家写正文即可 |
| L2 | delta 扩展层（时间序回放，范围由作家控制） | 作家每拍（`context` 档位 / `since` 锚点） |
| L3 | world + 领地 state | 自动 |
| L4 | knowledge（作家已注入的动态知识条目，按角色可见性过滤） | 自动 |
| L5 | 角色自己的 session 历史 | 自动 |

组装序：`<state>`（world + 自己领地，开头）→ `<scene_brief>`（定位）→ `<knowledge>` → 引导头"你上次出现之后的经过" + 扩展层 → `<narration>` 保底旁白（末尾，紧邻角色回复）。消息是原子单位：扩展层起点命中的消息整条进入。

### 4.2 公开流规则（区间内全给，不设内容类型开关）

扩展层区间内所有公开叙事——玩家输入、作家旁白、其他角色回复、出戏元对话、玩家直聊输入——按时间序带来源标签**全给**，只有两个例外：

1. **自己的直聊**：`player_direct_input`（对话对象 = 自己）永不进自己的 delta（会话历史已有，进了 = 重复看见自己的聊天记录）；
2. **`invisible` 角色**：其回复/元对话/直聊输入永不进其他角色的 delta（**感知是默认态，不可感知是例外**）。

### 4.3 范围控制（作家每拍）

| 档位（`context`） | 扩展层起点 | 典型场景 |
|---|---|---|
| `"brief"`（默认） | 无扩展层，只保底旁白 | 偶尔打交道、离队回归、敏感场景（信息边界默认安全） |
| `"since-last"` | 该角色上一条真实回复之后；首次递话筒 → 最近一次玩家输入之后 | 入队后常规；群戏转交 |
| `"all"` | 会话起点 | 开局就在的脑内共居角色 |

省略 = IP 默认档位；`since` 锚点引用一段原文（子串匹配、从后往前取最近），命中消息整条为起点，优先于 `context`。

### 4.4 信息边界哲学

**范围控制为主，作家终审兜底**：敏感段落留在区间外（默认 brief 最安全，宽范围是显式选择）；越界由作家续写圆回（delta 给的公开经过 = 角色"事后听说"的内容，角色若因此知道不该知道的，作家续写时自然圆回）。

**正交性**：范围控制决定**给多少**（`context`/`since`），信息边界规则决定**给了怎么用**（预设层写作纪律，§7.3）——两个机制不打架。

**思路**：这是编排层最值得抄的设计。它把"角色该知道什么"从**每拍策展**（点估计，漏了断片、多了泄露）变成**结构性配置 + 每拍范围控制**——作者按"这个 IP 的戏建在什么信息结构上"设一次，作家每拍只控制宽窄，不控制内容。

> ⚠️ AIRP 注：**AIRP 只继承"给角色尽量少"的思想，不继承自动机制、也没有信息边界规则**。AIRP 没有 state 层（L3）、没有 knowledge 注入（L4）、没有自动抓取（L1/L2）、没有公开流规则、**没有预设层的信息边界/守密纪律**——**角色知道什么 = preset 引用文件 + 遮罩 invoke 时注入的最近场景情况 + 自己手动 read_canvas**，不要刻意防备。AIRP 的上下文构造简化为：
> - **preset 引用文件**（身份/性格/记忆，spawn 时载入，角色自己的）——对应 L5 的持久部分；
> - **遮罩 invoke 时注入的最近场景情况**（一段"此刻场景里发生了什么"的摘要）——对应 L0 的最窄档；
> - **角色手动 read_canvas**——需要什么看什么，不自动塞。
> 角色"不知道什么"不是规则防出来的，是**没人告诉它**——没有共享通道可泄，防备机制整体不存在。**没有自动 = 没有上下文膨胀，token 只花在 agent 主动要看的地方**。

## 5. 状态模型：schema 门禁 + 共享文件双向同步

### 5.1 命名空间与可见性

| 命名空间 | 内容 | writer | character | 写者 |
|---|---|---|---|---|
| `world` | 公开投影（time/situation/present/threads/rumor + canon） | ✅ | ✅（共享输入层） | 主进程 state-updater |
| `<角色id>` | 角色领地（name/role/location/mood/goal + beliefs[]） | ✅（全量仪表盘） | ✅ 只有自己的 | 主进程 state-updater |
| `player` | 玩家私有工作区 | ✅ | ✗（schema 级不加载） | 主进程 state-updater |

- **门禁由 schema 驱动**：`--schema world[,<id>]` + `--strict`——角色只加载/提交自己有 schema 的命名空间，写别人领地直接被拒（不是运行时过滤，是**结构上不存在**）；
- **领地本身可选**：`schemas/<id>.json` 不存在 = 无领地进程（作家型视角，只加载 world）；
- **暗线不在 state**：秘密活在设定集知识条目（`knowledge/secret.md`，`visible` 名单指定可见预设，常见 `[referee]`），角色进程不加载——角色连"存在"都不该确定知道的东西。

### 5.2 双向同步（共享 state 文件）

`<save>/.pi/state/*.json` + 引擎 fs.watch（pi 的 StateStore）：

- **world 下发**：writer 写 `world` → 共享文件 → 角色进程 fs.watch 自动重载（按命名空间 revision 跳过，无变化不重载）；
- **领地回传**：角色进程写自己的领地 → 共享文件 → 主进程自动读入（subagent 与作家快照读到实时状态）；
- **同步失败都不抛——scene_brief 永远是最终兜底，同步是尽力而为**。

**思路**：
1. **"结构上不存在"胜过"运行时检查"**：角色拿不到别人领地的 schema，就不可能写、不可能引用——隔离是配置层的事实，不是代码层的防御；
2. **文件即桥梁**：进程间不搞复杂 IPC，共享文件 + fs.watch 就够了（"文件即真相"的跨进程版）；
3. **兜底哲学**：同步是尽力而为，叙事上下文（scene_brief）永远是最后防线——基础设施可以挂，叙事不能断。

> ⚠️ AIRP 注：wl 的状态模型是 pi-rp state 系统的高级用法。**AIRP 不用 pi-rp state，也没有自己的 state 机制**（2026-08-31 明月拍板）：没有 schema、没有命名空间、没有 knowledge 注入、没有门禁——**可见性 = preset 引用哪些文件 + agent 手动 read**，**同步 = fs.watch 世界目录**，"结构上不存在"在 AIRP 里退化为"没引用就没得看"，比 wl 更薄一个量级。

## 6. 状态演化：单更新器（state-updater）

- **主进程 ×1**，每个 trace 触发（`agent_end` 时），读 `contextMessages`（完整 LLM 视图，含角色发言）→ 写**全部存在的 schema 命名空间**（world / player / 所有角色领地，无白名单）；
- **角色子进程不挂更新器**——领地数值由主进程从行为推断（角色发言在作家上下文里，行为足以推数值），写完后经共享文件同步回角色；
- **输出契约**：LLM 直接调 `state_update` 工具（op：replace/add/remove/merge），路径必须带命名空间前缀；字段级更新语义来自 schema 各字段的 `hint` 注解；
- 资源约束：120s 超时、inflight 去重（上一轮还在跑不叠发）。

**共创落地**：canon（公共基线：publicEvents/publicFacts）与 beliefs[]（角色信念）都由主进程更新器在同一轮维护——beliefs 基于作家全量视角推断（设计立场：**行为足以推断数值**）。

**思路**：
1. **单更新器**（曾经是每个角色一个更新器，后收敛）：一个进程统一推断全部状态，避免多写者冲突——"领地权威"让位给"单一演化者 + 共享同步"；
2. **行为推断数值**：不给角色加"写状态"的负担，角色只说话，数值由观察者（作家视角）推断——少结构化、少框架，与 AIRP 的哲学完全一致；
3. **AIRP 对应物：没有更新器（2026-08-31 明月拍板）**——状态需要更新就 **writer 手动 write/edit**（叙事 frontmatter 里的 status 快照 / journal / 角色记忆文件），没有 agent_end 钩子、没有自动推断、没有专门工具；引擎只靠 fs.watch 感知文件变化并广播事件。wl 用"单更新器统一推断"，AIRP 用"作家想更新时自己更新"——后者更薄、更可控，代价是作家要记得维护状态（写进作家预设的纪律里）。

## 7. 共创哲学：视角作者制（为什么这么设计）

### 7.1 认知转向：从"防"到"写"

**旧模型（信息隔离）**：scene_brief = 策展，每次递话筒由作家决定"这个角色知道什么"。结构性矛盾：写太详细 → 泄露；写太少 → 断片；策展是点估计，每一点误差都是硬错误。

**探针发现（threelies 真实案件，12 次真实模型调用）**：
1. **守秘是角色自己的写作决定**——裸泄露也守（领地 truth 三组全守）；
2. **吸收世界事实是特性不是缺陷**——角色在同一世界观里自洽（"压榨六年"被合理吸收为世界常识）；
3. **约束管的是写作纪律**（不引用、不对线"玩家与别人的对话"），不是知识封锁。

### 7.2 三层模型

| 层 | 内容 | 谁写 | 谁读 |
|---|---|---|---|
| canon（公共层） | 世界的公开知识 | 主进程 state-updater（distiller） | 所有角色 + 作家 |
| territory（私有层） | 每个角色的 truth/goal/beliefs/mood | 角色自己 | 该角色 + 更新器 + 作家 |
| orchestration（编排层） | 全量 | 更新器从行为推断 | 更新器 + 作家 LLM |

**同质化缓解的关键**：原始共享把 input（事实）和 output（解释）混在一起倒给所有人；三层模型把它们切开——**事实层收敛**（canon 是同一份权威公共基线），**解释层发散**（同一 canon × 各自 truth/goal/persona → 不同 beliefs）。共享的是 input，差异在 output。

### 7.3 继承反转 + 信息边界规则

- **继承反转**：不给角色做内容策展，改为"多给 + 边界声明"——角色渲染 world 公开投影 + 自己领地（粗过滤，不做语义策展），同时预设层内置信息边界规则：领地 truth/secret 是底线、信息来源只有领地/场景简述/world 公开状态/亲身经历、**玩家与他人的对话视作不存在**、拿不准时选择不知道；
- 泄露探针 D 组验证：预设层规则 ≈ 手写约束——约束进预设层，作家 handoff 不再需要写保密措辞；
- 作家重定位为 **showrunner**：写局面、递话筒、终审（越界圆回、不成为玩家可见事实），不再代笔角色台词。

**思路**：这是 wl 最深的洞察。**承认角色无法被严格隔离，放弃"控制角色看到了什么"，改为"控制角色把什么当作已知"**——LLM 对显式命名的"你不该知道 X"有良好的角色扮演支持，越界的代价有界（角色行为怪异，不是硬信息泄露），作家是叙事最后一道门。

> ⚠️ AIRP 注：**"继承反转"和"信息边界规则"都是 wl 为了自己的信息共享通道（state/knowledge）配套的补救设计——AIRP 没有共享通道，两者都不需要**。AIRP 的角色只拿到：preset 引用文件 + 遮罩 invoke 时注入的最近场景情况 + 自己手动 read 的东西——**没有"多给"就没有"边界声明"，没有守密纪律这回事**。角色不知道什么 = 没人告诉它，不是规则防出来的。作家是叙事质量的唯一把关人（叙事是否合理），不是信息泄露的门。

## 8. 开场播种：opening + 剧情树

- **pi-rp 内建通用播种器**（`src/extensions/opening/`）：`/opening [<id>]` 命令 + `PI_OPENING` env（session_start 自动应用，会话有消息条目时跳过 = 续档不重播）；预设 = `<config-dir>/openings/<id>.json`，可播种 user/assistant 真实消息、任意 customType 自定义消息、state 叶子覆写；
- **wl-opening.ts 是角色语义适配层**：按 `WL_PROCESS_ROLE` 变换预设——main 全量；角色只拿 narration + 自己 `character_reply` 的 assistant 记忆 + 自己领地 state；
- **开场白剧情树**：开场预设带 `choices` 即成树——逐节点复用内建播种器播内容 → 发树选项（`when` 不满足的选项 lock 置灰）→ 玩家选择落 user 输入推进 → terminal 触发作家；树状态机在 wl-opening + opening-tree.ts（跨扩展单例），留痕走 `opening_tree` custom entry；
- 角色子进程沿 `WL_OPENING_PATH` 播种路径记忆（角色"记得开场时发生了什么"）。

**为什么出生继承（init_context）替代不了播种**（CROSS-SESSION-COORDINATION 论证）：角色进程重启/续档时，继承的是父会话**当前**历史窗口，开场早已滑出窗口；"角色记得开场时我说了 X"必须落在**角色自己的会话文件里**才是跨续档持久的——所以哪怕 init_context 全落地，播种 + 锚点依然需要。

**思路**：开场的"角色出生记忆"是**播种进角色自己的会话**，不是临时注入——记忆要跟着角色走，不跟着会话窗口走。AIRP 直接复用（doc-07 A4：opening 播种预设）。

## 9. 工程纪律（wl 的防坑经验）

1. **spawn 参数单一事实源**（launch.mjs）：run.sh / gateway / handoff.ts 三入口共用，曾有三份复制互相漂移（web 漏 `_` 前缀过滤、漏 opening 挂载）——合并后改规则只改一处；
2. **扩展挂载清单按进程角色定**：writer 8 件套 / 角色 4 件套 / creator 1 件套——角色不挂 handoff（防递归递话筒）、不挂 choice、不挂 state-updater（单更新器只挂主进程）；
3. **`WL_PROCESS_ROLE` env 区分进程身份**（main / character:<id> / creator）——扩展据此分支，不靠进程名推断；
4. **seam 渲染**：来源标签在作家 LLM payload 处生产、渲染前切分——标签只存在于作家视角，玩家端零标签泄漏；
5. **锚点语义**（回滚 ↔ 角色进程同步）：`character_reply` 经 `reply_entry_id` 显式关联作家树与角色会话的 entry，不再要求 id 双端一致；同步用 `navigateTree` 推导，推导不到不动角色；
6. **OOC 协议**：角色输出里的 `<ooc>…</ooc>` 段（出戏元对话）在 relay 落定时切出，以独立 `character_ooc` 消息发出（前端异样式渲染）——"角色知道自己在被写"与"角色在戏里"分开；
7. **进程级 settings 覆盖层**（`--settings-file` 三 scope 合并）：save 级 userName 等经覆盖层进引擎，不写全局；
8. **测试纪律**：纯逻辑（handoff-context / opening-tree / pass-mic）抽成纯模块带单测，扩展层薄壳；协议级单测（rpc-orchestration.test.ts / rpc-affiliated-context.test.ts）不 spawn 真实子进程。

## 10. AIRP 借鉴映射（2026-09-10 更新）

**AIRP 已砍掉世界内角色编排**，wl 的编排层整体只作参考。实际采用的子集聚焦**角色遮罩对话**（被点开时才 spawn 的独立进程）：

| wl 机制 | AIRP 用法（2026-09-10） | 采用？ |
|---|---|---|
| mode 三态 | **不用**。AIRP 拓扑固定：作家常驻 + 角色按需 spawn | ❌ |
| **懒加载角色 spawn** | **直接采用**（doc-05 §4.1 角色遮罩）：角色进遮罩才 spawn、出遮罩回收、独立会话文件——"第一句话才存在"的进程层实现 | ✅ 照抄 launch.mjs 范式 |
| handoff（递话筒） | **不用**。作家不再把话转交角色——叙事全由作家写，角色只在遮罩内与玩家一对一 | ❌（旧架构 call_character 废除） |
| pass_mic + relay + 阻塞门禁 | **不用**。角色间通信整体砍掉 | ❌ |
| 上下文分层 L0-L5 | **只留两物**：preset 引用文件（身份/性格/记忆）+ 最近场景情况注入（invoke 时给一段"此刻场景里发生了什么"）——无自动抓取、无 state、无 knowledge | ⚠️ 继承"少给"思想，自动机制全砍 |
| schema 门禁 + 共享 state 同步 | **没有 schema、没有 state、没有门禁**——可见性 = preset 引用 + 注入 + 手动 read；同步 = fs.watch 世界目录 | ❌（fs.watch 替代） |
| knowledge 注入（L4） | **没有 knowledge** | ❌ |
| 单更新器 state-updater | **没有更新器**——状态 = 叙事 frontmatter（status.data），作家 edit 写 | ❌（作家手动更新） |
| **opening 播种** | **直接采用**（doc-05 §4.1）：角色出生记忆/开场白，跨续档持久——遮罩里"角色记得自己是谁"全靠它 | ✅ 直接用 pi-rp 内建播种器 |
| **角色独立会话文件** | **直接采用**：遮罩对话存 `characters/<名>/` 下角色自己的会话，跨遮罩连续 | ✅ |
| 共创（视角作者制） | **不再适用**——AIRP 没有多角色共创，作家一人写全部叙事 | ❌ |
| 信息边界规则（预设层） | **不存在**：角色知道什么 = preset 引用 + 最近场景注入 + 自己 read，无共享通道可泄 | ❌ |
| subagent（referee 式） | world subagent 委托（doc-05 §4.3） | ✅ pi-rp 原生 |
| seam 渲染 / OOC 协议 | 前端消息来源标签（作家/角色/玩家）；角色出戏元对话 | ⚠️ 思路继承（单聊遮罩内角色出戏切分） |

**AIRP 简化后剩下的真正依赖**：
1. **懒加载 spawn 的参数范式**（wl launch.mjs 的瘦身版：无 `--schema`/`--strict`，加角色标记）；
2. **opening 开场播种**（pi-rp 内建，纯 JSON 资产）；
3. **角色会话文件**（`characters/<名>/` 下，跨遮罩持久）；
4. **fs.watch 世界目录**（文件变化的免轮询推送）。

**代价与对策**（为什么敢这么薄）：
- 角色"不知道场景"→ 靠最近场景情况注入（invoke 时给摘要）+ 角色手动 read_canvas；
- 状态漂移 → 靠"文件即真相"兜底（frontmatter status 是文件，作家随时 edit 修正）；
- 上下文膨胀 → 反过来被消灭：不注入 = 不膨胀。

## 11. 一句话总结

> wl 的编排层回答了多 agent 叙事的三个问题：**谁说话**（handoff 递话筒，一次一个，编排权在作家）、**角色知道什么**（上下文分层 + 范围控制 + 预设层信息边界）、**世界怎么动**（单更新器从行为推断状态，共享文件同步）。它的设计哲学是：**信任角色（共创），约束写作纪律（边界规则），保留人类闸门（/approve /deny）**。
> **2026-09-10 后 AIRP 的立场**：AIRP **不做多 agent 共创**——作家就是唯一讲故事的人，角色是被点开时才活过来的对话对象。wl 证明"编排层"该有什么（多角色实时互动的完整答案），AIRP 证明"没有编排层"的另一种产品形态（叙事文本是唯一主角）——**wl 的价值保留为：懒加载 spawn 范式、opening 播种、角色独立会话文件这三个机制，恰好构成 AIRP 角色遮罩对话的实现底座**。
