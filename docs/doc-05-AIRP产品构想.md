## 0. 一句话定义

**一个让玩家像角色一样活在"活的无限画布世界"里的 AI 互动叙事游戏**：世界有层级（大地图→城市→商店→抽屉→纸），叙事由作家实时书写，玩家既能沉浸扮演，也能切换上帝之手自由捏造世界。**玩家与叙事文本之间只有一个 agent——作家；角色是被点开时才活过来的独立存在。**

**2026-09-10 架构转向一句话**：**叙事文本是唯一主角，其余全是修饰和呈现辅助**。世界内不为独立角色做编排——黑客松追求演出效果，作家写作时漂亮的组件和演出效果就够了，独立角色打断叙事反而累赘。

> **2026-09-11 评委导向升级（doc-19）**：对标黑客松四位顶级评委（Playable Intelligence 警告不用 Blender / 要 playable；PlayCo 要求视听动大满贯；Supercell 要求经典游戏玩法与 Tool Pipeline；AnotherBall 要求舞台大秀与情感沉迷），核心哲学升级为：
> **叙事是世界的灵魂，多模态（视听动）与实体交互（道具/骰子/空间）是游戏的肉体与玩法主力。** 叙事文本统摄全局，道具拖拽解谜、大号物理掷骰、全景声场与全套 6 情绪差分立绘共同构成高可玩性、高秀感的互动体验。

## 1. 三条核心哲学

1. **体验优先，不做世界模拟器**。"营造出世界在自己动的感觉，但不一定真的得搓一个世界模拟器出来——太重、太慢、成本太高，而且不好玩。"世界的"动"靠：**懒加载**（玩家看着的时候世界才转）+ **作家现编**（世界、角色、冲突、时间流逝全部"需要时现编"）。
2. **懒加载是万能兜底**。世界、地图、物件、角色、时间，全部"需要时现编"：新地图进入时才实例化、角色被点开时才激活、角色这两个月做了什么——作家现编。
3. **叙事是灵魂，视听动与实体交互是玩法主力**。作家的旁白板书是一场戏的总导演脚本；2.5D 纸雕微缩视差、全景声场（环境音/拟音/BGM）与实体道具拖拽解谜（Point-and-Click）共同赋予世界触手可及的游戏乐趣与舞台秀感。

## 2. 玩家体验

| 决策 | 共识 |
|---|---|
| **玩家身份** | 上帝之手 + 角色双模。平时是世界里的一员，并由独立 avatar 表示“我在这里”与当前行动原点；可切换上帝模式自由定义世界。avatar 不是 NPC，不进入 Character Agent |
| **世界入口** | 每个世界先以一个世界内的导言层完成身份、地点与动机交接，再由一段小而明确的入口 Chalk 把玩家送入主关卡；“我能造成什么影响”必须由第一次反馈证明，不靠教程说明 |
| **核心循环** | 双轨：叙事主线（角色模式探索推进）+ 上帝支线（上帝模式捏造），共享同一个世界状态 |
| **世界生长** | 双驱动：探索驱动（角色走到哪，剧情需要就开新地图）+ 意志驱动（上帝模式捏造/修改） |
| **叙事来源** | 预写骨架 + 动态生成：世界设定/关键事件/结局条件预写，剧情细节、支线、NPC 反应由作家实时生成 |
| **结局与续玩** | 每个 10–30 分钟篇章必须抵达一次可进入的结算空间；结局表现为 Outcome Folder，而不是最后一段字幕。有限案件可有多个结局并从检查点重玩；开放世界以阶段结局打开下一片边界，不强造唯一世界终局 |
| **行动模型** | 对话 + 探索 + **以物解谜**。玩家对作家说任何话；画布行动（点门=开门、点物品=拿取、**道具拖拽出示/使用=解谜**）；叙事 frontmatter 里的 choice 选项 |
| **对话通道** | 打字为主（对作家说任何话）+ 画布行动（点门/点物/拖物出示）+ 选项卡（叙事 frontmatter 的 choice） |
| **移动手感** | 点哪到哪（RTS 式移动命令，无物理行走模拟）+ 显式进入（点路口/地点切层） |
| **角色在场** | **类光标 + 圆形头像**（轻量在场感，不做精灵）；进入单聊遮罩时切换为**左右分屏大半身立绘，带全套 6 情绪差分**（normal/smile/shock/sad/angry/thinking，Prompt 句首标签显式驱动）+ 呼吸动效 |
| **玩家背包** | **`player/` 目录 = 玩家的小天地**，右侧边栏"背包"tab 列表预览；支持**双向拖拽**（拿走/放回）与**以物解谜（拖拽到目标卡片/门/NPC 触发 `use_item_on`）** |
| **角色导航** | 右侧边栏"角色"tab 列出世界角色头像：**点头像 = 导航**（跳到该角色所在场景）、**找角色聊天**（进入对话遮罩）、**设置跟随**（角色跟着玩家切场景） |

**角色交互**：画布上的角色是一个**头像（光标态）**。**单击角色头像 = 直接进入单聊对话遮罩**（特写态，与角色的正式单聊，见 doc-06 §3）——**没有"场景搭话/一句气泡"这类轻量中间态**。角色只在被点开时才 spawn agent；遮罩内立绘拥有全套 6 情绪差分，角色 Prompt 输出台词句首附带 `[emo: <tag>]`，前端捕获平滑切表情。

**背包交互（玩家小天地 + 以物解谜）**：右侧边栏常驻一个**双 tab**——**背包** tab 是 `player/` 目录的列表形式预览（资源管理器式，见 doc-06 §5），**角色** tab 是世界角色头像列表（见 doc-06 §5.4）。背包 tab 支持三类手势：
1. **拿走/收藏**：把场景里的物件卡拖进右侧背包（文件从场景目录移动到 `player/`）；
2. **放回场景**：把背包里的条目拖到画布空白处（文件移回场景目录，作为掉落物）；
3. **以物解谜（核心游戏性，2026-09-11 新增）**：**把背包里的道具拖拽释放到场景卡片、门卡或 NPC 头像上**（`use_item_on`，如钥匙拖到门上、证物拖到角色头上）。前端捕获碰撞事件派发给引擎，直接触发开锁/审讯演化，作家即时叙事回应。不再把推进唯一锁定在 choice 上。

**角色 tab（导航/聊天/跟随）**：右侧边栏"角色"tab 列出世界所有角色的头像：
- **点头像 = 导航**：跳到该角色所在的场景（切层 + 相机定位到角色）；
- **聊天按钮 = 找角色聊天**：在角色当前所在场景与他进入对话遮罩（等价于画布上单击该角色头像）；
- **跟随开关 = 设置跟随**：开启后角色"跟着"玩家——玩家切换场景时，角色的在场状态同步到玩家所在层，画布上该角色头像出现在新场景。关闭则角色留在原地/回到自己的位置。

**角色跟随的语义**：跟随是**运行时在场状态**（记在 DB 状态层），不是文件搬移——角色目录（`characters/<名>/`）不移动，只是"此刻他在你身边"。跟随状态由玩家控制（主动开关），作家可感知并可叙事回应（"老周跟着你进了城……"）。

### 2.1 世界入口：导言、入口 Chalk 与双线启动（2026-09-12 定案）

世界的第一层不是功能教学页，而是**世界内导言层**。它必须在极短时间内回答：玩家是谁、身处何处、现在要做什么、为什么非做不可。载体数量不固定，可以是三张纸，也可以是一封信、一段 HTML 演出或“悲剧画面 + 信物”。

导言结尾必须给一段很小、回应很确定的入口 Chalk——它可呈现为打开信、拿起遗物、接受邀请或点击地点卡——并立刻给足视觉、声音、空间和持久状态反馈。这个动作同时启动两条线：

- **行动 / 空间线**：实体可操作 → 世界回应 → 出现可进入的场景门 → 进入主关卡；
- **情感 / 剧情线**：身份 → 委托 / 遗憾 / 承诺 → 不行动的代价 → 玩家愿意继续。

此处的核心入口是 **Chalk**，不另造 “Chunk” 概念。导言 Chalk 可以以信、卷轴或其他世界内文件的形态呈现，并通过 frontmatter 给出 RP / Choice / Dice 或移动机会；它所提及的遗物、线索与地点仍由 note、letter、item、gate、component 等现有协议承载。完整设计详 `doc-20` §2。

## 3. 世界模型

| 决策 | 共识 |
|---|---|
| **世界活性** | 懒加载：玩家看着时世界按节拍动，不看时静止；记忆跨会话持久化。"活性"的实现 = 作家现编 + 角色被点开时激活，**不做常驻角色进程的自主行动** |
| **层级结构** | 预写拓扑 + 按需实例化：区域拓扑预写（模板/作家按世界观生成），每层内部在首次进入时生成——"第一眼才存在"。**每一层都是一块平等的无限画布，切换层级 = 换一块画布**（见 §3.2） |
| **叙事载体** | 混合：旁白板书承载叙述与对话（可读性），画布承载"沉默细节"（纸上的字、椅子的摆法、物品的用途——旁白覆盖不到的世界真实感） |
| **状态更新** | 都走 agent，少结构化。一般只有时间/地点/角色物品栏；世界文本（journal）跟玩家绑定；不做"门开没开"级的状态模拟 |
| **时间** | 剧本时间（叙事驱动）：剧情说过了多久就过了多久——玩家两小时体验游戏两个月的剧情；角色这段时间做了什么由作家现编 |
| **互动组件** | 场景内嵌活物件（谜题/书/乐器/天气/装置）+ 演出型组件（过场/特效）。**组件是叙事的补充装饰，不是主要互动元素**（见 §3.1） |
| **画布视觉** | **统一渲染**：每一层都是同一套画布底座 + 材质皮肤 + 物件；不存在"结构层/场景层"两套视觉语言（2026-09-08 修正） |

### 3.1 叙事、组件、状态的关系（2026-09-10 定稿）

**一串叙事 = 一个 `type: chalk` 的 md 文件。状态、选项、骰子都不是独立组件，是缠绕在这段叙事文本上的 frontmatter。**

```
---
type: chalk
roll_dice:            # 骰子检定（玩家点击掷出，见 §3.1「骰子协议」）
  type: 1d100
  desc: 检定是否通过
  expect: ">50"        # 通过条件（引擎可读比较式，必须带引号）；作家不写 result
choice:               # 玩家行动选项
  - "先给公司起名"
  - "找王安波"
status:               # 状态快照（叙事 frontmatter）
  data:
    公司名称: "(未定名)"
    当前阶段: "车库期"
    时间: "1980-04"
---

正文……（叙事主体）
```

**渲染方式**：不是 HTML，是**类 md 表格渲染**——状态/选项/骰子渲染成可折叠的表格块，绑在具体叙事文本下方。前端天然可折叠，跟剧情位置强关联。

**骰子（roll_dice）的交互协议（2026-09-11 定稿）**：**骰子由玩家掷——不是作家写死、不是引擎落盘时自动掷。**

- 作家写 frontmatter 时**不写 `result`**（掷骰结果不是作家该预知的东西）；写 **`expect`**——**引擎可读的通过条件表达式**（如 `">50"` / `"<20"`。**必须带引号**：裸写 `>50` 会被 YAML 当作 block scalar 报错）。它既是剧情意图标注（"这次得 <20 才成功，把玩家逼向另一条线"），也是引擎将来判定骰子结果是否通过的依据；
- 前端把 `roll_dice` 渲染成一个**骰子卡**（未掷态：骰子图标 + desc + 通过条件 `expect`）；**玩家点击骰子** → 骰子演出特效（纸世界语汇：纸骰弹跳/旋转 → 落定，见 doc-06 §2.6）→ 服务端真随机掷出，**按 `expect` 判定** → 结果**回写 frontmatter 的 `result`** → 卡片落定显示（数值 + 通过/未通过）；
- 结果同时**作为事件落事件表**（§5.1，type: `roll_resolved`）——作家在下一轮 Hook 收到"玩家掷骰：检定「推理检定」掷出 62（>50 通过）"，可据此叙事回应；
- **剧情判定不再用 roll_dice 表达**：结果由剧情说了算时，作家直接写进正文（"这一刀没能劈开锁"），根本不写骰子——骰子只承载"真随机带来的紧张感"，是玩家参与的仪式。

**由此产生的边界（2026-09-11 修正）**：
- **独立组件（component）**：保留信/谜题盒/棋盘等真正有渲染+交互逻辑的物件——**既是叙事的沉默细节，也是以物解谜的目标实体**（如带锁的门、等待投喂的信箱）。剧情推进支持双通道：常规走 choice 推进，关键解谜通过背包道具拖拽释放（`use_item_on`）直接推进。
- **叙事辅助（frontmatter）**：roll_dice / choice / status 全部收进 chalk frontmatter，随文本走。
- **入口 Chalk**：用世界内叙事给出第一个小而确定的动作。玩家可点开、展开或回应 Chalk；具体的拿取、使用和切层仍由 note/item、component 与 gate 协议执行，再由 Chalk 承认结果。
- **轻量时间感知（无复杂 HUD）**：不做夸张的 MMORPG 式状态栏/数值槽；底层状态纯粹随 frontmatter 走，前台仅以极简印章形式呈现游戏内的**世界时间与天数**（如“第 3 天 · 暴雨深夜 23:15”）。

### 3.2 层级画布（2026-09-08 定稿，原 doc-10 并入）

**一个目录 = 一块画布。同一时刻世界只有一块画布在场。进入子目录不是"钻进一个洞"，是"换了一块画布"——上一块画布退成历史，不常驻、不并排、不透视。**

推论：
1. **没有"世界树管理器"**——想看世界全貌？大地图本身就是一块普通画布，切过去就是了。
2. **没有"两套渲染管线"**——结构层/场景层合并成一种视图：**画布 + 材质皮肤 + 物件**。房间看起来"像场景"，只是因为它的背景是一张图、物件摆得密——底座和大地图完全同一套。
3. **深度免费**——目录能嵌多少层，画布就能换多少层。抽屉里的一张纸和整个世界用同一个渲染器。

**一块画布上有什么（统一物件系统）**：

| 物件 | 来源 | 呈现 |
|---|---|---|
| **场景卡（门）** | 子目录的 README.md | 封面图 + 标题 + 摘要，材质随本层；这就是"入口/门" |
| chalk 浮字 | `type: chalk` 的 md | 楷体墨字浮在画布上，无卡片壳（叙事正文） |
| 便签 / 文件卡 | md / txt 等 | 纸卡，双击阅读器 |
| 组件 | `type: component` | 信、谜题盒、棋盘……iframe/组件渲染 |
| 图片 / 背景 | `type: asset` | 图片是卡；`background` 特例铺满画布做底 |
| 关系线 | canvas.db 画布状态（作家用专用 `link` 工具管理） | 手绘线 / 丝线 / 墨线，大地图上=道路；**样式多样（实线/虚线/箭头/特粗/红线），属于画布状态层，不落 md、不从 md 派生**（见 doc-10 E13） |
| 角色头像 | 角色卡 + 在场状态 | **类光标 + 圆形头像**（轻量在场感），点=对话 |

**材质身份**：每层 README 的 frontmatter 声明 `material`（世界默认材质在 world.json 顶层 `material`），决定这张"画布"长什么纸——大地图=羊皮纸、城市=牛皮卷宗、商店=便签墙、抽屉=索引卡、题材包=终端墨版（科幻）。场景层就是 `material: scene` + 背景图的特例。

**每层记住自己的相机**：离开时什么缩放、看到哪儿，回来还是什么样——"每一层是一个地方"的关键细节。

**切换交互**：

| 动作 | 模式 | 说明 |
|---|---|---|
| **点门 / 双击场景卡** | 主入口 | 角色模式：点门=走过去+进入（演出一步）；上帝模式：双击直进 |
| **面包屑** | 常驻 | 左上角，路径即 id 的可视化，点任意祖先跳回 |
| **Alt+← / Esc** | 返回 | 回上一层（浏览器 back 语义） |
| **历史栈 前进/后退** | 导航 | 穿越过的层缓存着，秒回 |
| **小地图** | 空格/M | 只画当前层 + 视口框（"导航控件不是第二视图"） |

明确不做：滚轮缩放自动穿越、画布边缘拖拽切层、"世界全貌"悬浮视图。

**切换效果：穿越（zoom-through）**——空间语义：下层=更近，上层=更远。进入：相机向门推进 → 门卡放大充满视口 → 门面成为全屏"底" → 新画布从底里展开落定；退出是对称逆过程。过场相机四条纪律（锚点式插值 / z 全程连续 / 缩放上限 / 房间记忆只在交互结束时机存）——原型踩坑后沉淀，见 `archive/2026-09-10旧编号/doc-10` §4.5。

**画布生老病死**：懒加载天然成立（进哪层挂哪层）；离开的层 LRU 缓存最近 ~3 层 DOM 冻结，更早卸载只留 canvas.db 坐标；布局对账每层坐标存 canvas.db（按目录路径键）；视点上报表带画布路径。

## 4. Agent 架构（2026-09-10 重构）

| 角色 | 实现 | 职责 |
|---|---|---|
| **作家** | 主 agent（常驻进程） | **唯一的叙事主体**：写剧情细节、更新场景物件、维护 journal。玩家不找就不介入，但**随时响应** |
| **角色** | **按需 spawn 的独立进程**（第一句话才启动，懒灵魂） | 被点开时扮演角色与玩家对话（对话遮罩）；有自己的目录小天地（`characters/<角色名>/` 根目录）。**不参与世界内编排、不打断剧情** |
| **NPC（村民）** | 无独立 agent，作家一句话现编 | 世界的"布景"：背景填充，少一个不影响体验 |
| **场景初始化器**（profile `scene-init`，`delegatable: true`） | 作家 `subagent` 工具委托 / 引擎直唤（doc-11） | 从零→100 的体力活：首次进入 stub 层时生成"世界的第一眼"（骨架 + 物件 + 开场白） |

**关键区分消失（2026-09-10）**：不再有"独立角色 vs NPC"的两分法。**任何角色点击都能进遮罩（背后有 agent，第一句话才 spawn）；没被点开的只是布景头像。** 区分被"懒灵魂"取代——统一按需。

**砍掉的东西（2026-09-10 定案）**：
- ~~世界内角色编排~~：不做 pass_mic / 角色间直连 / call_character 搭线 / 黑板旁听路由 / 节拍偶发推演。角色间互动由作家在叙事里现写（NPC 化处理）。
- ~~角色精灵~~：不做精灵动画、idle 生活、走位调度。在场 = 类光标 + 圆形头像。

**保留的东西**：角色独立进程（懒加载 spawn）、角色有独立记忆（自己的目录）、作家懒加载思想（只回应玩家）。

### 4.1 角色模型（遮罩 + 小天地）

**角色 = 两个存在形态**：

1. **对话遮罩（被点开时）**：单击角色头像 → 进入遮罩特写（左右分屏大半身立绘）→ spawn 角色进程（拿最近场景情况，独立于作家）→ 角色以自己的记忆/人格与玩家对话。对话结束（Esc/说完），进程可回收。**作家不介入、不考虑角色意见**——这是演出管线（§5）对角色透明的直接原因。
2. **目录小天地 = 角色自己的根目录**（`characters/<角色名>/`）：角色目录本身就是角色的"私人空间"——玩家随时可以去逛，看 ta 留下的作品、便签、生活痕迹（参考 `角色-yoshi.html` 的 Elias 私人房间原型：画作、笔记、世界经历卡、共同作品）。**小天地 = 角色根目录 + 私人痕迹，不是额外子目录**。

**角色"自己写"目录的义务（2026-09-10 三个情境）**：

| 情境 | 可见性 | 说明 |
|---|---|---|
| **场景内单聊中顺手写** | 玩家**不可实时见**，但提示"角色留下了东西" | 角色在遮罩对话中顺手往自己根目录写（agent 能力），痕迹等玩家去小天地才揭晓 |
| **玩家进小天地，根目录为空时** | — | 触发**初始化**：像走进一个空白场景，角色/系统生成初始内容（第一眼才存在） |
| **玩家在小天地内与角色聊天** | **实时可见、可评论** | 角色在小天地里写，玩家实时看到，还能留下评论/评价——小天地是"活的" |

**角色目录结构**（每个独立角色一个目录）：

```
characters/
└── 旅店老板/                 # 角色根目录 = 小天地本体
    ├── README.md              # type: readme，角色简介（小天地门面/封面）
    ├── preset.json            # 角色提示词预设（引用本目录下的 md 文件）
    ├── identity.md            # 身份与背景
    ├── appearance.md          # 外貌（遮罩立绘描述）
    ├── personality.md         # 性格
    ├── memory/                # 记忆（角色自己写自己读，遮罩对话的连续性）
    ├── 作品.md                # 小天地内容：作品/便签/生活痕迹（chalk 文件，直接放根目录）
    └── ...
```

- **preset.json 是角色的"大脑"**：用 pi-rp 的 preset 机制组装提示词——`slot` 的 `system-char` 注入平台统一的角色行为规范（情绪差分、特写对话规范），`slot` 的 `file` 引用本目录下的 md 文件（`baseDir` 指向角色目录，因为相对路径的基准是会话 cwd = 世界根）：
```json
{
  "schemaVersion": 1,
  "id": "tavern-keeper",
  "name": "旅店老板",
  "items": [
    { "kind": "slot", "id": "character-instruction", "slot": "system-char" },
    { "kind": "slot", "id": "profile", "slot": "file",
      "options": { "path": ["identity.md", "appearance.md", "personality.md"],
                   "baseDir": "characters/旅店老板", "stripFrontmatter": true, "onMissing": "skip" } },
    { "kind": "slot", "id": "chat-history", "slot": "chat-history" }
  ]
}
```
> **两条硬约束与定案（2026-09-11 实测）**：① **不存在内建 `system` 这个 slot**——`slot` 只能取内建槽名或扩展注册的自定义槽。AIRP 通过扩展 `extensions/instructions.ts` 为不同职责的 Agent 注册专属 instruction slot：角色专用 `system-char`、作家专用 `writer-char`、场景初始化专用 `scene-init-instruction`、小天地初始化专用 `nook-init-instruction`。slot 的 name 与 item id 严格隔离互不混用。② pi-rp 的 preset 顶层**没有 `system` 字段**——顶层只有 `schemaVersion`/`id`/`items` 等，提示词一律进 `items`；写成 `{"system": "..."}` 会被 loader 整个忽略（`items` 缺失 → 报错）。
- **角色 spawn 上下文 = 极薄**：preset 引用文件（身份/性格/记忆）+ 最近场景情况（invoke 时注入）+ 自己手动 read_canvas。没有共享状态通道、没有自动注入、没有信息边界规则——**角色知道什么 = 没人告诉它什么，不是规则防出来的**。

**玩家目录（`player/`）= 玩家的小天地 / 背包**：玩家是真人，不是 agent，不需要 preset.json——但 `player/` 目录本身就是玩家的私人空间，前端右侧边栏的背包就是它的列表预览。玩家从场景收藏进背包的东西就落在这里：

```
player/
├── README.md              # 玩家角色简介
├── identity.md            # 玩家设定
├── 铜钥匙.md              # 从场景收藏进来的物品（背包）
└── 给老周的信.md          # 玩家在小天地里写的东西
```

与角色小天地对称：角色有自己的根目录（`characters/<名>/`），玩家有自己的根目录（`player/`）。区别只是**呈现方式**——角色小天地是"可进入逛的空间"，玩家小天地是"右侧常驻的背包列表"（资源管理器式，见 doc-06 §5）。

**玩家记忆 = 作家记忆 = journal**：玩家经历了什么，作家就知道什么。作家的视角/背景/经历是玩家的参考材料。

### 4.1.1 右侧边栏：背包 + 角色（双 tab）

右侧边栏常驻**两个 tab**，都直接投影文件系统（路径即 id，无额外索引）：

| tab | 内容 | 能力 |
|---|---|---|
| **背包** | `player/` 目录列表（资源管理器式） | 双向拖拽（场景→背包=收藏拿走，背包→场景=放回）；背包内分类/看详情 |
| **角色** | 世界角色头像列表（`characters/` 扫描） | 点头像=导航到角色场景；聊天按钮=进入遮罩；跟随开关=角色跟着玩家 |

#### 背包 tab（收藏/拿出）

**右侧边栏背包 = `player/` 目录的列表形式预览**（资源管理器式）。与画布双向拖拽：

| 方向 | 动作 | 结果 | 文件操作 |
|---|---|---|---|
| **场景 → 背包** | 把场景里的物件卡拖到右侧背包 | **收藏/拿走**：物品从场景消失，落进 `player/` | `move(物品.md: 场景目录/ → player/)` |
| **背包 → 场景** | 把背包里的条目拖到画布上 | **放回/使用**：物品重新出现在场景指定位置 | `move(物品.md: player/ → 场景目录/)` |

- **语义 = 移动**（不是复制）：拿走就是场景里没了，放回就是重新出现——与"收藏/拿走"的直觉一致，也是资源管理器的默认行为；
- **一律经引擎 move()**：两次拖拽都走 `worldStore.move()`（§8.3）——自动附带引用重写（md link / 组件 ref 就地改路径）与事件上报（§5.1），dangling 断链渲染"已被带走……"兜底态；
- **路径即 id 的又一次体现**：背包就是 `player/` 目录，拖拽就是文件搬移，不需要任何额外索引；
- **作家感知**：物品消失/出现经引擎动作层（§8.3 move）追加事件表 → 作家在下一轮收到人话 system reminder 后可叙事回应（"咦，那把钥匙不见了……"），见 §5.1 事件注入；
- **背包内组织**：玩家可在背包里给物品分类（`player/` 下建子目录）、看物品详情（点开阅读器）；
- **上帝模式不冲突**：上帝模式里玩家本来就能直接拖文件，背包只是把这条能力变成了角色模式也能用的收藏动作。

#### 角色 tab（导航 / 聊天 / 跟随）

**右侧边栏角色 tab = 世界角色头像列表**（`characters/` 目录扫描）。三个能力：

| 能力 | 操作 | 结果 |
|---|---|---|
| **导航** | 点角色头像 | 跳到该角色所在的场景（切层 + 相机定位到角色，穿越动画） |
| **聊天** | 点头像旁的聊天按钮 | 在角色当前所在场景与他进入**对话遮罩**（等价于画布上单击该角色头像，见 doc-06 §3） |
| **跟随** | 点跟随开关 | 开启/关闭"角色跟着玩家"：开启后玩家切换场景时，角色的**在场状态**同步到玩家所在层，画布上出现该角色头像 |

**跟随的语义**：
- 跟随是**运行时在场状态**（DB 状态层），不是文件搬移——角色目录（`characters/<名>/`）不移动，只是"此刻他在你身边"；
- 玩家主动开关（角色 tab 每个角色一个跟随钮）；切换场景时系统把角色在场位置顺延到新层；
- 作家可感知跟随状态变化，叙事回应（"老周跟着你进了城……"）；
- 跟随与懒灵魂不冲突：跟随只是"在场"，被点击聊天时才 spawn agent。

### 4.3 委托协议（profile：`scene-init`）

| 判定 | 内容 | 理由 |
|---|---|---|
| **亲自写** | 剧情细节：对话、关键道具、伏笔、玩家的即时体验 | 质量与准确性优先——"交给外包会漂移" |
| **委托** | 全新内容的从零→100：新城镇/新区域/大量生成 | 发散内容，体力活 |

**委托机制 = 子代理 + 可委托 profile**：作家用 `subagent` 工具调 `scene-init`（`delegatable: true`），给 brief（目标/风格/约束/参考），子代理在独立上下文里写盘（目录 + 布局 + 物件 + 文件真相），回报三行摘要。**同一 profile 也被引擎直唤复用**（玩家建目录 / 进 stub 层给需求），见 **doc-11**。

**验收 = 摘要过目**：默认信任，子代理回报摘要（路径清单+一句话摘要），作家过目一遍；不满意 → 重 roll 或顺手小改。

## 5. 单轮互动管线（作家侧，2026-09-10 定稿）

**作家 chat history 不进画布，只有 chalk 落板。** 单轮（1 Turn）四个阶段：

| 阶段 | 作家动作 | 落什么 |
|---|---|---|
| **Hook 上下文注入** | 玩家输入动作（`[user] 我走上去`）→ 底层 Hook 自动注入"当前场景目录下有什么文件"，让作家感知视口内已有的物件/旧组件/线索 | — |
| **① 正文落板** | 对话通道中响应（`[AI] 让我想想……`）→ 立即 `[chalk]` 写下本轮剧情正文（落盘 `xxx.md`）。**只专注叙事，不做复杂数值计算** | 正文 chalk 文件 |
| **② 回写修饰** | `[edit]` 对刚生成的 chalk 文件二次补充：frontmatter 注入 status（数值更新）、choice（玩家下一步按钮）、roll_dice，顺带润色正文 | frontmatter 元数据 |
| **③ 场景物件演化** | `[write]` 生成新剧情组件（场景里新掉落的信件 letter.md、谜题等）；`[edit]` 更新旧组件（改旧道具描述、移除被拿走的关键物品） | 新组件文件 / 旧组件更新 |
| **④ 轮次收敛** | 输出轻量总结（`[AI] 好了，简短总结当前场景……`），自言自语，回合结束，等待玩家下一步 | — |

**画布呈现布局（单轮）**：
- **左侧**：主剧情 chalk——当前轮次生成的核心板书，正文自上而下展开。正文里如果出现线索词并支持 md link 格式（如 `[钥匙](./钥匙.md)`），可**自动建议**连一条动态关系线，指向右侧渲染在画布上的对应物件卡（最终是否连线由作家用 `link` 工具确认/统一管理，见 doc-10 E13）。
- **右侧**：连线组件（Component）——`write` 生成的线索卡片（如右上角带图钉或角标的纸片），承载具体物件的沉默细节。
- **下方**：Choice 选项槽——frontmatter 里声明的 choice 选项，整齐排列在主板书正下方，作为可点击的行动卡片供玩家点击推进下一轮。

**四个阶段在对话通道里的样子**：作家在对话通道的中间语言（让我想想/好，让我更新场景/好了，总结）**绝不进画布**——画布上只有 chalk 落成的正文 + 组件 + 选项。

### 5.1 作家感知变化：事件注入，不是 diff（2026-09-11 定案）

> **结论先放**：玩家/世界的一切行动先落**事件表**；作家**不读 diff、不被推送**——只在玩家下一轮输入触发的 **Hook 上下文注入阶段**收到一段人话化的 **system reminder**（"玩家把「铜钥匙.md」放进了自己的背包"）。**不打断、不自动起 turn、不给文件差异。**

| 项 | 定案 |
|---|---|
| **事件源** | 一切写世界动作统一经引擎动作层 → 追加事件表：背包拖拽（=move，§8.3）、背包→场景放回、进入新层、角色跟随开关、上帝模式改文件 |
| **注入时机** | **不打断**。只挂在玩家下一轮输入触发的 Hook 上下文注入阶段（本 § 的阶段 Hook），作为固定位置的"世界动态"段 |
| **注入形态** | 人话陈述句，无 diff、无路径清单噪音。**合并去重**：同类事件（短时间连续拖拽 / 进出）加总成一句；N 轮未被提及自然过期丢弃 |
| **权威性** | 事件表 = 世界变化的历史。全量落 `.airpworld/history.db`（§8.6）；注入只取"自上次作家发言以来"的增量段 |

**事件表条目（最小 schema）**：

```json
{ "at": "2026-09-11T10:00:00Z",
  "type": "player_moved_item",       // player_moved_item / player_dropped_item / player_entered_layer / player_followed_char / roll_resolved / god_patched_file / writer_chalk
  "detail": { "from": "world/旅馆/铜钥匙.md", "to": "player/铜钥匙.md", "by": "player" } }
```

**注入示例（作家下次发言时收到的 reminder 形态）**：

```
[世界动态]
- 玩家把「铜钥匙.md」从柜台拿到了自己的背包里。
- 玩家掷骰：检定「推理检定」掷出 62（>50 通过）。
- 玩家刚切到「Abandoned Orchard」层。
- 老周还在柜台边（跟随中）。
```

**为什么够**：作家的知识来源本来就该是"我记得发生了什么"，不是"我能读所有文件"——这是懒加载哲学（§1）在作家感知上的一致性延伸。diff 是给调试者的，不是给叙事的。

| 决策 | 共识 |
|---|---|
| **开世界** | 模板世界为主 + UGC（玩家=创作者），AI 辅助生成骨架（降低写设定门槛），玩家上帝模式随时增删改 |
| **单机/多人** | 单玩家世界（一个世界 = 一个玩家的私人世界，叙事最纯粹，最符合懒加载：一个玩家=一个视点） |
| **时间与存档** | 剧本时间 + 记忆持久化（文件即世界状态，跨会话继续） |
| **平台** | **本地开源自部署 + 云端托管服务**。代码开源，用户可自行部署；官方提供托管版（增值服务）。浏览器 Web 应用 |
| **世界存储** | 分层存储：内容层走本地文件系统（云端版走 S3），状态层走 SQLite（云端版走 PostgreSQL）；"路径即 id"钉死两层。详见 §8 |

## 7. 组件与扩展系统

### 7.1 基本概念

| 术语 | 定义 | 例子 |
|---|---|---|
| **扩展（Extension）** | pi-rp 扩展，TypeScript 模块，有代码能力，可注册工具/事件/命令/组件 | 战斗系统扩展、天气系统扩展、letter 组件注册 |
| **组件（Component）** | 扩展注册的一种能力，有渲染逻辑和交互逻辑，实例为 `type: component` 的 md 文件 | letter、chess、puzzle-box、lamp |
| **叙事辅助（frontmatter）** | **不是组件**——状态/选项/骰子，缠在 `type: chalk` 文本的 frontmatter 上，类 md 表格渲染 | roll_dice / choice / status |
| **素材（Asset）** | 纯数据，固定格式，无代码 | 世界模板、角色 profile、主题包、场景背景图 |

**组件定位（2026-09-11 升级）**：**组件是叙事细节补充，同时是传统冒险解谜玩法的实体承载者。** 叙事骨架由旁白板书搭起，组件为叙事铺垫沉默细节；在此基础上，组件支持接受玩家背包道具的拖拽出示（`use_item_on`，如钥匙开地窖锁、信件投递），作为与 choice 并行的剧情推进通道。推进既靠 choice 选择，也靠以物解谜。

扩展是"引擎层面的插件"——加载在世界引擎进程，影响整个世界的运行规则。扩展注册的工具按角色过滤分发（作家看到作家工具，角色看到角色工具）。

### 7.2 扩展能做什么

| 能力 | 说明 | 例子 |
|---|---|---|
| **注册工具** | 给作家/角色增加新工具 | 战斗系统（`resolve_combat`）、天气系统（`advance_weather`） |
| **拦截事件** | 在工具调用/世界事件前后插逻辑 | 角色离开场景时自动清理状态 |
| **注入上下文** | 往 agent 提示词里注入自定义数据 | 给每个角色加一个体力值，值实时更新到上下文 |
| **操作世界状态** | 读写世界文件、角色卡、物件状态 | 扩展维护的额外 dashboard 数据 |
| **注册自定义事件类型** | 定义新事件，其他扩展或 agent 可以监听/触发 | "日落到黑夜"事件，触发角色夜间行为 |
| **注册自定义命令** | 玩家在聊天框里输入 `/` 开头的命令 | `/roll` 骰子、`/inventory` 查看背包 |
| **注册自定义组件** | 注册新的交互组件类型，定义渲染逻辑和 schema | letter 组件、chess 组件、puzzle-box 组件 |

### 7.3 扩展的声明、分发、安全

- **声明**：世界 manifest（world.json）`extensions` 数组；`optional: false` 开世界必须加载，`optional: true` 可选。
- **分发**：npm 包（`npm install @airp/combat-system`）、git 仓库（`git:github.com/user/repo@v1`）、世界包内嵌、hub 市场。
- **安全**：默认全权限，安装时有提示，用户自行判断信任来源，不做沙箱（同 pi-rp）。

### 7.4 万物皆 md：渲染路由

**一切内容都是 `.md`，frontmatter 的 `type` 字段决定前端行为。**

前端遍历目录的逻辑：
```
遍历目录：
  README.md         → 目录描述，读 frontmatter + 正文（type: readme，可选 cover）
  *.json           → 不渲染，功能区可编辑（配置）
  *.yaml           → 不渲染，功能区可编辑（状态/dashboard）
  *.md             → 读 frontmatter，按 type 路由
  *.html           → iframe 渲染，读 <meta description> 做摘要
  .airpworld/      → 系统目录（assets/history.db/canvas.db/agent/），不直接遍历
  其他             → 按类型处理
```

| type | 前端行为 | 例子 |
|---|---|---|
| `chalk` | 长在画布上的文字 + **frontmatter 渲染**（choice/status/roll_dice 折叠表格）；专属快速工具 | 旁白正文、环境描述、剧情推进 |
| `component` | 渲染为可交互组件（component 字段指定渲染器） | 信、谜题盒、棋盘、消息窗口 |
| `readme` | 目录描述，显示场景标题/摘要/配图 | README.md |
| `asset` | 加载资源（ref 指向 `.airpworld/assets/`） | 背景图、角色立绘、音乐 |
| 无 frontmatter | 纯叙事文本 | 日记、便签、留言 |
| `.html` | 直接 iframe 渲染，读 `<meta description>` 做摘要 | 复杂几何图、动态连线图、粒子效果 |
| `.json` | 不渲染，功能区可编辑 | 配置 |
| `.yaml` | 不渲染，功能区可编辑 | 状态/dashboard |

**chalk frontmatter 渲染约定（2026-09-10）**：
- `choice`：渲染为选项卡片组，每个选项可点击 → 作为玩家下一轮输入推进；
- `status`：渲染为折叠表格（类 md 表格），键值对展示状态快照；
- `roll_dice`：渲染为**骰子卡**——玩家点击掷出、演出特效、结果回写（见 §3.1「骰子协议」）；
- 三者都可折叠，绑定在具体叙事文本下方，随剧情走。

功能区有一个专门的编辑器面板，玩家可以统一发现并编辑当前目录下的 `.json` 和 `.yaml` 文件。

## 8. 世界文件结构与存储

### 8.1 分层存储：内容走文件系统，状态走 SQLite

> 原则不变的是"内容走文件系统，状态走 DB，路径即 id 钉死两层"。

对比 Nodesign 的教训（项目级单一 board.json → 对账/并发/层级三大痛点），AIRP 采用**分层**：

| 层 | 本地版 | 云端版 | 存什么 |
|---|---|---|---|
| **内容层（真相）** | 本地文件系统（`<worldId>/` 根目录） | 对象存储（S3，key=路径） | 场景目录、角色卡、md 文本、图片、记忆文档 |
| **状态层** | SQLite（`<worldId>/.airpworld/canvas.db`） | PostgreSQL | 画布布局坐标、角色在场、玩家视角——运行时状态 |
| **历史层** | SQLite（`<worldId>/.airpworld/history.db`，含 session 表 + events 表） | PostgreSQL（session 表 + events 表） | agent session 记录 + 操作行为、角色对话、世界事件，含完整内容 |

**世界自包含**：一个世界 = 一个 `<worldId>/` 目录（或云端一个 S3 前缀）。整个世界可整体打包为 `.airpworld.zip` 包——UGC 分享、云迁移、备份用同一个动作。
**历史层**：pi-rp 的 SQLite 后端已原生支持 `entries` 表（session entry 存储），AIRP 在其上加 `project_id` 字段实现跨 session 查询——AIRP 的 world 即 pi-rp 的 project，一个世界所有 agent 的 session 和事件都通过 `project_id` 关联。

### 8.2 为什么不用纯 DB

1. **工具链断裂**：git/系统编辑器/diff/agent 的 Read/Write/Edit/Glob/Grep 全要桥接；
2. **渲染通道断**：HTML 组件的资源引用、下载/发布站点都要现写导出器；
3. **UGC 生态断**：模板世界 = 拷目录；DB 世界 = 导出/导入格式；
4. **迁移与锁定**：世界困在 DB schema 里，演进要迁移脚本；
5. **"纸的隐喻"破**：手账风的"一张纸=一个文件"变成伪装的 UI。

### 8.3 存储抽象层（worldStore）

**MVP 阶段就要做**：不散落文件系统/SQLite 调用，收进 `worldStore` 模块：

```typescript
interface WorldStore {
  // 内容层（文件系统）
  readFile(path: string): Promise<string | Buffer>
  writeFile(path: string, content: string | Buffer): Promise<void>
  deleteFile(path: string): Promise<void>
  listFiles(prefix: string): Promise<string[]>
  // 移动语义（2026-09-11：一切搬移统一走 move，前端与 agent 绝不裸 mv）
  move(from: string, to: string): Promise<MoveResult>
  // MoveResult = { ok, rewrote: string[], dangling: LinkRef[], event: WorldEvent }
  //   rewrote = 已被就地重写的引用；dangling = 无法安全重写的断链记录；
  //   event = 追加进事件表的世界事件（§5.1 作家感知）

  // 状态层（SQLite / PostgreSQL）
  query(sql: string, params?: any[]): Promise<Row[]>
  // 历史层（`.airpworld/history.db`，复用 pi-rp 的 entries 表 + project_id 字段）
  appendEntry(sessionId: string, entry: NewEntryRow): Promise<void>
  queryEntriesByProjectId(projectId: string, filter?: EntryFilter): Promise<Entry[]>
  queryEntriesBySessionId(sessionId: string, filter?: EntryFilter): Promise<Entry[]>
  appendSession(session: AgentSession): Promise<void>
  querySessions(filter: SessionFilter): Promise<AgentSession[]>

  // 世界元数据
  getManifest(): Promise<WorldManifest>
  updateManifest(updates: Partial<WorldManifest>): Promise<void>
}
```

本地版实现 = fs + better-sqlite3（通过 pi-rp 的 `@earendil-works/pi-session-backend-sqlite-node` 包），云端版实现 = S3 SDK + pg。接口一致，部署时切换实现。

**移动语义与引用重写（move pass，2026-09-11 定案）**：背包拖拽（场景→背包 / 背包→场景）、上帝模式搬移、目录重构——**全部经引擎 `move()` 统一处理，前端与 agent 绝不裸 `mv`**。`move()` 三件事一次做完：

1. **物理搬移**（本地 fs / 云端 S3 同 key 语义）；
2. **引用重写 pass**——扫描世界内所有指向被移动路径的 md link（`[钥匙](./钥匙.md)`）、组件 ref、world.json 引用，相对路径就地重写；关系线存 canvas.db、不走文件引用，移动时由 `link` 工具按端点 re-link（doc-10 E13）。
3. **落账**——产出 `MoveResult` 记入历史表；`dangling`（改不动的引用，如玩家背包里指向场景、跨层无法安全重写的链接）记为**断链记录**：前端对断链渲染"已被带走……"兜底态，同时作为世界事件（§5.1）供作家下轮感知。

> 教训来源："md link 自动连线"（§3.2）在物品被 mv 走之后会直接 404——**移动不是裸文件操作，是有引用图的世界操作**。统一由引擎处理后，任何新增移动入口（背包 / 重构 / 拖拽）都自动获得同一套行为，不再每次踩坑。

### 8.4 世界 manifest（world.json）——世界级配置

> **层级不在这里（2026-09-11 修正）**：`world.json` 只写**世界级**事实（名字、题材、角色清单、世界默认材质、扩展）。**层级拓扑由目录树扫描得出**——`world/**/` 下每个目录就是一个层，目录里的 `README.md` 是它的场景配置（有 README = 已写层；没有 = `stub` 懒加载层）。曾在 `world.json` 里声明 `layers`，那是第二个真相源，与目录漂移过（manifest 写 `world/baker-street/abandoned-orchard`、目录却是 `world/abandoned-orchard`），已删除。派生逻辑：`packages/shared/src/store/layers.ts`。
>
> **唯一 manifest 约定**：世界级配置 `world.json` 是唯一的 manifest 文件——**不存在** `world/config.json` 之类承载 manifest 职责的副本（旧样例 holmes-world 曾双写，已合并为一份）。场景级 `config.json`（灯光/音乐/氛围）仍允许，但只作纯配置、不参与世界结构定义；材质身份由各层 README 的 frontmatter 声明（世界默认材质在顶层 `material`）。

```json
{
  "id": "com.example.my-world",
  "name": "我的世界",
  "version": "1.0.0",
  "schema": 1,
  "description": "一个校园恋爱题材的互动叙事世界",
  "author": "玩家名",
  "cover": "cover.png",
  "tags": ["校园", "恋爱", "日常"],
  "genre": "school-romance",
  "material": "parchment",
  "extensions": [
    { "id": "airp:letter", "version": ">=1.0.0", "optional": false },
    { "id": "airp:chess", "version": ">=1.0.0", "optional": true },
    { "id": "community:weather-effects", "version": "^2.1.0", "optional": true }
  ],
  "characters": [
    { "id": "watson", "home": "world/baker-street", "role": "companion" },
    { "id": "constable", "home": "world/baker-street", "role": "npc" }
  ],
  "createdAt": "2026-09-11T00:00:00Z",
  "updatedAt": "2026-09-11T00:00:00Z"
}
```

| 字段 | 类型 | 说明 | 必需 |
|---|---|---|---|
| `id` / `name` / `version` / `schema` | string / number | 世界唯一 id（`com.example.my-world`）、名字、版本、manifest schema 版本（演进用迁移） | ✅ |
| `description` / `author` / `cover` / `tags` / `genre` | string / string[] | 世界元数据（启动器 / UGC 市场展示） | `description`/`tags` ✅ |
| `material` | string | 世界默认材质（`doc-04 §6` 材质词汇表；各层 README 可覆盖） | 可选 |
| `extensions[]` | `{ id, version, optional }` | 扩展声明（§7.3）：`optional: false` 开世界必须加载 | ✅ |
| `characters[]` | `{ id, home, role? }` | 世界角色扫描清单（§4.1 / §4.1.1）：`id` = 角色目录名，`home` = 初始所在层 key（角色 tab 导航 / 跟随的起点），`role` = companion/npc 语义提示 | ✅ |

> **没有 `layers` 字段**：层级从目录树派生（见上）。`holmes-world/world.json` 即按此 schema（2026-09-11 起不再声明 layers）。

### 8.5 状态的两分法（DB vs 文件的判定准则）

**状态进 DB 还是进文件，判定标准是"有没有代码逻辑要消费它"：**

| 类型 | 例子 | 载体 | 理由 |
|---|---|---|---|
| **架构状态**（代码逻辑消费） | 目录内容、物件 x/y 坐标、层级、在场 | DB | 系统要查询/渲染/导航，必须结构化 |
| **世界内容状态**（纯展示/叙事） | 好感度、状态快照、journal、角色记忆 | **叙事文本本身（chalk frontmatter / md 文件）** | 没有严格逻辑，agent 维护、随时可改；**没有独立的状态文件** |

**2026-09-10 更新**：
- **状态快照（status）** = **叙事 frontmatter**（`type: chalk` 的 `status.data` 键值对），随叙事文本走，类 md 表格渲染，可折叠。**不存在独立的状态文件，没有状态栏 UI**。
- **journal** = 叙事日志目录（`journal/`），按 `序号-世界时间-标题.md` 命名，agent 续写不重写；
- **角色记忆** = 角色自己目录里的记忆文件（`characters/旅店老板/memory/` 下自由组织），角色/作家共同维护；
- 世界内容状态的更新**不需要专门的状态工具**——作家/角色直接用原生 `read`/`bash`/`edit`/`write` 维护（状态快照就在叙事文本的 frontmatter 里，作家 edit 时顺手更新）；引擎侧只靠 fs.watch 感知文件变化（黑板的免轮询推送）。

### 8.6 版本与回滚：快照 + 事件（不用 git）

| git 概念 | AIRP 替代 |
|---|---|
| commit（原子快照） | **世界快照**：剧情节点/会话结束/玩家重要操作前，打包 `.airpworld.zip` 存快照目录 |
| log（历史叙事） | **历史表**（SQLite `.airpworld/history.db`：agent session 记录 + 谁在何时做了什么，**含完整内容**） |
| branch（分叉） | **派生**：UGC fork = 拷贝世界快照（断链独立） |
| checkout（回滚） | **快照回滚**：切回某个世界快照（原子、一致，一条操作） |
| diff（差异） | **历史表回溯**：两个快照之间的事件差异 |

**关键设计：历史表 entries 存完整内容，不怕与文件重复**——完整内容是可回溯的前提（回溯=一条 SQL）；文件是可变的"当前工作副本"，历史表 entries 是不可变的"历史记录"。存储便宜，数据不一致的 debug 成本贵。

**快照打点策略**：剧情节点（作家主动打）、每会话结束、玩家重要操作前（上帝模式大改前）。存关键帧，不逐秒存。

**历史表 vs 文件（行为 vs 结果）**：操作行为（session 记录/记记忆/写 journal/说一句话）→ DB 历史表 entries；操作结果（记忆内容/journal 内容/角色卡）→ 文件。

## 9. 工具参数规格（doc-07 并入，2026-09-10 更新）

> 约定：参数 camelCase；可选参数末尾加 `?`；所有工具返回 `{ content: [{type:"text", text}], isError? }`；部分工具有事件广播。

### 9.1 作家工具

**文件操作**
```
read / bash / edit / write   // 原生工具
delete: { path: string | string[] }
```

**委托**
```
subagent / subagent_profiles
```

**画布感知**
```
read_canvas: { path?: string | string[] }
  // 以渲染视角读画布：md 去 frontmatter 只展示正文；html 只读 <meta description>；
  // 按目录结构顺序返回，含子目录 README.md；含方位关系
view_canvas: { path?: string, mode?: center|..., from?: player|character_id }
  // 返回画布截图（image content block）
```

**板书（叙事主体）**
```
chalk: { path?: string, content: string, link_to?: string, append_to?: string }
  // 写长在画布上的叙事正文（type: chalk 的 md 文件）
  // append_to 自动设置 frontmatter 连接到前一条；link_to 自动设置连线
  // 紧随的 [edit] 调用往 frontmatter 注入 status / choice / roll_dice（见 §5 单轮管线）
  // 作家写 roll_dice 时不写 result；expect 写引擎可读的通过条件（如 ">50"，必须带引号）；result 由玩家点击骰子后引擎真随机回写并按 expect 判定（见 §3.1「骰子协议」）
```

**叙事辅助**
```
generate_image: { prompt: string, style?: string, width?: number, height?: number }
  // 生成图片，落盘到 assets/
```
> ~~roll_dice / ask_option 不再是独立工具~~——收编为 chalk frontmatter（`roll_dice` / `choice`），随叙事文本走，类 md 表格渲染。

**组件**
```
get_component: { component: string | string[] }   // 返回组件 schema/用法/示例
show: { component: string, params?: object }      // 演出型组件，纯展示不落盘
```

**目录重构**
```
restructure_preview: { scope, packs?, unpacks? }
confirm_restructure: { plan, readmes }
```

## 10. Nodesign → AIRP 借鉴映射（2026-09-10 更新）

| Nodesign 机制 | AIRP 用法 |
|---|---|
| 无限画布（单 transform 世界层/相机/手势仲裁） | 直接复用整套画布底座 |
| 卡片 = 磁盘投影（id 即路径） | 世界物件 = 文件投影；层级 = 目录；**层级画布是 Nodesign 没想到的扩展** |
| pending-changes 缓冲（手势产载荷、消息是指路牌） | 玩家/上帝的操作进缓冲，作家拉取处理 |
| 视点上报表（"这个/这里"消解） | 作家每回合知道玩家在看哪——叙事聚焦玩家视点 |
| 板书（agent 写的可编辑真实文件） | **作家的叙事正文**（chalk），**叙事文本是唯一主角** |
| 黑板选项板（可点按钮写在 markdown 里） | **choice frontmatter**——选项就是叙事文本的一部分 |
| 精灵 + 在场感（位置/正在做什么/台词） | ~~角色精灵~~ → **类光标 + 圆形头像**（不做动画演出） |
| 眼睛模式（复用同一渲染真相截图） | view_canvas——作家/角色看到的世界 = 玩家看到的世界 |
| 幻影物件（异步产物先占位、座位过户） | "场景初始化器正在这里生成"的占位（doc-11 §3.4） |
| 关系线（`link` 工具管理） | 地点道路、人物关系、物品来龙去脉——世界拓扑；**线条归 canvas.db 状态，作家用 `link` 工具统一管理，不从 md 派生**（doc-10 E13） |
| frame-freeze 冻结渲染循环 | 世界懒加载的渲染层实现（不看不渲染） |
| 圈选/评论/直接编辑（Nodesign 全量） | 上帝模式的直接操作手感 |
| ~~角色直达 + 舞台状态~~ | ~~独立角色进程与统一通信模型~~ → **对话遮罩 + 小天地**（按需 spawn，不做编排） |
| 骰子/舞台状态表 | **roll_dice / status frontmatter**——绑在叙事文本上，不是独立组件 |
