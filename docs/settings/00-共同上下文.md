## 1. 一句话问题

**「玩家一进门 / 一选项，作家立刻起一轮」是 niko 侧的一个实现选择（commit `f914d0a`，`routes/world.ts` 的 `dispatch`），它绕过了 I1 初始化内核、也违反 doc-21 §5.5；而 main 侧的 I1 前端触发线（`airp_init`）在合并中被丢掉，只剩服务端 handler。** 玩法上「开门即生成」的 Demo 节奏又是需要的，于是不能一刀切删掉——**做成一个每世界可配的三态开关，默认回到契约（`off`）。**

一句话修法：**`<worldRoot>/.airpworld/settings.json` 存 `{ autoWrite }`；服务端 `/api/world-settings` 读写；`/choice` 按档决定是否 `dispatch`；`/enter-layer` 永不 `dispatch`（门回归 I1，前端按 `first` + 开关发 `airp_init`）。**

## 1bis. 交互后果总口径（唯一真相源，全仓文档以本节为准）

**2026-09-14 补充：显式直接动作。** 六世界体验版的 `choice_actions` 将阅读、拿取、材料预览、进层意图、角色入口、短反馈与作家请求分开。声明动作由 HTTP 外层组合既有动作，不经过自动作家分发；即使 `scenes-and-choices` 也不会把读信变成作家回合。`writer` 声明只填输入框，Send 才执行。`dice_outcomes` 可在原骰子卡确定性写回短结果与下一组选项，不自动生成新剧情。下面旧选项／裸骰子表仍是**无此声明**时的口径；三态枚举与 I1 不变。详见 [六世界选项解耦与骰子解谜](../gameplay/六世界选项解耦与骰子解谜.md)。

**玩家的任何交互（choice / 掷骰 / 用物 / 开门 / 拖卡 / 上帝动作）默认只产生「一条事件」，不直接产生叙事后果。** 叙事后果（作家起一轮、写新 chalk、改文件）一律**可选**，由每世界开关 `autoWrite` / `use_item_on` 破例登记等**显式档位**决定。**2026-09-15 niko 改口：出厂默认 `autoWrite = scenes-and-choices`**（玩家点了选项就期待故事往前走，不该再按一次 Send）；`off` 仍是可选的安静档，下文「默认」指的是 `off` 档的语义，不是出厂值。

### 为什么这是默认，不是保守

1. **若干预同时发生会互相打架**。玩家掷一次骰子作家立刻起一轮、玩家再打字又起一轮 → 画布上出现两篇抢戏的板书（`docs/development/后端实现计划.md §T4.2` 的原话）。
2. **事件是唯一变更来源，不是触发器**。`doc-21 §5.5`：「一条事件落库**永远不触发** agent 的一轮」；`doc-05 §5.1`：「不打断、不自动起 turn」。作家在**玩家下一轮输入**的 Hook 注入阶段，从事件段里读到这些事实再回应。
3. **交互是「记录事实」，叙事是「作家的活」**。两者耦合会把叙事决定权交给一次拖拽/一次点击（`docs/tools/08 §13` 的完整论证）。

### 一张表：每个交互的默认与破例

| 交互 | 默认（`off`） | 可选加强 | 开关/登记 |
|---|---|---|---|
| 玩家选项 `/api/choice` | 只落 `choice_selected` | 起作家一轮 | `autoWrite=scenes-and-choices` |
| 进未写场景 `/api/enter-layer` | 只落 `layer_entered` | **I1 初始化器**物化场景（**不是**作家一轮） | `autoWrite ∈ {scenes, scenes-and-choices}` |
| 掷骰 `/api/dice` | 只落 `roll_resolved` | —（`doc-20 §7`：引擎裁决，本就不打断） | 无 |
| 用物 `/api/use-item` | 只落 `use_item_on` + 组件 handler 即时可见 | 是否破例即时叙事，**待拍板** | `docs/tools/08 §13`；`后端实现计划.md §11 #4` |
| 上帝动作 `/api/god-action` | 只落 `god_patched_file` | — | 无 |

**`use_item_on` 的边界**：**确定性 handler（锁开没开）与叙事后果（门后有什么）是两件事**。handler 结果立即在卡面可见，这是前端与组件的事、**不需要作家**；叙事后果仍默认留给下一轮（`docs/tools/08 §13.4`）。

### 写文档时的措辞纪律

上表之外**任何**「X 之后作家/引擎就……」的说法都 MUST 先问「默认还是可选」，并在句中明写档位。**禁止**把「直接产生后果」写成无条件的定案——这正是本仓 2026-09-13 数处文档漂移的根因。

## 2. 冻结契约

### 2.1 三态语义（唯一真相源）

| `autoWrite` | 进未写场景（门） | 玩家选项（choice） |
|---|---|---|
| `off` | 只落 `layer_entered`，作家在玩家下一轮注入里看见 | 只落 `choice_selected`，同上 |
| `scenes` | 前端发 `airp_init` → I1 内核建场景 | 只落 `choice_selected` |
| `scenes-and-choices`（**出厂默认，2026-09-15**） | 同 `scenes` | 服务端 `dispatch` → 作家起一轮 |

**为什么门与选项分开**：两者是**不同性质的工作**。门 = **场景物化**，是 I1 的活（`scene-init` preset + 结构化 brief + 产物校验 + W2 兜底 + 并发在飞锁）；选项 = **叙事推进**，本来就是作家的活，I1 没有也不该有 choice 处理器。合成一个布尔会逼出「要么两个都自动、要么两个都不自动」的假二分。

### 2.2 纯函数（`packages/shared/src/schemas/world-settings.ts`）

```
AutoWriteSchema     = enum(['off', 'scenes', 'scenes-and-choices'])
WorldSettingsSchema = strict({ autoWrite })
DEFAULT_WORLD_SETTINGS = { autoWrite: 'scenes-and-choices' }   // 2026-09-15 起；此前为 'off'
startsSceneInit(autoWrite)   ⟺ autoWrite ∈ {scenes, scenes-and-choices}
startsChoiceTurn(autoWrite)  ⟺ autoWrite === 'scenes-and-choices'
```

**MUST NOT** 在别处再写一份档位判断——服务端与前端同 import 这两个谓词。

### 2.3 存储（每世界一份）

- 路径：`<worldRoot>/.airpworld/settings.json`，内容 `{ "autoWrite": "off" }`（原子写：`.tmp` + `rename`）。
- **为什么每世界**：它决定那个存档的节奏，跟 `model-preferences.json` 同族、同为**存档属性**；放 `localStorage` 会让服务端看不见（服务端才是决定是否起一轮的一方），两边必漂。
- **MUST 当作不可信输入**：本文件用户可手改，用 `.strict()` + `.partial()` 解析，**任何非法值/坏 JSON 一律 fail-soft 回默认**（`off`）——绝不因一个手改文件把路由搞崩。
- 读：`apps/server/src/engine/world-settings.ts::readWorldSettings`；**写（唯一对外写口）= `updateWorldSettings`**（读盘 → 合并 patch → 原子写）。`writeWorldSettings` 降为它内部调用的**整体写原语**，MUST NOT 被路由直接调用——路由直连它就等于绕过 §2.4 的 patch 语义。

### 2.4 端点（唯一读写口）

请求体是 **patch（部分更新）**，**不是整体覆写**——这是 `docs/command/00-共同上下文.md §10.13` 冻结的正确性缺陷修法，也是本条与那份文档唯一的语义交点。

| 方法 | 路径 | 体 | 返回 |
|---|---|---|---|
| GET | `/api/world-settings` | — | `{ world, autoWrite }`（无存档 → 409；缺失文件 → 默认） |
| POST | `/api/world-settings` | **patch：可只带 `autoWrite`，也可只带将来新增的任意子集**（`WorldSettingsPatchSchema`） | `{ world, ...合并后的完整设置 }`（非法 → 400；`{}` 合法，等于不变） |

**为什么是 patch 而不是整体覆写**（`§10.13` 的三层定性，此处只写结论）：整体覆写的正确性建立在「`WorldSettings` 恰有一个字段」这个**巧合**上——调用方只要送出自己关心的字段，其余字段就被静默重置。**任何人给 `WorldSettingsSchema` 加第二个字段，那一次 POST 就会把它清掉**，且是 fail-open 方向（例如把一个功能开关重置回默认）。patch 让「省略」与「重置」在语义上分开：**省略 = 保持原值**，要清零 MUST 显式送值。

| 环节 | 冻结形态 |
|---|---|
| 请求体 schema | `packages/shared/src/schemas/world-settings.ts::WorldSettingsPatchSchema`（= `WorldSettingsSchema.partial()`，**strict 继承** ⇒ 未知键 400，不会被静默丢弃；全空 `{}` 合法） |
| 写入器 | `apps/server/src/engine/world-settings.ts::updateWorldSettings`（读盘 → 合并 patch → 原子写；`writeWorldSettings` 仍是整体写的原语，只被它调用） |
| 路由 | `apps/server/src/routes/world.ts` 的 `POST /api/world-settings`：`WorldSettingsPatchSchema.safeParse` → `updateWorldSettings`；返回**合并后的完整对象**（含未在请求体里出现的字段） |
| 前端 | `apps/web/src/state/useWorld.ts::reloadSettings` / `saveSettings` **保留服务端返回的整个对象**（不再只挑 `autoWrite`） |

> **反模式（本批的真实缺陷形态）**：POST 声称是"设置端点"、实现却是"写整个对象"，而前端只送一个字段——两者今天的等价性是巧合、不是设计。**任何"MUST NOT 覆写未知字段"的说法都 MUST 落到 `updateWorldSettings` 这一处，不得在别处再写一份合并逻辑。**

### 2.5 门控点（谁读这个开关）

| 点 | 位置 | 行为 |
|---|---|---|
| 门（建场景） | **前端** `apps/web/src/state/useWorld.ts::enterLayer` | 服务端 `/api/enter-layer` 返回 `first:true` 且 `startsSceneInit(settings.autoWrite)` → `sendSocket({type:'airp_init', kind:'scene', target, by:'player'})` |
| 选项（叙事） | **服务端** `apps/server/src/routes/world.ts` `/choice` | `startsChoiceTurn(readWorldSettings(store.worldRoot).autoWrite)` → `dispatch` |

**`/api/enter-layer` 的 handler MUST NOT 调用 `dispatch`**（回归契约：只 `enterLayer({layer})` 落一条 `layer_entered`）。门走 I1 内核，不走作家——这是 `docs/init/00 §2.4` 的 R2 路径。

> **与请求体语义的关系（MUST 一起读）**：上表两个门控点读的都是**服务端已合并的完整设置**。门控点本身不感知 patch——它只在 `updateWorldSettings` 落盘之后读到新值。**将来新增第三个字段时，patch 语义 MUST 与新增字段同批落地**，否则该字段会被前端的单字段 POST 静默重置（`docs/command/00 §10.13`）。

### 2.6 前端读取时机

- `useWorld` 挂载时 `reloadSettings()`；`App.loadWorld` 在**新存档激活后、进首个层之前**再 `reloadSettings()` 一次（开关是每世界的，文件在新存档的 `.airpworld/` 下）。
- `settings` 同时镜像进 `settingsRef`：`enterLayer` 是同步读（点击那一刻的 fetch 未必已落地）。

### 2.7 UI

`AgentSettings` 面板（niko 已建）新增一个 `<select>`，三档。**保存即 `POST /api/world-settings`**，失败静默保留旧值（`saveSettings` 抛错则 npm 层面不更新本地态——由调用方决定是否提示）。

## 3. 反模式（本批出现的真实错误）

- ❌ **把开关读在 `localStorage`**：服务端看不到 → 选项档门控在服务端无从判断。
- ❌ **在 `/enter-layer` 里保留 `dispatch`**：会绕过 I1 的 brief / 判空 / W2 兜底 / 并发锁，并让 `layer_initialized` 落两处（`docs/init/02` 已修过一次的双事件）。
- ❌ **门用作家 prompt 写场景**：作家人格 ≠ scene-init preset；产物无校验、无兜底。
- ❌ **档位判断散落各处**：必须走 `startsSceneInit` / `startsChoiceTurn`。
- ❌ **坏 settings.json 让路由 500**：必须 fail-soft 回 `off`。
- ❌ **把 POST 当整体覆写**：调用方送一个字段的子集、服务端写整个对象 ⇒ 其余字段被静默重置（fail-open）。MUST 走 `updateWorldSettings` 合并（`§2.4`、`docs/command/00 §10.13`）。
- ❌ **前端只挑 `autoWrite`**：`settingsRef.current = { autoWrite }` 把服务端返回的其余字段丢掉，等价于本机先把 patch 还原成覆写。MUST 保留整个对象。
