## 1. 一句话定位

**命令改了世界之后，agent 必须在「下一轮的事件段」和「本轮的 tool_result」两个地方各被告知一次，而且被告知的是「这件事已经有人做完了」，不是「这里有件事等你去叙述」——否则作家会把命令已经发过的奖励再发一遍。**

命令产生的事件会**自动**流进作家的事件段（经动作层执行、落普通事件、`actor` 是触发者、`turn` 是触发者的 turn），这条通路是既有管线的**免费产物**，不需要新代码。本文要解决的不是通路，而是通路上的**四处语义错位**，每一处都已核实：

| # | 错位 | 后果 | 本文的答案 |
|---|---|---|---|
| 1 | 契约 §5.3 声称同 turn 会「合成一组连贯事实」——**不成立** | 有人按错误的机制去实现"因果合并" | §3.0 核实结果；因果改由命令主语渲染承担（§3.6） |
| 2 | 命令事件的 actor 是玩家 → 渲染成「**The player** wrote a new page」（`events.ts:210-227`） | 作家以为玩家自己写了那份线索，进而以为"还有活" | §3.6 命令主语替换 |
| 3 | `next-step` 只看队尾一条（`next-step.ts:113-117`），命令事件把队尾顶掉 | **整条"下一步"消失**：掷骰那轮作家不再被告知去叙述判定 | §3.7 |
| 4 | 排他判据 `excludeActor` 的语义在命令接入后漂移 | 作家自己触发的命令后果**永不回显** → 重复发奖 | §3.8 同轮回执（确切结论见 §3.9） |

**核心判断**：世界命令进注入的正确姿势不是"多加一段"，而是「**改判据、改主语、改祈使、补一条同轮回执**」。任何试图新增第 7 个顶层 key、新增事件类型、或新增一节注入的做法，都在本模块的驳回范围内。

## 2. 完整 schema / 签名 / 字段表

本节是本文涉及的全部形状。**除 `commandReceiptText` 外全部是既有文件的增量改动，不新增模块。**

### 2.1 `detail.command` —— 命令归属的唯一判据

| 项 | 值 |
|---|---|
| 键名 | `command`（顶层 `detail` 的可选键） |
| 类型 | `string` |
| 必填 | 否。缺失 = 普通事件 |
| 默认 | 缺失 |
| 上限 | 48 字符（`01` 的 id 正则 `^[a-z0-9][a-z0-9-]{0,47}$` 的镜像） |
| 合法值 | `^[a-z0-9][a-z0-9-]{0,47}$` |
| 非法值 | **不报错**；`commandOf` 返回 `null`，该事件按普通事件渲染 |
| 谁写 | `04` 的每条效果落账时。**MUST NOT 写 `detail.by`**（理由见 §11 冲突 2） |
| 消费者 | 本文（渲染 / 祈使 / 回执）、`docs/hooks/03`（同一渲染器）、`05`（幂等的可选辅助） |

**为什么不用契约 §5.1 提议的 `detail.by = 'command'`**：`by` 这个键**已被占用**且语义不同——`layer_initialized` 的 `detail.by` 是闭枚举 `z.enum(['writer','player','engine'])`（`packages/shared/src/schemas/events.ts:99`），表示「谁跑了这次层初始化」（`packages/shared/src/actions/layer.ts:93`）。详见 §11 冲突 2。

**`detail.command` 能活过落账（已核实）**：`AppendEventArgs.detail` 的类型是 `WorldEventDetail<T> & Record<string, any>`（`schemas/events.ts:132`），而 `appendEvent` 的 `safeParse` **只用于通过/失败判定**，落库写的是 `JSON.stringify(args.detail)` 原件（`packages/shared/src/store/local-store.ts:697`）。额外键**不会被 zod strip**。

**非法值的错误文案**：无。这是**有意的**——注入侧铁律是「永远不能让一轮失败」（`docs/hooks/00` §11），而 `detail.command` 只影响一句英文的措辞，不是安全边界。非字符串 / 空串 / 超长一律降级为普通事件。用户可见文案不存在（玩家完全看不到这个字段）。

### 2.3 `EventWindowLine` 新增一个可选字段

```ts
// packages/shared/src/render/events.ts:28-44（现有形状，此处只列新增行）
export interface EventWindowLine {
  type: WorldEventType;
  layer: string | null;
  name?: string;
  actor: Actor;
  count: number;
  subject: string | null;
  text: string;
  /** NEW — 10 §2.3. The producing world command id, when this WHOLE group came
   *  from one. Absent for every ordinary event (never set to ''), so
   *  `'command' in line` is false in the common case — same discipline as `name`
   *  (events.ts:573). */
  command?: string;
}
```

| 字段 | 类型 | 必填 | 默认 | 上限 | 来源 |
|---|---|---|---|---|---|
| `command` | `string` | 否 | 缺席（不写该键） | 48 字符 | `commandOf(g.events[0])` |

**取组内第一条事件**（`g.events[0]`），与 `type` / `actor` / `name` / `subject` 的取法一致（`events.ts:499-511`），也与 `04` 的 `NextStepEvent` 投影一致。

**合并键必须同时加严，否则会撒谎**：一个组只有在**全部成员**都来自同一条命令时才能对外宣称 `command`。规则 1 的 `sameKey` 判定追加一项（`events.ts:473-480`）：

```ts
// NEW — rule 1's key becomes (turn, type, actor, command)
const sameKey = mergeable && prev !== undefined && prev.open &&
  prev.turn === e.turn && prev.type === e.type &&
  actorKey(prev.actor) === actorKey(e.actor) &&
  commandOf(prev.events[0]) === commandOf(e);   // ← 新增
```

**不加这个约束会怎样**：同一个 actor（例如玩家）在同一 turn 里「先手动写了一份笔记、再触发命令写了一份笔记」，两条 `entity_created` 会因同 turn + 同 type + 同 actor 合并成一个 `count: 2` 的组，而组只带一个 `command` → 渲染成「命令写了 2 页」，**其中一页不是命令写的**。理由与 `MERGE_EXEMPT` 同源（`events.ts:60-62` 注释）：合并**不得撒谎**。`MERGE_EXEMPT` 防「N 次独立动作被说成 1 次批量动作」，这里防「不同来源的动作被归给同一来源」。

### 2.5 NEW：`subjectPhrase`（渲染主语的唯一改动点）

```ts
// NEW — packages/shared/src/render/events.ts
/**
 * The sentence subject. For an ordinary event this is EXACTLY `actorPhrase`
 * (so every existing golden holds byte-for-byte). For an event produced by a
 * world command it names the WORLD as executor and keeps the actor as cause
 * (10 §3.6):
 *
 *   subjectPhrase({type:'player'},    'investigate-clue') -> 'The world, after the player acted,'
 *   subjectPhrase({type:'writer'},    'investigate-clue') -> 'The world, after the narrator acted,'
 *   subjectPhrase({type:'god'},       'investigate-clue') -> 'The world, after the world itself acted,'
 *   subjectPhrase({type:'character', id:'watson'}, 'x')   -> 'The world, after the character "watson" acted,'
 *   subjectPhrase(a, null)                                -> actorPhrase(a)          // unchanged
 *
 * Pure; never throws. Only the PRESENCE of `command` matters — the id itself is
 * never printed (10 §2.1: it is a judgement key, not narrative).
 */
function subjectPhrase(actor: Actor, command: string | null): string;

/** NEW — one-line helper: 'The player' -> 'the player'. Four of the five
 *  `actorPhrase` returns start with a capital; the `character` one is already
 *  lower-case (`the character "watson"`, events.ts:148), so `lowerFirst` is
 *  the identity there. The rule is therefore total for all five. */
function lowerFirst(s: string): string;
```

### 2.6 读取预算：**复用 `03` 的常量，不新增**

**`10` 不定义自己的预算常量。** 读侧的增量直接引 `03` 已导出的 `WORLD_COMMAND_EFFECT_BUDGET`（`03` 已定稿为 **24**，`docs/command/03` §6.2）：

```ts

import { WORLD_COMMAND_EFFECT_BUDGET } from '../commands/effects.js';   // 03 导出，本文 import
…
```

**为什么复用而不是另提一个常量（`03` 的论证，本文采纳）**：**同一个量只有一处文本**。若 `10` 另取一个 `8` 或 `16`，将来有人调 `WORLD_COMMAND_EFFECT_BUDGET` 时两处必然漂移——正是契约 §8 反模式 3（"把分档规则硬编码两遍"）的同类错误。

**量纲成立的前提（`03` 提供，本文依赖并 MUST 在实现里注释）**：

- 一个效果产出的世界事件 **恒 ≤ 1 条**：`createEntity`→`entity_created`、`editEntity`→`entity_edited`、`moveEntity`→`entity_moved`、`enterLayer`→`layer_entered` 各 1 条；而 **`linkCards` / `arrangeCards` 不落事件**（`packages/shared/src/actions/canvas.ts:204-246`）。
- 所以**一次触发新增的事件数上界 = 效果数上界 = 24**。
- `24` 是**展开后**的上界：`03` §14.4 的 A5/A6 在**预检期**就把 `list-args` 的数组长度计入 `n`（`n = Σ_steps (数组长度 或 1)`，`fold-args` 恒算 1）。因此 `give: "{{ trigger.entry.rewards }}"` 的 `do` 虽只 1 条、展开 ≤3 条，**都在这 24 里**。
- ⚠️ **这条依赖是硬约束**：若将来有人把 `list-args` 的展开挪出预检期，本文的守卫会**静默失效**（读取量退回 12，命令爆发重新挤掉旧事实）。实现时 MUST 在 `collect.ts` 那行旁边写明这个前提。

### 2.8 NEW：`computeNextStep` 的两个内部辅助

```ts
// NEW — packages/shared/src/render/next-step.ts

 * The newest event that was NOT produced by a world command (10 §3.7). Scans
 * backwards at most `events.length` times (the window is already ≤ 12 by cap).
 *
 * Rationale: a command's consequences are appended AFTER the act that triggered
 * them, so they displace the act from the tail. `computeNextStep` decides from

function hasSettledCommand(events: readonly NextStepEvent[]): boolean;
```

## 3. 行为契约逐步

以最小可判别切片（契约 §9.3）为样本：玩家在 `world/london-map/04-investigation-dice.md` 上掷骰、命中 `13..60` 档、命令 `investigate-clue` 落 3 个效果（`give` 一份笔记、`consume` 一份灯油、`edit` 写回两个选项）。

### 3.0 前提核实：契约 §5.3 的 turn 合并主张（**被证伪**）

契约 §5.3 逐字：

> 后果（这是免费拿到的好处，各文档不要重新发明）：玩家掷骰产生的 `roll_resolved` 与命令产生的 `entity_created` **带同一个 turn**，作家下一轮的事件注入会把它们合成一组连贯事实，而不是两条孤立记录。

**裁决：前半句成立，后半句不成立。**

**前半句（同一 turn）成立**：

- `ActionContext.turn` 的语义是「一个 agent turn，或一个 HTTP request」（`packages/shared/src/actions/types.ts:18-22`）。
- `rollDice` 落 `roll_resolved` 时写 `turn: ctx.turn`（`packages/shared/src/actions/roll-dice.ts:235`）。
- 命令的效果经动作层方法执行，那些方法同样写 `turn: ctx.turn`（`create.ts:144`、`move.ts:223`、`layer.ts:62`）。
- 命令在**触发它的那次动作调用内同步跑完**（契约 §4.3），所以 `ctx` 是同一个、`ctx.turn` 是同一个字符串。

**后半句（合成一组连贯事实）不成立，四条证据**：

| 证据 | 位置 | 说明 |
|---|---|---|
| 合并键是三元组 `(turn, type, actor)` | `packages/shared/src/render/events.ts:467-482` | `prev.turn === e.turn && prev.type === e.type && actorKey(prev.actor) === actorKey(e.actor)`（`:473-480`）——**跨 type 永不合并** |
| 只合并**相邻同键**的连续段 | `events.ts:471,484` | `prev.open` 被非同键事件打断即置 false（`:484`），后面的同键事件另起一组 |
| `roll_resolved` 在 `MERGE_EXEMPT` 里 | `events.ts:60-71` | `['roll_resolved','choice_selected','layer_entered','layer_initialized','layer_init_failed','following_changed','character_moved']`——**它自己不参与任何合并** |
| 唯一跨 type 的合并与 turn 无关 | `events.ts:534-554` | 规则 3 的键是 `created.detail.path === moved.detail.from`（同一个实体），与 turn 无关 |

再加一条决定性的：**十五条模板没有一条印 turn**（`events.ts:193-397` 的 `renderEventChecked` 全部 `text` 里都不含 `event.turn`）。即使两句相邻，读者也**看不出**它们同轮。

**实际效果**：`roll_resolved` 与命令的 `entity_created` 渲染成**两条相邻、互相独立的句子**，顺序正确，仅此而已。**因果可读性因此必须由 §3.6 的命令主语渲染承担。**

**连带发现（cap 折叠会破坏这种相邻）**：规则 4 保留**最新** `caps` 组（`events.ts:556-561`，`groups.slice(-caps)`），丢的是**旧**的。若一轮内超过 12 组，可能出现「创建那句被留下、掷骰那句被丢掉」——读者看到一条凭空出现的创建记录，**连顺序相邻都不剩**。这正是 §3.3 读取预算要解决的一半问题。

> 建议的契约 §5.3 修订见 §11 冲突 1。

### 3.1 步骤 0 — 命令效果落账（`04` 的职责，本文的输入）

每个效果经动作层方法落一条事件，`actor = ctx.actor`（= 触发者）、`turn = ctx.turn`、`detail.command = 'investigate-clue'`。事件序列（按 seq 升序）：

```
seq 41  roll_resolved    actor=player  turn=t-7  detail={path, name, dice, desc, expect, result:62, passed:true}
seq 42  entity_created   actor=player  turn=t-7  detail={path:world/london-map/investigation-success.md, name, kind:'note', command:'investigate-clue'}
seq 43  entity_edited    actor=player  turn=t-7  detail={path:world/london-map/04-investigation-dice.md, name, kind:'chalk', command:'investigate-clue'}
seq 44  entity_edited    actor=player  turn=t-7  detail={path:…, name, kind:'chalk', command:'investigate-clue'}   ← consume 是状态迁移，非删除
```

**漏了会怎样**（`04` 不写 `detail.command`）：全部 4 条渲染成"玩家做了四件事"，作家把自动发奖读成玩家手动创建；硬门 2（不重复结算）退化为靠提示词兜底，正是契约 §1.2 说的结构性失败。

### 3.2 步骤 1 — 读取（`01` 的 `readEventSlice`，本文改它的取量）

### 3.3 步骤 2 — 为什么读取量必须与渲染上限脱钩（**本文发现的真实缺陷**）

**现状**：`limit` 与 cap 是同一个数——`collect.ts:112` 传 `limit: opts.caps`，而调用方把 `caps.dynamics` 同时用于读取（`collect.ts:252`）与渲染（`collect.ts:256`）。

**故障**：一次命令落 5 个效果 = 5 行事件，**在读取层就消耗掉 12 个名额中的 5 个**；而规则 1 的合并发生在**下游**，救不了这次读取。被挤掉的旧事实因为游标照推 `getMaxSeq`（`cursor.ts:27-50` 的默认 `seq`）、且**没有历史面工具**（`docs/hooks/00` §4.2 评审 A-13），是**永久丢失**。

**缓解的一半来自现有机制**：规则 1 会把命令的同类效果塌缩成一句（见 §3.4 步骤 3），所以 **`do` 有 5 个 `give` 的常见情形只渲染 1 行**。这解释了为什么读取预算不需要很大——但它必须**存在**，否则"5 种不同效果"的 `do` 仍然吃掉 5 个槽位。

**漏了会怎样**：玩家在一次高风险决定里拿到 5 个效果，则作家这一轮"看不见"过去 5 条世界变化（包括别的玩家的、别的角色的）——而且永远补不回来。

### 3.6 步骤 8 — 渲染成人话：命令主语替换（主张 + 模板）

#### 3.6.1 问题

契约 §5.1 把 actor 定为触发者（玩家），而渲染器的主语来自 actor（`events.ts:209-226`）：

```
The player wrote a new page: "核心を記した覚え書き" (world/london-map/investigation-success.md).
```

#### 3.6.2 两面都有理，但没有一样重

| 立场 | 论据 | 代价 |
|---|---|---|
| **不体现**（保持 `The player …`） | 契约 §5.1：从世界的角度是**玩家的行动**导致的；历史面板与注入应把因果归给玩家 | 作家**无法区分**"玩家自己写的"与"规则替玩家写的"。这不是审美问题：**它是重复发奖的直接诱因**（§3.8），并且是一处**假证据**——文件在那儿，归属错了 |
| **体现**（换成世界主语） | 作家知道这部分已有人做 | 可能破坏沉浸：读者/作家看到"世界自己动了" |

**主张：体现，用「世界 + 触发者」的复合主语，不用旁白式元叙述。** 三条理由：

1. **因果与执行者可以同时保留**。`The world, after the player acted, …` 一句里同时有执行归属（世界做的）与因果归属（因为玩家）。契约 §5.1 要的因果**没丢**；而契约 §1.2 的分工原则（「确定性的后果由代码执行，不确定性的意义由 Agent 叙述」）**要求**执行归属可见，否则分工原则在注入里无对应物。
2. **沉浸问题不存在**，因为注入块是**给模型的事实块**，不是叙事文本。渲染器里已有先例：`layer_initialized` 逐字 `The layer "X" was instantiated by the ${by} ({n} files).`（`events.ts:340-346`）——它已经在注入里说"这是谁做的、怎么来的"，且它恰好是 `unseenCreation` 判据的基础。**"世界自己动过"已是既有语域。**
3. **不能靠元叙述**（如 `(automatically)` / `(by world command "investigate-clue")`）。括号元信息会被模型当作可复制的文体，且违反现有风格——十五条模板**没有一条**带括号注释。

#### 3.6.3 模板（英文，照 `events.ts` 现有风格）

**实现方式：只新增一个主语函数（§2.5），十五条模板的骨架一行都不改。**

| type | 现有模板位置 | 命令版本输出（actor = player） |
|---|---|---|
| `entity_created`(note) | `:223` | `The world, after the player acted, left a note: "核心を記した覚え書き" (world/london-map/investigation-success.md).` |
| `entity_created`(chalk) | `:217` | `The world, after the player acted, wrote a new page: "…" (…).` |
| `entity_created`(count>1) | `:418-421` | `The world, after the player acted, created 5 things.` |
| `entity_edited`(chalk) | `:236` | `The world, after the player acted, revised "…" (…).` |
| `entity_edited`(count>1) | `:424-425` | `The world, after the player acted, edited 2 entries.` |
| `entity_moved` | `:252` | `The world, after the player acted, moved "灯油" from world/harbor-chart/old-lighthouse into the player's bag.` |
| `entity_moved`(count>1) | `:413-417` | `The world, after the player acted, moved 2 items into the player's bag.` |
| `character_moved` | `:262-280` | **主体是角色本身，不是 actor**（`events.ts:263` 注释逐字 `Subject is the character itself, never the actor`）→ 命令**不改这条**，仍输出 `Watson moved from … into …` |
| `entity_deleted` / `layer_*` / `*_talked` / `following_changed` / `roll_resolved` / `choice_selected` / `use_item_on` | — | **不由命令产生**（`04` 的七个效果 give/move/edit/set_status/consume/enter/link 里没有对应原语：没有 `delete`——`consume` 是 `editEntity` 式的状态迁移而非删除；`enter` 只落 `layer_entered`；`link` 不落事件）→ 命令主语在这些类型上是**不可达分支**；但函数写法与类型无关，不需要特判 |

`character_moved` 的特例值得写进实现注释：它的主语是**被移动的角色**，与 `actor` 无关。命令通过 `move` 搬动一个角色时落的仍是 `entity_moved`（`move.ts:209-211`），所以不影响本表。

#### 3.6.4 为什么不改台词、只在主语上动手

- **零回归面**：`subjectPhrase(a, null) === actorPhrase(a)`，所有不涉及命令的既有 golden 逐字不变。
- **零新文体**：不引入括号、不引入第二人称。
- **一处真源**：同一条命令的所有效果共享同一种主语措辞，因为它只依赖 `actor` 与"是否是命令"。

### 3.7 步骤 9 — `next-step` 的修订（**本文最重要的实现陷阱**）

#### 3.7.1 现状与故障链

```ts
// packages/shared/src/render/next-step.ts:112-118（现有）
const events = facts?.events ?? [];
const tail = events.length > 0 ? events[events.length - 1] : null;
const owed = tail && tail.actor?.type !== 'writer' ? INTERACTIVE_TAIL[tail.type] : undefined;
```

`INTERACTIVE_TAIL` 是白名单，只有三个键：`choice_selected` / `use_item_on` / `roll_resolved`（`next-step.ts:71-75`）。

**故障链**（每一环都已核实）：

1. 命令事件的 seq **大于** `roll_resolved`（§3.1 的 42/43/44 > 41）；
2. `facts.events` 是 `window.events`（`inject/collect.ts:174`），**按 seq 升序**（`events.ts:21` 注释 + `getEventsSince` 的 `ORDER BY seq ASC`）；
3. 所以**队尾**是最后一条命令事件，不是 `roll_resolved`；
4. 队尾 type 不在白名单 → `owed === undefined`；
5. `unseenCreation` 通常 false（掷骰不生成层）、`quiet` false（`window.events.length !== 0`，`inject/collect.ts:178`）；
6. → 落到末尾 `return ''`（`next-step.ts:133`）。

**结果**：`''` 意味着**整节缺席**（`next-step.ts:11-14` 注释 + `docs/hooks/00` §3.1）。玩家掷骰那一轮，作家**不再**被告知「这次判定还没有被叙述」——**命令越生效，祈使句越消失**。这不是措辞问题，是一整节的丢失。

#### 3.7.2 修订：队尾**跳过命令行**，并按"是否已结算"换文案

判定序（仍是 first-hit-wins，`next-step.ts:96-104` 的顺序只扩不重排）：

```ts
// 0. NEW: the act, recovered from behind the command's consequences.
const tail = actTail(events);
const settled = hasSettledCommand(events);
const owed = tail && tail.actor?.type !== 'writer' ? INTERACTIVE_TAIL[tail.type] : undefined;
```

| 序 | 条件 | 返回 |
|---|---|---|
| 1 | `owed !== undefined && !settled` | 现有三条（`CASE_CHOICE_SELECTED` / `CASE_USE_ITEM_ON` / `CASE_ROLL_RESOLVED`） |
| **1′（新）** | `owed !== undefined && settled` | **对应类型的「已结算」文案**（§3.7.3） |
| **1″（新）** | `owed === undefined && settled && tail !== null` | `CASE_ACT_SETTLED`（兜底） |
| 2 | `unseenCreation && currentLayer != null` | `CASE_UNSEEN_CREATION`（不变） |
| 3 | `quiet` | `CASE_QUIET`（不变） |
| 4 | 否则 | `''`（不变） |

**角色分支不动**（`next-step.ts:121-127`）：`C2` 的判据是 `events.length > 0`，命令事件在角色窗口里（若同层）已落在 `events` 中，`C2` 自然触发。刻意的**最小改动**——契约 §3.3 已把角色侧定为四节 + 下一步，改动面越小越好。

**序 1″ 为什么需要**：cap 折叠可能把 `roll_resolved` 丢掉、留下命令事件（§3.0）。此时 `actTail` 返回 `null`、`settled` 为 `true`——我们知道"世界刚替某个动作结算了东西"，但不知道是哪个动作。`CASE_ACT_SETTLED` 只说这件事，**不猜类型**。它比回落到 `CASE_QUIET`（明说"世界无变化"，**是假话**）或 `''`（整节消失）都诚实。

**序 1″ 的门 `tail !== null`**：若整段都是命令事件，`actTail` 为 `null` 且 `owed` 无从判断；`settled && tail === null` 会退到序 2/3/4。加这个门是为了让"**至少有一条非命令事件**"成为它的精确适用域。

#### 3.7.3 文案定稿（英文，照 `next-step.ts:48-64` 的现有风格）

参照系是同文件的 `CASE_UNSEEN_CREATION`（`next-step.ts:54-55`）——它已经确立了「**告诉作家哪些事已经落盘了、别再做一遍**」的写法（`Its opening is already on disk, so do not write it again`）。新文案沿用同一语域：**陈述事实 + 禁止重复执行 + 保留意义叙述的自由**。

```ts
// NEW — packages/shared/src/render/next-step.ts（与 :52-53 同一常量区）
const CASE_CHOICE_SELECTED_SETTLED =
  'The player has just made a choice, and the world has already carried it out: what it owed is on disk now. Say what it means; do not re-describe the mechanics, and do not write the same thing again.';

  'The player has just used an item on something, and the world has already carried it out on disk. Say what it means; do not repeat the effect or write a second copy of it.';
```

### 3.8 步骤 10 — 同轮回执（**本文新增**）

**为什么必须有**：§3.9 证明作家自己触发的命令事件在它下一轮的注入里**被排他掉且永不重现**。回执是唯一在**同一轮**就把后果送到它上下文的手段。

#### 3.8.1 输出模板（英文，照 `rolledText`（`actions/roll-dice.ts:63-65`）与 `ok()`（`extensions/toolkit/result.ts:13-15`）的既有风格）

回执的抬头是 `settle`（§2.7）的**纯函数**——四种 verb 各一种措辞，**没有第五种**，且 verb 由 `05` 定义、`10` 只翻译成英文：

| `settle` | 模板 |
|---|---|
| `ran`（成功） | `The world settled this for you, through "<name>":` + 效果行 + 收尾行 |
| `failed` | `The world could not settle this for you, through "<name>":` + 失败行 + 收尾行 |
| `reused` | `The world had already settled this, through "<name>": nothing changed again.` |
| `resumed` | `The world finished settling this, through "<name>":` + 效果行 + 收尾行 |

`ran` 的完整输出（最小可判别切片的 2 个效果）：

```
The world settled this for you, through "Investigate the clue":
  - The world, after the player acted, left a note: "核心を記した覚え書き" (world/london-map/investigation-success.md).
  - The world, after the player acted, moved "灯油" from world/harbor-chart/old-lighthouse into the player's bag.
Narrate what this means; do not write, grant, or move any of it again.
```

`failed`（硬门 4 在作家侧的落地；`[C-1]` 尚未拍板"失败是否**落账**"，但"模型可见"这一半由本文要求）：

```
The world could not settle this for you, through "Investigate the clue":
  - "world/harbor-chart/old-lighthouse/lamp-oil.md" is not in the player's bag, so nothing was taken.
Nothing was granted. Say what the player can still try.
```

`reused`（`05` 的幂等复用；**本条只有一个整句，没有效果行，也没有收尾行**——没有效果可列，重复收尾句只会在复访时刷屏）：

```
The world had already settled this, through "Investigate the clue": nothing changed again.
```

`resumed`（`05` 的续跑；`05` 已定义 `resumed` 为「上次中断，本次补齐剩余 `do[]`」）：

```

  - …
Narrate what this means; do not write, grant, or move any of it again.
```

- 多条命令时按 `commands` 数组顺序分段，每条一个抬头（`name` 取自 `command/<id>.yaml` 的 `name:` 字段，契约 §3.2）。
- **收尾行是定稿文本**，不是可选项；对应 §3.7.3 的措辞分工（一个在本轮、一个在下一轮，措辞可以相似但**必须各自完整**——读者时刻不同）。
- **不使用 `settle` 里的 `ran` 之外的字面量**：`10` MUST NOT 自造 verb。若 `05` 增加第五种 verb，回执的映射表**必须同批更新**（否则落到默认分支——见 §7 的降级行）。

#### 3.8.2 接线点（`02` 拥有的触发点，`10` 只提供函数）

### 3.9 步骤 11 — 排他：`excludeActor` 问题的确切结论

#### 3.9.1 现状（每一环已核实）

| 环节 | 位置 | 行为 |
|---|---|---|
| 读者 id | `actions/actor.ts::readerOfActor` | 作家 → `'writer'`；角色 → `'character:<id>'`；player/god/engine → `null` |
| 读取 | `inject/collect.ts:107` `store.readCursor(reader)` | `0` = 从创世读 |
| 排他 | `inject/collect.ts:251` `excludeActor: actor` | **传的是"这个进程的 actor 本身"** |
| SQL | `local-store.ts:745-749` | `NOT (actor_type = ? AND COALESCE(actor_id,'') = ?)` |
| 冷启动 | `collect.ts:118-129` | `getEvents` 无 `excludeActor`，JS 侧同一判据过滤 |
| 结算 | `extensions/context.ts:149-151` + `cursor.ts:27-50` | 作家轮边界 `{ advance: true }` → `seq = getMaxSeq()` |

#### 3.9.2 结论：**是的，会被滤掉，且是永久性的**

契约 §5.1 定「命令事件的 actor = 触发者」。当触发者是作家时：命令事件 `actor.type === 'writer'` → `excludeActor: actor` 传的就是 `{type:'writer'}` → SQL 的 `NOT (actor_type = 'writer' AND COALESCE(actor_id,'') = '')` 成立 → 这些行被排除；而游标照推 `getMaxSeq()`（`context.ts:150`），越过它们；且**没有历史面工具**（`docs/hooks/00` §4.2）→ **永不重现**。

不是推测：`packages/shared/test/foundation.test.mjs:199-200` 已钉住这个 SQL 行为，`packages/shared/test/inject.test.mjs:249-252` 钉住 `readEventSlice` 的同类行为。

一个细节：作家没有 `actor_id`（`packages/shared/src/actions/actor.ts:9`：只有 `character` 带 id），所以 `COALESCE(actor_id,'') = ''` 命中。若未来某个 writer 变体带上 id，判据依然成立（`collect.ts:126` 的 JS 分支同样比较 `actor.id ?? ''`）。

#### 3.9.3 为什么不改排他（**这是结论，不是妥协**）

| 候选 | 评估 |
|---|---|
| **A. 放开排他**（作家读自己的事件） | **驳回**。排他的设计意图逐字是「不把自己刚写的念给自己听」（`docs/hooks/00` §6.1）与「作家把自己刚做的选择读成'玩家做的'并被告知去回应**自己的**动作」（`docs/hooks/04` §3.1 评审 A-12）。放开 = 重新引入 A-12，还要再补一层过滤，把同一个问题推来推去 |
| **B. 只放行带 `detail.command` 的 writer 事件** | **驳回**。要在 SQL 里对 JSON 文本列做关键词匹配（`detail` 存的是 `JSON.stringify` 的结果，`local-store.ts:697`），既贵又不精确；而且**游标已经推过去了**——排他与游标是两件独立的事，"只放开排他"解决不了任何问题 |
| **C. 给命令事件换一个 actor（如 `engine`）** | **驳回**。契约 §5.1 逐字禁止，且破坏因果归属（`doc-21` §3.2 把 `god` 从 `player` 单列的同一条理由） |
| **D. 同轮回执（本文选它）** | **采纳**，且与主 agent 的独立复核结论一致。它不碰排他、不碰游标、不碰 actor 口径，只在**已经存在**的模型可见通道（工具结果）上补一句，而且比下一轮注入**更早**生效 |

#### 3.9.4 D 的已知缺口（诚实登记）

若触发命令的那次工具调用**不经过** `ActionResult.text`（例如未来新增一条不经动作层返回值的路径），回执不会出现。落实时 MUST 在 `02` 的触发点表里为每个触发点确认接线行（§3.8.2 给了三处）。

#### 3.9.5 去重的分工（本文不负责）

- 「同一意图 × 同一目标 × 同一已结算结果不二次结算」= 契约 §7 硬门 2，归 `05`。
- 本文只保证：**若 `05` 让重复触发不落新事件，注入侧自动没有新行**（免费的一致性）；若 `05` 选择落一条 `already resolved` 类事件，那是 `05` 的选择，本文不额外处理。
- 「同 turn 重复」在渲染层由规则 1 自动合并（§3.4），本文无需额外动作。

#### 3.9.6 去重与渲染的边界：`reused` 只影响回执，不影响事件段

`settle: 'reused'`（§2.7）**MUST NOT** 在事件段产生任何行——复用的前提就是"没有新事件"，而事件段按定义只报"变化"。它唯一的作用是让回执能说「已经结算过了，没有变化」，而不是在复访时**什么都不说**（硬门 4 的弱形态：不静默）。

**同理 `settle: 'failed'`**：若 `[C-1]` 拍板"失败不落账"，则失败**没有事件**——`hasSettledCommand` 为 false，`next_step` 退回今天的普通文案（`CASE_ROLL_RESOLVED`）。这是正确的：下一轮注入只需要说"这次判定还没被叙述"，**失败的事实由同轮回执承担**（它更早、更准）。若 `[C-1]` 拍板"失败落账"，那条事件的 `detail` MUST 带 `command`，`settled` 分支就会启用——两种拍板下行为都自洽。

### 3.10 步骤 12 — 角色 Agent 的层窗口（**会漏看，且是设计**）

#### 3.10.1 现状（已核实）

```ts
// packages/shared/src/inject/collect.ts:250
layer: actor.type === 'character' ? (layer ?? undefined) : undefined,
```

角色读**本层**事件（`getEventsSince` 的 `WHERE layer = ?`，`local-store.ts:742-744`）；作家读全天下的（`layer: undefined`）。契约的措辞是：**`layer` 过滤是"省 token"，不是门禁**（`docs/tools/00` §3.3 更正 / `doc-21` §8）。

#### 3.10.2 命令在别的层创建东西时，角色会漏看吗？**会，两处，且两处都是既有的**

| 情形 | 角色是否看见 | 机制 |
|---|---|---|
| 命令在角色**所在层**创建/编辑 | ✅ | `entity_created` / `entity_edited` 的 `layer = resolveLayer(path)`（`create.ts:135,143`；`editEntity` 同），等于本层 |
| 命令在**别的层**创建 | ❌ | `layer = 'world/other'` ≠ 本层 → SQL 不等 → 排除 |
| 命令写 `player/…`（玩家背包） | ❌ | `resolveLayer('player/key.md') === null`（契约 §4.1 已核实 `resolveLayer` 只认 `world/**`）→ 落库 `layer = NULL` → `WHERE layer = 'world/x'` **永不匹配 NULL** |

**第二行是重点，且比"漏看"更严重**：角色游标在**关遮罩时**推到 `getMaxSeq()`（`apps/server/src/index.ts:263` + `cursor.ts:27-50` 的默认 `seq`）——所以别层的命令事件对角色**永久消失**，不是"下次再看"。

#### 3.10.3 结论：**这是设计，本文不修**

三条理由：

1. **角色不需要知道别层发生了什么**。角色的职责是在它所在的地方和玩家对话（`CHARACTER_INSTRUCTION`，`extensions/instructions.ts:211-268`）。命令在别处发了一份笔记，与"我现在该怎么回答眼前这个人"无关。
2. **修它就要动 `layer` 过滤，而那是 `docs/hooks/00` §6.1 / `docs/hooks/03` 的冻结口径**，且带来真实成本：角色窗口的 12 个名额会被别层事件挤占——这正是 §3.3 读取预算在作家侧要防范的同类问题，在角色侧会更严重（角色 cap 更小，冷启动按层查就是专为省 token 设计的，`collect.ts:118-120`）。
3. **玩家可见的叙事通道不由角色注入承担**。若一次命令的后果应该被某个角色知道，正确的做法是**作家在叙述里说出来**（作家能看见全场事件）——这恰好又是契约 §1.2 的分工：代码改世界，Agent 叙述意义。

**需要登记**（已在 §11 冲突 3 写好）：本结论 MUST 进 `04` 的"哪个效果会跨层"表，免得 `04` 以为所有效果对所有读者都可见；且 MUST 进 `docs/hooks/00` 的失败/边界表，因为它今天是**隐含**的（契约只说了 `layer` 过滤不是门禁，没说"命令的跨层后果对角色**永久**不可见"）。

**一个必须澄清的连带事实**：`docs/hooks/00` §3.3 说**角色不注入 `bag`**（玩家的口袋不在角色视野里），且明说那"**不是权限门禁**——角色真要 `look_at player/` 也拦不住"（`doc-05` §4.1）。命令写进玩家背包的**事件**与这个"看不见玩家的口袋"是同向的：**角色既看不到背包内容（不注入 `bag`），也看不到背包变化（`layer = NULL` 被过滤）**。两处一致，不是矛盾；把它们写在一起能防止实现者以为"事件段会补上 `bag` 不报的东西"。

### 冲突 8 —— 数组实参的两条契约（`list-args` / `fold-args`）对事件段的影响（**本文的增补，需要 `04`/`03` 确认**）

主 agent 二次裁定走「数组值实参 + 引擎内有界展开」，并在三次裁定里把它**拆成两条契约**（命名冻结）：`list-args`（逐项迭代，N 个独立效果）与 `fold-args`（折叠，恒 1 次结构性写入）。**`10` 从事件段角度确认两条都安全，但两条的影响完全不同，必须分开说。**

#### `list-args` 的后果（例：`give: "{{ trigger.entry.rewards }}"`）

- **展开后每个奖励各自落一条 `entity_created`**，因此**事件数量 = 数组长度**，上界由实体侧 schema 的 `≤3` 封死。
- 这就是读取预算（§2.6）要覆盖的量级。**这条已经解决**：`03` 的 `WORLD_COMMAND_EFFECT_BUDGET = 24` 本身就是**展开后**的上界（`03` §14.4 在预检期把 `list-args` 的数组长度计入 `n`），所以守卫不需要自己区分"声明条数"与"展开条数"——**但这条依赖 MUST 写进 `collect.ts` 的注释**：若将来把展开挪出预检期，守卫会静默失效（§2.6）。
- **展开的各项共享同一 `detail.command`**，因此在规则 1 下合并（同 turn / 同 type / 同 actor / 同 command）→ 3 项奖励塌缩成**一句** `The world, after the player acted, created 3 things.`（§3.4）。**"引擎内展开"对作家的可读性是正的：一个档位发 3 份奖，仍然是一句话。**
- **逐项失败**（第 2 项路径被占）→ 该项没有事件、成功项有 → 事件段印成功的那部分，回执单独列失败项（§7 的降级行）。`hasSettledCommand` **不会误判**：只要有任意一项成功，`settled` 就是 true，祈使句就是"已结算"文案。**这个方向是对的**——部分失败仍然意味着"世界做了一部分，别再做一遍"。
- **若全部项都失败** → 没有事件 → `settled` 为 false → `next_step` 退回普通文案（`CASE_ROLL_RESOLVED`），失败事实由同轮回执承担（§3.9.6）。**自洽，`10` 无需改动。**

**`04` 侧必须确认的一条**：展开的每一项 **MUST** 各自落一条带 `detail.command` 的独立事件，**MUST NOT** 落一条聚合事件（例如一条 `entity_created` 带 `files: [3 项]`）。理由：后者会让事件段的路径信息丢失（`detail.path` 只有单数），而"文件即真相"（契约 §7 硬门 1）要求每个效果**可复访**。

#### `fold-args` 的后果（例：`options → choice.options + choice_actions`）

- **恒 1 次写入 = 恒 1 条 `entity_edited`**（`edit` 是 `04` 七个效果之一）。**不放大事件数**，与 `list-args` 相反。
- 它落的事件与一次普通 `editEntity` **形态完全相同**（同 `detail` 形状、同 `layer` 由目标路径决定）。因此 `10` **不需要为它做任何事**——`entity_edited` 的模板（`events.ts:236-241`）与合并规则（规则 1 / 规则 2）对它一律适用。
- **它的一条真实风险不在这份文档**：折叠出的 map 与实体已有 `choice_actions` 键相交时是拒绝还是覆盖（`04` 拥有该效果契约）。**`05` 已给出一条决定性理由，支持"拒绝"**（`docs/command/05` §5.7）：若折叠覆盖了实体已有的键，那个键可能正是**上一次运行写下的**——覆盖它等于**改写已结算结果**（契约 §7 硬门 3），且会让 `command_log` 说"跑过了"而世界里的按钮已经不是那次跑出来的，**日志与世界不一致**。
  `10` 从**注入侧**追加一条独立理由：**覆盖会让事件段撒谎**。一次折叠覆盖落的是普通 `entity_edited`（模板 `:236-241`：`The world, after the player acted, revised "X" (path).`），读者无法从这一行看出"它同时抹掉了一次已结算的按钮组"。**拒绝**则干净得多：**若 `04` 选择拒绝，MUST 有一个可见结果**（`ok: false` + 回执的效果行），否则回执里就是一条"世界什么都没发生"的沉默——违反硬门 4。**`10` 的立场：拒绝 + 可见错误**（与 `05`、主 agent 的倾向一致）。

#### 两条共有的、`10` 依赖的一条

**数组的顺序 MUST 保留到落账**（`list-args` 影响事件 seq 顺序 → 影响事件段的行序；`fold-args` 影响生成对象的键序 → 影响 `05` 的 `plan` 摘要稳定性）。主 agent 已要求 `03` 把"保留顺序"写进求值契约。**对 `10` 的具体后果**：`list-args` 展开的各项必须是**连续的 seq**，从而在规则 1 下**相邻**→ 能合并成一句。若非连续（中间插了别的效果），`countPhrase` 的合并会断成两句（`events.ts:288-296` 的 `prev.open` 判定）——**这是可接受的**（读者仍能读），但 `04` 的实现应优先把同一 `list-args` 的各项**连续落地**。

**认领方**：`04` 确认两条的事件形状与键冲突语义；`03` 保证展平后的效果序列顺序稳定（本文只消费）。
