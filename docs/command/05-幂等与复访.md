## 1. 一句话定位

**幂等真相源是被触发实体自己 `.md` frontmatter 上的 `command_log`；事件表只做审计，永远不被查询来决定"要不要执行"。**
一次运行的尝试身份由 `commandKey = source × hook × command × fact` 唯一确定（§3 —— 注意 **`args`（`with:` 与 `{{ trigger.* }}`）与命令文件内容都不在里面**，这是本文与直觉最相左、也最关键的一个决定）；重复触发查 key，命中即证明"同一次尝试已经结算过"，复用；命中但未跑完即**续跑**；未命中才**首跑**。

## 2. 数据形状

本文拥有契约 §3.3 分配的两个顶层 key，两者都在**被触发实体的 `.md` frontmatter** 上（不是 `command/<id>.yaml`——契约 §3.2/§3.3 已改为独立 YAML，命令文件顶层只有 `name` / `desc` / `params` / `do`）。

### 2.1 `command_log`（幂等回执，本文独占）

```yaml
# world/london-map/04-investigation-dice.md 的 frontmatter 片段
command_log:
  - key: 9f2c41ab7de05513
    command: award-clue
    hook: roll_resolved
    index: 0
    status: done
    at: '2026-09-14T10:31:02.418Z'
    turn: 'req:7c1f'
    plan: 3a91e0c4
    steps:
      - { step: 0, action: give,    event: evt-118 }
      - { step: 1, action: consume, event: evt-119 }
      - { step: 2, action: edit,    event: evt-120 }
```

| 字段 | 类型 | 必填 | 默认 | 上限 / 取值 | 非法值的错误文案 |
|---|---|---|---|---|---|
| `key` | string | ✅ | — | `^[0-9a-f]{16}$`，见 §3 | `command_log[i].key must be 16 lowercase hex characters (the engine writes it; do not hand-edit).` |
| `command` | string | ✅ | — | 同 01 的 id 正则 `^[a-z0-9][a-z0-9-]{0,47}$` | `command_log[i].command "<v>" is not a valid command id.` |
| `hook` | string | ✅ | — | `roll_resolved` \| `choice_selected` \| `use_item_on`（触发点名集合归 02，见 `02 §2.6` 的 `CommandTriggerHook`；本文只消费） | `command_log[i].hook "<v>" is not a known trigger point.` |
| `index` | int | ✅ | — | `0..63`，`on.<hook>[]` 的下标。**溯源与续跑定位用，不进 key**（§3.4） | `command_log[i].index must be a non-negative integer.` |
| `status` | enum | ✅ | — | `partial` \| `done` | `command_log[i].status must be "partial" or "done".` |
| `at` | string | ✅ | — | ISO-8601，由 `ctx.now?.()` 产出（`actions/types.ts:23-24` 的可注入时钟） | `command_log[i].at must be an ISO-8601 timestamp.` |
| `turn` | string \| null | ✅ | — | 原样转发 `ctx.turn`（`actions/types.ts:18-22`，动作层"从不解析只转发"） | `command_log[i].turn must be a string or null.` |
| `plan` | string | ✅ | — | `^[0-9a-f]{8}$`，**命令文件 `do` 的「声明形态」摘要**（不求值），见 §3.5。**provenance only, never a verdict** | `command_log[i].plan must be 8 lowercase hex characters.` |
| `steps` | array | ✅ | `[]` | `0..WORLD_COMMAND_EFFECT_BUDGET`（`03 §575` 定的 24，**本文不另写数字**）；**按展平后计数** | `command_log[i].steps must be an array of step receipts.` |
| `steps[].step` | int | ✅ | — | `0..WORLD_COMMAND_EFFECT_BUDGET-1`，**扁平效果序**：`do` 展开后的执行次序（含 `list-args` 的引擎内有界展开），**严格递增且无空洞**（§5.4、§5.7） | `command_log[i].steps is not a gap-free prefix of the run's effect sequence.` |
| `steps[].at` | string | ✅ | — | 声明位置，`do[<i>]` 或 `do[<i>]#<k>`（数组实参的第 k 次展开，1-based）。**溯源用，不进任何判据** | `command_log[i].steps[j].at must look like "do[1]" or "do[1]#2".` |
| `steps[].action` | string | ✅ | — | `04` 的 `WORLD_COMMAND_EFFECTS` **七名**之一：`give` · `move` · `edit` · `set_status` · `consume` · `enter` · `link` | `command_log[i].steps[j].action "<v>" is not a known effect.` |
| `steps[].event` | string \| null | ✅ | — | `evt-<seq>`（`schemas/events.ts:114` 逐字 `evt-<seq>`）；效果无事件时为 `null` | `command_log[i].steps[j].event must look like "evt-123" or be null.` |

**数组上限 32 条**。超限时**不截断**：`fail('command_log_full', …)`，文案见 §7。理由：静默截断会让最老的一条 key 消失 → 那次运行变回"未跑过" → 重复结算。这正是硬门 2 要挡的事，所以宁可报错也不丢。32 条意味着一个实体上最多 32 次**语义不同**的运行；`04-investigation-dice.md` 这种一次性判定卡实际用 1 条。

**排序**：追加序（最老在前）。不排序、不去重、不压缩——`upsertLogEntry` 按 key 原地替换（§8.2）。

### 2.2 `command_error`（失败可见，与 `06` 共有）

契约 §3.3 把 `command_error` 分配给 `05` + `06`。**本文定形状与写入/清除时机，`06` 定渲染。**

```yaml
command_error:
  key: 9f2c41ab7de05513
  command: award-clue
  hook: roll_resolved
  step: 1
  action: consume
  code: not_found
  message: 'Entity not found: "world/harbor-chart/old-lighthouse/lamp-oil.md"'
  pending: 2
  at: '2026-09-14T10:31:02.512Z'
```

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `key` / `command` / `hook` / `at` | 同 §2.1 | ✅ | 与 `command_log` 里同 key 的那条一一对应 |
| `step` | int | ✅ | 失败发生在 `do[]` 的哪一步 |
| `action` | string | ✅ | 那一步的效果名 |
| `code` | string | ✅ | `ActionErrorCode`（`actions/errors.ts:3-21`）原值，不翻译 |
| `message` | string | ✅ | `ActionError.message` 原文，上限 1000 字符，超出截断并加 `…`（**此处截断安全**：这是展示文本，不是幂等判据） |
| `pending` | int | ✅ | **剩余未执行的步数** = `plannedSteps.length - steps.length`，与 `plan`/`steps` **同基准（展平后）**。MUST NOT 用 `do.length`——`list-args` 展开后 `steps.length` 可以超过 `do.length`，那样会算出负数 |

**单数，不是数组**。同一实体同时只保留**最近一次**失败。理由：失败是要人处理的当前状态，不是历史；**F1 的历史保留只对「终局失败（不续跑）」成立**——`command_log` 用 `upsertLogEntry` 按 key **原地替换**（`:57`、`:764`），一旦同 key 达到 `status: done`（`:435`），那条记录就与一次成功运行完全同形、不再携带任何"曾经失败"的信息（「失败 → 续跑成功」在 `command_log` 里只剩 `done`）；此时历史只存在于事件里（若 `[C-1]` 决定落账）。

**清除时机**：同 key 的运行到达 `status: done` 的那一次写入里删除 `command_error`。本文的写入器走 `stringifyFrontmatter`，直接 `delete`（`editEntity` 的删除语义见 `actions/delete.ts:198` 逐字 `if (value === null) delete merged[key]`）。

> **`command_error` 是硬门 4（不静默失败）在文件侧的落点。** 契约 §7.4 逐字要求失败进入"模型可见的输出"**与**"玩家可见的状态"。`ActionError` 覆盖前者（`errors.ts:64-74` 的 `toToolResult` 带 `details`），`command_error` 覆盖后者。两个都要，缺一条就是 `console.warn` 级别的假实现。

## 3. 幂等 key 的构造公式

### 3.1 公式

```ts
// packages/shared/src/commands/idempotency.ts (NEW)
import { createHash } from 'node:crypto';   // 先例：origin/niko declared-actions.ts:2,147-149

export interface CommandKeyInput {
  /** 被触发实体的世界相对路径（= target） */
  source: string;
  /** 触发点名（集合归 02） */
  hook: 'roll_resolved' | 'choice_selected' | 'use_item_on';
  /** command/<id>.yaml 的 id（= intent） */
  command: string;
  /** 触发这次运行的、已经结算下来的世界事实（§3.3） */
  fact: string;
}

/** 16 位小写 hex。纯函数、无 I/O，可在动作层与 extension 两侧复用。 */
export function commandKey(input: CommandKeyInput): string {
  const material = [input.source, input.hook, input.command, input.fact].join('\u0000');
  // NUL 分隔：世界路径与 id 正则都不含它，不需要转义
  return createHash('sha256').update(material, 'utf8').digest('hex').slice(0, 16);
}
```

**四个分量，没有第五个。** 特别注意**没有 `args`**（拍板 B2 的 `with:` 与 `{{ trigger.* }}`）与**没有命令文件内容**——这两条排除都是刻意的，理由在 §3.5。

**为什么截到 16 位 hex（64 bit）**：碰撞空间要对抗的是**同一个实体上的 ≤32 条记录**，不是全局。64 bit 下 32 条的碰撞概率约 `32²/2^65 ≈ 3e-17`。全长 64 字符只会让 frontmatter 变丑而不增加任何安全性。

### 3.2 四个分量分别覆盖 `_shared/failure-and-revisit.md:22` 的哪一项

该文件逐字：「The same intent, target, prerequisites, authorization, risk, and world context reuses the existing result. A changed material, target, authorization, risk, or world version is a new attempt.」

| 契约里的词 | 本文的分量 | 说明 |
|---|---|---|
| intent | `command` | 命令 id 就是意图名。`with:` 实参**不是**意图的一部分，见 §3.5 |
| target | `source`（+ `use_item_on` 时 `fact` 里的材料路径） | 被触发实体即目标 |
| risk / world context | `fact` | 骰点、选了第几项、用了哪份材料 |
| **material** | 仅 `use_item_on` 的 `fact` 含材料内容摘要 | 其余触发点上材料不参与身份，见 §3.3 |
| prerequisites | **故意不进 key** | 前置条件由每个效果自己在执行时检查（硬门 6）。把前置塞进 key 会让"背包里多了一件无关物品"变成新尝试 |
| authorization | **故意不进 key**，见 §3.7 | |
| world version | **部分进**：`fact` 是"这一次结算下来的世界事实" | |

### 3.3 `fact` 逐触发点

| hook | `fact` 取值 | 来源 `file:line` | 为什么是它 |
|---|---|---|---|
| `roll_resolved` | `` `r:${result}` `` | `roll_dice.result`，权威值在文件 frontmatter 里（`schemas/frontmatter.ts:86`），由 `rollDice` 的 step 9 写入（`actions/roll-dice.ts:201-208`） | 重掷被 step 6 门禁堵死（`roll-dice.ts:149-155`），所以同一张卡的 `result` 一生只有一个值，`fact` 天然稳定 |
| `choice_selected` | `` `c:${index}:${choice}` `` | `choice_selected` 的冻结 detail（`schemas/events.ts:74-79`，`index` 注释逐字"1-BASED … Never converted"） | 同一张卡可以有多个选项，选不同项是不同尝试；选同一项两次是同一尝试 |
| `use_item_on` | `` `u:${item}@${revisionOf(itemRaw).slice(0,16)}` `` | `use_item_on` 的冻结 detail（`events.ts:89-94`）。`revisionOf` 是 **NEW**，签名见下 | **唯一把材料内容写进 key 的地方**，理由见下 |

**为什么只有 `use_item_on` 带材料内容**：契约原文把 **material** 单列为"改了就是新尝试"，而 `use_item_on` 的 `item` 就是 material。04 已核实"消耗"的真实形态是**状态迁移**（满灯油 → 空瓶，`templates/wuwu/skills/wuwu-play/SKILL.md:47`），不是删文件——所以"满瓶"与"空瓶"是**同路径、不同材料**，只有内容摘要能区分。区分开之后，拿空瓶再点同一个目标会得到一次**新的**运行，并被效果自己的前置检查诚实拒绝（硬门 6），而不是被幂等误判成"你已经做过了"——后者会让玩家永远看不到"瓶子是空的"这句话。

**`revisionOf` 的签名，与"它不引入新的文件 I/O"的硬约束**：

```ts
// packages/shared/src/commands/idempotency.ts (NEW)
/** sha256 hex。纯函数、无 I/O——调用方必须把已经读到的内容传进来。 */
export function revisionOf(raw: string): string;
```

**`itemRaw` MUST 由触发点传入，MUST NOT 由 `commandKey` 自己去读盘。** `useItemOn` 在执行时**本来就已经读过 item 文件**（它要检查存在性与 `portable`），所以把那份 `raw` 顺手传下来是**零额外 I/O**。

> **漏了会怎样**：若 `commandKey` 自己 `await store.readFile(item)`，幂等计算就从一个纯函数变成一次磁盘读——而它在 `S2` 里对**每条绑定**都要算一次。那会把 §4.2 优点 1（"查询 O(本实体记录数) 且零额外 I/O"）这条论证直接推翻，本文选 `command_log` 而非事件表的性能理由也就不成立了。**因此 `CommandKeyInput.fact` 收的是一个已经算好的字符串，`commandKey` 本身保持无 I/O**（签名 §3.1 已如此）。

**`choice` 的 `index` MUST 取自 `NormalizedOption.index`（可见序、1-based），MUST NOT 取自 `choice.options[]` 的数组下标。** 这是一条会让 key 静默算错的条件，不是措辞偏好——两者在有 `when` 隐藏选项时**会分叉**：

```ts
// packages/shared/src/rules/interactive.ts:262-271
// Visibility is decided once, here, so display and resolution share it (§3.5).
const visible = when === undefined ? true : evalWhen(when, statusData);
options.push({ index: visible ? ++visibleCount : 0, /* … */ });
```

数组下标 3 的选项可以显示为 `2.`。`packages/shared/test/interactive.test.mjs:92-107` 正是这条的守卫（逐字断言 `[1, 2]`, `'not 1/3'`）。而且玩家看到的序号、`look_at` 打印的序号（`interactive.ts:412-415`）与 `choice_selected.index` 用的都是这一个值——所以**取数组下标会让 key 与玩家实际选的东西脱钩**：玩家两次都点 "2. 弹未完成的夜曲"，若中间有选项的可见性变了，两次会算出两个不同的 key → 重复结算。`03` 独立确认了同一结论（`interactive.test.mjs:97-106`）。

> 归属：这条的**拥有者**是 `01`（模板语法）与 `02`（触发上下文），本文只声明**它的负载后果**——`fact` 是幂等 key 的 4 个分量之一，取错来源则 key 错，硬门 2 破。

**为什么 `source` 的内容摘要绝不能进 key**：`command_log` 本身就写在 `source` 上，写完摘要就变了。把它进 key 等于每次运行都生成新 key，幂等直接失效。这是一个会在实现期被"顺手加上去显得更严谨"的陷阱，写在这里防止它发生。

### 3.4 `index` 不进 key

`on.<hook>[]` 的下标只作为**溯源与续跑定位**（§5.1 的 S5）记进 `command_log`，不参与 key：

- 同一数组里把同一命令用**同一 `when` + 同一 `with`** 声明两遍 = 重复声明，第二条应是 no-op（key 相同 → 命中复用）。把 index 进 key 会让它变成"跑两遍"，正好违反硬门 2。
- 作者在数组中间插入一条新的 `on` 条目，会让后面所有条目的 index 平移。若 index 进 key，**所有已结算的运行会在一次无关编辑后集体变成"未跑过"** → 批量重复发奖。这是最危险的一种漂移，必须从公式里排除。
- **不会因此漏跑合法情况**：同一命令挂在一个 hook 的两个分支上（例如 `on.choice_selected` 的两个选项各绑一次），`fact`（`c:1:ask` / `c:2:back`）本身就不同 → key 不同 → 两次都能各跑一次。

### 3.5 `args`（`with:` 与 `{{ trigger.* }}`）不进 key，命令文件内容也不进

**主张：已结算的运行不因为"规则被改好了"而重新结算。`command/<id>.yaml` 的 `do`、以及实体 `on` 条目里的 `with:`，都 MUST NOT 进入 key。**

理由分两组。

**(a) 硬门 3 直接推出（适用于 `do`）**

一次 `done` 的运行是已结算事实。作者事后把 `do` 从"扣 1 份灯油"改成"扣 2 份"，**不应该**回溯地再扣玩家 1 份——玩家当初看到并同意的是旧版本的公开约定（硬门 8「先公开，后执行」）。`Chalk玩法形态与判定约定.md:28` 逐字：「掷完不能提高门槛、改奖惩或篡改点数」。回溯执行新版本就是事后改奖惩。

**(b) 加上 `args` 会引入一个真实的 key 不稳定通道（决定性，来自拍板 B2）**

拍板 B2 定了 `{{ trigger.fm.* }}`：命令通过它读**触发实体自己的 frontmatter** 拿内容。而**命令的效果会写回这个实体的 frontmatter**——`edit` 效果写 `choice` / `choice_actions` 是本批次的核心用法（主代理 2026-09-14 澄清：`kind: writer` 不是效果，命令只是把 `choice_actions` **数据**写回实体），`append_body` 会追加正文。于是：

> 设 `on.roll_resolved[0].with` 里有一个 `{{ trigger.fm.* }}`，它读到的字段恰好是该命令自己会改写的字段。
> **第一次运行**：用当时的字段值算出 `key_A`，落账 `key_A`，然后**改写那个字段**。
> **第二次触发**：同一 `with:` 表达式解析出**不同的值** → `key_B` → 日志里没有 `key_B` → 判定"没跑过" → **再结算一次**。

这不是理论构造：`dice_outcomes` 迁移后的形态正好是"命令把 `choice_actions` / 正文写回触发实体"，而内容（4 段文本、奖励路径、label）按拍板 B2 就住在实体 frontmatter 里。

**把 `args` 定义为"声明层的字面量"（即未代换的 `with:` 原文）能修掉这个不稳，但那只是把问题挪到 §3.5(a)**：作者编辑 `with:` 同样会导致 key 漂移 → 批量重跑。**唯一的解是让规则完全不参与身份。**

**代价，如实认账两条**：

1. **同一个 `command` 绑在同一个 `(source, hook, fact)` 上、用不同 `with:` 声明两遍，只会跑第一次**，第二次记 `reused`。这是**fail-safe 方向**的错误（少发而非多发），且 `SettleReport.reused` 会如实报出来，作者能看见。有表达需求时应拆成两个命令 id（内容作者本来就有任意多个 id 可用）。
2. **命令写错了，改好之后不会自动重来。** 玩家想重来，唯一正当路径是"发生新行动 → 新的检定与代价"（`Chalk玩法形态与判定约定.md:28`）。作者想强制重来，唯一正当路径是**手动删掉那条 `command_log` 记录**——一次显式的、可 diff、可追溯的世界编辑，而不是一次悄悄的副作用。

3. **区间相交的两条 entry 指向同一 `run` 时，第二条会静默 `reused`**（08 登记为 `overlapping_command_when`）。这是代价 1 在**骰子档位**上的具体形态：`commandKey` 不含 `args`，所以 `on.roll_resolved[0]`（`when: 1..12`）与 `on.roll_resolved[1]`（`when: 1..60`）若都 `run: same-command`，玩家掷出 5 时两条的 key **完全相同** → 只跑第一条，第二条记 `reused`。
   **08 已登记，本文交叉引用（应主代理要求确认）。** 裁定 A（`from` 是绑定声明、不进 key）**不改变**这条——所以它需要在**写入时**被检出：`07` 的 `parseOnBindings` 应在同一 `(hook, run)` 上检查 `when` 区间是否相交，相交即拒绝（错误码归 `02`/`07` 对齐）。
   > 与代价 1 的区别：代价 1 是"作者真的重复声明了同一件事"（少跑是**对的**）；代价 3 是"作者想表达两件事但机器看成了同一件"（少跑是**错的**，正是硬门 2 的反面——该给的没给）。**这两者在 `command_log` 里长得一样**（都是 `reused`），所以必须在写入期用区间相交把它们分开，不能靠运行期观察。

**但 `plan` 摘要仍然要记进日志**（§2.1）：它是**溯源**不是**判据**。它回答的是「**这份 log 是哪个版本的命令规则写的**」，所以取**声明形态**——`do` 的规范化文本，`{{ }}` 引用**规范化为 `{{name}}` 而不求值**（01 提供 `canonicalCommandStepText`）。作者排查"这份奖为什么跟我现在写的不一样"时，`plan: 3a91e0c4` 与当前文件的声明摘要一比，就能区分「规则被改过」与「内容被改过」。

> **为什么不是"代换后形态"**（`03` 曾按此提议，本文不采纳，理由登记见 §11.7）：代换后形态把运行期值（`{{ roll.result }}`、`{{ trigger.fm.* }}`）卷进摘要，于是**同一份命令文件在不同触发上算出不同 `plan`**。那样的摘要无法与"当前文件的摘要"比较，也就回答不了上面那个问题。更糟的是它把 §3.5 排除 `args` 的那个自指通道又请了回来——`{{ trigger.fm.* }}` 读的字段会被命令自己写回，同一 key 两次运行的 `plan` 会不同。声明形态一次写入即可确定，**且不需要运行期上下文**（07 的写入校验顺手就能算，不必依赖 03 的求值器）。

> **记录 ≠ 参与判定。** 这两件事在实现期极易混淆，所以签名上把它们放在两个不同的位置：`plan` 是 `CommandLogEntry` 的字段，不是 `CommandKeyInput` 的字段。

### 3.6 一句话记住这条边界

**key 只回答"玩家在世界里做的哪一次尝试"；它不回答"引擎当时用的哪份规则"。**
规则住在文件里、可以被改好；尝试住在世界里、一旦结算就不再改变。

### 3.7 `actor` 故意不进 key

`failure-and-revisit.md:22` 把 authorization 列为"改了就是新尝试"。**本文明确不遵守这一条，并给出理由。**

契约 §4.1 的整个存在理由就是：玩家 HTTP 路径与作家工具路径调同一个动作 MUST 得到同一套后果。`origin/niko` 的事故正是两条路径行为不一致（主代理 2026-09-14 已把契约 §10.1 从 `[推断]` 升级为**实测**：`origin/niko:apps/server/src/routes/world.ts:950` 在 `POST /api/dice` 里调 `runDeclaredRoll`，而 `extensions/toolkit/roll-dice.ts:49` 直调 `rollDice({path})`）。如果 `actor` 进 key：

- 玩家点掷骰 → 发奖，`key_player` 落账；
- 作家 Agent 这一轮读到事件，调 `roll_dice` 或走无门禁的 `chooseOption` → `key_writer` 未命中 → **再发一次奖**。

这正好是硬门 2 要挡的事故，而且是由"忠实执行上位契约的字面"导致的。因此本文**在这一点上偏离 `failure-and-revisit.md:22`**，在 §11 登记，请评审裁决措辞。

## 4. 幂等真相源：三个候选逐个评估

### 4.1 候选 A：事件表（`events`）

**优点**：它已经是 append-only 的真相源；每个效果本来就会落自己的事件（契约 §5.2），`detail.command='<id>'`（契约 §5.1，按主代理裁定 1 已**删去 `detail.by`**，见 §11.8）已经把归属写进去了。理论上"这个命令在这个 source 上跑过吗"= 一次查询。

**先查现有索引（本文被要求先查，已查完）**：

```sql
-- packages/shared/src/db/schema.ts:137-151（= docs/tools/00 §5.1 的 :192-207）
CREATE TABLE events (
  seq INTEGER PRIMARY KEY AUTOINCREMENT, id TEXT NOT NULL UNIQUE,
  project_id TEXT NOT NULL, type TEXT NOT NULL,
  actor_type TEXT NOT NULL, actor_id TEXT, layer TEXT, subject TEXT,
  turn TEXT, detail TEXT NOT NULL, created_at TEXT NOT NULL
);
CREATE INDEX idx_events_seq   ON events(project_id, seq);
CREATE INDEX idx_events_layer ON events(project_id, layer, seq);
```

**回答"能不能高效地问'这个命令在这个 source 上跑过吗'"：不能。** 三层原因：

1. **没有 `subject` 上的索引。** 只有 `(project_id, seq)` 与 `(project_id, layer, seq)`。按 `subject` 过滤会退化成 `idx_events_seq` 全区间扫描。`subject` 列已经存在，所以这一条是三者中最省的一条加法：`CREATE INDEX idx_events_subject ON events(project_id, subject, seq)`。**但它解决不了下一条。**
2. **命令 id 只活在 `detail` 这个 TEXT JSON blob 里，不在 `subject` 里——这是关键的错位。** `detail.command` 是契约 §5.1 的约定，`subject` 装的是实体路径。SQLite 不能索引 JSON 内部字段，除非加**生成列** `command TEXT GENERATED ALWAYS AS (json_extract(detail,'$.command')) VIRTUAL` 再对它建索引。**只加 `subject` 索引不足以回答本文的问题。**
3. **store 的读接口根本没暴露这个查询。** `getEventsSince(seq, { layer?, excludeActor?, limit? })`（`store/local-store.ts:734-762`）与 `getEvents(limit, { layer? })`（`:812-826`）是仅有的两个读事件方法，**都不接受 `type` 或 `subject` 过滤**。所以调用方只能取回一堆行再在 JS 里过滤——这正是 `origin/niko` 干的事：在 `for (const reward of band.rewards)` 循环里两次 `store.getEventsSince(0)`（契约 §8.2 登记为 `:183,188`），每次扫**全部历史**并逐行 `rowToEvent` 反序列化 `detail`。O(奖励数 × 历史长度 × 2)。

**要修好它需要什么，代价写清楚**：

| 需要的改动 | 代价 |
|---|---|
| `CREATE INDEX idx_events_subject ON events(project_id, subject, seq)` | 一行 DDL + 每次 append 多维护一棵 B-tree。可接受，但**不足以回答"哪个命令"**（见错位 2）。 |
| 生成列 `command` / `commandKey` + 其索引 | 需要 `ALTER TABLE`。**但本表没有 ALTER 迁移路径**：`schema.ts:127-153` 是**形状探测式重建**——`PRAGMA table_info(events)` 探不到期望列就 `DROP TABLE IF EXISTS events` 再建。加列必须同步扩展探测条件（`:134` 的 `eventCols.has('seq') && eventCols.has('actor_type')`），**写错一个字就在下次启动时静默清空整个世界的历史**（`:127-130` 的注释逐字承认这个风险存在过）。还要回写 `docs/tools/00 §5.1` 的索引清单。这是不成比例的代价。 |
| `WorldStore` 新增读方法 `findCommandRun(subject, key)` | `world-store.ts` 是两个进程共用的接口，加方法要同步 `LocalWorldStore` 与任何测试替身。中等代价。 |
| **回滚语义**（致命，见 §4.4） | 无法用索引解决。 |

**结论：A 单独不成立。** 性能可修但不便宜，回滚语义不可修。

### 4.2 候选 B：被触发实体的 `command_log` frontmatter

**优点**：

1. **查询是 O(本实体上的记录数)，且零额外 I/O。** 触发点已经读过并 `parseFrontmatter` 过 source 了（`roll-dice.ts:117,124`；`choose.ts` / `use-item.ts` 同形），`command_log` 就在手里的那个对象上。对比 A 的"两次全表扫 + 全量 JSON 反序列化"，差距不是常数级。
2. **它与它守护的事实在同一个文件里**，一起备份、一起 diff、一起回滚（§4.4）。
3. **它复用了动作层既有的幂等惯例，而不是新造一套。** `rollDice` 的重掷门禁判据就是**文件自己的 frontmatter** `roll_dice.result`（`roll-dice.ts:149-155`），不是事件查询。`command_log` 是同一个模式往上一层。选 A 等于在既有惯例旁边立第二套幂等约定 = 契约 §8 反模式 5。
4. **玩家与 Agent 都看得见。** `look_at` 读的是文件；作家 Agent 读的是文件。硬门 1「玩家要能复访到」在这里是免费的。

**缺点（如实列，不粉饰）**：

1. **能被人/Agent 改。** `editEntity` 对任何顶层 key 做浅合并（`actions/delete.ts:195-201`），`write`/`edit` 工具对 `world/**.md` 全放行（`extensions/world-context.ts:50-56`）。一个想改的 Agent 能改。
2. **写它要重新序列化整个 frontmatter**，丢注释、重排键。见 §4.5 的专门分析。
3. **实体被删除，日志跟着消失。** 删了再由命令重建 → 重新发奖。但这是**正确**的：文件即真相，实体不在了，"它上面发生过什么"也不该在了。

**对缺点 1 的处置**：

- **不加密、不签名、不做校验和。** 单机单玩家世界里给自己的存档加防篡改是安全剧场。玩家本来就能直接改 `roll_dice.result`——这个洞早就存在且被接受。云端多租户下这条是否变成真问题，归 `09`。
- **真正要防的是"Agent 误伤"，不是"玩家作弊"。** 但必须把**限损措施**与**真防线**分清——**真防线只有一道**：

| | 是什么 | 挡得住什么 | 挡不住什么 |
|---|---|---|---|
| **真防线**：`04` 的保留键拒绝列 | `edit` / `set_status` 效果对 `command_log` / `command_error` 这两个保留键**拒绝写入** | **命令自己蓄意或误写保留键——根本不可能发生** | 不经动作层的直接改文件（`bash`、人手改） |
| 限损措施 (a)：`editEntity` 的浅合并 | 只动调用方传的键（`actions/delete.ts:195-201`） | 键的**意外丢失**（Agent 改 `title` 不会碰掉 `command_log`） | **保留键的蓄意写入**——浅合并对"你传了这个键"是照单全收的 |
| 限损措施 (b)：`07` 的 skill 文案 | 声明这两个键引擎所有、禁止手写 | 顺从的模型 | 什么都挡不住——**提示词级，不是工具级**（契约 §6.2 的区分） |
| 限损措施 (c)：形状校验 | §2.1 的 strict schema | 被改**坏**的日志 → `command_log_corrupt` **报错**而不是被当成"没跑过"（fail-closed，与 `rules/interactive.ts:70-72` 同向） | 被改得**合法但错误**的日志；以及整段删除 |

> **不要把 (a)(b)(c) 读成"三道防线"。** (a) 防的是丢失不是写入，(b) 是提示词，(c) 是发现而非阻止。**只有 `04` 的拒绝列真正让"命令写坏自己的幂等回执"不可能发生**；其余三条只是把损害面收窄。
- **`command_log` 被完整删除**这一种情况，上面没有一条挡得住（空数组 = 合法 = "没跑过"）。这是 B 路线剩下的真实洞，用 C 的交叉校验兜底（§4.3）。

### 4.3 候选 C：两者结合 —— **本文的主张**

**主张：单一真相源 = `command_log`（唯一被查询以决定执行与否的东西）；事件表 = 审计面（永不参与判定，只用于诊断与验收）。**

这不是"两个都是真相"的和稀泥，而是一次明确的角色分工：

| | `command_log` | `events` |
|---|---|---|
| 谁写 | 本模块的 `writeCommandLog`（§8.2） | 每个效果自己调的动作方法（契约 §5.2） |
| 热路径读 | **是**——唯一判据 | **否**——任何"为了幂等去查事件"的代码在评审直接驳回 |
| 回滚时 | 随文件回滚（§4.4） | append-only，不回滚 |
| 被篡改时 | 形状错 → 报错；整段丢失 → 退化为"没跑过" | 无法被 Agent 篡改（无写事件工具） |
| 用途 | 判定 | 诊断、验收断言、作家注入（`10` 拥有） |

**事件表在这套分工里赚到的那份钱**：因为每个效果的事件都带 `detail.command`，所以**"日志说没跑过但事件说跑过了"这种不一致是可检测的**。检测点不放在热路径，放在两个地方：

1. **验收测试**（§10 的 N1/N2 断言直接查事件计数）；
2. **一个诊断入口**——建议挂在 `07` 已经要做的写入即校验旁边，或做成 `tools/` 下的一次性脚本；**不新增动作方法，不新增路由**。`[推断]` 它的实际使用频率很低，因此不值得进 `ACTION_METHODS`。

#### 4.3.1 `detail.commandKey` —— 本文曾提议，现**撤回**（与 `09` 协商收口）

本文早前提议给效果事件追加 `detail.commandKey`，使审计从"哪个命令干的"精确到"哪一次运行干的"。`09` 主张 `detail.command` 是**唯一**可选键。**本文撤回提议，采用 `09` 的口径**，并正面回答"把内部标识写进世界事件是否恰当"：

**不恰当。** 三条理由，一条比一条硬：

1. **`detail` 的服务对象是事件表与人话渲染，不是幂等。** `docs/tools/00 §5.2:238` 逐字要求「`detail` 必须**自足**……渲染人话时不许回读世界目录」——它的设计意图是"让这条事件能被读懂"。`commandKey` 是一个 16 位 hex，**对任何渲染模板都没有意义**，它只对本模块的内部比对有意义。往 `detail` 里塞它，是把一个内部标识伪装成世界事实。
2. **它会制造第二个幂等真相源的外观。** 本文 §4.3 的整个分工是"`command_log` 判定、事件表审计"。一旦 key 出现在事件里，下一个读代码的人**必然会问"那能不能直接查事件表？"**——而 §4.1 已经证明不能（无索引、JSON blob、无查询接口）。**把判据的材料摆进审计面，等于给一条已经被否掉的路重新铺砖。**
3. **本文并不需要它。** 审计要回答的是"日志与世界是否一致"，`detail.command` + `subject`（实体路径）+ `type` 已经足够：对某个 source 数一数某命令产生了几条 `entity_created`，与 `command_log` 里该命令的 `steps` 对照即可。**精确到"哪一次运行"是锦上添花，而它的代价是污染一个有明确职责的结构。**

> **撤回后不留残件**：`command_log` 内部仍有 `key`（那是**本模块自己的**文件，不是世界事件），外发 `detail` 只有 `detail.command`。`09` 与本文两处口径现已一致。

> **`detail.by` 同样已按主代理裁定删除**（§11.8）：它撞上了 `layer_initialized.by` 的闭枚举（`schemas/events.ts:99` 逐字 `z.enum(['writer','player','engine'])`）。只留 `detail.command` 是更好的设计——它本身就表达了"来自命令"，而 `by: 'command'` 是冗余的第二真相源。

### 4.4 决定性的那一条：回滚

把它单列，因为它一条就能否掉 A。

**事件表是 append-only 的。** `world_rolled_back` 是**追加**一条"回滚发生过"（`schemas/events.ts:108`，detail `{snapshot, to}`），不是删除历史行。`store/cursor.ts:66-70` 的注释逐字说明将来的 handler 应该「append `world_rolled_back` FIRST, then call this in the SAME `historyDb` transaction」——依然是追加。

于是：

- **若真相源在事件表**：回滚把奖励文件还原成"不存在"，但 `entity_created` 事件行还在 → 幂等判定说"跑过了" → **玩家永远拿不到那份奖，且没有任何入口能修**。这是不可恢复的死状态，直接踩契约 §9.5 的 reopen 触发条件 2。
- **若真相源在 `command_log`**：回滚把 source 文件还原成"没有那条 key"的样子，奖励文件也还原成不存在 → 下一次触发**重新首跑** → 世界自洽。**幂等与回滚的一致性是白送的，不需要写一行代码。**

这是 §4.3 主张的最强论据，也是本文对契约 §9.5 reopen 条件 2 的正式答复：**能在不新增事件类型、不新增状态存储的前提下做到幂等**，条件是真相源必须随文件走。

> **前提**：`rollbackWorld` / `snapshotWorld` 今天**没有任何 handler**（`actions/service.ts:75-76` 只有签名、`:105-106` 只有注册；`store/cursor.ts:66-68` 逐字「there is no rollback handler today」；`docs/tools/01:1121`、`docs/hooks/03:597` 互相印证）。本文的设计是**为将来的 handler 预设约束**：回滚 MUST 恢复整份实体文件（含 frontmatter），MUST NOT 只恢复正文。

### 4.5 写 `command_log` 的代价：frontmatter 重序列化

**必须如实登记的一条。**

`rollDice` 写回 `result`/`passed` 时用的是 `patchRollDiceResult`（`actions/roll-dice.ts:204`）——一次**外科式的改写**，注释逐字说明理由：「Inline YAML / no block: never guess, never rewrite the author's frontmatter」（`:206`）；`rules/dice.ts:273-276` 进一步解释它为什么不整体重写（会重排 frontmatter、把 `result: 62` 变成字符串）。而 `editEntity` 走的是 `stringifyFrontmatter(merged, body)`（`actions/delete.ts:220`），**整份重序列化**，注释、键序、YAML 风格全部丢失。

写 `command_log` 只能走后者（新增一个顶层数组键，外科式插入没有意义）。后果：

- **同一次 `rollDice` 调用里，step 9 刚外科式地保住了作者的 YAML，本模块随后就把它整份重排了。** 外科式补丁的价值被抵消。
- 影响面：**每个被命令触发过的实体**的 frontmatter 会被规范化一次。`templates/whitechapel-jp/world/london-map/04-investigation-dice.md:19-20,27,36-37` 是多行折行的长文本标量，重序列化后折行位置会变。**内容不变，diff 变大。**

**处置**：接受，并把它压到最小——

1. **每次运行只在 §5.4 规定的时刻写 source**（不是每步都写整份）；
2. **写之前必须重新 `readFile` + `parseFrontmatter`**（不能复用触发点早先读的那份），否则会把效果刚写进 source 的东西覆盖掉；
3. 若实现期实测 diff 噪音不可接受，**备选方案**是仿 `patchRollDiceResult` 写一个 `patchCommandLog(raw, entries)`，只替换 `command_log:` 到下一个同级键之间的区块。**本文不预先选它**——它要处理 YAML 缩进与块结束边界，复杂度明显高于收益，标为实现期的可选优化。

## 5. 行为契约逐步

统一入口（`03` 拥有执行序与部分失败语义，本文拥有它前后的幂等门；边界已与 `CmdEval` 划分）：

```ts
// packages/shared/src/commands/run.ts (NEW)
export type SettleMode = 'fresh' | 'resume';

export interface SettleInput {
  /** 被触发实体的世界相对路径 */
  source: string;
  hook: 'roll_resolved' | 'choice_selected' | 'use_item_on';
  /** 触发点算出来的 fact（§3.3） */
  fact: string;
  /** 已经 parse 过的 source frontmatter，避免重复读盘 */
  parsed: ParsedFrontmatter;
  mode: SettleMode;
}

export interface SettleReport {
  /** 本次真正执行了效果的运行 */
  ran: Array<{ key: string; command: string; steps: number }>;
  /** 命中 key、原样复用的运行 */
  reused: Array<{ key: string; command: string }>;
  /** 续跑补完的运行 */
  resumed: Array<{ key: string; command: string; from: number; to: number }>;
  /** 本次失败并写进 command_error 的那一条（至多一条） */
  failed?: { key: string; command: string; step: number; code: ActionErrorCode; message: string };
}

export async function settleWorldCommands(
  ctx: ActionContext,
  input: SettleInput
): Promise<SettleReport>;
```

### 5.1 步骤

**S0 取源锁。** `withSourceLock(ctx.store, source, work)`（§8.3）。
> **漏了会怎样**：玩家双击 → 两个 HTTP 请求并发进到 S1，都读到"没有这条 key"，都执行，都写日志（后写者赢，日志里只剩一条），奖励却发了两份。硬门 2 当场破。

> **`dry-run` MUST NOT 写 `command_log`**（与 `09` 协商收口）。`09` 的 dry-run 是"只算不做"的预演。若它留下一条日志，**真实触发时按 key 查到"跑过了" → 判 `reused` → 奖励永不落地**。这是硬门 2 的**反向**违反：不是重复结算，是**该给的永远不给**——而且比重复结算**更难发现**（玩家看不到多出来的东西，只看到什么都没发生，且世界自洽、无错误、无半成品）。
>
> 因此本文的规定是**最简单的那条**：dry-run 在 S0 之前就分岔，**完全不进入 S4/S5 的任何写盘路径**。
>
> 若 `09` 坚持要留痕，唯一可接受的形态是新增 `status: 'planned'`，并在 **S3 按"未跑过"处理**（即 `planned` 记录既不算 `done` 也不算 `partial`，不参与复用、不参与续跑），**且与 `09` 同批改**、`SettleReport` 的四 verb **不增第五个**（`planned` 是日志状态，不是结算动词）。**本文不主张这条**——留痕的价值低于它引入的那一类静默失败。

**S1 读日志。** 从 `input.parsed.frontmatter.command_log` 解析出 `CommandLogEntry[]`；形状非法 → `fail('command_log_corrupt', …)`（§7）。
> **漏了会怎样**：一条被改坏的记录会被 `Array.prototype.find` 静默跳过 → 判定"没跑过" → 重复结算。fail-closed 是唯一安全的默认。

**S2 解绑定，算 key。** 从 `on.<hook>[]`（02 拥有）解出 `(command, index)` 列表，逐条 `commandKey({source, hook, command, fact})`。
> **S2 只需要 `command` 与 `index`，不需要 `with:` 的值**——这是 §3.5 的直接后果。若实现期发现 S2 不得不读 `with:` 才能算 key，说明 key 公式被改坏了。

**S3 分流（本文的核心判定）。** 对每条绑定：

| 日志里同 key 的记录 | `mode: 'fresh'` | `mode: 'resume'` |
|---|---|---|
| 不存在 | **首跑**（S4） | **不动**（`ran` / `reused` 都不记）。**这是 resume 模式最重要的一条约束**，见下 |
| `status: done` | 复用，计入 `reused` | 同左 |
| `status: partial` | **续跑**（S5） | **续跑**（S5） |

> **resume 模式绝不首跑。** 否则会出现：作者改了 `with:` 或改了 `on` 的分支（`fact` 变 → key 变 → 日志里没这条），resume 模式下会当成"没跑过"而**首跑一次全新的运行**——而此时 `roll_dice.result` 已经存在，玩家并没有做任何新行动。那就是凭空多一次结算。所以 resume 只被允许**补完已经开始的事**，不被允许**开始新的事**。

**S4 首跑。** 写入 `status: 'partial'` 的意向记录（`steps: []`）→ 落盘 → 逐步执行 → 每步成功后追加 step 回执并落盘 → 全部成功后置 `status: 'done'`、删除同 key 的 `command_error` → 落盘。执行序归 `03`；效果总数上界 `WORLD_COMMAND_EFFECT_BUDGET = 24`（见 §5.4）。

**S5 续跑。** 从 `entry.steps.length` 开始，跳过前面所有已有回执的步。校验 `on.<hook>[entry.index]` 仍然指向 `entry.command`；不指向 → `fail('command_resume_drifted', …)`（§7）。
> **漏了会怎样**：作者在 `on` 数组里插了一条，index 平移，续跑会从**另一个命令**的第 2 步接着跑 → 执行一个从未开始过的命令的后半段。这比重复结算更难排查。

**S6 收尾。** 返回 `SettleReport`。失败时把 `command_error` 写进 source（§2.2），并按 `03` 的部分失败语义决定是抛还是返回。

### 5.2 触发位置：两个调用位，一个函数

`02` 把触发点定在 `rollDice` / `chooseOption` / `useItemOn` 三处。**本文对 `rollDice` 追加一个必需的第二调用位**，理由是一个会导致永久卡死的真实缺口：

```
roll-dice.ts:149-155   step 6 重掷门禁：declared.result !== undefined → fail('dice_already_rolled')
roll-dice.ts:243/:245  step 11 之后 = 02 提议的触发点
```

**第一次掷骰后命令跑到一半崩了，此后任何重试都在 step 6 被拒，永远到不了 step 11，半成品永久卡死。**

因此：

| 调用位 | 位置 | mode | 何时生效 |
|---|---|---|---|
| **A** | `roll-dice.ts` step 11 之后（`:243` 与 `:245` 之间） | `fresh` | 刚掷出点数 |
| **B** | `roll-dice.ts` step 6 抛错**之前**（`:153` 的 `if` 内、`fail` 之前） | `resume` | 已有点数，重复触发 |

调用位 B 的性质：

- `parsed` 在 step 3（`:124`）已经在手里，**读日志零额外 I/O**；
- 日志全是 `done` 时是**纯 no-op**，不写盘、不发事件；
- 有 `partial` 时补完，然后**照常抛 `dice_already_rolled`**，消息里追加补完了什么（§7）。

`chooseOption` / `useItemOn` 没有等价的一次性门禁，只需要调用位 A（mode `fresh`，S3 自己会判复用）。

**代价，如实认账**：`rollDice` 因此出现一条"**以错误结束，但世界确实发生了变化**"的路径。这与 `actions/errors.ts:46-48` 的注释「throwing means nothing was appended」字面冲突，已在 §11.2 登记。

### 5.3 `append_body` 这类非幂等效果

拍板 A 给 `edit` 增加了 `append_body` 子形态。**它是非幂等效果的代表**（重复执行会把同一段文本追加两次），与 `moveEntity` 的天然幂等正好是两极：

| 效果 | 天然幂等？ | 判据 |
|---|---|---|
| `move`（→ `moveEntity`） | 是 | 目标已存在 → `already_exists`（`actions/move.ts:147-149`）；源不存在 → `not_found`（`:87-90`）。**上游 `choice_actions` 里的同一能力仍叫 `kind: take`**（既有系统的名字，不改）；命令的 `do[].action` 一律写 `move` |
| `consume`（→ 状态迁移） | 是 | 已是空瓶就不再变（`templates/wuwu/skills/wuwu-play/SKILL.md:47`） |
| `give`（→ `createEntity`） | **否** | 只在**同路径**上幂等（`actions/create.ts:100-103`）；目标被玩家挪走后第二次会成功（§10.1 的非空性断言就是它） |
| **`append_body`** | **否** | 追加没有天然守卫，**只有 `command_log` 能挡住** |

**`append_body` 自己不判重**（主代理给 04 的硬约束 2：幂等 MUST NOT 靠扫正文——niko 的 `<!-- resolved-dice:62 -->` 正是契约 §8 反模式 1）。判重在 **S3 这一层统一做**，与效果种类无关。这是本文"step 级回执"设计的主要收益之一：**新增效果不需要自带幂等逻辑**，只要它自己是确定性的。

### 5.4 落盘时机：为什么是"意向先写 + 逐步回执"

三个候选：

| 协议 | 写 source 次数 | 崩在中间会怎样 |
|---|---|---|
| **P1 全跑完再写一次** | 1 | **零记录，N 个效果已落地** → 下次重跑 → 重复结算。**致命，否决。** |
| **P2 只写意向、跑完改 done** | 2 | 知道"开始过"，不知道"做到哪一步" |
| **P3 意向 + 每步回执（本文选它）** | N+1 | 精确知道做到哪一步 |

P2 为什么不够：续跑必须知道做到第几步。能不能从世界现状反推？**不能可靠反推**——`give world/x/clue.md` 之后玩家把它拖进背包，`world/x/clue.md` 变成 missing，与"从来没发过"在文件系统上**完全不可区分**。`origin/niko` 正是为此写了 7 行跟踪 `entity_moved` 链的代码（`runDeclaredRoll` 里 `let actual = reward.path; for (const event of await store.getEventsSince(0)) if (…entity_moved…) actual = …`），代价是一次全表扫，而且对"玩家把它删了"依然无解。**一条 step 回执让这 7 行和那次全表扫一起消失。**

**P3 的代价**：N+1 次 `writeFileAtomic`（`store/local-store.ts:195-198`，mkdir + 写 tmp + rename），每次伴随一次 frontmatter 重序列化（§4.5）。`03` 已定 `WORLD_COMMAND_EFFECT_BUDGET = 24`（一次**触发**跨所有匹配命令的效果总数上界，不是"每条命令 12 步"）：**最坏 25 次写盘，典型 4 次**——`03 §7.2` 的典型触发是 3 个效果（发 1 奖 + 追加正文 + 写回选项）。本地盘上两者都可忽略。`03` 的取数理由也成立：24 = 2 × 12，12 是本仓对"作者手写列表"的既有共识（`CHOICE_LIMIT=12` `rules/interactive.ts:14`；`MAX_ACTION_PATHS=12` 与 `MAX_SLOT_PATHS=12` `declared-actions.ts:34,36`）。**上限是这个代价的唯一护栏，所以它必须存在**——`03` 提供了。

> **超限是"世界零改动"的拒绝，这一点对本文的续跑有利**：`03` 保证效果数在阶段 A 就已静态确定（不变量 I-2：无循环/无递归/无算术 ⇒ 所有上限静态可核验），所以超限在执行前被拒，**既不产生半成品，也不消耗 `command_log` 的任何步骤**。因此它不会留下需要续跑的中间态——本文的 `partial` 只可能来自"效果执行到一半时进程死亡"，不会来自"跑到一半发现超限"。

**每次落盘前 MUST 重新 `readFile` + `parseFrontmatter`。** 因为效果本身可能刚写过 source（`edit` 写 `choice` / `choice_actions` 回 source 是最常见用法之一；`append_body` 写正文）。复用旧快照写回去会把效果的成果抹掉。这是同步执行下唯一需要的一致性纪律——没有并发，只有**自己踩自己**。

### 5.5 失败可见性的第二条通路：`SettleReport` 必须进 `details`

契约 §5.1 冻结了「命令事件的 actor = 触发者」。而作家注入**必然排除 actor == 自己**：

```ts
// packages/shared/src/inject/collect.ts:250-252
layer: actor.type === 'character' ? (layer ?? undefined) : undefined,
excludeActor: actor,
```
```ts
// packages/shared/src/store/local-store.ts:745-748
where.push(`NOT (actor_type = ? AND COALESCE(actor_id, '') = ?)`);
```

**后果链条（主代理已实测确认）**：作家调 `roll_dice` 触发命令 → 命令产生的事件（例如新建的笔记）在它**自己下一轮**的注入里被过滤掉 → 它看不见 → 以为没人发奖 → 自己再 `write` 一份 → **重复发奖**。

**修法不是改 actor**（那会让世界史读成"引擎自己拿走了东西"，违反契约 §5.1 与 `doc-21 §3.2` 把 `god` 从 `player` 单列的同一条理由），而是**让后果走 `tool_result`**：

```ts
// extensions/toolkit/roll-dice.ts:49-50 —— 触发动作的 details 里 MUST 带上命令回执
const result = await getActionService(ctx).rollDice({ path: params.path });
return ok(result as { text: string; details: RollDiceDetails });
```

**因此本文的规定**：触发点的 `ActionResult.details` MUST 带上 `SettleReport`。形状的最终归属是 `04`（建议 `details.commands: Array<{id, ok, effects: [{action, ok, error?}]}>`）；本文只要求在**两个通路**里都能看到同一次运行的同一批事实：

| 通路 | 覆盖谁 | 内容 |
|---|---|---|
| `details` → tool_result | **触发它的那个 Agent，同一轮** | `SettleReport`（`reused` / `resumed` / `failed` 全在里面） |
| `command_error` → 实体 frontmatter | 玩家（`06` 渲染）与后续任何读到该文件的人 | 最近一次失败 |
| 事件注入 | 其他 actor 与下一轮 | 命令产生的效果事件（**触发者自己看不到**，这是 excludeActor 的已知行为） |

**这三条通路对幂等的意义**：`details` 那条是**唯一**能让触发者在同轮知道"这次是复用不是新结算"的通路。没有它，作家 Agent 无法区分"我刚发的奖"和"玩家早先发的奖"，也就无法抑制自己的重复发奖冲动——提示词级的「Do not record the choice a second time」（`world.ts:1178`）补不上这个信息缺口。

### 5.6 `resumed` 与 `reused` 的语义分界（与 `06` 的接口确认）

`06` 已把玩家侧状态枚举定为 `applied` / `reused` / `resumed` / `skipped` / `blocked` / `failed`，并要求 **`resumed` 在玩家侧与 `applied` 同形**。本文确认，并给出本文一侧的分界，因为**两者的模型侧语义与玩家侧语义不同**：

| | `SettleReport` 里的归属 | 世界发生了什么 | 玩家侧（`06`） | 模型侧（`details`） |
|---|---|---|---|---|
| `reused` | `reused[]` | **什么都没做**，上次的步骤原样还在 | `reused`（"这次没再给"的语气**是对的**） | 明确标 `reused` |
| `resumed` | `resumed[]`（带 `from` / `to`） | **补做了缺的步骤**——世界因此变完整了 | **与 `applied` 同形，MUST NOT 有独立文案** | 明确标 `resumed`，且带 `from` / `to` |

**答复 `06` 的两条**：

1. **`resumed` MUST NOT 被归进 `reused`，也 MUST NOT 被归进 `failed` / `blocked`。** 它是独立的一档。归 `reused` 会丢掉 `from` / `to`（模型侧就看不到"补了几步"）；归 `failed` / `blocked` 会让玩家看到"这次没给"的语气，而**断点续跑恰恰是给了**。本文对这一条的形式化要求就是 `SettleReport` 里 `resumed` 必须是独立的数组，不能合并进 `reused[]`。
2. **玩家侧与 `applied` 同形，本文同意，且理由与 `06` 给的一致**：对玩家而言"结果都在那里了"就是全部事实，说出"上次只做了一半"会让玩家以为世界曾经处于坏状态，而事实是世界现在是完整的。这与 `_shared/failure-and-revisit.md:30` 的「a second visit may repair missing pieces」同向——**修补是正常行为，不是故障报告**。

**回执 MUST 逐效果带上缺失细节。** `06` 要求 `details` 的回执里每个效果带 `error.detail`（缺什么）。本文追加一条更硬的理由：那是**模型自修的唯一输入**，也是玩家 `command_error.message` 里 `Missing: {target}` 的唯一来源。`not_found` 只说"实体不存在"对模型不够——它需要知道**哪个路径**才能改。这与硬门 4「不静默失败」要求失败**可行动**一致，不是措辞偏好。

**`plan` 是否进 UI**：`06` 不必渲染它，也不必刻意跳过——`[推断]` 显示成一个短 hex 无害。本文不把它列为玩家信息（它是溯源），因此**不构成对 `06` 的约束**；最终由 `06` 定。

### 5.7 数组实参的引擎内有界展开：step 回执 MUST 记「扁平效果序」

主代理裁定：效果实参可以传**整个数组**（`with: { rewards: "{{ trigger.entry.rewards }}" }`），**展开发生在效果的引擎实现内部**，对作者不可见——没有作者可见的循环、下标或 `foreach` 语法。上界由**实体 frontmatter 的 schema 上限**封死（`rewards` ≤ 3，见 `declared-actions.ts:146-151`；08 实测存量 144/144 档恰好 1 项）。`04` 采用的两个冻结形态名：**`list-args`**（逐项迭代）与 **`fold-args`**（折叠为一个 map）。

**两者对本文的幂等后果完全不同，必须分开说：**

| | `list-args`（如 `give: "{{ trigger.entry.rewards }}"`） | `fold-args`（如 `options → choice.options + choice_actions`） |
|---|---|---|
| 语义 | N 个**独立效果** | **1 个结构性写入**，整个数组变成一个对象 |
| 效果数 | = 数组长度（≤ schema 上限 3） | **恒为 1** |
| 失败 | 逐项独立；第 2 项失败**不回滚**第 1 项 | 整体成功或整体失败 |
| **本文的 step 回执** | **每项各占一个 `step`** | **只占一个 `step`** |
| **续跑粒度** | 可以停在"第 2 项做完、第 3 项没做" | 停在"折叠做完了/没做完"，无中间态 |

于是本文的 `steps[]` 必须能表达两种形状，用**扁平效果序**（`steps[].step`）作续跑游标，用**声明位置**（`steps[].at`）作溯源：

| 概念 | 定义 | 用途 |
|---|---|---|
| 声明位置 `at` | `do[<i>]`，或 `list-args` 展开时的 `do[<i>]#<k>`（1-based） | **溯源**：告诉作者"这条回执是哪个声明产生的" |
| 扁平效果序 `step` | 展开后**实际执行**的次序，`0..23`，严格递增无空洞 | **续跑的游标**——`S5` 从 `entry.steps.length` 接着跑 |

**为什么续跑的游标必须是扁平序而不是声明位置**：`S5` 的实现是 `steps.length`。若 `step` 记声明位置，`list-args` 展开后会出现重复值（`do[0]`、`do[0]`、`do[0]`、`do[1]`…），`steps.length` 就不再等于"已完成的扁平效果数"，续跑会从错误位置开始 → **重复结算或漏跑**。

**为什么仍要同时记 `at`**：扁平序回答不了"崩在哪个声明里"，而作者排查要的正是这个。`at` 是免费附带的，**MUST NOT 参与任何判据**（与 `plan` 同样的纪律：记录 ≠ 参与判定）。

**与 §5.3 的关系**：04 已定数组迭代的**逐项前置检查与失败独立**（第 2 项已存在、第 3 项被占 → 分别报，不整体回滚）。这正好落在本文的 step 粒度上——**每项各占一个回执**，所以"第 2 项成功、第 3 项失败"在 `command_log` 里可表达、可续跑。

> **`fold-args` 的键冲突检测对本文有直接影响**（主代理派给 `04`）：折叠出的 map 与实体已有 `choice_actions` 键相交时若选择**覆盖**，那是一次**静默覆盖已结算事实**——若那条 `choice_actions` 是上一次运行写下的，覆盖它等于改写了已结算的结果。**本文建议 `04` 选"拒绝 + 可见错误"**（硬门 4），并补一条本文的理由：覆盖会让 `command_log` 说"跑过了"而世界里的按钮已经不是那次跑出来的，两者不一致。**但这归属 `04` 的效果契约**，本文只登记后果。

**上界仍然静态可界定**：展开次数 = 数组长度 ≤ schema 上限（`rewards` ≤ 3），执行前已知。与 `03` 的 `WORLD_COMMAND_EFFECT_BUDGET = 24` 的关系：**24 是展开后的效果总数**，不是声明条数。`03` 的 I-2（无循环/无递归/无算术 ⇒ 上限静态可核验）**不受影响**——展开次数的上界来自 schema，不来自运行期值。

**数组进 `with` 但不进 `commandKey`**（主代理复核确认，与 §3.5 一致）：数组内容或长度变化**不改变 key**，因此不会因数组变化而重复结算。这是 `args` 排除的又一好处。**但代价 3（`overlapping_command_when`，§3.5）因此更需要**——已交叉引用。

## 6. 四种重复场景的语义表

| 场景 | 会不会再次进入触发点 | 幂等如何生效 | 玩家看到 | 需要新代码吗 |
|---|---|---|---|---|
| **① 快速双击（并发同一请求）** | 会，两次 | **S0 源锁**串行；第二个进来时日志已有 key → `reused` | 同一份结果，无闪烁；`06` 决定是否提示"已结算" | **要**：源锁（§8.3） |
| **② 刷新页面（含运行中途刷新）** | 不会（刷新只重拉卡片，不重发动作） | 不需要——世界事实在盘上 | 与刷新前一致；**运行不会被客户端断开中断**（§6.2） | 否 |
| **③ 关掉浏览器，明天回来（复访）** | 不会（除非玩家主动再点） | 不需要；若上次是 `partial`，`command_error.pending` 让它**可见且可点** | 同一批已落地事实 + "还有 N 项未落地"的入口 | `06` 的渲染 |
| **④ 作家 Agent 同一轮又调了同一个动作** | 会 | key **不含 actor**（§3.7）→ 命中玩家那次的记录 → `reused`；且 `details` 让它**当场看见**（§5.5） | 无变化 | 否（靠 §3.7 + §5.5） |

### 6.1 场景 ①：`serialDeclared` 的层次错位必须解决

**现状（已核实）**：

```ts
// apps/server/src/engine/declared-actions.ts:152-162
const inFlight = new Map<string, Promise<unknown>>();
export async function serialDeclared<T>(key: string, work: () => Promise<T>): Promise<T> { … }
```

调用点只有两处，**都在 server 路由层**：`apps/server/src/routes/world.ts:1141`（`/material-review`）与 `:1170`（`/choice`）。key 是 `store.worldRoot`——**整个世界一把锁**。

三个独立的问题：

1. **`/api/dice`（`world.ts:1102-1120`）与 `/api/use-item`（`:1124-1135`）根本不在锁内。** 而这两个正是 `02` 定的触发点中的两个。骰子的双击今天靠 `dice_already_rolled` 兜底，`use_item_on` 什么都没有。
2. **锁是一个模块级 `Map`，在 `apps/server/src/engine/` 里。** 作家 Agent 走 `extensions/toolkit/*` → `getActionService(ctx)`（`extensions/toolkit/deps.ts:77-79`）→ 直接进动作层，**永远拿不到这把锁**。这与契约 §4.1 登记的架构事故是同一个病。
3. **粒度过粗**：整个世界一把锁，意味着玩家在 A 卡上的操作会阻塞 B 卡上的操作。

**处置：把锁下沉到动作层，并改成按 source 的粒度。**

```ts
// packages/shared/src/commands/serial.ts (NEW)
/**
 * 按世界根 + 源路径串行。进程内、内存态、无持久化——它不是世界状态，
 * 跑完即从 Map 移除（同 declared-actions.ts:160 的 finally 语义）。
 */
export function withSourceLock<T>(
  store: WorldStore,
  source: string,
  work: () => Promise<T>
): Promise<T>;
```

`settleWorldCommands` 在 S0 取它。这样**任何入口**（玩家 HTTP、作家工具、角色工具）都自动被串行，因为它们都经过动作层——这正是契约 §4.1 要的性质。

`world.ts:1141,1170` 的 `serialDeclared` **本批次不动**：它还在保护 `prepareMaterialReview` 与 `runDeclaredChoice`，那是 `08` 的收敛范围。两把锁并存一段时间不会死锁（层次严格嵌套：server 锁在外，source 锁在内）。

**但进程内锁不够，必须诚实登记。** `extensions/toolkit/deps.ts:4-7` 的注释逐字：「The two processes (server / agent) each build ONE WorldStore」，`:18,37` 是 agent 进程自己 `new LocalWorldStore(root)`。**server 与 agent 是两个进程，各持一个 store 指向同一个世界目录。** 进程内的 `Map` 对另一个进程不可见。因此：

- **玩家点击 vs 作家工具调用同时发生**这一种并发，源锁挡不住。
- 兜底只剩"落盘前重读 + 复查 key"（§5.4 的纪律），它把窗口缩到一次读写之间，但不消除。
- 本仓已经就这个问题裁决过：`docs/tools/01:1123` 逐字「**同一文件并发动作**：不加锁，后写者赢」，`docs/tools/REVIEW-评审报告.md:158` 记为 D-4「单玩家世界，实测后再说」。
- **本文不推翻这个裁决**，只把它的适用范围写清楚：单玩家世界里"玩家点击"与"作家轮"天然错开（玩家点击后作家轮才被 `dispatch` 起，`world.ts:1177-1178`），实际碰撞概率极低。`[推断]` 这是可接受的。
- 若评审要求闭掉，代价是一把**跨进程锁**：`.airpworld/locks/<sha1(source)>.lock` 用 `fs.open(..., 'wx')` 独占创建 + 崩溃后的 TTL/pid 回收。`[推断]` 约 40 行，但引入"锁文件泄漏"这一类新故障。**本文不主张现在做**，登记给 `09`。

### 6.2 场景 ②：刷新（含运行中途刷新）

刷新不重发动作，所以幂等根本不参与。**唯一需要写下来的是"刷新发生在运行中间"**：`ActionContext` 的冻结字段里没有 `AbortSignal`（`actions/types.ts:8` 逐字「No AbortSignal, no progress channel」），契约 §4.3 也重申不引入它。所以浏览器断开连接**不会**中断服务端的运行——命令照常跑完，照常落盘。玩家刷新后看到的是完整结果。

**这是一个优点，不是缺陷**，但它意味着：**真正的"中断"只有进程死亡**（崩溃、kill、断电）。§5.4 的 P3 协议就是为这一种情况设计的，不是为"用户点了取消"。

### 6.3 场景 ③：复访 + 半成品不能永久躺着

`_shared/failure-and-revisit.md:30` 逐字：「On revisit, the player should find the same landed facts and a clear next action. A second visit may repair missing pieces, but it must not silently rewrite settled truth or reroll the same action.」

- "same landed facts" ← 文件即真相，白送。
- "**may repair missing pieces**" ← 正是 S5 的续跑。这句话是续跑机制的上位依据。
- "must not … reroll" ← `roll_dice.result` 的重掷门禁 ＋ 调用位 B 用的是 `resume` 模式（只补不新开）。

**`Chalk玩法形态与判定约定.md:51` 逐字：「重复点击沿用真实骰点并修补缺件」**——"沿用真实骰点" = 复用，"修补缺件" = 续跑。内容侧的公开约定已经把本文的两条语义都写死了。

另一条独立的内容侧证据，`templates/wuwu/skills/wuwu-play/SKILL.md:46` 逐字：「Recheck real items and records; **on resume from pauses, fix only deficiencies. Do not draw oil a second time for empty bottle**」——"resume from pauses, fix only deficiencies" 与"do not draw oil a second time"合起来，正是本文 S3 的 `partial` → 续跑语义，逐字对得上。

**半成品不会永久躺着**：`command_error.pending`（**int**，剩余未执行的展平步数，见 §2.2）让 `06` 能渲染一个"还有 N 项未落地"的入口，点它就是再次触发 → 走调用位 B → 续跑。若玩家一直不点，世界仍然可玩（硬门 7）——已落地的部分是真的，未落地的部分作家可以叙述绕过。

### 6.4 场景 ④：作家在它那一轮又调了同一个动作

今天这条路上已经有一个**提示词级**的挡板：`world.ts:1178` 派给作家的 prompt 逐字含「Do not record the choice a second time」。提示词不是机制（契约 §6.2 的区分）。

两道机制把它补上：

1. **key 不含 actor**（§3.7）：作家再调一次 `chooseOption` → 同 source、同 hook、同 command、同 fact → 同 key → 命中 → `reused`。
2. **`details` 里带 `SettleReport`**（§5.5）：`reused` 这个事实**当场**进 tool_result，绕开 excludeActor。这是作家能"知道自己不该再发一次"的信息来源。

`roll_dice` 那条路更硬：`extensions/toolkit/roll-dice.ts:49` 只传 `path`，进 `rollDice` 后在 step 6 撞 `dice_already_rolled`，然后走调用位 B 的 resume（多半是 no-op）。

> **顺带发现的一个冲突**，见 §11.3：该工具的 `promptGuidelines` 第 3 条（`extensions/toolkit/roll-dice.ts:45`）逐字教模型「to re-open the check, edit the old result out of the file first」——**教 Agent 删 `result` 来重掷**，与硬门 3 和 `Chalk玩法形态与判定约定.md:28` 正面冲突。

## 7. 错误边界

| 错误码 | 触发条件 | 给模型看的（`ActionError.message`，英文，随 `toToolResult`） | 给玩家看的（`command_error.message` → `06` 渲染） |
|---|---|---|---|
| `command_log_corrupt` **NEW** | `command_log` 存在但形状不合 §2.1 | `"world/x/a.md" has a malformed command_log at entry 2: key must be 16 lowercase hex characters. The engine owns this field — remove the hand-written entry instead of repairing it by hand.` | 「这张卡的结算回执被改坏了，引擎不敢继续，以免重复发放。」 |
| `command_log_full` **NEW** | `command_log` 已 32 条 | `"world/x/a.md" already carries 32 command_log entries, the maximum. Truncating would let a settled run look unsettled and be paid out twice, so the engine refuses instead.` | 「这张卡的结算记录已满，引擎停下了。」 |
| `command_resume_drifted` **NEW** | 续跑时 `on.<hook>[index]` 不再指向 `entry.command` | `Cannot resume "award-clue" on "world/x/a.md": on.roll_resolved[0] now declares "grant-map". The binding moved after the run started; the engine will not finish one command's steps with another command's plan.` | 「这张卡的规则在结算中途被改过，未完成的部分需要重新处理。」 |
| `dice_already_rolled`（**既有**，`errors.ts:14`） | 调用位 B，且 resume 无事可补 | 原文案不变（`roll-dice.ts:67-70` 的 `alreadyRolledMessage`） | 「这次判定已经出过点数。」 |
| `dice_already_rolled` + 补完 | 调用位 B，resume 补完了 M 步 | 原文案 + `` ` Completed ${M} pending effect(s) from the earlier run: ${names}.` `` | 「这次判定已经出过点数；刚刚把上次没落地的 M 项补齐了。」 |
| 效果自身的错误（`not_found` / `already_exists` / …） | `do[]` 某步失败 | 由动作层原样抛出，本文不包装、不吞 | 由 `command_error.code` + `message` 承载 |

**三个 NEW 码的代价**：`ActionErrorCode` 是 `errors.ts:3-21` 的字符串联合，`HTTP_STATUS` 是 `:24-43` 的 `Record<ActionErrorCode, number>` ——**TypeScript 会强制两处同步**（漏一个编译失败）。建议 HTTP 状态：`command_log_corrupt` → 422（与 `malformed_entity` 同类）、`command_log_full` → 409、`command_resume_drifted` → 409。每个码 2 行，**这是本模块对上位冻结契约最小的一次侵入**。

**不新增码的替代**（若评审要求零新增）：三者都塞进 `malformed_entity` / `invalid_argument`。代价是前端与 Agent 无法区分"卡被改坏了"与"你传错参数了"，硬门 4 要求的"可见"会退化成"可见但不可辨"。**本文主张新增。**

**一条纪律**：本模块 MUST NOT 出现 `console.warn` 作为唯一的失败出口。契约 §7.4 逐字点名了这条既有教训。

**给玩家看的文案的归属**：本文只保证 `command_error` 里**有**这些字段，具体措辞与层级（是否折叠、是否带"下一步"）归 `06`，按 `airp-human-language-information-hierarchy` 的"先说真实状态，再说原因与下一步"来写。本文不替 `06` 定文案。

### 9.1 为什么"把幂等标记藏进正文"绝不能用

逐条，每条都是独立的否决理由：

1. **正文是叙事，不是状态存储。** 契约 §3.2 的整个论证（以及主代理后来把命令文件从 `.md` 改成 `.yaml` 的第 2 条理由）都建立在"不受 schema 约束的文本不能承载机器契约"上。正文里的 marker 是同一个错误的实例——而 niko 的实现正好是契约 §8 反模式 1 的原始标本。
2. **作家 Agent 每一轮都可能改写正文。** 命令的 `edit` 效果**自己**就会追加正文（拍板 A 给 `edit` 加的 `append_body`，正是为 **36** 个声明文件迁移里"骰后短结果显示在原卡上"这条玩家可见功能准备的）。**幂等判据会被它自己守护的那次运行改掉。**
3. **HTML 注释会被渲染器吞掉，于是"看不见"变成"不存在"。** 前端把正文当 Markdown 渲染，注释不显示。人工"清理一下正文"时把它删掉是无痛且无提示的。而 frontmatter 里的 `command_log` 至少是**可见的、有名字的、可被 schema 校验的**。
4. **它只能编码一个标量。** `<!-- resolved-dice:62 -->` 塞得下一个骰点，塞不下"3 步里做完了 2 步、第 2 步的事件是 evt-119"。§5.4 的 P2 分析证明了只有 step 级回执才能支撑续跑。想在正文里塞下这些，等于在正文里发明一套序列化格式——那就是把 frontmatter 重新实现一遍，只是没有 parser。
5. **`includes()` 是子串匹配，不是结构匹配。** 玩家在正文里引用了一句提到 `resolved-dice:62` 的文字（例如作家写了一段解释判定机制的话），守卫就误判成"已结算"。frontmatter 上的 key 是结构化查找，不会有这类误命中。
6. **它无法回滚一致。** 正文回滚会连带 marker 回滚——这一条其实是对的。但正文也会被**非回滚**的编辑改掉，所以它的回滚一致性是偶然的，不是设计出来的。

## 11. 发现的冲突 / 需要修订的上位文档

### 11.1 硬门 2 与 `dice_already_rolled` 的语义冲突

- **哪两份**：契约 §7.2（＋ `_shared/failure-and-revisit.md:22,30`、`docs/gameplay/Chalk玩法形态与判定约定.md:51`） vs `packages/shared/src/actions/roll-dice.ts:149-155`。
- **哪一句**：契约逐字「重复触发 MUST **复用**既有结果」；`Chalk:51` 逐字「重复点击**沿用**真实骰点并**修补缺件**」。而 `rollDice` 对重复触发的回答是 `fail('dice_already_rolled')` → HTTP **409**（`errors.ts:35`）。**"复用"与"报错"不是一回事。**
- **为什么矛盾**：玩家在一张已结算的卡上再点一次掷骰，按上位契约应该看到"这是你上次掷出的 62，结果如下"，实际看到的是一个 409 错误。
- **建议怎么改**：本文的调用位 B（§5.2）是**在不改 `rollDice` 既有错误契约的前提下**能做到的最大限度——补完缺件，但仍抛 409。**彻底对齐需要把 `dice_already_rolled` 从"错误"改成"复用成功"**，那会改变一条已冻结的动作层错误语义，影响 `docs/tools/07`、前端 `06`、以及 `roll-dice.ts:67-70` 的既有文案。**本文不擅自改，提请评审裁决**：是接受"补完 + 409"这个折中，还是立项改 `rollDice` 的返回语义。

### 11.2 "抛错 = 什么都没发生"的约定被调用位 B 打破

- **哪两份**：`packages/shared/src/actions/errors.ts:46-48` 的类注释逐字「Convention (00 §8 / doc-21 §3.6): **throwing means nothing was appended**; a caught ActionError MUST NEVER be downgraded into a success result」 vs 本文 §5.2 的调用位 B（先补完效果、再抛 `dice_already_rolled`）。
- **为什么矛盾**：调用位 B 抛错时，事件确实被 append 过了。
- **建议怎么改**：把该注释的适用范围收窄为「**本次动作自身**的落账」，并追加一句「一个动作可以在失败前完成它所**恢复**的既有运行，此时 `ActionError.details` MUST 带上恢复报告」。同时登记一个实现期的缺口：`ActionError.toHttp()`（`errors.ts:77-82`）只回 `{ok, code, error}`，**丢掉 `details`** ——玩家路径因此拿不到"补完了什么"。**`06` 需要知道这条**；修法是给 `toHttp` 加 `details`（一行，但改的是 C 入口的冻结响应形状，需 `docs/tools/00 §7` 同步）。

### 11.3 `roll_dice` 工具的提示词在教模型违反硬门 3

- **哪两份**：`extensions/toolkit/roll-dice.ts:45` 的 `promptGuidelines` 逐字「If an entity already has a result, roll_dice refuses; **to re-open the check, edit the old result out of the file first.**」 vs 契约 §7.3 逐字「MUST NOT 删除 `result` 制造免费重掷」＋ `docs/gameplay/Chalk玩法形态与判定约定.md:28` 逐字「同一检定不靠删 `result` 免费重掷」。

- **建议怎么改**：删掉该条的后半句，改为「A settled check stays settled. If the story needs a new roll, create a **new** entity with its own `roll_dice`; do not edit `result` out of the old one.」**归属**：`07`（Agent 创作接口）或 `08`（迁移）认领具体改动；本文只登记。

### 11.7 `plan` 摘要的形态：01 与 03 的分歧，本文裁决为「声明形态」

- **哪两份**：`01` 的 `canonicalCommandStepText(step: WorldCommandStep)`（声明形态，不求值） vs `03` 的 `canonicalPlanDigest(resolved: ResolvedEffect[])`（代换后形态）。
- **为什么冲突**：两者都满足"确定性、可单测"，但回答的是**不同的问题**。01 回答"这条 log 是哪个版本的命令规则写的"；03 回答"这次实际跑的是哪份计划"。**同一个字段不能同时回答两个问题。**
- **本文裁决：取 01 的声明形态。** 判据是 `plan` 的**唯一用途**——本文把它定义为溯源（§3.5），而溯源要能跟"**当前**文件的摘要"比较才叫溯源。代换后形态在这一点上不可用：同一份文件在不同 `roll.result` 上算出不同 `plan`，没有可比对象。
- **附加理由**：代换后形态把 §3.5 排除 `args` 的那个**自指通道**又请回来了——`{{ trigger.fm.* }}` 读的字段会被命令自己写回，于是同一 key 两次运行的 `plan` 不同。声明形态一次写入即可确定，且**不需要运行期上下文**（`07` 的写入校验顺手就能算，不依赖 `03` 的求值器）。
- **代价**：`plan` 因此**不能**用来回答"这次实际用的是哪份参数"。`[推断]` 目前没有这个需求——若将来有，那应该是**新的**字段（例如 `resolvedPlan`），而不是改变 `plan` 的含义。
- **给两方的动作**：`01` 的 `canonicalCommandStepText` 是本文依赖的那个；`03` 已接受裁决并删除 `canonicalPlanDigest` 与 `plan.ts`，其四条规范化规则与 01 的三条实质一致（两条独立推导收敛，是好信号）。
- **一条 MUST，已写进 `planDigest` 的签名注释**：`plan` 是 provenance only, **never a verdict**。它 MUST NOT 参与 S3 分流。若有人实现成"plan 变了就重跑"，§3.5 排除 `args` 的理由就被推翻了、那个重复发奖通道就回来了。

### 11.8 `detail.by` 已按主代理裁定删除（本文原引用已修正）

本文 §4.1/§4.3 原先引用契约 §5.1 的 `detail.by = 'command'`。主代理 2026-09-14 裁定删除该键，理由（`10` 取证）：

- `by` 已被 `layer_initialized` 占用，且是**闭枚举** `z.enum(['writer','player','engine'])`（`packages/shared/src/schemas/events.ts:99`）。
- dev 模式的 `appendEvent` 对 `detail` 跑 `safeParse`（`store/local-store.ts:668-679`），写 `by: 'command'` 会**炸**。今天不炸只因 `recordLayerInitialized` 不在 `04` 的七个效果里——**一颗埋着没炸的雷**。
- **只留 `detail.command` 更好**：它本身已表达"这次变化来自命令"，`by: 'command'` 是冗余的第二真相源。没有命令上下文的事件不带这个键，语义自动正确。

**本文的修正**：`command_log` 与外发 `detail` 一律**只用 `detail.command`**，不使用 `by`，也不使用本文曾提议的 `commandKey`（§4.3.1 已撤回）。已改 §4.1、§4.3、§11.6。

> 这是本批次第二个"闭枚举惩罚顺手新增语义相近键"的坑（第一个是实体侧 frontmatter 的 passthrough，§11.5 与主代理已登记的 `on` 校验缺口）。**两者同源**：既有 schema 在保护自己的同时，也惩罚看起来无害的邻近键。值得注意的是 `by` 的问题**不是"未知键"而是"已知但取值域封闭"**——`detail` 对未知键是逐字宽容的（`docs/tools/00 §5.2:239`），对已知键的取值域却是严格的。**同一个对象上，两个位置的宽容度不同**，这正是顺手加键最容易踩空的地方。（本文曾据此认为 `commandKey` 作为未知键是"安全"的；虽然技术上成立，但 §4.3.1 已按更强的理由撤回了它——**能加不等于该加**。）

## 12. 判定与仍未知

### 12.1 `[C-1]` 命令执行失败是否落账 —— **已由评审门裁定：F1（只落文件，不落事件）**

> 契约 §11.1 逐字：「**`[C-1]` = 失败不落账（F1）**：命令执行失败**不产生任何世界事件**，只落 `details.commands` + 实体 `command_error`。」本节保留三案的理由与代价，作为判定的记录。

**判定的依据（三条）**：硬门 4 与硬门 1 均由「同轮回执 `details` ＋ 卡片 `command_error` 文件」两条**非事件**通路满足；**F2 因静默破坏 `10` 的 `hasSettledCommand` 而失效**（F2 下失败事件带 `detail.command` ⇒ `settled=true` ⇒ 作家被明确告知"不要再发"，而奖其实没发出来——硬门 2 的**反向**违反）；**F3 正面违反契约 §5.2**（本批次不新增第 16 个事件类型）。

约束：`docs/tools/00 §5.2:241` 逐字「工具返回 `isError` 时不落事件。唯一例外 `layer_init_failed`」；契约 §5.2 逐字「本批次不新增第 16 个事件类型」；硬门 4 要求失败对**模型与玩家都可见**。三者不能同时完全满足。

| 方案 | 做什么 | 代价 | 它保住了什么 / 牺牲了什么 |
|---|---|---|---|
| **F1 只落文件，不落事件** | `command_error` 写进实体 frontmatter + `SettleReport` 进 `details`（§5.5） | 零事件改动；零枚举改动 | **保住**：失败不落的铁律、不新增类型；且因为有了 §5.5，**触发它的那个 Agent 当场看得见**。**牺牲**：失败**不进入其他 actor 的事件注入**（作家下一轮、角色冷启动都看不到）→ 另一个角色 Agent 无法主动叙述"那份奖没发出来" |
| **F2 复用 `entity_edited`** | 写 `command_error` 本来就是一次编辑，就让它落 `entity_edited`，`detail` 带 `command` / `commandError:<code>`（**不带 `by`**，见 §11.8） | 零枚举改动；`detail` 可选键已被 `docs/tools/00 §5.2:239` 允许 | **保住**：所有 actor 的事件注入都看得见。**牺牲**：`packages/shared/src/render/events.ts` 会把它渲染成「edited "X"」——**一句关于失败的、读起来像成功的人话**，正好踩硬门 4"不静默失败"的精神。除非同时改渲染模板，而改模板就等于承认它是个新类型 |
| **F3 新增第 16 个类型 `command_failed`** | `WORLD_EVENT_TYPES` + `EventDetailSchemas` + 渲染模板三处同步 | `schemas/events.ts:4-7` 的注释**逐字写明了这个代价**：「Adding one requires BOTH a detail shape below AND a render template」。另需检查所有消费方（`render/events.ts`、`inject/collect.ts`、WS 帧、前端历史面板） | **保住**：语义诚实、可渲染、可查询、所有 actor 可见。**牺牲**：正面违反契约 §5.2 的"本批次不新增"，需要契约本身改口径 |

**三案的判据（评审门据此判 F1）**——本文原列两条供评审使用，现作为判定依据保留：

1. **F1 与 F3 的差别，本质上是"失败要不要进入触发者之外的因果链"这个产品问题，不是工程问题。** §5.5 的落地让这个问题**变小了**——触发者已经当场看得见；剩下的只是"别的 actor 要不要知道"。若答案是"作家应当能主动补救失败的结算"，F1 不够；若答案是"失败由触发者与玩家处理即可"，F1 足够且最便宜。
2. **F2 有一个隐性的代价要先量化**：它会给每一次失败追加一条**进入所有人注入的** `entity_edited`。这对作家上下文是噪音（`10` 的范围），且"编辑了 X"与"X 的奖没发出来"在注入渲染里是同一条人话。**除非 `10` 愿意为它单独出一条渲染分支，F2 不成立。**（评审门据此补充：F2 还会让 `10` 的 `hasSettledCommand` 在失败运行上返回 `true`，从而在失败场景造成**永久漏发**——这是判 F1 的决定性理由，见契约 §11.1。）

**残留代价（如实登记）**：失败**不进入其他 actor 的事件注入**（作家下一轮、角色冷启动都看不到）→ 另一个角色 Agent 无法主动叙述"那份奖没发出来"。若将来出现"角色应主动叙述失败"的需求，**重开 `[C-1]`**。这是**已知缺口**，不是遗漏。
