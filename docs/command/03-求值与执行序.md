## 0. 一句话结论

> **一份语法、三套 profile、一个求值器；结构性错误在写入时响亮地拒绝，运行时只可能遇到"值确实不在"，而那也 MUST 中止而不是默默为假。**

把 `evalWhen` 与 `parseExpect` 收敛成**同一个解析器 + 同一个求值器 + 三张权限表**（profile）：既不让 `evalWhen` 多认一个字（否则选项序号会平移），也不让 `expect` 多认一个字（否则 `EXPECT_RE` 的必要条件不变量破裂）。世界的后果按**严格顺序**执行、**先预检后落地**、失败**停在失败处**且**半成品可见**——因为动作层没有跨动作事务（契约与 `origin/niko` 均自认），假装"全或全无"只会把半成品藏起来，那才是真正的静默失败。

## 1. 一句话定位

**`03` 定义"什么时候发什么效果"，并保证这些效果要么按声明的顺序真的发生，要么以玩家与模型都能看见的方式失败。**

它回答三个问题：某效果**该不该发**（条件求值）；该发的效果**按什么顺序、以什么上限、在什么时机**发（执行序与上限）；发到一半发不出去时世界与玩家的观感**是什么**（部分失败语义）。

它不回答"某效果具体怎么写文件"（→ `04`），也不回答"重复触发怎么算"（→ `05`）。本文的每个语义决定都给那两份文档留下必须满足的接缝（§10）。

## 2. 条件表达式：统一语法

### 2.1 为什么必须统一

现状是**两个正交的半拉子解析器**，各自缺的正好是对方有的：

| | 位置 | 有 | 缺 |
|---|---|---|---|
| `parseWhen` | `packages/shared/src/rules/interactive.ts:73-87` | **命名操作数**（`<flatKey>`，读本实体 `status.data`）、`==`/`!=` | 无 `>`/`<`/区间/`&&`/`||`；不能表达"点数落在某档" |
| `parseExpect` | `packages/shared/src/rules/dice.ts:106-190`（`ExpectParser`） | **丰富算子与连接词**（`>` `>=` `<` `<=` `=` `!=` `41..60` `&&` `||`；`DiceAtom` 见 `dice.ts:22-29`） | 只能比较**一个匿名数字**——`evaluateExpect(ast, result)` 的 `result` 是唯一操作数（`dice.ts:204-206`） |

而 `dice_outcomes` 要的正好是**两者之并**："点数落在 `41..60` 这一档"（区间——`parseExpect` 会）+ "这一档发哪份奖励"（分派——两者都不会）。契约 §1.4 逐字要求"把这三个半拉子收敛成一个，而不是在旁边造第四个"。

**收敛形状**：不是"扩展其一"，也不是"合并两者"的简单叠加，而是**抽出第三个模块承载唯一的语法与求值器，让两者都委托给它，各自保留一张窄权限表**。

> **对题面"扩展其一 vs 合并两者"的回答：都不选，选"新建一个、两者委托"。** 理由见 §2.5：前两条路都会让某一侧的**可接受输入集合发生变化**，而两侧各有一个已冻结的不变量会被踩破。

### 2.2 统一语法的 BNF

```bnf
(* 顶层：OR of AND，两层、无括号、无嵌套。
   与 ExpectAst 的 anyOf[][] 结构同形（dice.ts:31-34）——收敛是结构上的，不是措辞上的。 *)
condition     ::= ws orExpr ws
orExpr        ::= andExpr ( ws "||" ws andExpr )*
andExpr       ::= atom    ( ws "&&" ws atom )*

atom          ::= predicate | comparison | rangeOperand | scalarOperand
predicate     ::= ( "defined" | "missing" ) "(" ws ref ws ")"
                | "has" "(" ws pathString ws ")"
comparison    ::= operand ws op ws rhs
op            ::= "==" | "!=" | ">=" | "<=" | ">" | "<" | "=" | "in"
operand       ::= ref | intLiteral | stringLiteral
rhs           ::= operand | rangeOperand
rangeOperand  ::= intLiteral ws ".." ws intLiteral
scalarOperand ::= intLiteral | stringLiteral

(* 引用：点分路径。根名由 profile 白名单限定。 *)
ref           ::= ident ( "." ( ident | intLiteral ) )*
ident         ::= [A-Za-z_] [A-Za-z0-9_-]*
intLiteral    ::= "-"? digit{1,15}                (* 15 = dice.ts:42 的 INT_DIGITS_MAX *)
stringLiteral ::= '"' [^"]* '"' | "'" [^']* "'"
pathString    ::= stringLiteral                   (* has() 只吃字符串字面量 *)
ws            ::= " " | "\t"
```

**语法层面的四条"不"**（对齐契约 §2.3 的三处既有决定）：

1. **无括号**。优先级只有两层：`&&` 紧于 `||`。祖先 `parseExpect` 逐字拒绝括号（`dice.ts:193-194`："no parentheses, no variables, no arithmetic"）。
2. **无算术**。`roll.result + 5 > 60` 不成立——**没有 `+`**。刻意，非疏漏（§12 登记为表达力天花板，归 `09`）。
3. **无赋值、无函数定义、无循环**。`has()`/`defined()`/`missing()` 是**封闭的三个谓词**，不是可扩展函数表。
4. **无隐式类型转换的惊喜**。比较语义逐算子写明（§3.3）。

**与 `parseExpect` 的关系**：现有语法是本文文法在 `expect` profile 下的**真子集**——`dice.ts:84-85` 的 `ATOM_SRC`/`AND_SRC` 正则正是 `atom`/`andExpr` 的数字子形态。`41..60` 就是 `rangeOperand`。契约与 `02` 的判断（"区间语法 `41..60` 与 `dice_outcomes` 的 `min`/`max` 是同一件事"）在此落实：**此后世界里只有一个区间写法**。

### 2.3 三套 profile（语法相同，权限不同）

语法一份；**谁能引用什么、能用哪些算子**由 profile 决定。profile 是**求值器的参数**，不是第二套语法。

| profile | 谁在用 | 裸名 | 允许的引用根 | 允许的算子 | 谓词 | 隐式主词 |
|---|---|---|---|---|---|---|
| `expect` | `roll_dice.expect`（`dice.ts:196`） | — | **无（禁止一切 ref）** | `>` `>=` `<` `<=` `=` `==` `!=` | 无 | `result` |
| `when` | 实体 `choice[].when`（`interactive.ts:263`） | 裸名 = `status.<名>` | 仅 `status`，**且必须裸写** | 仅 `==` `!=` | 无 | 无 |
| `command` | `command/<id>.yaml` 的 `do[].when`、以及实体 `on.<hook>[].when`（`02` 拥有形状） | **禁用**（必须带根） | `roll` `status` `params` `trigger` | 全部 | 全部 | `roll_resolved` 钩子 → `roll.result`；其余钩子 → **无** |

**四条 MUST 约束**（每条防一个具体的既有不变量破裂）：

1. **`expect` profile 禁止一切引用。** 若 `expect` 接受 ref，`parseExpect("roll.result > 50").ok` 会为真而 `EXPECT_RE.test("roll.result > 50")` 为假——`EXPECT_RE` 的**必要条件不变量**（`dice.ts:88-92` 逐字"Never use this as the final verdict"；`dice.test.mjs:172-192` 在 69,905 个穷举串上断言）破裂。
   > 注意：那条穷举测试的字母表**不含 `i`/`n`**（`dice.test.mjs:173`），所以它**测不出** `in` 的混入。**不变量比测试宽——按不变量设计，不按测试设计。**
2. **`expect` profile 也不接受 `in`。** `in 41..60`（隐式主词 + `in`）会被解析器接受而被 `EXPECT_RE` 拒绝。裸 `41..60` 已足够表达同一件事，且已在模板里用着。**能用一条写法就不用两条。**
3. **`when` profile 禁止一切新算子。** **这条最要紧**：`evalWhen` 决定 `visibleChoiceOptions`（`interactive.ts:336-338`），而可见序编号被**三处共享**——`choose`（`choose.ts:114`）、`look_at`（`interactive.ts:412`）、前端（`apps/web/src/lib/fm.tsx:36`）。任何"多认一种表达式"的放宽都会让**曾经 fail-closed 的选项变可见**，后续**所有序号平移**，三处同时错位。现有测试逐字断言 `evalWhen('k > 1', {k:1}) === false`（`interactive.test.mjs:76-78`），这条 MUST 保持为真。
4. **隐式主词只在 `roll_resolved` 钩子存在。** `02` 的 `on.roll_resolved[].when: "41..60"` 因此合法（主词 = `roll.result`）；`on.choice_selected[].when: "41..60"` 合法但主词缺失 → 解析期 `missing_subject`。**一条声明语法，两种钩子语义分明。**

### 2.4 求值语义表

左值/右值先各自**求值**成 `Scalar = string | number | boolean | null`，再按算子比较。标量归一化复用 `interactive.ts:54-66` 的 `normalizeScalar`（引号剥离、`true`/`false`/`null`/`~` 折叠、数字字面量折叠）——**这是两侧必须共用的那一份**，现状是它**私有**（`interactive.ts:54` 无 `export`），本文要求提到共享位置（§9.1）。

| 算子 | 语义 | 类型不匹配 | 引用缺失 |
|---|---|---|---|
| `==` | `normalizeScalar(L) === normalizeScalar(R)`；`1 == "1"` 真、`1 == true` **假**（对齐 `interactive.test.mjs:65-74`） | 不报错，恒 `false` | **`unresolved_ref`**（见 §3） |
| `!=` | `!==` 的对应物 | 不报错，恒 `true` | **`unresolved_ref`** |
| `>` `>=` `<` `<=` | 两侧 MUST 是有限数 | **`type_mismatch`** | **`unresolved_ref`** |
| `in` | 左 MUST 是有限数；右 MUST 是 `rangeOperand` | **`type_mismatch`** | **`unresolved_ref`** |
| 区间 `41..60` | `min <= x <= max`；`min > max` 在**解析期**拒绝（`dice.ts:158` 已有此拒绝，逐字"inverted range — the regex lets this through"） | 同 `in` | — |
| 裸标量 `50` | 等价 `result == 50`（**仅** `expect` profile；`dice.ts:150-162` 已有此语义） | — | — |
| `defined(ref)` | 引用**解析成功且非 `null`** → `true`；否则 `false`。**永不报错** | 永不 | **永不**（这是它的全部用途） |
| `missing(ref)` | `!defined(ref)`。**永不报错** | 永不 | **永不** |
| `has("path")` | 预解析的 `statKind` 结果：`file`/`dir` → `true`，`missing` → `false` | — | 路径不存在是 `false` **不是错误**；**非法路径**在解析期拒绝 |
| `&&` `\|\|` | **短路**（沿用 `dice.ts:205` 的 `.every`/`.some`，本身就是短路）。求值顺序 = 书写顺序，左到右 | — | 短路可**掩盖**缺失（见 §3.4） |

`&&`/`||` 短路不是新语义，是既有语义；本文第一次让它**承载**语义（`defined(x) && x == 1` 依赖它）。

### 2.5 为什么不选另外两条路（逐条列调用方影响）

**先给全量调用方（grep 实测）：**

| 符号 | 生产调用方 | 测试调用方 |
|---|---|---|
| `parseExpect` | `actions/roll-dice.ts:146`（**唯一**） | `test/dice.test.mjs:116,122,128,159,186,190-191` |
| `evaluateExpect` | `actions/roll-dice.ts:176`（**唯一**） | `test/dice.test.mjs:162` |
| `EXPECT_RE` | **无生产调用方** | `test/dice.test.mjs:186,190-191` |
| `evalWhen` | `rules/interactive.ts:263`（`buildChoice` 内，**唯一**） | `test/interactive.test.mjs:65-77` |
| `visibleChoiceOptions` | `rules/interactive.ts:350`（`resolveChoice`）、`:412`（`formatInteractiveText`）、`actions/choose.ts:114`、前端 `apps/web/src/lib/fm.tsx:36` | `test/interactive.test.mjs:97,105,206`、`apps/web/test/tools/hover-actions.test.mjs:43`（源码文本断言） |

**候选 A：扩展 `parseExpect`（让它认 ref）。**
- 影响 `roll-dice.ts:146`：`invalid_field_value` 的**拒绝集合收窄**——`expect: "roll.result > 50"` 从"拒绝"变成"接受"。今天作者写错会当场被告知，改后会被静默接受。
- 影响 `EXPECT_RE`：**必要条件不变量破裂**（§2.3 第 1 条）。`dice.test.mjs:172` 的财产性测试在字母表 `{> < = ! & | . 0-1 9 - + 空格 a \t}` 上**测不出**这个破裂——**坏的不是测试，是不变量**。
- 影响 `roll-dice.ts` 的判定：`evaluateExpect(ast, result)` 要改成吃 scope，`roll_resolved` 事件 `detail` 的形状会跟着动摇（`doc-21` 冻结）。
- **结论：拒绝。** 为 `command` 需要的能力去改 `roll_dice` 的公开契约，是把新需求的成本转嫁给一个已冻结的旧面。

**候选 B：合并两者（`evalWhen` 吃 `parseExpect` 的算子）。**
- 影响 `interactive.ts:263` → `visibleChoiceOptions` → **选项序号平移**（§2.3 第 3 条，三处共享编号）。
- 影响 `interactive.test.mjs:76-78`：逐字断言 `k > 1` 是 `false`。这条断言失效，且它是 `doc-tools/06 §10.1` 的验收表行。
- 影响 `doc-tools/06 §3.5` 的 `when` 文法契约（该文档把 `when` 文法写成三条 EBNF），改名/放宽都要回写。
- 内容侧回归面**今天是空的**（`08` 实测：templates + archive 里 `when:` 零命中；本文独立 grep 复核一致），所以"改动风险小"**大体成立**——但**序号平移的风险不来自内容，来自未来作者**：今天能写 `when: k > 1` 而得到"选项不可见 + 无报错"，明天它会突然可见。**这是把 fail-closed 的面悄悄换成 fail-open**，而 fail-closed 正是 `doc-tools/06 §3.5` 逐字论证过的选择（"fail-open 会让玩家点到一个门锁着却写着'进去'的按钮——这是对玩家撒谎"）。
- **结论：拒绝。**

**候选 C（本文采纳）：新建 `packages/shared/src/commands/condition.ts`，承载唯一解析器 + 唯一求值器；两者委托，各带窄 profile。**
- 影响 `roll-dice.ts`：**零签名变化**。`parseExpect` 内部改为调 `parseCondition(raw, EXPECT_PROFILE)` 并把 AST 适配回 `DiceAtom[][]`（§9.1）。35 条 `parseExpect` 用例、20 条 `evaluateExpect` 判定用例、69,905 串穷举不变量测试**全部保持原样通过**。
- 影响 `interactive.ts:93`：**零签名变化**。`evalWhen(when, statusData)` 改为 `parseCondition(when, WHEN_PROFILE)` + `evaluateCondition`，**`Err` 一律映射为 `false`**——把 fail-closed 策略写成一行显式代码 + 注释，而不是隐式行为。
- 影响前端 `fm.tsx:36`：**零变化**（只调 `visibleChoiceOptions`）。
- 影响 `EXPECT_RE`：**零变化**（§2.3 第 1、2 条保证必要条件仍成立）。
- **代价**：`condition.ts` 是新增文件；`normalizeScalar` 需从 `interactive.ts` 提到共享位置（纯搬移，无行为变化）。
- **收益**：`command` 拿到完整能力而**没有动任何既有调用方的行为**；且 `expect`/`when` 的 fail-closed 从"实现细节"升格为"显式策略"（§3.4），未来若要放宽 `when`，改的是一张表而不是一次考古。

### 2.6 第三条候选：CEL（正式评估，结论：本期不采纳）

`agent://SandboxExec` 把 **CEL（Common Expression Language）** 作为"最不易被 LLM 写错的语法面"给出，`Main` 要求把它作为统一的**第三个候选**正式评估。**正面评估如下，不是敷衍。**

**CEL 的真实优势（不否认）：**
- `google/cel-spec` README:16-24 逐字："CEL evaluates in linear time, is mutation free, and not Turing-complete"——**非图灵完备是它的设计目标**，与契约 §2.3 的选择**同向**而非冲突。
- 工业先例全是"声明式规则 + 白名单上下文"：Kubernetes ValidatingAdmissionPolicy / CRD validation、Google Cloud IAM Conditions、Unleash feature flag targeting（SandboxExec 事实清单）。
- `@marcbachmann/cel-js` 8.0.0（zero deps）提供 parse-time 结构上限 `maxAstNodes`/`maxDepth`/`maxListElements`/`maxMapEntries`/`maxCallArguments` 与 `expr.check()` 类型检查（SandboxExec 抄录其 README:49-64,134-142）。
- GitHub Actions 的形态是"YAML 结构 + `if:` 表达式"，与我们"YAML `do` + `when`"同构——**LLM 熟悉度确实高**。

**本期仍不采纳，四条理由（按重量排序）：**

1. **CEL 无法表达 `expect` 的现有语法，而"能收敛两个解析器"正是本文的题面。**
   CEL 没有隐式主词概念：`>50`、`41..60`、裸 `50` 在 CEL 里都不是合法表达式（必须写 `result > 50`）。采纳 CEL 意味着 `parseExpect` 要么**继续保留一个独立解析器**（= 契约 §1.4 明令驳回的"旁边造第四个"），要么**迁移 `expect:` 语料**。语料本身不大（实测 `templates/` 只有 **2 种**写法：`<=60` ×16、`">=11"` ×8，共 24 个文件），但迁移面不止语料：`docs/tools/07-roll-dice.md` 的 §2.2.1 EBNF、§2.2.5 的 35 条 `ok` 用例表、§2.2.6 的 20 条判定用例表、§2.2.2 的 `EXPECT_RE` 不变量、`dice.ts:95-96` 逐字错误文案（被 `dice.test.mjs:121-128` 断言）、`doc-06`/`doc-05` 里"`expect` 必须带引号"的注释。**CEL 把"写一份求值器"换成"改五份已冻结文档 + 动一条不变量"。**
2. **错误文案层无论如何要自己写，所以"用库省事"是假的。**
   契约 §6.1 要求写入时校验、错误**模型可见且可自修**；`Main` 已拍板"错误必须带行列位置"（`yaml` 的 `parseDocument` 给 `linePos`）。CEL 的 `ParseError` 是通用的；要达到 `Did you mean "give"?` 这个量级必须**包一层**。包完之后我们**仍然拥有**错误层——那么唯一省下的是 ~150 行解析器，代价是引入一个对我们语义一无所知的黑盒。
3. **`has()` 需要 I/O，CEL 的 async handler 会破坏本设计最重要的性质。**
   `has("player/lamp-oil.md")` 必须查 `store.statKind`（`world-store.ts:147`）。SandboxExec 抄录 `@marcbachmann/cel-js` README:262-277：一旦注册 async handler，`env.evaluate()` **返回 Promise**，官方警告避免 unbounded async。我们在 §4.3 刻意把 `has()` 做成**求值前预解析**、使 `evaluateCondition` **保持纯同步**——这是所有硬门（上限、确定性重放、可单测）的地基。为 CEL 放弃同步性，是**用架构的骨架换语法糖**。
4. **它放宽的是我们要收紧的那一维。**
   CEL 自带括号、算术、三元、list/map、`all`/`exists`/`filter`/`map` 宏。`maxAstNodes` 限制的是**规模**，不是**种类**。契约 §2.3 的论证是"组合空间来自效果原语 × 条件 × 参数 × 链式触发，**不是**语法的图灵完备性"；把条件语言换成远超需要的表达力，正是那句话在防的事——作者与 LLM 面对的可写错的**构造**数量同时上升。

**依赖负担**：`packages/shared` 的 `dependencies` **只有两项**（`yaml: 2.9.0`、`zod: ^3.24.2`；`Main` 已实测复核）。引入 CEL 会变成三项，且两个候选各有风险：`cel-js` 0.8.2 README 公开寻找新 maintainer、找不到可能 archive；`@marcbachmann/cel-js` 虽 zero-dep 但 8.0.0 是一年内的第 8 个大版本（SandboxExec 版本清单）。**零依赖不是洁癖，是这份包当前的事实姿态**：`rules/dice.ts:1-8` 与 `rules/interactive.ts:1-11` 两份头注释都**逐字**写了 "ZERO dependencies on purpose"。

**诚实登记一条反向触发条件（MUST 回写 `09`）**：契约 §2.3 已认账"存在一类玩法（需要循环、需要累加器、需要跨实体聚合计算）无法用声明式表达"。**当本批次或后续真的撞上"需要算术/聚合"那面墙时，CEL 是本仓最合理的逃生口**——那时重评，迁移成本就是上面第 1 条列的那份清单。**现在不需要，就不要提前付这笔钱。**

### 3.3 运行时只可能遇到的两类：`unresolved_ref` 与 `type_mismatch`

写入时校验**不可能**覆盖全部——因为 `status.data` 长在**触发实体**上，而命令文件是**共享的、静态的**（这正是 `Main` 拍板 B2 的直接后果：1 份命令服务 36 个实体）。"`status.lid` 在这个实体上存在吗"只有**绑定那一刻**才知道。这是运行时唯一必须存在的错误：

|---|---|---|---|---|

### 3.4 缺失 MUST fail-closed —— 但"fail-closed"是策略，不是属性

**这是题面要求正面解决的那个矛盾，本节是全文的核心。**

**矛盾的两半：**

- `evalWhen` 逐字写着"**a malformed expression is always false**"（`interactive.ts:91`），`doc-tools/06 §3.5` 论证了为什么这是对的（fail-open 会让玩家点到一个"门锁着却写'进去'"的按钮——**对玩家撒谎**）。契约要求新模块"缺失 MUST fail-closed（与 `evalWhen` 一致）"。
- 硬门 4 逐字要求"**不静默失败**……`console.warn` 不算"。而在命令里，条件求值为假 = **该效果不发**。一个因为**写错了引用名**而变成 `false` 的条件，会让**该给的奖不发**，且没有任何输出。**默默返回 false 正是一种静默失败。**

**解法分五步。**

#### 第一步：承认 `evalWhen` 的 fail-closed 是**有条件的**，不是普遍正确的

`evalWhen` 能 fail-closed，靠两个前提：

1. **它的消费者把"假"当成合法世界状态**，而不是一次失败——`visibleChoiceOptions`（`interactive.ts:336-338`）用 `o.visible` 过滤选项，"这个选项此刻不可见"是完全正常的世界状态。**"关闭"是可达的、有意义的。**
2. **它没有更早的响亮通道**。"`k === 1` 写错了"没有任何地方会报给谁——`parseWhen` 返回 `null`（`interactive.ts:73-87`），`evalWhen` 返回 `false`，`buildChoice` 把它记进 `errors`（`interactive.ts:263` 附近的 `note`），而 `errors` 的去向是 `look_at` 的文本。**这是"能拿到的最大声量"，不是"最优声量"。**

**两个前提在命令上都不成立：** 命令里"假"意味着**玩家少拿一份奖励**——这不是中性状态，是一次**未被报告的失败**；而命令**有**更早的响亮通道（契约 §6.1 的写入时校验，`Main` 已定"错误带行列位置、模型当场自修"）。

#### 第二步：把失败空间**按"何时可发现"分区**，每区路由到能看见它的最响通道

| 分区 | 何时可发现 | 谁来发现 | 出口 | 为什么不能更早 |
|---|---|---|---|---|
| 语法错、未知根/成员、未声明参数、非法 `has()` 路径、倒区间、缺主词、钩子与引用不匹配、非 ASCII 机器字段 | **解析期** | `parseWorldCommand`（`01`） | **写入时拒绝**（模型当场看到） | — |
| 引用缺失、类型不匹配 | **运行时**（`status` 长在实体上，命令是共享的） | `evaluateCondition` | **中止整个命令** + `command_error`（`05`/`06` 拥有形状） | 静态不可知：同一份命令服务 36 个实体 |
| 效果自身失败（路径被占、物品不在） | **执行期** | 动作层（`ActionError`） | **停在失败处**（§5） | 只有真去改世界才知道 |

**结构：解析期能发现的，永远不让它走到运行时。** 这把契约 §6.1 的"写入即校验"从一条工程纪律升级成**求值器设计的负载条件**：因为解析期吃掉了一整类错误，运行时的 `false` 才**有资格**只剩"真实判定"一种含义。

#### 第三步：给"缺失是正常的"一条**显式**写法

条件求值是**三值**的：`Ok(true) | Ok(false) | Err(reason)`。

```ts
// NEW. 求值结果。三值，不是布尔。
export type ConditionResult =
  | { ok: true; value: boolean }
  | { ok: false; error: ConditionEvalError };

// NEW. 运行时仅有的三个错误码，与 §3.3 的表一一对应。
export type ConditionEvalErrorCode = 'unresolved_ref' | 'type_mismatch' | 'io_failed';

export interface ConditionEvalError {
  code: ConditionEvalErrorCode;
  /** 出错的引用原文，如 "status.lid"；供文案与 05 的 command_error 使用。 */
  ref?: string;
  /** 面向模型的一句英语，与 §3.3 的表逐字一致。 */
  message: string;
}
```

**唯一的"缺失也算正常"的写法，就是 `defined()` / `missing()`**：

```yaml
do:
  # 正确：显式说"没有 lid 也算通过"
  - action: give
    path: "{{ trigger.fm.reward_path }}"
    when: "missing(status.lid) || status.lid == open"

  # 正确：显式说"没有 lid 就不要发"
  - action: give
    path: "{{ trigger.fm.reward_path }}"
    when: "defined(status.lid) && status.lid == open"

  # 错误：lid 不存在 → 中止整个命令，玩家与模型都看到"缺 status.lid"
  - action: give
    path: "{{ trigger.fm.reward_path }}"
    when: "status.lid == open"
```

#### 第四步：不变量 I-1（可机械核验）

> **不变量 I-1**：在 `command` profile 下，`evaluateCondition` 返回 `Ok(false)` **当且仅当**所有被求值的原子都**成功解析出值**且判定为假。**任何 `Ok(false)` 都不可能是被吞掉的错误。**

这条不变量就是"fail-closed 与硬门 4 共存"的答案：

- **对 `evalWhen`（`when` profile）**：**保留 fail-closed**。实现是把委托层显式映射——`evaluateCondition` 返回 `Err` 时 `evalWhen` 返回 `false`。**行为逐字不变**，但它是**一行显式代码 + 一条注释**，而不是隐式副作用（§9.1）。
- **对 `evaluateExpect`（`expect` profile）**：**永远不可能返回 `Err`**（该 profile 禁止一切引用，只有匿名数字与字面量）——所以它的签名与语义**一个字都不用改**（`dice.ts:204-206`）。
- **对世界命令（`command` profile）**：`Err` 一律**中止**，绝不降级为 `false`。

#### 第五步：一条实测事实，说明现有代码的"fail-closed"并不均匀

**`evalWhen('k != 1', {})` 实测返回 `true`**（`packages/shared/test/interactive.test.mjs:70` 逐字断言 `evalWhen('k != 1', {}) === true`）。

原因在实现：`normalizeScalar(undefined)` → `null`（`interactive.ts:55`），`null !== 1` → `true`（`:98`）。**所以 `interactive.ts:91` 那句"a malformed expression is always false"只覆盖了"畸形表达式"，键缺失在 `!=` 下是 fail-OPEN 的。**

**这不影响本文的设计**（`when` profile 逐字保留现状，故该行为也逐字保留），但它是**`doc-tools/06 §3.5` 契约表述与实现的一处真实缺口**：`k != foo` 在键缺失时**开**选项。作者写 `when: lid != closed` 想表达"不是关着就让我选"，实际得到的是"没有 `lid` 字段也让我选"。**登记进 §11，归 `06`/`08`。**

## 4. 求值器形态

### 4.1 选择：手写递归下降，扩展现有 `ExpectParser` 的形状

`dice.ts:106-190` 的 `ExpectParser` 是 ~85 行递归下降扫描器，已处理空白（`ws()`）、整数（`integer()`，含 15 位上限）、`&&`/`||` 两层。本文要求：

- **搬移**：把该扫描器提到 `packages/shared/src/commands/condition.ts`，泛化成吃 `ConditionProfile`；
- **扩展**：`atom()` 增加 `ref` / `predicate` / `rangeOperand` 三个分支；
- **保留**：`expect` profile 下它的**可接受输入集合逐字节不变**（§2.3）。

### 4.2 理由

1. **收敛是本文的题面。** 契约 §1.4 逐字"任何设计文档提出'再加一套并行机制'，评审直接驳回"。引库 = 再引入一套平行语法（§2.6）。
2. **`expect` profile 必须逐字兼容，包括错误文案。** `dice.ts:95-96` 的 `EXPECT_EXAMPLES` 与 `dice.test.mjs:121-128` 逐字断言了错误字符串 `roll_dice.expect ">abc" is not evaluable; expected e.g. …`。**没有任何库会产出这句话**，所以库路线一定要包适配器——包完就等于自己拥有错误层，省的只是那 85 行。
3. **零依赖是本包的事实姿态。** `rules/dice.ts:1-8` 与 `rules/interactive.ts:1-11` 两份头注释逐字写着 `ZERO dependencies on purpose`；`packages/shared` 的 `dependencies` 只有 `yaml` 与 `zod`。**这两项是"数据格式与校验"级别的依赖，不是"执行引擎"级别的。** 语法求值器属于后者，标准更高。
4. **`has()` 让求值器必须是纯同步函数**（§3.3 的 `io_failed` 被限定在预解析阶段）。手写求值器天然纯；库路线的 async handler 会破坏这一点（§2.6 第 3 条）。
5. **性能不是理由，所以不拿它当理由。** 见 §8：求值成本被磁盘 I/O 淹没三个数量级。

### 4.3 三阶段：解析（纯）→ 预解析（唯一 I/O）→ 求值（纯同步）

这是本文在实现层面最重要的决定。

```text
parseCondition(src, profile)  ──►  ConditionAst（纯、无 I/O、可缓存、可静态分析）
                                        │
                          collectHasPaths(ast) ──► string[]（去重后的路径集）
                                        │
                              预解析（唯一有 I/O 的一步，受上限约束：§6）
                                   store.statKind(p) for each p
                                        │
                                        ▼
                          ConditionScope.paths ← ReadonlyMap<string, StatKind>
                                        │
                    evaluateCondition(ast, scope) ──► ConditionResult
                             （纯、同步、零 I/O、确定性）
```

**为什么值得这么绕**（三个收益，每个对应一个硬门）：

1. **`evaluateCondition` 是纯函数** → 可单测、可重放、可在写入时用假 scope 做验证、**不可能在求值中途改世界**（硬门 1）。
2. **I/O 被限制在"这条命令真正会问的问题"上，且每个路径最多查一次。** `collectHasPaths` 对 AST 求并集并去重，所以 12 步里问 5 次 `has("player/lamp-oil.md")` 只查一次磁盘；且查的次数**在解析期就是已知的常量**（§6 的上限因此可静态核验）。**这一条直接回应契约 §8 反模式 2**（`origin/niko` 在每个奖励里 `getEventsSince(0)` 扫全史，扫描次数随历史长度增长）——本设计里 I/O 次数与历史长度**无关**。
3. **求值顺序完全确定** → 同一命令 + 同一 scope 永远产生同一结果与同一事件序，从而可重放（§7 的验收 6）。

### 4.4 签名（全部 `NEW`）

```ts
// packages/shared/src/commands/condition.ts  —— 零依赖、无 I/O、纯函数

/** 三套 profile 的名字。见 §2.3 的权限表。 */
export type ConditionProfileName = 'expect' | 'when' | 'command';

export interface ConditionProfile {
  name: ConditionProfileName;
  /** 允许出现的引用根；'expect' 为空集，'when' 为 ['status']。 */
  roots: readonly string[];
  /** 允许的算子。'when' 只有 == / !=；'expect' 不含 'in'。 */
```

## 5. 执行序与部分失败语义

### 5.1 严格顺序，不并发

`do` 是**严格顺序**的，MUST NOT 并发执行任何两个效果。四条理由，每条都是具体风险：

1. **同一文件被两步写。** 两个效果都改 `world/london-map/x.md` 时，并发 = 后写的赢、先写的**静默丢失**。`writeFileAtomic`（`local-store.ts:195-209`）保证的是"单次写的原子性"，不是"两次写的顺序性"。
2. **事件序不可预测。** `appendEvent` 走 `BEGIN IMMEDIATE` + 自增 seq（`local-store.ts:681-702`）；并发下 seq 与实际因果序可能不一致，而作家注入按 seq 渲染（`event-bridge.ts:430-453`）。**事件序 = 叙事序**，不能掷骰子决定。
3. **`ActionContext` 没有 `AbortSignal`**（`types.ts:8` 逐字"Frozen fields"，契约 §4.3 明确不引入新中断机制）。并发出错时的取消语义**无地基可站**。
4. **确定性重放要求事件序确定。** §7 的验收 6 依赖"同一命令 + 同一 scope ⇒ 同一事件序"。

### 5.2 现实约束：没有跨动作事务（诚实陈述）

- 契约 §4.3 冻结"同步执行，不排队、不后台"。
- `origin/niko` 分支自己的文档认账"文件与事件非跨动作事务"；`SandboxExec` 的事实清单第 6 条独立复核了同一件事（"现有动作先写文件再记 event…外部执行引擎的'事务'与 WorldStore 的文件/event 原子性不是同一件事"）。
- **现状确实如此**：`roll-dice.ts` 的 step 10 先 `writeFileAtomic`（`:212`）再 step 11 `appendEvent`（`:222`），并逐字注释"**a failure here is reported without rolling the file back**"（`:217-219`）。

**所以"全或全无"是幻觉。** 本文不假装能做，而是设计一个**没有事务也能用**的语义。

### 5.3 选择：先预检 → 顺序执行 → **停在失败处**（stop-at-failure）

**不是"全或全无"，也不是"跳到下一个"。是停。**

`do` 序列分三个阶段：

```text
 阶段 A ── 预检（pre-flight，只读）
   A1 解析并校验命令文件（写入时已做过一次，运行前再做一次廉价复核）
   A2 求值 on.<hook>[].when，得到本次要跑的命令集
   A3 对每个将要跑的命令，求值每个 step 的 when，得到待执行效果列表
   A4 collectHasPaths → 一次性预解析（唯一 I/O）
   A5 对每个待执行效果做存在性预检（04 拥有判据）
   A6 核对上限（§6）——步数、效果总数、has() 路径数
   ↳ 任一失败 ⇒ 拒绝执行，**世界零改动**，返回可见错误

 阶段 B ── 执行（顺序、串行、有账）
   for each step in order:
     if not step.when → skip（记为 skipped，不是失败）
     else → 经动作层执行效果 → 记录 〔ok | fail(reason)〕
     on fail ⇒ **break**（停在失败处），进入阶段 C

 阶段 C ── 收尾
   返回 CommandRunResult（§9.5）：effects[] 每项带 settle，整条命令的 settle 由它们归纳
     （任一 failed ⇒ 'failed'；否则 'ran'）——'reused'/'resumed' 由 05 的幂等判定层产出，
     不在本阶段（§9.5 的四 verb 与 05 的 SettleReport 同一套）
   若有失败则写 command_error（05 拥有形状）
```

**为什么预检存在（这是本文给"没有事务"的主要答案）**：绝大多数真实失败（路径被占、物品不在、条件引用缺失）**不需要改世界就能发现**。预检把它们从"执行到第 7 步才炸"提前到"一步都没做就拒绝"。这不是事务，但它**消灭了事务本要解决的大部分场景**。

**为什么"停在失败处"而不是"跳过继续"**：一个 `do` 序列是作者写下的**因果链**（发笔记 → 把选项写回卡上 → 扣掉灯油）。第 2 步失败而强行跑第 3 步 = **扣了灯油但没有笔记**，这是对玩家撒谎。停止让半成品**小**且**可解释**。

### 5.4 部分失败：半成品长什么样

**"半成品状态"的准确定义**（本文的验收对象）：

> **已结算前缀**（settled prefix）= 失败步之前（不含）所有**成功执行**的效果。它们是**真实、持久、可在画布上复访**的世界变化——文件变了、事件落了、`seq` 有序（硬门 1）。失败步与它之后的步**完全没有发生**。

对玩家与模型，半成品 MUST 呈现为**三件同时可见的事**（硬门 4）：

1. **真实的痕迹**：已结算前缀留下的文件与事件，照常出现在画布与历史面板上（**不隐藏、不回滚**）。
2. **一条 `command_error`** 落在触发实体上（`05` 拥有形状，契约 §3.3 已把该 key 分配给"被触发的实体"）：写明**哪条命令、第几步、错在哪、缺什么**。
3. **触发动作的 `details` 里带命令回执**（`Main` 已拍板：命令回执走触发动作的 `details`，绕开 `excludeActor` 的注入过滤）。形状**归 `04` 独占拥有**（契约 §R.4）：`details.commands = WorldCommandReceipt[]`（`04 §6.6`）。本文只要求失败项在该数组中可辨（`settle === 'failed'`）。

**为什么不尝试回滚**：契约 §5.2 冻结"不新增第 16 个事件类型"；更根本的是——回滚会**删除一个已经真实发生、玩家可能已经看见**的变化。用"删除"来伪造"没发生"，与反模式 1（把状态藏进正文）是同类错误：**用一个不透明的机制掩盖真实状态**。

**为什么这不是静默失败**：静默失败的定义是"失败发生了而没人知道"。这里失败**同时**进入三个通道（画布痕迹、`command_error`、触发者 tool_result）。**半成品不是失败模式的缺陷，它是失败的诚实呈现。**

### 5.5 可续、可复访（与 `05` 的接缝）

停在失败处带来的必然后果：**同一张卡可以再次触发**。本文要求：

- 重新触发**从第 1 步重跑**（不引入"断点续跑"状态机——那会要求持久化执行进度，是新状态存储）。
- 已经结算的前缀 MUST 被 `05` 的幂等机制识别并**跳过**（硬门 2：不重复结算）。于是修复后重跑会**推进过**失败点。
- **这条对 `04` 是一条硬要求**：每个效果 MUST 可被单独判定"已经发生过"。`05` 实测已确认 `moveEntity` 天生满足（目标已存在 → `already_exists`，`move.ts:147-149`；源不存在 → `not_found`，`:87-90`），而 `give`（`createEntity`）与 `append_body` **不天然满足**（`Main` 已拍板 `append_body` 是"非幂等效果的代表"）。**`04` 与 `05` MUST 为这两个效果给出幂等判据**——否则"停在失败处 + 重跑"会二次发奖，直接踩硬门 2。

### 5.6 `on_error: stop | continue` 的执行层语义（`02` 拥有字段，本文拥有语义）

`02` 已定 `on_error` 默认 `stop`。本文定其**语义**：

- `stop`：一旦某条匹配的命令失败，**不再执行后续匹配的命令**（本文 §5.3 的 stop-at-failure）。
- `continue`：后续匹配的命令**照常执行**（用于"四档里发多份独立奖励"这类互不依赖的声明）。
- **两种都 MUST 把失败写进 `command_error` 与 `details.commands`**——`continue` 减少的是**中断面**，不是**可见性**。

> **`on_error: continue` 与 §5.3 的"停"是什么关系**：`stop`/`continue` 管**命令之间**（`on` 数组的多个条目）；§5.3 的停在失败处管**一条命令内部**（`do` 的步）。**命令内部永远是 `stop`，不提供 `continue`**——理由是 §5.3 那条：`do` 是因果链，跨过失败步会产出撒谎的半成品。**只有声明里彼此独立的命令之间才允许 `continue`。** 这个不对称是刻意的。

### 5.7 并发触发：串行门（与 `05` 的接缝，层次错位已修）

**风险**：同一张卡被连点两次，两次 HTTP 请求各自进入动作层；预检通过后两串效果交错落地 → 绕过预检的存在性检查（TOCTOU），二次发奖。

**既有先例在错误的层**：`apps/server/src/engine/declared-actions.ts:152-156` 的 `serialDeclared` 是一个**模块级 `Map`**，长在 `apps/server/src/engine/`。命令落在动作层（契约 §4.1），**用不上它**（`Main` 已确认这处层次错位）。

**本文的立场**：串行门是执行序的前提，所以**由本文声明要求**，**实现归 `05`**（幂等是它的范围）：

- MUST 在 `packages/shared`（动作层）内，不是 `apps/server/src/engine/`。
- 键 MUST 是"世界 × 触发实体路径"（不是命令 id——同一实体上的两次触发才是要互斥的）。
- **这一点与 `05` 的真相源选型耦合**：若 `05` 用 `command_log` 做幂等，串行门是**同一条记录上的锁**，两者可以合并。**本节只声明"必须有"，不预设形状。**

## 6. 上限与中断（含理由）

### 6.1 原则：上限 MUST 在**执行前**判定，且超限 = 拒绝

契约 §4.3 逐字："单次触发的**总效果数量有上限**……超限 = 拒绝执行 + 可见错误，**不是截断后假装成功**。"

本文补一条更强的性质,**这是本设计能不用计时器的全部原因**：

> **不变量 I-2**：本模块的每一个上限都是**静态可核验**的常量——步数来自 `do[]` 的长度（解析期已知）、效果总数来自匹配到的命令集（阶段 A 已知）、`has()` 路径数来自 AST（解析期已知）。**没有任何上限依赖于"运行了多久"。**

因为语言没有循环、没有递归、没有算术（§2.2），一次触发的**效果数有一个有限上界**，所以**执行时间天然有界**——不需要计时器来保证它。

### 6.3 链式：深度 = 1，即**没有链式**

**本文的决定：效果内部触发的动作 MUST NOT 再触发世界命令；命令的 `do` MUST NOT 调用另一条命令。**

两条独立的理由：

1. **隐式递归是真实风险，不是假想。** `02` 已确认 `moveEntity`/`enterLayer` 若接上触发点，会与自己最常用的效果互相触发。`04` 的注册表里 `move`（→`moveEntity`，已把上游 `Recipe` 的 `kind: 'take'` 等合并为一个效果名）与 `enter`（→`enterLayer`）正是命令最常用的效果——**接上触发点 = 默认开递归**。**保护形态已由契约 §R.15 第 6 条裁定**：`02` 曾提议的 `ActionContext.commandDepth` **不采用**（它要求修改 `docs/tools/00 §4` 冻结的 `ActionContext`），改为**命令执行器内部的模块级计数**，照 `apps/server/src/engine/declared-actions.ts:152` 的 `inFlight` 形态（但 MUST 落在动作层内，见 §5.7），释放点在 `finally`。
2. **显式链式（`do` 里 `run` 另一条命令）本期不提供。** 契约 §2.3 把"链式触发"列为组合空间的一个来源。但组合空间**已经由 `on.<hook>` 数组的多样式获得**：四档区间可以各配一条 `on.roll_resolved` 条目，全部指向**同一条**共享命令并传不同的标量 `with:`（`Main` 拍板 B2；`params` 只支持标量）。**这正是"消除 `declared-actions.ts:154`/`:179` 阈值硬编码两遍"所需要的全部表达力，而且不需要任何链式。**
   > **已由契约 §R.15 裁定：`action: run` 语法删除**，`04` 的 `WORLD_COMMAND_EFFECTS`（**7 个**）**不含 `run`**。本文 §12.1 曾登记的 `[C-03-1]` 分歧因此**已关闭**（裁决与本文立场一致）。保留这段论证是为了记录**为什么**不提供，而不是留一个待办。

### 6.4 为什么**没有**总执行时间上限（诚实说明）

**不加计时器是一个正面决定，不是遗漏。四条理由：**

1. **不变量 I-2 让计时器无事可做。** 没有循环、没有递归、没有算术，效果数有静态上界，执行时间 = 上界 × 单效果成本（§7），**没有"跑不完"的形态需要计时器去打断**。计时器防的是死循环，而这里写不出死循环。
2. **`ActionContext` 没有 `AbortSignal`**（`types.ts:8` 逐字"Frozen fields"；契约 §4.3 逐字"不引入 `AbortSignal` 之外的中断机制"——而 `AbortSignal` 本身就不在冻结字段里）。**没有可用的中断通道。**
3. **打断本身会制造本设计要避免的状态。** 若在效果 7 处按时间打断，得到的是一个**没有任何人声明的半成品**（不是"作者写的因果链走到第 7 步失败"，而是"时钟到点了"）。§5.6 的 stop-at-failure 之所以诚实，是因为**失败的原因可以被说出**；"超时"说不出作者能修的东西。
4. **单效果的阻塞是既有故障模式，不是新引入的。** 若某个效果卡在 I/O 上，它与今天 `rollDice` 卡在 `writeFileAtomic` 上（`roll-dice.ts:212`）是同一类问题，由 HTTP 请求超时与既有的错误通道处理。**世界命令不制造新的阻塞面。**

> **反向登记（归 `09`）**：若云端多租户场景判定"必须有一个墙钟上限"，那么唯一干净的位置是**每次动作调用之外**（server 层对所有 HTTP 请求已有的超时），而不是动作层内。在动作层内加计时器会需要 `AbortSignal`，即需要修改 `docs/tools/00 §4` 的冻结形状——**代价面远大于收益**。

## 7. 毫秒级的诚实核算

契约 §1.2 逐字说明"**'毫秒级'是这条分工的副产品，不是它的目的**"，所以这一节有空间说实话。

### 7.1 实测数字（本机 Node v26.8.1 / WSL2 / ext4，**不是 SLA**）

逐项按 `local-store.ts` 的**实际调用序列**测量（脚本逐字复刻了每个函数的系统调用序列）：

| 单次操作 | 实现位置 | 实测 |
|---|---|---|
| `store.readFile` | `local-store.ts:179-182` | **0.169 ms** |
| `store.writeFileAtomic`（`mkdir -p` + 写临时文件 + `rename`，**3 个系统调用**） | `local-store.ts:195-209` | **0.796 ms** |
| `store.statKind`（1 次 `stat`） | `world-store.ts:147` | **0.127 ms** |
| `store.appendEvent`（`BEGIN IMMEDIATE` + `INSERT` + `UPDATE` + `COMMIT`，WAL） | `local-store.ts:681-702` | **0.030 ms** |
| `parseDocument(frontmatter)` | `schemas/frontmatter.ts:2` 的 `yaml` | **0.193 ms** |
| `parseDocument(command.yaml)` | 同上 | **0.268 ms** |
| `stringify`（YAML） | 同上 | **0.030 ms** |
| `evaluateCondition` | 本文 §4 | **微秒级，可忽略** |

**`appendEvent` 用的是仓库的真实 pragma 组合**：`db/schema.ts:5,111` 逐字只设了 `journal_mode = WAL` 与 `busy_timeout = 5000`，**没有设 `synchronous`**，所以走 SQLite 默认的 `FULL`。实测（`synchronous=2`）**0.030 ms**；对照 `synchronous=NORMAL`（`=1`）是 0.028 ms。**两者几乎无差**——说明本机 WSL2/ext4 上的 `fsync` 很便宜，**这个结论不能外推到别的文件系统**。

### 7.2 一次触发的量级估算

**每效果**（读 → 解析 → 原子写 → 落事件）：

```text
0.169 (readFile) + 0.193 (parse frontmatter) + 0.796 (writeFileAtomic) + 0.030 (appendEvent)
= 1.188 ms
```

**每次触发**（一次性开销）：`parseDocument(command.yaml)` 0.268 ms + 每条不同的 `has()` 路径 0.127 ms。

| 场景 | 效果数 | 估算 | 磁盘 I/O（系统调用数） | SQLite 写 |
|---|---|---|---|---|
| 最小可判别切片（`00 §9.3` 第 2 条：物化一份笔记） | 1 | **≈ 1.5 ms** | 1 读 + 3 写（mkdir/write/rename） + 1 stat | 1 事务 / 2 语句 |
| 典型（`dice_outcomes` 一档 = 发 1 奖 + 追加正文 + 写回 2 个选项） | 3 | **≈ 4 ms** | 3 读 + 9 写 + ~2 stat | 3 事务 / 6 语句 |
| 上限（`WORLD_COMMAND_EFFECT_BUDGET`） | 24 | **≈ 29 ms** | 24 读 + 72 写 + ≤12 stat | 24 事务 / 48 语句 |

### 7.3 结论：是**毫秒级**，但是**几十毫秒**，不是**一毫秒**

**直说：单次触发典型在 1–5 ms，最坏（撞上限）约 30 ms。所以"毫秒级"成立，但把它读成"一毫秒"是不成立的。**

**哪一项是瓶颈**：`writeFileAtomic` **一项占每效果成本的 67%**（0.796 / 1.188）。它做 3 个系统调用（`mkdir -p`、写临时文件、`rename`），而 `rename` 是关键——`local-store.ts:193-194` 的注释逐字解释了为什么要它（"the same file concurrently"）。**这个成本是"原子写"的价格，不该被优化掉。**

**求值器成本被淹没**：条件求值是微秒级，比一次 `readFile` 便宜**两个数量级**。→ **§4.1 的理由 5 因此成立：任何"换个更快的求值器"的论证在这个数量级上都是没有意义的。** 这也是本文拒绝 CEL 时**不把性能当理由**的原因（§2.6）。

### 7.4 四条必须一起说的限定

1. **页缓存是热的。** 上述数字是 300 次循环的均值（前 30 次预热后），文件与 DB 都在页缓存里。冷启动的第一次触发会明显更慢。
2. **`writeFileAtomic` **不** `fsync`。** `local-store.ts:195-209` 只有 `mkdir` + `writeFile` + `rename`，**没有 fsync 文件或目录**。所以契约 §1.1 的"**毫秒级落盘**"这个措辞是**不准确的**——它实际保证的是"**对后续读者立即可见**"（`rename` 的原子替换），**不是"断电后仍在"**。这是本仓既有的语义，不是本文引入的；但既然 `00 §1.1` 把"落盘"写进了产品答案，**这条措辞差异登记进 §12.3**。
3. **WAL 的 `COMMIT` 在 `synchronous=FULL` 下会 fsync WAL**，本机测得便宜（0.030 ms），**换文件系统可能贵一到两个数量级**。这一项是全部数字里最不可外推的。
4. **未计入的项**：`fs.watch` 触发的前端刷新广播（`event-bridge.ts:538-557` 每 1 秒 kick drain + watcher 立即触发）会在 24 个效果下产生约 24 次 `file_changed`，以及 tail reader 的 `world_event` 广播（`:430-453`）。**这是前端与 WS 的成本，不是动作层的延迟**，故不计入上表；但它意味着 `WORLD_COMMAND_EFFECT_BUDGET = 24` 也是**对前端的保护**（§6.2 的理由与此一致）。

## 8. 与 `08` 的对齐：分档阀值只存在一处

### 8.1 现状：同一套阀值被硬编码两遍（实测行号）

`origin/niko:apps/server/src/engine/declared-actions.ts` 的 `runDeclaredRoll`（`:159` 起）把 `1d100` 的四档阀值写了**两遍**：

```ts
// :154 —— 第一遍：校验"档位必须铺满分值域"
const expected = percentile ? [[1, 12], [13, 60], [61, 95], [96, 100]] : [[2, 4], [5, 10], [11, 17], [18, 20]];
if (bands.some((b, i) => b.min !== expected[i][0] || b.max !== expected[i][1])) return bad('Dice bands must partition the declared outcome range');

// :179 —— 第二遍：同一套边界用嵌套三元重写，产出 grade 字符串
const grade = percentile ? (score <= 12 ? 'great-success' : score <= 60 ? 'success' : score <= 95 ? 'setback' : 'failure') : band.min >= 18 ? 'great-success' : band.min >= 11 ? 'success' : band.min >= 5 ? 'setback' : 'failure';
```

另有 **`:176`** 第三处：`{ crit: score <= 12, fumble: score >= 96 }` —— **`12` 与 `96` 又被写了一遍**（作为 crit/fumble 的边界）。所以同一套四档边界在**三处**出现，`:154` 与 `:179` 已经可以漂移，`:176` 更隐蔽。

契约 §8 反模式 3 逐字点名这条："把分档规则硬编码两遍……两处必然漂移。"

### 8.2 本文如何机制性地排除它（不是"靠纪律")

**做法：让"档"成为声明的对象，而不是代码里的常量。**

```yaml
# command/investigation-dice.yaml —— 档位只此一份，阀值只出现一次
name: Investigation dice outcome
desc: Materialise the outcome band for a 1d100 investigation check.
params:
  grade: { type: enum, values: [great-success, success, setback, failure], required: true }
  reward_path: { type: string, required: true }
  outcome_text: { type: string, required: true }
do:
  - action: give
    path: "{{ params.reward_path }}"
    args: { title: "{{ params.outcome_text }}", portable: true }
  - action: edit
    path: "{{ trigger.path }}"
    args: { append_body: "{{ params.outcome_text }}" }
  - action: edit
    path: "{{ trigger.path }}"
    args:
      frontmatter:
        dice_grade: "{{ params.grade }}"
```

```yaml
# 实体 world/london-map/04-investigation-dice.md 的 frontmatter
# 阀值逐档出现一次，且在**声明**里（不在代码里）
on:
  roll_resolved:
    - when: "roll.result in 1..12"
      run: investigation-dice
      with: { grade: great-success, reward_path: "{{ trigger.fm.rewards.great.path }}", outcome_text: "…" }
    - when: "roll.result in 13..60"
      run: investigation-dice
      with: { grade: success, reward_path: "{{ trigger.fm.rewards.success.path }}", outcome_text: "…" }
    - when: "roll.result in 61..95"
      run: investigation-dice
      with: { grade: setback, reward_path: "{{ trigger.fm.rewards.setback.path }}", outcome_text: "…" }
    - when: "roll.result in 96..100"
      run: investigation-dice
      with: { grade: failure, reward_path: "{{ trigger.fm.rewards.failure.path }}", outcome_text: "…" }
```

**为什么这样就漂移不了**（三条机制，不是一条纪律）：

1. **阀值只有一处文本。** `13..60` 在声明里出现一次。`grade` 是**档的标签**，由声明**传给**命令（`with:`），不是命令从 `score` 反推出来的。`:179` 那种"从数字反推标签"的代码**没有对应的语法**——本语言没有算术（§2.2），`score <= 12` 反推 `great-success` 需要知道"12 是 success 的下界"，而那正是第二份阀值。**语法上的不存在 = 机制上的不可能。**
2. **`give` 的路径、正文、选项全部来自 `params`**，即全部由**声明**给定，命令里没有第二份副本。
3. **`crit`/`fumble`（`:176`）不进命令。** 它们已经在 `RollDiceDetails` 里（`roll-dice.ts:43,45`），由 `rollOnce`（`dice.ts:255-256`）算好。命令若需要，读 `roll.crit` / `roll.fumble` 即可——**`:176` 那处 `12`/`96` 的硬编码在新设计里没有存在的理由**。
   > **注**：`origin/niko` 用 `12`/`96` 覆盖 `crit`/`fumble` 是因为它把 `1d100` 判成"低于 12 = 大成功"，与 `rollOnce` 的"每颗骰子都是最大面"（`dice.ts:255`）语义不同。**这是 `08` 迁移时必须裁决的语义差异**（`dice.crit` 是骰型事实，`1d100 <= 12` 是分档事实），登记于 §12。

### 8.3 验收断言（非空性）

**`08` 的验收 MUST 包含**：对合并后的 `command/*.yaml` + 实体 `on` 做一次文本扫描，断言**每个阀值边界数字（12/13/60/61/95/96）在"声明 + 命令"的合计文本里对每个世界只出现一次**。这条断言在 `origin/niko` 的形态下**必然失败**（`:154`、`:176`、`:179` 三处），因此它是非空的。

- **续跑语义归 `05`**：本文 §5.5 只要求"从第 1 步重跑 + 已结算前缀被跳过"。`05` 已定 `steps[].step` = **展平序**（续跑游标）、`steps[].at` = **声明位置**（`do[0]#2` 形态的溯源），续跑靠 `on.<hook>` 的**声明下标**定位，并有 `command_resume_drifted` 兜底。**本文确认 `02` 的"数组顺序 = 声明顺序 = 执行顺序"是硬要求**（`05` 的续跑定位依赖它，漂移会补错步）。

### 9.4 与 `04` 的接缝（本文对效果的硬要求）

1. **每个效果 MUST 可被单独判定"已经发生过"**（§5.5）——否则"停在失败处 + 重跑"会二次发奖。`05` 已确认 `move`（`moveEntity`，`04` 已把上游 `kind: 'take'` 等合并为此效果名）天然满足：目标已存在即 `already_exists`（`move.ts:147-149`）、源不存在即 `not_found`（`:87-90`）；**`give`（`createEntity`）与 `consume` 的 `append_body` 形态不天然满足，MUST 由 `04`/`05` 给判据。**
2. **每个效果 MUST 能被预检**（§5.3 阶段 A5）——即"不改世界就能判断这个效果会不会失败"。`04` 拥有判据；本文只要求它**存在**，且其成本计入 §7 的 stat 一栏。
3. **效果 MUST NOT 触发世界命令**（§6.3，深度 = 1）。
4. **`04` 的效果表 MUST 声明每个效果接受哪类数组形态**（`Main` 裁定：`list-args` 逐项迭代 / `fold-args` 折叠为 map / 或只接受标量）。本文只要求：**声明必须存在且是封闭枚举**——`01` 的写入时校验依赖它判断实参形态是否匹配（§14.3 的 `arg_not_array`/`arg_not_scalar` 就是"声明与实参不匹配"）。**求值器不猜**（§14.2 契约 1）。
5. **`list-args` 的逐项展开 MUST 各自成为一个独立回执单元**（`05` 已定：`list-args` 每项各占一个 `step`，`fold-args` 恒占 1 个）。这直接影响 §5.5 的可续性：`give` 传 3 项、第 2 项失败时，第 1 项留在世界里，续跑粒度是"第 2 项"而不是"整个 `give`"。
6. **`fold-args` 的键冲突 MUST NOT 静默覆盖**（`05` 的论证，本文附议）：折叠产出的 map 若与实体已有 `choice_actions` 键相交，那条键可能是**上一次运行**写下的——覆盖它就是**改写已结算结果**（硬门 3），且会让 `command_log` 说"跑过了"而世界里的按钮已不是那次跑出来的。**拒绝 + 可见错误**（`04` 定形状）。

### 9.5 `CommandEffectOutcome` / `CommandRunResult` —— 求值期内部投影（**本文是唯一定义处**）

`Main` 已把 `CommandEffectOutcome` 的**唯一定义处**指派给 `03`（`04`/`05`/`06`/`10` 一律 `import`，**MUST NOT 各写一份**，契约 §R.21 N-7）。它落在 `packages/shared/src/commands/execute.ts`（`NEW`，本文的文件）。

> ⚠️ **与 `WorldCommandReceipt` 的边界（契约 §R.4）**：`packages/shared/src/commands/receipt.ts` 与 `WorldCommandReceipt` **归 `04` 独占拥有**（`details.commands` = `WorldCommandReceipt[]`）。本文**不声明该类型、不注册该文件**。本文的类型是**求值器内部的投影**（`key`/`entry`/`hook` 是求值期自己算的），**不是 `details.commands` 的元素类型**；`04` 的回执由它自己从本文的执行结果投影出来。

```ts
// packages/shared/src/commands/execute.ts —— NEW。纯类型 + 执行器，无额外依赖。

/** 03 拥有的**求值 / 运行期**码集（§3.2 解析期 + §3.3 运行时 + §14.5 数组/绑定）。
 *  **不是** `01` 的写入期码集：`01` 另有 `WorldCommandErrorCode`（46 码，写入时拒绝）。
 *  两者 MUST NOT 互相 `import` 或合并——「写入时能验」与「执行时才知」是 §3.4 诚实表的两条边。 */
export type WorldCommandRuntimeErrorCode =
  // §3.2 解析期（写入时拒绝）
  | 'condition_syntax' | 'unknown_ref_root' | 'unknown_ref_member' | 'unknown_param'
  | 'bare_ref_forbidden' | 'missing_subject' | 'invalid_has_path' | 'inverted_range'
  | 'hook_ref_mismatch' | 'non_ascii_machine_field' | 'non_scalar_ref'
  | 'nested_interpolation' | 'nested_arg_array'
  // §3.3 运行时（中止整个命令）
  | 'unresolved_ref' | 'type_mismatch' | 'io_failed'
  // §6 上限（执行前拒绝，世界零改动）
  | 'step_limit_exceeded' | 'effect_budget_exceeded' | 'condition_nodes_exceeded'
  | 'has_paths_exceeded' | 'arg_array_too_long'
  // §14 绑定与实参
  | 'on_entry_unavailable' | 'entry_index_out_of_range'
  | 'arg_not_array' | 'arg_not_scalar';

/**
 * 一个效果执行完的结果 —— 世界命令回执的最小单元。
 *
 * 「一个效果」= §14.4 阶段 A5 **展开后**的一项：`list-args` 的每一项各占一个，
 * `fold-args` 与标量效果各占一个。**不是 `do[]` 的一条**（05 的续跑粒度依赖这条区分）。
 */
export interface CommandEffectOutcome {
  /** 04 的封闭效果名（`WORLD_COMMAND_EFFECTS`，**7 个**）。可独立成步的 6 个：give / move / edit / set_status / consume / enter；`link` 是 `give` 的附属，不单独成步（`04 §2.3`）。 */
  action: WorldCommandEffectName;
  /**
   * **展平序**：本次命令运行内所有展开后效果的 0-based 连续下标。
   * 05 的续跑游标 = `steps.length`，因此这里 MUST 连续、MUST NOT 跳号。
   */
  step: number;
  /**
   * **声明位置**，形如 `"do[0]#2"`（第 0 条 `do`、`list-args` 展开的第 2 项）。
   * 仅供溯源与错误文案；**MUST NOT 当游标**（05 的 N2b 断言专门守这条）。
   */
  at: string;
  /** 四个 verb，与 05 的 `SettleReport` 同一套，**无第五种**。 */
  settle: 'ran' | 'reused' | 'resumed' | 'failed';
  /** 这个效果写到哪个世界路径；纯画布效果（`link`，`04` 已把它降为 `give` 的附属）为 null。 */
  path: string | null;
  /**
   * 落账事件的 seq。按 `04` 的最终注册表，**每个可独立成步的效果恰落 1 条事件**，
   * 所以成功执行（`settle === 'ran'`）时 seq **必非 null**。
   * null 的两种情形：`settle === 'failed'`（什么也没落）与 `settle === 'reused'`
   * （复用上次结算，本次不产生新事件）。
   */
  seq: number | null;
  /** 仅 `settle === 'failed'` 时存在。`code` 可能来自动作层或本文。 */
  error?: { code: ActionErrorCode | WorldCommandRuntimeErrorCode; message: string };
}

/**
 * 一条命令跑完的**求值期结果**（`runWorldCommand` 的返回值）。
 *
 * **`WorldCommandReceipt` 归 `04` 拥有（契约 §R.4）；本类型是求值器内部的投影，
 * 不是 `details.commands` 的元素类型。** 两者形状不同：`04` 的回执是引擎侧最小单元
 * （`{ id, name, settle, effects: [{ action, ok, event?, error? }] }`），本文的是求值期视图
 * （`hook`/`entry`/`key` 只有求值器算得出）——**不是超集，故不 `extends`**，两者的字段映射由 `04` 负责。
 */
export interface CommandRunResult {
  /** 命令 id（= `command/<id>.yaml` 的 `<id>`），也是事件 `detail.command` 的值。 */
  command: string;
  /** 触发点名，取值 = `02` 的 `CommandTriggerHook`（`roll_resolved` / `choice_selected` / `use_item_on`）。 */
  hook: CommandTriggerHook;
  /** 命中的 `on.<hook>` **声明下标**（0-based）。 */
  entry: number;
  /** 05 的幂等 key（16 hex）。 */
  key: string;
  /** 整条命令的结论：`effects` 里任一 `failed` ⇒ `'failed'`。 */
  settle: 'ran' | 'reused' | 'resumed' | 'failed';
  effects: CommandEffectOutcome[];
}
```

**三条不变量（可机械核验）：**

1. **`step` 连续**：`effects.map(e => e.step)` MUST 等于 `[0, 1, …, n-1]`。`05` 的续跑游标是 `steps.length`，跳号会让续跑从错误位置开始（`05` 的 N2b 是这条的守卫）。
2. **`at` 与 `step` 是两个概念，MUST NOT 互相替代。** `list-args` 展开 3 项时，三项的 `at` 都是 `do[0]#1..#3` 而 `step` 是 `0,1,2`；若把 `step` 记成声明位置，三项会都是 `0`。
3. **`seq === null` 不蕴含失败。** `reused` 的效果复用上次结算、本次**不产生新事件**，seq 同样为 null。判"成不成功"只看 `settle`，**不看 `seq`**——这条防的是"用事件存在与否倒推成败"，而 `06`/`10` 的渲染最容易犯这个错（`10` 已确认它的注入侧看不到命令事件，只能靠回执）。

> **命名澄清（防碰撞）**：`detail.command`（**事件**的 detail 键，`Main` 裁定 1 已定，取代 `detail.by`）与 `details.commands`（**`ActionResult.details`** 里的回执数组）是**两个命名空间里的两样东西**，拼写相近但无技术冲突（`WorldEvent.detail` vs `ActionResult.details`）。本文在此显式登记，避免实现期把它们当成同一个。

## 14. `trigger.entry` 与数组值实参（`Main` 裁定 A + 方向三）

1. **路径段只有两种形态**：`ident` 与非负整数字面量下标。`{{ trigger.entry.rewards[{{ i }}] }}`（嵌套插值）MUST 在**解析期**拒绝（`nested_interpolation`）。理由即裁定 A：动态下标让效果数的**静态上界失效**，砸 §6 的不变量 I-2 与 `09` 的资源上限论证。
2. **`trigger.entry` 只读**。本语言无写引用，此条把"不能写"从"没有语法"升级为"显式禁止"，防止将来加效果时误开。
3. **条件里不出现数组**：`trigger.entry.<path>` 若解析为**对象**（非数组、非标量），在条件里使用 → 解析期 `non_scalar_ref`；若解析为**数组**用在条件里 → `non_scalar_ref`（数组是合法的实参值类型，但**只对效果实参开放**，不对条件开放——§2.4 的比较语义只吃标量，不放宽）。

### 14.2 数组值在求值器里的表示

求值结果类型从 `Scalar` **扩展**为 `InterpolatedValue = Scalar | Scalar[]`——**但只在"效果实参求值"这一个入口**。

```ts
// NEW（修订 §4.4 的 Scalar 定义）
export type Scalar = string | number | boolean | null;

/**
 * 插值（{{ }}）的求值结果。数组只在 trigger.entry.* / trigger.fm.* 的**静态路径**上可能产出；
 * 字面量内联数组 MUST NOT 出现（字面量数组是内容，内容住实体 —— Main 方向三口径）。
 */
export type InterpolatedValue = Scalar | Scalar[];

/**
 * NEW. 求值"效果实参"里的一个 {{ }}。profile 固定 COMMAND_PROFILE；无 I/O（scope 已在 A4 预解析）。
 * 注意：**求值器不区分 list-args / fold-args** —— 消费方式由 04 的效果表决定（Main 裁定）。
 */
export function evaluateInterpolation(
  expr: string,
  scope: ConditionScope
): { ok: true; value: InterpolatedValue } | { ok: false; error: ConditionEvalError };

/** NEW. 数组的静态上界。由 schema 上限决定，不是运行期测量。 */
export const WORLD_COMMAND_ARG_ARRAY_MAX = 3;
```

#### 求值器的三条契约（其中第 3 条是 `Main` 专门派给本文的）

1. **求值器只负责产出值，不负责消费。** `list-args`（逐项迭代）与 `fold-args`（折叠为 map）的区别**不在求值器**——同一个数组值交给不同的效果，`04` 的效果表决定它是被迭代还是被折叠。**求值器 MUST NOT 按效果名改变行为**（否则同一个 `{{ trigger.entry.rewards }}` 在 `give` 与 `edit` 上会得到不同的求值结果，而求值器本该是纯粹的值来源）。
2. **求值器 MUST NOT 展开。** 展开（迭代到 N 个效果、或折叠成 1 个 map）发生在 **`04` 的效果实现内部**，依据是阶段 A5 已求出的数组值。**求值器返回数组本身**。
3. **求值器 MUST 保留数组顺序，MUST NOT 排序、去重、或重排键序。** 理由（`Main` 裁定，本文确认）：`fold-args` 折叠出的对象**键序由数组顺序决定**，而 `05` 的 `plan` 摘要（`01` 的 `canonicalCommandStepText`）依赖**稳定键序**——数组顺序若不稳定，同一份声明会算出不同的 `plan`，溯源就失去基准。
   > **实现口径**：`InterpolatedValue` 的数组 MUST 是**有序**的（JS 数组天然有序），且求值器 MUST NOT 把它转成 `Set`/对象再转回来（那会丢序且改变键序）。**这条写进 T19 的验收。**

### 14.3 类型匹配：四类错误，方向相反

| 情形 | 错误码 | 文案 | 为什么不能宽容 |
|---|---|---|---|
| 效果**要求数组**（list 或 fold），实参解析出**标量** | `arg_not_array` | `command "investigation-clue" step 1: "give" expects an array for `rewards`, but "{{ trigger.entry.rewards }}" resolved to a string.` | 静默包成单元素数组 = 让"作者写错了路径"看起来像"只有一份奖励"——两种截然不同的原因产生同一结果 |
| 效果**要求标量**，实参解析出**数组** | `arg_not_scalar` | `command "…" step 2: "edit" expects a scalar for `path`, but "{{ trigger.entry.rewards }}" resolved to an array of 1. Address one item with [0], or pass the whole array to an effect that accepts arrays.` | 静默取首项 = 契约 §8 反模式 1 的同类错误（用隐式规则掩盖真实结构） |
| 数组长度 **> `WORLD_COMMAND_ARG_ARRAY_MAX`（3）** | `arg_array_too_long` | `command "…": "rewards" has 7 items; the maximum is 3.` | 上界若不在解析期确立，不变量 I-2（§6.1）破裂 |
| **数组嵌套数组** | `nested_arg_array` | `line {L}, column {C}: array elements must be scalars; nesting arrays is not allowed.` | 否则上界是 `3^n` |
| 数组**为空** | **不报错，展开为 0 个效果 / 折叠为空 map** | —— | 空数组是**合法且有意义的世界状态**（"这一档没有奖励"） |

> **空数组为什么不报错**：它满足不变量 I-1 的形式——"0 个效果"是**成功求值出的结果**，不是失败。这与 §3.4 的分野一致：**求值失败 MUST 中止；求值成功而结果为空 MUST 正常继续。** 作者若要"没有奖励就报错"，写一条守卫（如 `when: "defined(trigger.entry.rewards[0])"`）即可。

### 14.4 有界展开的执行序与上限（`Main` 派给本文）

```text
阶段 A（预检，只读）           ← 展开在这里发生，也是上界确立的地方
  A1 解析校验命令文件
  A2 求值 on.<hook>[].when，得到本次要跑的命令集
  A3 求值每个 step 的 when
  A4 collectHasPaths → 一次性预解析（唯一 I/O）
  A5 求值每个 step 的效果实参 → 数组实参**在预检期就确定其长度**
     ⇒ 待执行效果的**确切条数**在此确定：n = Σ_steps (list-args 数组长度 或 1)
        （fold-args 恒为 1 次写入，不增加 n —— Main 的两条契约在此体现）
  A6 核对上限：n ≤ WORLD_COMMAND_EFFECT_BUDGET（24）
     ※ 并核对每个数组长度 ≤ WORLD_COMMAND_ARG_ARRAY_MAX（3）
  A7 对展开后的**每一个**效果做存在性预检（04 的判据）
  ↳ 任一失败 ⇒ 拒绝，世界零改动

阶段 B（执行）  for each 展开后的效果, 顺序: 执行或失败即 break
```

**四条 MUST（缺一条则 I-2 破裂）：**

1. **数组长度 MUST 在阶段 A 确定，MUST NOT 在执行中途发现新元素。** A5/A6 的位置不是实现细节——它保证"效果总数"在**世界零改动时**就已确定，即超限与数组过长都是**无半成品的拒绝**（`05` 已据此把它的中断恢复面收窄了一整类）。
2. **数组长度上界 MUST 来自 schema，MUST NOT 来自运行期测量。** `Main` 口径：迭代次数 = 实体数组长度 ≤ schema 上限（`rewards` ≤ 3）。**这是声明式路线相对沙箱 JS 最有利的论据**（归 `09` 强调）：**不需要任何沙箱能力，就能在执行前给出效果数的确切上界。**
3. **展开后的每个效果 MUST 独立预检、独立成败**（`Main` 派给 `04`）。**但执行仍是 stop-at-failure**（§5.3）：`04` 报第 3 项失败时，第 1、2 项已结算且可见。**"逐项独立报错"与"停在失败处"不矛盾**——前者说的是错误**信息**逐项给出，后者说的是**中断位置**。
4. **`fold-args` 恒为 1 次写入，整体成功或整体失败**（`Main` 的两条契约）。因此它在 `n` 的计数里算 1，但它的**键冲突检测**是 `04` 的契约（`Main` 已倾向"拒绝 + 可见错误"），本文只要求：折叠产出的 map 与实体已有 `choice_actions` 键相交时，MUST NOT 静默覆盖——那会是一次**未经声明的世界改写**。

**对 §7 成本估算的影响**：最坏情形算术上不变——仍由 `WORLD_COMMAND_EFFECT_BUDGET = 24` 封顶 ≈ 29 ms（§7.2），因为展开后的效果**共享同一个 24 的预算**，不另开闸门。**方向三没有为 §7 引入新的成本项。**
