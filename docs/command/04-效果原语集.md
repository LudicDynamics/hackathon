## 1. 一句话定位

> **世界命令没有自己的世界改写能力。** 它拥有的是一张**封闭的映射表**：作者在 `do[].action` 里写 7 个**动词**之一，引擎把它翻译成 `ACTION_METHODS`（`packages/shared/src/actions/service.ts:80-107`，26 项）里**已经存在**的动作方法调用——从而免费继承路径解析、越界拒绝、nook 权限门、事件落账、`detail` 自足性与错误码（契约 §4.2）。

本文的职责是**把 26 项减到 4 项**：

```text
26 个动作方法  ──►  4 个可作效果  +  1 个仅作附属
                       createEntity   linkCards
                       moveEntity
                       editEntity
                       enterLayer
```

**其余 21 项明确拒绝**（§7）。**"宁可少给"是本模块的安全策略**：每一个开放的效果，都是命令文件能造成的一类世界改写，也是一个 Agent 能当场写下的破坏性能力。

## 2. 完整映射表

### 2.1 效果注册表（冻结，`01` 直接引用）

`do[].action` 的取值集合**只有效果这一类**（R.15 后 `run` 不再是合法值，链式触发归 `on` 数组）：

| 类别 | 成员 | 性质 |
|---|---|---|
| **效果**（`WORLD_COMMAND_EFFECTS`，7 个） | `give` `move` `edit` `set_status` `consume` `enter` `link` | **每个 MUST 落到一个 `ACTION_METHODS` 方法上** |

> `WORLD_COMMAND_EFFECTS` **不含 `run`**——R.15 已把 `run` 从 `do[].action` 移除（链式触发改由 `on` 数组表达），因此它既不是效果也不是任何 `do[].action` 值。§10 的 T-1 断言「每个效果名都在 `ACTION_METHODS` 里」因此可机械核验；契约 §4.2 的"能力集 ⊆ 动作层"约束的正是这张表。

| # | 效果名（作者写这个） | → 动作方法 | 一句话 |
|---|---|---|---|
| 1 | `give` | `createEntity` | 发一份**新的**实体（奖励笔记、信件、卡） |
| 2 | `move` | `moveEntity` | 把**已有**实体挪到别处（取物 / 放下 / 交付 / 归档） |
| 3 | `edit` | `editEntity` | 改字段 / 换正文 / **追加**正文，含写回 `choice`+`choice_actions` |
| 4 | `set_status` | `editEntity`（窄口） | 只改 `status.data` 的若干标量键 |
| 5 | `consume` | `editEntity`（复合，见 §3） | 消耗一份物件：状态迁移，**默认不删文件** |
| 6 | `enter` | `enterLayer` | 送玩家进入某层（**受 §4.6 的 gate 前置约束**） |
| 7 | `link` | `linkCards`（**仅作附属**） | 把新发的卡连到触发它的卡 |

**为什么是动词不是方法名**：作者写的是"发一份奖""灯油少一份"，不是"调 `createEntity`"。方法名是实现细节；一旦内容层开始写方法名，重命名动作方法就变成破坏性变更。`origin/niko` 的 `Recipe` 用 `kind: take/read/stage` 也是动词（`apps/server/src/engine/declared-actions.ts:17-23`），同一惯例。

**为什么 `move` 是一个而不是四个**：`docs/tools/00-共同上下文.md:372` 的反模式清单逐字写「❌ 造 `inspect` / 通用 `interact` …；**拆 `take/drop/place/give`**」。取物、放下、交付、归档在世界里是**同一个物理动作**（文件换位置），差别只在语义与参数。`Recipe` 的 `kind: 'take'` 之所以看起来独立，是因为它只允许一个固定目的地 `player/`（`declared-actions.ts:218`）。世界命令允许作者写 `to:`，一个效果就够。

### 2.3 逐效果的完整契约

> **共同的输入来源**：所有路径/文本参数都可以写 `{{ trigger.path }}` / `{{ trigger.fm.* }}` / `{{ roll.result }}` 这类内置上下文变量（**变量集**归 `02`，**语法**归 `01`）。下表"参数"列写的是**求值后**的形状。

#### E1 `give` → `createEntity`

| 项 | 值 |
|---|---|
| 动作方法 | `createEntity`（`packages/shared/src/actions/create.ts:87-151`，注册于 `:153-155`） |
| 参数 | `path: string`（必需，世界根相对，必须 `world/` \| `player/` \| `characters/` 前缀且 `.md` 结尾）；`body?: string`；`frontmatter?: Record<string, unknown>`；`content?: string` |
| 上游类型 | `CreateEntityInput`（`create.ts:25-38`）——**直接复用，不重新定义** |
| 落的事件 | `entity_created`；`detail = { path, name, kind }`（`create.ts:138-145`）。`kind` 是五值封闭枚举 `chalk\|component\|note\|letter\|other`，由 `eventKindOf`（`delete.ts:57-72`）从 frontmatter 推出 |
| 参数映射 | 声明式 `give { path, title, body, frontmatter }` → `createEntity { path, body, frontmatter: { title, ...frontmatter } }`。**`title` 是 `frontmatter.title` 的语法糖**：`nameOf`（`create.ts:48-53`）优先读它 |
| 存量需求 | `dice_outcomes[].rewards[] = { path, title, body }`（`templates/whitechapel-jp/world/london-map/04-investigation-dice.md:35-38`）—— **字段一一对应** |
| **实参形态** | **scalar-args**：`path`（单份）／ **`list-args`**：`rewards`（整数组，引擎内迭代）。两者**互斥**，MUST 恰好一个——完整语义见 §2.6 |
| **`list-args` 的回报** | 每个元素**各产出一个 `EffectOutcome`**，且**每项是一个独立 step**；`05` 的 step 回执因此也是**每项各占一步**（§2.6）。逐项失败受 **stop-at-failure** 管辖（第 k 项失败 ⇒ 第 k+1 项不执行；已成功的前缀留在世界里） |
| 前置检查 | §4.1 |

**为什么禁用 `content` 逃生舱**：`input.content` 是"整文件替换，调用者负责正确性"（`create.ts:32-37` 逐字），它是 god mode 的"整个替换这个文件"手势。世界命令是**声明式编排**（契约 §2.3）；把"整个文件正文由作者提供"作为效果会（a）绕过 `stringifyFrontmatter` 的组装（`create.ts:126-129`）、（b）让命令文件里出现一整篇叙事正文，与契约"取消 Markdown 正文"的理由 2（正文不受 schema 约束会成为第二真相源）是同一类错误。**拒绝**：`give.content` 不在 `EffectInput` 里。

这是本模块**价值密度最高**的效果：`origin/niko` 的 `declared-actions.ts:180-196` 用硬编码的 `createEntity` 实现了它，而 36 个内容文件的每一档都有 `rewards`。

#### E3 `edit` → `editEntity`

| 项 | 值 |
|---|---|
| 动作方法 | `editEntity`（`delete.ts:166-246`，注册于 `:260`） |
| 参数 | `path: string`；`frontmatter?: Record<string, unknown>`（**浅合并**，`null` 值删除该键——`delete.ts:196-201`）；`body?: string`（整体替换）；**`append_body?: string`（NEW，`[C-6]`，§3.5）** |
| 上游类型 | `EditEntityInput`（`delete.ts:36-42`）+ 新字段 |
| 落的事件 | `entity_edited`；`detail = { path, name, kind }`（`delete.ts:227-234`）。**`kind` 在合并前计算**（`delete.ts:191-193`）→ 一次 edit 永远不会把一个实体的历史类型改掉 |
| 前置检查 | §4.4 |

**`edit` 最重要的用途不是改正文，是写回"下一步选项"。** 见 §8.2「为什么不需要 writer 效果」。


**`edit` 的写入目标限制（`[C-6]`=(a) 派生的硬要求，契约 §11.2 硬要求 1）**：`[C-6]` 判定 `{{ trigger.fm.* }}` 读取面**全开**，其唯一出口是效果参数。7 个效果里没有"回显给玩家"的效果，**但 `edit` 可以把读到的值写进任意可读实体的 frontmatter**——玩家下次 `look_at` 那张卡就看到了。⇒ 若不限制，`trigger.fm.*` 就成为**经 `edit` 中转的、可跨实体传播的读取通路**。

**因此 `edit`（以及走同一 `editEntity` 的 `set_status` / `consume`）的写入 `path` MUST 是二者之一**：

| 允许的写入目标 | 依据 |
|---|---|
| **触发实体自己**（求值后 `path === trigger.path`） | 命令改的是自己声明过的实体——与 §3.5 末尾"它改的是自己声明过的实体的字段"同一口径 |
| **`trigger.entry` 指向的路径**（求值后 `path === trigger.entry.<静态路径>`） | `[C-5]` 路线 ④ 的合法写入面；由 `from` 选中的那一个条目 |

**MUST NOT 允许把 `trigger.fm.*` 的值写进另一个任意路径。**（否则 (a) 的读取面就是跨实体外泄通路。）校验落点两处（与契约 R.2 的"写入期 + 运行期"同构）：`01` 的 `parseWorldCommand` **写入时**静态校验（两个允许目标在声明里都静态可判——`trigger.path` 是内建名，`trigger.entry.*` 是静态路径）；`03` 的求值后**运行前**复核（`path` 求值后 MUST 命中其一）。违规复用 `01` 的写入期码 `param_invalid` 与运行期 `invalid_argument`，**不新增码**（§6.3）。

#### E4 `set_status` → `editEntity`（窄口）

| 项 | 值 |
|---|---|
| 动作方法 | `editEntity`——**不是新方法**，是 `edit` 的一个收窄子集 |
| 参数 | `path: string`；`values: Record<string, string \| number \| boolean \| null>`（值的类型受 `InteractiveValueSchema` 约束：`packages/shared/src/schemas/frontmatter.ts:14`） |
| 落的事件 | `entity_edited`（与 `edit` 同一个） |
| 参数映射 | **引擎内部 read-modify-write**：读 `path` 当前 frontmatter → 深合并进 `status.data` → 把**整个 `status` 对象**作为 `frontmatter.status` 交给 `editEntity` |

**为什么不能直接用 `edit` 写 `frontmatter: { status: { data: { oil: 'empty' } } }`**：`editEntity` 是**浅合并**（`delete.ts:196-201`），那样写会**整个替掉 `status` 键**，把作者的 `status.label` / `status.chart` 一起抹掉（`buildStatus` 认得这两个键，`packages/shared/src/rules/interactive.ts:131-147`）。`set_status` 存在的唯一理由就是提供这个深合并；它不引入任何新事件、新错误码、新动作方法。

**命名辩护（必须写，否则评审会误判违规）**：`docs/doc-20-agent工具与互动字段协议.md:113` 写「**状态就是实体 frontmatter 里的一个键**」；`:115` 写「**没有 `get_state / set_state / state_update / watch_state`，且永不会有**」；`:359` 重复并写理由「绝对不做，非暂缓」。

`set_status` **在实质上完全合规**：它不建状态文件（`doc-20:113` 逐字「没有 `.airpworld/state.json`、没有状态命名空间」）、不建命名空间、不新增读写通道——它写的正是 `doc-20:113` 自己指定的那个"键"，走的正是 `doc-20:359` 自己指定的那条写路（「写 `edit` / `write`」）。

它**在字面上**只差一个字母：`set_status` 容易被读成 `set_state`。`[推断]` 一个不会引起这个联想的名字更好。本文选择**保留 `set_status` + 显式辩护**，理由是"状态"（status）在本仓已是一个有明确 schema 的既有名词（`StatusSchema`，`frontmatter.ts:21-35`），改名反而会造出第二个词。**留给评审门拍板** → `[C-7]`。

### 2.5 人类文本 vs 机器字段（与本地化工具对齐）

`tools/localize-world-editions.mjs:38` 的既有纪律逐字：「Human fields only. **IDs, conditions, paths and shared compaction prompts stay byte-for-byte.**」命令文件的 schema MUST 写死同一条界：

| 类别 | 字段 | 纪律 |
|---|---|---|
| **人类文本**（可翻译） | `name` / `desc`；效果里面向玩家的 `title` / `body` / `append_body` / `mark` 的字符串值 | 走翻译通路（但见 §11 冲突 4：`.yaml` **今天不进翻译队列**） |
| **机器字段**（MUST NOT 被翻译污染） | `params[].name` / `params[].type` / `do[].action` / `do[].when` / 所有路径 / `link_to` / `mark` 的**键名** | MUST 匹配 ASCII 判定式（见下） |

**可机械核验的判据**（`01` 的 `parseWorldCommand` MUST 实施）：所有非人类文本的字符串字面量必须满足 `^[a-z0-9][a-z0-9/_.-]*$`。`{{ }}` 表达式内部的标识符同样受此约束（`{{ trigger.fm.油 }}` → 拒绝，因为 frontmatter 键名是 ASCII）。这条与 `01` 的 id 正则（`^[a-z0-9][a-z0-9-]{0,47}$`）同源。

### 2.6 受限数组实参：`list-args` 与 `fold-args`（主 agent 裁定，命名冻结）

**问题**：`dice_outcomes[].rewards` 与 `[].options` 是数组，而 `{{ }}` 禁止嵌套（裁定 A）。作者不能写 `rewards[{{ i }}]`，硬编码 `[0]/[1]/[2]` 会在只有 1 项时写出空串。

**先摆事实**（本文对全仓 `templates/**` + `archive/**` 的扫描）：

```text
含 dice_outcomes 的文件:              42
dice_outcomes 档位（rewards 块）总数: 144
每档 rewards 条目数分布:              {1: 144}   ← 144/144 全部恰好 1 项，无例外
dice_outcomes 档位里 options 条目数:  {2: 144}   ← 144/144 全部恰好 2 项
（全仓其它 options 块 36 个，均为 1 项，与 dice_outcomes 无关）
```

这两条数字是 `[C-5]` 迁移工作量的**实测依据**，也是本节两条契约的上界锚点。

引擎允许的 `rewards` 上限是 3（`origin/niko:apps/server/src/engine/declared-actions.ts:146` 逐字 `if (!Array.isArray(rewards) || rewards.length > 3)`）。

**主 agent 裁定方向三：作者不做循环、不写下标，把整个数组当实参交给效果，展开发生在引擎内部。** 并且**分两条契约**——它们不是同一个东西，放在一起会让读者以为后者是前者的特例：

| | **契约 A：`list-args`（数组迭代）** | **契约 B：`fold-args`（数组折叠）** |
|---|---|---|
| 语义 | N 个**独立效果**，各自有前置检查与成功/失败 | **1 个结构性写入**，整个数组变成一个对象 |
| 数量 | 迭代次数 = 输入长度（≤ schema 上限） | 恒为 1 次写入 |
| 失败 | **每个展开项是一个独立 step，受 stop-at-failure 管辖**：第 2 项失败 ⇒ 第 3 项不执行；已成功的前缀（第 1 项）留在世界里，不回滚 | 整体成功或整体失败 |
| 例 | `give: "{{ trigger.entry.rewards }}"` | `options` → `choice.options` + `choice_actions` |
| 上界锚点 | 实体 frontmatter 的 `rewards` ≤ 3 | `options` ≤ 2（实测），受同一 schema 上限机制约束 |
| 消费它的效果 | **只有 `give`**（§2.3 E1） | **只有 `edit`**（§8.1 的"下一步选项"） |

**两者都 MUST 是 `{{ trigger.entry.* }}` / `{{ trigger.fm.* }}` 的静态路径求值结果，都不允许字面量内联数组**（字面量数组是内容，内容住实体——`[C-5]` 路线 ④ 的核心，见 §11 冲突 4）。

> **`[C-6]` 的 scope（评审 NF-2）**：`[C-6]` 只约束 **`{{ trigger.fm.* }}` 插值面**，**不约束 `on.<hook>[].from`**。理由：`08 §4.1` 的最终样本一个 `trigger.fm.*` 都没有，它读 `trigger.entry.*`（由 `from: dice_outcomes` 解析），而 `dice_outcomes ∉ humanKeys`（实测）。⇒ 真正把 `[C-5]` 与 `[C-6]` 耦合的是 `from`，不是 `trigger.fm`。本节两条契约（`list-args`/`fold-args`）都不受 `[C-6]` 收窄的影响。

**哪个效果接受哪种形态由本表声明，`01` 不猜**（写给 `01`）：`with:` 的值类型是「标量 | 静态路径解析出的数组」，而"这个效果接受 scalar / list / fold"是**效果表的一列**。`01` 的 schema 在写入时校验形态匹配。

| # | 语义 | 依据 / 后果 |
|---|---|---|

#### 契约 B：`edit` 的 `fold-args` 与键冲突策略

`options` 的 144/144 恰好 2 项（实测）不是效果实参的迭代，是**一次结构性写入**：整个数组变成 `choice.options` + `choice_actions` 两个对象（§8.1）。**`edit` 因此没有 `list-args` 形态。**

**主 agent 要求 `fold-args` 的契约包含键冲突检测，本文给方案与理由。**（本节策略已按 `[C-5]` 阻断 B-1 的实测证据修订：**逐值相等即幂等放行，只有值不等才拒绝**。）

**裁定：逐值相等即幂等放行；只有值不等时才拒绝 + 可见错误（不覆盖）。**

理由三条：

1. **"有交集即拒绝"会让路线 ④ 在存量上功能归零。** 主 agent 实测（契约 §11.2 B-1）：**144/144** 档的 `dice_outcomes[].options` 都含 `id: back`，而 **36/36** 卡的静态 `choice_actions` 键集也都是 `{back}`（`templates/whitechapel-jp/world/london-map/04-investigation-dice.md` 的静态 `choice_actions` **逐字已有 `back` 键**）⇒ **交集必中 → 按钮永不写回**，而所有技术指标全绿。**"一律拒绝"不是安全，是静默的功能归零。**
2. **逐值相等 ⇒ 覆盖与放行产生同一世界状态。** 折叠值与静态既有值在本仓**逐字节相等**时（实测 144 档里 `back` 的折叠值 `{kind:'enter', target:'world/…'}` 与静态值逐字节相同），"覆盖"是一次恒等写入：写完后文件的字节与写入前**完全一致**，因此**不违反契约 §7 硬门 3**（不篡改已结算事实）。硬门 3 保护的是"已结算事实不被改变"，不是"同一个键被写两次"这个动作本身。
3. **值不等时才复用 `already_exists`（409）。** 它已经是本仓对"目标被占用，本动作不能覆盖"的标准答案（`errors.ts:8` 的注释逐字）。折叠的键冲突**且值不等**才是同一件事——那才是真覆盖、才会让既有条目无声消失（硬门 4）——复用同一个码，不新增（§6.3）。

**实现契约**：

```ts
/** NEW. Fold `options` into the two frontmatter keys.
 *  A key present in BOTH the fold and the entity is a CLASH only when its
 *  value DIFFERS (`deepEqual`); an equal value is a byte-identical no-op and
 *  is merged through unchanged (see the table below). */
function foldOptions(
  options: Array<{ id: string; label: string; action?: Record<string, unknown> }>,
  existingActions: Record<string, unknown> | null,
): { choice: { options: Array<{ id: string; label: string }> };
     choice_actions: Record<string, unknown> } | { clash: string[] };
```

| 情况 | 行为 | 文案 |
|---|---|---|
| 折叠出的 id 与实体已有 `choice_actions` 的键**无交集** | 写入 | — |
| **有交集，且该项值与既有键的值 `deepEqual`** | **放行（幂等 no-op）**：该键按折叠值写入，写入后文件的字节不变 | — |
| **有交集，且值不等** | `already_exists` / 409，**整体不写** | `edit: the folded options would overwrite existing choice_actions entries: "read-clue", "back". A command MUST NOT silently replace an entity's declared options — rename the option id or remove the existing entry first.` |

**"整体不写"只在值不等时适用**（上表第 2 行的相等项照常放行）：半个选择组比没有选择组更糟——玩家会看到一个**缺了几个按钮的菜单**，而没有任何东西告诉他为什么少了。`fold-args` 是契约 B（整体成功或整体失败），这条与它自己的定义一致。

**为什么"值不等即拒绝"是正确的（`05` 给了第二条更强的理由）**：若折叠**覆盖**了实体已有的 `choice_actions` 键且值不同，那条键可能是**上一次运行**写下的。覆盖它等于**改写已结算结果**（契约 §7 硬门 3），并且会让 `command_log` 说"跑过了"而世界里的按钮已经不是那次跑出来的——**日志与世界不一致**。拒绝只是拒绝；覆盖会造成一个无法自证的历史。**值相等时这一条不适用**：写入后按钮与那次跑出来的**逐字节相同**，日志与世界仍然一致。

#### 回执粒度：`list-args` 逐项各占一步，`fold-args` 恒占一步（写给 `05`）

两条契约对 `05` 的 step 回执要求**完全不同**，必须分开写：

| | `list-args`（`give: "{{ trigger.entry.rewards }}"`） | `fold-args`（`options → choice + choice_actions`） |
|---|---|---|
| 效果数 | = 数组长度（≤ 3） | **恒为 1** |
| `05` 的 step 回执 | **每项各占一个 `step`** | **只占一个 `step`** |
| 续跑粒度 | 可以停在"第 2 项做完、第 3 项没做" | 只有"做完 / 没做完"，**无中间态** |

**因此 `give`（`list-args`）的每个展开项是一个独立 step，MUST 受 stop-at-failure 管辖**：第 2 项 `already_exists` 时，**第 1 项留在世界里**（不回滚）、命令停在第 2 项，第 3 项**不执行**。这样"崩在第 2 项"才是可续跑的（`05` 的 `steps[].step` 用**扁平序**做游标，`steps[].at` 用声明位置 `do[0]#2` 做溯源）。

**对本文的后果**：`EffectOutcome` 数组的长度**不直接等于** `do[]` 的长度——一次 `give`（`list-args`）会产出 N 个 `EffectOutcome`。`03` 在算「总效果数上限」时 MUST 用**展平后**的计数（契约 §4.3 的上限指的是展平后的效果数），否则一个 `rewards: [a,b,c]` 就能绕过上限 3 倍。**这是上限实现的一个真实陷阱，登记为 `[C-9]`（§12.1）。**

#### 顺序与键序（写给 `03` / `05`）

求值器 MUST **保留数组的顺序**。理由：`fold-args` 生成的 `choice_actions` 对象键序影响 `05` 的 `plan` 摘要（稳定键序是摘要可比的前提），而 `list-args` 的执行顺序就是声明顺序。`01` 已冻结"数组顺序 = 声明顺序 = 执行顺序"。

**数组进了 `with`，而 `args` 不进 `commandKey`**（`05` 的公式 `sha256(source, hook, command, fact)` 不含 `args`）→ **数组长度变化不改变 key**。这是好事（不会因数组内容变化而重复结算），也是 `overlapping_command_when` 需要存在的原因（`05` 已有交叉引用）。

**这是本文最重要的一条结论** → §11 冲突 1。

### 3.2 「一份灯油」到底是什么？——这是真正的设计题目

`docs/gameplay/Chalk玩法形态与判定约定.md:41` 逐字：「**灯油是拟新增的可损耗资源**，未拥有时不能凭空扣除；数值与损失需用户确认后才写入模板」。而事实 1 说明：**模板里没有它作为"资源"的表示**，只有一个碰巧叫 lamp-oil 的便携 note。

所以真正的问题不是"怎么扣一个数量"，是 **"引擎怎么知道一样东西是可耗的、还剩几次"**。三个候选：

| 候选 | 表示 | 评估 |
|---|---|---|
| **Q-A 数量字段** `count: 1` | 引擎读 `count`，扣到 0 时…… | **半成品**：扣到 0 之后仍然回到"该怎么办"的同一个问题。且它引入一个**新的全局 frontmatter 语义**，要同时改 `look_at` 渲染、背包 UI、卡面（`apps/web/src/lib/item-action-draft.ts:12-18` 的 `displayTitle` 只读 `title`），而 `status` 已经占了"实体自己的标量状态"这个生态位（`doc-20:113`） |
| **Q-B `portable` 的姐妹键** `consumable: 1` | 同 Q-A，换名字 | 同 Q-A |
| **Q-C "用完变成什么"** | 不引入数量，引入**目标状态** | **本文推荐**，见 §3.4 |

**Q-C 的关键洞察**：可耗资源的真相不是"还剩几份"，是**"它现在处于什么状态"**。灯油用完 = 空瓶。引擎要表达的从来不是减法，是**状态迁移**——而"实体自己的标量状态"这个生态位，本仓已经有一个被 schema 约束、被前端渲染、被条件求值读取的载体：`status.data`（`packages/shared/src/schemas/frontmatter.ts:21-35`，`buildStatus` 读它 `interactive.ts:124-168`）。

**这条也解释了为什么 `consume` 不是新动作方法**：它做的是"把 `status.data` 里某个键设成某个值 + 把正文改成对应的叙述"，两件事都是 `editEntity`。

### 3.3 三种"扣掉"的实现，逐个对照硬门

**实现（NEW，`packages/shared/src/commands/effects/consume.ts`）**：

```ts
export async function runConsumeEffect(
  ctx: ActionContext,
  input: ConsumeEffect,
): Promise<EffectOutcome> {
  const store = ctx.store;

  // 1. Resolve the FIRST candidate that exists. Bounded by `input.from.length`
  //    stats — never an event scan (§4.3).
  let target: string | null = null;
  for (const candidate of input.from) {
    if ((await store.statKind(candidate)) === 'file') { target = candidate; break; }
  }
  if (target === null) {
    // 硬门 6: never silently treat a missing item as consumed.
    return {
      ok: false,
      action: 'consume',
      path: input.from[0],
      code: 'not_found',
      reason: `Nothing to spend: none of ${input.from.map((p) => `"${p}"`).join(', ')} exists.`,
    };
  }

  // 2. Idempotency precondition: the mark is already set → this is a REPLAY,
  //    not a new spend. Write nothing (硬门 2). `05` owns the receipt policy.
  if (input.mark && await alreadyMarked(store, target, input.mark)) {
    return { ok: true, action: 'consume', path: target, reused: true, event: null };
  }

  // 3. One call. The engine does the read-modify-write (§3.5); the AUTHOR never
  //    writes string concatenation (契约 §2.3 forbids it in the DECLARATION,
  //    not in the engine — `rules/dice.ts:281 patchRollDiceResult` is the precedent).
  if (input.to !== undefined) {
    const moved = await moveEntity(ctx, { from: target, to: input.to });
    return { ok: true, action: 'consume', path: moved.details.path, event: moved.details.event };
  }
  const edited = await editEntity(ctx, {
    path: target,
    append_body: input.append_body,
    frontmatter: await mergedStatusFrontmatter(store, target, input.mark, input.title),
  });
  return { ok: true, action: 'consume', path: target, event: edited.details.event };
}
```

**`alreadyMarked` / `mergedStatusFrontmatter` 是本文新提出的两个 helper（`NEW`，同文件内私有）**，签名：

```ts
/** NEW. True when every key/value of `mark` already equals the target's `status.data`. */
async function alreadyMarked(
  store: WorldStore, path: string, mark: Record<string, unknown>,
): Promise<boolean>;

/** NEW. Read-modify-write that produces the shallow-merge-safe `frontmatter` argument
 *  for `editEntity` (§2.3 E4). Returns `undefined` when there is nothing to change. */
async function mergedStatusFrontmatter(
  store: WorldStore,
  path: string,
  mark?: Record<string, string | number | boolean | null>,
  title?: string,
): Promise<Record<string, unknown> | undefined>;
```

### 3.5 `append_body` 的准确形态（`[C-6]`，主 agent 已拍板方向）

`editEntity` 的 `body` 是**整体替换**（`delete.ts:219` 逐字 `const body = input.body ?? parsed.body;`），所以"骰后短结果显示在原卡上"用现有参数表达不了。主 agent 已拍板采纳 `append_body`。准确形态与三条硬约束：

| # | 硬约束 | 落点 | 违反会怎样 |

**拼接语义（MUST 冻结为既有函数，不是新写一份）**：

### 3.7 `05` 需要知道的一件事

`consume` 的幂等**不依赖 `command_log`**：它依赖自己写下的 `mark`（`status.data.spent = true`），并把它当作**前置检查**（§3.4 step 2）。所以：

| 次序 | 条件 | 结果 |
|---|---|---|
| 第一次 | `mark` 未设 | 执行 → `editEntity` 落一条 `entity_edited` |
| 第二次 | `mark` 已设 | `reused: true`，**不写文件、不落事件**（没有文件变化就没有事件，符合 `doc-21 §2.1`） |

这与契约 §7 硬门 2「同一已结算结果 MUST 复用既有结果」一致：`reused` 就是"复用"，不是"拒绝"。

**这是一条给 `05` 的设计约束**：`command_log` 是命令级的回执（`05` 拥有），`mark` 是**实体级的状态真相**。两者不冲突，但 `05` MUST NOT 假设"没写 `command_log` 就意味着没执行过"——`consume` 可能已经执行过，而 `command_log` 因为 `[C-1]`（失败是否落账）未拍板而未落。**实体自身的状态是比命令回执更硬的一层真相。**

**现状的失败做法有两份，不是一份：**

| 位置 | 做法 | 复杂度 |
|---|---|---|
| `origin/niko` `declared-actions.ts:183,188` | 每个奖励 `getEventsSince(0)` 扫**全部历史**，外层套 `for` | **O(n²)** |
| **`apps/server/src/engine/declared-actions.ts:173`（**今天就在 main 上跑**）** | `resolveMaterialPath` 缓存未命中时也调 `store.getEventsSince(0)`（`:173`），把结果当 `moves` 传给下一个候选（`:188-193`） | **O(n) 全历史扫描** |

> 第二份**今天就在 main 上跑**（`/api/choice` → `world.ts:1171` → `runDeclaredChoice`），所以"全历史扫描"不是 niko 独有的债，本模块开工时它已经在生产路径上。

**替代方案：有序候选路径 + `statKind`。**

世界命令**不值得也不应该知道文件曾经在哪**。作者写的是"这个物件可能在的地方"，引擎按声明顺序探测**第一个存在的**：

```yaml
from:
  - "player/lamp-oil.md"                              # 玩家已取走
  - "world/harbor-chart/old-lighthouse/lamp-oil.md"   # 还没取走
```

| 维度 | 事件扫描（现状） | 候选列表 + `statKind`（本文） |
|---|---|---|
| 成本 | O(全事件历史) 次读 + O(k) 内存；最坏 O(n²) | **O(k) 次 `stat`**，k = 作者写的候选数（`03` 定上限，`[推断]` 建议 8） |
| 可静态分析 | ❌ 成本取决于世界运行了多久 | ✅ 成本 = `from.length`，**与历史长度无关** |
| 云端多租户 | ❌ 一个老世界会把所有命令拖慢 | ✅ 有界 |
| 语义 | "追着移动历史跑" | "在这几个地方找" |
| 失败文案 | `Content is unavailable: <path>`（`declared-actions.ts:199`） | `Nothing to spend: none of "a", "b" exists.`（**列出全部候选**，让模型知道该检查哪里） |

**为什么这是正确的**：`resolveMaterialPath` 的注释自己承认它在"追移动历史"（`:172`「Follow recorded moves only. A matching basename is not proof of identity.」）。世界命令**不需要做这个推理**——它只需要在**触发时刻**知道东西现在在哪。候选列表把"物件可能的位置"从**运行时发现的问题**变成**作者声明的事实**，而声明式系统的一切价值都在这个转换上。

**唯一的适用边界（诚实写出）**：如果作者不知道物件可能在的地方（例如"玩家可能把它藏到世界上任何地方"），候选列表就失效了。那种玩法**本文不支持**；`03` 应给出"候选数超限 = 拒绝执行"的行为（不截断、不静默取第一个）。这与 §1 的"宁可少给"一致。

### 4.4 `edit` / `set_status` / `consume` 的前置检查

| 情况 | 谁检查 | 错误码 / HTTP | 文案 |
|---|---|---|---|
| **目标不是 file**（不存在或是目录） | `delete.ts:173-176` | **`not_found` / 404** | `Entity not found: "<path>"` |
| 目标在角色小天地且无权 | `delete.ts:181-187` | `unsupported` / 501 | 见 §5 |
| `appearance` 非法 | `delete.ts:208-218` | `invalid_argument` / 400 | issue 自带 |
| `component: photo` 的 `image` 非资源 | `delete.ts:205-207` | `invalid_asset_ref` / 400 | — |
| 事件失败 | `delete.ts:235-240` | `event_failed` / 500（文件已写） | `File "<path>" was edited but the world event could not be recorded: <cause>` |
| **`body` 与 `append_body` 同时给** | NEW，`[C-6]` | `invalid_argument` / 400 | `edit: pass either "body" (replace) or "append_body" (append), not both.` |
| **`append_body` 超长** | NEW，`[C-6]` | `invalid_argument` / 400 | `append_body is <n> chars; the limit is <MAX>.` |
| `consume` 的候选全部不存在 | NEW，§3.4 | `not_found` / 404（**不落事件**） | `Nothing to spend: none of "a", "b" exists.` |
| `consume` 同时写 `to` 与 `mark`/`append_body`/`title` | NEW，§3.4 | `invalid_argument` / 400 | `consume: "to" (move it away) and "mark"/"append_body"/"title" (change it in place) are different outcomes; pass one.` |
| **`frontmatter` 命中保留键拒绝列** | NEW，契约 R.2 | `invalid_argument` / 400 | `edit: "roll_dice" is a reserved key — a world command MUST NOT rewrite already-settled facts or forge a command receipt. Reserved: roll_dice.result, roll_dice.passed, command_log, command_error, on.` |
| **`edit`/`set_status`/`consume` 的写入 `path` 既不是触发实体自己、也不是 `trigger.entry.*`** | NEW，`[C-6]` 硬要求（§2.3 E3 后） | 写入期 `param_invalid` / 400；运行期 `invalid_argument` / 400 | `edit: the write target must be the triggering entity or a path reached through trigger.entry — a command MUST NOT copy trigger.fm.* into an arbitrary entity.` |

> **`not_found` 对"已被移走"的处理是"让它自然失败"，不是"去找它"**：如果物件确实被移走了，且作者没把新位置写进候选列表，`edit`/`consume` 会 `not_found`——**这是正确的**。硬门 4 要求的是"可见地失败并说明缺什么"，不是"猜它在哪"。

### 4.5 "已被消耗"与前检查的区分

不要与"不存在"合并成一个错误：

| 状态 | 返回 | 依据 |
|---|---|---|
| **不存在** | `not_found` / 404，**拒绝** | 契约 §7 硬门 6 |
| **已被消耗**（`mark` 已设） | `reused: true`，**不写、不落事件** | 契约 §7 硬门 2 |

**如果把它合并成 `already_exists`**，玩家会看到"这个物件已经存在"这种与消耗毫无关系的句子——**错误文案与语义脱钩**。`already_exists` 的语义是"目标被占用，本动作不能覆盖"（`errors.ts:8`），不是"这件事已经发生过"。

### 4.6 `enter` 的前置检查与那处真实越权

| 检查 | 今天在哪 | 本文要求 |
|---|---|---|
| 层 id 为空 | `layer.ts:59-61` → `invalid_argument`（**动作层**） | 不变 |
| 层不存在 | **只在路由**：`world.ts:1246-1248` `if (!layers[layer]) throw ActionError('not_found', 'Scene does not exist.')` | 下沉到 `enterLayer` |
| **README gate（`requires.items`）** | **只在路由**：`world.ts:1196-1234`，错误码 `invalid_gate` / 409、`requirements_not_met` / 409 | **下沉到 `enterLayer`** |
| README frontmatter 非法 | **只在路由**：`world.ts:1197-1203`，`invalid_gate` / 409 | 下沉到 `enterLayer` |

**这是一个真实的越权，必须登记**：

- 事实：`POST /api/enter-layer` 在调 `enterLayer` **之前**做 gate 校验（`world.ts:1196-1234`），gate 的实现不在动作层。
- 后果：任何绕过该路由的 `enterLayer` 调用**不受 gate 约束**。世界命令是一条新路径（`runWorldCommand` → 动作层），因此它会**绕过入场门**——玩家可以用一条命令进入一个需要特定背包装备才能进的场景。
- **这与契约 §10.1 是同一类架构错误**：门该在哪一层被放错了。区别是 §10.1 是"同一个规则两处实现"，这里是"只有一处实现，而新的入口不经过它"。

**处置（本模块的正式提案）**：把 gate 校验从 `world.ts:1196-1234` **移进** `enterLayer`（`layer.ts:54-87`）。这不是"复刻"，是**下沉**——复刻会违反契约 §8 反模式 3（同一规则两处实现）。路由随后变成薄壳。

**在此之前**：世界命令的解析阶段（`01` 的 `parseWorldCommand`）MUST 拒绝 `enter`，fail-closed。错误文案（给模型看）：

```text
command/<id>.yaml line N: "enter" is not available yet — the scene gate is checked in the HTTP
route (apps/server/src/routes/world.ts:1196-1234), not in the action layer, so a command would
bypass it. Use "give" or "edit" instead, or wait for the gate to move into enterLayer.
```

给玩家的文案由 `06` 定（`command_error`）。这条与 `[C-8]` 绑定（§12）。

## 5. 权限继承：玩家触发的命令会撞上什么

### 5.1 权限门的完整逻辑（逐字核实）

`assertNookMutationAllowed(actor, agentScope, path, operation, registeredCharacterIds)`（`packages/shared/src/actions/actor.ts:128-156`）：

1. `characterIdOfPath(path)` 为 `null` → **立即 return，什么都不检查**（`actor.ts:135-136`）。**只有 `characters/<id>/**` 下的路径会进入这个门。**
2. 是角色配置文件（`characterRootConfigOf`） → `move`/`delete` 抛 `not_movable` / 409，其余抛 `unsupported` / 501（`actor.ts:137-149`）。
3. 否则走 `isLifeTraceMutation`（`actor.ts:86-106`）。逐分支：

| actor | `write`/`edit` | `move`/`delete` |
|---|---|---|
| `character` | `agentScope === 'character' && actor.id === characterId`（`actor.ts:101`） | 同左（`:97`） |
| `writer` | `agentScope ∈ {writer-top-level, initializer, engine}`（`:102-104`） | `agentScope ∈ {writer-top-level, engine}`（`:98`，**没有 `initializer`**） |
| `god` | `agentScope !== 'player'`（`:105`） | 同左（`:99`） |
| **`player`** | **恒 `false`**——落到底返回 `actor.type === 'god' && ...`（`:105`） | **恒 `false`**（`:99`） |
| `engine` | **恒 `false`**（`engine` 既不是 character/writer 也不是 god） | **恒 `false`** |

**谁知道 `agentScope`**：动作层按 `ctx.agentScope ?? (character ? 'character' : player ? 'player' : 'writer-top-level')` 兜底（`delete.ts:102-104`、`move.ts:97-99`）。所以**玩家 HTTP 触发时 `agentScope === 'player'`，作家工具触发时 `agentScope === 'writer-top-level'`**。

### 5.2 逐效果确认：actor 是 player 时哪些会被拒

| 效果 | 目标在 `world/**` 或 `player/**` | 目标在 `characters/<id>/**` |
|---|---|---|
| `give` | ✅ 通过 | ⚠️ **也通过**——`createEntity` 根本没有 nook 门（见 §5.3） |
| `move` | ✅ 通过 | ❌ `unsupported` / 501（`move.ts:101-107` 或 `:137-143`） |
| `edit` | ✅ 通过 | ❌ `unsupported` / 501（`delete.ts:181-187`） |
| `set_status` | ✅ 通过（走 `editEntity`） | ❌ `unsupported` / 501 |
| `consume` | ✅ 通过 | ❌ `unsupported` / 501 |
| `enter` | ✅（与路径无关） | — |
| `link` | ✅ 通过 | ❌ 不是权限问题：小天地不是层，`sharedLayer` 端点校验失败（§2.3 E7） |

**当 actor 是 writer 时，同一份命令的行为完全不同**：`agentScope` 变成 `writer-top-level`，而 writer 分支对 `write`/`edit` 接受 `writer-top-level`（`actor.ts:102-104`）→ **通过**。

> **这是契约 §10.1「同一规则两套行为」的同构问题，但这次它在语义上是**对的**：`doc-20 §1.1` 的意图就是"角色小天地只有角色/作家能写"，权限门本身没写错。**问题在于它会让一条命令"玩家触发时失败、作家触发时成功"** ——玩家会看到一次神秘的失败，`command_error`（`05`+`06`）必须解释清楚。

### 5.3 `give` 的 nook 权限洞（本文的第二个重要发现）

**事实**：`createEntity`（`create.ts:87-151`）**没有** nook 权限检查。全文 grep `assertNookMutationAllowed` / `characterIdOfPath` → **0 命中**。

对比（同一动作层内，逐文件计数）：

| 文件 | 有 nook 门 |
|---|---|
| `chalk.ts` | ✅ `:493-499` |
| `delete.ts` | ✅ `:106-112`（remove）、`:181-187`（edit） |
| `move.ts` | ✅ `:101-107`、`:137-143` |
| **`create.ts`** | ❌ **0 处** |
| `layer.ts` / `canvas.ts` / `create-char.ts` | ❌ 0 处 |

**后果**：任何 actor（包括 player、engine）都能用 `createEntity` 在 `characters/<id>/` 下**创建**文件。玩家理论上能往角色的私人小天地里塞一张卡。

**这个洞今天就存在**——god 路由 `/api/god-action` 的 create 分支就调它（`world.ts:1313-1338`，actor 是 `god`，而 god 的 nook 分支要求 `agentScope !== 'player'`（`actor.ts:105`），所以现状由 god 的身份兜着）。**但世界命令会把它变成可声明、可复制的路径**：一条命令被 36 个内容文件引用、被玩家反复触发。

**本文的处置（三重）**：

1. **世界命令侧：解析阶段拒绝 `characters/` 前缀的 `give`。** 用**写入时**拒绝而非运行期——运行期拒绝会让玩家看到一次神秘失败，而这**是作者写错的命令**，应在写入时报错（契约 §6.1「写入即校验」）。文案：

```text
command/<id>.yaml line N: a "give" effect may not create anything under characters/ — a
character's nook is written by that character or the writer, never by a world command. The nook
permission gate does not cover createEntity (packages/shared/src/actions/create.ts has no
assertNookMutationAllowed call), so a command could place a card in someone's private space.
Use world/ or player/ instead.
```

2. **动作层侧：建议给 `createEntity` 补 nook 门**——在 `create.ts:97` 的 `statKind` 检查旁加

```ts
const agentScope: AgentScope =
  ctx.agentScope ?? (ctx.actor.type === 'character' ? 'character' : ctx.actor.type === 'player' ? 'player' : 'writer-top-level');
const manifest = await ctx.store.getManifest();
assertNookMutationAllowed(ctx.actor, agentScope, path, 'write', manifest.characters.map((c) => c.id));
```

**登记为对既有代码的修复，不是本模块的范围** → §11 冲突 3，归 `09` 评估、`08` 执行。

3. **`link` 不受影响**：小天地不是层，`linkCards` 已经拒绝。

### 5.4 全局推论：一条命令的权限取决于"谁触发"——这是设计约束不是 bug

> **同一条 `command/*.yaml` 在玩家触发与作家触发下的成功集合不同。** 作者写命令时 MUST 能预知这件事，因此：
> (a) `01` 的 schema 校验 MUST 对"静态上玩家一定做不到的效果"在**写入/解析**阶段报错（如 §5.3 的 `characters/` 前缀 `give`）；
> (b) 对**参数化**而无法静态判断的路径（`{{ trigger.fm.reward_path }}`），校验器无法拦截，因此必须在**运行期**可见地失败（`command_error`，`05`+`06`）；
> (c) **不要试图在命令层复刻权限门**——那会造出同一规则的第二份实现（契约 §8 反模式 3）。让动作层拒绝，把拒绝的文案原样冒泡到 `EffectOutcome.reason`。

## 6. 效果的返回值

### 6.1 形状（`03` / `05` / `06` / 模型 / 触发者的 tool_result 都消费它）

```ts
/** NEW — packages/shared/src/commands/effects.ts */

/** The closed set of effect names (§2.1). 7 entries; `run` is NOT a member. */
export const WORLD_COMMAND_EFFECTS = [
  'give', 'move', 'edit', 'set_status', 'consume', 'enter', 'link',
] as const;
export type WorldCommandEffectName = (typeof WORLD_COMMAND_EFFECTS)[number];

/** One effect's declared shape AFTER `{{ }}` substitution. */
export type EffectInput =
  | GiveEffect                                            // §2.6 (single OR array form)
  | { action: 'move'; from: string | string[]; to: string; near?: string }
  | { action: 'edit'; path: string; frontmatter?: Record<string, unknown>;
      body?: string; append_body?: string }
  | { action: 'set_status'; path: string;
      values: Record<string, string | number | boolean | null> }
  | ConsumeEffect                                   // §3.4
  | { action: 'enter'; layer: string }
  | { action: 'link'; from: string; to: string; style?: string; label?: string }

/**
 * What ONE effect reports back. `03` uses it to decide `on_error: stop|continue`;
 * `06` uses it to play the result; the trigger's tool_result carries it verbatim.
 */
export interface EffectOutcome {
  ok: boolean;
  action: WorldCommandEffectName;
  /** The FINAL path this effect acted on (after directory expansion / candidate
   *  resolution). `null` only for `enter` (which acts on a layer, not a path). */
  path: string | null;
  /** Present on success when a world event was recorded. Absent for `link`
   *  (an attachment of `give`: it takes effect with the `give`'s `entity_created`
   *  and produces no event of its own) and for `reused` replays (no write → no event). */
  event?: WorldEvent;
  /** `true` when the effect deliberately did nothing because its result was
   *  already settled (硬门 2). NOT a failure. */
  reused?: true;
  /** Present when `ok === false`. An `ActionErrorCode` — never a new code
   *  invented by this module (§6.3). */
  code?: ActionErrorCode;
  /** The action layer's own message, verbatim. NEVER rewritten (04 §5.4 (c)). */
  reason?: string;
}
```

### 6.2 为什么 `EffectOutcome` 必须有 `event`：一条被实测确认的通路

`packages/shared/src/inject/collect.ts:250-252` 在作家注入时传 `excludeActor: actor`，而 `local-store.ts:745-748` 逐字：

```ts
if (opts.excludeActor) {
  // NOT (type AND id) — an OR here would also drop every character event.
  where.push(`NOT (actor_type = ? AND COALESCE(actor_id, '') = ?)`);
```

→ **作家 Agent 的事件注入必然排除 `actor == 自己` 的所有事件**（已由主 agent 实测确认）。而契约 §5.1 冻结「命令事件的 actor = 触发者」。**结论：作家调 `roll_dice` 触发命令后，命令产生的事件（比如新建的笔记）在它自己下一轮的注入里被过滤掉——它看不见。**

**推论（写给 `02`/`03`/`05`/`10`）**：命令的后果 MUST 同步出现在**触发动作的 `details`** 里，让触发者通过自己的 tool_result 在同一轮看到它。`EffectOutcome` 的 `event` 字段正是这条通路的数据源。契约的 actor 口径**不变**（改成 `engine` 会让世界史变成"引擎自己拿走了东西"，违反 `doc-21 §3.2` 把 `god` 从 `player` 单列的同一条理由）。

### 6.3 错误码：**不新增任何 `ActionErrorCode`**

`ActionErrorCode` 是 18 值封闭 union（`packages/shared/src/actions/errors.ts:3-21`），带 `HTTP_STATUS` 映射（`:24-43`）。**本文不新增一个**。所有效果失败都复用已有码：

| 失败 | 复用码 | 为什么不新增 |
|---|---|---|
| 物件不存在 / 候选全空 | `not_found`（404） | 语义精确 |
| 目标被占 | `already_exists`（409） | 语义精确（`errors.ts:8`） |
| 路径非法 | `invalid_path`（400） | 语义精确 |
| 权限拒绝 | `unsupported`（501） | 动作层原文即此 |
| 参数类型/上限 | `invalid_argument`（400） | 语义精确 |
| 层不存在 | `not_found`（404） | 语义精确 |

**唯二可能真正需要新码的地方，本文都选择不新增**：

1. "已经被消耗过" → 用 `reused` 标志表达，**不是错误**（§4.5）。
2. "命令执行失败" → 不是动作层错误，是**命令层的执行报告**（`{ ok: false, code, reason }`），落不落账是 `[C-1]`（`05` 提方案）。

新增一个码要同时改 `errors.ts:3-21` 的 union、`:24-43` 的 `HTTP_STATUS`、`docs/tools/00` 的错误表与 `docs/tools/01 §7.1`。**在语义能被既有码精确表达时，这笔开销是纯负债。**

### 6.4 一次成功的效果返回什么文字（给谁看）

| 消费者 | 拿到什么 | 说明 |
|---|---|---|
| **触发它的 Agent** | 整个 `EffectOutcome[]` 经 `details.commands` | §6.2；由触发动作的 `details` 承载 |
| **`03` 的 execution** | `ok` | `on_error: stop` 时遇 `ok: false` 停止后续效果 |
| **`05` 的幂等** | `reused` + `event` | `event === undefined && reused` = "本次没写任何东西" |
| **`06` 的演出** | `path` + `event` | 有 `event` 就能渲染成演出；只有 `path` 就渲染成"卡变了" |
| **玩家** | **不直接读** `EffectOutcome` | 玩家看到的是文件变化的效果（卡出现、卡变空瓶），加上 `06` 设计的 `command_error` 文案 |

**`path` 必须是"最终路径"而不是"声明路径"**：`move` 会把层目录展开成完整文件名（`move.ts:127-136`），`consume` 会在候选列表里挑一个（§3.4 step 1）。`06` 要用这个路径去画布上找卡；给错路径 = 演出找不到目标。


### 6.5 每条效果的 `detail` MUST 带 `detail.command: <id>`（**逐效果，无例外**）

主 agent 已裁定：**只用 `detail.command`，不用 `detail.by`**。

**为什么 `detail.by` 必须删掉（本文独立实测确认）**：`detail.by` 已被 `layer_initialized` 占用且是**闭枚举**（`packages/shared/src/schemas/events.ts:99` 逐字 `by: z.enum(['writer', 'player', 'engine'])`），而 dev 模式 `appendEvent` 会对 detail 跑 `safeParse` 并抛 `invalid_argument`（`local-store.ts:668-679`）。

本文用 zod 逐条复核过（**这是实测，不是推断**）：

```text
entity_created + { by: 'command' }        -> true   （passthrough，今天不炸）
entity_created + { command: 'x' }         -> true
layer_initialized + { by: 'command' }     -> false  Invalid enum value.
                                            Expected 'writer' | 'player' | 'engine', received 'command'
```

→ **`detail.by = 'command'` 是一个埋着没炸的雷**：今天不炸只因为 `recordLayerInitialized` 不在 §2.1 的 7 个效果里。**这是"靠巧合维持，不是机制保证"**。

**`detail.command` 则零碰撞**：十五个 `EventDetailSchemas` 没有一条声明 `command`，全部是**非 strict** 的 `z.object`（`events.ts:42-109`），因此额外键透传。且它**比 `by` 携带更多信息**——`command: 'investigation-clue'` 本身就表达了"这次变化来自哪条命令"，而 `by: 'command'` 是冗余的（没有命令上下文的事件根本不会带这个键）。

**逐效果落实（§2.4 表的追加列）**：

| 效果 | 落的 `detail` 追加 |
|---|---|
| `give`（`entity_created`） | `{ path, name, kind, command: '<id>' }` |
| `move`（`entity_moved`） | `{ from, to, name, rewrote, dangling, command: '<id>' }` |
| `edit` / `set_status` / `consume`（`entity_edited`） | `{ path, name, kind, command: '<id>' }` |
| `enter`（`layer_entered`） | `{ layer, name, first, command: '<id>' }` |
| `link` | **无事件**（附属），故无 detail（§2.3 E7） |

**实现口径（写给 `03`）**：`command` 必须**由执行器统一注入**，不是每个效果自己填。理由：`10` 的注入层对此是**沉默失败型依赖**——它不能报错（`docs/hooks/00 §11`），所以"某个效果忘了带 `command`"只会表现为注入段的文字变淡，没有任何测试会红。**统一注入 = 让"忘记"在结构上不可能发生。**

```ts
/** NEW. The executor stamps every event's detail — effects never do it themselves. */
function stampCommand(detail: Record<string, unknown>, commandId: string): Record<string, unknown> {
  return { ...detail, command: commandId };
}
```

### 6.6 回执形状（`10` 的输入，与 `05` 的 verb 对齐）

```ts
/** NEW — packages/shared/src/commands/receipt.ts.
 *  The per-command receipt carried in the triggering action's `details`. */
export interface WorldCommandReceipt {
  id: string;
  name: string;
  /** `05`'s four verbs. NOT a boolean — `ok` cannot express `resumed`. */
  settle: 'ran' | 'reused' | 'resumed' | 'failed';
  /** One entry per FLATTENED effect (§2.6), not per `do[]` entry. */
  effects: Array<{
    action: WorldCommandEffectName;
    ok: boolean;
    /** The REAL event, not the effect name — `10` renders each line through the
     *  existing `renderEvent` (render/events.ts:401-406) so the receipt's wording
     *  is byte-identical to the next turn's event section (doc-22 机制 9). */
    event?: WorldEvent;
    error?: string;
  }>;
}
```

**为什么回执必须给真事件对象而不是效果名**：`10` 的每一行都靠既有渲染器 `renderEvent`（`render/events.ts:401-406`）产出，从而与下一轮注入的事件段**逐字相同**（一份措辞、两处复用）。只给 `action` 名字，`10` 就得写**第二套渲染器**——那正是契约 §8 反模式 5（在旁边造并行机制）。

**`list-args` 的两条硬要求（`10` 从事件段角度提出，本文采纳为效果契约）**：

| # | 要求 | 依据 |
|---|---|---|
| 1 | 展开的**各项 MUST 各自落一条独立事件**，MUST NOT 落一条聚合事件（如 `entity_created` 带 `files: [3 项]`） | 聚合会让事件段丢 `path` 信息（`detail.path` 只有单数），而硬门 1 要求每个效果可复访 |
| 2 | 各项 MUST **连续落地**（连续 seq） | 同 turn/同 type/同 actor/同 command 时，注入的合并规则会把它们塌缩成**一句**（`The world, after the player acted, created 3 things.`）；中间插别的效果会断成两句（`render/events.ts:288-296` 的 `prev.open`）。**断句可接受，连续更好** |

**顺带一条好消息**：`list-args` **不放大注入体积**——3 项奖励合并成 1 行。所以"引擎内有界展开"对作家的可读性是**正的**。

### 6.7 每个效果 MUST 声明自己产出几条事件（写给 `03` 的预算、`05` 的粒度）

主 agent 裁定 4 要求的效果表新列。**同一个声明同时喂两条下游**：

| 效果 | 事件条数 | `03` 的读取预算（`COMMAND_EVENT_BUDGET_GUARD`） | `05` 的 `steps[].step` 粒度 |
|---|---|---|---|
| `give`（scalar-args） | **1** | 1 个名额 | 1 步 |
| `give`（**`list-args`**） | **= 数组长度（≤ 3）** | **按展开后条数算** | **每项各占一步** |
| `move` | 1 | 1 | 1 |
| `edit` / `set_status` / `consume` | 1（`fold-args` 时**仍为 1**，§2.6 契约 B） | 1 | 1 |
| `enter` | 1 | 1 | 1 |
| `link` | **0** | 0 | 1（效果占一步，但无事件） |

**这条为什么是硬约束**：`10` 实测发现 `limit` 与渲染 cap 是**同一个数**（`collect.ts:112` = `caps.dynamics` = 12）；一次命令 5 个效果**在读取层**就吃掉 12 个名额中的 5 个，下游的合并规则救不了，被挤掉的旧事实因游标已推 + 无历史工具 = **永久丢失**。**按 `do[]` 条数算预算会让 `list-args` 展开 3 项时预算失效。**

**与 stop-at-failure 的关系（`03 §5.3` / R.1）**：上表的条数是**上界**。`give`（`list-args`）在展开中途失败时，实际落地条数 **< 数组长度**（失败项及其后不执行），但 `03` 的预算仍 MUST 按**数组长度**预留——预算不足会让整条命令在阶段 A 被拒（世界零改动），预算够大才允许"部分落地"，两者不能混。

### 6.8 `give` / `append_body` 的幂等判据（`03:531` 的上游必做 / R.10）

`03:531` 逐字要求「**`04` 与 `05` MUST 为 `give` 与 `append_body` 给出幂等判据**」——否则"停在失败处 + 重跑"会二次发奖，直接踩硬门 2。本节给出这两条判据，`05` 消费它们。

| 效果 | 天然幂等？ | 判据（本文给出的形状） |
|---|---|---|
| `give`（`createEntity`） | **否** | **判据是 `05` 的 `commandKey`**（`source × hook × command × fact`，**不含 `args`**，`05:113-116`）：同 `(source, hook, fact)` 再次触发 ⇒ `command_log` 命中 ⇒ `reused`，`give` MUST NOT 被调用（产出 0 个 `EffectOutcome`）。**`already_exists` 不是幂等判据**——它只在**声明路径为静态常量**（`path:` 字面量，或 `{{ trigger.path }}` 这类不随 `fact` 变的引用）时**等价于**"这份奖已经发过"（`create.ts:98-104`）；一旦路径含 `{{ roll.result }}` / `{{ trigger.entry.rewards[*].path }}`，两次不同的 `fact` 会算出**不同的路径**，`already_exists` 永不触发（§4.1 的 ⚠️ 就是这条）。⇒ **`give` 的判据 MUST 是 `05` 层，`already_exists` 只是静态路径上的最后一道防线。** |
| `append_body` | **否**（非幂等效果的代表） | **MUST NOT 靠扫正文判重**（§3.5 硬约束 2；`origin/niko` 的 `<!-- resolved-dice:62 -->` 是契约 §8 反模式 1）。判据 = **`05` 的 `command_log` 步级回执**（`05 §5.3`/`§5.4`）：重跑时 `05` 在 **S3** 按已记录的 step 跳过"已经跑过的 `do[i]#k`"，因此 `append_body` 这个效果**根本不会被第二次调用**。⇒ **`append_body` 的判据是"它自己是确定性的 + `05` 逐步跳过"，而不是任何自带守卫。** |

**两条判据的共同形状**（写给 `05`）：**判据不住在效果里，住在 `05` 的 `commandKey` + `command_log` 步级回执里。** 这是刻意的——`05 §5.3` 的首条收益就是"**新增效果不需要自带幂等逻辑**，只要它自己是确定性的"。本文的两个非幂等效果（`give`/`append_body`）因此都对 `05` 提出同一个要求：**重跑 MUST 让跳过的步产出 `reused`/`resumed` 回执，而不是让效果再跑一次。**

## 8. 两个必须解释清楚的"表达力缺口"

### 8.1 为什么不需要 `writer` 效果

**这是本节的核心，写在这里是因为不写读者会以为表达力缺了一块。**

**区分**：命令的「效果」与命令「写下的下一步选项」是两件事。

| | 是什么 | 谁在什么时候执行 | 归属 |
|---|---|---|---|
| **效果**（`do[].action`） | 世界改写 | 命令触发时，**同步**，经动作层 | ⊆ `ACTION_METHODS`（§2.1 的 7 个） |
| **下一步选项** | 写回实体的 `choice` + `choice_actions` **数据** | 命令只负责**写数据**；玩家点击后才由现有 `runDeclaredChoice` + 前端解释 | **一次 `edit` 效果** |

`Recipe` 的 `kind: 'writer'` **不需要**成为效果。命令要做的是把

```yaml
choice_actions:
  play-result:
    kind: writer
    prompt: 判定元 world/london-map/04-investigation-dice.md を読む。…
```

**写进实体的 frontmatter**——那是一次 `edit`，完全在动作层内。玩家点了那个按钮之后，走的还是**今天那条路**：

```text
EntityInteractions.tsx:157-163  →  POST /api/choice  →  world.ts:1178 的 dispatch
```

**这不是推断，`origin/niko` 就是这么做的**：`declared-actions.ts:204-205` 逐字用一次 `editEntity` 把 `choice: {options: [...]}` 与 `choice_actions: {...}` 一起写回 source。**它没有"起作家轮"这个效果，它只是写了一组按钮。**

**残余表达力缺口（诚实登记）**：命令写回的 `choice_actions` 里，`kind: 'writer'` 的 prompt 仍然是**源语言写死在实体 frontmatter 里**的（迁移时逐字保留），命令本身不参与翻译。这与今天的行为一致，不构成回归。

### 8.2 为什么不需要 "reply / 说话" 效果

`Recipe` 的 `kind: 'reply'`（`declared-actions.ts:138-140`）是一条**给玩家看的文本**，它的执行发生在 `details.action` 被前端读取时（`EntityInteractions.tsx:181`），不是世界改写。**它同样是一次 `edit` 的产物**（写进 `choice_actions[id].text` 或实体正文）。

**如果评审认为"命令应该能直接对玩家说一句话"是必要的**，那它违反的不是能力集约束，而是契约 §1.2 的分工：「Agent 负责'雾散开一线，你看清了第二艘船的舷号'」。**引擎不叙述。** 命令能改的只有文件；叙述由作家读文件后写出。这条口径不允许为便利而破例。

### 8.3 为什么 `read` / `stage` 留在 UI 层（与 `02` 的分工确认）

`Recipe` 的 `kind: 'read'`（展示一个实体）与 `kind: 'stage'`（材料槽位预览）是**对话框的预览行为**，不是世界改写：`prepareMaterialReview` 的注释逐字写「this function never records, moves, consumes, or executes」（`declared-actions.ts:309`）。**它们留在 `choice_actions` 里当数据**，命令通过 `edit` 写它们，与 §8.1 同一条逻辑。

### 12.4 一个诚实的实现期风险

§3.5 末尾登记的那条：`append_body` 走 `editEntity` 会**整体重写 frontmatter**（`stringifyFrontmatter`，`frontmatter.ts:251-255`），因此会丢掉 YAML 键的注释与顺序。`patchRollDiceResult`（`rules/dice.ts:281`）之所以做行级外科手术，`dice.ts:273-276` 的注释逐字解释了正是为避开这件事。

**本文的判断**：对世界命令可接受（它改的是自己声明过的实体的字段），但**这是一个真实的行为差异，不是免费的**。如果实现期发现它破坏了内容作者的手写 frontmatter 排版，唯一的出路是给 `editEntity` 也做行级追加——**那会显著扩大改动面（`refs.ts` 式的偏移扫描），本文不推荐，但登记在此以便评审看到全貌。**
