### 面 2 —— `05` 的并存不冲突 × `09` 的恶意命令攻击面：命令重名会不会跨世界串扰？

**结论：一致——不会跨世界串扰。**（附**一条**两文口径矛盾的旁证，见 B2。）

**核验**：

- `09:573`（攻击面 #3「写到别人的世界」）逐字：「store 实例绑定 `worldRoot`（`local-store.ts:168`），路径解析以它为根 → **增量零**。跨世界隔离在进程/实例层，不在命令层」。
- `05` 的幂等真相源 `command_log` **写在被触发实体自己的 `.md` frontmatter 上**（`05:18,20`），即随世界文件走，天然按世界隔离。
- `05:760` 的 `withSourceLock` key 逐字为 `` `${worldRoot}\0${source}` ``——**含 `worldRoot`**，锁本身也是世界作用域的。

⇒ 命令 id 即使在世界 A 与世界 B 里同名，`command_log` 的查询、锁的键都在各自世界内闭合，**不产生跨世界串扰**。两文档的结论一致。

**但发现一条同面内的两文矛盾（B2）**：

- `09:377` 逐字：「`detail.command = '<id>'` 是**唯一**的可选附加键，不改变类型」。
- `05:303` 逐字：「**`detail.commandKey` 是本文向契约 §5.1 追加的一个可选 detail 键**」，并在 `05 §4.3` 用它把审计从"哪个命令干的"精确到"哪一次运行干的"。

`09` 声称 `detail.command` 是唯一可选附加键，`05` 却追加了第二个。两文对**可选 detail 键的封闭性**给了矛盾口径。`09` 全文 `grep commandKey` 零命中 ⇒ `09` 不知道 `05` 的追加。

**建议**：`09 §5.1` 的「唯一」改为「除 `05` 追加的 `detail.commandKey` 外，`detail.command` 是唯一的归属键」；或若评审否决 `commandKey`，则由 `05` 删除。**不建议两文都保留现状**——这是一个对"detail 面封闭性"的权威声明，不能有两套。

### 面 5 —— `09` 的 `[C-4]` 三态开关 × `05` 的中断恢复：`dry-run` 下 `command_log` 写不写？

**结论：矛盾（B1）——`09` 明确说写（并因此污染恢复语义），`05` 从未提及 `dry-run`，且其 `command_log` 形状无法容纳一个"未执行"的运行。**

**`09` 的原文**（`09:249`）逐字：

> `dry-run` | **完整跑解析 → 求值 → 静态核算 → 构造效果计划，但不应用。** **计划写进 `command_log` / `details`**

**`05` 的原文**：
- `05 §1`（`:11`）：「**幂等真相源是被触发实体自己 `.md` frontmatter 上的 `command_log`**；事件表只做审计，永远不被查询来决定"要不要执行"。」
- `05 §5.1`：S1 读 `command_log`；**S3 是核心判定**（`:388-396`）——同 key 记录 `status: done` → `reused`；`status: partial` → 续跑（S5）；不存在 → 首跑（S4）。
- `05 §2.1` 的 `CommandLogEntrySchema`（`:690-700`）：`status` 是**闭枚举 `['partial','done']`**，`steps` 必填、`key` 必填、`plan` 必填。
- `05` 全文 **`grep dry-run` 零命中**——`05` 完全不知道 `[C-4]` 有 `dry-run` 这一态。

**矛盾链条（按字面实现即触发）**：

1. `dry-run` 下，某次触发把"计划"写进 `command_log`。
2. 计划里**没有真实效果**（`09:249` 逐字"不应用"），因此没有 step 回执。
3. 该条目要么取 `status: done`（凭空声称成功），要么取 `status: partial`（声称"跑了一半"）。`05` 的枚举**没有第三个值**能表达"这是计划、不是运行"。
4. 玩家把开关切回 `on`，真实触发同 `(source, hook, command, fact)` → **同 key 命中**（`05 §3.1` 的 key 不含 `args`/命令内容，见 `05:120`）→ S3 判为 `reused`（`done`）或续跑（`partial`）→ **真实效果永不落地**。

这与 `05` 存在的理由——硬门 2「不重复结算」的反面——**完全同构**：不是重复发奖，而是**该发的奖被一次 dry-run 永久吃掉**。且玩家看不到任何错误（`dry-run` 的"计划"看上去就是一条正常回执）。

**`09` 自身的第二处内部张力**：`command_log` 写在**被触发实体的 `.md` frontmatter** 上（`05:18`）。因此"计划写进 `command_log`"= **对世界文件的写**，与同一格里的「**但不应用**」字面冲突。`dry-run` 按 `09:256` 的设计意图是"plan-then-apply / 只读"，但这一句把它变成了"会写世界"。

**给两方的建议（择一，MUST 在拍板 `[C-4]` 时一并冻结）**：

- **方案甲（推荐，代价最小）**：`dry-run` **MUST NOT 写 `command_log`**。计划**只进 `details`**（这正是 `09 §10.1` 的验收断言实际读取的地方——它断的是 `details.commands[0]`，不是 `command_log`）。`09:249` 删去「计划写进 `command_log` /」，改为「计划写进 `details`，不触碰任何世界文件」。
- **方案乙**：`05` 的 `CommandLogEntry` 新增一个 `status: 'planned'`，并**显式规定 S3 对 `planned` 条目的处理**（必须视为"未跑过"，可被真实运行覆盖）。同时 `09:249` 改为"计划写进 `command_log`（`status: planned`）"。注意这会扩大 `05` 的闭枚举，且需在 `05 §5.1` 的 S3 分流表里加一行。

无论哪种，**两文必须同时改**——现状（`09` 说写、`05` 说它是唯一判据且形状不容纳）不能并存。
