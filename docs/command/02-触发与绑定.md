## 1. 一句话定位

**世界命令不会自己发生。** 本文定义世界里的一个实体如何用 `.md` frontmatter 的 `on` 键，把「某个动作在我身上落成事实」这件事，绑定到一个或多个 `command/<id>.yaml` 上；以及动作层在哪些精确位置读取这份绑定、把什么变量交给命令、绑歪了谁在什么时候会看见。

一句话的设计约束：

> **命令只能挂在已经落账的事实之后，挂在这条事实的 `subject` 身上，且命令内部触发的动作不再触发命令。**

## 2. 完整 schema

### 2.1 `on` 的整体形状

`on` 是**被触发实体**（chalk / note / component / README …）**Markdown frontmatter** 的顶层键。契约 §3.3 已把它冻结给本模块，契约变更**没有动它**（变迁通知逐字：「实体侧不变：`on` / `command_log` / `command_error` 仍在 `.md` frontmatter 上」）。

```yaml
on:
  <hook>:                 # 三个封闭 hook 名之一
    - <binding>
    - <binding>
```

```yaml
# <binding>
when: "<表达式>"           # 可选；缺省 = 无条件触发
run: <command-id>         # 必填；指向 command/<command-id>.yaml
with:                     # 可选；实参表，值只能是标量或 {{ }} 模板
  <param>: <标量 | "{{ 变量 }}">
on_error: stop            # 可选；stop（默认） | continue
```

### 2.2 hook 名：封闭三项，规则只有一条

**规则：hook 名 == 触发它的那个动作所追加的世界事件类型名。**

这一条规则同时定死了三件事：命名、插入点、以及未来怎么扩展。

| hook | 动作 | 事件类型（`packages/shared/src/schemas/events.ts:9-25`） | 承载 `on` 的实体 |
|---|---|---|---|
| `roll_resolved` | `rollDice` | `roll_resolved` | 掷骰实体（`input.path`） |
| `choice_selected` | `chooseOption` | `choice_selected` | 选项实体（`input.path`） |
| `use_item_on` | `useItemOn` | `use_item_on` | **被作用的目标**（`input.target`） |

**为什么是事件类型名，而不是玩法词（`roll` / `choice` / `use`）**：

1. 它把「不新增事件类型」（契约 §5.2）这条纪律自动传导到触发点上。想加第四个 hook？先得有第十六个事件类型，而那扇门是关着的。这比在本文里写「不要随便加 hook」有效得多。
2. 它让插入点不需要第二条规则：hook `X` 的插入点就是 `appendEvent({type:'X'})` 成功返回之后。
3. 它对作者诚实：`on.roll_resolved` 读作「骰子被判定之后」，而不是「掷骰的时候」。后者会让人以为能改骰子结果——那是硬门 3 明令禁止的。

**为什么不是 `on.roll_dice` / `on.choice`（即互动块名）**：`use_item_on` 的目标实体身上根本没有对应的互动块（`accepts` 在运行时不被消费，见 §12 第 5 行），那样就得写两条规则。一条规则打败两条。

`[待拍板 T-1]` hook 命名是措辞选择，评审可推翻。推翻的代价是本节三条理由全部失效，且 §3 的插入点规则要另写。

### 2.3 `on.<hook>` 的值：恒为数组

`on.<hook>` **MUST 是 YAML 序列**，即使只有一条也要写成列表。**不提供标量简写、不提供 mapping 形式。**

- **不给标量简写**（`on: { roll_resolved: my-command }`）：省下的一行换来两种形状要解析、两套错误文案、Agent 要学两种写法。不值。
- **不给 mapping 形式**（`on: { roll_resolved: { back: cmd-a, lantern: cmd-b } }`，即 `choice_actions` 的形状）：YAML mapping 的键顺序不是契约，而**执行顺序必须是确定的**（§3 步骤 9）。

> **这是硬要求，不是风格偏好，且它在两个地方被依赖。**
>
> 1. **`05` 的 `command_log` 用绑定下标做步索引。** `commandKey = sha256(source, hook, command, fact)`（`05` 定稿）不含位置信息，所以 `resume` 靠 `on.<hook>[<binding>]` 定位要补的那一条。**顺序漂移 = 补错步。** `05` 有 `command_resume_drifted` 兜底，但那是最后一道。
> 2. **`do[]` 与绑定下标的对应**：`command_log` 的 `steps[].step` 下标 = `do[]` 下标。
>
> 因此：**一次 `fresh` 运行与一次 `resume` 运行之间，实体的 `on.<hook>` 数组顺序 MUST NOT 改变。** 这不是靠约定，是靠两条：
>
> - YAML 序列的顺序是**语法**保证的（这正是拒绝 mapping 形式的根本原因——`choice_actions` 用 mapping，`apps/server/src/engine/declared-actions.ts:266-268`（旧标 `:258-260`，**快照已漂移**），它做不到「同一选项触发两个命令」和「两个选项触发同一命令」）；
> - 解析器 `parseOnBindings` **MUST NOT 排序、去重或重排**绑定数组。它只做校验与类型归一。
>
> **中间插入一条绑定会移动它后面所有绑定的下标**——这是作者可见的、需要 `command_log` 配合处理的变化。`[给 05]` 检测这种漂移是 `command_resume_drifted` 的职责，本文只保证「你读到的下标就是声明那份文件的顺序」。

**`from` 是主 agent 2026-09-14 裁定 A 的落地**：`{{ }}` **禁止嵌套**，数组条目在**绑定时**解析，不在插值里解析。`from` 声明「这条绑定从哪个 frontmatter 数组里选条目」；选中的条目以扁平内建根 `trigger.entry.*` 暴露给命令（§2.5）。

**`from` 是可选的（契约 §R.20）。** 不写 `from` 的绑定完全合法——它只是**没有 entry**，`trigger.entry.*` 对它不可用。这类绑定靠 `with` 传标量、靠 `trigger.fm.*` 读内容，`§15.2`/`§15.3` 两个例子都属于这一类。

> **不写 `from` 却引用 `trigger.entry.*` → 专用码 `on_entry_not_bound`**（**不是** `on_from_missing_key`——后者是「`from` 指向的 key 不存在」，两回事）。写入时静态可查：`parseOnBindings` 扫该绑定的 `when` 与 `with` 里的 `{{ }}`，命中 `trigger.entry` 根名而该绑定无 `from` 即报错。

#### `from` 的 entry 选中规则（契约 §R.19，冻结）

**`on.<hook>` 的第 `i` 条绑定，取 `from` 所指数组的第 `i` 项。一对一，按下标对齐。**

```text
on.<hook>[0].from = dice_outcomes   →  trigger.entry = dice_outcomes[0]
on.<hook>[1].from = dice_outcomes   →  trigger.entry = dice_outcomes[1]
on.<hook>[2].from = dice_outcomes   →  trigger.entry = dice_outcomes[2]
```

**因此 `on.<hook>` 的长度与 `from` 数组的长度 MUST 相等**（对所有声明了 `from` 的绑定而言）。越界 → 专用码 **`on_entry_unavailable`**（**不是** `entry_index_out_of_range`）。

**为什么是下标对齐而不是「`when` 匹配到哪项就取哪项」**：后者要求求值器先把数组整个扫一遍去找匹配项，那是**动态选择**，上界不可静态界定（`09` 的资源上限论证会塌）。下标对齐是**纯静态**的：读一眼 `on` 就知道第 `i` 条绑定读第 `i` 项，写入时就能校验长度是否相等。这与裁定 A 拒绝「下标里嵌 `{{ }}`」是同一条理由的延伸。

**代价，诚实写出来**：作者**不能**只为四档里的第 3 档写一条绑定——要么四条都写（其余三条用 `when` 挡掉），要么把数组本身改短。`§15.1` 的四条绑定各自 `from: dice_outcomes` 且数组恰好 4 项，就是这条规则的样子。

**`when` 与 `from` 的分工**：`when` 决定**这条绑定要不要跑**，`from` 决定**跑的时候 entry 是哪一项**（= 本绑定的下标）。两者正交：`when` 为假时该绑定 `skipped`，**不消费**它那一项，也不会让后续绑定的下标平移。

**为什么 `from` 属于绑定而不是命令**：同一个命令文件被多个档位共享（§15.1），「读哪张表」是**这次触发**的属性，不是命令的属性。命令只知道 `trigger.entry` 是一个对象，不知道它来自哪里。

#### `from` 的引用完整性（`07` 与本文共同负责）

**`from` 是一个跨字段引用，不是一个自由字符串。** 它指向的 key MUST 在**同一实体的 frontmatter 里真实存在且是数组**。写作 `from: dice_outcome`（少个 `s`）在 passthrough 下**静默保留**（§14.6），后果是 `trigger.entry` 解析不到数组 → **整个档位的奖励凭空消失**，没有任何一处报错。

**校验必须发生在两处，缺一不可**：

| 层 | 谁 | 错误码 |
|---|---|---|
| 写入时（`extensions/world-context.ts:50-56` 的 `tool_call` 接线） | **`02` 实现的 `parseOnBindings`**（本文 §11.1 拥有），由 **`07` 在写入时调用** | §10.1 的 `on_from_missing_key` / `on_from_not_a_list` / `on_from_empty_list` / `on_entry_unavailable` / `on_entry_not_bound` |
| 触发时（§3 步骤 4） | 本文 | 与写入时**同名同码**（§10.2） |

**MUST 共用同一套错误码**，理由与 §2.4 的 `parseOnBindings` 共用实现同源：同一份错误在两个层的文案不同，会让 Agent 在写入时学到的修正方法在触发时对不上号。

**这条校验是纯同步、纯静态的**——它只在**同一份已解析的 frontmatter 对象内查 key**，不引入任何 I/O。所以它满足 `07` 的硬需求（`parseWorldCommand` 无 I/O），两者可以共用同一个纯函数。

> **归属冻结（契约 §R.16 + 主 agent 2026-09-14 补充裁定）**：`parseOnBindings` **由 `02` 拥有并实现**（`packages/shared/src/commands/bindings.ts`），**`07` 是调用方**。判据：它解析的是**实体上的 `on`**（`02` 是 `on` 形状的拥有者），且五个校验点里有三条的语义只有 `02` 能定义（hook 名、区间语法、`from` 的一对一绑定下标 = §R.19）。**`07` 定的是"何时调用"与"怎么回错误"，不是实现。**
>
> ⚠️ **本批次第四次「同一件事被两处用不同口径描述」**（契约附录 S.2）：`07:81` 曾用 `export function parseOnBindings(...)` 自称实现方，而本文 `:140` 又写「`07` 的」——**双向认领**。已按上述裁定统一。

**`parseOnBindings` 的 `from` 校验清单（五条，全部写入时可查）**：

1. key 存在 → 否则 `on_from_missing_key`；
2. 值是数组 → 否则 `on_from_not_a_list`；
3. 数组非空 → 否则 `on_from_empty_list`；
4. **数组长度 ≥ 声明了该 `from` 的绑定的最大下标 + 1**（契约 §R.19 的一对一）→ 否则 `on_entry_unavailable`；
5. 未声明 `from` 的绑定不得引用 `trigger.entry.*` → 否则 `on_entry_not_bound`。

> **第 4 条就是数组长度上限的落点（契约 B-4）。** 上界**不是**「由实体 frontmatter 的 schema 上限封死」——`on` 住在 passthrough 的 `.md` 上，没有 schema 在保护它（§14.6）。**上界由 `parseOnBindings` 在写入时校验**，这是唯一真正执行的地方。`09` 的资源上限论证 MUST 引用这一条，而不是引用一个不存在的 schema 上限。

**`with` 的值有三类**（主 agent 裁定 A + 「方向三」）：

1. **标量**（string / number / boolean / null）。
2. **一个求值为标量的 `{{ }}` 模板**。
3. **一个静态路径，求值出一个数组**——术语是 `list-args`（逐项迭代，效果数 = 数组长度）与 `fold-args`（折叠成一个 map，效果数恒为 1）。**由 `04` 的效果表声明每个效果接受哪一类**，`01` 的 schema 留声明位并在写入时校验形态匹配。

**`with` 仍然不是内容容器的理由**（拍板 B2）：规则住 `command/*.yaml`（1 份，N 个实体共享），内容仍住实体自己的 frontmatter。若 `with` 能装下整块内容，实体的 `on` 就会和原来的 `dice_outcomes` 一样大——那不叫迁移，叫改名。

**第 3 类的两条边界**（裁定「方向三」，两条都是硬性的）：

- **只允许来自 `{{ trigger.entry.* }}` 或 `{{ trigger.fm.* }}` 的静态路径**。**MUST NOT 内联字面量数组**——字面量数组是内容，内容住实体。
- **数组长度必须在执行前静态可知**（`rewards` ≤ 3 由实体 frontmatter 的 schema 上限封死）。这是 `09` 的资源上限论证依赖的性质，不是实现细节。

**`list-args` 与 `fold-args` 的实现差异**（`05` 已按这个区分设计 step 粒度，`04` 必须遵守）：

| | `list-args` | `fold-args` |
|---|---|---|
| 效果数 | = 数组长度（≤ 3） | 恒为 1 |
| `05` 的 step 回执 | **每项各占一个 step**（可续跑到「第 2 项做完、第 3 项没做」） | **只占一个 step**（只有做完/没做完） |
| 失败粒度 | 逐项独立；第 2 项失败不回滚第 1 项 | 整体成功或整体失败 |
| 例 | `give: "{{ trigger.entry.rewards }}"` | `options → choice + choice_actions` |

**`with` 里的 `{{ }}` 与命令文件里的 `{{ }}` 同形但作用域不同**（`01` 拥有语法，本文拥有变量集）：

| 出现位置 | `{{ x }}` 解析成什么 |
|---|---|
| `command/<id>.yaml` 的 `params` / `do` 内 | 该命令自己的 `params` 的实参 + `01` 的保留根命名空间 |
| 被触发实体的 `on.<hook>[].with` 内 | **触发上下文变量**（§2.5 的封闭表） |

YAML 陷阱（`CmdSchema` 开工播报 (b)）：**以 `{{` 开头的标量 MUST 加引号**（`{` 是 YAML flow-map 起始）。错误文案：`Binding <n>: a value starting with "{{" must be quoted in YAML — write "{{ roll.result }}", not {{ roll.result }}.`

`on_error` 默认 `stop` 而非 `continue`：与 `evalWhen` 的 fail-closed（`packages/shared/src/rules/interactive.ts:70-72` 逐字「Anything else … is malformed → fail-closed」）和 `parseExpect` 的取向一致。半套后果比没有后果更难收拾。

### 2.5 触发上下文：命令能看到什么

**规则：一个 hook 暴露的变量 == 该动作 `ActionResult.details` 里的标量键（命名空间化）+ 六个通用变量 + 两个读取通道（`trigger.entry.*` / `trigger.fm.*`）。**

**其中 `trigger.entry.*` 是唯一"可选"的成员**（契约 §R.24）：它**只在本绑定声明了 `from` 时存在**。未声明 `from` 的绑定引用它 → `on_entry_not_bound`（§2.4）。其余变量对该 hook 恒存在。

**命名空间与保留根名已与 `01` 对齐**（`CmdSchema` 定稿口径 + 裁定 A）：`trigger` / `roll` / `choice` / `item` / `entry` 是保留根名，`params` 声明的名字 MUST NOT 与之冲突。

## 3. 行为契约逐步

触发层收在一个函数里：

```ts
/** NEW — packages/shared/src/commands/trigger.ts
 *  契约：NEVER THROWS（步骤 12）。 */
export async function settleWorldCommands(
  ctx: ActionContext,
  args: {
    /** 承载 `on` 的实体路径 == 该事件的 subject。 */

    /** 触发事实。`fresh` 由动作自己算；`resume` 由 05 的 command_log 快照回放。 */
    facts: Readonly<Record<string, string | number | boolean | null>>;
    /** 调用方已解析好的 frontmatter（步骤 3）。 */
    frontmatter: Record<string, any>;
    mode: CommandTriggerMode;
  }

```

每一步都写清「**漏了会怎样**」——这是本文的验收面。

### 步骤 1 — 动作先把自己的事做完（`fresh`）

`fresh` 的调用点在 `appendEvent` **成功返回之后**、`return` 之前。

**漏了会怎样**：命令基于一条还没落盘、可能失败的事实执行。`roll-dice.ts:211-215` 写盘失败会 `fail('write_failed')`，`:238-243` 落账失败会 `fail('event_failed')`；把触发点放在这两步之前，就会出现「奖励发了，但骰子结果没写进文件」的世界——硬门 1（文件即真相）直接破。

### 步骤 1b — `resume`（仅 `rollDice`，采纳 `05` 的提案）

`rollDice` 的步骤 6 重掷门在 `declared.result !== undefined` 时**直接失败**（`roll-dice.ts:149-155`），根本走不到步骤 1。后果：第一次掷骰后命令执行到一半进程挂了（效果 1 成功、效果 2 没跑），此后**任何重试**都在步骤 6 被拒，半成品永久卡死。

**因此 `rollDice` 有第二个调用位**：在 `:152` 之后、`:153` 的 `if` **之前**，以 `mode: 'resume'` 调用：

- `resume` 只补做 `command_log` 里标记未完成的步；log 全为 `done` 时是**纯 no-op、零额外 I/O**（`parsed` 与 `declared` 在 `:124-147` 已经在手里）。
- 补完之后**照常抛 `dice_already_rolled`**，只是 message 追加「顺带补完了 N 个未落地的效果」。
- 不重掷（硬门 3 保住）、不重复结算（硬门 2 保住）、不静默（硬门 4 保住）、无后台任务（契约 §4.3 保住）。

**已知代价，认账不掩饰**：`rollDice` 因此出现一条「**以错误结束，但世界发生了变化**」的路径。`ActionError` 本来就带 `details`（`packages/shared/src/actions/errors.ts:52-57`（旧标 `:50-55`，**快照已漂移**）），`resume` 的 outcomes 随 409 一起回给前端。**这条必须让 `06` 知道。**

`chooseOption` / `useItemOn` **没有**等价的重掷门，位置 A 就够，不需要步骤 1b。

### 步骤 2 — 重入门

```ts
if ((ctx.commandDepth ?? 0) > 0) return undefined;
```

在读取任何 frontmatter **之前**。

**漏了会怎样**：`do` 里调 `chooseOption`，而目标实体自己绑着 `on.choice_selected` → 无限递归。同步执行（契约 §4.3）且 `ActionContext` 逐字没有 `AbortSignal`（`types.ts:8`「No AbortSignal, no progress channel」），这个循环**没有任何东西能停下它**，会一直写文件直到进程崩。完整机制见 §11.4。

> 返回 `undefined` 而不是 `[]`：被跳过的重入不该在外层 details 里冒充「有绑定但全跳过」。重入的可见性由**内层**负责——`runWorldCommand` 在调用动作时就知道自己是深度 1，由 `03` 在 `CommandEffectOutcome` 上标注。

### 步骤 3 — 取 `on`，不重读文件

`settleWorldCommands` 接收调用方**已经解析好的** frontmatter：`roll-dice.ts:124` 的 `parsed.frontmatter`、`choose.ts:86` 的 `fm`、`use-item.ts:205` 的 `targetRef.frontmatter`。

**为什么复用是安全的**（三条都要成立，否则 MUST 改成重读）：

1. `rollDice` 在 `:212` 只做了外科式回写——`patchRollDiceResult` 逐字承诺「Rewrite ONLY the `result` / `passed` lines inside the `roll_dice:` block — every other byte of the file is preserved verbatim」（`packages/shared/src/rules/dice.ts:268-272`）。`on` 不可能被它改到。
2. `chooseOption` 完全不写文件（`choose.ts:41-46` 逐字「never writes a file」）。
3. `useItemOn` 的 handler **会**改写目标（`components/core.ts:32-50`），但只碰 `status.data`（`:54-67,73-88`）。本期的变量表不含 `status.*`（§2.5），`on` 本身不受影响。

**漏了会怎样**：多一次 `readFile` + `parseFrontmatter`，在最热的玩家路径上，换来零信息。反过来，若 `03` 扩展变量表却忘了改这里，命令会基于 handler 执行**之前**的状态分支——一个安静的、只在 lock/container 上复现的错判。

无 `on` 或无 `on[hook]` → 返回 `undefined`。

### 步骤 4 — 解析绑定

`parseOnBindings(frontmatter, hook)`（纯函数，无 I/O，§11.1）。语法错 → 返回**一条** `status:'error', code:'on_malformed'` 的 outcome，不继续执行任何绑定。

**漏了会怎样**：这是 `dice_outcomes` 事故的原样复现。`parseFrontmatter` 对未知键是 passthrough 保留（`packages/shared/src/schemas/frontmatter.ts:137-146` 的两个 `.passthrough()` intersection，`:150-166` 逐字「NO schema filtering」）——写坏的 `on` **不会报错**，只会不执行。36 个文件就是这么活下来的（契约 §1.3）。

> **这次契约变更改变了什么、没改变什么。** 变更让**命令文件**（`command/*.yaml`）走 strict schema，机制上离开了 passthrough。但 **`on` 仍然活在实体的 `.md` frontmatter 上，仍然在 passthrough 里。** 所以对 `on` 而言，写入时校验（`07` 接线 `parseOnBindings`）+ 触发时这条二次防线，是**唯一**挡在 `dice_outcomes` 式静默之前的东西。§14.6 展开。

### 步骤 5 — 逐条求值 `when`

求值器归 `03`；**语法解析器由本文导出**（`01` 要求在写入时校验命令自己的 `do[].when`，需要一个纯同步函数直接 import，`CmdSchema` 定稿口径）。

触发层只负责：

- `when` 缺省 → 视为真。
- 求值为假 → `status:'skipped', skipped:'when_false'`。**不是失败，不触发 `on_error`。**
- 语法坏 → **fail-closed 跳过，但带 `code:'when_malformed'` 与 message**。

**漏了会怎样**：第三条最容易被做成静默。现有 `buildChoice` 已经踩过并改对了——`interactive.ts:258-260` 对 malformed `when` 既 fail-closed **又** `note()` 一条人话错误。触发层照抄这个取向。不照抄的后果是作者把 `roll.result in 1..12` 写成 `roll.result in 1-12`，卡片永远不出现，而没有任何一处告诉他为什么。

### 步骤 5b — `resume` 的事实可用性

`resume` 的 `facts` MUST 来自 `05` 在 `fresh` 运行时写进 `command_log` 的事实快照。若快照不存在（首次运行在写快照之前就崩了），`resume` 只有 `result`/`passed`（文件里有），**没有** `crit`/`fumble`/`forged`（§2.5 的说明）。

任何 `when` 引用了不可用变量 → `status:'error', code:'facts_unavailable'`，message 逐字点名缺哪个变量。

**漏了会怎样**：把 `crit` 当 `false` 处理，于是「大成功」的奖励**永远补不上**，而玩家和模型都以为补完了。这是硬门 4 的典型违反形态：失败被伪装成成功。

`[给 05]` `command_log` MUST 携带 `fresh` 运行的事实快照。这条不是可选项——没有它，`resume` 对任何依赖 `roll.crit` 的绑定都不可信。

### 步骤 6 — 解析 `run`

读 `command/<id>.yaml`（契约 §3.2 变更后是 YAML，不是 Markdown）。缺失 → `code:'command_not_found'`；解析失败（`01` 的 `parseWorldCommand`）→ `code:'command_malformed'`。两者都按该条绑定的 `on_error` 决定停/继续。

**漏了会怎样**：硬门 4。见 §7 对「什么时候发现」的完整回答。

### 步骤 7 — 绑定实参

对 `with` 的每个值做 `{{ }}` 替换，变量表 = §2.5 该 hook 的封闭表（含 `trigger.fm.<path>` 的求值）。未知变量 / 缺必填参数 / 类型不符 / 保留根名 → `code:'param_invalid'`。

**漏了会怎样**：`{{ roll.reslut }}` 拼错，或 `{{ trigger.entry.rewards[0].pth }}` 拼错（`[0]` 是静态字面量，路径末段写错）。若把解析不到的值替换成空串，命令会拿到 `path: ""` 照常执行，发一份路径为空的奖励并报一个更难懂的错。这是**比不执行更坏**的失败形态：世界被改了，但改错了，而且错误发生在离原因很远的地方。所以 `param_invalid` 的 message MUST 回显**那条原始路径**。

### 步骤 7b — 幂等判定（`05` 拥有机制，本文负责它在序列里的**位置**）

`05` 的定稿公式逐字（`CmdIdempotent` 定稿广播）：

```
commandKey = sha256(source, hook, command, fact).slice(0, 16)
```

**四个分量，没有第五个。** `source` = 被触发实体路径；`fact` = 已经结算下来的世界事实（roll 用 `roll_dice.result`；choice 用 1-based index + choice；use_item 用 item 路径 + 其内容 sha256）。

触发层对该公式有三条**实现期 MUST**，全部与本文的序列位置有关：

1. **`commandKey` MUST 在步骤 7 之前算出来，MUST NOT 依赖 `with` 的求值结果。**
   `05` 刻意把 `args` 排除在 key 之外，理由是本文（以及拍板 B2）引入的一条真实的不稳定通道：**内容住实体、命令用 `trigger.fm.*` 读回，而命令的效果会写回那个实体**（`edit` 写 `choice`/`choice_actions`、`append_body` 追正文）。若 `args` 进 key，第一次运行算 `key_A` 并落账，然后改写字段；第二次触发解析出 `key_B` → 日志无此 key → 判定「没跑过」→ **再结算一次**。
   → **判据**：如果实现里**必须**求值 `with:` 才能算出 key，说明公式被改坏了。步骤 7 的求值只为**执行**服务，不为**身份**服务。

2. **`actor` MUST NOT 进 key**（`05` 已定）。触发层必须**原样**把 key 算法交给 `05`，不能因为「同一个命令被作家和玩家各触发一次」就顺手加个 actor 维度——那正是 T3 那条重复发奖链的另一半。

3. **`plan`（命令 `do` 的规范化摘要）MUST NOT 参与判定**，只作溯源。`05` 已把它的签名放在 `CommandLogEntry` 而不是 `CommandKeyInput` 里。触发层**不计算**它。

**判定结果与本文序列的关系**：

| `05` 的判定 | 本文 `CommandOutcome` | 行为 |
|---|---|---|
| key 已在 `command_log` 且 `done` | `status:'skipped', skipped:'already_done'` | **不执行**，不触发 `on_error` |
| key 已在且未完成（`mode: 'fresh'`） | `status:'error', code:'internal'`（或 `05` 的专用码） | 提示需要一次 `resume`；MUST NOT 从头重跑 |
| key 不在 | 正常执行 | — |

**`SettleReport`（`05` 的形状：`{ran, reused, resumed, failed?}`）MUST 出现在 `details` 里**——它是触发者同轮唯一能看见「这次到底真的跑了，还是复用了既有结果」的通路（§3 步骤 10）。

**漏了会怎样**：`already_done` 被做成 `status:'ok'`，于是玩家/模型看到一个「成功」的回执，却分不清**这次真的发了奖**还是**复用了上次的**。两者都需要，但混在一起就是在回执里撒谎。

### 步骤 8 — 交给 `03`，深度 +1

```ts
const child: ActionContext = { ...ctx, commandDepth: (ctx.commandDepth ?? 0) + 1 };
const outcome = await runWorldCommand(child, spec, args);   // 签名归 03；效果表归 04 §9.1
```

`{ ...ctx, <override> }` 不是新发明：`writeNookNote` 已经这么调 `writeChalk`（`packages/shared/src/actions/nook-note.ts:104` 的 `writeChalk({ ...ctx, nookNote: true }, …)`）。

**漏了 `commandDepth + 1` 会怎样**：步骤 2 的门永远是 0，等于没有门。递归止只有这一处写入点，它是整个机制的**单点**。

### 步骤 9 — 汇总与短路

按声明顺序**串行**执行。某条 `status:'error'` 且其 `on_error === 'stop'` → 后续绑定全部记为 `status:'skipped', skipped:'short_circuit'`，**不执行**。

**已经执行的不回滚。** 理由**不是**「动作层没有回滚原语」——那条论据已过期：`snapshotWorld` / `rollbackWorld` **已经注册**（`packages/shared/src/actions/world.ts:248-249`）。

替代理由有两条，都比原论据强：

1. **粒度完全不匹配。** `rollbackWorld` 是**整世界**从快照 zip 还原（`actions/world.ts` 的 `restoreEntries` / `removed` 语义），不是「撤销刚才那一个效果」。用它回滚一条半途失败的绑定，会把**这次掷骰本身**（`roll_dice.result`）连同其他 actor 的并发改动一起抹掉——硬门 3（不篡改已结算事实）直接破。
2. **回滚也擦不掉历史。** 事件表 append-only，`docs/doc-21:256-259` 明确「回滚也不删事件」，`rollbackWorld` 自己还会再落一条 `world_rolled_back`。所以「回滚」在这里既不能让世界回到从前，也不能让日志回到从前。

**因此触发层不回滚，而是把「哪几条跑了、哪几条没跑」如实写进 `commands[]`**（§3 步骤 10）。假装能回滚才是骗人。

**漏了会怎样**：默默继续执行后续绑定 = 玩家拿到半套后果且不知道少了哪一半；把短路做成静默跳过 = 同一个问题换个位置。所以被短路的条目**也要出现在 `commands[]` 里**，带 `skipped:'short_circuit'`。

### 步骤 10 — 失败可见（两条通道，缺一不可）

1. **同轮、同步、进 `details`**：`ActionResult.details.commands = outcomes`。
2. **玩家可见 / 可复访**：任一 `status:'error'` → 把摘要写进**被触发实体**的 `command_error` 顶层键（契约 §3.3 已把该键分给 `05` + `06`；**本文 MUST NOT 定义它的形状**，只主张「触发层是它的一个写入者」）。

**通道 1 不是「顺手」的，它是作家 Agent 唯一能看见后果的通道。** 实测确认（主 agent 2026-09-14）：

- 作家注入的事件查询**必然排除 actor == 自己**的事件——`packages/shared/src/inject/collect.ts:250-252` 传 `excludeActor: actor`，`local-store.ts:837-840`（旧标 `:745-748`，**快照已漂移**） 逐字 `NOT (actor_type = ? AND COALESCE(actor_id, '') = ?)`。
- 而契约 §5.1 冻结了「命令事件的 actor = 触发者」。所以**作家调 `roll_dice` 触发命令后，命令产生的事件在它自己下一轮的注入里被过滤掉，它根本看不见。**
- 后果链条：看不见 → 以为没人发奖 → 自己再 `write` 一份 → **重复发奖**。

actor 口径 MUST 保留（改成 `engine` 会让世界史变成「引擎自己拿走了东西」，违反 `doc-21 §3.2` 把 `god` 从 `player` 单列的同一条理由）。**正确的修法是让后果走 `tool_result`**：`extensions/toolkit/roll-dice.ts:49-50` 是 `return ok(result as { text: string; details: RollDiceDetails })`——`details` **原样**回到触发它的 Agent 手里，同一轮、同步。

**漏了会怎样**：硬门 4 逐字写着「`console.warn` 不算」。只做通道 1 不做通道 2 的话，玩家刷新页面后错误就蒸发了——世界里没留下任何痕迹，而奖励确实没发。只做通道 2 不做通道 1 的话，作家 Agent 在下一轮**结构性地看不见**它自己造成的后果。

### 步骤 11 — 命令 MUST NOT 改写触发它的那条事实

命令的 `do` 里若出现 `edit` 改 `trigger.path` 的 `roll_dice.result` / `roll_dice.passed`，就是硬门 3（不篡改已结算事实）。触发层无法拦住它——`editEntity` 的浅合并（`packages/shared/src/actions/delete.ts:170-221`）对任意键一视同仁。

**执行点在 `04`**（效果原语的键白名单）。本文登记为对 `04` 的硬性要求，并给出判据：删掉 `result` 就能制造免费重掷——因为 `roll-dice.ts:151-155` 的重掷门禁**唯一依据**就是 `declared.result` 是否存在。

### 步骤 12 — 永不抛出

`settleWorldCommands` 的函数级契约是 **NEVER THROWS**。catch-all 把任何逃逸异常转成 `status:'error', code:'internal'`。

这条**与动作层其余部分的取向相反**（其余部分用 `ActionError` 作为唯一失败通道，`packages/shared/src/actions/errors.ts:44-50`（旧标 `:42-48`，**快照已漂移**）），所以需要单独论证。触发点在 `appendEvent` 之后，此刻**骰子已经掷了、结果已经写进文件、事件已经落账**。若抛出：

- HTTP 返回非 2xx，前端 `DiceRoller`（`apps/web/src/components/narrative/DiceRoller.tsx:87-93`（旧标 `:58-68` → 更早 `:66-78`，**两次漂移**））校验 `rawObj?.ok !== true` 失败，玩家看到失败提示；
- 但文件里 `result` 已经存在，**再点一次会被 `dice_already_rolled` 挡死**（`roll-dice.ts:153-155`）；
- 玩家既拿不到结果，也拿不到重来的机会 = **死局**。硬门 7（关掉仍可玩）直接破。

**因此：触发层的失败 MUST 降级为「动作成功 + 回执带错」，MUST NOT 升级为动作失败。**

> 与 `03` 的边界：`03` 决定**一个命令内部** N 个效果失败了算不算整条命令失败；本文只决定**命令失败了要不要让动作失败**——不要。
>
> 唯一的例外是步骤 1b 的 `resume`：它有意识地在**抛出之前**补完未落地的效果，且抛出的是**既有**的 `dice_already_rolled`。这不违反本条——本条禁的是「让一条本来会成功的动作变失败」。

### 4.1 触发层自己读/写什么

| 操作 | 路径 | 时机 |
|---|---|---|
| 读 | 无（复用调用方已解析的 frontmatter，§3 步骤 3） | — |
| 读 | `command/<id>.yaml` | 步骤 6，每条命中的绑定一次 |

### 4.2 效果落到哪些文件、改哪些 key —— 归 `04`

本文**不**定义效果的文件副作用（那是 `04` 的效果表 + `03` 的执行序）。本文只钉住一条必须由触发层的顺序保证的性质：

### 4.3 `on` 自身不被改写

`settleWorldCommands` **MUST NOT 改写触发实体的 `on` 键**。命令的效果可能改写同一实体的别的键（`trigger.fm.*` 读的那些、`edit` 效果写的那些），但 `on` 是**绑定声明**，不是命令的输出。

**这条不靠约定，靠 §3 步骤 3 的实现**：`on` 来自调用方在动作早期解析好的 frontmatter 快照，触发层不重读文件。所以即使命令改写了实体，**本次触发用的是触发那一刻的绑定**——`05` 的 `command_resume_drifted` 正是为「下一次触发的绑定与 `command_log` 不一致」准备的（§2.3）。

## 5. 落账

### 5.1 触发本身不落事件

一次触发不是一条独立事实，它是「某条已落账事实之后发生的事」。命令的每个效果落它**本来就会落**的事件（契约 §5.2）。触发点本身没有第十六个事件类型可落，也不需要。

### 5.2 actor / turn 原样透传

| 字段 | 值 | 依据 |
|---|---|---|
| `actor` | `ctx.actor` 原样 | 契约 §5.1：玩家掷骰 → `player`；作家调工具 → `writer`。**不用 `engine`** |
| `turn` | `ctx.turn` 原样 | `types.ts:18-22` 的 opaque 锚点 |
| `detail.command` | `<id>` | 契约 §5.1（**主 agent 2026-09-14 裁定 1 已删除 `detail.by`，只留 `detail.command`**） |
| `subject` | 由**效果动作自己**决定 | 不是被触发实体。发奖创建的是 `world/.../investigation-success.md`，那才是 `entity_created` 的 subject |

> **`detail.command` 而不是 `detail.by = 'command'`**：主 agent 裁定 1 采纳了 `10` 的取证——`detail.by` 已被 `layer_initialized` 占用且是**闭枚举** `z.enum(['writer','player','engine'])`（`packages/shared/src/schemas/events.ts:99`），而 dev 模式 `appendEvent` 对 detail 跑 `safeParse`（`local-store.ts:760-771`（旧标 `:668-679`，**快照已漂移**））→ 写 `'command'` 会炸。**本文不引入 `by`。**

### 5.3 顺序是免费的，但「同 turn = 一组连贯事实」**不成立**

`appendEvent` 在 `BEGIN IMMEDIATE` 里取自增 seq（`packages/shared/src/store/local-store.ts:758-813`（旧标 `:666-721`，**快照已漂移**）），串行。因此命令产生的事件 seq **必然大于**触发事件的 seq，且二者 turn 相同。

> **修正（主 agent 2026-09-14 裁定 2，采纳 `10` 的实测）**：契约 §5.3 原写的「同 turn → 作家注入会把它们合成一组连贯事实」**已被证伪**。实测链：合并键是 `(turn, type, actor)` 且只合并**相邻同键**（`packages/shared/src/render/events.ts:286-298`（旧标 `:284-296`，**快照已漂移**））；`roll_resolved` 在 `MERGE_EXEMPT` 里（`:60-71`）；唯一跨 type 的合并键是 `path` 不是 turn（`:346-365`）；十五条渲染模板没有一条印 turn。
>
> **实际只保证「两句相邻」，且 cap 折叠（`:367-372`）还会打断相邻。** 因果可读性由命令的主语渲染承担，不靠 turn 合并。**本文不依赖 turn 合并，§13 的验收断言也不依赖它。**

### 5.4 命令事件的注入侧代价（归 `10`，本文只登记）

`10` 实测：`computeNextStep` 只看队尾（`packages/shared/src/render/next-step.ts:114`），命令事件 seq 更大 → 队尾变成 `entity_created` → 不在白名单（`:71-75`）→ 玩家掷骰那轮作家**失去**「去叙述这次判定」的祈使句。修法归 `10`（C1 必做项）。**本文的触发点顺序不能为此改变**——触发仍在 `appendEvent` 之后（§3 步骤 1）。

## 7. 绑定解析与缺失：硬门 4 在哪一层被守住

「`on` 引用了一个不存在的命令 id → 什么时候发现？」这个问题有**三个**答案，缺一不可。

| 层 | 时机 | 行为 | 依据 |
|---|---|---|---|
| **1. 写入时** | Agent `write`/`edit` 一个带 `on` 的实体时 | **拒绝写入**，错误带行列位置与「先建命令文件再绑定」的指令 | 契约 §9.1「写入即校验」；`07` 接线 `parseOnBindings` |
| **2. 触发时** | 动作跑完、绑定解析时 | **不拒绝动作**，产出一条 `command_not_found` outcome | §3 步骤 6 |
| **3. 呈现时** | 同一次动作的响应里 | outcome 进 `details.commands` + `command_error` | §3 步骤 10 |

**为什么第 1 层是 block 而不是 warn**（`[待拍板 T-4]`）：warn 会让「写了但没人执行」重新变成无声状态——那正是 `dice_outcomes` 活了 36 个文件的原因。代价是 Agent 必须先写命令文件、再写绑定，`07` 的 skill 文案要教这个顺序。收益是这种错误**在世界上活不过一次写入**。

**为什么第 2 层不拒绝动作**：见 §3 步骤 12。骰子已经掷了，拒绝动作 = 死局（硬门 7）。

**第 1 层挡不住的两条路，因此必须有第 2 层**：

- Agent 的 `bash` 工具没有路径/扩展名白名单（`docs/doc-05:440-442`；契约 §9.2 已登记「工具级强制 ≠ 物理级强制」）。
- 命令文件可能在绑定之后被删除或重命名。

**玩家/模型看到什么**：动作 `ok:true`，`details.commands` 里那条带 `command_not_found` 与逐字路径，被触发实体获得 `command_error`，玩家侧看到「结果已经记下，但它该触发的后果『<id>』找不到了。这一步没有发生。」完整文案见 §10.2。

## 8. 多命令的顺序与短路

**声明层（本文负责）**：`on.<hook>` 是序列，**数组顺序 == 执行顺序**（§2.3）。某条失败后后续跑不跑，由该条自己的 `on_error` 决定，默认 `stop`。

**执行层（`03` 负责）**：一个命令内部 N 个效果怎么算成功、部分失败的语义、总效果数上限。

两层的交界只有两个量：`on_error` 与 `CommandOutcome`。**本文不定义效果级语义，`03` 不定义绑定级顺序。**

`[给 03]` 交接清单：

- `on_error` 的字段名与取值（本文已定：`stop` | `continue`，默认 `stop`）。
- `CommandOutcome.effects` 的元素类型（`CommandEffectOutcome`）。
- `runWorldCommand(ctx, spec, args)` 的签名。
- 一条判据：**「命令内部效果失败时，该命令的 `status` 是 `error` 还是 `ok`」**——它决定 `on_error: stop` 会不会被触发。本文只要求 `03` 给出唯一答案并写清。

**`skip` 不是 `error`**：`when` 为假、重入、被短路，三类都是 `skipped`，都不触发 `on_error`。

**漏了会怎样**：把 `when_false` 当失败，四档骰子的**第 1 档会把它后面三档全部短路掉**——整个 `dice_outcomes` 迁移直接崩。这是最容易写错的一处，验收 T8 专门测它。

## 9. 与 `choice_actions` 的关系

**主张（已按 `04` 的实测事实与主 agent 的架构澄清修正）：`choice_actions` 不是 `on.choice_selected` 的语法糖，两者正交，长期并存。**

| | 是什么 | 谁在什么时候执行 | 归属 |
|---|---|---|---|
| **`do[].action`**（效果） | **世界改写** | 命令触发时，**同步**，经动作层 | ⊆ `ACTION_METHODS`（`04` 的封闭注册表） |
| **`choice_actions`**（数据） | 「玩家选了以后前端/路由做什么」 | 命令只是**写数据**；玩家点击后才由现有 `runDeclaredChoice` + 前端解释 | 一次 `edit` 效果 |

**`on.<hook>` 说「玩家选了以后引擎跑什么」；`choice_actions` 说「玩家选了以后前端/路由做什么」。** 前者是引擎行为，后者是 UI 数据。两者在时间上错开一层：`on` 是**本次**点击的后果，`choice_actions` 是命令给**下一次**点击写下的按钮。

### 9.2 两者在同一实体上并存的硬约束（不可协商）

**同一实体 MUST NOT 同时声明 `choice_actions` 与 `on.choice_selected`。** 理由两条，都实测于源码：

1. **会直接报错**。`runDeclaredChoice` 在 `:252` 判断 `frontmatter.choice_actions === undefined` 才返回 `null`（让路由 fall through）。实体**有** `choice_actions` 时继续，在 `:259` 要求选中的 `optionId` 必须在 `choice_actions` 里，否则 `fail('The selected option has no declared action')` → HTTP 400。
   → 实体有 `choice_actions`（只覆盖 `back`）+ `on.choice_selected`（覆盖 `lantern`），玩家选 `lantern` → **400，命令永不触发**，玩家看到一句与真实原因无关的报错。
2. **会双重结算**。同一路径的 `:271-273` **会调用** `svc.chooseOption(...)`，随后 `:275-282` 才执行 recipe 的 `take`。
   → 同一个选项两边都声明 → 命令先跑、recipe 的 `take` 后跑，**两套后果都发生**。硬门 2 直接破。

**落点**：`parseOnBindings` MUST 在**写入时**（`07` 接线）与**触发时**（§3 步骤 4）都拒绝这个组合，错误码 `choice_actions_conflict`，fail-closed（一条绑定都不跑）。**这是唯一一条能同时挡住上面两条的静态规则。**

> **这条约束不禁止命令去写 `choice_actions`**——那是一个 `edit` 效果的结果。它禁止的是**作者在同一个文件里同时手写两套**。

`[待 08/06 裁决]` `read` / `stage` 的最终去向（保留 `choice_actions`、迁到 `ChoiceOption.then`、还是别的）需要 `06` 一起定。本文只定「它们不是效果」。

### 9.3 命令不能再调命令：`action: run` 已被 §R.15 删除

**初稿曾按 `01` 的口径写「`do[].action: run` 是显式命令调用，与隐式触发正交，两者共享 `commandDepth`」。契约 §R.15 已删除该语法，本节随之作废并改写。**

**现状口径：命令的 `do` 里没有任何调用另一个命令的效果。** `04 §9.1` 的封闭效果表里不存在 `run`。因此：

| | 还存在吗 | 谁挡它 |
|---|---|---|
| **隐式触发**（动作落事件 → hook 命中另一实体的 `on`） | **是**，这是本模块唯一的链式向量 | 本文 §11.4 的深度上限 1（§3 步骤 2） |
| **显式 `run`**（命令 `do` 里写死调另一个命令） | **否**，§R.15 已删 | — |

**这让递归止的论证变简单，而不是变复杂**：链式只有一个入口，深度门只需要守一个地方。初稿担心的「隐式与显式混合的链会绕过两边各自的上限」**在语法层面就不可能发生**——没有显式那一半。

**代价没有变**（仍登记在 §17.3 第 1 条）：**链式玩法（A 触发 B 触发 C）本期不可表达**，且现在连「作者自己在一个命令里显式串三步命令」也不可表达。替代路径仍是**在一个命令的 `do` 里把三步效果顺序写完**——这是显式的、可静态读的、可在写入时数出总效果数的。

> **`09` 的表达力天花板 MUST 按这条更新**：删掉 `run` 之后，「命令的组合能力」只剩 `do[]` 内部的顺序编排，跨命令复用只能靠**内容层重复声明**或**作者把公共部分抽成一个被多个实体 `on` 指向的命令**——后者是横向复用，不是纵向调用。

### 11.4 递归止机制

**上限硬编码为 1。落点有两种等价形状**（契约 §R.15.6 采纳模块级计数；本文保留 `ActionContext.commandDepth` 作为等价备选，判据见 §14.7）：**①深度上限 1；②单一写入点；③释放点在 `finally`（模块级计数）或随调用栈天然释放（`ActionContext`）**。

下面以 `ActionContext.commandDepth` 形状写出，模块级计数把同一判据搬进模块作用域即可，**语义与验收断言（T4）完全相同**。

```ts
// types.ts:10-27
export interface ActionContext {
  store: WorldStore;
  actor: Actor;
  agentScope?: AgentScope;
  nookNote?: boolean;
  /**
   * How many world commands deep this call is. Absent === 0 === a real actor's
   * first action. Any value > 0 suppresses every implicit command trigger point
   * (docs/command/02 §8.4): a command's effects never trigger further commands.
   */
  commandDepth?: number;
  turn: string;
  now?: () => string;
  rng?: () => number;
```

- **写入点唯一**：§3 步骤 8，`{ ...ctx, commandDepth: (ctx.commandDepth ?? 0) + 1 }`。**这是全仓唯一的 +1 处**——§R.15 删除 `action: run` 之后，命令不能再调命令，不存在第二个写入点（§9.3）。
- **读取点三处**：三个触发点的步骤 2。
- **上限是 1，不是 N。** 即：命令内部触发的动作**永不**再触发命令。

**为什么是硬 1 而不是深度 N**：

1. **静态可判定。** 深度 1 让「点一次 = 一层后果」成为一条不需要运行时分析就能陈述的契约。深度 N 下，作者写的绑定图里有没有环、玩家会在第几层被砍掉，只有跑一遍才知道。
2. **硬门 8（先公开，后执行）。** 链式触发的总代价玩家在决定之前看不见。深度 1 让「这次点击会发生什么」可以在 UI 上被完整列举。
3. **契约 §4.3 的同步执行。** 深度 N 的最坏情况是 N 层嵌套 I/O 压在一次 HTTP 请求里，而 `ActionContext` 逐字没有 `AbortSignal`（`types.ts:8`），没有任何东西能中断它。
4. **内容层没有需求证据。** 36 个 `dice_outcomes` 文件里没有任何一档的 outcome 会触发另一个 outcome（逐档形状见 `templates/whitechapel-jp/world/london-map/04-investigation-dice.md:16-94`）。为一个没人要的能力付出前三条代价，是反过来的。

**为什么不用「调用栈里记 command id 去重」**：那只防自环。`A → move → B → choose → A` 这种互环需要保存整条链，是运行时状态，而且「第二次遇到 A 就跳过」对作者不可预测（跳过的是哪一次？）。深度 1 是常数空间、零状态、一句话能说清。

**明确的代价（MUST 写进 `09` 的表达力天花板）**：**链式玩法（A 触发 B 触发 C）本期不可表达。** 替代路径是在一个命令的 `do` 里把三步顺序写完——显式的、可静态读的、可在写入时数出总效果数的。

### 14.7 递归止的落点：`commandDepth` 与模块级计数是等价备选（契约 §R.15.6 已收窄）

**为什么没有更轻的办法**（逐一排除）：

| 候选 | 为什么不行 |
|---|---|
| 模块级 **`Set<string>`** 记「正在跑的命令 **id**」 | **被否决的是「按身份去重」这一点**：它只防自环，防不住 `A → move → B → choose → A` 这类互环；且以 id 为键时，同一命令在一次请求里的两次**合法**调用会被误判为环 |
| 模块级 **深度计数**（无释放点） | 被否决的是**缺释放点**：命令抛异常后计数停在 > 0，此后该进程内**所有**触发点被永久静默——一个比递归更难查的失败 |
| 用一个 `AsyncLocalStorage` 存深度 | 引入新的隐式上下文机制，`ActionContext` 的整个设计意图就是「Everything an action needs, and nothing else. Deliberately transport-free」（`types.ts:5-9`）；ALS 正是它刻意回避的那类东西 |
| 靠 `command_log` 判「这个 source 上已经跑过命令」 | 那是**幂等**（`05` 的活），不是**递归止**。它挡不住一个命令在**同一次**执行里再触发另一个命令；两者是不同的问题 |
| 靠约定「作者不要写递归」 | 用户明确要求「给出机制，不是'约定不要这么写'」 |

**结论已按契约 §R.15.6 收窄：本文不再主张「必须改 `ActionContext`」。**

契约最终采纳的是**模块级深度计数 + 明确释放点**。上表否决的两行**都不是**它：第一行否决的是「按 id 去重」，第二行否决的是「没有释放点」。**带释放点的模块级计数不在被否决之列**，本文此前把它和那两行混为一谈，是错的。

**释放点的形状（两种实现共有的硬要求）**：计数的 `+1` 与 `-1` MUST 成对且 `-1` 在 `finally` 里——

```ts
depth += 1;
try { return await runWorldCommand(/* … */); }
finally { depth -= 1; }   // ← 命令抛异常也必须回落，否则整进程静默
```

**两种形状的判据完全相同**，评审只需核这三条：①深度上限 1；②**单一**写入点；③释放点在 `finally`。`ActionContext.commandDepth` 的额外好处只有一条——它**天然随调用链传递、天然随调用栈释放**，不需要 `finally`，因为它从来不是可变状态（每层是一个新对象，§3 步骤 8 的 spread）。

`nookNote`（`types.ts:16-17`）仍是「内部能力开关」的同类先例（`nook-note.ts:104` 的 `{ ...ctx, nookNote: true }`），**本文把 `commandDepth` 形状作为等价备选保留**，由评审门在两者间定。

### 14.8 `from` 的引用完整性：跨字段校验不能只做形状校验

**这条由 `08` 发现、主 agent 采纳并要求 `07` 升级校验**（契约 §10.8 登记位）。

`from: dice_outcomes` 是**跨字段引用**。只校验 `on` 自身的形状（是不是 mapping、hook 名对不对、值是不是数组）**挡不住** `from` 指向一个不存在的 key。校验 MUST 增加一条：**`from` 指向的 key 必须在同一实体的 frontmatter 里真实存在且是数组**。

**这条校验是纯同步、纯静态的**（同一份已解析的 frontmatter 对象内查 key），**不引入 I/O**——所以它满足 `07` 对 `parseWorldCommand` 的硬需求，两者可以共用同一个纯函数。落点见 §2.4 的「`from` 的引用完整性」。

### 15.1 骰子：`dice_outcomes` 的目标形态（对照存量 36 个文件）

**`command/investigation-outcome.yaml`**（1 份，36 个实体共享；`name`/`desc`/`params`/`do` 形状归 `01`/`04`）：

```yaml
name: Investigation outcome
desc: Materialises the notes a dice outcome earned, and appends the short result to the source card.
do:
  - action: give
    args:
      rewards: "{{ trigger.entry.rewards }}"          # list-args：整数组交给效果
      grade:   "{{ roll.result }}"
  - action: edit
    args:
      path: "{{ trigger.path }}"
      append_body: "\n\n**{{ roll.result }}** — {{ trigger.entry.text }}"
```

**四件事必须一起读，否则会看错这个例子**：

1. **`from: dice_outcomes` 声明「这条绑定从哪个数组选条目」**（裁定 A），选中的条目以 `trigger.entry.*` 暴露。**`{{ }}` 里没有嵌套**——`rewards` 是静态路径，`[0]` 这种下标**不出现**，因为没有 `[0]` 了。
2. **`{{ trigger.entry.rewards }}` 是一个数组值实参（`list-args`，裁定「方向三」）。** `give` 在**引擎内部**有界展开，对作者不可见。**命令文件里没有循环、没有下标、没有 `foreach`。** 迭代次数的上界由 **`parseOnBindings` 在写入时校验**（§2.4 的 `from` 校验清单第 4 条）——**不是**由某个 schema 上限「封死」：`on` 住在 passthrough 的 `.md` 上，没有 schema 在保护它（§14.6）。校验在写入时发生，因此迭代次数在执行前已知，这正是 `09` 的资源上限论证需要的那条静态性质。
3. **`text` 与 `rewards` 都来自 `trigger.entry`，不是 `trigger.fm`。** 命令**不需要知道那张表叫什么名字**，`from` 已经把它选好并塞进 `trigger.entry`。这就是「1 份命令服务 36 个实体」的机制。
4. **`edit` 的 `append_body`** 归 `04`（拍板 A）：只追加、不删不改已有正文，**不判重**（幂等由 `05` 负责，`append_body` 自身是非幂等的代表效果）。

> **本次例子相对初稿的修正记录（供评审对照）**：初稿曾用 `{{ trigger.fm.dice_outcomes[entry].rewards[0].path }}`——**下标里嵌 `{{ entry }}`，即 `{{ }}` 嵌套**。裁定 A 禁止嵌套（动态下标会让上界不可静态界定，直接砸 `09` 的资源上限论证），改为 `from:` + `trigger.entry`。初稿的 `with: { entry: 0 }` 也随之删除：`entry` 由 `when` 匹配决定，不需要作者手写。

**这四条绑定里没有一条声明 `on_error`**，即全部默认 `stop`。四条 `when` 互斥，实际只命中一条，其余三条 `skipped:'when_false'` 并出现在 `commands` 里——玩家和模型都能看到「引擎确实评估了四档，选中了第二档」（T8）。
