## 8. 问题清单（逐条，按优先级）

**BL-1（P1）`list-args` 失败后是否继续执行：三处冲突，其一写在验收断言里**
`04:253`（§2.6 语义 3）写「第 2 项目标已存在 → 该项 `ok: false`，**第 1、3 项照常执行，不整体回滚**」；`04:302` 写「第 2 项 `already_exists` 时，**第 1 项留在世界里**」并称「这样"崩在第 2 项"才是可续跑的」；`04:1486`（T-15）断言 `outs.map(o=>o.ok)` **等于 `[true,false,true]`**（即第 3 项跑了）。而 `03:497` 是 `on fail ⇒ break`、`03:541` 逐字「**命令内部永远是 `stop`，不提供 `continue`**」，`05:880`（N2b）断言首次触发 `steps.length === 2`、第 3 项要等第二次触发才补。**同一件事三个答案。** 修法二选一（须由 `04` 与 `03` 同批确定）：(a) 按 `03`，`list-args` 的展开体也是 `do` 的一步，**整体 stop**——那么 `04:253/302` 与 T-15 的 `[true,false,true]` 都要改为 `[true,false]`，N2b 不变；(b) 按 `04`，`list-args` 展开体**豁免 stop**——那么 `03:541` 与 `05:880` 要改，且 `03:497` 的 `break` 需要为 `give` 开例外。**建议取 (a)**：它保住"`do` 是因果链"这条 `03` 的论证，而 `list-args` 的三项奖励本就是**互相独立**的，用三条 `do` 条目表达即可，不必让一个效果违反自己所属序列的失败语义。

**BL-2（P1）`edit.frontmatter` 无保留键限制 → 可绕过硬门 2 与硬门 3**
`04:111` 给 `edit` 的参数是 `frontmatter?: Record<string, unknown>`（浅合并，`null` 删键）。命令文件是 strict schema，但**值的形状不受约束**，于是：
- `edit: {path: <chalk>, frontmatter: {roll_dice: {…, result: 100, passed: true}}}` —— `editEntity` 的浅合并会**整键替换** `roll_dice`（`delete.ts:195-201`），而 `eventKindOf` 只在**合并前**算 `kind`（`:193`），**不会**拦这次写入。这正是硬门 3 逐字禁止的"改写 `roll_dice.result`"。
- `edit: {path: <entity>, frontmatter: {command_log: [{key: '…', status: 'done', …}]}}` —— 直接伪造幂等回执，硬门 2 破。`05:280` 处置缺点 1 时写「**真正要防的是"Agent 误伤"，不是"玩家作弊"**」并列出三道防线，但其 (a) 只覆盖"改 `title` 不会碰 `command_log`"、其 (b) 明确自认是**提示词级**、其 (c) 只是形状校验——**三道防线都不拦"命令自己写 `command_log`"这条路径，而命令是引擎执行的，提示词级约束对它无效**。
- 连带：`05:142` 的 `fact` 稳定性论证（"`result` 一生只有一个值，`fact` 天然稳定"）在此塌方。若 `result` 可被命令改写，则同 `(source, hook, command)` 的两次触发可能算出**不同的 `fact`** → 不同 key → **重复结算**，正是 `05 §3.5` 花整节论证的通道又回来了。
