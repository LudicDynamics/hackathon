> 评审 agent：`RevPendingC1`。范围：**只裁决「失败是否落账」这一项**（`05` 提方案、`09` 评代价）。

## 1. 判定（唯一明确）

**判定：不落账（`05` 的 F1）。**

- **命令执行失败不产生任何世界事件**——既不新增第 16 个类型（F3），也不复用 `entity_edited`（F2）。
- 失败只落两条**非事件**通路：`ActionResult.details.commands`（同轮、同步，进触发者 tool_result / HTTP 响应）＋ 被触发实体 frontmatter 的 `command_error`（玩家侧、可复访）。
- `rollDice` 调用位 B 的「以错误结束但世界已变化」（`05:468`）仍是**实现事实**，但它**不构成落账的理由**（见 §2.3、§3.3）。

一句话理由：**硬门 4 与硬门 1 都能被「非事件」的同轮回执 + 卡片文件满足；而 F2 会静默破坏 `10` 已冻结的 `hasSettledCommand` 不变量（把一次失败判成「已结算」，从而命令作家**不要**补救），F3 则为本批次一次性推翻契约 §5.2 的冻结。三者中只有 F1 同时满足硬门 4、硬门 1、`docs/tools/00 §5.2:241` 的铁律与契约 §5.2 的「本批次不新增第 16 个事件类型」。**

> 我**没有**推翻主 agent 的倾向——主 agent 未就 `[C-1]` 表态（它把 `[C-1]` 派给评审门）。这是**首次裁决**，不是推翻。

## 2. 六条必须核的事实（逐条实测）

### 2.1 `05 §12.1` 的方案全清单（读全，非摘要）

原文在 `05:1047-1056`。它给**三个**方案：

| 方案 | 做法 | `05` 自列的代价 |
|---|---|---|
| **F1** | `command_error` 写实体 frontmatter ＋ `SettleReport` 进 `details`（`05:1053`） | 零事件改动；零枚举改动。**牺牲**：失败不进入**触发者之外**的 actor 注入 |
| **F2** | 复用 `entity_edited`，`detail` 带 `command` / `commandError:<code>`（`05:1054`） | 渲染成「edited "X"」= 一句**读起来像成功**的人话 |
| **F3** | 新增第 16 个类型 `command_failed`（`05:1055`） | 枚举＋detail schema＋渲染模板三处同步；正面违反契约 §5.2 |

`05` 明确「**三条都不预设结论**」（`05:1057`），只补两条判据：(1) F1 与 F3 的差别是产品问题不是工程问题；(2) F2 的隐性代价是「每次失败追加一条进入所有人注入的 `entity_edited`」，**除非 `10` 愿意为它单独出一条渲染分支**（`05:1058-1060`）。

**关键澄清（任务书点名）**：`05:795` 逐字「若 `[C-1]` 最终选了 F2，那只影响 `command_error` 的落账，**不改变 `command_log` 不落账**这条——两者是分开的。」**该句成立**：我核过 `05 §8.2`（`:764-796`），`command_log` 走 `writeCommandLog`、不落事件；`command_error` 是另一条写入。两者确是独立的落账决策。✅

> 但 `05` 的 F2 分析**只评估了渲染面**（`render/events.ts`），**漏了 `10` 的判定面**——这正是我推翻 F2 的依据（§4.1），而 `05:1030` 只说「`[C-6]` 收窄不影响 key」，从未提「失败事件的 `detail.command` 会翻转 `settled`」。

### 2.2 「不落账也能满足硬门 4」的三条通道（任务书点名，逐条核实）

| 通道 | 覆盖谁 | 机制位置（实测） | 覆盖面 |
|---|---|---|---|
| `details.commands` | **触发它的那个 Agent，同一轮** | `ActionResult.details` 是开放 `Record<string,any>`（`packages/shared/src/actions/types.ts:28`）；`extensions/toolkit/roll-dice.ts:49-50` 原样透传 `details`；HTTP 侧 `reply` 摊平（`apps/server/src/routes/world.ts:74-80`）。设计见 `02:559`、`10 §3.8.2`、`06:138-141` | **模型可见 ✅**（同轮）；玩家侧进响应体 ✅ |
| `command_error`（实体 frontmatter） | 玩家（`06` 渲染）＋后续任何读到该文件的人 | `05:64-88` 定形状与清除；`06 §7.5`（`:544-593`）定渲染，**默认展开**（`06:552-554`、`:583`） | **玩家可见 ✅**（常驻、刷新仍在、可复访） |
| 事件注入 | 其他 actor 与下一轮 | **触发者自己看不到**——`packages/shared/src/inject/collect.ts:251` 传 `excludeActor: actor`，`local-store.ts:745-748` 逐字 `NOT (actor_type = ? AND COALESCE(actor_id, '') = ?)` | 仅其他 actor；F1 下**失败无事件 ⇒ 此通道对失败为空** |

**结论：`details`（同轮模型）＋ `command_error`（玩家可复访）已同时覆盖硬门 4 要求的「模型可见的输出」与「玩家可见的状态」。** 第三条（事件注入）在 F1 下对失败**什么都不提供**——它是 F1 唯一的缺口，但它**不是**硬门 4 的要求（硬门 4 要的是「模型」与「玩家」，触发者那个模型已经看见）。判为**可接受**，理由见 §3.2。

> **实测出的边界**：`excludeActor` 过滤的是「与本进程 actor 完全相同的 `(type, id)`」。玩家侧 `player` 没有 `id`（`packages/shared/src/actions/actor.ts:9` 只有 `character` 带 id），读者是 `writer`/`character:<id>` ⇒ **玩家触发的事件不会被任何读者排除**。所以若把**失败**落成事件，玩家触发时它**会**进作家注入——这既是 F2 的隐性收益，也是 F2 的致命处（§4.1）。

### 2.3 `layer_init_failed` 先例：它的存在理由能不能套到命令失败上？

**它的存在理由（逐字取证）**：

```
packages/shared/src/actions/layer.ts:12
  `recordLayerInitFailed` is the sole exception to "failure appends nothing"
  (doc-21 §3.6): the failure IS the fact consumers need.
```

**它的消费者**：`doc-11:350` 逐字「前端降级提示 ＋ 作家（可重试/现编）」；`doc-11:368` 超时路径；`doc-11:483` 历史面板可视化。

**它与命令失败的关键差异（逐条）**：

1. **actor 是 `engine`**（`layer.ts:189` `actor: { type: 'engine' }`）——引擎发起、**无触发者**的记账。命令失败的 actor **恒等于触发者**（契约 §5.1，`00:257`）。两者**不同构**。
2. **它是一个专用记账动作**（`recordLayerInitFailed` 在 `ACTION_METHODS` 注册，`layer.ts:205-207`），不是「某动作抛了 `isError`」。命令失败是**动作层抛 `ActionError`**（`packages/shared/src/actions/errors.ts:46-48` 的约定）。⇒ 先例的**机制**（为失败专开一个动作）在命令场景要新造动作，而契约 §4.2（`00:231`）要求效果 ⊆ 既有 `ACTION_METHODS`——**开不了这个口子**。
3. **它的 actor=engine 不被任何人的 `excludeActor` 排除**；命令失败 actor=触发者，**恰被触发者自己的注入排除**（`10 §3.9.2` 已证）。⇒ 照搬先例会得到一条**消费者存在但收不到**的事件——比不落账更糟。

**结论：先例的理由在命令场景下不成立。**

> **反向证据**：`04:1054`（`04 §9.1.17`）逐字「`recordLayerInitFailed` … **在 `[C-1]` 拍板之前，任何『让命令能落失败事件』的路径都必须关闭**」。`04` 独立得出同向结论。

### 2.4 `command_error` 的清除时机 —— 删除后历史去哪了？

**清除规则（`05:87`）**：「同 key 的运行到达 `status: done` 的那一次写入里删除 `command_error`」，写入器**直接 `delete`**（`05:87` 引 `actions/delete.ts:198` 逐字 `if (value === null) delete merged[key]`；我核过 `delete.ts:195-201` ✅）。

**关键实证：删除后历史确实没了，且 `05:85` 的兜底说法站不住。**

`05:85` 逐字：「理由：失败是要人处理的当前状态，不是历史；**历史在事件里（若 `[C-1]` 决定落账）与 `command_log` 的 `status: partial` 里**。」

**实测反驳**：
- `command_log.status` 枚举 = `partial | done`（`05:45`）。
- 写入用 `upsertLogEntry` **按 key 原地替换**（`05:57` 逐字「不排序、不去重、不压缩——`upsertLogEntry` 按 key 原地替换」；`:764` 签名注释逐字「按 key 原地替换；不存在则追加」）。
- S4/S5 终态是 `status: 'done'`（`05:435`）。

⇒ **一次「失败 → 后来续跑成功」的运行，在 `command_log` 里只剩 `status:'done'` 一条**，不再记录它曾 `partial`；同时那次写入**删掉了 `command_error`**。所以 `05:85` 括号里「历史在 `command_log` 的 `status: partial` 里」**在任何终态为 done 的运行上都是假的**。

**但它不构成阻断**，理由（另一半要如实说）：
- **终局失败**（玩家放弃、不续跑）⇒ `command_error` **永不清除**（清除条件要求「同 key 到达 done」）⇒ 历史**保留**在卡片上，可复访。
- **被修复的失败**⇒ 世界现在完整，玩家看「失败过」反而是杂音——`05:547` 逐字「`resumed` 在玩家侧与 `applied` 同形，**MUST NOT 有独立文案**」，「说出『上次只做了一半』会让玩家以为世界曾经处于坏状态，而事实是世界现在是完整的」。⇒ **丢失这段历史是刻意设计**。

⇒ 登记为**文档不精确（P3）**，见 §6.1。

### 2.5 `detail.command` 可选键 —— 若选落账，`detail` 里要带什么才自足？

**上位硬约束**：`docs/tools/00 §5.2:239` 逐字「`detail` 必须自足（doc-21 §3.3）：除路径外 MUST 带**当时的 `name`**，渲染人话时不许回读世界目录。但**不存正文**」；同处逐字「`detail` MAY 额外带可选键（如 `component` / `secondLayer`），既有键名与枚举不变」。

**实测：`detail.command` 可以加，且不需改任何 schema。**

```text
$ node -e "… EventDetailSchemas …"      # 实测输出
entity_edited + command/commandError => PASS
entity_edited baseline               => PASS
layer_initialized + by=command        => FAIL:["invalid_enum_value"]
WORLD_EVENT_TYPES.length = 15
```

⇒ 往 `entity_edited` 的 `detail` 里塞未知的 `command`/`commandError`/`step` **静默通过**（`z.object` 默认非 strict）；只有撞上 `layer_initialized` 的闭枚举 `by` 才会炸。**与 `09 §5.1`（`:394-406`）的实测完全一致。** ✅

**若选落账，`detail` 至少需要**（按 F2 的定义 ＋ 自足要求）：

```yaml

  path: world/london-map/04-investigation-dice.md   # entity_edited schema 必填
  name: "ホームズに推理を任せる"                      # 必填（当时的名字）
  kind: chalk                                       # schema 必填
  command: investigate-clue                          # 归属（契约 §5.1 唯一可选键）

  step: 1                                            # 第几步
```

⇒ **F2 的 `detail` 是自足的**（`path`+`name`+`kind` 齐），技术上可行。

## 3. 正面回答那个必须回答的问题

**「不落事件表」≠「不留痕」。** 分开答：

### 3.1 当下能不能看见？（硬门 4）

| 读者 | F1 下看见失败吗 | 机制（实测） |
|---|---|---|
| **玩家** | ✅ | `06 §7.5` 卡片 `command_error` **默认展开**（`06:552-554`、`:583` 逐字「默认展开是硬门 4 在这个组件里的落地形态」）＋ 仪式落定处的回执行（`06:609`） |
| **触发它的那个模型**（作家调 `roll_dice` / 角色调工具） | ✅ | `details.commands` 搭同一次 tool_result 回来（`10 §3.8.2`；`02:559`；`extensions/toolkit/roll-dice.ts:49-50` 原样透传） |
| **同一轮同步** | ✅ | `details` 同步返回（契约 §4.3 `00:245`）；`10:429-431` 逐字「同一轮、通过自己的 tool_result **同步**看到后果，完全不依赖事件注入，因而绕开 `excludeActor`」 |
| **其他 actor（作家下一轮 / 角色冷启动）** | ❌ | F1 下失败无事件 ⇒ 事件注入里根本没有这一行 |

⇒ **硬门 4 满足**：它的字面要求是「进入**模型可见的输出**与**玩家可见的状态**」，两者都兑现。「其他 actor」不在硬门 4 的字面里。

### 3.2 世界史里事后查不查得到？

- **终局失败**（玩家放弃/不续跑）⇒ ✅ **查得到**：`command_error` 挂在卡片 frontmatter 上，**永不清除**（清除要求「同 key 到达 done」，`05:87`）。
- **被修复的失败**⇒ ❌ **查不到，且这是刻意的**：`command_error` 被删、`command_log` 原地改写成 `done`（§2.4）。`05:547` 明确要求 repaired 的运行在玩家侧与成功**同形**。
- **事件表**⇒ ❌ F1 下永远查不到（这正是「落账」与「不落账」的唯一实质差别）。

**这就是落账的真正价值，也是它唯一的代价**：事件表提供一条**不可清除的时序**。但命令失败的「不可清除」是**负资产**——`09` 理由 #2 的「一个会被修好的问题不该留在不可删除的历史里」。

### 3.3 硬门 1 的「玩家要能在画布上复访到它」——对失败而言，复访对象是什么？

**答案：不是一个「失败的记录」，而是一个「仍然不完整的中间状态」＋ 一个「标记着它的文件」。**

- 硬门 1 的字面（`00:318-319`）逐字：「**每个效果** MUST 落成文件变化 + 事件…一条审计事件本身也不够——玩家要能在画布上复访到它」。
- **失败不是一个「效果」**。硬门 1 的适用范围是**效果**：成功落地的效果各自有自己的事件（`10:1082` 逐字「展开的每一项 **MUST** 各自落一条带 `detail.command` 的独立事件」）；**未落地的效果没有事件，也不构成硬门 1 的违反**（没有「效果」就没有「效果 MUST 落账」这条要求）。
- 玩家复访到的对象是：
  1. **仍未出现的奖励卡**（`06:610` 逐字「**没有新卡**（没有发出去的东西）」）——玩家看到「该有的卡不在」；
  2. **卡片上常驻的 `command_error`**（`06:552-554`）——它是**文件**，满足「文件即真相」；
  3. **部分已落地的效果**（G6 部分失败时）——各自有事件，硬门 1 已在效果层满足。

⇒ **硬门 1 满足**，且它要求的复访对象**本来就该是「状态」而非「记录」**。

### 3.4 一句话收束

> **「落账」提供的是「历史」，「文件 + 同轮回执」提供的是「当下 + 复访」。而命令失败要的正是后两样——失败是一个**可修复的当下状态**，不是一个**要写进史书的事件**。** 这是我判 F1 的产品理由。

## 4. 独立于提案人论据的新发现（≥2 条）

### 4.1 【新发现·最承重】F2 会静默破坏 `10` 的 `hasSettledCommand` 不变量 → 该给的**永远不给**

**`05` 的 F2 分析只看了渲染面**（`05:1058-1060` 逐字只讨论「渲染成『edited "X"』」与「作家上下文噪音」）。**没有任何文档检查过 `10` 的判定面。**

**`10` 的判定面（实测）**：

```ts
// docs/command/10-事件与作家上下文.md:244-246（逐字）
/**
 * True when at least one event in the window carries a `command` (10 §3.7).
 * Deliberately NOT "any event after the act": a command whose condition did not
 * match lands nothing, and must leave the plain wording untouched.
 */
function hasSettledCommand(events: readonly NextStepEvent[]): boolean;
```

**它按键是「事件是否携带 `detail.command`」，与「这次运行成功还是失败」无关。**

**把 F2 接上去会发生什么**（逐步）：

1. 玩家触发（`actor: 'player'`）；命令第 2 步失败 ⇒ F2 落一条 `entity_edited`，`detail.command = 'investigate-clue'`。
2. 玩家不是 `excludeActor` 的目标（§2.2 实测：读者是 `writer`/`character:<id>`）⇒ **这条失败事件进作家下一轮注入**。
3. `hasSettledCommand(events)` → **`true`** ⇒ 判定序落到 `10:447` 的序 1′ ⇒ 作家拿到 `CASE_ROLL_RESOLVED_SETTLED`，其定稿文案（`10:469-470` 逐字）：

   > `A dice check has just resolved and the world has already settled what it owed: the result is on disk. Report what it means this turn; **do not grant, move, or write any of it again.**`

4. **而事实是：奖没发出来。** 作家被**明确命令不要补救**。⇒ 奖励**永久不落地**——玩家掷了骰、看到失败，此后又被告知「世界已经结算了」。

**这是硬门 2 的**反向**违反**（该给的永远不给），比重复结算更难发现（世界自洽、无错误、无半成品）。它与 `05:413` 自己登记的那类「静默失败」同族。

**更糟的是 `10:612` 把这个 bug 当成了「自洽」**：逐字「若 `[C-1]` 拍板『失败落账』，那条事件的 `detail` MUST 带 `command`，`settled` 分支就会启用——**两种拍板下行为都自洽**。」**实测为假**：
- F1 下失败无事件 ⇒ `settled=false` ⇒ 作家拿到 `CASE_ROLL_RESOLVED`（继续叙述），且同轮回执（`10:514`）告诉他「`Nothing was granted. Say what the player can still try.`」——**F1 自洽**；
- F2 下失败有事件 ⇒ `settled=true` ⇒ 作家被**禁止补救**——**F2 不自洽**。`10:612` 只在 F1 下成立。

⇒ **这条是判 F1 的决定性理由**：F2 不是「贵」，是**会静默造成永久漏发**。`05` 与 `09` 都没看到它，因为 `05` 只评渲染面、`09` 只评审计面，**没有一份文档把 F2 接到 `10` 的判定上走一遍**。

### 4.2 【新发现】`06:588` 与 `06:611` 自相矛盾 —— 作家究竟读不读得到 `command_error`？

`06 §7.5` 用它**论证失败必须是卡片而不是 toast**（`06:585-589`）：

> `06:588` 逐字「**不可 diff**。toast 不进文件，**作家注入也读不到**，Agent 无法据此自修。」

`06 §7.6②` 用它**论证失败已经被作家看到**（`06:609-611`）：

> `06:611` 逐字「5. 源卡上 `command_error` **默认展开**，常驻。刷新后仍在（它是 frontmatter）。**作家下一轮读到它**（归 `10`）。」

**两者不能同时为真**：`06:588` 说作家**读不到**（用来否定 toast），`06:611` 说作家**下一轮读到**（用来肯定卡片）。

**实测：`06:611` 的那半句没有任何机制支撑。**

- `docs/command/10-事件与作家上下文.md` 全文**零次**出现 `command_error`（`grep -c` 实测 = 0）。
- 作家注入的分节固定六节（`packages/shared/src/render/sections.ts:423-430` 的 `WRITER_SECTIONS`：`viewpoint / layer_files / cast / bag / recent_chalk / dynamics`）。**没有一节读焦点卡的任意 frontmatter key。**
- `layer_files` 只印「路径—kind—标题—摘要」（`sections.ts:107-112` 的 `layerLine`），**不印 `command_error`**。
- `look_at`（`packages/shared/src/actions/look-at.ts:267` → `renderEntityBlock` → `entityBody`，`packages/shared/src/render/layer-page.ts:90-107`）只印**正文**与 `preview/sign`，**不印 `command_error`**；`formatInteractiveText`（`packages/shared/src/rules/interactive.ts:398-438`）只印 `status/choice/roll_dice` 三块，**不含 `command_error`**。
- 唯一的自动读者是**前端**（`06 §7.5` 的 widget），而前端不是 Agent。

⇒ **`06:611` 是错的（或至少未经取证）**：作家要看到 `command_error`，**只有一条路——它自己主动 `look_at` 那张卡**，而没有任何注入或回执提示它去这么做。**`06:588` 那一半才是对的。**

**对 `[C-1]` 的影响**：这正是 F1 唯一的真实缺口（「其他 actor 事后看不到」），而且它**比 F1 的拥护者以为的更严重**：不是「其他角色 Agent 无法叙述」，而是**连触发链上的作家也错过了**。但——**这不改变 F1 的判定**，因为：
- 触发者**当轮**已通过 `details` 看到（`10 §3.8.2`，覆盖作家调 `roll_dice` 的场景）；
- 玩家触发 + 作家未醒的场景，失败由玩家侧 `command_error` 与下一轮 `CASE_ROLL_RESOLVED`（`settled=false`，F1）覆盖——**作家被告知「这次判定还没有被叙述」**，它去 `look_at` 就会看到 `command_error`；
- 把 `06:611` 改成「作家**下一轮看不到**；它必须 `look_at`」是**文档修正**（P3），不是设计变更。

### 4.3 【新发现】`06:469` 把「命令写错」映射成 `skipped`，与契约 §5.2 一起把 F3 的失败类语义挤没了

`06:469` 逐字：`③ 命令写错（YAML 非法 / 文件不存在） → status: 'skipped'`。而 `06 §7.1`（`:477-489`）的码表里，`command_invalid`/`command_missing`/`command_disabled` 全部映射到 `skipped`。

这与「失败落账」叠加后产生一个**覆盖面缺口**：若 F3 被采用，需要落账的失败**至少有四类**（写错、目标缺失、部分失败、写盘失败），而 `06` 已把其中两类归为 `skipped`（非失败）。⇒ F3 的「一个 `command_failed` 类型」**装不下**这个分类，需同时改 `06` 的状态枚举。这是 F3 代价被低估的**第三处**（前两处是 `05:1055` 自列的三处同步）。

### 4.4 【新发现】`02:559` 的「触发层是 `command_error` 的一个写入者」与 `05:87` 的「写入器直接 `delete`」有**双写者**风险

`02` 自称「触发层是它的一个写入者」（`02:559`），`05` 自称「本文定形状与写入/清除时机」（`05:60`）且写入器**直接 `delete` 键**（`05:87`）。两个写入者 + 「单数、不是数组」（`05:85`）⇒ **后写者整键覆盖前写者**，且两个写入者的**清除条件可能不同**（`05` 的是「同 key 到 done」）。这是实现期的真实竞态面（同步执行下是「自己踩自己」，不是并发）。`[推断]`：`05 §8.3` 的 `withSourceLock` 会串行化同一 source 的写入，所以**可能无害**——但**没有任何文档写过这一点**，登记为待闭合。
