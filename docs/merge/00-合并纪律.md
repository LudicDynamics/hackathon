# 合并纪律（Merge Discipline）—— 冻结契约

> **本文是同一条纪律的三件套里的契约件**：① 本文（怎么做）② `docs/merge/*.md`（做过的登记）③ `tools/check-merge-log.mjs` + `.githooks/pre-push`（怎么强制）。
> **2026-09-13 立。** 缘起：`origin/niko` 那次大合并（543 文件 / 9 冲突文件 / 18 冲突块）暴露了一类**静默丢失**，事后花了两天才补回来（复盘见 §5）。
>
> **一句话**：**每一次合并，都要有一份人看得懂的登记；没有登记，不许推送。**

---

## 1. 为什么要立这条纪律

合并是**唯一一种「git 自己会改你的代码、且改错了不报错」的操作**。它有三个特性叠加：

1. **冲突块的解决没有留痕。** `git log --merges` 只记「合过」，不记「怎么解的」。你当时为什么选 A 不选 B，只存在于当时的对话里——对话一关就没了。
2. **两边各自绿、合起来死的漂移，门禁不一定抓得到。** 2026-09-12 抓到 14 条 WS 帧漂移；`origin/niko` 合入又丢了 8 个 i18n 键、1 个入站 WS 帧、21 个角色的 `voice:`。这些都是**事后**靠人肉清点才发现的。
3. **合并提交是「第一个父提交 + 第二个父提交」的合成，`git diff` 看不全。** 想知道某次合并在某个文件上到底保留了哪边，必须 `git diff <merge>^1 <merge>` **和** `git diff <merge>^2 <merge>` 各看一次——**没人会在两天后还愿意做这件事**（实测：`813c0f3` 丢的 `airp_init` 就是这么漏掉的，见 §5.2）。

所以纪律的目标不是「走流程」，是**给未来的自己留一张能复原现场的地图**。

## 2. 登记文件（硬要求）

### 2.1 命名与位置

```text
docs/merge/<title>-<merge 短哈希 7 位>-<作者>.md
```

| 段 | 规则 | 例 |
|---|---|---|
| `<title>` | 中文或英文短标题，**kebab-case**，说清合了什么 | `niko-沉浸式界面` / `windows-启动入口` |
| `<7 位短哈希>` | **被登记的那个 merge commit** 的 `git rev-parse --short=7` | `813c0f3` |
| `<author>` | 小写 kebab，你平时用的代号 | `yoshi` / `niko` / `fangsunjian` |

**解析规则（门禁按此实现）**：从右往左取最后两段 `-`，即 `<...>-<7hex>-<author>.md`。所以 `title` 里可以有 `-`（`niko-沉浸式界面-813c0f3-yoshi.md` 的 title 是 `niko-沉浸式界面`）。

> 为什么短哈希进文件名：**让「哪次合并」和「哪份登记」互相可查**。你 `git log` 看到一个 merge，直接就能猜出登记文件叫什么；反过来在 `docs/merge/` 看到一份登记，文件名里就有它登记的 commit。
> 为什么不是时间戳当唯一标识：**哈希是内容派生的，时钟不是**。同一天可能有多次合并（2026-09-13 一天就合了 3 次），日期会撞、会因时区错位、会在 rebase/amend 后失真。

### 2.2 必含三节（门禁逐字核验）

**标题、`## 1. 这次合了什么`、`## 2. 冲突处理`、`## 3. 验证`** 四者必须有，`## 2` 内容**不得为空**（≥40 字符）。

```markdown
# <一句话标题>

> 合并 `<7hex>` · 父提交 `<7hex>`（ours）与 `<7hex>`（theirs）· 作者 <you> · <日期>
> 来源分支：`<branch>`（<它是什么>）

## 1. 这次合了什么

- **对方带来的**：<列对方独有的东西——新世界 / 新模块 / 新协议>
- **我方带来的**：<列我方独有的东西>
- **两侧同时改的**：<就是下面 §2 要处理的>

## 2. 冲突处理

> 这一节是登记的**全部意义**。写「怎么解的」，不是「解了」。

| 文件 | 两侧各是什么 | 裁决 | 理由 |
|---|---|---|---|
| `path/to/file` | A 侧 <…> / B 侧 <…> | 取 B + 补 A 的 <…> | <为什么> |

**结构决策单独展开**（凡是「不是解冲突块，是把两条演进缝成一个」的，都属于这里）：
- `<文件>`：<两侧的设计意图> → **裁决 <…>**，因为 <…>。

**静默丢失自查**（见 §3 的清单）：这次有没有丢**没报冲突**的东西（自动合并吃掉、被删除、被改名）？

## 3. 验证

```bash
# 实跑的命令与结果，别写「应该没问题」
pnpm build && pnpm test            # → PASS / 641/641
pnpm check:ws && pnpm check:bodies # → PASS
```

**浏览器冒烟**（UI 合并必做）：<跑了哪条路径、看到什么>
**未决/遗留**：<登记但不擅改的，或「无」>
```

### 2.3 何时写、何时推

**顺序不可颠倒**：`merge` → **写登记** → `pnpm check:merge` 绿 → `commit`（登记可与 merge 同一次提交，也可紧随一次）→ `push`。

- 登记文件**和被登记的 merge 在同一段历史里**，这样 reviewer 拉到这个 merge 就同时拿到地图。
- `tools/git-hooks/pre-push` 会在 `git push` 时再跑一遍本门禁，**没登记就推不出去**（见 §4）。

## 3. 合并执行的机械清单（先做检查，再解冲突）

> 这份清单是**从两次真实事故里提炼的**，不是理论。逐步照做，别跳。

### 3.1 动手之前

1. **看清分叉**：`git fetch --all --prune` → `git rev-list --left-right --count A...B`。**两边都有对方没有的提交才是常态**（`main` 与 `origin/niko` 互为领先 18 / 20 条）。
2. **只读试合并**（不碰工作树）：`git worktree add -f /tmp/probe --detach <theirs>` → `cd /tmp/probe && git merge --no-commit --no-ff <ours>`。**在临时 worktree 里看清全部冲突，再决定策略**；看完 `git worktree remove --force`。
3. **逐文件两侧对照**：`git show <theirs>:<path>` vs `git show <ours>:<path>`。**不要只看冲突块**——块外的自动合并也可能丢东西（§3.3）。

### 3.2 解冲突时

4. **判据是「两侧分叉后各自的增量」，不是冲突块数。** 9 文件 / 18 块听着不多，但里面两处是「730 行 vs 589 行的两套 UI 外壳」——那是**融合**，不是解标记。
5. **先定结构决策，再机械解。** `origin/niko` 那次的三处结构决策（角色 README frontmatter 形状 / `CharacterModal` 两套实现 / `i18n` 两语 vs 三语）定了之后，其余 9 块都是取并集。
6. **取并集时逐条核**：import 取并集、state 取并集、`switch case` 取并集、`.gitignore` / `package.json` scripts / `.env.example` 取并集。**丢一个 case 就是丢一条 WS 帧。**
7. **别信「main 的版本就是对的」。** 实测：`moveFile` 我一度按审查建议回退成 main 的裸 `rename`，**niko 的测试立刻红**——而测试才是对的（`docs/tools/04` 明确要排他）。合并时「我方」未必是真相。

### 3.3 合完之后（**静默丢失自查 —— 这一步最容易被省，也最致命**）

> `airp_init` 入站帧、8 个 i18n 键、21 个 `voice:` 声明，**三次都不是冲突块里的**，是自动合并/删除/改名吃掉的。

8. **按「连接面」整面扫，而不是按冲突块扫**：

   | 面 | 怎么扫 |
   |---|---|
   | **WS 帧** | 服务端发射面 ↔ 前端消费面 ↔ `docs/tools/12 §6.2`：`pnpm check:ws` |
   | **HTTP 请求体** | 前端 body 键集 ↔ `docs/wiring/00 §6`：`pnpm check:bodies` |
   | **i18n 键** | 用到的 `t('…')` 必须解析：`pnpm check:i18n` |
   | **工具/组件注册** | `registerAction` / `CARD_FORMS` / 事件 `type` 枚举：diff 两侧计数是否相等 |
   | **preset slot** | 四个 slot 都在：`pnpm probe:prompt` |
   | **导出符号 / 删除文件** | `git diff A B --diff-filter=D` 与两侧 `ls` 对照 |
   | **内容声明**（`voice:` 等） | `pnpm check:voices` / `pnpm check:emotions` |

9. **两条链要「两端都在」才算活。** 例：`airp_init` 的**服务端 handler 在、前端发送方没了**——这不是「弃用」（弃用会两侧都删），是**合丢了一半**。判据：**当一个能力的生产端或消费端单独存活时，去两侧查它原来是不是成对的。**
10. **门禁红了，先问「门禁为什么没抓到」，再反向验证。** `origin/niko` 合入时两条真 BLOCKER（gateway 请求体形状错）能进 main，是因为 `check:bodies` 只认内联 `fetch(...JSON.stringify)`，看不见 gateway 的封装形状。**修完 bug 要把门禁补上，并把它反向验证（故意改坏 → 门禁必须红）。**

### 3.4 验证

11. **`main` 必须可编译可跑**（§6.2）：`pnpm build` + `pnpm test` + 全部门禁 + 探针，见 §6.4。
12. **UI 合并必须浏览器冒烟**，且**用 A/B 定位回归**：拖拽松手闪现我先猜错（以为是 hover 走 React），A/B（同一棵树、同一脚本、`frame()` 开/关）才证到根因是取景 effect 回写了座位。**第一直觉不可信。**

## 4. 强制机制

| 层 | 手段 | 挡什么 |
|---|---|---|
| **推送时** | `tools/git-hooks/pre-push` → `pnpm check:merge` | 没登记的 merge **推不出去** |
| **收工时** | `pnpm check:merge`（在 §6.4 自检链里） | 同上，且给 CI/reviewer 一个机械判据 |
| **评审时** | 人读 `docs/merge/<…>.md` 的 §2 | 登记写没写「怎么解的」 |

**启用推送钩子**（每台机器一次，`core.hooksPath` 指向仓库内 `.githooks/`）：

```bash
pnpm hooks:install        # = git config core.hooksPath .githooks
```

> 钩子不随 clone 生效（git 不传播 hooks），所以它是**双保险**：`pnpm check:merge` 进自检链是主，pre-push 是兜底。**没装钩子的人靠自觉；装了的人想漏也漏不掉。**

### 4.1 门禁的判据（`tools/check-merge-log.mjs`）

- **范围 = `git log --merges --first-parent HEAD`**，不含被合进来的分支内部 merge。理由：这是**你即将推送的那条线上落地的合并**。（分支内部合并的登记**强烈建议**并会被主条目引用，但门禁从 HEAD 看不见它。）
- **豁免 = `docs/merge/BASELINE.md` 里逐个列出的 SHA**。立法之前的历史合并一次性 grandfather；**用 SHA 白名单，不用日期**——日期是门禁信不过的时钟，白名单可以逐行审计。
- **每条非豁免 merge 必须**：① 有对应登记文件；② 含三节标题；③ 正文引用 merge 短哈希与**两个父提交**短哈希；④ `## 2` 非空。
- **反向验证**：`tools/check-merge-log.test.mjs` 驱动纯核心 `evaluate()`（不需要 git 仓库），逐个断言「门禁能红、能绿、豁免生效」。

### 5.4 方法论教训（**写进 §3 的就是这几条**）

1. **冲突块数 ≠ 工作量**：判据是**两侧分叉后各自的增量**。
2. **A/B 是唯一硬判据**：第一直觉（hover state）被 A/B 推翻。
3. **测试红了先怀疑「谁对」**：`moveFile` 回退到 main 的裸 `rename` 让 niko 的测试红，而**测试才是对的**。
4. **门禁盲区要主动堵**，并**反向验证门禁真能抓**。
5. **子代理只读清点 + 主代理实测复现**：scout 给的 `file:line` 是线索不是结论；每条 BLOCKER 都由主代理 curl/浏览器复现过。

## 6. 与既有纪律的关系

- **§6.1 提交即推送**：本文是它的**合并分支**。提交即推送不变；**合并**多一道「先登记、后推送」。
- **§6.2 `main` 必须可编译可跑**：§3.4 的验证就是它的合并版。
- **§6.3 架构文档跟代码走**：合并若改了架构/协议，**同 commit 改对应文档**——这条不因合并而豁免。
- **§6.4 收工自检**：`pnpm check:merge` 已并入自检链。
- **§6.5 Build 红线**：合并后**必跑 `pnpm build`**——合并的正是源码，产物不 build 就静默跑旧代码。

## 7. 附：机械命令

```bash
# 启用推送钩子（每台机器一次）
pnpm hooks:install

# 门禁
pnpm check:merge

# 分叉全景
git fetch --all --prune
git rev-list --left-right --count origin/main...origin/niko

# 只读试合并（不碰工作树）
git worktree add -f /tmp/merge-probe --detach origin/niko
cd /tmp/merge-probe && git merge --no-commit --no-ff origin/main    # 看清全部冲突
cd - && git worktree remove --force /tmp/merge-probe && git worktree prune

# 单文件两侧对照（不要只看冲突块）
git show origin/niko:<path>      # theirs
git show origin/main:<path>      # ours
git diff <merge>^1 <merge>       # 合并相对我方保留了什么
git diff <merge>^2 <merge>       # 合并相对对方保留了什么

# 找「只在一侧被删」的东西（静默丢失高危面）
git diff --diff-filter=D --name-only <base> <ours>
git diff --diff-filter=D --name-only <base> <theirs>
```
