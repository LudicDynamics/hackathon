## 1. 一句话与定位

**`link` / `arrange` 在 `canvas.db` 里改了线条或坐标之后，服务端把「改了哪几行」随帧送给前端，前端就地把这几行合进 `worldState.links` / `worldState.items`——不重取整层。**

三条定位：

1. **它是「工具路径」专属的帧**（`docs/tools/12 §6.5:636-646`）。玩家拖卡走 `card_position`（`routes/world.ts` 的 `router.post('/card/position')`，其 `eventBridge.broadcast({ type: 'card_position', path: cardPath, x, y })` 那一行），agent 调 `link`/`arrange` 走本帧。两者**不重叠**：`apps/server/test/smoke-routes.mjs:93` 逐字断言「`/card/position` does NOT broadcast `canvas_patched`」。
2. **本帧存在的唯一意义就是「不 `fetchLayer`」**（`docs/后端实现计划.md:214` 逐字：「只刷线/位，不整层重取」；契约 §9 反模式 8）。若在消费它时顺手 `fetchLayer`，本帧就是纯多余的带宽——因为 `file_changed` 已经会兜底重取（§11.1 实测：`canvas.db-wal` 会触发 `file_changed`）。
3. **它是演出帧，不是世界事件**（`docs/tools/00 §5.3`）。改动的是「世界现在什么样」（`canvas.db` 是当前值库），永远不落 `events` 行（§5）。

**服务端已经做完，本批只做消费侧。** 映射点 `apps/server/src/engine/event-bridge.ts` 的 `if (event.toolName === 'link' || event.toolName === 'arrange')` 分支已把 `details` 完整塞进帧（实读；`[行号待复核]`，实读时在 `:134-146`），且 `apps/server/test/map-engine-event.test.mjs:44-67` 已断言其形状。**本批服务端零改动**（§4）。

## 3. 行为契约逐步（每步写「漏了会怎样」）

### 3.1 门禁形状（守护前提）

```ts
case 'canvas_patched': {
  // ① 形状守卫：缺 layer 或缺 kind 的帧无法判定归属，整帧忽略。
  if (typeof msg.layer !== 'string') break;
  // ② 层归属：契约 §7 —— 别的层的改动不该让当前页抖一下。
  if (msg.layer !== layerRef.current) break;
  // ③ 按 kind 分派；未知 kind（服务端未来扩展）→ 忽略不崩。
  if (msg.kind === 'links') { /* §3.2 */ }
  else if (msg.kind === 'cards') { /* §3.3 */ }
  break;
}
```

**漏了 ② 会怎样**：作家在 `world/intro` 摆位，玩家正在 `map` 看——`items` 里没有那张卡（`setState` 的 map 找不到 path），而 `links` 里会凭空多出一条**端点不在本层的线**：`buildPaths` 的 `elForPath`（`LinkLayer.tsx` 内，`[行号待复核]`，实读时在 `:180-182`）找不到元素 → 不画（侥幸不崩），但 `registry` 里留下的悬空行会让 `refreshLinkArchives`（`LinkLayer.tsx:159` 的 `export function refreshLinkArchives`）把「最新的虚线」判给一条不存在的线 → **本层真正的虚线被误标 `.thread-archived`（`index.css:161-163`：`opacity: 0 !important`）而消失**。这不是理论风险：`refreshLinkArchives` 按数组顺序取最后一个 dashed，插进一条更晚的跨层 dashed 就会夺走 `.thread-latest`。契约 §7 的「整帧忽略」正是为这类「别的层的状态污染当前页」设的。

**漏了 ①（`layer` 缺失时不忽略、而是照合）会怎样**：`details.layer` 恒有值（两个 type 都必填 `layer: string`，`canvas.ts:32`/`:40`），故这是**纯防御**——但若真缺失（未来某个只读动作复用了 `kind`），照合的结果是把行合进当前层，而行的 `layer` 字段是别的层：高亮/归档语义会作用在错误的层。忽略是唯一安全的默认。

### 3.2 `kind:'links'` 逐步

对 `frame.links` 逐行（顺序敏感，见下）：

1. **行形状校验**：`id` 必须是字符串。非字符串 → **跳过该行**（不整帧放弃：一条坏行不该吞掉同批其余好行；但也不能静默——§7）。
2. **`action === 'deleted'`** → 从 `links` 里**按 `id` 过滤掉**。缺席（本来就没有该 id）→ no-op（删除是幂等的，重复删不报错）。
3. **否则（`created` / `updated` / 未给）** → **按 `id` upsert**：
   - `id` 已存在 → 用帧里的整行**替换**。
   - `id` 不存在 → **append 到数组末尾**。
4. **顺序语义**：append 到末尾 = 「最新」（`LinkLayer.tsx:154-158` 注释逐字：「Registry insertion order follows the `links` array, so "last" = last row in the payload」）→ 新增的 dashed 自动成为 `.thread-latest`（`:163-167`）。这是**刻意保留**的语义。
5. **引用纪律**：一次 `setState` 里把整批行合完（同一个新数组），**绝不每行一次 setState**（N 行 → N 次 render + N 次 SVG 全量重建，§3.5）。

**为什么是「整行替换」而不是「浅合并字段」**：`LinkRecord` 是**完整行**（服务端回填整行，§2.1），`color: null` 是**有语义的默认值**（「用 style 的默认色」，`canvas.ts:46-48` 逐字）。浅合并 `{...old, ...row}` 在「畸形帧缺 `color`」时会把上一版的颜色留在本应清空的位置；整行替换 + 缺字段补默认（`null`/`false`/`0`，与 `rowToLink`：`local-store.ts:1057-1069` 同款）是唯一与「完整行」前提一致的做法。

**漏了「按 `id`」而按 `(from,to)` 会怎样**：一对卡片之间**允许多条线并存**（`docs/tools/09 §2.4:137`；`id` 是 PK、`(from,to)` 不是唯一约束）→ 按 `(from,to)` upsert 会把两条线压成一条。`id` 是身份，`(from,to)` 是规格，不能互换。

### 3.3 `kind:'cards'` 逐步（**与既有 `card_position` 同一份逻辑**）

契约 §7 逐字：「与 `case 'card_position'` **同一份幂等合并逻辑**（按 `(path,x,y,z)` 合并；`x/y` 相等的早退守卫，不加 id）」。这是一条**硬要求**：不允许另写一套。

现状 `case 'card_position'`（`useWorld.ts:342-359`，实读）：

```ts
case 'card_position':
  if (typeof msg.path === 'string' && typeof msg.x === 'number' && typeof msg.y === 'number') {
    setState((s) =>
      s ? { ...s, items: s.items.map((it) => (it.path === msg.path ? { ...it, x: msg.x, y: msg.y } : it)) } : s
    );
  }
  break;
```

它**没有** `x/y` 相等早退，**也不处理 `z`**，**也不写 `stateRef`**。契约 §7 与本任务都要求把两者收敛成**同一个函数**，并补上早退守卫（`docs/tools/12 §6.5:509` 已预先背书：「若实现时发现重复渲染，用 `x`/`y` 相等的早退守卫，而不是给帧加 id」）。收敛后的唯一实现（`NEW`，落点 §8.1）：

```ts
// 幂等合并一张卡的坐标。返回同一引用 ⇒ 无变化（调用方据此免去 render）。
export function mergeItemPatch(
  items: LayerItem[],
  patch: { path: string; x?: number; y?: number; z?: number }
): LayerItem[] {
  for (const it of items) {
    if (it.path !== patch.path) continue;
    const x = patch.x ?? it.x;
    const y = patch.y ?? it.y;
    const z = patch.z ?? it.z;
    // 早退守卫：值全等 ⇒ 一个字节都不动（契约 §7 / 12 §6.5:509）。
    if (it.x === x && it.y === y && it.z === z) return items;
    return items.map((o) => (o.path === patch.path ? { ...o, x, y, z } : o));
  }
  // 卡不在本层 items 里（跨层帧已在上游被拦；或该 path 是 scene README）⇒ no-op。
  return items;
}
```

`case 'card_position'` 与本帧都调它：

```ts
case 'card_position':
  if (typeof msg.path === 'string' && typeof msg.x === 'number' && typeof msg.y === 'number') {
    setState((s) => (s ? { ...s, items: mergeItemPatch(s.items, { path: msg.path, x: msg.x, y: msg.y }) } : s));
  }
  break;
```

**为什么返回「同一个数组引用」而不是「总是新数组」**（这是本篇与 `card_position` 现状的**唯一行为差异**，且是修正）：

1. **免 render**：`state` 引用不变 ⇒ React 跳过 `Canvas` 子树重渲染。一条重复帧（同卡同坐标）在现状下会白跑一次整棵画布树；`docs/tools/12 §6.5:643-644` 逐字点了这个场景（同一次拖拽发两帧「值相等，幂等，但白跑一次 render」）。
2. **保住 `stateRef` 与测量缓存**：`Canvas.tsx:145-149` 的 `invalidateMeasures()` 以 `[items, links]` 为键，`items` 引用不变 ⇒ 不清缓存。
3. **不改 `CanvasObject` 的 `item` prop**：新对象会让每个 `CanvasObject` 重渲染并重写 inline `left/top`（`CanvasObject.tsx:203-214`），早退把这条路径整个短路。

**漏了早退会怎样**：每次 `arrange` 重排 N 张卡 → N 个新对象 → N 个 `CanvasObject` 重渲染并写 inline 坐标，而 `elementBox` 的缓存（`lib/measure.ts:26-28` 的 `generation` 计数器）未失效 → 位置读写在同帧竞争，表现为**重排后线读到旧坐标**（§3.4）。

**「按 `(path,x,y,z)` 合并」的 `z` 语义**：`arrange` 的 `z` 是 `z_index`（`docs/tools/09 §2.6:220`）；`card_position` 的帧**不带 `z`**（`routes/world.ts` 的 `router.post('/card/position')` 只发 `path/x/y`）→ `patch.z === undefined` ⇒ `z = it.z`（保持），与现状逐字兼容。

### 3.4 合并后必须触发 `LinkLayer` 重算——**机制要选对**

`LinkLayer` 的几何有两个独立入口：

| 入口 | 触发条件（`file:line`） | 覆盖什么 |
|---|---|---|
| `buildPaths(svg, links)` | `useEffect(..., [links])`，`LinkLayer.tsx` 的 `LinkLayer` 组件内（`:218-230`，`[行号待复核]`） | **注册表重建**：删掉全部旧 `<path>`/圆点，按新 `links` 数组重新 `elForPath` 找 DOM、建节点、重算 `d` |
| `updateAllLinks()` | 模块态，`LinkLayer.tsx:133` 的 `export function updateAllLinks`；被 `Canvas.tsx` 两处显式调用（拖拽 `move` 回调与落定回调，实读时在 `:328`/`:376`，`[行号待复核]`） | **只重算已有节点的 `d`/圆点坐标**，不动注册表（`LinkLayer.tsx` 的 `updateAllLinks` 实现体） |

**结论（确定做法，含理由）**：

- **`kind:'links'` 只靠 `[links]` 引用变化**（`buildPaths` 路径）。理由：新增/删除/改样式的线**必须重建节点**——样式在节点创建时写死（`stroke`/`stroke-width`/`thread-dashed` class，`LinkLayer.tsx:186-194`），而 `updateAllLinks` **只改 `d` 与圆点，改不了颜色/线型**。故此路**只能**走 `useEffect([links])`，也正是契约 §7「合进 `worldState.links`，触发 `LinkLayer` 重算」的字面落法。
- **`kind:'cards'` 必须补一条 `updateAllLinks()`**。**这是本篇发现的真实缺口**：`arrange` 只改 `items` 坐标，`links` 引用**不变** ⇒ `useEffect([links])` 不跑；而 `updateAllLinks()` 今天**只在拖拽热路径被调用**（`Canvas.tsx` 的两处调用点：`move` 回调与落定回调；实读时在 `:328`/`:376`，`[行号待复核]`）。即：**agent 重排一层卡之后，所有关系线停留在旧坐标，直到下一次 `fetchLayer`**（线「脱锚」）。修法（落点 §8.2）：

  ```ts
  // Canvas.tsx —— 坐标变化（拖拽或 canvas_patched 合并）后重算线几何。
  useEffect(() => { updateAllLinks(); }, [items]);
  ```

  **为什么挂 `[items]` 而不是从 `useWorld` 直调 `updateAllLinks()`**：`useWorld` 是**状态层**，`LinkLayer` 是**渲染层**；从 `useWorld` import `LinkLayer` 会反转依赖方向（现状 `Canvas → LinkLayer`，`useWorld.ts` 的 import 全是 `lib/`，谁也不依赖）。且 React 提交顺序保证 `useEffect` 在 DOM 写入之后跑，读到的 `left/top` 是新值——**direct call 若在 `setState` 之前跑会读到旧 DOM**。故「引用变化驱动、effect 内调用」是唯一定序正确的做法。

  **漏了会怎样**：§10.2 判据 3 直接失败（线不跟着卡走），且**静默**（无报错，只是画错）。**独立复核**（`R2`/`R5` 均确认）：`updateAllLinks()` 全仓调用点仅 `Canvas.tsx:328`/`:376` 两处（均拖拽热路径），`useEffect(..., [items, links])` 只 `invalidateMeasures()` 不重算线——**「`arrange` 改坐标后线脱锚」是真缺口，浏览器可验**（`R5:192`：「发现的一个真缺口修得很好」）。

- **为什么不用「给 `links` 造新数组」来顺带覆盖 cards 情形**：会**误触 `Canvas.tsx` 的 `useEffect(() => { clearAllLifts(); }, [links])`**（`[行号待复核]`，实读时在 `:141-143`）——把玩家拖拽会话中的 z 提升全部清掉（§7）。

## 5. 落账（**演出帧一律不落事件**——说清为什么）

**本帧不落事件，且本批也不新增任何落账。** 三层理由：

1. **通道定义**（`docs/tools/00 §5.3` / `docs/tools/12 §6.1:563`）：事件回答「世界怎么变成现在这样的」，本帧回答「世界现在什么样」。`canvas.db` 自己就是当前值库（`docs/tools/09 §1:30` 逐字：「关系线、卡片坐标、角色 presence 属于**当前值**，存 `canvas.db`」）。
2. **动作自己不落**（**实测**）：`grep -c appendEvent packages/shared/src/actions/canvas.ts` = **0**。`linkCards` / `arrangeCards` 全程只调 `store.upsertLink` / `deleteLink` / `placeCard` / `placeCards` / `readFile` / `resolveLayer` / `seatUnplaced`（`canvas.ts` 内 `store.*` 全集实读）。没有事件可转、也没有事件需要补。
3. **补一条事件会立刻造成可见故障**：`world_event` 的消费分支（`useWorld.ts` 的 `case 'world_event'`）**必然 `fetchLayer`**（`[行号待复核]`，实读时在 `:326-334`）。即「为一个『不重取整层』的帧补一条必然触发整层重取的事件」——自相矛盾。另外事件表按字符膨胀、`seq` 游标被无意义推高（`docs/tools/09 §5.3:416` 同款结论）。

**机械判据**：实现完成后 `grep -c "appendEvent" apps/server/src/engine/event-bridge.ts` 仍为 1（`:265` 是注释词，非调用——实读）；`grep -c appendEvent packages/shared/src/actions/canvas.ts` = 0。运行期判据见 §10.2 判据 5（`getMaxSeq()` 前后不变）。

### 6.1 状态更新（精确形状）

```ts
case 'canvas_patched': {
  if (typeof msg.layer !== 'string' || msg.layer !== layerRef.current) break;   // §3.1 ① ②
  if (msg.kind === 'links') {
    if (!Array.isArray(msg.links)) break;
    setState((s) => {
      if (!s) return s;
      const next = mergeLinkPatch(s.links, msg.links, msg.action);
      if (next === s.links) return s;          // 无变化 ⇒ 同一 state 引用（免 render）
      const out = { ...s, links: next };
      stateRef.current = out;                  // ← 见下「stateRef 同步」
      return out;
    });
  } else if (msg.kind === 'cards') {
    if (!Array.isArray(msg.cards)) break;
    setState((s) => {
      if (!s) return s;
      let items = s.items;
      for (const c of msg.cards) {
        if (typeof c?.path !== 'string') continue;   // 坏行跳过，不吞整批
        items = mergeItemPatch(items, c);
      }
      if (items === s.items) return s;
      const out = { ...s, items };
      stateRef.current = out;
      return out;
    });
  }
  break;
}
```
**`stateRef` 同步是必须的**：`stateRef.current` 在 `fetchLayer` 里被写（`useWorld.ts:137`，实读），并被 footprint 调度器（`widths` 读取处，`:240`）与 `moveCard` 的回滚（`:166`/`:187`）当作权威快照读。若本帧只 `setState` 不写 `stateRef`，则 ① footprint 上报的宽度回退到旧值，② `moveCard` 失败回滚会把坐标**回滚到合并之前的快照**。现状的 `case 'card_position'` 分支（`:342-359`）**也有这个缺口**，本批顺手补齐（同一次 `setState` 内写，无额外 render）。

**`break` 而非 `return`**：`break` 出去后仍走 `catch` 边界（`catch` 处理函数，`[行号待复核]`，实读时在 `:387-389`），与既有各 `case` 形状一致。

## 7. 错误与边界（失败必须可见，不静默）

| 场景 | 期望行为 | 为什么 / 漏了会怎样 |
|---|---|---|
| **`layer` 缺失** | 整帧忽略 | §3.1 ①。「是否当前层」不可判定，合了就是污染 |
| **`layer !== 当前层`** | 整帧忽略，**不 warn** | 契约 §7。这是**正常流量**（作家常在别的层干活），不是错误。反模式 3 禁的是「拿 warn 当失败可见」，**不等于「任何忽略都要 warn」**——正常路径若都 warn，控制台被刷满，真正错误被淹没 |
| **`kind` 缺失/未知** | 整帧忽略，**可见**：`console.warn('[canvas_patched] unknown kind', msg.kind)` | 未知 kind 是**契约漂移信号**（服务端加了新 kind 前端没跟上），必须看得见。此处 `warn` 是诊断用途，不阻塞画面 |
| **`links` / `cards` 非数组** | 该分支 no-op，**可见 warn** | 畸形帧。与 `world_event` 的 `if (!ev || typeof ev.id !== 'string') break;`（`:330` 逐字注释「畸形帧不污染去重集合」）同款纪律：**先判形状，再动状态** |
| **单行 `id`/`path` 非字符串** | 跳过该行，其余照合，**可见 warn 带行内容** | 一批里一条坏行不该吞掉其余，但不静默 |
| **`kind:'cards'` 的 path 不在 `items` 里** | no-op，**不 warn** | 正常场景：该 path 是 `scene`（层的 README，`routes/world.ts` 的 `/layer` 分支把 `scene` **单独返回、不在 `items`**；`[行号待复核]`，实读时在 `:574-591`）。`arrange` 可以合法地摆位 scene README ⇒ 永远合不进 `items`。**若 warn，每次摆门牌都刷告警**。用 §10.2 判据 7 的负向断言守住「不崩、不 warn」 |
| **同一 id 帧乱序（旧值后到）** | 以**后到者为准**（last-write-wins） | 帧不带版本号（契约 §1 明列「不做 `expectedRevision`」）。乱序窗口 = 单次工具往返（ms 级），且 `canvas.db` 写入是同一进程串行 ⇒ 服务端发出顺序 = 提交顺序。**接受**；登记 §12 |
| **合并后 `links` 引用变了，且玩家正在拖拽** | **z-lift 被清**（`Canvas.tsx` 的 `useEffect(() => { clearAllLifts(); }, [links])`，`[行号待复核]`，实读时在 `:141-143`） | **真实回归风险**：`clearAllLifts` 的触发键是 `[links]`，其注释（`Canvas.tsx` 的 `links` 引用注释，`:138-140`）逐字说它是「server order restored」信号。`kind:'cards'` 不动 `links` ⇒ 安全；`kind:'links'` 会清。玩家拖卡时作家同时画线的概率低，且 lift 只影响拖拽会话内的叠放（`CanvasObject.tsx:19-33`），下一次拖拽即恢复。**接受 + 登记 §12** |
| **`action:'deleted'` 但行不在 `links` 里** | no-op | 删除幂等。服务端 `deleteLink` 返回 `false` 表示没删到（`local-store.ts` 的 `deleteLink`，`[行号待复核]`，实读时在 `:973-976`），但帧仍回填被删的行（`actions/canvas.ts` 的 `deleteLink` 分支用的是删除**前**读到的 `row`）⇒ 前端按 id 过滤即可，无需判存在 |
| **同一帧 `kind:'links'` 与 `cards` 都给** | 按 `kind` 只走一支 | `LinkDetails` / `ArrangeDetails` 各只有一个数组（`actions/canvas.ts`），服务端不会两个都给 |
| **帧在 `state === null`（首帧未落地）时到达** | no-op | `setState((s) => !s ? s : …)`——与既有 `case 'world_frozen'`（`[行号待复核]`，实读时在 `:336-341`）同款守卫。随后 `fetchLayer`（初始加载 effect，`:396-398`）会带来完整状态 |

**可见性的总纪律**：本帧的「失败」分两类——**畸形**（可见 warn）与**正常忽略**（静默）。区分它们本身就是设计：把正常流量刷成告警会让真正的畸形帧不可见。

## 11. 发现的冲突 / 需要修订的上位文档

### 11.1（主 agent 点名）`arrange` 改位后，`file_changed` 会不会覆盖本帧的增量合并？

**答案：会，且必然发生；但接受它——因为覆盖是幂等的，且本帧的价值不是「唯一通道」而是「即时通道」。** 论证链（全部实测/实读）：

1. **`canvas.db` 的写入会触发 `file_changed`**（**实测，非推断**）：`fs.watch(worldRoot, {recursive:true})`（`event-bridge.ts` 的 watcher 建立处，`[行号待复核]`，实读时在 `:365`）的忽略名单只滤 `.airpworld/assets/`、`.airpworld/sessions/`、`node_modules/`（同处 `:372-377`；**注**：`R2` 实读确认还含 `sessions/`）。spike（`node:fs` + `node:sqlite` + WAL，写两行）实测输出：`watched filenames: ['.airpworld/canvas.db-wal']`，`survives the ignore list (=> file_changed): ['.airpworld/canvas.db-wal']`。⇒ `upsertLink` / `placeCard` 落库 → `-wal` 变化 → 150ms debounce（`const WATCH_DEBOUNCE_MS = 150`，`event-bridge.ts`，`[行号待复核]`，实读时在 `:13`）后广播 `file_changed`。
2. **`file_changed` 在前端是整层重取**（`useWorld.ts` 的 `case 'file_changed'` 内 `void fetchLayer(layerRef.current)`，`[行号待复核]`，实读时在 `:323-325`；A 档定案未变，契约 §6b-5）。`fetchLayer` 会用 `/api/layer` 的完整响应**整体替换** `stateRef.current` 与 `state`（`useWorld.ts` 的 `fetchLayer` 内 `stateRef.current = next` 一带，实读时在 `:127-138`）。
3. **为什么仍接受**：
   - **`arrange` 的写入在 `file_changed` 之前**（工具动作先提交 `canvas.db`，`fs.watch` 才看到 `-wal`）⇒ 重取回来的**就是**新坐标，`mergeItemPatch` 的结果被同值替换 ⇒ **视觉上无跳变**（`items` 的引用变一次，但值相同；`CanvasObject` 的 inline `left/top` 写出同样的数值）。
   - **`links` 同理**：`upsertLink` 已提交，重取回来的行与帧里的一致（同一条 `rowToLink` 口径，`local-store.ts` 的 `rowToLink`，`:1057-1069`）⇒ 合并结果被同值替换。
   - **本帧的收益是「即时性」**：帧沿 WS 直达（工具 `tool_execution_end` 的那一刻），而 `file_changed` 要等 debounce + `fs.watch` 的交付 ⇒ 本帧把「线出现」提前约 150ms–数秒（WSL 的递归 watch 在大目录上不可靠，`docs/后端实现计划.md:482` 逐字点了这点）。**本帧消灭的是「等重取」的延迟，不是重取本身**。
   - **反过来说**：**若本帧自己不合并、只等 `file_changed`，则本帧毫无意义**（那正是契约 §9 反模式 8 警告的形态）。故「并存」不等于「本帧可省」。
4. **一处必须写明的诚实时序风险**：`fetchLayer` 有 stale-response 守卫（`useWorld.ts` 的 `reqSeqRef`，`[行号待复核]`，实读时 `:117` 自增、`:126` 判定），但**本帧不走那条路**（它直接 `setState`）。若一个**更早发出**的 `fetchLayer`（例如同一 turn 里 `chalk_landed` 触发的）在本帧**之后**才 resolve，它会把本帧的合并结果**整体盖回旧值**（该响应早于 `arrange` 的提交）。这是**既有的**通用竞态（`card_position` 同样受它影响），不是本帧引入；登记 §12。
5. **建议（登记给 `06`/后续）**：`docs/tools/05 §11 冲突 4:1079` 已建议把 `.airpworld/canvas.db*` 加入 `file_changed` 的忽略名单，并逐字留了退路「若评审认为『宁可多刷不可漏刷』，保留现状也可接受（幂等，只是带宽）」。**本篇的立场：保留现状**——因为若滤掉 `canvas.db-wal`，本帧就成了**唯一**通道，而本帧的可靠性依赖 WS 不断线（WS 重连期间的画布改动会彻底丢失）。**两条通道互为兜底，这是要保留的特性，不是要消灭的冗余。**
