## 1. 一句话与定位

**`dice_result` 是「裁决已经产生」的瞬时演出帧：agent 调用 `roll_dice` 落盘、落账之后，服务端把同一份裁决广播出来，前端用它演一次与玩家点击完全相同的骰子仪式。**

三件事决定了本篇的形状：

1. **它只演权威结果，不演触发假象**。帧到达时 `result/passed/rolls/crit/fumble` 已知；玩家 HTTP `RollDiceDetails` 也只有在权威 2xx details 到达后才能进入同一仪式。`roll_ceremony`（`performances.ts`）是不带结果的预备演出，不能另起一套结算仪式。
2. **它是多来源入口，不是多套实现**。玩家 HTTP、writer `dice_result`、character `dice_result` 都先经过各自的边界解析，再归一化为 `docs/ux/00 §4.6.2` 的 `DiceCeremonyInput`，最后只由一个 `DiceCeremony` 消费。HTTP 路径不伪造 WS 帧，WS 路径也不绕过权威结果。
3. **它是浮层，不是卡片装饰**。仪式是 `fixed inset-0`（`DiceRoller.tsx:339`），与卡片的座位无关——这一点在契约 §6b-5（`file_changed` 仍整层重取、可能重新排座）之后不再是可选项，而是必需（§6.4）。

## 2. 签名 / 载荷（逐字段与源码核对）

### 2.1 帧载荷（发射点实读，逐字段）

`apps/server/src/engine/event-bridge.ts:147-167`：

```ts
if (event.toolName === 'roll_dice' && !event.isError) {
  push({
    type: 'dice_result',

    path: details.path,
```

`push`（`:56-61`）统一补 `timestamp`，并在角色车道附加 `characterId`（A1 冻结）。`details` 来自 `event.result.details`（`:114-115`），形状 = `RollDiceDetails`（`packages/shared/src/actions/roll-dice.ts:25-50`）。既有测试逐字段锁死了它：`apps/server/test/map-engine-event.test.mjs:69-95` 用 `assert.deepEqual(dice, { type: 'dice_result', source: 'writer', ...details })`。

|---|---|---|---|
| `type` | `'dice_result'` | 帧名（契约 §4；`docs/tools/12 §6.2:580`） | `case` 字面量（§6.1） |
| `source` | `'writer' \| 'character'`（`event-bridge.ts:7`） | 哪个车道 | **不渲染**（人称归历史面板的 `roll_resolved.actor`）；§6.3 只用来选文案语气 `[推断]` |
| `characterId` | `string` 可选，仅角色车道（A1） | 归属（`docs/wiring/00 §3`） | **必须容忍缺失/存在**，不影响演出 |
| `path` | `string`（`roll-dice.ts:27`） | 被裁决实体的世界相对路径 | 幂等键（§6.2）+ 落定后 `[data-path]` 高亮（§8.2） |

| `result` | `number`（`:37`） | 引擎最终点数（多骰为和 + modifier） | 大号数字（`.dice-result-number`，`index.css:672`） |
| `passed` | `boolean`（`:39`） | `evaluateExpect` 的判定 | `Check Passed/Failed` 徽标（`DiceRoller.tsx:273-282`） |
| `rolls` | `number[]`（`:41`） | 逐骰面（`1d100`→`[62]`，`2d6`→`[3,4]`；`rollOnce` `rules/dice.ts:241-258`） | **逐骰面翻滚**（§3.2 步骤 5、§8） |
| `crit` | `boolean`（`:43`） | 每颗骰子都是最大面（`rolls.every(r => r === faces)`，`rules/dice.ts:255`） | 金光爆裂（`.crit-glow`，`index.css:681`） |

**与契约 §4 的逐字一致性**：契约 §4 的 `dice_result` 行写 `{ source, path, name, dice, desc, expect, result, passed, rolls, crit, fumble, layer, timestamp }`——与 `event-bridge.ts:152-166` + `push` 完全一致。**帧里没有 `forged`**（见 §11.1）。

### 2.2 `fumble` 的边界（实读，别照抄直觉）

`rules/dice.ts:249-257`：`rolls.push(Math.floor(v * spec.faces) + 1)`，`fumble = rolls.every(r => r === 1)`。

- `2d6` 掷出 `[1,1]` → `fumble === true`（每颗都是 1）；
- `2d6` 掷出 `[1,3]` → `fumble === false`（`result === 4 > 5` 也是 `false`，但**不是因为** `result`）；
- **`crit` 与 `passed` 正交**（`docs/tools/07 §2.2.7` 第 4 条）：`1d100` 掷 100、`expect: "=1"` → `passed=false, crit=true`。前端**两件事各演各的**（金光 + `Check Failed` 徽标），不许用一个吞掉另一个。
- `forged`（god 伪造）**不进帧**：`details.forged` 存在（`roll-dice.ts:191`），但 `event-bridge.ts:152-166` 没搬它。工具路径的 actor 是 `writer`/`character`（`extensions/toolkit/roll-dice.ts:49` 不传 `forcedResult`），**工具路径结构上不可能 forged**——所以缺它不是漏，是冗余字段的拒绝（§11.1）。

### 2.3 `rolls` 是「骰面」不是「骰子个数」的证明

`rolls.length` = 声明的 `count`（`1..20`，`rules/dice.ts:243-250`），**不是** `result` 的位数。`2d6+3` 掷 `[5,6]` → `rolls=[5,6]`、`result=14`。前端渲染 N 个骰面时用 `rolls.length`，**永不从 `dice` 字符串重解析**（那会是第二套 `NdM` 解析器，`docs/tools/07 §2.2.7` 第 2 条明禁）。

### 3.2 前端逐步（每一步的「漏了会怎样」）

### 3.3 统一节拍（所有输入共用一个 `DiceCeremony`）

玩家路径的蓄力属于输入控制；writer/character 帧没有手势，因此跳过 `charging`。但三种来源在进入 `DiceCeremony` 后共享同一套 `rolling`、`settled`、音频、crit/fumble 和收场时序：

| 输入 | 进入仪式前 | `DiceCeremony` |
|---|---|---|
| 玩家 HTTP | `DiceRoller` 负责按住蓄力并等待权威 `RollDiceDetails` | `rolling` → `settled` → 收场 |
| writer `dice_result` | `parseDiceFrame` + layer/identity guard | `rolling` → `settled` → 收场 |
| character `dice_result` | `parseDiceFrame` + `characterId` guard | `rolling` → `settled` → 收场 |

所有输入都使用同一份 `ROLL_MS`、`SETTLE_MS`、逐骰面、音频和结果高亮。玩家 HTTP 响应不能由 `DiceRoller` 另播一套；`DiceRoller` 只负责输入/蓄力控制和把权威 details 交给 canonical dice ingress。

帧到达时结果已知，但翻滚只是视觉，不重新判定点数；翻滚结束才停在真实 `rolls`，避免“先显示答案再补表演”。

## 4. 文件与副作用（精确到函数）

**零副作用是硬要求**：本篇**不改任何数据、不发任何请求、不落任何事件**（§5）。全部改动是「接一条帧 + 演一次」。

**副作用边界**：本篇的演出 renderer 不改世界、不发请求、不落事件；但玩家 HTTP 的权威 details 必须经过 UX04 的 `ActionFeedbackStore` 和 canonical dice ingress，不能被错误地当作“只有帧路径才有输入”。

| 文件 | 操作 | 归属 |
|---|---|---|
| `apps/web/src/state/useWorld.ts` | 加 `case 'dice_result'`，只转发演出帧 | 唯一 WS 消费点 |
| `apps/web/src/lib/dice-ceremony.ts` | NEW；边界 parser、layer/character guard、`DiceCeremonyInput` 归一化、`DiceIngressAllocator`、去重和快照 | 唯一 dice ingress/source owner |
| `apps/web/src/components/performance/DiceCeremony.tsx` | NEW；消费归一化 input，单例渲染器 | 唯一结算仪式 |
| `apps/web/src/components/narrative/DiceRoller.tsx` | 保留玩家输入/蓄力；成功后把真实 `RollDiceDetails` 交给 ingress，不自行播第二套 ceremony | 输入 owner，不是 ceremony owner |
| `apps/web/src/App.tsx` | 挂载唯一 `DiceCeremony` renderer；不复制 HTTP/WS parser | projection host |
| `apps/server/src/engine/event-bridge.ts` | 不改 `dice_result` 发射 | 服务端现有帧源 |

两条禁止：

1. HTTP 路径不得伪造 `dice_result` WS 帧；
2. `DiceRoller` 不得在 pending 阶段或 HTTP 结果确认前播放成功仪式，也不得在 `DiceCeremony` 外重复播放结果仪式。

## 5. 落账（**演出帧一律不落事件**——说清为什么）

`dice_result` **不落任何事件**，理由有三层，逐层都与「再落一条」会冲突：

1. **事实已经落完了**。`rollDice` 在读文件之后、掷骰之后**先 `writeFileAtomic`**（`actions/roll-dice.ts:211-215`），再 `appendEvent({ type:'roll_resolved' … })`（`:222-237`）。`dice_result` 是 `tool_execution_end` 的**事后**产物（`event-bridge.ts:147`），此刻账已经在 `history.db` 里。再落一条就是同一事实两行。
2. **它是动画，不是变化**（`doc-21 §1.1`，契约 §1 逐字引用）。事件表回答「世界变成了什么」；「玩家看到了一次金光」不是世界的一部分。落了它，注入段会多出一句没有信息量的行（作家读到"有人掷骰"而它上一轮已经读过 `roll_resolved`）。
3. **落账会让 `dice_already_rolled` 彻底失效**。`rollDice` 的重掷门禁读的是**实体 frontmatter 里的 `result`**（`actions/roll-dice.ts:151-155`），不是事件表。所以这里不是"多一条无害"——它是**第二份真相**的开端，会引诱实现者去用事件表判重掷。

**与 `roll_resolved` 的分工（契约 §4 / `docs/tools/12:604`）**：

| | 通道 | 落账 | 谁消费 | 说什么 |
|---|---|---|---|---|
| `dice_result` | 演出帧（瞬时） | ❌ | `DiceCeremony`（本篇） | "骰子落定了"（视觉） |
| `roll_resolved` | `world_event{event}`（尾部读表，`event-bridge.ts:280-290`） | ✅（由 `rollDice` 落） | `useWorld` 的 `world_event` → `fetchLayer`（既有，`:326-335`） | "这个实体的 `result/passed` 变了"（数据） |

**两条都必须能独立工作**：刷新页面后 `dice_result` 早已错过，骰子卡靠 frontmatter 里已有的 `result/passed` 显示落定态（`DiceRoller.tsx:73-77` 的 `rolled` 初值）——这条链由 `roll_resolved` → `fetchLayer` 保着（`docs/tools/07 §6.3` 的 `world_event` 行）。**演出丢了不丢数据，数据丢了才丢真相。**

## 6. WS 与前端（消费点、状态更新、与既有 `case` 的关系）

### 6.1 唯一消费点：`useWorld` 的 `case 'dice_result'`

```ts
// apps/web/src/state/useWorld.ts —— switch（:322-386）内新增，位置在 case 'character_*' 之后
case 'dice_result': {
  // 演出帧（docs/tools/12 §6.2）：无条件转给演出层，不进 world_event 的去重/重取路径，
  // 不 fetchLayer（那由 roll_resolved → world_event 负责，§5）。
  window.dispatchEvent(new CustomEvent('airp:dice-frame', { detail: msg }));
  break;
}
```

**为什么派发而不是直接调渲染**：`useWorld` 的职责是"帧 → 状态/事件"，它是 hook，不能 return 一个 Portal；而仪式是**屏幕固定层**（`fixed inset-0`），必须挂在 `App` 的根（`:443` 的 `div.flex.flex-col` 下），不能挂进 `Canvas` 的 `worldRef`（那会被相机 `scale` 拉伸——`worldTransform` 是 `translate(...) scale(cam.z) ...`，`lib/camera.ts:72-74`）。契约 §6b-1 已确立同类先例：`chalk_writing` 的湿墨壳也是"独立于 `items` 的浮层"。

**与既有 `case` 的关系**（逐条，防止碰撞）：

| 既有 `case` | 与 `dice_result` 的关系 |
|---|---|
| `world_event`（`:326-335`） | **独立**。`roll_resolved` 在这里到达并触发 `fetchLayer`（整层重取 → 卡片显示 `result`）。`dice_result` **不**触发它（§5） |
| `case 'tool_start'/'tool_end'`（`:360-369`） | **不重叠**。那两个只经 UX03 writer ingress 更新 `WriterPublicState.toolCount` / 派生 `isFootprintBusy`；`dice_result` 不碰 writer state |
| `case 'error'`（`:377-382`） | **相关但不合并**：工具失败时 `isError:true` → `event-bridge.ts:147` 的 `!event.isError` 让**帧根本不发**。故帧路径**没有失败画面**（§7）|
| `default`（`:383-385`） | 现状的注释"…`roll_resolved` 等仍在此忽略"**保持**（它是 `world_event` 里的事件，不再出现在这里；`docs/tools/07 §6.3` 的该行已由 A 档落地为 `world_event` 分支） |

**门禁视角**：`tools/check-ws-contract.mjs:124-134` 的 `consumedFrom` 只认 `case 'dice_result'` / `msg.type === 'dice_result'` 字面量——上面这行让它变 consumed。**但那只证明"有监听"，不证明"演了"**（契约 §10 的假绿），所以 §10.2 的浏览器判据是本篇的硬验收。

### 6.2 `lib/dice-ceremony.ts`（NEW）—— 帧的边界守卫与去重

**守卫逐条（与 `parseDiceVerdict`（`DiceRoller.tsx:49-65`）同款纪律，放宽到宽响应）**：

| 字段 | 判据 | 不满足 |
|---|---|---|
| `path` | `typeof === 'string' && !== ''` | 丢弃整帧（无法定位/去重） |
| `result` / `passed` | `number` / `boolean` | 丢弃（与 `parseDiceVerdict:51-58` 同款） |
| `rolls` | `Array.isArray && every(typeof === 'number')` | 丢弃（无法逐骰面） |
| `crit` / `fumble` | `typeof === 'boolean'` 且字段必须存在 | 丢弃（不能从 rolls 猜测） |
| `desc` / `expect` / `dice` / `name` | `typeof === 'string'` 且字段必须存在 | 丢弃（不能用空字符串伪造详情） |
| `layer` | `typeof === 'string' || raw.layer === null` 且字段必须存在 | 丢弃（不能把缺失当不过滤） |

**边界守卫与归一化要分开理解**：`DiceRoller` 的 `parseDiceVerdict` 仍只负责 HTTP 原始响应的最低边界检查；`parseDiceFrame` 负责 WS 帧的完整字段检查。两者输入形状不同，不能粗暴合并 parser；但两者通过 `dice-ceremony.ts` 统一归一化到 `DiceCeremonyInput`，之后绝不能各自触发视觉仪式。

### 6.4 座位 / 层 / 相机：三条与重取相关的边界（契约 §6b-5 直接命中）

| 层过滤 | `v.layer !== null && v.layer !== currentLayer` → **丢弃播放**（不排队） | 排队会在切层后突然补演一次陈年仪式。丢弃的代价是"那个层的玩家没看到"，而 `roll_resolved` 已经让那张卡显示结果（§5 的分工） |

| z-index | 仪式层 **50**（`DiceRoller.tsx:339` 的 `z-50`）；fumble 裂痕 **55**（`index.css:714`） | 已告知 `05` 把 `PerformanceLayer` 排到 **≤20**；两层同时出现时骰子仪式优先 |

## 7. 错误与边界（失败必须可见，不静默）

**先立一条事实**：帧路径**结构上没有"失败画面"**。`event-bridge.ts:147` 的条件是 `event.toolName === 'roll_dice' && !event.isError`——工具失败时**一条帧都不发**（已由 `apps/server/test/map-engine-event.test.mjs:97-106` 锁定）。因此帧路径的错误处理对象是**畸形的帧**和**错过的帧**，不是"掷骰失败"。

### 7.1 工具失败的可见性归谁

| 情形 | 谁负责可见 | 机制 |
|---|---|---|
| 作家/角色调 `roll_dice`，引擎拒绝（`dice_already_rolled` / `not_interactive` / `invalid_field_value` / `write_failed`） | **不归本篇**（前端看不到这条工具调用） | `extensions/toolkit/roll-dice.ts:51-53` 的 `fail(err)` → pi-rp 把错误结果交回**模型**（`toolkit/result.ts:9`），作家据此改稿或放弃。**玩家侧不弹任何东西**，这是正确的：玩家没发起这个动作 |
| 玩家自己点击（HTTP 路径） | `DiceRoller` 的 `error` state（A4 已落地，`DiceRoller.tsx:83/200-206/330-334`） | 与本篇无关，**不改** |
| 帧到达但 `path` 指向的卡不在当前层 | **静默**（§6.4 的层过滤），非错误 | `roll_resolved` 已让那个层的卡显示结果 |

**这条分工必须写进文档**，否则实现者会想在 `DiceCeremony` 里加"掷骰失败"提示——而**帧根本不会为失败而发**，那段代码永远是死代码。登记 §11.4。

### 7.2 畸形帧全表

| 情形 | 处理（可见，不静默） |
|---|---|
| `detail` 不是对象 / `result` 非数 / `passed` 非布尔 / `path` 空 | `parseDiceFrame` → `null` → **整帧丢弃**；`console.warn` 一次（**调试用**，玩家侧无可演之物——注意：这不是"失败可见"，因为没有任何玩家动作失败，见 §7.1） |
| `rolls` 非数组 / 含非数 | 同上丢弃。**不回落**：回落成 `[result]` 会把 `2d6` 演成一颗骰（`§2.3` 反例） |
| `crit`/`fumble` 缺省或非布尔 | **回落**：`crit = passed && rolls.every(r => r === max(rolls))` 不可算（不知道 `faces`）→ 直接取 `false`，**只演中性落定**（不做 95/5 的老启发式——`docs/tools/07 §2.2.7` 第 1 条证明它对 `1d20`/`2d6` 全错） |
| `rolls` 为空数组（`[]`） | 丢弃（一张骰面都没有的仪式没有意义） |
| 同一 `path` 5s 内第二条帧 | `shouldPlayFrame` → `false`（去重，§6.2）；**不报错**（重连重放是正常网络行为） |
| 仪式播放中又来一帧（不同 `path`） | **打断前一场，播新的**（不排队）；`key` 递增保证组件重挂载、动画从头 | 排队会让玩家在 10s 后看到一场属于过去的仪式；而骰子是"再看一眼"的即时反馈 |
| 仪式播放中切层 | `DiceCeremony` 监听 `currentLayer` 变化 → **立即收场**（`onDone`） | 切层是玩家的明确意图；跨层残留一个全屏遮罩等于劫持 |
| `prefers-reduced-motion` | 把 `rolling` 相位压到 ~180ms、去掉震颤（`.dice-shake`）与裂痕动画，**结果与徽标照常出现** | 减少动效但不减少信息（`前端改造计划.md:211` 的 `skip` 语义：跳过演出不改变已判定的结果） |
| `layer === null`（背包 / 小天地实体） | **不层过滤**（照演）。`[推断]`：这类实体不让掷骰（`resolveLayer` 返回 `null`，`store/local-store.ts:550-556`），但若真发生，演出来比吞掉好 |

### 7.3 音效的边界（实读）

`playFoley`（`audio.ts` 的 `playFoley`）无 Web Audio 时 `initAudio()` 返回 `null` → **静默返回**，有设备但资源缺失 → `failCached` → `synthFoley`。`playCharge`/`endCharge`（`audio.ts` 的 `playCharge`/`endCharge`）只在玩家蓄力路径用，**帧路径不调**（帧路径无蓄力相位，§3.3）。

**结论**：帧路径的音频 = 翻滚音 `playFoley('dice-roll')`（`FoleyName` 真实值，`audio.ts:24-33`）+ 落定情绪瞬时音 `crit ? playStinger('smile') : fumble ? playStinger('shock') : —`（契约 §8b；`Emotion` 真实值见 §11.7）。`playFoley('dice-roll')` 有真实素材（`assets/audio/PLAN.md`）；`stinger/` 6 条**尚未生产**（`assets/audio/CREDITS.md` 的 PENDING），缺素材时 `playStinger` 静默 no-op——接线就绪、素材到位才响。

**必须 `unlock()` 吗**：**不必，也不能**。浏览器的 autoplay 策略要求 `unlock()` 发生在用户手势里（`audio.ts:905-921`），而帧到达**不是**手势——在 `DiceCeremony` 里调 `void unlock()` 无意义（没有手势上下文，`resume()` 会被拒）。`[推断]`：帧到达时如果音频从未解锁，`playFoley` 的 `playClip` 会落在 suspended 的 context 上**静默**。**处置**：接受静默（视觉完整），**不**弹"点击以启用声音"。**但有一个真实的机会**：若此前玩家已经在画布上点过任何东西，`Canvas.tsx:180` 的 pointerdown 已解锁——**绝大多数真实会话里音频是活的**。登记 §12.4。

3. **角色车道（`source === 'character'`）掷骰时是否该演全屏仪式**（§6.3）。现设计**照演**（帧到了就演）。反方意见：玩家正在读遮罩里的对话，全屏压暗会打断。**建议**：本批照演（简单、一致）；若演示里显得吵，后续加"遮罩打开时降级为卡上高亮"——**那需要读 `App.tsx` 的 `activeModalCharId` state**，是另一个状态耦合，本批不做。

4. **帧到达时音频未解锁 → 静默**（§7.3）。本设计**接受静默**（不弹"点击启用声音"），依据是绝大多数会话里 `Canvas.tsx:191` 的 `unlock()` 已被指尖触发过。**待拍板**：是否要在仪式上挂一个"第一次手势时补 `unlock()`"的兜底（成本低，但那不是音乐路径的常规做法——`unlock()` 必须在手势里）。

5. **`roll_ceremony` + `dice_result` 的接续是否需要显式握手**。当前设计**不需要**：`05` 的入场是 `durationMs` 定时收场（`SHOWS` 表里 `roll_ceremony` 的 `defaultDuration: 2200`，`performances.ts:86-99`），我的落定是帧到达即演。若作家先 `show({component:'roll_ceremony'})` 再 `roll_dice`，两条演出**重叠**（入场还没完，落定已经压上来）。**待拍板**：是否要求 `DiceCeremony` 在检测到 `roll_ceremony` 在场时延后挂载（需要跨模块读演出层状态 → 新的耦合），或由 `05` 在 `roll_ceremony` 期间把后续落定**排队**。**建议**：本批不排队（两条重叠在视觉上是"翻滚中落定"，可接受），登记为后续观察项。

6. **`path` 去重的窗口时长（5s）与上限（50）** 是 `[推断]` 的经验值，无原型量取。依据：`roll_resolved` 的尾部读表兜底是 ~1s（`event-bridge.ts:10`），WS 重连重放窗口远小于 5s；50 条覆盖一个会话的骰子数。**若评审有量取值，替换 §6.2 的两个常量。**
