## 3. 冻结裁决 A：`writer_delta` 的来源流（**本批最重要**）
**问题**：现状 `writer_delta` 映射 `text_delta`（助手的**纯文本回复**流）。而 AIRP 明确「回复里的文本到不了画布」——**叙事正文是 `chalk` 工具的参数**。照现状接线，会把作家的**过程语言**（"让我想想"、工具调用之间的自语）当叙事湿墨演上画布，随后又被真正落地的 chalk 覆盖。这是**契约级缺陷**，比"零消费"更糟。

**冻结决定**：`writer_delta` 的 `delta` 载荷**改为来自 `chalk` 工具调用 `content` 参数的增量流**：

1. `mapEngineEvent` 在 `message_update` 分支**同时**识别 `text_delta` 与 `toolcall_delta`：
   - `text_delta` → **不进 `writer_delta`**（作家车道）。它降级为**调试/思考通道**：本批**不广播任何帧**（登记为"思考指示"后续，见 `01` 冲突节）。
   - `toolcall_delta` → **仅当该工具是 `chalk`** 时，抽取 `content` 字段的**已到达前缀**，产出 `writer_delta { source:'writer', delta, toolCallId }`。**工具名在 delta 期间不可知**（§3.1 spike 2）——判定与确认机制见 §3.2，**MUST 可机械核验**。
2. **增量 JSON 字段提取器**是纯函数（`packages/shared` 或 `apps/server` 内），MUST 单测：处理转义 `\"` `\\` `\n` `\t` `\uXXXX`，处理 `content` 非首字段、处理未闭合字符串（返回已确定的字符前缀，**不输出半截转义**）。
   - **漏了会怎样**：把 `{"content":"a\"b` 的 `\"` 当边界 → 正文错位、"湿墨"打出一个引号就停。
3. **`delta` 语义改为"增量片段"**（与 `character_delta` 一致），前端**累积**而非替换。**载荷形状**：`{ type, source, delta, toolCallId, timestamp }`（新增 `toolCallId`，用于把 delta 归属到对应的 `chalk_writing`/`chalk_landed`）。
4. `character_delta` **不受影响**：角色遮罩的台词就是助手的**文本回复**（`CHARACTER_INSTRUCTION` 让角色直接说话，没有 chalk 工具；`extensions/instructions.ts:168`），故 `text_delta` 仍是它的正确来源。**两个车道的来源流不同，这是刻意的。**

**依据**：`extensions/instructions.ts:74-79`（回复不进画布）、`extensions/toolkit/chalk.ts:41-66`（正文=工具参数）、`vendor/pi-rp/packages/ai/dist/types.d.ts:395-448`（事件全形状）、`rpc.md:1126`（分片缓冲语义）、`tools/probe-provider.ts:52-72`（两条流的实证脚本）。

**回写对象**：`docs/tools/12 §6.2:573` 的 `writer_delta` 载荷行、`docs/tools/02 §6.4:476`、`docs/后端实现计划.md:209`。由 `06` 篇统一改。

### 3.1 服务端可见形状（**三处 spike 实测，2026-09-12；不是推断**）

**Spike 1/2/3 的实测事实**（harness 同 `tools/probe-writer.mjs`；provider 剧本见 `tools/probe-provider.ts` 与临时 chalk 版）：

1. **RPC 模式下 `partial` 被剥掉**：`toJsonEvent`（`vendor/pi-rp/packages/coding-agent/dist/modes/json-event.js:12`）删除 `assistantMessageEvent.partial`，而服务端走 RPC（`rpc-mode.js:386` 调 `output(toJsonEvent(event))`）。
   - 实测：`toolcall_delta` 到达时**只有** `{ type, contentIndex, delta }`；`toolcall_start` / `toolcall_end` 同理**没有 `partial`、没有工具名**。
2. **时序是 `toolcall_start → toolcall_delta… → toolcall_end → tool_execution_start`**。**唯一带 `toolName` 的事件（`tool_execution_start`）在参数流全部结束之后才到达。**
   - 实测序列（probe-provider 剧本）：`msg_update:toolcall_start / toolcall_delta / toolcall_end → TOOL_START name=write → TOOL_END`。
   - **推论（重要）**：`toolcall_delta` 到达时，服务端**既无 `partial`（被剥）也无 `toolName`**。任何"从 partial 读工具名"或"delta 期间已知 toolName"的设计**都不成立**。
3. **`delta` 是原始参数 JSON 的分片**：`delta` 逐片拼接后 = `JSON.stringify(toolCall.arguments)`。
   - 实测（chalk 剧本，7 字符分片）：首片 `"{\"conte"`，拼接后 `{"content":"The fog parts and the gaslight catches the wet cobbles."}`。
   - **不可依赖参数顺序做前缀判定**：R2 用 6 组配置矩阵实测，**LLM 生成的参数 JSON 不遵循 schema 声明序**——带 `path` 的 chalk 实测以 `{"path":` 开头，**与 `write` 逐字不可区分**。故 `content` 是否首个键**不是**可靠信号（`extensions/toolkit/chalk.ts:41-60` 的声明序只约束 typebox schema，不约束模型输出）。
4. `toolcall_end.toolCall` 携带**完整 `{ id, name, arguments }`**（实测 `name='write'`），且 **id 与随后的 `tool_execution_start.toolCallId` 一致**——这是唯一可靠的"事后确认工具名"的锚点。

### 3.2 冻结方案：延迟确认 + 追字（**绝不显示未确认的内容**）

**原则**：`toolcall_delta` 期间工具名未知，**因此不得直接把它当 `writer_delta` 广播**（`write` 也有 `content`，且前缀不可判别）。冻结方案：

1. 服务端**按 `contentIndex` 缓冲** `toolcall_delta` 的累积 JSON 分片（一个 turn 内可有多个 tool call）。
2. `toolcall_end` 到达时读 `toolCall.name`：
   - `name === 'chalk'` → 从 `toolCall.arguments.content` 取正文，**按缓冲顺序发出 `writer_delta` 流**。
   - `name !== 'chalk'` → 丢弃该缓冲，**不产帧**。
3. **`tool_execution_start`（带 name）到达后，`toolCallId` 与 `toolcall_end.toolCall.id` 对齐**，用于把 `chalk_writing`（`:87-89`）与 `writer_delta` 归到同一次调用。
4. **强制：延迟确认，禁止乐观流。** 早期设计曾允许「凭 `{"content":` 前缀在 delta 期间就开始流」——**R2 实测推翻**（见 §3.1 item 3）。**本批 MUST 延迟到 `toolcall_end` 确认后再发**。视觉上以「追字播放」补上流式感（拿到全文后按 ~24ms/字 追播，等价湿墨）。**绝不在 delta 期间显示未确认内容。**


> **对 `01` 的强制要求**：为**增量 JSON `content` 提取器**写 `node --test`：必须覆盖**未闭合转义**（`{"content":"a\"` 返回 `a` 而非 `a\`）、`\n` `\t` `\\` `\uXXXX`、`content` 非首字段（`{"path":"x","content":"y"}`）。**含一条"没有这段修复就会失败"的非空性用例。**

**为什么 §3 初稿错了**：初稿写"从 `partial.content[contentIndex].name` 读工具名"——spike 1 证明 `partial` 被 RPC 剥掉，该路径不存在。此处按实测改正。

## 5. 冻结形状：幻影与座位过户（跨 `01`/`03` 共用）

**纪律（`doc-10 E3`）**：**幻影座位 = 成品座位（期望）**。幻影壳（`chalk_writing` / `image_generation_progress`）出现时按排座算法落位；内容落地（`chalk_landed` / `image_landed`）时**座位不变**，只换壳内内容与影深。

- **前端排座与服务器排座输入集合不同**（前端 = `/layer` 成功镜像的 `items` + 同层全部幻影；服务器 = `/layer` 页面完整 `items` 对应 rows + 本批 boxes）。双方调用 layout 批次冻结的 shared `flowColumns`，但算法同源不保证输出同构；**不一致时以真实重取为准**（`file_changed` → `fetchLayer` 后坐标赢），幻影由 `reconcileLanded(paths)` 撤销。**绝不出现"内容到了但卡在别处"。**
- **座位 helper 唯一属主 `03`**：`phantomSeatFor(size, layer): { seat, occupied }`（`03 §8.5`），内部 MUST 调用 `packages/shared/src/layout/flow-columns.ts` 的 `flowColumns`，occupied 包含同层全部未撤离幻影（Chalk + image）。`01` MUST 调用它；**禁止自造 `nextInkSeat` 或第二份排座**（§11「不得各写一份」）。

**"数据先落，DOM 才是投影"**（`doc-06 §2.2`）：演出用的临时 DOM 必须在 `file_changed`/`world_event` 驱动的真实重取落地后**移除**，由数据渲染接管；否则重进层就丢字（encore 事故）。

**排座 API 现状**：服务端在 `/api/layer` 读取时排座（`seatUnplaced`）。前端**不重排**已落位的卡。跨篇协调点：`01` 与 `03` **共用同一个幻影注册表**（`lib/phantom.ts`，见 §8），不得各写一份。

**失败撤离**：`tool_end` 带 `isError:true` 时，幻影壳 MUST 淡出撤离（`doc-10 E3` 的 `cancelPerformance` 纪律），**不留半成品**。`01`/`03` 共用同一撤离入口（`phantom.ts::evict`）。

**P0 时序纪律（R3 实锤）**：`writer_delta`（源自 `toolcall_end`）**一定先于** `chalk_writing`（源自 `tool_execution_start`）到达。故 `phantom.ts::appendInk(toolCallId, delta)` **MUST 对未知 `toolCallId` 建 pending 缓冲**，`register` 时把缓冲灌入 `entry.text`。**否则湿墨静默丢弃（零报错）**——本批最隐蔽的失败形态。

## 6b. 加载顺序与时钟事实（**主 agent 复核，跨 `01`/`02`/`03`/`04`**）

这些是**实现前必须知道、否则会做出错误设计**的机制事实（已读码/实测）：

1. **`chalk_writing` 不带 `path`，`chalk_landed` 才带**（`event-bridge.ts:87-89` vs `:123-133`）。时序：`tool_execution_start(chalk)` → `chalk_writing{toolCallId}` → `tool_execution_end` → `chalk_landed{path}`。
   - **后果（`01` 必须处理）**：湿墨/幻影壳出现时，**目标卡片在 `items` 里还不存在**（文件未落盘）。故 `writer_delta`/`chalk_writing` 的渲染是**独立于 `items` 的浮层**（`phantom.ts` 注册表），**不能**去 `items.find(path)`。到 `chalk_landed` 才用 `path` 与真实卡对齐过户。
   - `writer_delta` 新带的 `toolCallId` 正是为把 delta 归到同一 `chalk_writing`（无 path 可归）。
2. **`toolcall_delta` 与 `tool_execution_start` 的先后**：见 §3.1（工具名在 delta 期间不可知）。
3. **watcher 忽略 `.airpworld/assets/`**（`event-bridge.ts:373-377`）。**后果（`03` 必须知道）**：生图落盘**不会**触发 `file_changed`，所以 `image_landed` 帧是前端唯一能知道"图好了"的通道——**这条帧不是冗余**。
4. **`generate_image` 的 `onUpdate` 真发**（`extensions/toolkit/generate-image.ts:79-95`：`resolving` → `generating` + 每 10s 心跳 + `unref()`）——`image_generation_progress` 有真实数据源。
5. **`file_changed` 仍是整层重取的触发器**（A 档定案，未变）。故 `chalk_landed` 之后，`file_changed` 会把真实卡带进 `items`——**过户应幂等**（幻影撤、真实卡留）。**`01`/`03` 共用同一过户入口。**
6. **作家 public state 的唯一 owner 是 `docs/ux/03-Chrome与公开状态.md`**：`writerToolsInFlight` 不能再作为第二 busy store。footprint 的 `isFootprintBusy` 从 UX03 的 `WriterPublicState.phase/toolCount` 派生；`writer_idle` 是唯一正常终态，断线由同一 writer adapter reset。`01` 只负责演出帧 source、phantom 与 writer-state ingress，不得再定义第二个 WriterState。


7. **必须同批改写的既有测试**（否则假绿）：`apps/server/test/map-engine-event.test.mjs:218-220` 已断言 writer `text_delta` 不产 `writer_delta`，不是待推翻项；`:229-255` 覆盖 chalk toolcall fragments。当前 `:222-226` 仍断言无 `characterId` 的历史帧会产出 character frame，必须在 strict identity migration 中改为 server migration adapter 补 ID，或前端 strict fixture 丢弃 + `airp:notice`，不能保留 active-modal fallback。
