## 1. 一句话与定位

**`show_frame` 是演出型组件的唯一前端入口：服务端把 `show` 工具返回的 `ShowFrame` 逐字广播，前端按 `frame.component` 分发到 7 种一次性演出——放完即撤，不写文件、不落事件、不碰画布状态。**

三条定位：

1. **`show_frame` 是「传输帧」，不是「世界变化」**（`docs/tools/00 §5.3`、`docs/tools/10:188`）。它与 `chalk_landed`/`dice_result` 同属演出帧通道，**一条事件都不落**（§5）。因此它**不参与**「数据先落、DOM 才是投影」那条纪律——它不是投影，它是一段**自灭的动画**。
2. **分发器的形状由帧决定，不由演出决定**。前端只认 7 个 id；未知 id 静默跳过 + 不崩（契约 §6，`docs/tools/10:158`）。服务端侧的合法性由 `ShowKind` 封闭枚举保证（`extensions/toolkit/show.ts:19-22` 的 `Type.Union(SHOW_IDS.map(Type.Literal))`），前端这层是**纵深防御**，不是重复校验。
3. **7 种演出全部是「复用既有机制」，只有 `PerformanceLayer` 一个新挂点**。`camera_focus` 用 `useCamera().flyTo`（`apps/web/src/state/useCamera.ts:52`）、`ink_burst` 用 `index.css` 的 `.ink-spread`（`:237-239`）、`evidence_burst` 用 `LinkLayer` 的手绘曲线（`LinkLayer.tsx:70-80`）、`roll_ceremony` 用 `DiceRoller` 的 `.dice-cube-ceremony`（`index.css:616-650`）。**MUST NOT 再造第二套。**

**为什么单独立一篇**：`show_frame` 是全批唯一「一条帧、七种行为」的帧。其余四条篇都是「一条帧一条行为」。分发器的**默认分支**（未知 id）与**边界纪律**（只演不留）是这一篇的核心产出。

## 2. 签名 / 载荷（逐字段与源码核对）

### 2.1 帧的冻结形状

服务端广播的就是 `ShowFrame` 本身（**逐字**，无包裹、无改名）：`event-bridge.ts:168-176` 的 `push(details.frame as Record<string, unknown>)`。

`ShowFrame` 的 TS 定义在 `packages/shared/src/actions/show.ts:21-33`（实读）：

```ts
export interface ShowFrame {
  type: 'show_frame';
  component: string;
  target?: string;
  targetName?: string;
  links?: string[];
  params: Record<string, unknown>;
  durationMs: number;
  caption?: string;
  actor: Actor;
  /** Filled by the server mapping layer, never by the tool. */
  timestamp?: string;
}
```

| 字段 | 类型 | 生成处（实读） | 前端怎么用 |
|---|---|---|---|
| `type` | `'show_frame'` | 字面量 `show.ts:158` | **分发键**（`useWorld` 的 `case`） |
| `component` | `string`（服务端侧是 `ShowKind`） | `show.ts:159` `component: id` | **演出选择键**（§3.3 的分发表） |
| `target` | `string?` | `show.ts:160`，仅 `target` 有值时展开 | 世界根相对路径 → `[data-path]` 定位（§3.4） |

| `links` | `string[]?` | `show.ts:162`；源 `:124-143`（坏路径被剔除并计数） | 仅 `evidence_burst` 的丝线起点 |
| `params` | `Record<string, unknown>` | `show.ts:163`；**已经过该演出的 zod `safeParse`**（`:146-153`） | 每种演出的参数（§2.2 逐字段） |

**两个「不是推断」的关键断言**：

1. **`durationMs` 已被服务端 clamp**。`show.ts:47-48` 定义 `MIN_DURATION=300 / MAX_DURATION=12000`，`:155` 是 `Math.min(MAX_DURATION, Math.max(MIN_DURATION, input.duration_ms ?? def.defaultDuration))`。**故前端 MUST NOT 再 clamp**（契约 §6 末条逐字：「前端按帧值计时，不自行 clamp」）。前端一旦 clamp，帧值 300ms 会被前端改成别的数——两端两个真相源。
2. **`params` 已被 zod 校验**。非法参数在服务端就 `isError`（`show.ts:146-152`），**根本不会广播**（`event-bridge.ts:168` 的 `!event.isError` 门槛）。故前端读 `params.foo` 时**可以信任字段已通过 schema**，但 MUST 仍容忍**缺失**（字段全是 `.optional()`）与**多余键**（每条 schema 都 `.passthrough()`）。

### 2.2 7 种演出的真实 `params`（逐行照抄 `packages/shared/src/components/performances.ts:15-105`）

> **id 清单的真源是 `SHOWS`/`SHOW_IDS`**：`SHOWS`（`performances.ts:15`，`ShowDef[]`）、`SHOW_IDS`（`:105`，`SHOWS.map((s) => s.id)`）。**`SHOW_REGISTRY` 不是这个**——它是 `packages/shared/src/components/registry.ts:27` 的**组件注册表**（`Record<string, ShowDef>`），与本篇的 7 个演出 id 无关（`R1-10`，契约 §6 已改称 `SHOW_IDS`）。本篇全文凡引「7 个 id」一律指 `SHOW_IDS`。

**这是参数的真源**；下文所有实现方案只许引用这些字段，**不许发明**（如 `spotlight.intensity`、`fireworks.particleCount` 都不存在）。

| 2 | `lights_out` | `:29-40` | `dim?: number`（`.min(0).max(1)`）、`focus?: string` | 1800 | false |

| 4 | `evidence_burst` | `:54-66` | `links?: string[]`、`staggerMs?: number`、`color?: string` | 3600 | **true** |

**逐条实读要点**：

- **`camera_focus` 没有坐标字段**（`:70` 逐字 `z.object({ zoom: z.number().optional() })`）。**帧里也不带坐标**（§2.1 无 `x/y`）。所以相机目标**只能**由前端从 `target` 卡的 DOM 盒推导（§3.4）。**任何「服务端算好坐标」的设计都不成立**——帧里没有。
- **`roll_ceremony` 不带结果字段**（`:88-89` 注释逐字：`this one does NOT roll dice. It only performs the entrance`）。没有 `result`/`faces`/`dice` 点数。`dice?: string` 是**骰子的面子规格**（如 `"1d100"`），不是掷骰结果。
- **`lights_out` 的 `focus` 是路径**（`:34` `focus: z.string().optional()`），而 `requiresTarget:false`（`:39`）——即 `lights_out` **不走** `target`，它用 `params.focus` 指「留一处微亮」的卡。**这是 `lights_out` 与 `spotlight` 的分工差**（§11 冲突 3）。
- **`evidence_burst` 的 `links` 出现两次**：帧顶层 `links`（`show.ts:162`，服务端**已剔除不存在的路径**，`:131-138`）与 `params.links`（`:59`，zod 只做类型校验，**不剔除**）。**前端 MUST 规定唯一优先级**，否则两条来源会打架（§3.4、§11 冲突 4）。
- **7 条 schema 全带 `.passthrough()`**：未知键被保留。前端**只许读上表的键**，读别的等于依赖一个未被冻结的约定。

## 3. 行为契约逐步（每步写「漏了会怎样」）

### 3.1 消费点与分发（唯一 WS 入口内加一个 `case`）

前端**唯一**的 WS 消费点是 `apps/web/src/state/useWorld.ts:315-390` 的 `ws.onmessage`（`new WebSocket` 在 `:308`，反模式 2）。本批在它的 `switch` 里**加一个 `case 'show_frame'`**（`:322` 的 switch，现有 case 在 `:323-385`）：

```ts
case 'show_frame':
  // 演出帧：一次性、无状态、不重取。分发器自己防御未知 component（契约 §6）。
  performShowFrame(msg as ShowFrame);
  break;
```

`performShowFrame` 是 `PerformanceLayer.tsx` 导出的**模块态函数**（§3.3），**不是 React state 更新**——理由：演出是**瞬时动画**，进 React state 会让「该帧到达」与「整棵画布子树重渲染」绑定；而 `show_frame` 可以在一轮里连发多条（作家连演两场），每次都重渲染世界层是纯浪费（`AGENTS.md §7.6-2` 的同一条纪律：高频/瞬时驱动不进 React）。

**为什么放在 `useWorld` 而不是 `App`**：`docs/tools/12 §6.2:581` 把消费点定在 `useWorld`；门禁 `consumedFrom`（`tools/check-ws-contract.mjs:124-134`）只扫 `CONSUMERS = ['apps/web/src/state/useWorld.ts']`（`:56`）。写在别处 → **门禁永远 DARK**。

**漏了会怎样**：不加这个 `case`，`default`（`:383-385`）静默吞掉帧——门禁 DARK 不消，且 `show` 工具在游戏里**完全无效**（作家「演了」但玩家看不到任何东西）。这是本批 9 条 DARK 里最容易被误判为「已经能用」的一条：`show` 工具会返回成功文案（`show.ts:169-177` 的 `Showing "spotlight" on …`），模型以为演了。

### 3.2 分发器形状（`NEW`，`PerformanceLayer.tsx`）

模块态是刻意选择：演出**不需要**跨帧持久，也**不需要**订阅（没有别的组件读它）。所以不需要 `useSyncExternalStore`（对比 `01` 的 `phantom.ts`——那个必须被 React 渲染，故有订阅）。

```ts
// NEW apps/web/src/components/performance/PerformanceLayer.tsx
import type { ShowFrame } from '@airp/shared';
import { resolveShowKind } from '../../lib/show-geometry.js';   // §8.6

/** 一次演出在模块态里的存活期记录（供撤场与重叠去重）。字段集与 §8.1 一致。 */
interface ActiveShow {
  id: number;               // 自增，撤场定时器比对用（§3.6-1）
  component: string;
  resourceKey: string;      // 重叠去重键（§3.5）
  startedAt: number;
  durationMs: number;
  /** 撤场时用来清 CSS 变量 / 取消 animation 的引用。 */
  cleanup: () => void;
}

let active: ActiveShow[] = [];   // 在演场次（异资源并存，§3.5）
let seq = 0;
let liveCtx: ShowCtx | null = null;   // 由 <PerformanceLayer /> 挂载时写入（§8.1）

/**
 * `show_frame` 的唯一入口（`useWorld` 的 case 调用）。
 * 未知/畸形 component → 不演、不崩；**非空 string 的未知 id 打一次 `console.warn`**（§3.2 步 2）。
 * 返回是否真的演了一场（供单测断言；生产不读）。
 */
export function performShowFrame(frame: ShowFrame): boolean;

/** 显式中止（层切换 / 世界冻结时调用，§7）。 */
export function cancelShow(reason?: string): void;

/** 当前演出快照（只读，供单测与 DevTools 断言）。§3.5 起是**数组**（异资源可并存）。 */
export function activeShow(): Readonly<ActiveShow[]>;
```

**`performShowFrame` 逐步**：

1. **形状校验**：`if (!frame || typeof frame !== 'object' || frame.type !== 'show_frame') return false;`（畸形帧防御，与 `04 §7` 同款「先判形状，再动状态」）。
   - **漏了会怎样**：`JSON.parse` 出来的畸形帧会让分发器读 `undefined.component` 抛 TypeError，`useWorld` 的 `try`（`[行号待复核]`，实读 `:316`）接住后**整条消息的其他处理也跳过**——一个坏帧吞掉同一批里的好帧。
2. **归一化 id**：`const kind = resolveShowKind(frame.component);`（§8.6；**与 §10.3 的单测共用同一个函数**，避免分发器与测试两套判据）。
   - **未知分两种，行为不同**：
     - `component` 是**非空 string** 但不在 `SHOW_IDS` 里 → **版本错配信号**：`console.warn('[show_frame] unknown component', frame.component)`，返回 `false`。warn 是**开发者诊断**，不是玩家可见失败（与 `04 §7` 对「未知 `kind` → 可见 warn」**同构**，`R3/P3-1`；与契约 §6「静默跳过」措辞的关系见 §11 冲突 11）。
     - `component` 缺失 / 非 string → **完全静默**返回 `false`（畸形帧，步 1 已拦，此处纵深防御）。
   - **漏了会怎样**：抛错 → `useWorld` 的 `catch` 打 `WS parse error`，但**玩家已经看不到这场演出而不知道原因**——违反「失败必须可见」（`docs/tools/00` 硬约束 4）。**不演、不崩**是唯一正确的选择：服务端已保证只发 `SHOW_IDS` 内的 id，前端若真收到未知 id，那是版本错配，**不该崩掉整条通道**（契约 §6）。
3. **同资源接管、异资源叠加**：`const key = ruleKeyOf(kind);`（`spotlight`/`lights_out` → `'dim'`；其余 → `kind`）。派发前 `cleanup` 所有 `resourceKey === key` 的在演场并移除；异资源键的场次**保留并存**（§3.5）。
   - **漏了会怎样**：两场 `spotlight` 叠在一起 → 两个压暗遮罩相乘（`brightness(0.15)² = 0.0225`，画布近乎全黑），且两个定时器都以为自己拥有同一份 DOM。
4. **派发**：`SHOW_RENDERERS[kind](frame, liveCtx)`（**统一签名** `(frame, ctx)`，§8.1）；`liveCtx === null`（组件未挂载）→ `console.warn` + 返回 `false`（不崩）。返回该场演的 `cleanup`。计时用 `frame.durationMs`（**不 clamp**）。
   - **漏了会怎样**：clamp 会让 `durationMs=300` 的 `ink_burst` 演成前端自己定的长度，服务端文案（「for 300ms」）与实际不符——两端不一致。
5. **撤场**：`const my = ++seq; setTimeout(() => { if (active.some((s) => s.id === my)) { cleanup(); active = active.filter((s) => s.id !== my); notify(); } }, frame.durationMs);`。**定时器不因 React 重渲染重置**（模块态 + `id` 比对，§3.6-1；`notify()` = 依次调 `listeners`）。
   - **漏了会怎样**：DOM 永久留在画布上 → 全屏压暗不散（玩家以为界面坏了）。这正是「只演不留」的反面。

**`ruleKeyOf(kind)` 放哪**：`show-geometry.ts`（§8.6）再导出一个 `ruleKeyOf(kind: string): string`（`kind === 'spotlight' || kind === 'lights_out' ? 'dim' : kind`）——纯函数、可单测。**登记为第 9 个导出**。

### 3.3 7 种演出的渲染表（逐个给实现方案）

分发器只做**一件事**：把 `frame` 交给下面 7 个**统一签名**的渲染函数之一（`(frame, ctx)`，§8.1）。每个函数**返回 `cleanup`**，并在调用时**立即让演出可见**（不等待 React）。

| id | 演什么（`docs/tools/10 §6.3:347-355` 逐行） | 挂点（复用既有 DOM/CSS） | 读哪些 `params` | 计时 | 声音（§4.5） |
|---|---|---|---|---|---|
| `spotlight` | 全画布压暗 + 暖金光束打在 `target` + 微尘 | **`PerformanceLayer` 自己的遮罩 div**（`--show-dim`）+ 复用 `ParticleLayer` 的既有尘埃 | `dim`（缺省见 §3.4）、`spread`、`tone` | `durationMs` | 无 |
| `lights_out` | 全屏关灯（压暗 + 焦点卡微亮 + 环境音切低） | 同上遮罩，但**无光束**；`focus` 卡加 `.show-focus-lift` | `dim`、`focus` | `durationMs` | `setAmbient(null)`（§4.5） |
| `fireworks` | 画布上空粒子爆裂 | `ParticleLayer` Module 的 `burst` surface：沿用 ambient 的 sprite/parallax/resize Adapter，但以 bounded DOM/sprite surface 归 `performance`，不新增第二个 full-screen composite canvas | `color`、`bursts`、`origin`（格式见 §12.4） | `durationMs` | `playFoley('crit-chime')` |
| `evidence_burst` | `links` 每张卡向 `target` 拉**临时**红线 | `PerformanceLayer` 内自己的 `<svg>`，容器写 `worldTransform`（§3.6-2b、§12.2 裁定)；**不进 `LinkLayer.registry`** | `links`（优先级见 §3.4）、`staggerMs`、`color` | `durationMs` | 无（钟鸣缺音，§4.5） |
| `camera_focus` | 相机飞向 `target`，**不压暗** | `ctx.camera.flyTo`（`useCamera.ts:52`） | `zoom`（**唯一字段**） | `durationMs`（仅用作 `activate` 时长，见下） | 无 |
| `ink_burst` | `target` 卡上墨迹一次扩散 | `target` 卡的 DOM 上临时加 `.show-ink`（复用 `index.css:237-239` 的 `.ink-spread` 机制） | `tone`、`scale` | `durationMs` | `playFoley('pen-scratch')` |
| `roll_ceremony` | 大号骰子入场翻滚（**不带结果**） | **复用 `DiceRoller` 的 `.dice-cube-ceremony` / `.dice-scene-ceremony`**（`index.css:616-650`）的**几何**，但渲染在 `PerformanceLayer`（尺寸变体 `.show-ceremony-cube` 120px，§12.5） | `dice`、`anticipation` | `durationMs` | 无（归 `02`） |

**`durationMs` 对 `camera_focus` 的特殊用法**（唯一一处）：`flyTo`（`useCamera.ts:142-148`）是**设定目标**，`lerpCam` 的插值速率由 `LERP_K = 0.13`（`lib/camera.ts:17`）决定，**与 `durationMs` 无关**。故 `durationMs` 在 `camera_focus` 里**只决定「这场演出何时算结束、何时可被下一场接管」**，不决定飞行快慢。

- **为什么不把 `durationMs` 映射成 `LERP_K`**：`useCamera` 是**模块级共享**（`useCamera.ts:41-42`），`LERP_K` 是 `lib/camera.ts` 的常量，改它会影响**玩家滚轮缩放与拖拽平移的所有手感**。为了一个演出去改全局相机阻尼，是本批最典型的越界。
- **`flyTo` 的 `z` 参数**：`flyTo(x, y, z?)`，`z === undefined` 时**保持当前 z**（`useCamera.ts:146`）。故 `params.zoom` 缺省时**不要传 z**，传 `undefined`——不要传 `1` 或 `0`（会跳到极限）。`params.zoom` 有值时传它，`flyTo` 内部会 `clampZ`（`:146` → `lib/camera.ts:23`）。

**`roll_ceremony` 的边界（与 `02` 已 IRC 对齐）**：**只演入场翻滚，不渲染点数、不判 crit/fumble、不播 `crit-chime`/`fumble-break`**。理由：`roll_dice` 的落定归 `02`（`dice_result` 帧，`event-bridge.ts:147-167`），`roll_ceremony` 的 schema 里**根本没有结果字段**（§2.2）。两条帧若同轮到达，视觉上天然接续：入场翻滚 → 落定（`02` 已确认不需要握手，见协作记录）。

### 3.4 `target` → DOM 定位（所有需要 `target` 的演出共用）

`target` 是**世界根相对路径**（契约 §6），例如 `world/baker-street/rusty-key.md`。卡片 DOM 的对应钩子是 `data-path`（`CanvasObject.tsx:125` `data-path={item.path}`）。

```ts
/** 世界根相对路径 → 卡片 DOM 节点。找不到返回 null（不抛）。 */
function cardEl(path: string | undefined): HTMLElement | null {
  if (!path) return null;
  try {
    return document.querySelector(`.object[data-path="${CSS.escape(path)}"]`);
  } catch {
    return null;
  }
}
```

**这个实现必须与 `LinkLayer.tsx:116-123` 的 `elForPath` 逐字同构**（同一选择器、同一 `CSS.escape`、同一 `try/catch`）——`target` 与 `link.from/to` 是**同一种路径**（都来自 `store.readFile` 的调用方 `show.ts:113` / `LinkLayer` 的 `links` 行）。两处若用了不同选择器，卡的坐标会算成 0。

**几何读法用 `lib/measure.ts` 的 `elementBox`**（`measure.ts:44`），**不是** `getBoundingClientRect`：

- `elementBox` 返回**世界坐标**（`left/top` 内联 + 缓存的渲染尺寸，`measure.ts:44-70`），与 `LinkLayer.readBox`（`LinkLayer.tsx:125-130`）一致 → 可直接写进同一个世界变换层。
- `getBoundingClientRect` 返回**缩放后的屏幕坐标**（`measure.ts:63-65` 注释逐字「offsetWidth/offsetHeight are untransformed layout px — the world units this cache serves (getBoundingClientRect is zoom-scaled)」）→ 相机缩放不为 1 时坐标全错。**这条是量测结果被吃掉的经典坑。**
- 用 `elementBox` 的另一好处：**命中按代缓存**（`measure.ts:33`），演出期间多次读同一张卡不触发 reflow（`AGENTS.md §7.6-3`）。

**读不到 DOM 时的行为（必须写死，不许静默）**：

| 演出 | `target` 卡不在当前层 DOM | 行为 |
|---|---|---|
| `spotlight` | 是 | **不演**，返回 `false`，并 `console.warn` 一次（**与未知 id 的 warn 同款**，见 §7） |
| `camera_focus` | 是 | 同上 |
| `ink_burst` | 是 | 同上 |
| `evidence_burst` | `target` 卡缺 → 不演；**单条 `links` 缺 → 跳过那一条**，其余照演 | 部分降级，可见性由服务端文案承担（`show.ts:172-176` 已报数） |
| `lights_out` | `params.focus` 卡缺 → **照演关灯，只是没有微亮**（`focus` 是可选的） | 降级但不失败 |
| `fireworks` / `roll_ceremony` | 不需要 target（`requiresTarget:false`，`performances.ts:52/98`） | 永远演 |

**`console.warn` 在这里是合规的**：`docs/tools/00` 硬约束 4 禁止的是「**用 warn 冒充失败可见**」——即玩家该看到撤离却只打了日志。这里玩家**什么都没看到**（演出没发生），前端 warn 是**给开发者的诊断**。**但服务端文案不等于玩家可见**（`R3/P2-1`）：`show.ts:169-171` 的返回文案是**给模型的 tool result**，模型是否复述、复述经哪条玩家可见通道（chalk）——**两处都无机制保证**。故这条 warn **MUST NOT** 被当作「失败可见」的交付（§7 详述），此路径玩家**可能完全无感**。

**`evidence_burst` 的 `links` 优先级（冻结）**：**顶层 `frame.links` 优先，`params.links` 仅作后备**。理由（逐条）：

1. 顶层 `links` 是服务端**读世界校验过的**（`show.ts:131-138`：每条都 `store.readFile` 成功才留下），坏路径已被剔除；`params.links` 只是 zod 的类型校验（`performances.ts:59`），**路径可能不存在**。
2. 两者都可能出现（schema 允许 `params.links` 与顶层 `links` 同时给）。若无单一优先级，前端会出现「到底拉几条线」由代码顺序决定——**这是不可核验的**。
3. 冻结写法：`const paths = frame.links ?? (frame.params?.links as string[] | undefined) ?? [];`

**`spotlight` 的 `dim` 缺省值**：schema 是 `.optional()`（`performances.ts:21`），**服务端不填缺省**（`params` 只经过 `safeParse`，`show.ts:146-153`，zod 的 `.optional()` 不注入值）。故缺省由**前端**定：`dim ?? 0.15`（`docs/tools/10 §14.3:731` 逐字「`dim`(0-1, def .15)」）。`lights_out` 的缺省是 `0.08`（`:732` 逐字「`dim`(def .08)」）。**这两个数字是文档冻结的**，不许前端自造。

### 3.5 重叠纪律：**同资源接管、异资源叠加**

`show_frame` 可能一轮里连发（作家先 `spotlight` 再 `fireworks`，或 `spotlight` + `ink_burst`）。三种可选语义：

1. **全局队列**（一场演完演下一场）：会让 `durationMs` 累加，玩家等得比作家预期的久；且队列长度无界。
2. **全局并存**（同时渲染所有场）：两个压暗遮罩相乘 → 画布全黑（压暗是**乘性**的：`filter: brightness(0.15)` 叠两层就是 `0.0225`）。
3. **按资源键去重**（**冻结选它**）：资源键＝`spotlight`/`lights_out` 共用 `'dim'`，其余演出用自身 `kind`（`ruleKeyOf`，§3.2/§8.6）。派发新场时只 `cleanup` **同资源键**的在演场；**异资源键的场次并存**，各自按 `frame.durationMs` 独立计时。语义是「同一种视觉资源，最新意图赢；不同资源，各演各的」。
   - **`spotlight` + `ink_burst` 互不打断**（`docs/tools/10:543` 的手测判据 4）：资源键不同（`'dim'` vs `'ink_burst'`），墨迹加在卡上、与遮罩无共享 DOM → 结论与判据 4 **一致**。
   - **两场 `spotlight`（或 `spotlight` + `lights_out`）仍后到者接管**：它们抢的是**同一张遮罩**，叠起来就是黑屏。
   - 与 `docs/tools/10:543` 判据 4 措辞的差异见 §11 冲突 10（判据 4 原文「两种演出叠加…互不打断」须限定为「**异资源**」）。

**漏了会怎样**：选 2 → 两次压暗后画布全黑，玩家看到「屏幕坏了」；选 1 → 演出时间轴与叙事脱节；把同资源也叠加 → 黑屏。

### 3.6 与 React 重渲染解耦（契约 §6b-1 的直接要求）

主 agent 的 §6b-1 说：`file_changed` 仍触发整层重取，DOM 会重建。**`show_frame` 与 `file_changed` 无因果关系**（演出不写文件，`show.ts:64-71`「It never writes a file…」，`docs/tools/10:242` 逐字「零副作用」），但**它可能与 `file_changed` 同时到达**（同一轮里作家既写 chalk 又 show）。

纪律：

1. **计时器在模块态，不在组件里**。`setTimeout` 由 `performShowFrame` 自己持有；`PerformanceLayer` 的 React 树重建**不重置它**。撤场靠 `id` 比对（§3.2 步 5），不靠 effect 清理。
2. **压暗遮罩挂在 `App` 级的稳定节点上**，不是挂在 `Canvas` 的 `worldRef` 变换层内（那层会随 `items` 重渲染）。挂点见 §8。
2b. **丝线容器用「自写变换」而非「挂进 `worldRef`」**（§12.2 裁定 A）：`evidence_burst` 的丝线要在**世界坐标**里与卡对齐，但 `PerformanceLayer` **不**挂在 `worldRef` 子树内。做法：丝线容器是 `absolute inset-0` 的 div，其 `transform` 由 `camera.subscribe`（`useCamera.ts:162-168`）写 `worldTransform(vw, vh, cam)`（`lib/camera.ts:72`，与 `useCamera.ts:125` 写给 `worldRef` 的**同一条公式**）。坐标源是 `elementBox` 的世界坐标（§3.4）→ 经同一变换即得屏幕位置。**对齐前提**：`PerformanceLayer` 的盒子与 `Canvas` viewport 同尺寸同原点（§12.1 挂点裁定保证）。**为什么不做屏幕固定层（原选项 B）**：`evidence_burst` 常与 `camera_focus` **同轮**；相机飞走后屏幕固定丝线会错位（`R5/B2`）。
3. **`target` 卡被重建时演出不撤**：演出用**一次性**定位（`cardEl` 在开演时算一次，遮罩/光束/丝线端点各算一次），不持续追踪卡片。代价是卡片若在演出中途被拖动，光束/丝线不跟随——**接受**（演出最长 12s，玩家在演出中拖卡的概率极低）。

**漏了会怎样**：把演出写成 `useEffect(() => {...}, [frame])` → 每次重取 `items` 都重跑，演出时间轴被重置；若写成订阅 `items` 里 `target` 卡的坐标，则重取那一刻（卡短暂不存在）演出会崩。


### 3.7 `prefers-reduced-motion`（必须处理，否则演出变成伤害）

仓库已有现成的探针：`apps/web/src/lib/motion.ts:28-36` 的 `useStill()`（读 `(prefers-reduced-motion: reduce)`）。`Canvas.tsx:123` 已用它（`stillPortraits`）压掉立绘视频。

**冻结纪律**：`show` 是**装饰性动效的大宗**（全屏压暗、粒子爆裂、相机飞行），**在 `reduce` 下必须降级到「瞬时可见、不动」**：

| 演出 | `reduce` 下的行为 |
|---|---|
| `spotlight` / `lights_out` | 压暗**仍然发生**（它是**信息**：告诉玩家「注意这张卡」），但压暗/恢复**不加过渡**（`transition: none`），光束静态 |
| `fireworks` | **整场跳过**（纯装饰，且是粒子动画的最大宗） |
| `evidence_burst` | 丝线**直接出现**（无 stagger 延展），`durationMs` 后消失 |
| `camera_focus` | **整场跳过**（`reduce` 下相机位移是位移刺激；`useCamera` 无瞬间入口，见下） |
| `ink_burst` | 直接显示墨迹（无扩散动画），或整场跳过 |
| `roll_ceremony` | 骰子**静态入场**（无翻滚） |

**实现落点**：`PerformanceLayer` 在组件内取 `useStill()`（`motion.ts:28`）写进 `ctx.still`（§8.1 的 `ShowCtx`）——`useStill` 是 hook，只能在**组件内**取值，再传给模块态渲染函数。渲染函数读 `ctx.still` 决定是否降级。

**`camera_focus` 的 `reduce` 处理**：`useCamera` 无「瞬间」入口 `[推断]`（`flyTo` 只写 target，插值走 `LERP_K`）——**本批取「整场跳过」**（`ctx.still` 为真时不派发），避免为它新增一个相机 API。

> **`useStill` live rule**：`motion.ts` 的系统偏好必须订阅 `MediaQueryList.change`；运行中切换 reduced-motion 在下一帧停止/降级所有 show、burst、camera 与 particle。旧的 mount-only 限制只作为现状证据，不能成为本批验收例外。

### 4.4 `fireworks` 与 `ParticleLayer`：**同一 Module，分离 ambient / burst surface**

**问题**：`fireworks`（`performances.ts:41-53`）要「画布上空的粒子爆裂」（`docs/tools/10 §14.3:733` 逐字「前景层（z:150）粒子爆裂 + 余烬下落」）。最直觉的做法是**新写一个 `<FireworksCanvas>` 全屏 canvas**。**这必须被论证否决或接受**——`AGENTS.md §7.6-1` 逐字：

> **整屏 canvas 每帧重绘 = 一帧预算的一半**。实测（WSL2 软件渲染 + 真 GPU 两种环境同向）：仅一个 1×1 缓冲区、全屏 CSS 盒的空 canvas 就把 57fps 压到 34fps；隐藏即回到 57fps。代价在**合成**而非绘制……**新增全屏 canvas 前先想清楚它是否值得半帧预算。**

**现状事实（实读 `ParticleLayer.tsx`）**：

- 它**已经**是一张全屏 canvas：`canvas.width = window.innerWidth; canvas.height = window.innerHeight`（`:64-65`），`className="absolute inset-0 … z-10"`（`:182`）。
- 它**已经**为合成代价付过三笔优化（`:96-100` 注释逐字）：预渲染 sprite（`:34-46` 的 `makeGlowSprite`）、限 30fps（`:100` 的 `FRAME_MS = 1000/30`）、`document.hidden` 跳帧（`:108`）。注释的原话是「the measured dominant cost on this app」。
- 它每帧 `ctx.clearRect(0,0,width,height)` 后重画全部 48 粒（`:112-167`）。
- **它的粒子上限是 48**（`:73` `const count = 48; // Lightweight particle budget (< 1% CPU)`），且尺寸/速度在**挂载时一次性随机**（`:78-94`），**不是演出参数**。

**结论：**`fireworks` 继续复用 `ParticleLayer` Module 的共享 sprite、resize、parallax 与生命周期 Adapter，但不再与 ambient dust 共写一个无法表达 Depth 的 canvas。ambient 保持既有低频 canvas；burst 使用 bounded DOM/sprite surface（或等价的非 full-screen surface），归 `performance`，由 `playBurst` 驱动。不得新增第二个 full-screen composite canvas。

**论证（三条，逐条可核验）**：

1. **代价论证**：不新增第二张 full-screen canvas，避免再次支付全屏合成成本；burst surface 只挂在演出生命周期内，结束即卸载/清空。
2. **视觉一致性论证**：ambient 保持既有 sprite、resize、parallax 与 30fps；burst 只共享这些 Adapter，不共享 ambient Depth 或 ambient loop 状态。
3. **参数映射论证**：`bursts` 映射为 burst sprite 团数，`color` 映射 CSS 色，`origin` 映射 bounded surface 的归一化位置；非法 origin 回落 `0.5,0.2`，不触碰世界坐标或真实卡座位。

**实现形状（NEW，`ParticleLayer.tsx` 内部 burst surface，不改变现有 ambient canvas）：**

```ts
// NEW 追加到 apps/web/src/components/canvas/ParticleLayer.tsx
export interface BurstSpec {
  color?: string;
  bursts?: number;
  origin?: string;       // "<0..1>,<0..1>" 屏幕比例
  durationMs?: number;
}
/** 播一场烟花；返回取消函数。资源键为 'fireworks'，同资源后到者接管。 */
export function playBurst(spec: BurstSpec, host: HTMLElement): () => void;
```

`playBurst` 只写 burst surface；ambient loop 不读取 fireworks 状态。burst surface 的 DOM root 必须登记为 `performance`，`pointer-events:none`，结束时清空。它可以复用既有 `makeGlowSprite` 或 CSS sprite，但不能把 burst 粒子重新画回 ambient canvas。

**粒子预算（写死，可核验）**：`bursts × 12` sprite nodes/团，上限 96 nodes（`bursts` 缺省 5 → 60 nodes）。burst surface 复用 ambient 的 resize/parallax timing Adapter，但不进入 ambient canvas ctx；其 DOM/sprite 生命周期仍受 30fps/Effects/visibility gate 管理，MUST NOT 自己开持续 RAF。
**为什么不做“仅 fireworks 期间才创建第二个 full-screen layer”**：看起来省，实际会在演出首帧触发合成资源分配，造成 Money Shot 首帧卡顿；常驻 ambient surface + 按演出挂载的 bounded burst surface 更可控。

**`bursts` 的「上限」不是前端加的（§2.2）**：schema 是 `z.number().int().positive().optional()`（`:46`），**无上限**。前端若真收到 `bursts: 1000`，`12×1000 = 12000` 粒会拖垮帧率。**冻结取舍**：前端**按 `clampBursts(...)` 内部封顶 8**（§8.6；8 团 × 12 = 96 粒），并在 §11 冲突 5 登记「服务端 schema 缺上限」——**这是防御性封顶，不是替服务端校验**。

## 5. 落账（**演出帧一律不落事件**——说清为什么）

`show_frame` **不落任何事件、不写任何文件、不碰 `canvas.db`**。这不是本批的选择，是 `show` 的定义：`packages/shared/src/actions/show.ts:64-71` 的文档注释逐字「It never writes a file, touches the canvas DB, or appends an event — a performance is a transient frame, not a world change」；`packages/shared/test/components.test.mjs:245` 已有断言锁死这一点（`assert.deepEqual(calls, { write: 0, event: 0, canvas: 0 }, 'show writes nothing')`）。

**四条理由（逐条可核验）**：

1. **事件表准入第一问是「它改变了世界吗」**（`docs/tools/10:274` 引 `doc-21:23`）。烟花放完，世界与放之前**逐字节相同**——事件表里多一行就是幽灵事件。作家演 10 次追光 → 历史面板 10 行噪音。
2. **演出帧是「动画」不是「变化」**（`docs/tools/00 §5.3`、`doc-21:276`）。这部分**没有历史**：重放一场 3 秒前的烟花没有意义（对比 `chalk_landed`：重放能重建画布状态）。
3. **`actor` 字段在帧里，但本批不消费**（§2.1）。帧带 `actor`（`show.ts:166`）是给**将来**的「谁在演」UI 留位（如角色自爆身份时的高亮），不是落账用。落账由**世界事件**承担（`docs/tools/10 §5.1` 的 `entity_created`），与演出帧**互不相干**。
4. **前端不重取**。`show_frame` 的 `case`（§3.1）**MUST NOT** 调 `fetchLayer`——演出不改变 `items`/`links`，重取是纯浪费，且会在演出中途重建 DOM（§3.6-1）。对比 `world_event` 的 `case`（`useWorld.ts:326-334`）才重取。

**因此 `show_frame` 不参与「数据先落、DOM 才是投影」那条纪律**（契约 §5、`doc-06 §2.2`）。那条纪律管的是**幻影**（`chalk_writing`/`image_generation_progress` 的临时壳必须在真实重取后移除，否则重进层丢字）。演出**没有对应的真实数据**，所以它的临时 DOM **就该被自己撤掉**——`durationMs` 到即 `cleanup()`（§3.2 步 5），**不存在「等重取接管」这一拍**。

**唯一与「持久」交叉的一处是 `evidence_burst` 的线**——它**看起来**像 `link` 工具建的持久关系线，但**不是**：

| | `link` 工具 | `evidence_burst` |
|---|---|---|
| DOM | `LinkLayer.registry`（`LinkLayer.tsx:33`） | `PerformanceLayer` 自己的 svg |
| 数据 | `canvas.db` 的 `links` 表（经 `canvas_patched` 帧，`event-bridge.ts:134-146`） | **无** |
| 生命 | 直到 `link` 被删（`docs/tools/09`） | `durationMs`（默认 3600ms，`performances.ts:64`） |
| 重进层 | 还在 | 不在（**正确**：它没被记录，重进层就不该有） |

**MUST NOT 把 `evidence_burst` 的线写进 `canvas.db`**（契约 §6、`docs/tools/10:357`、反模式 7）。

### 6.2 状态更新：**没有 React state**（这是刻意的）

`case 'show_frame'` **不调 `setState`**，只调 `performShowFrame(msg)`。理由：

1. **演出是瞬时的、单消费者的**（只有 `PerformanceLayer` 一处渲染）。进 state 会让「一条帧」触发整棵 `App` 子树的协调（`:562` 的主区 + `Canvas` + 卡片）。`AGENTS.md §7.6-2` 的同一条纪律：瞬时驱动不进 React。
2. **计时与撤场不能被 React 生命周期牵动**（§3.6-1）。state 更新会让 `PerformanceLayer` 重渲染，若撤场逻辑写成 effect cleanup，重渲染会**提前撤场**（React 19 的 effect 语义）。
3. **`PerformanceLayer` 是唯一读模块态的组件**。它用 `React.useReducer` 触发「演出开始/结束」的重渲染（§8.1）——但那是**组件内部**的事，`useWorld` 不参与。

## 7. 错误与边界（失败必须可见，不静默）

**本批的失败面比别的篇窄**——因为 `show` 工具**在服务端就把所有错误挡住了**（`show.ts:77-152` 的 E1–E11，全部 `fail(...)` → `isError:true`），`event-bridge.ts:168` 的 `!event.isError` 让**坏演出根本不会广播**。故前端只面对「帧合法但演不出来」这一类。

> **可见性总纲（按 `R3/P2-1` 诚实化）**：本前端的所有失败路径**都不保证玩家可见**——服务端在 `show` 的返回文案里说了演了什么（`show.ts:169-177`），但那是**给模型的 tool result**，不是玩家可见帧；模型是否复述、复述经哪条通道到玩家，**均无机制保证**。故本批的 `console.warn` 是**纯开发者诊断**，**不冒充**任何可见性交付。

|---|---|---|---|---|
| S1 | 帧不是对象 / `type !== 'show_frame'` | `performShowFrame` 返回 `false` | **无**（通道层已保证；这是纵深防御） | §3.2 步 1 |

/** frame.component → 合法 id，否则 null（不抛）。**未知/畸形一律 null**（契约 §6）。 */
export function resolveShowKind(id: unknown): string | null;

**实现要点（逐个，可核验）**：

1. `resolveShowKind`：`return typeof id === 'string' && SHOW_IDS.includes(id) ? id : null;`。**先判 string**（`R4/F-3` 的 `undefined.includes` 崩溃口）。

3. `clampBursts`：`const n = typeof v === 'number' && v > 0 ? v : 5; return Math.min(Math.floor(n), 8);`。
4. `clampStagger`：见签名行注释。
5. `spotlightDim` / `lightsOutDim`：`typeof v === 'number' ? v : DEF`（**只用 `typeof` 判，不 `??`**——`null` 也须回缺省）。
6. `zoomOf`：`const z = params?.zoom; return typeof z === 'number' ? z : undefined;`（**`0` 也是合法 z 但会被 `clampZ` 抬到 `Z_MIN`；这里只做类型判**）。
7. `inkToneOf`：白名单数组 `INK_TONES = ['ink','rust','blue','sage'] as const`，`includes` 判，越界 `undefined`。
8. `ruleKeyOf`：`return kind === 'spotlight' || kind === 'lights_out' ? 'dim' : kind;`。
