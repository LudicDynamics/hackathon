# Agent、photo 与内容能力共同上下文

> 本文是 2026-09-14 本轮设计的共享地基。六份领域设计必须遵守本文；若领域设计发现冲突，只能在“发现的冲突”中提出，不能私自改写共同口径。本文只冻结跨模块边界，不替代各领域详细设计。

## 1. 本轮范围与明确非目标

本轮包含：

- `component: photo` 的前端专用呈现：大图、下方预览、点击后二层模态详情；
- Agent 可见的世界根目录路径与 `world/`、`player/`、`characters/{id}/` 语义；
- 场景初始化教程 Skill；
- 把时间、平行线、关键决策、结局等抽象概念写成目录的剧情教程 Skill；
- 角色小天地管理教程 Skill；
- Writer 专用 `create_char` 工具及其 instructions 说明。

HTML、iframe、任意 HTML 组件渲染不在本轮范围。任何设计不得要求或暗示本轮已经支持 HTML/iframe。

## 2. 权威事实与路径身份

1. Agent 进程的 `cwd` 是当前世界根 `worldRoot`，见 `apps/server/src/engine/launch.ts:106-138,152-185`；子代理继承父 Agent 的 cwd，见 pi-rp `subagent/prepare.ts:113-125,250-267`。
2. AIRP 动作层使用世界根相对 POSIX 路径：不得使用绝对路径、`.`、`..` 或隐藏段。稳定路径示例：
   - `world/baker-street`
   - `world/baker-street/README.md`
   - `player/key.md`
   - `characters/watson/README.md`
3. `world/` 是世界内容及层目录；代码中的虚拟根层 id 是 `map`，但面向 Agent 的文件路径仍写 `world/`。层由 `world/**` 扫描派生，不能把 `player/**` 或 `characters/**` 当普通 layer。
4. `player/` 是真人玩家的背包/私人空间，不是 Agent 的工作目录，也没有角色 preset。
5. `characters/{id}/` 是独立角色的小天地及其角色文件，不是普通层；`GET /api/nook?character={id}` 单独读取。角色根配置和小天地内容同属该目录，但职责不同；面向玩家的 public nook projection 不展示根配置文件。
6. `characters/{id}` 的稳定 id 使用 ASCII 小写 kebab-case；显示名可以随世界语言变化。
7. 现有模型侧 instruction slot 没有 `PLAYER_INSTRUCTION` 或玩家 Agent。面向模型的路径解释应进入 `WRITER_INSTRUCTION`，必要时进入 `CHARACTER_INSTRUCTION`；若要让真人玩家看到同样的说明，必须另有前端文案入口，不能臆造不存在的 player slot。

## 3. Agent 状态与 brief 边界

- Writer/Character 的每轮 world state 由 `agent_start` 采集并在 `context` 中复用；这是动态状态块，不是初始化 brief。
- Scene-init/Nook-init 的 brief 是唯一动态上下文，默认不含 viewpoint、presence、玩家相机或主 Agent 历史；领域设计不得假设初始化子代理看得到这些信息。
- 指向模型的路径必须使用明确的 `world/...`、`player/...`、`characters/...` 路径，不得只使用显示标题或模糊的“当前场景”。

## 4. photo 数据与前端边界

1. 共享输入沿用现有 `component: photo`：`image?`、`caption?`、独立 Markdown 正文 `body`；`body` 不是 frontmatter 字段。
2. `/api/layer`、`/api/nook`、`/api/backpack` 已提供 `{path, filename, frontmatter, body}` 形状；设计不得新增第二套 photo 数据源。
3. Photo 卡面的目标呈现是：主图作为大图，下方显示 `preview`（若存在）作为预览摘要；点击或键盘激活后进入二层模态，展示大图、caption 与独立 Markdown body。
4. Photo 仍使用现有 `item.kind`、appearance、`CARD_FORMS`、`CanvasObject` 可读卡行为、`EntityInteractions` 互动所有权、既有唯一 WS 和 HTTP 重取；不得新增第二条 WS 或第二份状态。
5. 图片引用（`photo.image`、`create_char.avatar`）沿用 `assetUrl`/`/api/asset`，但必须通过 image-specific validator：只允许 `assets/**` 与引擎生成的 `.airpworld/assets/**`，并做 realpath/symlink 复核、常规文件检查和 **PNG/JPEG/WebP**（`image/png`、`image/jpeg`、`image/webp`）扩展名与实际 MIME 一致性检查。`/api/asset` 还服务既有背景、portrait、音频等媒体，不能把整个通用 asset 路由错误收窄为 image-only；实现应按已验证的媒体类型/调用字段分流，并保留视频与音频回归。不能把任意 world-root 文件暴露为媒体。
6. 会写入或编辑 `component: photo` 的**受支持服务端动作**（generic `createEntity`、`editEntity`、`create_char`）必须调用同一个 image-specific validator；`writeChalk` 与模型侧 native `write/edit` 当前不允许产出 `component: photo`，必须在写盘前显式拒绝，不能用未校验的通用路径绕过安全边界。只在浏览器拒绝非法路径不算闭环。
7. 唯一 canonical image validator 统一命名为 `assertImageAsset(worldRoot: string, relativePath: string): Promise<void>`，实现落在 `packages/shared/src/rules/media.ts`（NEW）；它负责路径根、realpath/symlink、常规文件和 PNG/JPEG/WebP 实际 MIME/扩展名。验证失败统一抛 `ActionError` code `invalid_asset_ref`；前端只能做无 I/O 的预检，不得复制 validator 语义。
8. `invalid_asset_ref` 必须同步加入 `packages/shared/src/actions/errors.ts` 的 `ActionErrorCode`、HTTP status/serialization 映射和 shared/server 错误测试；在该代码落地前，不能声称四个媒体写入负例已闭环。
9. photo 的 `use_item_on`、可移动性、背包投影不能因新增卡面而丢失；若背包视图暂不使用专用大图，必须明确写出范围和后续入口。
10. 通用媒体请求必须显式携带 `mediaKind: 'image' | 'video' | 'audio'`（`assetUrl(path, session, mediaKind)` → `/api/asset?path=...&kind=...`）；服务端不得按扩展名猜类型。image 走上述图片门禁，video/audio 走各自现有 allowlist；所有既有调用方需在同一实现批次迁移。

## 5. 内容 Skill 边界

### 5.1 场景初始化

教程必须覆盖用户指定的最小完整场景：

1. `README.md`；
2. 1–3 个物件类组件，各自可用短 chalk 介绍；
3. 1–2 篇 opening chalk；
4. 互动选项和行动选项；
5. 强烈建议 1–3 个子目录，各自含 README，可含组件或成为新的 opening 场景。

重要或复杂场景的“父场景先设计、再并发派 scene-init 子代理”是教程工作法，不得伪称当前 `airp-init` 已具备批量编排能力。当前实现单次只 spawn 一个 scene-init；教程目标数量是本轮新的规范，落地时必须同步迁移 `SCENE_INIT_INSTRUCTION` 与 `buildSceneInitBrief` 的旧数量断言，不能让 Writer 与初始化器继续看到两套要求。

### 5.2 抽象目录剧情

时间、平行线、关键决策、结局等目录仍然是 `world/**` 下的普通 layer；目录名是叙事语义，不是新的状态命名空间。教程不得引入 `branch_state`、`active_branch` 等第二状态真相，也不得让 choice 自动推进后果。

现有机制中：choice 只记录 `choice_selected`，后果仍由 Writer 通过文件/动作落地；`requires.items` 只表达现有玩家物件门槛。真正的 branch identity、并行分支切换、结局事件、快照回滚均不属于当前实现，必须标为未实现或待后续契约。

### 5.3 小天地

角色根目录中以下文件是不可移走、不可删除的角色基础配置：

- `README.md`
- `identity.md`
- `personality.md`
- `memory.md`

物品、日记、纪念物、信件、生活痕迹可写入角色根目录或子目录。物品送给玩家使用 `move` 到 `player/...`；放入场景使用 `move` 到 `world/...`；角色自身位置使用 `move_to`，不能把 nook 目录当场景移动目标。根配置可以在真实事实基础上编辑，但不能被移动或删除；通用 native `write/edit` 对根配置默认拒绝，显式配置维护必须走受信的 `edit_character_config` action，并在动作层执行 actor 矩阵；`write`、`edit`、`move`、`delete` 四个入口都必须有统一门禁，并在 Skill 装载给 Character 之前落地。
本轮将 `edit_character_config` 冻结为唯一配置编辑入口：`EditCharacterConfigInput { characterId: string; file: 'README.md' | 'identity.md' | 'personality.md' | 'memory.md'; content: string; mode: 'replace' | 'append' }`。Character 只能编辑自身 `memory.md`，Writer 可编辑 `manifest.characters` 中任一已登记角色的四项，其他 actor 和初始化器拒绝。该 action 复用 `entity_edited` 落账，不能使用可由模型传入的 `configurationMaintenance` 布尔值旁路授权。

9. `nookCardPaths` 是角色公开根目录卡片的唯一 helper；落地时直接迁移该 helper 及其所有 callers（route、canvas、arrange、测试）以过滤四个根配置，不另造只改 route 的平行 helper。旧模板的配置泄漏是迁移前基线，不能作为新验收预期。
10. 本轮 canonical layer-root README（包括 child）统一使用 `type: readme`；只有父层下独立 authored `<child>-door.md` 使用 `type: gate`。已有 `type: gate` 的 child README 是 legacy fixture，必须在模板/文档迁移中处理；`stub: true` 只表示显示标记，本轮不把它变成新的初始化状态。
11. 新 authored opening 的 canonical 文件名为带序号的 `NN-opening.md`（首篇通常 `01-opening.md`）；`opening.md` 仅是旧 W2 fallback 产物，`evening.md` 仅是历史 legacy 文件。新 Skill、scene-init instruction、brief 与验收不得混用三者；本轮不要求把旧文件自动重命名。
public nook projection 必须过滤 `README.md`、`identity.md`、`personality.md`、`memory.md`，这些文件不属于玩家可见 items。

Skill 必须区分配置文件与可移动的生活内容；如果代码门禁尚未同步，该差距必须写入设计的运行时前提，不得把提示词约束说成已由动作层强制执行。

## 6. create_char 输入契约（设计必须保留）

Writer 工具名为 `create_char`，不是 Skill。用户指定的输入概念为：

- `id`：稳定 ASCII 小写 kebab-case id；只用于 `characters/{id}/` 路径、manifest key、preset/session 定位；
- `name`：自由散文的角色显示名/称呼，不参与路径拼接，不要求 ASCII；
- `desc`：自动成为 `characters/{id}/README.md` 的正文；
- `avatar`：必填，世界根相对图片路径；必须先准备好图片再调用工具；
- `identity?`、`personality?`、`memory?`：存在则分别写入同名文件；
- `voice?`：写入角色 README/frontmatter，值遵循 `voice-casting` 的 alias/raw 解析契约。

创建角色必须同时解决“角色被发现”的 manifest、目录、preset 与事件闭环，不能只调用通用 `createEntity` 写一个 Markdown。角色骨架来自平台 `presets/character.json`，并在倒数第二个 items 位置插入 `profile` file slot：

```json
{
  "kind": "slot",
  "id": "profile",
  "slot": "file",
  "options": {
    "path": ["README.md", "identity.md", "personality.md", "memory.md"],
    "baseDir": "characters/{id}",
    "onMissing": "skip",
    "stripFrontmatter": true
  }
}
```
7. `create_char` 是 top-level Writer 专用工具。它不得进入 scene-init/nook-init 的 `customTools`；若现有工具注册是进程级共享，仍必须在 spawn 层注入不可伪造的 `AIRP_AGENT_SCOPE=writer-top-level`（初始化子代理使用不同 scope）或独立 tool allowlist 拒绝调用。只检查 `ctx.actor.type === 'writer'` 不足，因为子代理可能继承 Writer 身份。

其中 `{id}` 必须由工具安全拼接，不能由 Agent 传入任意路径；`name` 只作为自由文本保存/展示，不能被当作路径或稳定 id；`avatar` 的必填校验是 `create_char` 的专用契约，即使现有 `CharacterConfigSchema.avatar` 可选，也不能因此放宽本工具。

## 7. 统一设计文档要求

每份领域设计必须包含：定位、输入/输出或教程结构、逐步行为、文件与副作用、事件/状态、错误边界、代码落点、与现状差异、验收测试、发现的冲突、未决事项。所有“现状是”必须附 `file:line`；所有建议性结论标 `[推断]`。

六份设计不得修改本文的路径、身份、状态真相或范围口径。
8. 新增的三个平台 Skill（scene-init、abstract-directory-story、nook-management）必须同步登记 `tools/check-skills.mjs` 的 expected/triggers，并以实际 `loadSkillsFromDir`、`skillArgs` 和新 session 的 `available_skills`/prompt 探针验收；只读文件存在或静态字符串检查不算装配闭环。
