## 0. 现状体检（都是实测，不是推断）

### 0.1 致命项：我们说的话 pi-rp 听不懂

`apps/server/src/engine/rpc-client.ts` 发的是 JSON-RPC 风格的 `{ id, method, params }`；pi-rp 的 RPC 模式收的是**带 `type` 的 JSONL 命令**（`src/modes/rpc/rpc-types.ts` 的 `RpcCommand`）。实测：

```
→ {"id":1,"method":"prompt","params":{"message":"ping"}}
← {"id":1,"type":"response","success":false,"error":"Unknown command: undefined"}

→ {"id":"a","type":"get_session_stats"}
← {"id":"a","type":"response","command":"get_session_stats","success":true,"data":{...}}
```

**所以 `writer.prompt(...)` 这一年都在空转**——玩家说话、骰子回执、上帝动作通知作家，全部落在地上。连带三处协议不兼容：

| # | 问题 | 证据 |
|---|---|---|
| 1 | 命令用 `method`/`params`，pi-rp 认 `type` | 上面的实测回包 |
| 2 | 请求 id 用数字，pi-rp 的 `id` 是 `string`；回包形状是 `{type:"response",command,success,data}`，我们的 `handleMessage` 按 `msg.id` + `msg.error` 匹配 | `rpc-types.ts:21-330` |
| 3 | 用 `node:readline` 读 stdout | pi-rp `docs/rpc.md`「Framing」明确写：**readline 不合规**——它会在 `U+2028`/`U+2029` 上断行，而这两个字符在 JSON 字符串里合法 |

**为什么探针没抓到**：`tools/probe-writer.mjs` 只 spawn + 等 1.5 秒 + 查 stderr 有没有 `not found`，**从来没发过一轮 prompt**。地基探针只探到了地基的一半。

**修法不是修我们的 client，是删掉它**：pi-rp 自带完整的 `RpcClient`（`vendor/pi-rp/packages/coding-agent/dist/modes/rpc/rpc-client.js`），协议正确、JSONL 框正确，且已经有 `prompt` / `steer` / `followUp` / `abort` / `waitForIdle` / `onEvent` / `getEntries` / `appendMessage` / `switchSession` 全套。它不在 `package.json` 的 `exports` 里，但我们是 vendored，深路径 import 即可（或给 pi-rp 补一个 `./rpc` 导出，见 §11 取舍登记 #5）。

### 0.2 第二致命项：AIRP 一个工具都没注册

doc-20 的共享工具面——`look_at / move_to / move / choose / roll_dice / use_item_on / set_following / chalk / link / arrange / delete / get_component / show / generate_image`——**`extensions/` 里一个 `registerTool` 都没有**。`extensions/instructions.ts` 只注册了 4 个 instruction slot。

后果分两层：

- **作家与角色层**：提示词里的 AIRP 动作工具都不存在。作家只能拿内建 `write` 硬写 md；角色既不能走引用安全的物件移动，也不能移动 presence、选择组件动作或掷骰。
- **子代理层**：初始化器要落盘，能不能落取决于子代理的默认工具集。**这条我一开始照抄了 doc-11 §2.3 C1 的旧结论（"不含 write/edit"），是错的**——见 §0.4。


### 0.4 复核 pi-rp 源码后的更正：四条旧约束已被上游修掉

doc-11 §2.3 那张「pi-rp 源码级约束」表写于 2026-09-11 白天，当晚复核源码时发现**同一位作者当天已经把其中四条修掉了**：

| 约束 | 旧结论 | 现在 | 提交 |

| **C3** slot `options` 宏 | 不展开，`path:"{{x}}.md"` 原样传入 | 字符串叶子走宏展开 | `05893618c` |

| **C7** preset 目录 | 只读顶层，不递归 | `collectPresetFiles` 深度优先递归 | `6c693a7f3` |

上游甚至补了 `3ca27f746 test(subagent): airp-style world-init e2e covering C1/C2/C3/C5/C7`——**就是照着 AIRP 的用法写的 e2e**。

仍然成立的是 **C2**（`tools.allow` 是过滤器，加不出工具）、**C4**（`onMissing:"error"` 致命）、**C6**（`spawnAgent` 不校验 `delegatable`）、**C9**（回报被 `truncateTail` 截断）；**C8**（子会话扩展事件）已由 `5361105c3` 升级为工具级事件转发与 UI 上下文透传。

**但这里有一个更阴的坑**：`vendor/pi-rp/packages/*/dist/` 被 pi-rp 的 `.gitignore` 排除，**是每台机器本地构建的产物，不随 submodule 指针走**。实测本仓库的 dist 停在 **9/8**，比源码落后四天：

```
src/core/subagent/prepare.ts   9/11  DEFAULT_SUBAGENT_TOOLS = ["read","bash","edit","write",...]
dist/core/subagent/prepare.js  9/8   [...["read","grep","find","ls","bash"], ...]
```

我们的服务端与探针跑的都是 `dist/cli.js`——**所以运行时行为一直是旧的，源码修没修都白搭**。已重建，dist 现在与源码一致。为了不再靠记性，子模块工作流收进了 `tools/pi-rp.mjs`（`pnpm pi status|build|update|commit`，移植自 worldlines-rivet）——`status` 直接报 dist 新鲜度，凡是动 HEAD 的路径都自动重建。纪律见 AGENTS.md §6.5 / §7.2 与 doc-11 §2.3.1。

**对本计划的影响**：B1 不再需要为"让初始化器能写盘"造 `write_world_file` 之类的替身工具——扩展该注册的是引擎独有能力（`look_at / move_to / move / choose / roll_dice / use_item_on / set_following / chalk / link / arrange`），不是内建工具的同义词。

**`INIT_TOOLS` 也不需要了**（中途我一度写成"仍然必需"，那是在上游修掉之前）：`spawnAgent` 原本把 `tools` 预填成只有内建集，显式传进去的 `customTools` 因名字不在白名单里被静默滤掉；这违背 pi 自己的 `tools` 语义（收窄白名单，省略即全开），已由 pi-rp `dfebadcd3` 修正。现在 R2 只要 `spawnAgent({ profileId, task, customTools })`，与 R1 等价。详见 doc-11 §2.4。

## 2. 参考实现：worldlines-rivet（抄什么 / 不抄什么）

`~/projects/worldlines-rivet` 是同一套底座的成熟形态——**世界包 + 多 agent + pi-rp 引擎**，且已经跑过生产。它的会话域被抽成三个模块，正好对应我们缺的那一整块：

| 文件 | 行数 | 职责 |
|---|---|---|
| `services/gateway/wl-protocol.mjs` | 229 | **协议单一事实源**：命令集 / 事件目录 / 关闭码 / 回放魔法 id / 文本提取。**不含 I/O、不含状态、不认识 WebSocket** |
| `services/gateway/ws.mjs` | 315 | WS 外壳：路由 + 版本协商 + 鉴权 + 心跳 + 命令分发。**只把 sink 接到 ws 上**，回放与扇出全在会话域里 |
| `services/gateway/session-host.mjs` | 977 | **会话域**：spawn / stdout 行解析 / seq 盖章 / 回放缓冲 / pending 结算 / 两套 kill / 空闲回收 / 单回合护栏 |
| `launch.mjs` | — | **pi 启动参数与环境的单一来源**（writer / character / creator 三个入口共享） |

架构文档在 `docs/ARCHITECTURE.md`（§1 进程模型、§3 叙事循环、§7 存档、§9.1 web 壳）。

### 2.1 必抄（低成本、高收益，且我们一定会踩的坑）

| # | 机制 | 为什么我们需要 |
|---|---|---|
| 1 | **协议单一事实源模块** | 形状与词汇集中一处，**不掺 I/O**；并置一份 `.d.mts` 类型镜像，用测试锁死两者逐项一致，防手抄漂移。我们的落点是 `packages/shared/src/protocol/ws.ts`——AGENTS.md §6.3 要求"协议变更必须同步 schema"，这个模块就是那个锚点 |
| 2 | **事件目录分两类** | `EVENT_TYPES`（引擎透传）与 `GATEWAY_EVENTS`（网关合成）显式分开。我们的 `chalk_landed` / `layer_initializing` / `world_frozen` 是合成事件，`message_update` 是透传——混在一起迟早分不清谁该保证顺序 |
| 3 | **seq 盖章 + 回放缓冲 + `replay_done`** | 事件行前缀注入会话内单调 seq（**字符串手术，不 JSON.parse**：一次 slice 一次拼接）；buffer 有上界（4000 条）；回放按 `agent_end` 切轮次，回放最近 5 个**完整**轮次，最旧一轮不截断；回放帧与实时帧走**同一个 sink**、同一同步 tick 交付，所以交集只可能是逐字节相同的重复帧（客户端按内容去重），**不会丢事件**。我们现在刷新一下页面就丢一整段叙事 |
| 4 | **一码一义的关闭码** | `4400 协议不匹配 / 4401 仅鉴权 / 4404 会话不存在 / 1001 服务关闭`，配一个 `closeKind()` 做唯一分类实现，**禁止前端嗅探 reason 字符串**。他们踩过 4400/4401 共用一码逼得前端猜字符串的坑 |
| 5 | **`send` 即发即忘永不抛错 / `request` 永不 reject** | 超时以 `Result` 结算而不是抛异常，调用方不需要层层 try/catch，也不会吊死。我们现在 `PiRpcClient.send()` 的 pending 在进程死时靠 `cleanup()` 逐个 reject——形状对了一半，缺的是超时与"永不 reject" |
| 6 | **pending 唯一结算点** | 只在 `request` 创建、只经 `settle` 移除，同 id 多等待者 FIFO。这是并发下最容易写出幽灵 pending 的地方 |
| 7 | **两套 kill 策略** | `graceful`（SIGTERM → 共享宽限窗口 → SIGKILL）与 `immediate`（SIGKILL）。`stop()` **同步部分先完成**（删条目 / 发信号 / 关 watcher / 通知 sink）并返回一个 `done` Promise 等收割——删世界这种"要等进程真死"的动作才有得等 |
| 8 | **复用 + 收尸原子** | 同 (world, save) 已有存活会话直接**复用**，不 spawn 第二个。他们写明了理由：**重复 spawn 会往会话文件追加一轮 `preset_change`/`schema_change` 条目——这是正确性问题，不是优化**。顺手清掉同键的僵尸条目并关掉它的 state watcher（否则 inotify 一直盯着已删目录） |
| 9 | **⚠️ warmup 补历史（pi-rp 特有坑）** | rpc-mode **只在 `rebindSession()` 里订阅会话事件，而它跑在 `session_start` hook 之后**——会话建立期发的事件因此被丢掉。他们的解法：启动后延时补发一帧 `get_messages`（id=`init-history`）＋一帧 `get_entries`（id=`init-entries`，回收 choice 等 custom entry）。**AIRP 只取后半**：我们不要 chat 回放（chat 不进画布），只要 custom entry。详见 T0.6 |
| 10 | **单回合护栏 ≠ 空闲回收** | `turnTimeoutMs`（墙钟）与 `turnTokenBudget`（累计 token）任一触发就 **abort 本回合**，会话与存档保留，玩家能接着玩；空闲回收才是杀会话。他们实测过一次失控回合烧掉 294k 输入 / 13k 输出、撞满 150s 仍不收敛。**演示当场卡死是黑客松最贵的失败**，这道闸值钱 |
| 11 | **零回合会话的硬超时** | pi 在首个 assistant `message_end` 之前**根本不建会话 jsonl**，此时按常规空闲回收 = 开场那一下白演。他们对"完成回合数 = 0"的会话用 4 倍硬超时兜底 |
| 12 | **sink 抛错即注销该 sink** | 一个死连接不能拖垮其余客户端的推送 |
| 13 | **应用层 ping/pong + 服务端 30s 心跳** | 浏览器发不了协议层 ping；服务端一轮没收到 pong 就 terminate（移动网络 NAT 兜底） |
| 14 | **启动参数单一来源** | 他们的 `launch.mjs` 头注释写着血泪："三份复制（run.sh / gateway / handoff.ts）曾互相漂移，gateway 漏了 `_` 前缀过滤、缺挂载项"。**我们已经在漂移边缘**：`lifecycle.startWriter` 给 skills、`startCharacter` 不给，`probe-writer.mjs` 又自己拼第三份还多一个 `--offline`。收成 `writerLaunch()` / `characterLaunch()` / `initLaunch()` 三个函数，探针与服务端共用 |

### 2.2 抄形状不抄实现

- **gateway / runtime 服务边界**：`runtime-client.mjs` 与进程内 `createSessionHost` **完全同形状**（六入口 + 两个配置读数），靠 `WL_RUNTIME_URL` 一个环境变量切换，调用点一律 `await`（对同步返回值 await 无害）。我们不做远程 runtime，但**保持 host 的形状**——doc-05 §6 的云端托管版将来只换实现不换接口，正对上 doc-07 护城河 2「砍范围不砍形状」。零成本。
- **`admit` 准入钩子 + `maxSessions`**：多租户配额我们不需要，但留个钩子位几乎不花钱，且能顺手防"前端疯狂重连 spawn 出 30 个 pi 进程"。
- **`recorder` 四钩子**（session start/exit、turn start/end，含 token 累计）：他们用来做账本，我们用来做**演示后的成本复盘与卡点定位**，同一个接口。

### 2.3 明确不抄

| 他们的 | 为什么不抄 |
|---|---|
| **handoff / pass_mic 递话筒编排** | 不抄角色进程通信。角色由玩家点头像唤起；作家需要改变角色位置时直接调用共享 `move_to`，不启动角色会话、不递话筒 |
| **state / schema / `--strict` 门禁** | doc-07 §1 已定案 **AIRP 明确不用 pi-rp 的 state**；状态收编进实体通用 frontmatter（doc-05 §8.5），没有命名空间也就没有隔离门禁 |
| **mode 三态（solo / single-writer / multi）** | 我们只有一种形态：常驻作家 + 懒灵魂角色 |
| **鉴权 / 多租户 / 归属校验 / 配额 / 账本 / supabase** | 单机单玩家的黑客松版本不需要。**但关闭码 4401 的位置留着**，将来加不用改协议 |

### 2.4 明确不搬：wl 的"角色上下文分层"

`docs/ARCHITECTURE.md` §3.3 那套 `<state> → <scene_brief> → <knowledge> → <narration>` 组装，**是 wl 为自己"多角色同一场戏实时互动 + 信息边界"造的**：它靠 state 快照告诉角色世界状态，靠知识的 visible 名单防泄密，靠 handoff 每拍人工策展 scene_brief。

**AIRP 一条都不需要，也不能抄**（2026-09-12 明月三次纠正）：

| wl 的层 | AIRP 的对应真相 |
|---|---|
| `<state>` world / 领地快照 | **不存在**。世界没有独立状态文件——状态就是叙事 frontmatter（`status.data`），而它也只是 **chalk 的快照**。角色要看就读那篇 chalk |
| `<knowledge>` 注入 | **不存在**。没有知识条目、没有可见性名单、没有守密纪律（doc-08 §4.3 已作废此方向） |
| `<scene_brief>` 每拍手写策展 | **不存在**。没有一个"给角色的场景简报"这种东西；那是 **summary**，而 summary 是**作家与角色共用的**、且**尚未实现** |
| `<narration>` 保底旁白 | **就是下一篇 chalk**。它已经在世界目录里，角色自己 `look_at` 就能看，不需要引擎替它挑一段塞进上下文 |

**正确模型（写死在文里，别再漂）**：

1. **所有数据都在文件系统**——世界目录就是真相源，没有 state、没有独立状态文件、没有内存态。
2. **要看什么就直接读**——`look_at`（玩家可见语义）/ `read`（原始文件）/ `bash`。角色的知情权 = 读写权限，不是注入量。
3. **引擎的职责只有一件事**：在 hook 里**告诉角色当前场景有哪些文件**（一份预览/清单，不是全文），并**在文件变化时**刷新它。这就是 `before_agent_start` 注入的"本层现有 + 世界动态"。
4. **hook 凭什么知道有什么、变了什么**——靠 **event**：世界动作（move / choose / roll / chalk 落盘 / 初始化…）写进 `history.db` 事件表，`fs.watch` 抓文件变化。清单与增量都由事件派生，不是谁手写的。

**唯一被明确留白的**是 **summary**（把多轮叙事压成一段摘要）：它**作家与角色共用**，是 hook 注入的压缩层，**本轮不做**——不要用"角色场景简报"这个名字把它提前造出来。见 §6 与 §11 取舍登记 #3。

## 5. B2 Hook 注入（P0 · 4h）

> **先读 `doc-22-Hook注入协议.md`**（2026-09-12 定案）：状态块与事件段的分工、抄 Nodesign turn-state 的九条机制（首轮全量/之后只报变化/未变点名/压缩后重置/量化防抖）、作家与角色的分节表、`before_agent_start` 的接线纪律（不碰 systemPrompt）。本节以下是它落地前的旧口径，**三段式已扩成六节 + 一个事件段**。

doc-05 §5 的管线第一步叫「Hook 上下文注入」，doc-12 #1 把它列为赛时最小子集之一。**pi-rp 的 `before_agent_start` 就是这个 Hook**：它在玩家提交 prompt 之后、agent loop 之前触发，可以返回 `{ message: { customType, content, display } }` 注入一条持久化消息，也可以改这一轮的 system prompt。

三段各自的来源与纪律：

| 段 | 来源 | 纪律 |
|---|---|---|
| **视点上报表** | 前端上报（当前层 / 相机中心 / 选中项 / 背包清单）→ server 写 `canvas.db` → 扩展读 | doc-05 §10「这个/这里」的消解靠它；**不给坐标数字**，给人话方位 |
| **本层现有** | `look_at` 同款逻辑，只列文件名 + 一行摘要 | **只列不塞全文**——doc-08 定案 4「防回潮」的同一条原则 |
| **世界动态** | `history.db` 事件表取「自上次发言以来」的增量 | **人话陈述句、合并去重、N 轮未提及自然过期**（doc-05 §5.1）。不给 diff、不给路径清单噪音 |

**事实来源只有 event（2026-09-12）**：上面三段都不是谁手写或谁放进内存的——视点来自前端上报、清单来自扫描目录、动态来自 `history.db` 事件表。（**口径更正 2026-09-12**：视点的*当前值*在 `canvas.db`，不是从事件里 replay 出来的——事件表是历史不是状态表；只有 `layer_entered` 这类有叙事意义的视点变化才另落一条事件。见 doc-21 §1.1/§4.4。）引擎不做状态机，只做"把事件翻译成一份清单"。角色那份（B3）复用同一个扩展、同一张事件表，只是分节不同。

**关键工程细节**：扩展跑在 agent 进程内，`cwd` 就是世界根目录，所以它可以**直接用 `node:sqlite` 只读打开 `.airpworld/history.db`**——不需要 sidecar HTTP，不需要 server 拼字符串塞进 prompt。server 与扩展共享同一个文件，注意开 WAL、扩展侧只读连接。

**为什么不用 `--append-system-prompt` 或每轮 prompt 前置拼字符串**：前者不随轮变化，后者把系统噪音混进玩家的话里，作家会把它当玩家说的（doc-03 人话协议里最容易破功的地方）。`before_agent_start` 的注入是**独立的 customType 条目**，身份清清楚楚。

## 6. B3 角色上下文（P0 · 3h）

### 6.1 问题复述

玩家推了几轮剧情，作家落了几篇板书 md、演化了几个物件。这时玩家去找角色。角色进程是**刚 spawn 的**，它手里只有 preset 引的几个身份文件，**不知道此刻在场里发生过什么**，于是要么装傻，要么胡编——遮罩对话的质量当场塌掉（doc-07 风险表已登记）。B0 已把 `startCharacter` 上那个没人传的 `recentContext` 参数删掉，本节重建。

### 6.2 正确模型：不组装上下文，只告诉它"这儿有什么文件"

**先把错误方向钉死**：AIRP **没有** `state`、**没有** `knowledge`、**没有**"给角色的场景简报"这三种东西（§2.4）。上一版本节照着 wl 抄了一套 `<state> → <scene_brief> → <knowledge> → <narration>` 组装，还对着一个根本不存在的机制写了好几段设计——那是纯粹误导，已删。

实际成立的只有三句：

1. **所有数据都在文件系统里。** 世界目录 = 真相源。角色要知道什么，**自己读**：`look_at`（玩家可见语义 + 格式化互动字段）/ `read`（原始文件含 frontmatter）/ `bash`。角色的知情权等于它的读写权限，不需要任何人喂。
2. **引擎只负责告诉它"此刻场景里有什么"**——一份**预览/清单**，不是全文、不是摘要、不是状态快照。这是 hook 的职责。
3. **hook 凭什么知道有什么、变了什么**——靠 **event**。只有事件驱动，没有别的事实来源。

> **关于 `status`**：它不是"状态系统"，它是**某篇 chalk 的一个快照**（doc-20 §2.3）。角色想知道状态，就是去读那篇 chalk——`look_at` 会把 `status / choice / roll_dice` 格式化成稳定文本块。没有第二条通道。

### 6.3 角色的知情链条（三段，全部是"路径 + 一行说明"）

| # | 角色拿到什么 | 谁给的 | 纪律 |
|---|---|---|---|
| 1 | **preset 引用文件** | spawn 时载入 | identity / appearance / personality；这是角色的"我是谁"，与剧情无关 |
| 2 | **本层现有清单** | `before_agent_start` hook | 当前层目录里有什么文件（README / chalk / 物件 / 门牌）+ 人话方位。**只列路径 + 一行这是什么**，不给全文 |
| 3 | **世界动态** | 同 hook，从 `history.db` 事件表取增量 | "自上次以来"的人话陈述句（谁移动了什么、谁掷了骰、哪层第一次被走出来）。作家与角色**同一套事件表**，没有两套 |

hook 注入的形状（**是清单，不是散文**）：

```
[You are here] Baker Street — the counter. (Evening, after the rain.)
[Files in this layer]
  · README.md — the scene itself
  · 01-rainy-night.md — chalk, the door slammed open
  · 02-counter.md — chalk, the woman in room four
  · copper-key.md — a prop on the counter
[Recently, in the world]
  · The player moved "copper-key.md" into their bag.
  · A dice check on "Deduction" rolled 62 (passed).
[Read any of these directly if you need the detail.]
```

**这就是全部**。没有 `<narration>` 保底段（那篇 chalk 已经在清单里，角色要看自己看）、没有 `<state>`、没有 `<knowledge>`、没有"不连贯提示"这类精心设计——那些是 wl 为解决**自己的**共享通道问题而造的，AIRP 没有共享通道，也就没有那些问题。

### 6.4 为什么只给清单而不是灌全文

- **文件即真相**：全文注入 = 在内存里造第二份世界副本，与世界文件背离就成幽灵（doc-05 §8.5）。
- **token**：全量灌等于每次点开角色都把整层吞一遍，第 20 轮时角色的上下文比作家还长。
- **哲学一致**：这就是 pi-rp Agent Skills 的 progressive disclosure（system prompt 只带 description，正文按需 `read`），也是 doc-05 §1 懒加载的同一条。
- **共创一致**：指路只减少无关 token，不是信息门禁——角色有整个世界的读写权。

### 6.5 注入方式

> 分节表与装配规则见 `doc-22-Hook注入协议.md` §3.2（角色 4 节）/ §4。

走**扩展侧 `before_agent_start`**（与作家那份 B2 hook 同一个扩展文件、同一套读事件的代码，按调用者身份分节输出——见 §5）。**不要用 `prompt()`**：现在角色 spawn 里那行 `setTimeout(() => client.prompt("[System note: ...]"), 500)` 有三个毛病——① 占掉一个真实对话回合，角色会对着系统提示回话；② 500ms 是猜的；③ 每次点开都重复注入。`appendMessage` 也只作为退路（落一条不触发 turn 的会话条目），首选 hook。

**角色身份从哪来**：B3 要给 `characterLaunch` 加一个角色标记 env（如 `AIRP_AGENT_ROLE=character:<id>`），扩展据此知道"我是角色 agent，不是作家"，从而只输出 §6.3 那三段、不注入作家专用的视点上报表。（B0 只留了 `airpEnv()` 这个位置，尚未加标记。）

### 6.6 ~~summary 的边界~~ → **撤销这一层（2026-09-12）**

上一版写着"唯一被明确留白的能力是 summary：把多轮叙事压成一段短摘要的压缩层"。**这一层不该存在**——它要压的东西，正是 doc-21 的事件段 + doc-22 的状态块，只不过是有损版。留着它，将来一定会有人照着这行字造出第三条通道。

**"summary"这个词下面压着三件不同的事，拆开就没有幻觉了**：

| 要压的是什么 | 归谁 | 状态 |
|---|---|---|
| **画布上的叙事正文**（永久 chalk 增殖） | doc-08：`fold_chalk` + `type: scenario`。注意它明文定为**无损重组，不是摘要** | 方向已定案，赛后实现 |
| **会话 transcript 超窗** | pi-rp 自己的 compaction（`session_before_compact` / `session_compact`） | 引擎已有，我们只需在其后重置指纹记忆（doc-22 §4 规则 5） |
| ~~**注入给 agent 的上下文**~~ | ~~summary 层~~ | **撤销**。见下 |

**为什么第三件不需要压缩层：注入块天生有界，不随轮次增长。**

- 状态块：没变的节不发（指纹 diff），清单节只报增删，每节条目有上限，只给路径 + 一行不给全文（doc-22 §4）；
- 事件段：念过就推游标不再念，合并去重，超过 12 条折叠成一句（doc-21 §5.4）。

**一个大小不随轮次增长的东西，没有压缩的对象。**

**那"第 3 轮发生的事，第 50 轮还记得吗"？** 它有三个归宿，都不是注入层：① 会话 transcript（引擎管，超窗自己 compact）；② 世界文件（chalk 落盘，`look_at` 随时可读）；③ 事件表（全量保留，只是不主动注入）。这正是 doc-05 §5.1 那句"作家的知识来源本来就该是『我记得发生了什么』"的意思。

**唯一的真缝**：compaction 之后，agent"记得"的那部分被摘要吞了——状态块能补回"现在什么样"，补不回因果。处理方式是**调教 pi-rp 的 compaction，不是新建一层**。

**调教的入口是 preset，不是扩展**（`docs/prompt-presets.md`「Hidden Prompt Overrides」）：

```json
{ "hiddenOverrides": { "compaction": {
    "systemPrompt": "你是一个剧情总结助手。只输出结构化摘要，不要继续对话。",
    "updatePrompt": "【已有总结】：\n{previous_summary}\n\n【最新增量对话】：\n{conversation}\n\n……"
} } }
```

五个字段可覆盖（`systemPrompt` / `initialPrompt` / `updatePrompt` / `turnPrefixPrompt` / `branchSummaryPrompt`），占位符 `{conversation}` / `{previous_summary}`。**手动与自动压缩都走这一份**（`agent-session.ts:3133` 手动 / `:3480` 自动 / `:4835` 分支总结，三处取的都是 `_activePreset.hiddenOverrides?.compaction`）。

于是 doc-14 那三项持久事实（承诺 / 骰子结果 / 关系变化）的落点很清楚：**写进作家 preset 的 `updatePrompt`**；角色 preset 另写一份（角色该保住的是"我对玩家的态度怎么变的"）。pi-rp 自带的文档示例本身就是一个中文剧情总结提示词——上游已经为这个用例备好了。

> **一处澄清**（免得后人再走一遍我走过的弯路）：`customInstructions` 是**另一回事**——它是 `/compact` 那一次调用的临时侧重，以 `Additional focus: …` 追加在提示词后（`compaction.ts:668`），阈值自动触发时为 `undefined`（`agent-session.ts:3427`）。那是设计如此：一次性的侧重不该变成持久口径，**持久口径归 preset**。**pi-rp 这里不缺东西，不用改。**

### 6.7 顺带把 `character_prompt` 接上

`index.ts` 里 `character_prompt` 分支**是空的**（只有一行注释）。前端 `CharacterModal` 因此用本地假回复顶着。接上之后连带要做：`[emo: <tag>]` 标签从流里解析出来（提示词已经要求角色输出了）→ 走 WS 推给前端切表情 → 对应 `docs/前端改造计划.md` T3.2 的精灵表。

### T4.1 事件类型补齐

### T4.2 ⚠️ 纠偏：取消三处"裸 prompt 打断"

`routes/world.ts` 的 `/dice`、`/use-item`、`/god-action` 都在动作发生的**当下**直接：

```ts
writer.prompt(`[System notice: the player made a check ... rolled 62 ...]`)
```

**这违反 doc-05 §5.1 的明文定案**：「作家不读 diff、不被推送——只在玩家下一轮输入触发的 Hook 阶段收到人话 system reminder。**不打断、不自动起 turn。**」

现在这个写法的实际后果：玩家掷一次骰子，作家立刻自说自话起一轮；玩家再打字，又起一轮——两轮叙事互相打架，画布上会出现两篇抢戏的板书。

改法：三处都只 `appendWorldEvent(...)`，**由 B2 的 Hook 在玩家下一轮输入时合并注入**。（`use_item_on` 是否该破例即时响应，见 §11 取舍登记 #4。）

### T4.3 `fs.watch` 精细化

现在是单 watcher + 150ms debounce + 广播一条无差别 `file_changed`，前端收到就整层重取。至少要带上**变了哪个文件**与**是新增还是修改**——B2 的"世界动态"段和前端的幻影落地都要靠它。递归 watch 在 WSL 下对大目录不可靠，世界目录小，够用；但要过滤 `.airpworld/`（现在过滤了）与 `node_modules`（过滤了）。

## 9. B6 网关与会话域（P1 · 5h）——按 worldlines-rivet 的三层切

不要在 `index.ts` 里继续堆 `if`。照 §2 的切法分三个模块，**边界就是"谁认识什么"**：

```
packages/shared/src/protocol/ws.ts   ← 只有形状与词汇：命令集 / 事件目录 / 关闭码 / 回放 id
                                        不含 I/O、不含状态、不认识 WebSocket
apps/server/src/gateway/ws.ts        ← WS 外壳：路由 + 版本协商 + 心跳 + 命令分发
                                        只把 sink 接到 ws 上，回放与扇出不归它
apps/server/src/engine/session-host.ts ← 会话域：spawn / 事件解析 / seq / 回放缓冲 /
                                        pending / 两套 kill / 空闲回收 / 回合护栏
```

`lifecycle.ts` 被 `session-host.ts` 吸收（它现在做的三件事——单例、spawn、回收——正好是会话域的子集）。

### T6.1 协议模块（1h）

`packages/shared/src/protocol/ws.ts`，照抄 `wl-protocol.mjs` 的组织方式：

| 导出 | 内容 |
|---|---|
| `PROTOCOL_VERSION` | `"1"`，WS 查询参数 `?v=1` 协商，不匹配就响亮关连接 |
| `WS_COMMANDS`（**未实现，T6.1 目标态**） | 客户端 → 服务端：`input` / `choice` / `abort` / `character_open` / `character_input` / `character_close` / `viewpoint` / `ping`。**与现状完全不同**——当前实现是 `writer_prompt` / `character_prompt` / `character_start` / `character_stop`（`apps/server/src/index.ts:119-203`） |
| `WS_CLOSE` + `closeKind()` | `4400 协议 / 4401 鉴权（占位） / 4404 会话不存在 / 1001 关闭`。**唯一分类实现**，前端不许嗅探 reason |
| `EVENT_TYPES` | 引擎透传（`message_update` / `message_end` / `tool_execution_*` / `agent_settled` / `response`）+ 网关合成（`chalk_landed` / `canvas_patched` / `file_changed` / `world_frozen` / `layer_initializing` / `layer_init_failed` / `turn_aborted` / `process_exit` / `replay_done`） |
| `GATEWAY_EVENTS` | 上面后半截的清单，显式标出"这些不是引擎发的" |
| `REPLAY_ID` | `init-history` / `init-entries` / `rollback-history` 三个魔法 id 收成常量 |

配 zod（我们已经用 zod）而不是他们的手写 `.d.mts` 镜像——**同一份 schema 既校验又产类型**，比他们那套"两份镜像 + 一致性测试"更省。这是我们能做得比参考实现更好的一处。

### T6.2 会话域（2.5h）

按 §2.1 的 1/3/5/6/7/8/10/11/12 逐条落。最小形状：

```ts
createSessionHost({ spawn, log, timings, maxSessions, idleTimeoutMs, turnTimeoutMs })
  → { start(spec), send(id,msg), request(id,msg,{timeoutMs}), subscribe(id,sink),
      stop(selector,{policy,reason}), list(), info(id) }
```

**赛时可以砍的**：多租户归属、配额 `admit`、`recorder` 账本、远程 runtime。**不能砍的**：复用+收尸、seq+回放、pending 结算、两套 kill、回合护栏——这五条每一条都对应一个演示当场翻车的场景。

### T6.3 WS 外壳（1h）

- 路由 `/ws?v=1`（或 `/api/sessions/:id/events?v=1`，若走多世界）；
- 命令分发：每条带 `id` 的命令**必有 response**；pi 的 `response` 行经广播自然到达发起者（**无需按来源分发**），只有"pi 不回执"的命令（如 `extension_ui_response`）才由网关合成回执；
- 未知/非法消息：单发 `{type:"response", success:false, error}`，**不关连接**；
- 心跳：服务端 30s ping + 应用层 `ping`/`pong`。

### T6.4 世界切换与并发（0.5h）

- `/api/worlds/load` 现在只 `store.close()`：不停旧作家进程、`worldFrozen` 是 router 闭包里的模块级变量、切世界不重置 → 全部收进会话域的 `stop({world})`；
- `history.db` 被 server 与 agent 扩展同时打开：**开 WAL，扩展侧只读连接**；
- fail-loud（doc-07 §3 禁令）：模型不可用明确报错，不静默回退。

## 11. 取舍登记

| # | 事 | 结论 |
|---|---|---|
| 1 | 自研 RpcClient vs 用 pi-rp 的 | **用 pi-rp 的**。协议是人家定的，自研只会一路追着抄 |
| 2 | 上下文注入走 server 拼字符串 vs 扩展 hook | **扩展 hook**。它在 agent 进程内，cwd 就是世界根，能直读两个 db；且 `before_agent_start` 每轮新鲜，spawn 时注入只新鲜一次 |
| 3 | 角色上下文：组装 vs 只给清单 | **只给清单**。没有 state / knowledge / scene_brief 可组装；所有数据在文件系统，角色自己 `look_at` / `read`。hook 只报"这儿有什么文件 + 最近变了什么"，事实来源是 event（§2.4、§6） |
| 4 | `use_item_on` 是否即时打断作家 | **待拍板**。它是 doc-19 的 money shot（拖钥匙开锁要立刻有回应），"不打断"的定案在这里可能需要一个明写的例外。倾向：`use_item_on` 走 `followUp`（等作家当前轮结束再接），既不打断也不用等玩家再打一次字 |
| 5 | pi-rp 深路径 import vs 给它补 export | 先深路径（vendored，零风险）；若要上游化再补 `"./rpc"` 导出（AGENTS.md §7.2：改 pi-rp 在 vendored 副本里改，指针同步提交） |
| 6 | 协议类型：zod 单份 vs rivet 的「模块 + `.d.mts` 镜像 + 一致性测试」 | **zod 单份**。他们用手写镜像是因为纯 JS 无类型；我们有 zod，同一份 schema 既校验又产类型——这是少数我们能做得比参考实现更简的地方 |
| 7 | 抄不抄 rivet 的 handoff / pass_mic 递话筒 | **不抄**。角色只在玩家直聊会话中作为 Agent 行动；作家调度角色位置直接用共享 `move_to`，不需要角色间递话筒 |
