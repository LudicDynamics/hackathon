## 0. 结论先行

当前前端不是缺少视觉素材，而是同一舞台由多套视觉与交互 Module 同时解释：视觉 token 分裂、Depth 只存在于散落的 z-index、Chrome 与状态归属分散、Nook 只是局部复用 Canvas、角色遮罩同时承担过多演出职责。

这些问题会直接表现为：

- 画布、背包、阅读面板、角色遮罩看起来不像同一个世界；
- 交互入口重复，点击语义与文档冻结语义不一致；
- 演出层之间靠 z-index 竞争，新增效果容易遮挡已有内容；
- 小天地、角色对话、主场景之间的相机与退场连续性不稳定；
- 美学调整需要同时修改多个文件，测试只能靠逐页截图和人工回归。

本文件不提前定义新的 Interface。它只记录应继续挖掘的 Module、Seam、Adapter 与验证问题。进入实施前，应逐项完成设计与评审。

## 3. 候选一：收敛视觉语法 Module

**强度：Strong**

### Files

- `apps/web/src/main.tsx:5-7`
- `apps/web/src/index.css:5-20, 856-868`
- `apps/web/src/prototype.css:3-21`
- `apps/web/src/scene-shell.css:1-18`
- `apps/web/tailwind.config.js:8-49`

### Problem

当前至少有四个视觉来源同时定义颜色、字体、纸面、阴影与交互状态：`index.css` 的 v2 token、`prototype.css` 的紫色旧壳、`scene-shell.css` 的追加覆盖，以及 Tailwind 配置中的同名色彩。结果是视觉 Interface 依赖加载顺序、scope 和 specificity，几乎与 Implementation 一样复杂。

源码中还存在 literal 紫/棕值与 v2 token 并存的情况。浏览器实测可见：场景画布、背包、阅读面板、World shelf 与角色遮罩并没有稳定地共享同一材质语法。

### Solution direction

建立一个视觉语法 Module，集中解释：

- 颜色、字体、纸面、墨色和 shadow；
- 场景、背包、阅读、Nook、遮罩的 surface 关系；
- hover、focus、dragging、busy、disabled、error 等交互态；
- 桌面与移动尺寸的字号、间距和可触达尺寸。

题材差异应该通过明确的 Adapter 表达，而不是继续追加 CSS 覆盖。

### Leverage / Locality / Test surface

- **Leverage**：一个视觉 Interface 影响所有舞台 surface。
- **Locality**：审美调整与视觉 bug 集中在一个 Module。
- **Test surface**：可以对视觉状态矩阵做静态检查，再用固定尺寸截图验收。
- **Deletion test**：删除现有重复 token 与旧覆盖后，若没有实际调用点留下，说明它们没有提供有效 Leverage。

## 4. 候选二：建立舞台 Depth / 演出 Module

**强度：Strong**

### Files

- `apps/web/src/components/canvas/Canvas.tsx:520-580`
- `apps/web/src/components/performance/PerformanceLayer.tsx`
- `apps/web/src/App.tsx:539-611, 724-755`
- `apps/web/src/index.css:1935-2108`
- `apps/web/src/scene-shell.css:23-84, 174-185`

### Problem

`doc-19` 定义了背景、画布基座、实体、特写舞台和前景的 Depth 关系，但 Implementation 主要依靠散落的 z-index 表达：12、20、50、55、90、240、800、1001、1100、1200 等值分别出现在不同文件。

Canvas、PerformanceLayer、角色遮罩、骰子、grain、chrome 与系统反馈没有一个可检验的 Depth Interface。现有 CSS 注释已经承认 grain 可能覆盖 header/sidebar；新增演出很容易通过加大 z-index 解决局部问题，却破坏另一处遮挡关系。

### Solution direction

把“世界舞台、实体互动、show_frame、dialogue spotlight、chrome、系统反馈”收敛为同一演出 Module 的 Depth 语义。每个 Adapter 只声明自己位于哪种 Depth，不再自行竞争具体数字。

### Leverage / Locality / Test surface

- **Leverage**：追光、骰子、角色遮罩、动态背景共享同一舞台语法。
- **Locality**：遮挡、聚焦和退场规则集中维护。
- **Test surface**：可验证“哪个 Depth 覆盖哪个 Depth”，而不是只靠肉眼发现 z-index 回归。
- **Deletion test**：删除散落的 z-index 解释后，若演出仍由一个 Module 完成，旧数字就是泄漏的复杂度。

> 影响中涉及 stacking context 的部分是审查推断，实施时必须补充真实浏览器截图与交互回放。

## 5. 候选三：收回 Chrome 与舞台状态 Locality

**强度：Worth exploring**

### Files

- `apps/web/src/App.tsx:100-186, 194-282, 315-350, 396-503, 512-750`
- `apps/web/src/components/chrome/*`
- `apps/web/src/components/sidebar/RightSidebar.tsx:28-210`
- `apps/web/src/components/nook/NookView.tsx:331`
- `apps/web/src/lib/writer-state.ts`
- `apps/web/src/state/useWorld.ts:350-579`

### Problem

`App.tsx` 同时拥有 shell、背包、角色、Nook、writer busy、WS 事件、音频、Canvas、PerformanceLayer、所有 Chrome、Stop writing、遮罩和世界选择。与此同时，`components/chrome/*` 与 `RightSidebar` 保留着另一套 Adapter；源码搜索未发现 CompassRose、HintBar、LayerBadge、Minimap、RightSidebar 的当前调用点。

writer busy 也存在多份事实：App 的 `writerWorking`、`useWorld` 的帧处理、`lib/writer-state`，以及实体自身的 `busy/running`。当前 App 还同时渲染独立 Stop writing 和 Writer dock 内的 Stop，视觉与状态入口重复。

浏览器实测中，Header、右侧角色/背包、底部行动台、Writer 状态与右上角 Agents/Voice/Effects 同时出现时，玩家注意力没有明确的主次关系；移动端只是缩小内容，没有重新组织重点。

### Solution direction

先裁决唯一的 Chrome Module 与唯一的舞台状态投影：

- 哪个 Module 拥有打开、关闭、Escape、键盘焦点与移动端重排；
- 哪个 Module 拥有 writer busy、Stop writing、错误与重试的公开状态；
- 旧 Adapter 要么删除，要么成为真实 Seam 上有调用者的第二个 Adapter。

### Leverage / Locality / Test surface

- **Leverage**：桌面、移动和 Nook 共享同一套 Chrome 语义。
- **Locality**：入口、关闭顺序与忙碌态集中维护。
- **Test surface**：以状态转移测试替代大量“点这里再点那里”的分散回归。
- **Deletion test**：删除无调用点的 Chrome Module 不应改变运行行为；如果改变，说明调用关系没有被正确记录。

## 6. 候选四：把角色对话做成 Theatre Module

**强度：Speculative**

### Files

- `apps/web/src/components/overlay/CharacterModal.tsx:97-799`
- `apps/web/src/index.css:332-680`
- `apps/web/src/App.tsx:242-258, 724-747`
- `apps/web/src/lib/audio.ts`
- `apps/web/src/components/overlay/dialogue-pages.ts`

### Problem

`CharacterModal` 同时承担 WS frame 接收、页切分、逐字流、phase、emotion、TTS、stinger、输入、关闭与相机连续性。浏览器实测中，单角色对话仍按双角色舞台保留空的左侧 portrait slot；对话纸面、角色立绘和 `Visit private space` 没有完全共享同一套纸面语法。

### Solution direction

把“角色在场、注意力、对话页、声音、情绪、退场后果”视为一个 Theatre Module。portrait、voice、frame 可以是 Adapter，但舞台节奏和退场语义不应散落在遮罩内部和全局 CSS 中。

### Leverage / Locality / Test surface

- **Leverage**：单聊、语音、情绪切换和退场揭示共享同一舞台语法。
- **Locality**：对话节奏与声音规则集中维护。
- **Test surface**：可以直接测试“页推进、未完成快进、翻页、退场揭示”的状态转移。
- **Deletion test**：如果去掉当前空槽和随机布局特例后，单角色与双角色仍由同一 Module 解释，特例就是浅 Module 的信号。

这是 Speculative 候选：只有在角色戏剧确定为主要美学卖点时，重构收益才足够高。

## 7. 候选五：让 Nook 成为连续的舞台 Adapter

**强度：Strong**

### Files

- `apps/web/src/components/nook/NookView.tsx:17-45, 249-357`
- `apps/web/src/App.tsx:479-509, 540, 744-750`
- `apps/web/src/components/canvas/Canvas.tsx:87-156, 492-579`
- `apps/web/src/components/canvas/CanvasObject.tsx`
- `apps/web/src/components/canvas/CardRenderer.tsx`
- `apps/web/src/lib/footprint.ts:48-72, 110-122`
- `apps/web/src/state/useCamera.ts:20-36, 96-110, 126-193`

### Problem

NookView 说明自己复用 Canvas、避免第二个 `useWorld` / WebSocket，但实际只传入 move、choice、dice、take 等部分动作；没有传入完整的实体行动、角色打开、道具出示、背包拖入和门跳转能力。

App 同时保留主 Canvas 和 Nook Canvas。相机是 module-scope 单例，footprint 与 hover/drag 查询又扫描全局 `.object`。源码还显示：进入角色对话时保存 `dialogue` 相机记忆，从角色进入 Nook 后再保存 layer 记忆，可能覆盖原本的对话记忆；这一点尚未用浏览器完整回放验证。

浏览器实测中，Nook 是一块深色空舞台，和主场景的材质、互动、相机连续性不足。

### Solution direction

把层与 Nook 视为同一 Theatre Module 的两个 Adapter：

- 共享相机记忆、卡片互动、拖拽和演出 Depth；
- 任一空间都遵守相同的查看、行动、进入、出示规则；
- 页面只保留一个 active projection，避免隐藏 Canvas 继续接收全局事件和参与测量。

### Leverage / Locality / Test surface

- **Leverage**：层与 Nook 共享完整互动语义，而不是只共享 Canvas 外壳。
- **Locality**：进入、退出和相机恢复集中维护。
- **Test surface**：同一动作可以分别在层与 Nook 中回放并比较结果。
- **Deletion test**：删除第二个隐藏 Canvas 后，如果主舞台仍能通过 Adapter 投影 Nook，第二个 Canvas 没有提供有效 Depth。

## 8. 候选六：恢复门卡与道具的动作语义

**强度：Strong**

### Files

- `apps/web/src/components/canvas/CardRenderer.tsx:105-112, 125-154`
- `apps/web/src/components/canvas/PropCard.tsx:19-34`
- `apps/web/src/components/narrative/EntityInteractions.tsx:16-95`
- `docs/doc-06-演出与交互设计.md:194-241`
- `docs/gameplay/doc-25-未写之门Demo.md`

### Problem

`doc-06` 冻结：角色单击直进对话，门卡/场景卡双击穿越；查看外观与选择使用分离。但当前 visual door/gate 的根节点单击会直接 `onEnterGate`，`EntityInteractions` 又提供 Enter scene 按钮，形成单击直达与按钮进入两条路径。`PropCard` 在存在 `onEnter` 时也优先进入，无法先查看外观。

这不是单纯按钮样式问题，而是玩家无法稳定建立“查看、确认、穿越、使用”的动作语法。

### Solution direction

把“查看外观、选择行动、确认穿越、以物解谜”视为同一个交互 Module 的动作家族；每种实体只拥有一种默认入口，其他入口必须有明确的视觉与键盘语义。

### Leverage / Locality / Test surface

- **Leverage**：门、信件、手机、场景卡和 NPC 都共享动作语法。
- **Locality**：点击、双击、键盘聚焦和拖放判定集中维护。
- **Test surface**：可用动作矩阵覆盖单击、双击、Enter、Escape、拖放与失败回退。
- **Deletion test**：删除重复 Enter 路径后，若所有实体仍能完成查看和行动，重复路径就是浅 Module。

## 9. 候选七：让交互反馈服从持久事实

**强度：Worth exploring**

### Files

- `apps/web/src/App.tsx:442-467`
- `apps/web/src/components/canvas/CardRenderer.tsx`
- `docs/doc-06-演出与交互设计.md:58-75`
- `docs/doc-19-多模态与游戏性交互升级.md:159-178`

### Problem

用物解谜时，`CardRenderer` 可能在服务器动作确认前先播放 unlock 与解锁动画；App 的失败路径主要显示 toast，缺少明确的反演或回退演出。这样会让玩家看到“已经成功”的视听反馈，但持久事实可能并未改变。

`doc-06` 要求反馈至少覆盖视觉变化、拟音、Chalk 回执、空间去向和持久事实。当前反馈节拍还没有集中在一个 Module 中解释。

### Solution direction

建立“动作请求 → 事实确认 → 成功演出 / 失败回退”的统一节拍。拟音、动画、Chalk 和空间变化应由同一动作结果驱动，而不是各自提前猜测结果。

### Leverage / Locality / Test surface

- **Leverage**：移动、出示、开门、掷骰和选择共享可信反馈规则。
- **Locality**：成功、失败、重试和回退集中维护。
- **Test surface**：可以稳定测试网络失败、冲突、重复动作和持久化失败。

## 10. 候选八：收敛 writer busy 与角色帧归属

**强度：Worth exploring**

### Files

- `apps/web/src/App.tsx:130-186, 242-258, 428-438, 680-691`
- `apps/web/src/state/useWorld.ts:350-579`
- `apps/web/src/lib/writer-state.ts:29-54`
- `apps/web/src/components/narrative/EntityInteractions.tsx:16-95`
- `apps/web/src/components/overlay/CharacterModal.tsx:118-170`

### Problem

App、useWorld、writer-state、实体自身和 CharacterModal 都持有部分 busy、帧和错误状态。`useWorld` 先对每个 WS 帧广播通用 `airp:agent-frame`，App 与 CharacterModal 又分别消费角色帧，形成双通道。角色归属过滤还有 `undefined` 与 `null` 守卫不一致的风险。

这会让视觉问题和协议问题相互泄漏：一个遮罩显示错误，维护者需要同时检查多个 Module 才能判断是帧没到、帧归属错误，还是 phase 没结束。

### Solution direction

将 writer、character、show、error 的公开状态投影集中到一个帧归属 Module；App、CharacterModal 和 Writer dock 只消费同一份已归属状态。

### Leverage / Locality / Test surface

- **Leverage**：所有公开演出共享可靠的帧归属与 busy 语义。
- **Locality**：错误、停止、重试和结束态集中维护。
- **Test surface**：可用真实帧序列测试归属、去重、乱序、缺失 ID 和终止。

## 11. 候选九：把音频与视觉演出放到同一节拍

**强度：Worth exploring**

### Files

- `apps/web/src/lib/audio.ts`
- `apps/web/src/components/overlay/CharacterModal.tsx:307-422`
- `apps/web/src/components/performance/PerformanceLayer.tsx`
- `docs/doc-19-多模态与游戏性交互升级.md:99-134`
- `docs/audio/00-共同上下文.md`

### Problem

音频 Module 已定义 ambient、BGM、foley、stinger，但部分关键演出没有真实调用点：`gate-open` 与 `page-turn` 在 doc-19 中仍记录为本批无调用点；角色翻页节奏、遮罩声音和世界舞台的 show_frame 也没有一个共同的演出 Seam。

### Solution direction

让动作结果或演出阶段成为音频与视觉共同消费的节拍来源。BGM、ambient、foley、stinger 与动画不应各自从局部点击事件推断时机。

### Leverage / Locality / Test surface

- **Leverage**：开门、翻页、拖拽、落定、骰子和角色语音共享节拍。
- **Locality**：素材选择、抢占、延迟与错误回退集中维护。
- **Test surface**：可检查某一演出阶段是否触发正确音频，以及语音与 stinger 是否互斥。

- `apps/web/src/components/canvas/SceneBackdrop.tsx:38-67`

### Problem

`useStill` 能探测 `prefers-reduced-motion`，但粒子、视差、动态背景和 Effects 开关没有统一消费它。即使 effects 关闭，ParticleLayer 仍可能保留持续的 requestAnimationFrame；这一点尚未做设备级性能基准。

### Solution direction

统一“用户偏好、Effects 开关、页面可见性、演出强制播放”四种条件的优先级，并让所有装饰与演出 Adapter 通过同一状态语义决定是否运行。

### Leverage / Locality / Test surface

- **Leverage**：粒子、视差、视频和 CSS 动效共享一套开关规则。
- **Locality**：无障碍与性能策略集中维护。
- **Test surface**：可测试页面隐藏、系统偏好、Effects 开关和关键演出豁免。

## 14. 建议的挖掘顺序

你已经确认这些问题都值得挖掘。为了避免美学重构互相覆盖，建议顺序是：

1. **A01 视觉语法 Module**：先收敛颜色、材质、字体、交互态和响应式尺度。
2. **A02 舞台 Depth / 演出 Module**：再固定背景、实体、特写、前景、Chrome 的覆盖关系。
3. **A03 Chrome 与舞台状态 Locality**：明确入口、关闭、忙碌、Stop writing 和移动端排布。
4. **A06 门卡动作语义**：先恢复点击、双击、查看、行动和穿越的稳定语法。
5. **A05 Nook Adapter**：在舞台和动作语义稳定后统一层与 Nook 的投影。
6. **A07/A08/A09**：把事实确认、帧归属、音频与视觉节拍接到同一条演出路径。
7. **A04/A10**：最后根据角色戏剧的产品权重与真实性能数据决定是否深入。

这个顺序不是缩减范围，而是减少重复施工：如果先改角色遮罩或 Nook，之后的视觉 token、Depth 和 Chrome 统一很可能再次改写它们。
## 15. 与 `docs/components/`、`docs/layout/` 的对照

### 15.1 总结：互补为主，没有直接契约冲突

本次对照结论是：两个批次与本审查**互补为主**。它们已经解决或正在解决部分底层问题，但没有覆盖 A02、A03、A05、A06 的完整舞台与交互语义，因此不能把它们当成 UI/UX 总重构的替代品。

| 审查问题 | `docs/components/` 覆盖 | `docs/layout/` 覆盖 | 结论 |
|---|---|---|---|
| A01 视觉 token 与材质分裂 | **直接覆盖**：`appearance`、唯一 registry/resolver、Chalk `surface:none`、verified token、reduced motion、footprint 不变 | 不覆盖 | 互补；components 是 A01 的主要实现前置，但只处理实体外观，不自动收敛全局 Chrome / 场景壳 token |
| A02 舞台 Depth / z-index | 明确不覆盖；`appearance-view` 不拥有 shell z-index/transform | 只处理座位几何与 phantom，不定义 stacking depth | 无冲突；必须独立建立演出 Depth Module |
| A03 Chrome 与舞台状态 | 不覆盖 Chrome 状态、writer busy、Stop writing、移动端布局 | 只把 `attention` 与 Chalk drag permission 分开，间接提供状态边界 | 互补但不完整；layout 已阻止错误复用 `attention`，A03 仍需单独处理 |
| A04 角色 Theatre | 只规定 portrait/token/reduced-motion 不改对话语义 | 不覆盖角色对话 | 互补；appearance 能成为 Theatre 的视觉 Adapter，但不解决页推进、TTS、帧归属和空 portrait slot |
| A05 Nook 连续舞台 | `/api/nook` item 可携带同一 `AppearanceResolution` | 只覆盖 Nook 的 seat/flow/phantom 接缝，不拥有相机与完整互动 | 互补但有明确 Seam 缺口；Nook Adapter 仍需独立设计 |
| A06 门卡动作语义 | 04 保持 gate/PropCard callbacks 不变，未修正现有冲突 | 明确不改 gate 语义，只保护 Chalk drag lock | 无冲突，但不能宣称已解决单击/双击与查看/进入冲突 |
| A07/A08/A09 | appearance 只规定外观不改变动作、事件、WS；没有事实确认/帧归属/音频节拍方案 | phantom 过户、唯一 WS、失败可见与座位同源有覆盖 | 部分互补；仍需各自的动作结果、帧归属与声画节拍 Module |

### 15.2 components 批次已经解决的部分

`docs/components/00-05` 对 A01 的方向是正确且必要的：

- `00 §4-§5` 把实例外观收进唯一 `appearance` namespace，并明确 Chalk 默认 `surface:none`；
- `02 §2` 把世界/层 `material`、`bgStyle` 与实例外观隔离，避免背景加载状态直接冒充卡片视觉状态；
- `04 §3` 规定唯一的 ID → CSS token Adapter，且不改 `CARD_FORMS`、尺寸、旋转、点击后果和互动字段；
- `04 §7-§12` 已覆盖 CardRenderer、Chalk、letter、阅读层、响应式和 Reduced motion 的消费纪律；
- `05` 提供了旧 Chalk / letter 的兼容、迁移、截图与非空性验收。

但它不能单独消除本审查中观察到的全部视觉冲突。浏览器截图中的紫色 Chrome、暖纸面、背景暮色和整体 v2 墨画布属于全局舞台语法，不是某个实体的 `appearance`。因此 A01 仍需要在 `appearance` 之上明确全局 visual grammar；不能实现 appearance registry 后就宣布视觉系统已经统一。

### 15.3 layout 批次已经解决的部分

`docs/layout/00-05` 对 A02 的“空间几何”部分和 A03 的一个状态泄漏点是正确补强：

- `flowColumns` 统一服务端新卡、幻影和 footprint 纠偏的座位几何；
- 真实 `cards.width/height`、旧卡不动、同批顺序、右侧障碍扫描与并发事务被明确分开；
- phantom 座位过户不重排，真实 `/layer` 坐标优先；
- `03` 明确 `attention === 'authoring'` 不能作为 Chalk 解锁条件，God Hand 必须拥有独立 `isGodHandOpen/allowChalkDrag` 语义；
- `05` 把几何断言、服务端集成和浏览器截图验收分开，符合“几何绿不等于画面绿”的原则。

这些设计不能解决舞台 Depth：`flowColumns` 输出的是 x/y/w/h placement，不是 z-index、spotlight、PerformanceLayer、dialogue overlay 或 Chrome 的 stacking 语义。它也不能解决 Nook 的相机记忆、active projection、完整互动 parity 或全局 `.object` 测量范围。

### 15.4 需要防止的误接线

1. **不要把 appearance registry 当全局视觉 shell。** 它是实例外观的验证与 token Adapter；全局 `prototype.css` / `scene-shell.css` / `index.css` 的重复视觉来源仍需 A01 单独收敛。
2. **不要把 flowColumns 当舞台排版总管。** 它只负责自动座位几何；不要让 Canvas framing、pointermove、Depth Module 或 Nook 相机调用它来解释视觉层级。
3. **不要用 `attention` 解锁 Chalk。** layout 已明确要求独立 God Hand 状态；Writer action、全局 Enter 和 God Hand 不能共享同一个权限含义。
4. **不要把 Nook 的复用 Canvas 误认为 Nook 互动已完整。** `docs/components/04` 已准备完整 view callback 形状，但 `NookView` 当前仍未传入全部实体行动回调；这需要 A05 独立对齐。
5. **不要把 gate 语义“保持不变”当成 gate 已修复。** components/layout 都刻意不改 gate 点击语义，所以 A06 当前的单击直达、Enter 重复入口和查看/行动混淆仍然存在。
6. **不要把 Reduced motion 只当 appearance.motion。** components 规定实体动效降级，A10 仍需覆盖全屏粒子、视频、视差和 Effects 开关的全局优先级。

### 15.5 应回写的批次接缝

- `docs/components/04-前端渲染与交互呈现.md`：实现时需把 `appearance-view` 与 A01 的全局 visual grammar 明确分层，避免出现第四张 token 表。
- `docs/components/04-前端渲染与交互呈现.md` 与 `docs/components/05-迁移兼容与验收.md`：保留 gate/PropCard/EntityInteractions 的现有 callbacks 只是兼容约束，不是 A06 的动作矩阵验收。
- `docs/layout/02-幻影与演出接线.md`、`docs/layout/04-生成批次与初始化接缝.md`：继续明确 Nook 只复用 seat/flow/phantom 接缝，不拥有相机和完整互动。
