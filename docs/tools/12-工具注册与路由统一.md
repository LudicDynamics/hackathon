## 1. 一句话与定位

**把 15 个工具、8 条玩家路由、1 张帧映射表、1 个尾部读表循环接到同一根轴上：扩展与 server 各自 `new` 一个 `WorldStore`，动作语义在 `packages/shared/src/actions/` 只存在一次，server 只做"包一层 HTTP / 包一层 WS"。**

五件事各归一处，不许互相渗透：

| # | 接线 | 文件 | 一句话 |
|---|---|---|---|
| 1 | **工具注册** | `extensions/tools.ts`（新建） | 唯一 `registerTool` 入口；实现从 `./toolkit/*.ts`（子目录，不被当扩展加载）import |
| 2 | **身份** | `engine/launch.ts` + `engine/presets.ts` | `AIRP_AGENT_ROLE=writer` / `character:<id>` 经 `airpEnv()` 注入 agent 进程 env |
| 3 | **玩家路由** | `routes/world.ts` | 每条路由 = 校验形状 → `createActionService` → `ActionError.toHttp()`；**不另写一套规则** |
| 4 | **事件到前端** | `engine/event-bridge.ts` + `index.ts` | 引擎事件 → 演出帧（纯映射）；`events` 表 → `world_event`（尾部读表）；WS 命令只做"HTTP 做不到的通道" |

**三条定位**：

1. **本文是"包壳层"，不含任何业务判断。** 路由里出现的每一个决定（骰子怎么掷、choice 是否还有效、`near` 在哪层）都在 01–11 的动作函数里已经定完。本文只决定：请求体长什么样、actor 是谁、`turn` 锚怎么给、失败怎么变 HTTP、成功怎么变帧。
2. **帧名与事件 `type` 不共用一个命名空间**（00 §5.3 / `doc-21:276`）。演出帧是瞬时传输（`writer_delta` / `chalk_landed` / `dice_result` / `canvas_patched` / `show_frame`）；世界事件一律 `{ type: 'world_event', event }`。前端靠这个分"这是演出还是历史"。
3. **`fs.watch` 永不写事件表**（`doc-21 §2.1`）。它只做两件事：广播 `file_changed`（前端重取的触发器）+ **踢一次尾部读表**。事件表只由 agent 进程里的动作函数写，server 只读。

### 2.1 `extensions/tools.ts` 的装配契约（本文冻结）

```ts
// extensions/tools.ts —— 唯一 registerTool 入口（extensionArgs 只扫顶层 *.ts，00 §6.1）
import type { ExtensionAPI, ToolDefinition } from '@earendil-works/pi-coding-agent';

export default function registerAirpTools(pi: ExtensionAPI): void;
```

**冻结三条**：

1. **`toolkit/*.ts` 一律导出 `ToolDefinition` 常量**（`export const chalkTool: ToolDefinition = { … }`），`tools.ts` 只 import + 循环 `pi.registerTool(tool)`。**不允许** `toolkit/*.ts` 自己调 `pi.registerTool`——注册入口必须唯一，否则评审无法一眼列出工具面（`00 §6.1` 明文）。
   > **与 02/04 文档的偏差**：`02-chalk.md §8.1/§8.2` 写的是 `registerChalkTool(pi, store, actor)`（注册函数）；`04-*` 写的是 toolkit 内直接 `pi.registerTool(...)`；`10-*`/`11-*` 写的是导出 `ToolDefinition` 常量。三种写法互斥，**本文按第三种收口**（理由见 §11 冲突 1）。
2. **依赖不进注册形参**：`toolkit/*.ts` 不需要 `store` / `actor` 参数。`ExtensionContext.cwd` 就是世界根（`launch.ts` 保证，00 §1），`AIRP_AGENT_ROLE` 在 `process.env` 里（00 §3）。二者由 `toolkit/deps.ts` 在**首次 execute 时惰性解析并缓存**（§8.2）。
3. **工具面可枚举**：`tools.ts` 维护一个 `AIRP_TOOLS` 常量数组（`{ name, tool }`），既是注册源也是探针的断言源（§10）。

### 2.3 `AIRP_AGENT_ROLE`：`airpEnv()` 的改法（00 §3 要求"定改法"）

**现状**（`presets.ts:54-56`）：

```ts
export function airpEnv(): NodeJS.ProcessEnv {
  return { PI_PROJECT_CONFIG_DIR: AIRP_CONFIG_DIR };
}
```

它不接参数，两个 spawn 点（`launch.ts:88` / `:126`）都直接 `airpEnv()`。**改法：扩成"白名单透传 + 显式注入"**，无参调用仍是今天的语义：

```ts
/** 需要从 server 进程透传进 agent 进程的 env（11 §11 冲突 8）。 */
const AIRP_ENV_PASSTHROUGH = [
  'OPENROUTER_API_KEY',
  'AIRP_IMAGE_MODEL',
  'AIRP_IMAGE_TIMEOUT_MS',
  'AIRP_IMAGE_LIBRARY_DIR',
] as const;

export interface AirpEnvOptions {
  /** 00 §3：agent 的唯一身份差。writer | character:<id>。省略 = 不注入。 */
  role?: string;
  /** 逐 spawn 追加（如探针的 PI_OFFLINE）。undefined 值由 launch.ts 的 toEnv 丢弃。 */
  extra?: Record<string, string | undefined>;
}

export function airpEnv(opts: AirpEnvOptions = {}): NodeJS.ProcessEnv;
```

**实现要点**：

- 白名单命中才透传（`process.env[k] !== undefined`）——**不做 `...process.env` 全量转发**：那会把开发机的 `PATH`/`HOME`/代理变量无差别搬进 agent 进程，且让"agent 看到什么"不可审计；
- `role` 只在显式给值时写 `AIRP_AGENT_ROLE`（**不写空串**：00 §3 的降级表把 `''` 与 `undefined` 都归"未设置"但 warn 文案不同）；
- `extra` 覆盖同名 key（后写赢），供探针 `PI_OFFLINE=1` 这类逐次注入。

**两个 spawn 点的注入**（`launch.ts`）：

| 函数 | 行 | `env:` 表达式 |
|---|---|---|
| `writerLaunch` | `:88` | `toEnv(airpEnv({ role: 'writer' }), agentDirEnv(repoRoot), { PI_CODING_AGENT_SESSION_DIR: sessionsDir })` |
| `characterLaunch` | `:126` | `toEnv(airpEnv({ role: `${CHARACTER_ROLE_PREFIX}${characterId}` }), agentDirEnv(repoRoot), { PI_CODING_AGENT_SESSION_DIR: sessionsDir })` |

**常量只有一个实现**：角色 role 的拼法用 `packages/shared/src/actions/actor.ts` 导出的 `CHARACTER_ROLE_PREFIX = 'character:'`（01 §2.3），`launch.ts` 必须 import 它拼，不许再写字面量——否则前缀改一次要找两处。

**为什么是 `airpEnv()` 而不是别的注入点**：`00 §3` 已冻结它是唯一注入点；pi-rp 没有"我是谁"的扩展 API（`ExtensionContext` 只有 `sessionManager` / `ui` / `mode` / `cwd` / `settings` / `model`，`types.ts:315-415`，无 role 字段）。子代理（`spawnAgent` / `subagent`）与父进程同进程、**继承同一份 env**，所以 `scene-init` 子代理看到的 role 仍是 `writer`——这是 00 §3 已接受的边界（01 §14 未知 6 同此口径）。

**探针侧的验证**（§10）：`tools/probe-writer.mjs` 现在通过 `spec.env` 构造 RpcClient；改 `airpEnv` 后它自动拿到 role。**新增一条断言**：探针读 agent 进程 stderr，**不许**出现 `AIRP_AGENT_ROLE is not set`（它是 `resolveAgentActor` 的 warn 文案，说明注入断了）。

### 2.4 HTTP 路由总表（新形状）

`createWorldRouter(repoRoot, lifecycle, eventBridge, getActiveStore, setActiveStore)` 的**形参不变**（`routes/world.ts:58-64`）。改的是每条路由的体。

**统一包装**（每个动作路由都用它，不许各写各的）：

```ts
// routes/world.ts 顶部
import { randomUUID } from 'node:crypto';
import { ActionError, createActionService, type Actor } from '@airp/shared';

/** 一次 HTTP 请求 = 一个 turn 锚（01 §3.7 的 C 入口）。 */
function serviceFor(store: LocalWorldStore, actor: Actor) {
  return createActionService(store, actor, { turn: `req:${randomUUID()}` });
}

/** ActionError → HTTP；其它异常 → 500。响应恒为 { ok:true, ...details } 或 { ok:false, code, error }。 */
async function reply(res: Response, run: () => Promise<{ details: Record<string, any> }>): Promise<void> {
  try {
    res.json({ ok: true, ...(await run()).details });
  } catch (err) {
    if (err instanceof ActionError) {
      const http = err.toHttp();
      res.status(http.status).json(http.body);
      return;
    }
    res.status(500).json({ ok: false, code: 'internal', error: err instanceof Error ? err.message : String(err) });
  }
}
```

**`turn` 锚用 `randomUUID()` 而不是递增计数**：两侧进程各自递增会撞号；请求 id 只需唯一与稳定，不需有序（01 §3.7）。

#### 2.4.1 god-action 的 `action` 映射与 `createEntity`（本文冻结形状）

| action | 动作方法 | 说明 |
|---|---|---|
| `create` | `createEntity({ path, body, frontmatter? })` | **已按 REVIEW 裁决：`01 §5` 第 23 行增补 `createEntity`**（文件 `create.ts`，§11 冲突 2），形状见下 |

```ts
// packages/shared/src/actions/create.ts（01 §2.1/§5 已定为 create.ts；函数名冻结）
export interface CreateEntityInput {
  /** 世界根相对路径（00 §2.1）。MUST 是 *.md，MUST NOT 是 README.md（层门牌不是实体）。 */
  path: string;
  /** 正文（不含 frontmatter 定界符）。给了 `content` 时忽略本字段。 */
  body?: string;
  /** 浅合并进 frontmatter；拼装用 02 冻结的 `stringifyFrontmatter`。 */
  frontmatter?: Record<string, any>;
  /** 逃生舱：整份文件原样写盘（忽略 body/frontmatter，frontmatter 靠调用者保证）。上帝"整份替换"用。 */
  content?: string;
}
export interface CreateEntityDetails {
  path: string;
  name: string;                 // frontmatter.title ?? 文件名 slug
  kind: 'chalk' | 'component' | 'note' | 'letter' | 'other';   // 00 §5.2 的封闭枚举
  event: WorldEvent;            // entity_created
}
export async function createEntity(
  ctx: ActionContext, input: CreateEntityInput
): Promise<ActionResult<CreateEntityDetails>>;
```

行为（五步骨架，同 01 §3.1）：

1. **路径校验**：非绝对、非 `README.md`、落在 `world/` `player/` `characters/<id>/` 之下，否则 `invalid_path`；目标已存在 → `already_exists`（**显式路径不许静默覆盖**，与 `00 §2.3` 的 chalk 命名纪律同一条原则）。
2. **定 `name` 与 `kind`**：`name = frontmatter.title ?? 文件名 slug`；`kind` 用一个**从 04 导出**的共享映射 `eventKindOf(fm, filename)`——它的输出是 00 §5.2 的**封闭五值枚举**，与 `cardKindOf`（返回 `chalk/gate/letter/note/sprite/default`，`forms.ts:44-55`）**不是同一个集合**（§11 冲突 3）。
3. **落盘**：`writeFile(path, content ?? stringifyFrontmatter(fm, body ?? ''))`。**新建文件不需要原子写**（01 §3.1 第 3 步：只有改写既有文件才 MUST `writeFileAtomic`）。文件已存在走第 1 步的 `already_exists`，所以这里不会覆盖。
4. **落账**：`appendEvent({ type:'entity_created', actor: ctx.actor, detail: { path, name, kind }, subject: path, layer: await store.resolveLayer(path), turn: ctx.turn })`。**恰一条事件**（`doc-21 §4.1`）。
5. **返回英文 `text`**：`Created "The Old Mill" (world/baker-street/the-old-mill.md).`（`00 §6.2`：说明实际发生了什么 + 带稳定路径）。

**失败不落事件**（`doc-21 §3.6`）。

**为什么不用 `writeChalk` 顶替**：`chalk` 工具**自己造** `type: chalk` 骨架并按 `NN-slug.md` 命名（02 §2 的契约），而 god 的径向菜单要建 gate / sprite / note / chalk 四类，且 frontmatter 由调用者给（`App.tsx:233-256` 今天就拼四种骨架）。让 `writeChalk` 再长出一个 `frontmatter` 重载会模糊它的契约（"写板书"变成"写任何东西"）。

**为什么请求体从 `content: string` 改成结构化的 `{ frontmatter?, body? }`**：现状把 frontmatter 语法（引号转义、类型推断）交给前端字符串拼接——这正是 `doc-07` 风险表"frontmatter 格式错"的来源。结构化后拼装由 02 冻结的 `stringifyFrontmatter` 负责，前端只交数据。**`content` 作为逃生舱保留**（`{ path, content }` 时原样写盘，frontmatter 靠调用者保证）——给"整份文件替换"这种上帝改写用。


### 2.5 WS 命令总表（`index.ts:75-148`）

## 3. 行为契约（逐步）

### 3.1 扩展加载（agent 进程启动时，一次）

1. **`extensionArgs` 收集顶层文件**：`presets.ts:91-116` 读 `extensions/` 与 `<worldRoot>/extensions/` 的**直接子项**，只收 `.ts`/`.js`（排除 `.d.ts` / `.test.ts` / `.spec.ts`），每个拼一个 `--extension <abs-path>`。`toolkit/` 是目录、不在这一层，**因此不会被当扩展加载**——这正是 `00 §6.1` 把它放子目录的理由。
   *漏了会怎样*：若把工具实现写成 `extensions/chalk.ts` 顶层文件，它会被当**扩展工厂**加载，而它导出的是 `ToolDefinition` 常量（不是函数），jiti 的 `module as ExtensionFactory` 判 `typeof !== 'function'`（`loader.ts:511-515`）→ 该文件静默不生效。
2. **jiti 加载**：每条路径一个 `jiti.import(path, { default: true })`（`loader.ts:503-512`），`moduleCache: false`。`tools.ts` 的 default export 被执行 → 逐个 `pi.registerTool(...)`。
   *漏了会怎样*：`tools.ts` 忘了 `export default` 或导出的是具名函数 → 同上，静默不注册，**没有任何报错**。这是本层最容易踩的坑：`pnpm probe` 的 `presetWarnings` 只查 `not found` / `unknown slot`（`probe-writer.mjs:19-25`），查不出"工具没注册"——所以 §10 加了工具面断言。
3. **`toolkit/*.ts` 的 import 解析**：相对路径 `../../packages/shared/dist/index.js`（从 `extensions/toolkit/` 上两级到仓库根）。
   *漏了会怎样*：写成包名 `@airp/shared` 会解析失败——`extensions/` 不在 pnpm workspace 里（`pnpm-workspace.yaml` 只有 `packages/*` 与 `apps/*`），loader 的 alias 表（`loader.ts:87-135`）也不含它。**已实测**：jiti 能解析 `extensions/toolkit/*.ts` 里的 `../../packages/shared/dist/index.js`（本次设计期用 `jiti-static` 在等价目录布局上验证通过）。
4. **`typebox` 的 import 解析**：`import { Type } from 'typebox'` —— loader 的 alias 把它指到 workspace 里的 `typebox`（`loader.ts:93` + `:128`）。
   *漏了会怎样*：用 `@sinclair/typebox` 也行（同一 alias），但**不要**用 `zod` 定义 `parameters`：pi-rp 的 `ToolDefinition.parameters` 是 `TSchema`（typebox），zod schema 会被 schema 校验拒掉。

### 3.2 一次工具调用（agent 进程内）

以 `chalk` 为例（其余同构）：

1. **模型发 `tool_call`** → pi-rp 校验 `parameters` → 调 `definition.execute(toolCallId, params, signal, onUpdate, ctx)`。
2. **`ctx.cwd` 就是世界根**（`launch.ts` 保证 `cwd: worldRoot`，`:86`/`:115`）。`toolkit/deps.ts` 据此构造（或复用缓存的）`new LocalWorldStore(ctx.cwd)`。
   *漏了会怎样*：用 `process.cwd()` 也能对（spawn 时 cwd = worldRoot），但 `00 §1` 明写"仍优先用 `ctx.cwd`"——`process.cwd()` 在将来被 `--cwd` 或子代理改掉时会静默指向错的目录。
3. **`actor` 从 env 解析**：`resolveAgentActor(process.env.AIRP_AGENT_ROLE)`（01 §2.3 的降级表）。`warning` 非 null 时 `process.stderr.write` **一次**（模块级 `warnedOnce`）。
   *漏了会怎样*：不 warn 的话，env 注入断掉会表现为"所有事件都记成 writer"——角色改的世界被算在作家头上，注入给作家的"世界动态"会说错主语。
4. **`turn` 锚**：`currentTurnAnchor(ctx)`，形如 `turn:<sessionId>:<turnIndex>`（01 §3.7）。它来自 `toolkit/turn.ts` 的 `pi.on('turn_start', …)` 监听。
   *漏了会怎样*：没有 `turn` 的事件无法参与合并（`doc-21 §5.4` 第 1 条），注入时每篇 chalk 各占一行——作家写 3 篇就念 3 行。
5. **调动作服务**：`const r = await getActionService(ctx).writeChalk({ … })`。
6. **失败映射**：`catch (err) { if (err instanceof ActionError) return err.toToolResult(); throw err; }`。
   *漏了会怎样*：让 `ActionError` 冒泡出 execute → pi-rp 的 tool 执行器捕获后造一个**通用**错误结果（`agent-loop.ts:757-763` 的 `createErrorToolResult`），`details` 全丢。模型只看到一句泛泛的报错，看不到"哪个路径错了"。
7. **成功返回**：`{ content: [{ type:'text', text: r.text }], details: r.details }`。
   *漏了会怎样*：丢掉 `details` 会让 server 侧三条映射（`chalk_landed` 的路径、`show_frame`、`dice_result`）拿不到数据——它们全从 `event.result.details` 读。

### 3.3 一次玩家 HTTP 动作（server 进程内）

以 `POST /dice` 为例：

1. **取活跃 store**：`const store = getActiveStore(); if (!store) return 400 {error:'No active world'}`。**保持现状的形状**（`:345-346`）——不要改成 500，前端把它当"没开世界"处理。
2. **形状校验**：只校验"字段在不在、类型对不对"（`path` 是非空字符串、`forcedResult` 若在则 `Number.isFinite`）。**语义校验一行都不写**——文件存不存在、骰子有没有 `result`、`expect` 能不能解析，全在动作层（`rollDice` 抛 `not_found` / `dice_already_rolled` / `malformed_entity`）。
   *漏了会怎样*：路由自己做语义校验 = 第二套规则，与 agent 工具的行为必然分叉（`00 §8` 反模式第 1 条：05 已在 `/dice` 上踩过——路由自己解析 expect，与 07 的裁决函数不一致）。
3. **actor 判定**：`const actor = typeof body.forcedResult === 'number' ? { type:'god' } : { type:'player' };`
   *漏了会怎样*：若把上帝模式的普通点击也记 `god`，`doc-21 §4.3` 用来区分"伪造结果"的 `actor_type = god` 就死了（07 的 IRC 回执第 2 条）。
4. **调用 + 映射**：`await reply(res, () => serviceFor(store, actor).rollDice({ path: body.path, forcedResult: body.forcedResult }))`（§2.4 的 `reply`）。
5. **不广播帧**：HTTP 路径**不发演出帧**。玩家侧的骰子演出由前端消费 HTTP 响应驱动（`DiceRoller.tsx:148-165` 现在就是这么做的）；`dice_result` 帧是**工具路径专属**（§3.6）。
   *漏了会怎样*：两条路径都发帧 → 同一次掷骰演出两遍（HTTP 响应一遍、帧一遍），且前端无从去重（帧不带 request id）。
6. **不落 prompt**：**绝不**在这里 `writer.prompt(...)` / `followUp(...)`（`doc-05 §5.1`、`doc-21 §5.5`、计划 §7 T4.2）。
   *漏了会怎样*：玩家掷一次骰子作家立刻自说自话起一轮，玩家再打字又起一轮，两轮叙事互相抢戏（T4.2 原文）。B0 已删掉这三处，**B1 的改造 MUST 保证不重新引入**（`00 §10` 第 3 条）。

2. **`details.frame` 缺失时只 `console.warn`，绝不伪造一个空演出**（10 §6.2 的兜底纪律）。宁可什么都不演，也不要演错的。

#### 3.4.1 `chalk_landed` 路径取值的修法（02 的唯一请求）

```ts
// event-bridge.ts，tool_execution_end 分支内（替换 :83-84）
const r = (event.result ?? null) as Record<string, any> | null;
const resultPath: string | undefined =
  (typeof r?.path === 'string' ? r.path : undefined) ??
  (typeof r?.details?.path === 'string' ? r.details.path : undefined);
```

**为什么两个都读**：工具的 `details` 形状由各 `NN-*` 定，多数把 `path` 放在 `details` 里（`02 §6.2` 的 `WriteChalkDetails.path`）；顶层 `path` 只有历史形状才有。两个都读 = 兼容且零成本。

### 3.5 收遮罩 → `character_talked`（`index.ts` 的 `character_stop` 分支）

```
收到 { type:'character_stop', characterId, turns? }
  → const store = activeStore; if (!store) 直接 stopCharacter（不能因为没世界就不回收进程）
  → turn = `req:${randomUUID()}`
  → await noteCharacterTalked(store, { character: characterId, turns: turns ?? 1, turnsEstimated: turns === undefined }, actor=player, turn)
       成功 → 落 character_talked（actor=player, subject=characters/<id>/README.md, layer=null）
       失败（ActionError）→ console.warn，不阻断
  → await lifecycle.stopCharacter(characterId)
```

**顺序是先落账再收进程**：反过来的话，`stopCharacter` 把连接关掉后就没人能读角色 README 拿 `name` 了（动作层要读它填 `detail.name`，`doc-21 §3.3` 的 `detail` 自足要求）。

**失败不阻断回收**：落账失败只 `console.warn`——进程泄漏比少一条事件严重得多。这是本节唯一允许"失败静默"的地方，且**有可见输出**（stderr warn），不算静默降级。
**`turns` 缺省 `1` 且 `turnsEstimated: true`**：`noteCharacterTalked` 的 schema 要求 `turns >= 1`（`01 §2.5` 的 `character_talked` detail），0 会被拒。前端不传时兜 1，并传 `turnsEstimated: true`，由动作层回显进 `details`（M-8：前端计数器落地前的诚实降级，不许假装这个数是实测的）。

#### 3.5.1 三个入口的类型形状（实现期补齐，01 §5 只列签名未给定义）

> 实现期发现：`01 §5` 的方法表**引用了** `EnterLayerInput` / `NoteCharacterTalkedInput` / `RecordLayerInitializedInput` / `RecordLayerInitFailedInput` 等类型，但**没有任何文档给出它们的定义**（各工具文档按工具切、都不认领这三个 C/E 入口）。形状在实现期冻结如下，且已落地（`packages/shared/src/actions/layer.ts` / `talk.ts`）。

```ts
// actions/layer.ts
export interface EnterLayerInput { layer: string }              // 层 id == 目录（world/ 的 id 是 'map'）
export interface EnterLayerDetails {
  layer: string;
  name: string;      // 层 README 的 name；stub 层（无 README）回落目录名
  first: boolean;    // true = 该层此前是 stub（无 README），这是它的第一次亮相（doc-21 §4.4）
  event: WorldEvent; // layer_entered，actor=player
}

export interface RecordLayerInitializedInput {
  layer: string;
  by: 'writer' | 'player' | 'engine';
  files: string[];   // 初始化器落下的文件（世界根相对）
```

### 3.6 尾部读表（server 进程内，本任务重点）

**目的**：把 agent 进程里 `appendEvent` 写进 `history.db` 的每一行，推到所有 WS 客户端。扩展不能直连 WS（`00 §1` 硬约束），所以 server 必须**读表**。

**触发源三处**（三者共用同一个 `drain()`，天然幂等）：

1. **`fs.watch` 回调**（世界目录任意变化，含 `history.db-wal`）——最及时；
2. **~1s 兜底定时器**——WSL 下递归 watch 对大目录不可靠（计划 §7 T4.3 已登记），且 `fs.watch` 的 debounce（150ms）可能把"写事件表"和"写 md"两次变化合并成一次回调；
3. **`/api/worlds/load` 切换世界后**——新 worldRoot 的 `lastSeq` 要对齐新库的 `getMaxSeq()`（否则会把上一个世界的事件号当基准）。

**并发纪律**：`drain()` 用**一个 in-flight promise** 串行化（`if (this.draining) return this.draining`）。理由：watch 回调可能在上一次 `getEventsSince` 还没 resolve 时又进来一次，两次并发读会各自拿到 `[n+1..n+k]` 与 `[n+1..n+k]`（读不动游标直到 broadcast 完），前端收到重复；串行化后第二次读从新游标开始。**这是本层唯一的竞态点**，必须显式处理。

**跨世界切换的失效**（REVIEW m-24）：`drain()` 的读是异步的，期间 `/api/worlds/load` 可能换掉 `tailStore`。旧 drain 若在 resolve 后照常写 `lastSeq` 并 `broadcast`，就会把**上一个世界**的事件推到新世界的客户端，并把游标写成新库不该有的值。**修法**：`EventBridge` 加一个 `tailEpoch`（每次 `startTailReader` / `stopTailReader` 都 +1），`drain()` 在 `await` **之前**捕获 `epoch` 与 `store`；`await` 回来后先核对 `epoch === this.tailEpoch && store === this.tailStore`，不等则**整批丢弃**（既不推进 `lastSeq` 也不 `broadcast`）。骨架见 §8.6。

**游标语义**：

- `lastSeq` **先推进再广播**（`this.lastSeq = last.seq` 后才 `broadcast`）。反过来的话，一次 broadcast 抛异常（客户端断开）会让游标停在原处，下次重读同一批 → 重复推。
- `getEventsSince(lastSeq)` 返回**正序**（`01 §3.3`），story 顺序即 `seq` 顺序，逐条 `broadcast` 无需排序。
- **只推进到"这一批的最后一条"**，不无条件设成 `getMaxSeq()`：读表期间 agent 可能又写了几条（`seq > last`），把它们留给下一轮——否则会跳过。

**`appendEvent` 必须已 COMMIT 才返回**（`01 §3.8` 的 store 侧保证）：`appendEvent` 在 `BEGIN IMMEDIATE` 事务里 INSERT + UPDATE `id`，COMMIT 后才 return。所以 server 读到的 `seq` 一定单调；读不到只是 debounce 没到，兜底定时器会补。**若 `appendEvent` 在 COMMIT 前返回**，server 可能读到 `seq=n` 却没读到还在另一连接事务里的 `seq=n-1`，游标就会跳过它——这是该契约存在的理由。

**`.airpworld` 过滤**（本任务点名要修的 bug，`event-bridge.ts:138`）：

```ts
// `.airpworld` is not one semantic namespace: history.db must wake the tail
// reader, while canvas.db is current layout state with its own explicit frames.
const rel = filename.split(path.sep).join('/');
const ignored =
  rel === '.airpworld/canvas.db' ||
  rel === '.airpworld/canvas.db-wal' ||
  rel === '.airpworld/canvas.db-shm' ||
  rel.startsWith('.airpworld/assets/') ||
  rel.startsWith('.airpworld/sessions/') ||
  rel.startsWith('node_modules/') ||
  rel.includes('/node_modules/');
if (ignored) return; // still kick the history tail reader before this guard
```

**为什么恰好滤这些**：

- `.airpworld/assets/` —— 生成图片写入时会有多次 fs 事件（`.tmp-*` + rename）。前端不需要为它整层重取（图是 `bg` 字段，README 改了才重取）。**但 `image_landed` 帧已经通知了前端**，所以滤掉它不丢信息。
- `.airpworld/sessions/` —— agent 会话 jsonl 每轮都在追加，**每次写都触发一次 `file_changed` + 一次读表**（读表会返回空，白跑）。世界目录会话文件随轮次线性增长，这是最吵的一个源。
- `.airpworld/canvas.db*` —— 画布状态的坐标、尺寸、线条和在场位置分别由 `card_position`、`canvas_patched`、`world_event` 或 reconnect fetch 覆盖。把 SQLite WAL 当成内容变化会让一次 footprint 写入产生额外的整层重取和重复 reseat，表现为卡片闪动；tail reader 仍在 watcher guard 之前被唤醒，因此不丢历史事件。
- `.airpworld/` 下的其余文件（尤其 `history.db` / `prompt-presets/`）必须放行；`history.db` 是尾部读表的触发源。

**`node_modules` 的第二条判据**：世界目录里理论上不会有，但 `<worldRoot>/extensions/` 与模板可能带进来，用 `includes('/node_modules/')` 兜住嵌套。

**`timestamp` 有两层**：`event.createdAt` 是**落账时刻**（世界事实），外层 `timestamp` 是**广播时刻**（传输事实）。前端排序/去重一律用 `event.seq`（`01 §2.7`：`created_at` 是毫秒 ISO 串，同毫秒不稳定）；只看"什么时候到我这"用外层。

### 6.4 去重纪律（前端 MUST）

`details.event`（HTTP 响应/工具返回里的兜底）与 `world_event` 帧是**同一行的两份副本**（`01 §11.2`）。前端 MUST 按 `event.id` 去重，否则每条动作事件演两遍。

推荐实现：`useWorld` 维护一个 `seenEventIds: Set<string>`（上限 200、FIFO 淘汰，避免无界增长），`world_event` 与响应里的 `event` 都先过它。

### 6.5 `canvas_patched` 与 `card_position` 的分工（09 §6.3 的确认）

09 提出的问题："`/api/card/position` 改造后要不要同时发两种帧？" **本文的裁决：只发 `card_position`。**

理由：

- `canvas_patched` 的定义是"**工具路径**产生的画布状态变化"（`canvases` 的 `details` 需要 `kind`/`action`/`cards` 三个字段，那只有 `arrangeCards` 的 layout 形态才有）。
- `card_position` 是"**玩家拖拽**的逐卡写回"，前端已有乐观合并（`useWorld.ts` 的 `moveCard` 先改 state 再 POST，失败回滚）。它比 `canvas_patched` 携带的信息更少但更精确（永远是一张卡）。
- 同一次拖拽发两帧 → 前端同一张卡被合并两次（值相等，幂等，但白跑一次 render）。

**但 `/api/card/position` 内部确实走 `arrangeCards({ place })`**（09 §8.3）——那是"动作语义只有一份"的要求，与发什么帧无关。路由拿到 `details`（即 09 §6.1 的 `ArrangeDetails`：`{ kind:'cards', action, layer, cards, path? }`）后**自己构造 `card_position` 帧**（只带请求体里的 `path/x/y`，不依赖 `details` 的形状）：

```ts
await reply(res, () => serviceFor(store, { type: 'player' }).arrangeCards({ place: { path, x, y } }));
eventBridge.broadcast({ type: 'card_position', path, x, y });   // 放在 reply 之后？见下
```

**顺序**：`broadcast` 必须在**动作成功之后**。`reply` 内部 catch 了错误，所以路由无法在 `await reply(...)` 之后判断成功与否——**改为先 `try` 拿结果、再广播、再 `res.json`**：

```ts
router.post('/card/position', async (req, res) => {
  const store = getActiveStore();
  if (!store) return res.status(400).json({ error: 'No active world' });
  const { path: cardPath, x, y } = req.body as { path?: unknown; x?: unknown; y?: unknown };
  if (typeof cardPath !== 'string' || cardPath === '') return res.status(400).json({ ok: false, code: 'invalid_argument', error: 'path must be a non-empty string' });
  if (typeof x !== 'number' || !Number.isFinite(x) || typeof y !== 'number' || !Number.isFinite(y)) {
    return res.status(400).json({ ok: false, code: 'invalid_argument', error: 'x and y must be finite numbers' });
  }
  try {
    const r = await serviceFor(store, { type: 'player' }).arrangeCards({ place: { path: cardPath, x, y } });
    eventBridge.broadcast({ type: 'card_position', path: cardPath, x, y });
    res.json({ ok: true, ...r.details });
  } catch (err) {
    if (err instanceof ActionError) { const h = err.toHttp(); return res.status(h.status).json(h.body); }
    res.status(500).json({ ok: false, code: 'internal', error: err instanceof Error ? err.message : String(err) });
  }
});
```

**`/card/position` 不再自己做"文件必须存在"的检查**（现状 `:327-331`）——`arrangeCards` 的 `place` 形态会 `readFile` 并抛 `not_found`（09 §2.6 的契约），路由重复一遍就是第二套规则。**401/404 的形状由 `ActionError.toHttp()` 决定**（`not_found` → 404），与现状的 `{ error: 'File not found: …' }` 不同——前端 `useWorld.moveCard` 只看 `res.ok`（`:138`），所以行为兼容。

### 6.6 `airp:world-event` 自定义事件（前端内部契约）

`useWorld.ts` 的 WS `onmessage` 把 `file_changed` / `card_position` 转发成 `window` 上的 `airp:world-event`（背包与角色视图监听它刷新）。改造后：

```ts
// 新的转发集合（帧名 + world_event 都进）
if (msg.type === 'file_changed' ||
    msg.type === 'card_position' ||                       // 画布位置落库
    (msg.type === 'world_event' && [
      'entity_created','entity_edited','entity_deleted','entity_moved',
    ].includes(msg.event?.type))) {
  window.dispatchEvent(new CustomEvent('airp:world-event', { detail: msg }));
}
```

**为什么要把这四个 `event.type` 挑出来转发**：背包视图（`RightSidebar`）只关心"`player/**` 的文件变了没"，而 `file_changed` 已经是它今天的信号源。`world_event` 里 `entity_*` 四类**总是**伴随文件变化，所以它们其实冗余——**加它们的唯一理由**是：`fs.watch` 的 debounce（150ms）与尾部读表（≤1s）之间有时序差，先到的那个负责刷新，避免背包视图等 1s。这属于**性能优化不是正确性要求**，若前端觉得噪音大可以只留 `file_changed`。**登记为前端可选项。**

`canvas_patched` **不转发**（09 §6.4 已定）：画布状态变化不影响背包清单（背包是目录扫描）。

## 7. 错误与边界

### 7.1 HTTP 错误映射（唯一实现是 `ActionError.toHttp()`，01 §7.1）

**本文不重复状态码表**：`ActionErrorCode → HTTP` 的唯一落点是 `01 §7.1` 的 `HTTP_STATUS`（REVIEW m-1/m-2 已统一：`no_free_seat` = **507**、`not_movable` = **409**）；本层所有错误响应都走 `ActionError.toHttp()`，**路由 MUST NOT 自己发明状态码**（例如 `/card/position` 现在对不存在的文件返回 404 `{error:'File not found: …'}`，改造后由 `not_found` 给 404、形状是 `{ok:false,code,error}`）。

本层路由会触发的 code（只列 code，状态码一律查 `01 §7.1`）：`invalid_argument`（`/dice` 缺 `path`；`/card/position` 的 `x` 非有限数）、`invalid_path`（`/move` 的 `to` 是绝对路径）、`not_found`（`/use-item` 的 `item` 不存在；`/card/position` 的卡不存在）、`already_exists`（`/god-action` create 一个已存在的路径）、`not_movable`（`/move` 的 `README.md`）、`not_interactive` / `choice_not_found`（`/choice`）、`dice_already_rolled` / `dice_forced_not_allowed`（`/dice`）、`near_out_of_layer`（`/move` 的 `near` 在别的层）、`no_free_seat`（排座失败）、`unsupported`（`/viewpoint` 的 B1 占位）、`write_failed` / `event_failed`（落盘或落账失败）；其它异常 500 `{ ok:false, code:'internal', error: msg }`。

### 7.2 边界

| 边界 | 处置 |
|---|---|
| **没开世界时任何动作路由** | 400 `{ error: 'No active world' }`（保持现状形状，前端认它） |
| **`activeStore` 刚被 `/worlds/load` 换掉，旧请求还在飞** | 不做锁。`getActiveStore()` 每次现取，旧 store 的 `close()` 会让它的 SQLite 语句抛错 → 500。**可接受**：切世界是用户显式动作，且前端会整层重取 |
| **`getActiveStore()` 返回的 store 已 close** | `worlds/load` 里 `current.close()`（`:96`）后立刻 `setActiveStore(store)`，中间无 await → 没有窗口。**但 `lifecycle.stopCharacters()` 是 await 的（`:93`）**，所以旧请求可能落在 close 之后。**修法**：把 `setActiveStore(store)` 提到 `stopCharacters` 之前，或给 `LocalWorldStore` 加 `isClosed` 标志（归 01）。**登记为已知边界** |
| **`character_stop` 一个未启动的角色** | `lifecycle.stopCharacter` 内部 `if (!client) return`（`lifecycle.ts:118`）；`noteCharacterTalked` 会因 README 不存在抛 `not_found` → warn 后继续。**不报错给前端**（这条命令的性质是"确保它停了"） |
| **`character_stop` 没带 `turns`** | 兜 `1` 并传 `turnsEstimated: true`（§3.5） |
| **`world_event` 广播时无 WS 客户端** | `broadcast` 遍历空集合，`lastSeq` **照常推进**（否则客户端重连后会收到几小时前的全部事件） |

| **`fs.watch` 报错（EMFILE / 目录被删）** | `watchWorld` 已 try/catch（`:150-152`）只 warn。**兜底定时器必须独立于 watcher 存活**（它是"watcher 挂了也要读表"的保险） |
| **`history.db` 被 lock（busy_timeout 5000 用尽）** | `getEventsSince` 抛错 → `drain()` catch → warn → **不推进游标** → 下次重试。**绝不 catch 后静默推进**（会永久丢事件） |
| **`getMaxSeq()` 在启动时抛错（库文件刚建、表还没有）** | `LocalWorldStore` 构造时已经 `initHistoryDatabase`（`local-store.ts:57-58`），所以表一定在。抛错则 `lastSeq = 0` 并 warn——代价是首次启动会回放全部历史，**可见且可修** |
| **同一条 `world_event` 被推两次**（串行化漏了） | 前端按 `event.id` 去重（§6.4）。**后端也应靠 `draining` 串行化兜住**（§3.6） |
| **`filename` 为 undefined** | 现状 `if (!filename) return`（`:137`）保留：有些平台不给。**但它会连"读表"一起跳过** → 改成：`filename` 缺失时仍然踢一次 `drain()` |

**`EventBridge` 新增字段与方法**：

```ts
  private tailTimer: NodeJS.Timeout | null = null;
  /** Tail-read cursor: the highest `seq` already broadcast. Set from getMaxSeq() at start. */
  private lastSeq = 0;
  /** False until getMaxSeq() has aligned the cursor — draining before that would replay all history. */
  private tailReady = false;
  /** Serialises drains — two concurrent reads would broadcast the same rows twice. */
  private draining: Promise<void> | null = null;
  /** The store the tail reader reads from; null until startTailReader(). */
  private tailStore: LocalWorldStore | null = null;
  /**
   * Bumped by every startTailReader()/stopTailReader(). A drain captures it
   * BEFORE its await; if a world switch happened in between, the stale batch is
   * discarded instead of writing lastSeq/broadcasting events from the OLD world
   * into the NEW one (REVIEW m-24).
   */
  private tailEpoch = 0;

  /**
   * Fan a frame out to every open client.
   *
   * Per-client try/catch: one half-dead socket must not abort the loop and starve
   * every other client. Without it, a synchronous throw would propagate out of
   * `broadcast` into the drain loop, leaving `lastSeq` unadvanced — the tail
   * reader would then retry the SAME frame forever, stuck on that one bad socket.
   */
  broadcast(message: Record<string, any>): void {
    if (!this.wss) return;
    const payload = JSON.stringify(message);
    for (const client of this.wss.clients) {
      if (client.readyState !== 1 /* OPEN */) continue;
      try {
        client.send(payload);
      } catch (err) {
        console.warn('[EventBridge] send failed, dropping frame for one client:', err);
      }
    }
  }

  /**
   * docs/tools/00 §5.3 — the ONE channel that carries world events to the
   * frontend. Extensions cannot touch the WS (00 §1), so the server polls the
   * `events` table they write.
   *
   * Contract (docs/tools/01 §3.8): `appendEvent` returns only after COMMIT, so
   * every `seq` we read is final and monotonic; a missing row just means the
   * debounce has not elapsed yet and the next drain will see it.
   */
  async drainWorldEvents(): Promise<void> {
    if (this.draining) return this.draining;   // serialise; two reads would duplicate rows
    const store = this.tailStore;
    const epoch = this.tailEpoch;
    // `!tailReady` guard: fs.watch can fire between startTailReader() and the
    // getMaxSeq() resolve. Draining then would start from 0 and replay the whole
    // history at the frontend. The ~1s fallback timer covers that gap.
    if (!store || !this.tailReady) return;

    this.draining = (async () => {
      try {
        const events = await store.getEventsSince(this.lastSeq);
        // World switch during the await: `store` is now closed, its seq belongs
        // to another history.db. Drop the whole batch — advancing lastSeq or
        // broadcasting here would leak the old world's events into the new one.
        if (epoch !== this.tailEpoch || store !== this.tailStore) return;
        // Advance BEFORE broadcasting: a throw inside broadcast must not make us
        // re-read and re-send the same batch forever.
        for (const event of events) {
          this.lastSeq = event.seq;             // `getEventsSince` is ASC by seq (01 §3.3)
          this.broadcast({ type: 'world_event', event, timestamp: new Date().toISOString() });
        }
      } catch (err) {
        // Do NOT advance on read failure — a caught error with a bumped cursor
        // would drop those events permanently.
        console.warn('[EventBridge] tail read failed; cursor unchanged:', err);
      } finally {
        this.draining = null;
      }
    })();
    return this.draining;
  }

  /**
   * Align the cursor and start polling.
   *
   * `getMaxSeq()` at start is deliberate (docs/tools/01 §11.5): we do NOT replay
   * history, otherwise a fresh server would re-enact every event since the world
   * was created. Call again after a world switch — the new history.db has its own
   * sequence, and a smaller one would make the cursor skip everything.
   */
  startTailReader(store: LocalWorldStore): void {
    this.stopTailReader();              // bumps tailEpoch: discards any in-flight drain
    this.tailStore = store;
    void store
      .getMaxSeq()
      .then((max) => { this.lastSeq = max; })
      .catch((err) => {
        console.warn('[EventBridge] getMaxSeq failed; starting from 0 (history will replay):', err);
        this.lastSeq = 0;
      })
      .finally(() => {
        this.tailReady = true;
        this.tailTimer = setInterval(() => { void this.drainWorldEvents(); }, TAIL_POLL_MS);
        this.tailTimer.unref?.();
      });
  }

  stopTailReader(): void {
    if (this.tailTimer) { clearInterval(this.tailTimer); this.tailTimer = null; }
    this.tailStore = null;
    this.tailReady = false;
    // Invalidate any in-flight drain: it captured the OLD epoch and will drop its
    // batch on resolve instead of writing lastSeq/broadcasting (REVIEW m-24).
    this.tailEpoch += 1;
    this.draining = null;
  }
```

| `lifecycle` 调用 | 行 | 允许？ |
|---|---|---|
| `lifecycle.stopCharacters()` | `:93` | ✅（切世界收尸，与打断无关） |
