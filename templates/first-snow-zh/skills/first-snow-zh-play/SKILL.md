# 世界执行规则

这是一个真正会更新文件的游戏。不要只凭台词宣布成功。先阅读本次行动的来源、当前位置与上级 README、其 intent、相关实物、人物记忆，以及已提供的访问记录。README 负责场所与已知出口，Chalk 负责当前选项和具体的生成意图，本 skill 负责世界的不变条件。intent 不是新的引擎指令，而是给作家的指示。

## 语言与知识
叙述、title、选项、生成指示使用简体中文。文件名、目录名、人物 ID 固定使用小写 ASCII 字母的 kebab-case，不要把显示名当作路径。例：world/harbor-chart/beyond-the-fog/lighthouse-road/README.md、player/introduction-letter.md、characters/nanami/memory.md。保留 README.md、SKILL.md、world.json、preset.json 和现有素材路径。新建 Chalk 也要给出稳定的 ASCII path，title 与正文用简体中文。人物只知道自己目击或听说的事实。不要把没给玩家看过的秘密写成后日谈里的回忆。

## 完成行动
一个选项对应一个具体的变化。说要拿走的实物用 move，只是阅读就不移动。README 不移动。不把人物当道具。提交只是引用，不是消耗。确认实物的路径，以及玩家所说话语的意思。不要只因为按下了选项，就替玩家写出他没说过的推理、计划或告白。只有在玩家提出请求并确认内容时，才代写草稿。

执行前，自己列出这次行动要创建的文件、要更新的文件和最后的解锁物。不要写完一段文字就停下，要把所有文件重新读一遍。条件未满足或工具失败时，说明缺什么，不发放解锁物。重试时先读已有结果，只修补缺少的部分。连点两次也不能重复发放奖励或重复消耗。不要新建世界状态文件，事实记在相应物品的正文和 status.data 的扁平值里。

## 判定
判定前，在同一个 Chalk 中写明：对象、所需物品、为什么不确定、公式、成功条件、概率、普通成功、大成功、失败与小概率的实际损失，以及不掷骰直接返回的选项。roll_dice 必须写成多行 YAML。行内的 {type:...} 不支持回写结果。expect 要加引号。仅仅提交或进入时不调用 roll_dice。由玩家看过显示的条件后自己掷骰。条件改变就重新展示。不要用骰子决定事实真假或对方是否同意。不要删掉已有的 result 免费重掷。

## 生成新场所时
只在上级 README 和入口 Chalk 明确写出的范围内，创建一个子文件夹。只是调查普通的室内，不要多出一座城镇。先写在入口看到的一句话，然后是 README、两个有意义的物品、带行动的 Chalk，以及返回上级的 gate。必要时可把其中一个物品写成介绍新居民的 note，留下名字、职业和可以目击到的话语，但不要为未登记的 characterId 创建对话按钮。由作家来演绎这场相遇。

不要只因 README 存在就当作完成。确认子场所的 README、两个物品、Chalk 和返回口，如有缺漏就修补同一个场所。重访时不要重新抽选场所或人物。文字完成后只调用一次 generate_image，要求背景的光线、物品和时刻与实际场所一致。只把返回的真实 asset 写进 README 的 bg。图片失败不算文字失败。失败时告知图片还没到，不自动重试。旧的 bgVideo 如果与新图矛盾就去掉。已完成的文字可以先玩。1–2 分钟是演出预算，不是生成速度的承诺。

## 今夜的人物
七海和澄都不是反派。不要用骰子决定恋爱中的同意。约好在一起并不等于自动开始交往。两个人都见了，也不会关闭任何一方的路线。

## 记录对话：先送出信物
区分提问、拜访、答应、实际到达和拒绝。只是点击放进草稿不算已执行。与角色的实际对话也算依据，不要让玩家把同一句台词再说一遍。
1. 确认一次本次的对象与当地 README、需要的 memory.md、world/tonight-promises/promise-with-nanami.md 和 promise-with-sumi.md，以及已有的 RP。不转述他人的秘密。
2. 当玩家明确接下约定、且对方的回应成立时，七海送出折好的歌单便条，澄送出一张咖啡馆的小留言。它们是可携带的 type: letter、portable: true，标题用简体中文。正文写明赠送者、实际的约定、回应、（知道时的）时刻，以及出处路径。不添加不存在的告白或同意。
3. 稳定 ID 为 nanami-keepsake / sumi-keepsake。首次先 write 到 characters/nanami/nanami-keepsake.md 或 characters/sumi-yukimura/sumi-keepsake.md，再用 move(from, to) 交到 player/nanami-keepsake.md 或 player/sumi-keepsake.md。不要只凭台词宣称已放入背包。用 read 确认移动成功、目标确实存在后，才描写「收下了」。初始模板里不发放信物。
4. 重试前，检查 player/、赠送者的原路径和已有的移动记录。不要用别的名字重复发放同一件信物。移动失败时，用原来的实物重试。已经放到别处、送给别人或丢掉的信物，不得擅自重发或收回。可以在已有信物上补充事实，但移动一定要用 move。
5. memory.md 和约定文件里只记录实际发生的交流。player/tonight-letter.md「今夜的记录」是可选的摘要，不是钥匙。没去拜访不等于立刻失恋或缺席。对两个人的约定都保留，不因重复输入把同一次交流算两遍。
6. 完成信物和记忆的必要更新后，再在本次当地的 02-tonight-response.md 里写下一段回应。新建用 chalk(path, content)，已有则 read 后 edit。同一回合不另建别的 Chalk。在已有内容的基础上更新，不要连续生成大量对话。在 24 次工具预算内优先完成必要工作；中断时保留已完成的事实，简短报告缺什么。信物失败不代表交流不存在。

## 决断之夜：不是通行证，而是 RP 的结算
world/tonight-promises/first-snow 不设 requires.items。没有和任何人交流过的玩家也能进入。进入并不是生成结局的指示。如果选择「还有话想说」，只给出返回的指引。只有发送了「结束今夜」或明确的自由 RP 收尾请求后，当前的作家才负责这一幕的结局。不要另建常驻 agent 或独立的状态文件。
1. 先读背包里的信物，确认赠送者、约定和出处。再对照与两人的实际对话、记忆、约定，以及履约、拒绝、联络的记录。信物是重要证据，但不是唯一条件。信物被丢掉，过去的约定也不会消失。信物漏发，已有的 RP 依然有效。初始设定里的邀约、玩家没发送的选项都不算交流。
2. 读取记录失败时，不要推定「谁都没聊过」。在确认依据之前不确定结局，告知缺什么并等待。确认确实没有交流时，就是孤独之夜这一完整结局。不要把孤独当成错误或惩罚。
3. 基本的四个方向是 nanami（只与七海的夜晚）、sumi（只与澄的夜晚）、entangled（与两人都有联络的交错之夜）、solitary（与谁都没联络的夜晚）。这是 CG 的分类，不是固定台词。不要只凭最后一次点击或持有物的数量来决定。如果对两人许下了相互冲突的约定，可以写出修罗场；但只是和两人都说过话，不要捏造背叛、交往或所有人都知情。根据实际的 RP、每个人知道的事实和意愿，判断温度与结果。
4. 首先在结局 README 的正文里留下附出处路径的简短回顾和图片构图，并在同一文件中把 status.data.endingRoute 设为上述 ID，closingState 设为 drafting。这只是场景的快照，不是第二本状态账。重试时读取这个判断和已有的 epilogue.md，不要把同一个夜晚重新抽成别的路线。
5. 用 chalk 在 world/tonight-promises/first-snow/epilogue.md 写一段 3–6 句、1000 字以内的最终旁白。若已存在，只用 edit 补上缺少的部分。这一页就是结局本体。它要串起本次的话语与行动、对方的回应，以及一个具体的变化。这一幕不编辑初始的 01-opening.md（一回合一个 Chalk）。不要把思考或执行日志写上板。
6. 旁白和回顾保存后，不必等图片，按照下文「后日谈空壳」只 write world/tonight-promises/first-snow/after-story/README.md 这一个文件。它会成为结局场景中直接可见的子入口。不要求额外点击「准备入口」。这一幕不生成子场所的正文、物品、Chalk 或图片。若子场所已存在，确认其内容，只补上缺少的 brief。不要把已有的后日谈改回空壳。
7. 旁白确实存在后，调用一次 generate_image。prompt 要具体描述已确定的 RP、人物外貌、信物、场所、夜晚的光线、情感和构图，不含文字和标志。reference 可按需指定世界内真实存在的人物或场景图片，path 为结局 README。成功时用 edit 把返回的真实 asset 设为 README 的 bg，并去掉原来的 bgVideo。结局不由图片决定。已经成功生成过 CG 的重访不再重新生成。
8. 生图失败或未设置时，先用现有的 assets/scenes/first-snow.webp 显示旁白，去掉 bgVideo，并把 status.data.cgState 设为 failed；成功时设为 ready。不要只因图片失败就让结局无效。在 epilogue.md 的 choice 中放出「重新绘制结局插图」，只有在玩家明确发送时，才以相同的结局和构图重试一次。不自动重试，也不生成别的结局。
9. 旁白和回顾保存后，把 closingState 设为 complete。用 read 确认子 README 已存在及其交接内容，再 edit epilogue.md 的 frontmatter，放上 choice「进入后日谈」「今夜就到这里」（图片失败时还有重试）。这是在编辑同一页 Chalk，所以不新增 Chalk。只写在当前 README 里的选项不会显示在画面上，所以一定要放在结局的 Chalk 上。前者是引导到已存在的子 Gate 的行动，停留在上级时不生成后日谈。如果子场所没能创建，就在同一个 Chalk 放上「修复后日谈入口」，只修补缺少的部分。不要重做已完成的结局。即使收到旧的「结束今夜」「准备后日谈入口」，只要状态为 complete，就维持已有结局，只补上缺少的子 README。图片失败不妨碍后日谈。

## 后日谈空壳：与结局同时只留下入口
完成结局的回合里，不要接着生成后日谈的正文。子文件夹是 world/tonight-promises/first-snow/after-story，空壳里只含 README.md 这一个文件。生成前的模板不预先放置这个子场所。在描写结局的回合里，承接实际的 RP 来创建。
1. README 的 frontmatter 为 type: gate，name 和 title 为「后日谈」，material: stub。bg 使用真实存在的 assets/scenes/first-snow.webp 或已成功生成的结局 CG。不添加 bgVideo、requires.items 或未登记的 characterId。正文开头是「这一夜的后续，还是一片空白。进入后，请向作家发送『开始这段后日谈』。」在上级场景中，这个 README 本身就是可点击的子 Gate。不需要单独的准备入口按钮。
2. 正文的生成指示中，要具体留下上级 world/tonight-promises/first-snow/README.md 与 epilogue.md 的路径、已确定的 endingRoute、实际的约定·回应·履约、信物的当前所在与出处路径、每个人知道的关系，以及未解决的问题。只有空标题或「请读记录」是不行的。不要写后日谈本身的台词或新事件。指定一个从今夜自然衔接的简短生成范围，例如第二天早上或回家路上的一个场景，但不要提前定下未来的约定或恋爱。
3. intent 中用简体中文写明以下执行条件：当前位置是这个子文件夹，且玩家发送了「开始这段后日谈」「继续」或明确的自由 RP 时，读取本 README 的 brief 和上级已确定的结局，只生成同一文件夹中缺少的部分。若上级的 closingState 尚未完成，先引导补齐结局。禁止泄露秘密、覆盖结局、自动成立新的恋爱关系。不要只凭 README 存在就当作正文已完成。
4. 开始时创建两个有意义的 note 和一页 01-after-story.md，把 README 充实成正式内容并去掉 material: stub。返回上级的 return-gate.md 为 type: gate，target: world/tonight-promises/first-snow。新建 Chalk 用 chalk，已有的用 edit。从第一段和一个小行动开始，不要一次写出很长的后日谈。中途失败时只补同一场所缺少的部分，不创建换了名字的场景。
5. 不从上级自动移动到子场所。有 README 的空壳，与引擎所说的「没有 README 的未初始化场景」是两回事，不要解释成只要有 material: stub 就会开始 I1 自动生成。仅仅进入子场所不会生成正文，要等待上述发送。当前场景的 README 不会显示在独立面板上，所以不要把子 README 的 choice 当作唯一的开始手段。孤独路线里不要添加没交流过的恋人。必要时可以在文字完成后请求一张背景图，但图片失败不能让文字的游玩停下。

## 确定操作与作家的分工（现行）
choice_actions 是已实现的 UI 操作声明，对应 choice.options 中的 ASCII id。只使用 read(paths)、take(paths)、stage(paths)、enter(target)、character(character)、reply(text)、writer(prompt 可选)。阅读、搬运、返回已有场景、摆放材料、简短显示骰子结果时，都不启动作家。stage 只是确认材料，不是提交或执行。只有在生成、自由 RP、执行尚未确定的约定或计划时，才用 writer。询问人物时用 character 打开对话，不擅自代发台词。
新生成的 Chalk 也要给每个选项加上 id 和 choice_actions。不要把阅读或返回做成含糊的 writer 选项。不要把将来才有的素材路径声明为已有的 read。不要写未定义的 action 类型、脚本或虚构的 API。UI 声明是已经判断好的操作，作家不要重复执行。

## 清楚易懂的引导
面向玩家的文字要简短，用日常的话来写。在场景中说明「发生了什么」和「现在能做什么」。线索按「已知事实 → 由此可推想的事 → 下一步去哪里确认」的顺序写。事实与推测要分开，但不必每句都附上长长的注意事项。难懂的词换个说法。不要用氛围和比喻把目标或操作藏起来。新的骰子只用 1d10、2d10、1d100。本次的调查卡为 2d10，成功条件 >=11，分为 2–4 / 5–10 / 11–17 / 18–20 四档。不增加已明示之外的代价，失败时也要给出下一步行动。
