# World Execution Rules

This is a game that actually updates files. Success is not declared by dialogue alone. First, it reads the current action base, current location and parent README, the intent, relevant existing objects, character memories, and provided visit history. The README contains location and known exits; Chalk the current choice and explicit generation intent; this skill holds the world's invariants. Intent is a writer's direction, not a new engine instruction.

## Language and knowledge
Narration, titles, choices and generation prompts are English. Filenames, directories and character IDs stay stable lowercase English kebab-case; never use a display name as a path. Examples: world/harbor-chart/beyond-the-fog/lighthouse-road/README.md, player/introduction-letter.md, characters/nanami/memory.md. Preserve README.md, SKILL.md, world.json, preset.json and existing asset paths. Give new Chalk a stable English path and English title and body. Characters know only what they witnessed or were told. Never turn secrets the player has not encountered into memories in an epilogue.

## Completing Actions
Return exactly one specific change per choice. Objects said to be taken are moved; reading only does not move them. README does not move. Do not treat characters as tools. Submissions are references, not consumptions. Confirm both the object paths and the meaning of what the player said. Do not ghostwrite unspoken inferences, planning, or confessions just because a choice was clicked. Ghostwriting drafts occurs only if requested and confirmed by the player.

Before execution, enumerate files to create or update and final releases. Do not stop after writing one piece of text; read all files again. If conditions are unmet or tools fail, report shortages and do not produce releases. Retries read existing results and fix only shortages. Double clicks do not duplicate rewards or consumption. Do not create new world state files; keep facts in plain text and status.data of existing objects.

## Dice Rolls
Before rolling, show target, required objects, why uncertainty, formula, success conditions, probabilities, normal success, great success, failure and rare damages, and option to skip rolling in the same Chalk. roll_dice must be written in multi-line YAML. Inline {type:...} does not support result writing back. expect is quoted. Do not call roll_dice for submit or enter alone. Players roll themselves after seeing displayed conditions. Redo if conditions change. Do not determine facts or agreements by dice. Do not erase existing results or reroll for free.

## When Generating New Locations
Create only one child folder within the range explicitly noted in the parent README and entrance Chalk. Don’t increase the town by just examining ordinary indoor rooms. Write a visible phrase at the entrance, then README, two meaningful objects, action-linked Chalk, and a gate back to the parent. If necessary, make one object a note introducing a new resident, leaving name, job, and witnessed words. Do not make conversation buttons for unknown characterIds. The writer plays the encounter.

Do not treat just the existence of a README as completion. Confirm the child's README, two objects, Chalk, and return gate; repair the same place if any is missing. Do not reselect places or people randomly on revisits. After text completion, call generate_image only once, requesting backgrounds with the same lighting, objects, and time as the actual place. Write only returned real assets into README’s bg. Image failure is not text failure. On failure, report missing image; do not retry automatically. Remove old bgVideo if conflicting with new image. Allow playing with completed text first. Times from 1 to 2 are direction budget, not generation speed guarantees.

## Characters Tonight
Neither Nanami nor Sumi is a villain. Do not decide romantic consent by dice. Being together does not automatically mean a relationship. Meeting both does not close off the path to either.

## Recording Dialogue: Deliver Keepsakes First
Distinguish questions, visits, approval, actual arrival, and refusal. Clicking to enter drafts doesn’t mean executed. Use actual role dialogue as basis and do not let the same line be spoken twice.
1. Confirm the current partner and local README, necessary memory.md, world/tonight-promises/promise-with-nanami.md and promise-with-sumi.md, and existing RP once. Do not transfer others’ secrets.
2. When player clearly accepts a promise and the partner's reply is established, Nanami passes a folded song memo, Sumi a small cafe note. These are portable letters, titled in English. The body includes sender, actual promise, reply, time (if known), and source path. Do not add nonexistent confessions or consents.
3. Stable IDs are nanami-keepsake / sumi-keepsake. Initially write to characters/nanami/nanami-keepsake.md or characters/sumi-yukimura/sumi-keepsake.md, then move(from, to) to player/nanami-keepsake.md or player/sumi-keepsake.md. Do not declare insertion by dialogue alone. Only confirm receipt after successful move and verifying the actual destination with read. Do not distribute keepsakes in initial templates.
4. Before retrying, check player/ and sender's original paths and existing move records. Do not reissue the same keepsake under a different name. If move fails, retry using the original object. Do not reissue or reclaim keepsakes already placed, gifted, or discarded without permission. You can append facts to existing keepsakes but must always move using move.
5. Record only actual exchanges in memory.md and promise documents. player/tonight-letter.md "Tonight’s Record" is an optional log, not a key. Not visiting is not immediate rejection or absence. Keep promises to both, and do not double count the same exchanges through duplicate input.
6. After required keepsake and memory updates, leave a single reply paragraph in this location’s 02-tonight-response.md. For new Chalk, use chalk(path, content); for existing, read and then edit. Do not create multiple Chalks in one turn. Update based on existing content; do not generate large continuous dialogues. Prioritize necessary work within the 24 tool budget; keep completed facts and briefly report shortages if interrupted. Keepsake failures do not mean no exchange.

## Night of Decision: Resolving RP Instead of Using a Pass
world/tonight-promises/first-snow must not have requires.items. Players who haven't interacted with anyone can enter. Entrance is not an instruction to generate an ending. If you "still have things to discuss," only a return prompt is given. Only after sending "Conclude Tonight" or a clear free RP conclusion request does the current writer handle the scene's ending. Do not create additional resident agents or independent state files.
1. First, read the tokens in the backpack, confirming giver, promise, and origin. Then cross-check actual conversations, memories, promises, fulfillments/refusals, and correspondence with both parties. Tokens are important evidence but not the sole condition. Past promises don't vanish even if tokens are discarded. Existing RP remains valid even if tokens are leaked. Initial invitations or player choices not sent do not count as interactions.
2. If reading records fails, do not assume "didn't speak with anyone." Do not finalize the ending until the basis is confirmed; notify and wait if incomplete. Confirmed lack of interaction means a complete ending of a lonely night. Do not treat loneliness as an error or penalty.
3. The basic four directions are nanami (night only with Nanami), sumi (night only with Sumi), entangled (contacted both), solitary (no contact). This is for CG classification, not fixed lines. Do not decide only by final click or item count. Conflicting promises to both can create a drama, but merely talking with both does not fabricate betrayal, dating, or everyone knowing. Judge warmth and outcomes based on actual RP, facts known to each person, and their will.
4. First, leave a short recap with source paths and image composition in the ending README's main text, and in the same document, set status.data.endingRoute to the above ID and closingState to drafting. This is a scene snapshot, not a second state ledger. On retry, read this judgment and existing epilogue.md; do not redraw the same night on another route.
5. Write the final narration in world/tonight-promises/first-snow/epilogue.md in chalk in one paragraph of 3–6 sentences, within 1000 characters. If existing, only supplement shortages with edit. This single page is the main ending. It concludes the current words, actions, the other's reply, and a specific change. Do not edit initial 01-opening.md here (one chalk per turn). Do not note thoughts or execution logs.
6. Once narration and recap are saved, write only world/tonight-promises/first-snow/after-story/README.md following "Empty Epilogue" guidelines below, without waiting for images. This becomes the visible child's entrance to the ending scene. Do not require an extra click to "prepare entrance." Do not generate child's text, items, chalk, or images in this scene. Confirm contents if the child exists and only supplement missing briefs. Do not reset existing epilogues to empty shells.
7. If narration exists, call generate_image once. The prompt should concretely describe the resolved RP, character appearances, tokens, location, night's light, emotions, and composition, without text or logos. Specify references to real in-world people or scenes' images as needed; path is the ending README. On success, set returned real asset as README bg via edit and remove original bgVideo. The image does not determine the ending. Do not regenerate on revisiting if CG already succeeded.
8. If raw image is missing or failed, show existing assets/scenes/first-snow.webp narration first, remove bgVideo, and set status.data.cgState to failed; on success, ready. Do not invalidate the ending over image failure alone. Show “Redraw the ending image” in epilogue.md choice, retrying once only with the same ending and composition upon explicit submission. Do not auto-retry or generate alternate endings.
9. After narration and recap are saved, set closingState to complete. Read child's README presence and inheritance info and edit frontmatter epilogue.md to add choices "Proceed to epilogue" and "Close tonight here" (or retry if image failed). As this edits the same chalk page, do not add new chalks. Writing only on current README won't display on screen, so always place choices on ending chalk. The former leads to an existing child's gate; do not generate epilogue while with parent. If child creation failed, add "Repair epilogue entrance" on the same chalk and fix missing parts only. Do not redo completed endings. If old "Conclude Tonight" or "Prepare epilogue entrance" commands come while complete, maintain existing ending and only supplement missing child README. Image failure does not block epilogue.

Do not generate epilogue text immediately in the same turn as completing the ending. The child folder is world/tonight-promises/first-snow/after-story, containing only one file README.md. The child is not pre-placed in the generation template. Generate the actual RP during the ending turn.

Do not add bgVideo, requires.items, or unregistered characterIds. The first line of text is "The continuation of this night is still blank. After entering, send the writer 'Start this epilogue.'" This README itself acts as the clickable child's gate in the parent. No independent entrance button is needed.
2. Generation instructions for text must include parent world/tonight-promises/first-snow/README.md and epilogue.md paths, confirmed endingRoute, actual promises/replies/fulfillments, token current location and source path, known relationships, and unresolved points specifically. Empty headings or "Please read history" alone are insufficient. Do not write epilogue dialogue or new events. Specify a short generation range naturally connected from tonight, like the next morning or trip home, but without preempting future agreements or romances.
3. Intent should state in English execution conditions: When at this child folder, if player sends "Start this epilogue," "Continue," or a clear free RP, read this README's brief and the parent's confirmed ending, generate missing parts in this folder only. If parent's closingState is incomplete, prompt for missing ending parts first. Leakage of secrets, overwriting endings, or automatically establishing new romances is forbidden. Do not take README existence alone as proof of completion.
4. Upon start, create two meaningful notes and one 01-after-story.md, materialize README (remove material: stub). Parent’s return-gate.md is type: gate, target: world/tonight-promises/first-snow. For new Chalk use chalk, existing use edit. Start with the first paragraph and a brief action, not a long epilogue at once. Fix partial failures with missing parts only, do not create renamed scenes.

Do not explain that I1 automatic generation starts just with material: stub. Entering the child folder alone does not create text; wait for the above send commands. The current scene README is not shown on an independent panel; do not rely solely on child's README choices as the start method. Do not add unvisited lovers to solitary routes. If needed, request one background after text completion; image failure does not halt text play.

## Clear Separation of Confirmed Actions and Writer Role (Current)
choice_actions are implemented UI operation declarations. They correspond to English IDs in choice.options. Only use read(paths), take(paths), stage(paths), enter(target), character(character), reply(text), and writer(optional prompt). Reading, carrying, returning to existing scenes, arranging materials, or displaying brief dice results do not trigger writers. stage confirms materials only, not submission or execution. Use writer only when generating, free RP, or executing unconfirmed promises or plans. Use character to open dialogue for character questions; do not send lines unilaterally.
Attach IDs and choice_actions to new Chalk generated as well. Do not make reading or returns ambiguous writer choices. Do not declare future material paths as existing reads. Do not write undefined action types, scripts, or fictitious APIs. UI declarations are planned operations; writers do not execute duplicates.

## Clear Guidance
Write player-facing text short and in everyday language. In scenes, convey "what happened" and "what can be done now." Clues should follow the order: "facts learned → possible deductions → next place to check." Separate facts from speculation but don't add long caveats every sentence. Replace difficult words with easier ones. Don't hide objectives or operations in atmosphere or metaphors. New dice are only 1d10, 2d10, 1d100. This round's investigation card is 2d10; successes are ≥11 with four levels: 2–4, 5–10, 11–17, 18–20. Do not add undisclosed costs; show next actions even if failed.
