# 世界执行规则

这是真正更新文件的游戏。不要只靠台词宣布成功。先阅读本次行动的来源、当前所在地及其上级 README、其中的 intent、相关实物、人物记忆，以及提供的既往访问记录。README 记载地点与已知出口，Chalk 记载当前的选择与具体的生成意图，本 skill 记载世界的不变条件。intent 不是新的引擎命令，而是给作家的指示。

## 语言与知识
叙述、title、选项与生成指示均使用简体中文。文件名、目录名与人物 ID 固定为小写 ASCII kebab-case，不要把显示名称用作路径。例：world/harbor-chart/beyond-the-fog/lighthouse-road/README.md、player/introduction-letter.md、characters/nanami/memory.md。保留 README.md、SKILL.md、world.json、preset.json 以及已有的素材路径。新建的 Chalk 也要给出稳定的 ASCII path，title 与正文使用简体中文。人物只知道自己目击或听说的事实。不要把玩家没有接触过的秘密写成后日谈里的回忆。

## 行动的完成
每个选择返回一项具体的变化。被说要拿走的实物用 move，只是阅读则不移动。README 不移动。不要把人物当作道具。提交是引用，不是消耗。确认实物的路径，以及玩家所说的含义。不要仅因按下了选项，就代写玩家没说出口的推理、计划或告白。只有在玩家委托并确认了内容时，才代写草稿。

执行之前，自己先列出这次行动要创建的文件、要更新的文件和最后发放的物品。不要写了一段文字就中途结束，要把所有文件重读一遍。条件未满足或工具失败时，说明缺少什么，不发放奖励物。重试时先读已有结果，只修补缺少的部分。不要因为双击而重复发放奖励或重复消耗。不要创建新的世界状态文件，而是用相应物品的正文和 status.data 中的扁平值记录事实。

## 判定
判定之前，在同一张 Chalk 中写明：对象、所需物品、为什么不确定、公式、成功条件、概率、普通成功、大成功、失败与小概率的实际损害，以及不掷骰返回的选项。roll_dice 必须写成多行 YAML。行内的 {type:...} 不支持回写结果。expect 要加引号。仅提交或进入时不调用 roll_dice。由玩家看过显示的条件后自己掷骰。条件改变时要重新出示。不要用骰子决定事实真伪或对方是否同意。不要删掉已有的 result 来免费重掷。

## 生成新地点时
只在上级 README 和入口 Chalk 明确给出的范围内，创建一个子文件夹。只是调查普通室内时，不要新增城镇。先写入口处可见的一句话，再写 README、两件有意义的物品、带行动的 Chalk，以及返回上级的 gate。必要时，可以把其中一件物品写成介绍新住民的 note，留下名字、职业和可被目击的言语；不要为未注册的 characterId 创建对话按钮，由作家来演绎这场相遇。

不要只凭 README 存在就当作完成。确认子文件夹的 README、两件物品、Chalk 和返回口，有缺少就修补同一地点。重访时不要重新抽取地点或人物。文字完成后只调用一次 generate_image，要求背景与实际地点的光线、物品、时刻一致。只把返回的真实 asset 写入 README 的 bg。图片失败不算文字失败。失败时告知图片尚未送达，不自动重试。旧的 bgVideo 若与新图矛盾就移除。已完成的文字可以先玩。1–2 分钟是演出预算，不是生成速度的承诺。

## 雾坞镇的真相与短程目标
无人船是诱饵。领主家的账簿、旧海关隧道和熄灯的十二分钟连在一起。老莫不知道追踪船的存在。不要把薇拉的舵扣件和银鸢的空箱，轻易变成犯人的自白。

## 第二次 Hybrid 判定
根据内容确认在 world/harbor-chart/02-two-wakes.md 提交的两项以上独立观察与方法。同一记录的副本不算作两项。实物的位置按移动记录追踪。留下采用的证据路径和简短理由。若妥当，创建 world/harbor-chart/03-lighting-terms.md，写明准备确认与选项。若还没有灯油，引导前往灯塔。不要先放出谁都能按的骰子。

本 Demo 的候选条件：2d10，expect 为 ">=11"。雾与摇晃的落脚处是不确定的原因。2–4 为 6/100（6%），失败，并失去所持灯油一次的量。5–10 为 39/100（39%），失败但无消耗，可以通过其他观察修正方法。11–17 为 49/100（49%），普通成功，发现第二艘船的轮廓和安全的岸边小路。18–20 为 6/100（6%），大成功，另外获得一封能在下一座城镇得到协助的介绍信。合计成功率 55%。判定的是当场发现的成败，而不是既有真相。大成功与引擎的 crit（全部最大点数）不是一回事。

最初的预告放置 choice“按此条件准备判定”“不掷骰，返回调查”。获得同意后，再把同一条件的 roll_dice 以多行 YAML 追加到同一张 Chalk 中。type 为 "2d10"，desc 为“用投光确认雾的另一边”，expect 为 ">=11"。仅凭同意不调用 roll_dice 工具，等待玩家操作骰子。灯油不仅要看文件名，还要在正文中确认是否还剩一次的量。

## 掷骰后也不会停下的 Chalk
1. 准备骰子时，把同一张 Chalk 的 choice 更新为“根据点数行动”“返回调查”。正文写上“掷骰后，可以从这张卡继续选择。失败就去看脚下的线索，成功就去看光的前方”，并保留上面的四档结果。intent 中必须写上对本节的引用，以及判定来源 world/harbor-chart/03-lighting-terms.md。这是从已有 choice 回到作家的入口。即使只显示了点数，也不必一直等待。还没有 result 时就按了继续，只简短说明尚未判定，不代为掷骰，也不消耗、不生成。
2. 在作家能读取 result 的下一次行动中，应用已公开的四档结果。不改变点数、expect 和采用的证据。先用一两句话在同一张 Chalk 中说明有无实际损害和接下来能做什么。不强制要求长篇结果文、图片或场景转换。损害不等图片，先反映到实物上。在判定来源的 status.data 中以扁平值记录 rollOutcome（failure / success / great-success）、oilLossApplied（true / false）、revealState（pending / revealed，仅成功时）。这是作家的记录，不是引擎命令。重读实物与记录，从中途停止处恢复时只修补缺少的部分。若已是空瓶，不要第二次扣除灯油。
3. 若为 2–4，把 player/lamp-oil.md 的正文更新为失去一次灯油的空瓶，并保留一个 portable 的空瓶。简短写出“光断了，瓶里已经没有油。还看不见船，但能读出脚下的潮水痕迹”。若为 5–10，不减少灯油，写“雾把光推了回来。油还在。换个角度再确认吧”。两种情况的 choice 都是“对照潮痕与日志”“找薇拉商量方法”。不要只写“失败了”“继续调查吧”就结束。不要把判定前专用的“不掷骰，返回调查”留作判定后唯一的选项。
4. “对照潮痕与日志”不需要灯油，也不需要重新判定。把已读过的水位痕迹与灯塔日志实际对照，缺少的记录就引导到具体的已知地点。对齐后，在 world/harbor-chart/tide-route-note.md 中写下旧海关一侧下一个要确认的地点，并给出步行调查那里的 Chalk。不要写已发现安全的岸边小路，也还不发放第二艘船、介绍信和新城镇。只有玩家选择那次步行探索时，才可以在 world/harbor-chart/tidal-approach/ 生成一个小型调查场景。那是调查落脚处和潮水痕迹的地方，不同于仅限成功的捷径。备齐 README、两件物品、可选择下一步观察的 Chalk 和返回港口的出口，让调查能从新现场的观察继续下去。不要把失败换成免费的成功，也不要归还失去的灯油。找薇拉商量处理的是实际的方法修正，不要把它当作抹掉同一个 result 的借口。
5. 11–17 与 18–20 先设为 revealState: pending，放一句类似“光捕捉到了某个轮廓，可以靠近确认”的话，以及 choice“确认光的前方”“返回调查”。18–20 可以简短预告还有通往接应的线索在等着。此阶段不做完整的发现、子文件夹、背景生成，也不发放介绍信。即使是大成功，也不自动切换镜头或场景。
6. 只有成功的判定来源上的“确认光的前方”，或成功后按下的、已准备好的“根据点数行动”，才会打开完整的发现。若选“返回调查”，只结算未处理的损害，成功保持 pending，留待之后选择。点击时重读同一个 result 与公开条件，写出第二艘船从雾中出现的简短 Punch Line，并创建 world/harbor-chart/beyond-the-fog/README.md、两件物品、“沿岸边小路走”的 Chalk 和返回港口的出口。只有 18–20 时，才创建一封 player/introduction-letter.md，写明基于本次证据的接应。11–17 不给这项额外奖励。确认存在后记录 revealState: revealed。再次点击时引导到同一个入口，中途失败只修补缺少的部分。生成步骤依照上面的“生成新地点时”，先完成文字。1–2 分钟的生成从这里开始。完成后也不自动进入，让玩家自己选择入口。

## 雾的另一边
世界不会结束。只有选择“沿岸边小路走”时，才在 world/harbor-chart/beyond-the-fog/ 下生成一个新的道路与城镇入口，使用稳定的 ASCII 目录 ID 和简体中文 title。包括 README、两件物品（其中一件可以是当地住民）、Chalk、返回口和一张背景图。若确实持有介绍信，就把它反映为具体的协助。不要一次建好整座下一个城镇。刚失败后或成功后尚未点击时，不要抢先创建这个成功用的入口。

## 确定操作与作家的分离（现行）
choice_actions 是已实现的 UI 操作声明，对应 choice.options 中的 ASCII id。只使用 read(paths)、take(paths)、stage(paths)、enter(target)、character(character)、reply(text)、writer(prompt 可选)。阅读、搬运、返回已有场景、摆放材料、简短显示骰子结果时，不启动作家。stage 只是确认材料，不是提交或执行。只有在生成、自由 RP、执行尚未确定的约定或计划时，才使用 writer。询问人物时用 character 打开对话，不擅自发送台词。
新生成的 Chalk 也要为每个选项加上 id 和 choice_actions。不要把阅读或返程做成含糊的 writer 选项。不要把未来的素材路径声明为已有的 read。不要写未定义的 action 类型、脚本或虚构的 API。UI 声明是已判断好的操作，作家不重复执行。

## 骰子代为解读（现行，与手动解谜并行）
各调查地点与地图的 04-investigation-dice.md，是由角色代替玩家把观察串起来的路线。现实中的玩家不需要说出正确答案。可以直接选择地图上的判定，各地点的判定也没有必须遵守的顺序。真相是固定的，点数改变的是发现的方法、代价和余裕。dice_outcomes 通过现有的动作层，把四档简短结果和下一步的 choice_actions 反映到同一个文件中。作家不重复反映、不重新判定、不追加收费。
这条路线不要求“两项独立证据”或“推理与计划两份文档”。旧规则中的这些要求只适用于手动提交路线。即使点数低，也能得到立足点和下一步行动。只有在明确要求根据地图结果生成新场景或结局时，作家才生成。不要把尚未发现的人物当作已经交谈过，要区分读到的推理与对话记录。不要把等待生成当作骰子失败。

## 简明的引导
给玩家看的文字要简短，用日常用语。场景中要传达“发生了什么”和“现在能做什么”。线索按“查明的事实 → 由此能想到的事 → 下一个要确认的地点”的顺序写。事实与推测要分开，但不必每句都附上长长的注意事项。难懂的词要换个说法。不要用营造气氛的比喻掩盖目的或操作。新的骰子只用1d10、2d10、1d100。本次的调查卡为2d10，成功>=11，分2–4/5–10/11–17/18–20四档。不增加已明示的代价，失败时也要给出下一步行动。
