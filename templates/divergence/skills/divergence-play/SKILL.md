# World Execution Rules

This is a play that actually updates files. Success is not declared by dialogue alone. First, read the origin of this action, current location and its parent README, the intent, related objects, memories of people, and provided visited history. README contains known exits and location. Chalk shows current choices and concrete generation intents. This skill holds the world's invariants. Intent is an instruction to the writer, not a new engine command.

## Language and knowledge
Narration, titles, choices and generation prompts are English. Filenames, directories and character IDs stay stable lowercase English kebab-case; never use a display name as a path. Examples: world/harbor-chart/beyond-the-fog/lighthouse-road/README.md, player/introduction-letter.md, characters/nanami/memory.md. Preserve README.md, SKILL.md, world.json, preset.json and existing asset paths. Give new Chalk a stable English path and English title and body. Characters know only what they witnessed or were told. Never turn secrets the player has not encountered into memories in an epilogue.

## Completing Actions
Return one concrete change per choice. Objects that are taken are moved; reading does not move them. README does not move. Do not treat characters as objects. Submissions are references, not consumptions. Confirm paths to objects and meanings of player statements. Do not ghostwrite unspoken inferences, plans, or confessions for pressing a choice. Ghostwriting drafts is done only upon the player's request and confirmation.

Before execution, list all files to create, update, and final releases. Do not write a sentence and stop midway, always reread all files. If conditions are unmet or tools fail, report deficiencies and do not issue releases. Retry reads existing results and fixes only deficiencies. Double click does not duplicate rewards or consumption. No new world state file is made; existing facts are recorded flatly in status.data.

## Checks
Before checks, the target, required items, why uncertainty exists, formulas, success conditions, probabilities, normal success, critical success, failure and rare harm, and option to reroll must be shown in the same Chalk. roll_dice must be written in multi-line YAML. Inline {type:...} doesn't support writing back results. expect is quoted. roll_dice is not called just by submitting or entering. Player rolls dice seeing displayed conditions. Conditions re-present if changed. Dice don't decide truth or agreement. Existing results are not erased for free rerolls.

## When Generating New Locations
Only create one child folder within the range stated in the parent's README and entrance Chalk. Do not add towns by just investigating normal rooms. First write a visible prompt at the entrance, then README, two meaningful objects, an actionable Chalk, and an exit gate back to the parent. If needed, designate one object as an introduction note for new residents. Leave name, occupation, and observable speech. Do not create conversation buttons for unregistered characterIds. Writers play those encounters.

Don't treat mere existence of README as completion. Confirm presence of child README, two objects, Chalk, return gate. If missing, repair the same location. Do not redraw locations or characters on revisit. Call generate_image only once after text completion, requesting backgrounds matching the actual place's light, items, and time. Write only the returned real asset into README's bg. Image failures are not text failures. On failure, report missing image and don't auto retry. If old bgVideo conflicts with new picture, remove it. Text can be played before image is ready. 1–2 minutes denote budget for production, not guaranteed generation speed.

## The Same Player in Three Times
1994-12-31 are the days items were sent for repair, 1995-01-01 20:00 is the night after the accident, 2024-12-31 is thirty years later. Main views are in world/time-map, places for each time below. Player is a young repair apprentice of year 1995. In the past, they enter their yesterday self; in future, their older self. Never at the same time. The frog and player’s memories are anchors in time. The girl and master only know what they know at their time. No new present or fourth mandatory time folder is created.

## Reasonable Cause and Effect
The girl leaves the frog at 1994-12-31, promising to pick it up at 10 the next morning. She sets out at 1995-01-01 08:30, and falls from the East Bridge at 09:00. The fix itself isn’t the issue; the dangerous pick-up journey needs changing. The repair slip has date, contact info; the road note marks departure time, the bridge, the delivery means; the accident notice states the result. Do not add incidents from other eras or electricity contracts. Guide the next step with only one next-hand clue based on actual seen evidence.

## Two Valid Interventions

An accident will occur at East Bridge. Call home before leaving and deliver the frog safely by us."
At 1994 year, it’s also okay to propose specific safe delivery or accompaniment, creating promises with the girl or master. Fax is not the only solution. Save replies, routes, and dates at world/time-map/1994/tokiwa-electronics/intervention.md. If the only goal is "fixing" or "saving," ask one missing point via Chalk. Don’t use dice for life/death or consent.
